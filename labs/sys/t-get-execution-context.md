# get_execution не отсекает contextData

Суть: `get_execution` с `nodeNames` и `truncateData:1` не убирает contextData — фильтры ограничивают число элементов, но не размер содержимого узла. Режим `tail` не спасает: запрос хвоста в 3 000 символов вернул полный MAINT_HANDOFF на 138 КБ (исполнение 49582). Единственная работающая защита — размер результата: свыше ~50 КБ харнесс кладёт ответ на диск, и контекст сессии остаётся цел.

Третий прецедент 2026-09-15: `get_execution` для Git Commit Files (исполнение 62042, коммит четырёх файлов) с `nodeNames:[15_Build_Result]` и `truncateData:1` вернул ~40 КБ contextData — дерево репозитория и заголовки GitHub; это ниже порога сохранения на диск, так что защита порогом не сработала и всё легло в контекст. Обход записан в `registry/tools.md` (строка git-commit): статус через `includeData:false`, факт записи — Git Log + Git Read либо fetch клона.

Следующий шаг: воспроизведено 2026-09-13 при чтении SYS_INDEX — запрос узла ответа вернул 212 898 символов и был сохранён на диск автоматически. Это подтверждает и механизм, и защиту. Внести строку в Skill `google-drive-docs` как класс (б) уточнения §11.

Условие снятия: строка стоит в Skill и называет оба факта — фильтры не режут contextData, спасает только порог сохранения на диск.

Ссылки: исполнения 49582 (2026-08-26) и 60994 (2026-09-13); Skill `google-drive-docs` §9, §11; источник — Зона А SYS_INDEX, строка 362.
