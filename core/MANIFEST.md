# Состав CORE в репозитории — из чего складывается канон и что значит «прочитан целиком»

Заведён 2026-09-06. Причина — Т-25 журнала `projects/git-migration/LOG.md`: сессия, читающая CORE через git, не может узнать, из чего CORE состоит. Канал чтения (воркфлоу `git-read`) отдаёт файл по имени, а на каталог отвечает отказом; списка имён в репозитории не было ни одного.

Редакция 2 от 2026-09-06 (наряд Н-06.09-04): из списка убраны три монолита `core/R-02.md`, `core/R-06.md`, `core/R-12.md` — они удалены из ветки тем же коммитом, что правит этот файл. Второго носителя разрезанных разделов больше нет: их содержимое целиком лежит в подфайлах `R-02a…d`, `R-06a…d`, `R-12a…g`, а адрес источника в истории записан в `meta/MAP_core-sections.md`.

Редакция 3 от 2026-09-10 (решение Р-66 журнала `projects/git-migration/LOG.md`): из списка убраны `core/R-01.md`, `core/R-02a.md`, `core/R-02b.md`, `core/R-02c.md`, `core/R-02d.md`, `core/R-14.md` — они удалены из ветки тем же коммитом, что правит этот файл. Это реестры, а не правила: Раздел 1 (веса и карточки проектов) теперь в `registry/projects.md`, Раздел 2 (идентификаторы документов Drive) — в `registry/documents.md`, Раздел 14 (реестр протоколов) — в `registry/protocols.md`; блоки перенесены побайтово предыдущими коммитами той же сессии. Ссылка «CORE Р.1 / Р.2 / Р.14» разрешается через `meta/MAP_core-sections.md`.

Критерий состава с редакции 3: в список входит только то, что нужно любой сессии любого проекта в момент чтения CORE. Реестр, из которого берут одну строку в момент использования, и материал с единственным читателем в список не входят.

## Кто это читает

Мастер-промпты проектов (с закрытия ф3, 2026-09-06): шаг «прочитать CORE» = прочитать этот файл, затем все файлы его списка, список берётся из текста этого файла. Поэтому состав CORE меняется правкой одного этого файла, без правки мастер-промптов.

## Что значит «CORE прочитан целиком»

Прочитаны `meta/header.md` и все 18 файлов списка ниже.

Признак для отчёта сессии — три величины сразу:

1. число прочитанных файлов списка;
2. путь последнего файла списка;
3. blob sha этого файла — из ответа `git-read`, а не отсюда.

Blob sha в этом файле намеренно не записан. Прежняя формулировка признака (число файлов и последнее имя списка) списывалась с самого манифеста: сессия, прочитавшая один этот файл и ни одного другого, называла обе величины верно и потому не доказывала ничего. Величина, доказывающая чтение, обязана лежать вне текста, который сессия и так держит в руках; blob sha приходит только в ответе канала на конкретный путь. Если он появится в таблице ниже — признак снова перестанет что-либо доказывать.

Blob sha здесь не контрольная сумма содержимого и запрету Б-1 не противоречит: он доказывает, что вызов чтения по этому пути состоялся, а не что файл цел.

Хвостовой пароль-канарейка признаком полного чтения в git-форме НЕ является. Канарейка работала, пока канон был одним документом: пароль стоял в последних байтах, и назвать его мог только тот, кто дочитал до конца. Набор из многих файлов концом не обладает, а отдельный файл с паролем доказывает ровно одно — что прочитан этот отдельный файл. Файла с паролем в репозитории нет: `meta/canary.txt` удалён 2026-09-07 по позиции I-1 очереди обслуживания. Он не был частью CORE и проверкой не служил; его собственный маркер называл пароль `HEMD` при теле `FORM`; и он был единственным местом в репозитории, где литерал якоря стоял в угловых скобках — вопреки запрету PW-ЯКОРЬ от 2026-08-07. Содержимое читается из истории по `ref` родительского коммита `edb90528a73e3443dab3845b103af7c07f2fa67b`.

Контрольных сумм и байтовых пломб этот файл не хранит намеренно: запрет Б-1 — контрольная сумма и число байт не доказывают ни целостности, ни потери. Размеры ниже даны для оценки стоимости чтения, не для проверки.

## Ведение
