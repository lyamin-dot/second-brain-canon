Р-43 | В СИЛЕ | 2026-09-06 | как канал git-commit удаляет пути
  принято: необязательное поле тела deletes: ["путь", …]; каждый путь уходит в запрос дерева записью {path, mode, type:"blob", sha:null}, content для них не требуется. Валидация путей та же, что у files: пустой путь и сегмент ".." отбиваются; дубли внутри deletes и путь, встречающийся и в files, и в deletes, отбиваются на stage=validate_payload. Существование пути проверяется ДО записи по рекурсивному дереву коммита expectedSha; отсутствующий путь даёт success:false со stage=delete_check. files стал необязательным при непустом deletes — единственное изменение в поведении files. Паспорт 1cw8g7TS84v6qggNU-Su_zIhvoKwJywG-Z1PJ-eGT_Jk обновлён (Зона А, Зона Б, ADR), 13 186 Б, checkSum f53dd077
  почему: §2a.7 и запрет 8 second-brain-git требовали DELETE, которого канал не имел (Т-28). Проверка существования вынесена до записи, потому что GitHub на sha:null для отсутствующего пути ошибку не гарантирует — без проверки удаление могло бы отчитаться успехом, ничего не удалив
  отвергнуто: положиться на ответ GitHub при sha:null (риск тихого no-op); отдельная новая нода под чтение дерева (новая HTTP-нода из MCP не получает credential вообще); слить чтение дерева в 09_Create_Blobs первым item (одна нода с двумя разными вызовами не читается на графе)
  DoD, ответы дословно: (1) git-commit deletes:["registry/_probe-delete.md"] → success:true, stage "update_ref", commitSha f82e4b6ec4e67e99f75609536ff597844d89932b, newHeadSha тот же, deletePaths ["registry/_probe-delete.md"], deleteCount 1, paths [], fileCount 0, reason null. (2) git-read registry/_probe-delete.md без ref → success:false, reason "git-read failed: {\"error\":\"The resource you are requesting could not be found\"}", text null, sha null, byteLength 0. (3) git-read того же пути с ref 0b28c8aa1a04b340c9c75da9a37172510f27782e (родительский коммит) → success:true, sha 12f71380e408767b01f1cac5d4bf85be4632694c, byteLength 165
  вывод сессии (не факт источника, проверяется ответами (1) и (2) выше): слабое звено замысла снято — n8n не выбрасывает null-поле при сериализации jsonBody, иначе второй вызов вернул бы файл, а не отказ
  расхождение с DoD: reason второго ответа не содержит подстроки "file not found". Git Read классифицирует отказ регуляркой /not found/i, а нода GitHub отдаёт "could not be found" — регулярка не ловит. Ветка "file not found: path=…" в Git Read, судя по этому, мёртвая. К каналу удаления отношения не имеет; правка Git Read в рамку наряда не входит и вынесена как долг
