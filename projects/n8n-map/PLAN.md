Бюджет чтения этого PLAN.md — отступление по second-brain-git 4.6, основание Р-3: до 48 КБ вместо 10 240 Б (после этой правки файл весит около 46,8 КБ). Целиком файл читает один раз сессия фазы Ф1, которая пишет строитель: ей нужны вместе разделы 3, 4, 5 и 7. Сессии фаз Ф3 и Ф4 читают только свой раздел — сначала заголовки (`grep -n '^## '` клоном или Git Read Lines с pattern `^## `), затем диапазон строк раздела. Цель. Любой вопрос о составе и связях воркфлоу инстанса https://liamin-n8n.duckdns.org решается одним чтением одного места, а не обходом воркфлоу. Сведения вычисляются из JSON воркфлоу при каждом обновлении, руками не заполняются.

Инварианты проекта.
- ИН-1. В снимке только поля, выводимые из ответа n8n. Поле, которого нет в ответе, в снимок не попадает; оно остаётся в паспорте (раздел 7).

- ИН-3. Новых расписаний, мониторов, сигналов и порогов нет. Обновление идёт тем же ежедневным запуском 05:30, который уже существует.
- ИН-4. Каждое сведение живёт в одном носителе (И-1 second-brain-git). Если снимок делится на открытую и закрытую части, поле лежит только в одной из них.

## 3. Модель данных

Источник строителя — ответ `GET /api/v1/workflows` публичного API. Его уже вызывает Registry Sync узлом «Получить список воркфлоу n8n» по `localhost:5678`, с курсором и credential `monitor_key_v2` (Z-1). Сессия этот API не видит: прокси отбивает запрос (Z-12). Поэтому у каждого поля две отметки:
- **MCP** — поле подтверждено в ответе get_workflow_details или search_workflows;
- **API** — поле подтверждено в ответе публичного API.

Отметка API без зонда стоит «не проверено». Закрывает её фаза Ф1 (раздел 8).

Чего вывести нельзя.
- **ID динамический.** Документ приходит во входе вызова (gdocs-read, Z-5) или читается из таблицы настроек. Снимок пишет «динамический» и имя узла; сам ID не пишет. Для инструментов записи и чтения Docs это штатно: какой документ они трогают, знает вызывающий, а не граф.
- **Привязка credential.** get_workflow_details не отдаёт ключ `credentials` ни у одного узла: проверено у 9 воркфлоу (Z-1, Z-5, Z-7, Z-8, Z-10; engineering-manual R1a). Отдаёт ли его публичный API, не проверено: запрос из сессии отбит прокси (Z-12), сохранённых исполнений Registry Sync нет (Z-4). Ф1 отвечает на это одним вызовом.
- **Проект без паспорта.** В n8n один проект, personal (Z-11). `parentFolderId` и `tags` пусты у всех прочитанных воркфлоу (Z-1, Z-5, Z-7, Z-8). Проект выводится только из имени паспорта; у воркфлоу без паспорта (56 из 111) проект автоматически недостижим.
- **Внешние вызывающие.** Сессии Claude через MCP (R15), кнопки Apps Script, внешние сервисы в JSON инстанса не видны. На В3 снимок отвечает только про вызовы изнутри n8n.
- **Идёт ли воркфлоу на самом деле.** Успешные прогоны не хранятся: Registry Sync отработал 2026-09-23T03:30Z (Z-3), а search_executions по нему пуст (Z-4). Это вопрос наблюдения, и он вне рамки ИН-3.

## 4. Носитель и формат снимка

Формат — одна строка на факт, поля через `|`. Поиск по любому полю — один grep клоном или один вызов Git Read Lines с pattern. Обратные указатели — тот же файл, поиск по другой колонке; отдельный индекс не нужен.

```
W|<wf>|<name>|<state>|<draft>|<triggers>|<schedule>|<tz>|<passport|->|<project|?>|<errorWorkflow|->|<callerPolicy|->
D|<docId|dynamic>|<wf>|<node>|<nodeType>|<op>|<sheet|->
X|<callerWf>|<calleeWf|dynamic>|<node>|<wait|nowait>
H|<callerWf>|<node>|<calleeWf|DANGLING|dynamic>|<internal|public>
A|<wf>|<node>|<api resource>
C|<wf>|<credType>|<число узлов>
R|<wf>|<упомянутый wf>|<node>
```

Обратные указатели:
- документ → воркфлоу: `^D\|<docId>\|`;
- путь вебхука → вызывающие узлы: `^H\|[^|]*\|[^|]*\|<calleeWf>\|` в открытой части и `^HOOKCALL\|<path>\|` в закрытой;
- воркфлоу → саб-воркфлоу: `^X\|<wf>\|`;
- обратно, кто вызывает: `^X\|[^|]*\|<wf>\|`.

Строк в файле нет даты запуска: при неизменном инстансе файл не меняется, и коммита нет. Свежесть читатель сверяет по одному полю `instance_last_change` с `updatedAt` из search_workflows.

Публичность. Репозиторий публичный (git-migration PLAN §3, registry/tools.md). Опасное в снимке — пути вебхуков вместе с признаком аутентификации. Вебхук gdocs-read открыт (Z-5), открытых вне Канала 13 (Р-107), а домен инстанса уже назван в registry/projects.md. Публичный снимок с путями дал бы любому готовую карту открытых входов. ID документов и воркфлоу в repo уже лежат (registry/documents.md, registry/tools.md), и приращение риска по ним мало.

## 5. Механизм обновления

Посылка «Registry Sync — правильная точка расширения» принята. Основание: это единственное место, которое уже читает полный состав воркфлоу на стороне сервера, по внутреннему адресу, со своим ключом API. Ему не нужен контекст сессии, и у него уже есть ежедневный запуск (Z-1, Z-3). Сессионный обходчик отвергнут в разделе 8.

Доработка `gFFiBPm1OomOzJOj`, не замена:
1. Узел «Получить список воркфлоу n8n» остаётся. Если Ф1 покажет, что в ответе списка нет `nodes` или `description`, добавляется догрузка `GET /api/v1/workflows/{id}` по каждому живому воркфлоу: внутренний адрес, около 200 вызовов.
2. Узел «Построить реестр» переписывается. PASSPORT_MAP удаляется. Строки W, D, X, H, A, C, R и закрытые HOOK, HOOKCALL строятся по разделу 3 и сортируются, чтобы при неизменном инстансе текст совпадал байт в байт. Тяжёлый JSON не держать одним item (engineering-manual §4.11): считать постранично, архивные отбрасывать сразу.
3. Запись в repo — Каналом, не в обход (И-4). HTTP-узлы вызывают `git-read` и `git-write` по внутреннему адресу, с тем же Header Auth credential, что у вебхуков Канала (R13, R14). Git Write берёт blob sha самого файла, поэтому за голову main он с сессиями не гоняется (second-brain-git 8.9). Если текст совпадает с прочитанным, записи нет. Файл пишет только этот воркфлоу; первой строкой после пути идёт пометка «руками не править».
4. Закрытая часть пишется в N8N_REGISTRY существующим узлом «Перезаписать N8N_REGISTRY» через gdocs-overwrite-v2.
5. Защита открытой части стоит в самом коде, до записи: строка открытой части, содержащая `/webhook/`, `http:` или `https:`, `Bearer`, `@` или путь любого вебхука из строк HOOK, роняет прогон ошибкой, и в repo ничего не уходит. Это не монитор: защита срабатывает в момент записи и никого не оповещает.
6. Первый прогон — пробный (Ф1, Р-2, Р-5): правка ложится черновиком и не публикуется. Ручной запуск через MCP исполняет черновик, ежедневный запуск 05:30 — прежнюю опубликованную версию. Узлов записи в repo в черновике нет. Старый текст реестра идёт в N8N_REGISTRY первым и без изменений, кандидат открытой части, закрытая часть и строка `api_fields` — ниже него. Прогон 05:30 возвращает документ к прежнему виду. Строка `api_fields` перечисляет ключи верхнего уровня ответа API и ключи узла, в том числе есть ли `nodes`, `description`, `versionId`, `activeVersionId`, `credentials`. Если `description` нет ни в списке, ни в ответе по ID — стоп до решения владельца: без него не выводится паспорт (В4). Сессия читает N8N_REGISTRY через gdocs-read и ищет в кандидате пути вебхуков, адреса и строки, похожие на ключи. `get_execution` с `includeData:true` по Registry Sync ЗАПРЕЩЁН: узел httpRequest оставляет в contextData весь JSON инстанса (engineering-manual R4), и он целиком ушёл бы в контекст сессии. Константа переключается только после чистого пробного прогона (Ф2).

Частота — прежняя: 05:30 и ручной запуск. Новых расписаний нет (ИН-3).

Что происходит с воркфлоу, которых не было в прошлом снимке. Снимок каждый раз пересчитывается целиком, состояния между днями нет, поэтому копиться нечему:
- появился — его строки появляются;
- архивирован — строка W со state archived, остальные его строки исчезают (ответ API содержит архивные — Z-3);
- удалён — строки исчезают.

Что было вчера, читается из истории git этого файла; отдельного журнала изменений нет.
