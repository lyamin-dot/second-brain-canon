# PLAN_card-content-sync — цель, устройство, факты зондов

Проект-летопись. Единственный носитель — эта папка репозитория `lyamin-dot/second-brain-canon`; Claude Project и своего INDEX в Google Docs у проекта нет. Развёрнут 2026-10-04 из задачи лаборатории `labs/ozon-ue/t-card-content-sync.md` по 4б.7 `second-brain-git` (у задачи появились фазы); задача закрыта тем же коммитом, её текст читается из истории по родителю этого коммита. Наряд-основание — Н-04.10-01а (выдан в чате проекта 02_Unit_Econ._Ozon 2026-10-04, исполняется в Cowork).

## Цель

Андрей правит описание товара в одной шаблонной Google-таблице, и правка доходит до карточки этого товара во всех четырёх магазинах: Ozon основное юрлицо (Client-Id 559661), Ozon ИП, Wildberries основное юрлицо, Wildberries второе юрлицо. Сейчас описания меняются заливкой Excel-шаблона в каждом кабинете отдельно.

Финиш проекта: боевой режим записывает описание из книги в карточки всех магазинов, у которых есть ключ, и повторная «проверка» после записи не находит расхождений.

## Границы

- Только описание. Название, характеристики, фото и rich-контент вне проекта.
- Ассортимент магазинов между собой не сравнивается: магазины принадлежат разным юрлицам.
- Платные сервисы управления карточками (SelSup, MPsklad, Topseller) не используются.
- Существующие воркфлоу (`J0v5swjXLfiANJa2`, `PWFVE0UbM3ajvVFc`, `fGHfVrI58Ws1wfTw`, `QCQI6utFFH3dvTJT`, `BLNA8sbdnLtuz7Uj`) и структура листа Artikel книги Price Master не меняются — только читаются.
- Запись в карточки любого магазина запрещена до приёмки фазы Ф1; боевой режим — отдельный наряд.
- Каждый новый воркфлоу создаётся только после «да» Андрея в форме «Нода/воркфлоу [название]. Планирую: [что]. Подтверждаешь?».

## Решения об инструментах

Источник описаний — Google Sheets, а не 1С УНФ (`LOG.md` Р-1). УНФ технически доступна через REST-интерфейс OData, но каждое обращение к ней требует отдельной инфраструктуры: публикации базы наружу, авторизации, знания имён объектов конфигурации. Готовая интеграция УНФ с маркетплейсами — платный модуль. Google Sheets уже встроены в инструменты агента (воркфлоу gsheets-read, Skills, сервисный аккаунт Google) и правятся человеком напрямую в той же ячейке, которую читает воркфлоу. У Андрея есть 1С УНФ и модули iTone; в эту систему они не входят.

## Устройство (Андрей подтвердил 2026-10-04, `LOG.md` Р-2)

Книга-шаблон «Описания карточек» в папке DOCS проекта OZON_UE `1yifa_sfm6l7b0l08dB8ghzadeEGbIcSQ`:
- колонки Андрея: наш артикул, название, описание;
- колонки-формулы: длина описания против предела каждой площадки; четыре колонки идентификаторов карточек — формулами из листа Artikel и промежуточных листов (адреса в разделе «Ключ сопоставления»). Изменено 2026-10-05 (`LOG.md` Р-4): колонки идентификаторов магазинов ИП (Ozon ИП, WB второе юрлицо) пишет воркфлоу из живого чтения карточек, промежуточных листов для них не заводится; для магазинов основных юрлиц — см. раздел «Проект Ф1», пункт «Идентификаторы карточек»;
- служебные колонки, которые пишет только воркфлоу: по каждому магазину хэш последней отправленной версии, дата и статус.

Первичное наполнение: описания из одного кабинета (какого — решает Андрей; по умолчанию Ozon основное юрлицо). Одновременно в служебные колонки пишется хэш текущего описания, прочитанного из каждого магазина с ключом и найденной карточкой, со статусом «исходное состояние». Без этого шага первый прогон «проверки» выдал бы все пары: хэшей последней отправки ещё нет. Хэш считает воркфлоу; формул хэша в книге нет. Отдельно — отчёт, у каких артикулов описания в магазинах сейчас различаются.

Воркфлоу «Card Description Sync», запуск формой n8n, режим «проверка». По каждой паре «артикул × магазин» он делает две сверки:
1. хэш описания в книге против хэша последней отправки — расхождение даёт строку на листе «К отправке» с причиной «изменено в книге»;
2. хэш живого описания карточки против хэша последней отправки — расхождение даёт строку с причиной «изменено в кабинете» (правка вручную в личном кабинете или площадкой при модерации).
Если сработали обе сверки — одна строка с обеими причинами. В карточки режим ничего не пишет. Магазин без ключа помечается «ждёт ключ» и не останавливает остальные; карточка, не найденная в магазине с ключом, — «карточка не найдена».

Нормализация текста перед хэшированием — одно правило для обеих сверок и для всех магазинов, описывается в паспорте воркфлоу. Без неё площадка, вернувшая текст с другими переносами строк или пробелами, даёт ложное «изменено в кабинете». Что уже известно о форме текста — раздел «Факты зондов».

Документация — часть поставки Ф1: паспорт воркфлоу по Skill `n8n-workflow-passport`, строка `PASSPORT: <id>` в описании воркфлоу (вписывает Андрей руками), инструкция пользователя книги — RU для человека и EN для агента, с объяснением обеих причин и что делать с каждой.

## Проект Ф1 (Клод, 2026-10-05; не построено)

Ф1 строится на двух магазинах основных юрлиц, не дожидаясь ключей ИП (`LOG.md` Р-4). Магазин без ключа присутствует в книге с первого дня, его колонки заполняются статусом «ждёт ключ».

Книга «Описания карточек», листы:
- «Описания» — строка на артикул со статусом «продаётся» в Price Master!Artikel. Колонки Андрея: A наш артикул (целое число), B название (справочно, в магазины не уходит — название вне проекта), C описание, D описание для WB (колонка-исключение: пусто — в WB идёт C). Колонки-формулы: длина C, длина того, что уходит в WB (D, если не пусто, иначе C), признак превышения предела по каждой площадке. Колонка D существует с первого дня, а заполняется ли она при наполнении — решение Андрея по отчёту длины (раздел «Посылка „одно описание на все магазины“»).
- Справа на том же листе — служебный блок, который пишет только воркфлоу: по каждому из четырёх магазинов идентификатор карточки, хэш последней отправки, дата, статус. Блок защищён предупреждением (защита Google Sheets в режиме «только предупреждение»), чтобы ручная правка была осознанной.
- «К отправке» — перезаписывается каждым прогоном «проверки»: артикул, магазин, причина («изменено в книге», «изменено в кабинете» или обе), три хэша (книги, последней отправки, карточки), дата прогона.
- «Различия» — пишется один раз при первичном наполнении: артикулы, у которых описания в магазинах с ключом различаются, с длинами.
- «Магазины» — параметры: код магазина, название, есть ли ключ, предел длины описания. Правит Андрей; появление ключа ИП — смена одной ячейки.

Статусы служебного блока: «исходное состояние» (хэш снят с карточки при наполнении), «отправлено» (Ф2), «ждёт ключ», «карточка не найдена».

Идентификаторы карточек. Предложение Клода, ждёт подтверждения Андрея: все четыре колонки идентификаторов пишет воркфлоу из живого чтения, а не только колонки ИП. Основания: живое чтение карточек каждого магазина есть в каждом прогоне «проверки» (сверка 2), поэтому идентификатор приходит даром; формулы из Price Master потребовали бы функции IMPORTRANGE с ручным разрешением доступа между книгами и приведения артикула «1058.0» к целому; один механизм на все четыре магазина проще проверить. Ключ сопоставления — наш артикул как первое слово offer_id у Ozon и vendorCode у WB (подтверждено для основных юрлиц, раздел «Ключ сопоставления»). Если Андрей предпочтёт формулы для основных юрлиц — работает и так, меняется только этот пункт.

Нормализация текста перед хэшированием, по порядку:
1. Приведение Unicode к форме NFC.
2. Переводы строк CR LF и одиночный CR — в LF.
3. Неразрывный пробел U+00A0 и табуляция — в обычный пробел.
4. Пробелы в конце каждой строки удаляются, серии пробелов внутри строки сжимаются до одного.
5. Три и более подряд идущих LF сжимаются до двух.
6. Пробелы и переводы строк в начале и в конце текста удаляются.
Правило про HTML добавляется после зонда Ozon: WB отдаёт текст без HTML (зонд 74962), форма текста Ozon неизвестна.

Хэш — SHA-256 от UTF-8 нормализованного текста, в книгу пишутся первые 16 шестнадцатеричных знаков. Считается чистым JavaScript внутри узла Code: модуль crypto в Code-узле n8n доступен только при переменной окружения NODE_FUNCTION_ALLOW_BUILTIN, а её наличие на инстансе не проверено.

Воркфлоу «Card Description Sync», форма n8n, два режима:
- «наполнение» — выполняется один раз: отказывается работать, если в служебном блоке уже есть хэши; пишет строки артикулов, описания из выбранного кабинета, идентификаторы и хэши «исходное состояние» по всем магазинам с ключом, лист «Различия».
- «проверка» — читает книгу и живые карточки магазинов с ключом, делает две сверки, перезаписывает «К отправке» и колонки идентификаторов. В карточки не пишет.
Чтение магазинов: WB — POST content/v2/get/cards/list с курсором до конца выдачи (образец — узел 05_Fetch_Cards воркфлоу `QCQI6utFFH3dvTJT`, 5 страниц по 100). Ozon — способ выбирается по зонду: если атрибут 4191 в ответе /v4/product/info/attributes совпадает с ответом /v1/product/info/description, описание читается пакетно атрибутами (до 1 000 товаров за вызов); иначе — по одному товару, около 420 вызовов с паузой. Запись в книгу — не больше четырёх вызовов Sheets API за прогон (квота считается на сервисный аккаунт).

Зонд WB, основное юрлицо — из исполнения 74962 воркфлоу `QCQI6utFFH3dvTJT`, узел `05_Fetch_Cards` (POST `content-api.wildberries.ru/content/v2/get/cards/list`), без новых вызовов к WB:

## Посылка «одно описание на все магазины»

Под вопросом, не отвергнута. Предел WB — 2 000 символов, и 19 текстов в нём упираются; предел Ozon неизвестен. Если он заметно больше и тексты Ozon длиннее 2 000, первичное наполнение из Ozon даст WB тексты, которые WB не примет. Решение — после зонда Ozon: либо одно описание не длиннее наименьшего предела, либо колонка-исключение для WB (мандат наряда это допускает).

## Уроки записи в WB (из `projects/deklaration-ozon/PLAN.md`, раздел «Wildberries — перенос и обновление деклараций», и `LOG.md` того проекта Р-30)

- `/content/v2/cards/update` заменяет карточку целиком: пишется только карточка из свежего чтения того же прогона, меняется только описание. Узел WB Sync `06_Build` уже собирает такой пакет (nmID, vendorCode, brand, title, description, dimensions, characteristics, sizes) и сторожит отличия вне меняемого поля — образец для боевого режима.
- WB отклоняет всю склейку (imtID), если в ней есть карточка с ошибкой. Склейки у нас до 29 карточек — ошибка одной блокирует до 29.
- Ответ 200 не значит, что карточка применена: итог — POST `content/v2/cards/error/list`.
- Квота Google Sheets считается на сервисный аккаунт, а не на воркфлоу.
