### Ключ к собственному API n8n

Воркфлоу обращаются к `/api/v1/` своего же инстанса через credential типа Header Auth с заголовком `X-N8N-API-KEY`. Действующее значение живёт в credential `monitor_key_v2`, без даты истечения. Прежний `monitor_key` ротирован 21.07.2026 [владелец 21.07]; всякое указание на его срок истечения 25–26.07.2026 устарело и исполнению не подлежит.

Списка мест использования здесь нет намеренно: прежняя редакция такой список держала, он устаревал быстрее, чем его правили, и пропускал одного потребителя из четырёх — SYS Lint. Перед ротацией список берётся из снимка: строки `A` дают воркфлоу, обращающиеся к `/api/v1/`, строки `C` — тип credential на их узлах. На 26.09.2026 таких воркфлоу четыре: Workflow Health Monitor — Daily (`LguGCDYJvMQSahcj`, активен), Workflow Health Monitor — Intraday (`tABmSQXQalGnjRJw`, неактивен), SYS Lint (`TXNstdVL8xlIygBp`, активен) и N8N Registry Sync (`gFFiBPm1OomOzJOj`, активен) [снимок 26.09]. У всех четырёх в снимке есть узлы с типом `httpHeaderAuth` [снимок 26.09]. Привязать тип к КОНКРЕТНОМУ узлу снимок не может: строки C считают типы по воркфлоу целиком. Привязку к узлу даёт лист «Авто» книги N8N_CREDENTIALS: строка на каждую пару «credential в узле», с колонками «Активен в узле» и «Хост узла». Колонка «Активен в узле» нужна потому, что n8n не стирает прежний credential из узла при смене типа аутентификации: в узле может храниться несколько, а в запрос уходит только выбранный. Перед ротацией список потребителей ключа — строки листа «Авто» с его ID и «Активен в узле: да», после свежего прогона Credential Inventory. Лежит ли значение ключа открытым текстом в параметрах узла, не показывает ни снимок, ни лист — это проверяется только глазами в редакторе.

НЕ путать этот ключ с MCP-ключом, которым Claude обращается к n8n: тот не истекает и к воркфлоу отношения не имеет. И не путать ни один из двух с `git-channel-webhook-auth` — секретом вебхуков Канала: тип auth у всех трёх один, назначение разное, и подмена одного другим даёт не отказ доступа, а утечку не того секрета.

**Отзыв ключа.** Credential в n8n хранит копию значения ключа, а не сам ключ. Удаление credential стирает эту копию из n8n и проходит без ошибки, но ключ продолжает действовать там, где его выдали: утёкший ключ после такого удаления остаётся утёкшим. Ключ отзывает только тот, кто его выдал. Ключ к собственному API n8n выдаёт сам n8n, и отозвать его можно только в Settings → n8n API: кнопка Delete рядом с ключом, затем подтверждение Delete Forever. Там же ключ создаётся (Create an API key), с меткой (Label) и сроком действия (Expiration). Ключ, выданный внешним сервисом (Ozon, Wildberries, Voyage AI), отзывается у этого сервиса, в его кабинете. Порядок при утечке или ротации ключа к API n8n: создать новый ключ в Settings → n8n API → перевести на него всех потребителей (список — абзац выше: лист «Авто» книги N8N_CREDENTIALS после свежего прогона Credential Inventory) → удалить старый ключ в Settings → n8n API → только после этого удалить или переименовать credential со старым значением — это уборка, а не отзыв. Проверено чтением документации n8n 2026-10-13 (страница «API authentication», разделы «Create an API key», «Node configuration» и «Delete an API key»; репозиторий n8n-io/n8n-docs, коммит 928b0b7): отзыв описан только в Settings → n8n API, о связи удаления credential с ключом документация ничего не говорит. На инстансе не проверялось — проба требовала удалить действующий ключ, Андрей от неё отказался 2026-10-11 (запись Р-17 журнала projects/archivarius/LOG.md). Основание: 1 случай, 2026-07 — запись корпуса N8N_JOURNAL_2026, строка 2804: «удаление credential не отзывает ключ» (урок У-13г журнала projects/archivarius/LOG.md, запись Р-8).
