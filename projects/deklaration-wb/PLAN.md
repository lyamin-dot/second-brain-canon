## Цель

В карточке каждого нашего артикула на Wildberries, в обоих кабинетах (основной и ИП), стоит действующий документ — декларация соответствия ЕАЭС, РОСС, СГР — и сам документ верен: номер и даты в карточке совпадают с выпиской реестра Росаккредитации, документ относится к тому товару, WB не отклонил его при ежедневной сверке (`doc_verdict` в WB_Cards_Staging). Ручной труд — только то, что робот не может: загрузка PDF в кабинет WB (метода API нет, `projects/deklaration-ozon/LOG.md` Р-21), решения «да» на боевую запись, поиск документов, которых нет на сайте поставщика.

## Wildberries — перенос и обновление деклараций (проект устройства, 2026-10-02)

Статус: расширение проекта на Wildberries — решение Андрея (`projects/deklaration-ozon/LOG.md` Р-19); отдельный воркфлоу WB Sync и зонд Ф0 Андрей подтвердил 2026-10-02 (`projects/deklaration-ozon/LOG.md` Р-20), остальное устройство ниже — предложение Клода. Зонд Ф0 — «LM_DECL — WB Probe (temp)» `RJ9qlEVyBaaJkaGH`, только чтение; WB Sync — «LM_DECL — WB Sync» `QCQI6utFFH3dvTJT`, режимы «проверка» и «боевой», устройство и правила запуска — его паспорт (адреса ниже), не дублируются здесь (`projects/deklaration-ozon/LOG.md` Р-22). Оба воркфлоу не архивируются и не публикуются (слово Андрея 2026-10-02). Название проекта не меняется (имя папки — адрес, 2.1 `second-brain-git`).

Чем WB отличается от Ozon (открытые источники, прочитаны 2026-10-02; зондом не проверено — до зонда Ф0 правилом не считать): файл декларации через API не принимается — PDF загружается в кабинете (раздел «Товары → Документы»), а через Content API в карточку пишутся характеристики: вид документа, номер, дата начала и дата окончания действия; с 2026-09-01 площадка обязана держать в карточке активную ссылку на запись реестра Росаккредитации и сверяет карточки с реестром ежедневно — карточку без подтверждённого документа может скрыть. Отсюда единица работы у WB — карточка (nmID), а не документ, как у Ozon.

Что уже есть на инстансе (прочитано 2026-10-02 через get_workflow_details, ничего не запускалось): воркфлоу «Получение nmID WB» `gglEq5U90Gt3sI7h` читает карточки POST `content-api.wildberries.ru/content/v2/get/cards/list` (тело `settings{sort, filter{withPhoto:-1}, cursor{limit:100, updatedAt, nmID}}`, credential типа httpHeaderAuth — имя и id MCP не отдал) и пишет wb_nm_id в лист MASTER_MAP узлом `16_Write_WB_nmID` по our_sku. Пагинация в нём зашита на 5 страниц — не больше 500 карточек; для WB Sync брать курсор до конца выдачи, а не копировать узлы. Курсор во встроенной пагинации HTTP-узла передаётся одним параметром body с именем `settings` и объектом целиком; имена вида `settings.cursor.nmID` не работают (`projects/deklaration-ozon/LOG.md` Т-6); конец выдачи — `cursor.total` меньше limit. Колонки MASTER_MAP по схеме узла: our_sku, lm_id_1, lm_id_2, ozon_sku, wb_nm_id, is_duplicate, source_row, notes, vendor_Code.

Факты зонда Ф0 (прогон 73747, 2026-10-02, `projects/deklaration-ozon/LOG.md` Р-21): документ в карточке — характеристики 15001135 «Номер декларации соответствия», 15001137 «Дата регистрации сертификата/декларации», 15001138 «Дата окончания действия сертификата/декларации» (необязательные, строка, одно значение, даты ДД.ММ.ГГГГ), одинаковые у всех 12 предметов наших карточек; 15001136 — номер сертификата, 62945173 — свидетельство СГР (только предметы 802, 3935, 8409). Поля для ссылки на реестр нет. Поле карточки `documents` держит документ с вердиктом сверки WB (`verdict.reason`, `overallVerdict`) — его WB заполняет сам; признак сверки после записи брать оттуда.

Устройство (предложение):
- Отдельный воркфлоу «LM_DECL — WB Sync», не ветка Ozon Upload: другое API, другой credential, другая единица работы; сбой одного не должен останавливать другой. Не публикуется; запуск — форма n8n, режимы как у Ozon Upload: «проверка» (читает карточки, считает расхождения, ничего не пишет), «боевой» (только после «да» Андрея на конкретную декларацию), «статус» (сверка всех карточек MASTER_MAP с листом «Декларации», ничего не пишет в WB).
- Поток: строка «Декларации» (номер, date_from, date_to, articles) → артикулы → wb_nm_id из MASTER_MAP → карточки из `/content/v2/get/cards/list` → сравнение характеристик декларации с листом → запись `/content/v2/cards/update` только у расходящихся карточек.
- Ловушка записи (по документации Content API, проверить зондом Ф0): `cards/update` заменяет карточку целиком — характеристика, не переданная в запросе, стирается. Запись только чтение → правка → запись: карточка из свежего чтения того же прогона, меняются только характеристики декларации, отправляется целиком. Узел перед отправкой сравнивает отправляемое с прочитанным; отличие вне характеристик декларации — стоп прогона до записи.
- Учёт — отдельный лист «WB» в книге LM_DECL_MASTER, строка на nmID: nm_id, our_sku, declaration_no (ожидаемый по листу), card_declaration_no, card_date_to, wb_status, synced_at. Не колонка в «Декларации»: новая колонка там требует правки схемы узла `10B_Upsert_Declarations` в Scan (ловушка 1), а статус у WB живёт по карточке, а не по документу.
- Ссылка на реестр Росаккредитации через API не пишется: характеристики для неё нет, WB сверяет документ по номеру сам (`projects/deklaration-ozon/LOG.md` Р-21). Если понадобится — колонка B declaration_url листа «Декларации» уже держит ссылки на записи реестра.
- Факты записи (`projects/deklaration-ozon/LOG.md` Р-30): WB отклоняет всю склейку (imtID), если в ней есть карточка с ошибкой; ответ `cards/update` 200 не значит, что карточка применена; ошибки асинхронной записи — POST `content/v2/cards/error/list` (тело `{cursor:{limit:100},order:{ascending:false}}`, записи по пакетам и vendorCode, nmID нет; GET даёт 405); WB сверяет даты документа с реестром — даты брать из PDF или реестра, расхождение даёт «document_dates_mismatch».
- Что писать (правило Р-21, Андреем не подтверждено): только когда ожидаемая декларация действует. В карточке истёкший документ или поле пусто — запись после «да»; оба документа действуют, а номера разные — не писать, решает Андрей (вероятнее ошибка листа); ожидаемая декларация истекла — не писать никогда.
- Автоматика: на первом этапе WB Sync запускается после дайджеста Scan руками; запуск боевого режима из Scan без участия Андрея — только после двух боевых прогонов, которые повторная «проверка» подтвердила без расхождений. Основание: ошибка записи в живые карточки массово скрывает товары, а откат карточки у WB — та же запись целиком.

Фазы:
- Ф0 — зонд, только чтение, после «да» Андрея: какой credential WB имеет категорию «Контент» и право записи; характеристики документа у предметов наших карточек (`/content/v2/object/charcs/{subjectId}` — названия, id, формат значений, есть ли поле ссылки на реестр); текущие значения у всех карточек с wb_nm_id; снимок покрытия по классам, как `projects/deklaration-ozon/LOG.md` Р-17 для Ozon; есть ли в API метод документов (swagger на dev.wildberries.ru — с сервера облачной сессии закрыт прокси, читать из браузера или HTTP-узлом n8n).
- Ф1 — WB Sync, режимы «проверка» и «статус», лист «WB».
- Ф2 — «боевой» на одной декларации после «да», приёмка повторной «проверкой».
- Ф3 — связь со Scan: строки WB в дайджесте, затем автозапуск по правилу выше.

Техническая документация — часть поставки, а не отдельный шаг (требование Андрея 2026-10-02, `projects/deklaration-ozon/LOG.md` Р-20): фаза не считается закрытой, пока не сделано своё. Ф1 — паспорт WB Sync по Skill `n8n-workflow-passport` в папке DOCS и строка `PASSPORT: <id>` в описании воркфлоу; инструкции для человека и для агента (по образцу Ozon Upload); раздел о листе «WB» в техдоках книги RU и EN. Ф2 и Ф3 — ADR в паспорт и правка инструкций; при Ф3 — ADR в паспорт Scan. Зонд Ф0 временный, паспорта не получает: его итог — запись журнала и снимок в `STATE.md`.

Запреты: боевой режим — только после «да» на конкретную декларацию или список; не менять карточки вне articles выбранной декларации; не менять характеристики, кроме характеристик документа; PDF в кабинет WB загружает Андрей, пока зонд не нашёл метода API.

## Как вести проект

Проект — Летопись; единственный носитель — эта папка в репозитории `lyamin-dot/second-brain-canon`. Claude Project и своего INDEX в Google Docs у проекта нет. Правила записи — Skill `second-brain-git` (перед первой записью читать его `references/write.md`); здесь только то, что специфично для проекта.
Куда писать: сдвинулось состояние (записано в карточки, статус воркфлоу, очередь) — `STATE.md`; принято решение или попытка не удалась — запись в `LOG.md` по форме Р-/Т- (номер — по свежему чтению перед вызовом); изменилось правило или устройство — `PLAN.md`; изменилось то, что касается обоих проектов (книга, Scan, тип документа, кабинет), — `meta/DECLARATION_COMMON.md` или `meta/DECLARATION_SCAN.md` и строка в журнале общего слоя.
Как писать: `LOG.md` — только дозаписью (Git Append File, запасной путь Git Append), `STATE.md`, `PLAN.md` и файлы `meta/` — правкой фрагмента (Git Replace); результат доказывается чтением с `origin/main` после свежего `git fetch` и сверкой blob sha.
Кто исполняет: правки воркфлоу и запись в карточки WB ведёт отдельный чат Андрея и сам записывает результат сюда; сессия, не получившая «да» на конкретный список nmID, в карточки не пишет.
