## 13. Модель данных пилота (контракт раздела 12 — исполнен, с 2026-10-31 в блоке хроники LOG.md; проверена отдельным проверяющим тремя случаями этапа 2: первый круг — не прошла, второй — прошла, 2026-10-25; запись Р-14 журнала)

### 13.1. Главные правила модели

1. В центре — наш артикул (число из 4 и более цифр, хранится как текст). Кабинет — отдельный слой: всё, что площадка держит в кабинете (идентификаторы карточки, штрихкод, бренд в карточке, цена, остаток, продажа, деньги), живёт в строке «кабинет + товар площадки», а не в строке артикула. Ни одно свойство артикула не берётся из карточки какого-то одного кабинета.
2. Сырой слой (схема `raw`) хранит ответ площадки как прислан: одна строка = один элемент названного массива ответа (например, один элемент `cards` у WB), целиком в колонке `payload` (jsonb). Вложенные массивы элемента (размеры, склады) не режутся. Колонки рядом с `payload` — только ключи и даты, вынутые из него же.
3. Справочник (схема `ref`) хранит только то, чего площадка не присылает: юрлица, кабинеты, какой посредник ходит в какой кабинет. Список артикулов в `ref` — копия, не дом.
4. Кабинет = строка `ref.cabinet` + ключ, созданный Андреем + свой посредник (пункт 13.5). Имени кабинета нет в коде ни одного сборщика.
5. Пилот только читает площадки (инварианты 1–2 PLAN.md). Секретов в базе нет (инвариант 7).
6. Хозяин базы — роль `mkt2_writer`, читает агент ролью `mkt2_reader` (запись Р-13 журнала).

### 13.2. Схема `ref` — справочник

**ref.legal_entity — юрлица.** Дом свойства «какие у Андрея юрлица». Юнит-экономика считается на каждое юрлицо отдельно (PLAN.md, этап 4, область 2, пункт d).

| колонка | тип | смысл |
|---|---|---|
| entity_code | text | `kiparis`, `ip` — **первичный ключ** |
| title | text | «ООО «Кипарис»», «ИП» |
| kind | text | `ООО` или `ИП` |
| note | text | заметка |

**ref.cabinet — кабинеты.** Дом свойства «какие кабинеты, чьи, на какой площадке, собирается ли и с какой даты».

| колонка | тип | смысл |
|---|---|---|
| cabinet_code | text | `ip_ozon`, `ip_wb`, `kiparis_ozon`, `kiparis_wb` — **первичный ключ** |
| entity_code | text | ссылка на ref.legal_entity |
| marketplace | text | `ozon` или `wb` (проверка значения) |
| title | text | название магазина |
| collect_enabled | boolean | собирать ли сейчас |
| collect_from | date | с какой даты грузить историю при первом сборе |
| added_at | timestamptz | когда строка добавлена |
| note | text | заметка |

В пилоте `collect_enabled = true` только у `ip_ozon` и `ip_wb`. Строки Кипариса заводятся с `false`; их включение (параллельный сбор с 01.01.2027, запись Р-12) — проверка критерия «новый кабинет».

**ref.cabinet_api — какой посредник ходит в кабинет по какой категории.** Дом свойства «через какой воркфлоу-посредник сборщик достаёт данные кабинета данной категории».

| колонка | тип | смысл |
|---|---|---|
| cabinet_code | text | ссылка на ref.cabinet |
| api_scope | text | `ozon_seller`, `wb_content`, `wb_statistics`, `wb_finance`, `wb_marketplace`, `wb_prices`, `wb_analytics` |
| purpose | text | `read` — посредник для сборщиков MKT2; `write` — зарезервировано, в пилоте строк нет (инвариант 2) |
| api_proxy_workflow_id | text | ID воркфлоу-посредника (пункт 13.5) |
| note | text | заметка (имя credential можно писать сюда для человека, правдой оно не считается) |

**Первичный ключ** — (cabinet_code, api_scope, purpose): так у одного кабинета помещаются два ключа одной категории (у WB ИП уже есть «Контент» на чтение и на запись — STATE.md, строки 31–32). Какой credential привязан, видно только в узле посредника — это и есть единственный дом связки «кабинет → ключ». Права и срок ключа — только закрытая книга ключей N8N_CREDENTIALS, лист «Ключи»; таблица STATE.md «Ключи по кабинетам» — её снимок.

**ref.article — копия списка артикулов.** Не дом. Пересобирается воркфлоу MKT2 целиком (удалить всё — записать всё) из Price Master, лист Artikel, диапазон A:N, только четыре колонки, которые приходят из справочника по цепочке «Справочник → Акт.цена → sku_cost → Artikel» (`meta/PRODUCT_DATA_HIERARCHY.md`, строки 13–15 и 52):

| колонка | тип | смысл |
|---|---|---|
| article | text | наш артикул (Artikel!A) — **первичный ключ**; приведение: число и текст «1180» → один текст; ошибки и пустые строки отбрасываются; дубль после приведения — пересборка останавливается без записи |
| lm_id_1 | text | номер Liqui Moly 1 (Artikel!F); «#N/A» и пусто → NULL |
| lm_id_2 | text | номер Liqui Moly 2 (Artikel!G); то же |
| product_name | text | название (Artikel!H) |
| copied_at | timestamptz | время пересборки |

Не копируются: Artikel!AA brand и Artikel!N status (берутся из карточек WB Кипариса), колонки идентификаторов карточек B, C, D, E, J, L, M (свойства карточек Кипариса — их дом в модели — сырые карточки кабинета).

**ref.v_article_item — артикул в кабинете (представление).** Вычисляется из текущих версий сырых карточек, не хранится. Дом связи — артикул продавца в карточке кабинета (vendorCode на WB, offer_id на Ozon), который ставит Андрей.

| колонка | смысл |
|---|---|
| cabinet_code, marketplace | кабинет и площадка |
| item_key | WB — nmID; Ozon — product_id |
| seller_code | WB — vendorCode; Ozon — offer_id |
| ozon_sku | Ozon — SKU (0 = пусто, `labs/ozon-ue/t-product-data-model.md`, строка 159); WB — NULL |
| article | первое слово seller_code, если оно есть в ref.article; иначе NULL |
| first_seen_at, last_seen_at | первая и последняя загрузка карточки |
| is_live | карточка есть в последнем прогоне этого кабинета и метода со статусом `ok` (raw.load_run); прогоны `error` и `partial` не считаются |

Правило «первое слово = наш артикул» — у действующих роботов (WB: `meta/PRODUCT_DATA_HIERARCHY.md`, строка 26; Ozon: `labs/ozon-ue/t-product-data-model.md`, строка 89). Если у одного артикула в кабинете окажется больше одной живой карточки, представление показывает все, а свойства «цена артикула в кабинете» и «остаток артикула в кабинете» тогда не одно число — запрос обязан идти по item_key. Гипотеза (не проверена): у карточек-наборов первое слово может совпасть с одиночным артикулом. Проверить: выборка seller_code обоих кабинетов ИП с более чем одним словом после первой загрузки.

**«Продаётся / не продаётся»** — не хранится: вычисляется как «у артикула есть хотя бы одна строка ref.v_article_item с is_live».

### 13.3. Схема `raw` — сырые данные кабинетов ИП

Три способа загрузки:

- **«Версии»** (продажи, заказы, отправления, начисления, отчёты, карточки). Первичный ключ (cabinet_code, natural_key, payload_hash). Сборщик вставляет строку; если такая же версия уже есть — только обновляет `last_loaded_at`. Изменённый элемент ложится новой версией. **Текущая версия** элемента = версия с наибольшим `last_loaded_at` (а не `first_loaded_at`: при возврате статуса A → B → A текущей снова станет A).
- **«Снимок дня»** (остатки, цены). Первичный ключ (cabinet_code, snapshot_date, natural_key). Запись — одной транзакцией: удалить строки этой таблицы за (cabinet_code, snapshot_date), затем записать ответ целиком. Транзакция выполняется только если весь ответ получен (прогон `ok`); при ошибке день остаётся как был. Так товар, выпавший из ответа, не остаётся в дне со старым остатком.
- **raw.load_run** — одна строка на прогон. Не монитор и не сигнал: отсюда номер исполнения n8n для доказательства по строке контракта и признак `ok` для is_live.

Общие колонки каждой таблицы `raw`:

| колонка | тип | смысл |
|---|---|---|
| cabinet_code | text | ссылка на ref.cabinet |
| source_method | text | метод API, как в документации |
| payload | jsonb | один элемент ответа целиком |
| payload_hash | text | отпечаток payload (md5 текста jsonb) |
| load_run_id | bigint | прогон, впервые принёсший версию |
| first_loaded_at | timestamptz | когда версия впервые легла (UTC) — колонка даты загрузки |
| last_loaded_at | timestamptz | когда последний раз пришла снова |

Ключевые колонки заполняются из payload. Где выражение неизменно (текст, целое), строитель может сделать их вычисляемыми колонками PostgreSQL; даты заполняет сборщик. Гипотеза (не проверена): перевод текста в дату не годится для вычисляемой колонки PostgreSQL 16. Проверить: DDL на базе mkt2.

Естественный ключ каждой таблицы ниже — ключ ЭЛЕМЕНТА названного массива. Где он помечен гипотезой, строитель берёт его из страницы метода или первого ответа и записывает в строку контракта до загрузки; придумывать ключ без чтения нельзя.

**raw.load_run**

| колонка | тип | смысл |
|---|---|---|
| run_id | bigserial | **первичный ключ** |
| cabinet_code, source_method | text | кабинет и метод |
| n8n_workflow_id, n8n_execution_id | text | сборщик и номер исполнения |
| period_from, period_to | timestamptz | окно запроса (у снимков пусто) |
| started_at, finished_at | timestamptz | начало и конец |
| rows_received, rows_new | integer | элементов прислано / новых версий |
| status | text | `ok`, `error`, `partial` |
| error_text | text | текст ошибки (без ключей и заголовков) |

### 13.5. Новый кабинет без правки воркфлоу — проверено, и уточнение критерия

Проверено 2026-10-25, get_node_types на инстансе Андрея:
- узел Execute Sub-workflow (n8n-nodes-base.executeWorkflow, версия 1.4): параметр `workflowId` имеет тип «список / ID **или выражение**» — ID вызываемого воркфлоу можно взять из данных;
- узел HTTP Request (версия 4.5): выражением задаются адрес, метод, заголовки, тело и даже тип авторизации (`genericAuthType`), но сам ключ (`credentials`) — ссылка на конкретный credential, выражением не задаётся.

Отсюда устройство:
- на каждую тройку «кабинет + категория + назначение» — воркфлоу-посредник `MKT2 API <cabinet_code> <api_scope>`: вход — метод, адрес, тело; внутри один узел HTTP с привязанным ключом; выход — ответ площадки. Все посредники — копии одного образца;
- сборщики (один на метод, общие для всех кабинетов) читают ref.cabinet и ref.cabinet_api и вызывают посредника по `api_proxy_workflow_id`;
- новый кабинет = ключ (Андрей) + копии образца посредника (новые объекты MKT2) + строки ref.cabinet и ref.cabinet_api. Ни одна формула и ни один существующий воркфлоу не меняются.

Уточнение критерия этапа 2 (было → стало; внесено в раздел 5, этап 2, и в PLAN.en.md 2026-10-25, запись Р-14):
- было: «adding a cabinet changes no formula and no workflow — cabinet = master row + own credential»;
- стало: «adding a cabinet changes no formula and no existing workflow — cabinet = master row(s) + own credential + one proxy workflow per API category, copied from the template (n8n binds a credential to a node, not by expression: get_node_types 2026-10-25)».
Внесено интегратором.

### 13.6. Бренд и список артикулов Lopal — нужно решение Андрея

Факты: бренд как поле есть в Справочнике LM, лист РРЦиМП, колонка F (всегда LM), и в карточках WB (колонка D листов WB_Cards_Staging и WB_Cards_Staging_IP); Artikel!AA берёт бренд из карточек WB Кипариса (`meta/PRODUCT_DATA_HIERARCHY.md`, строка 92); в «Закупке» есть колонка F brand (`registry/documents.md`, строка 162). ### 13.8. Чего модель сознательно не решает в пилоте

1. **Расчёт юнит-экономики ИП** — копия таблиц Кипариса после ревизии (PLAN.md, этапы 3 и 4).
2. **Закупочная цена в базе.** Дом назван — «Закупка» (запись Р-73). Пилоту не нужна; копия расчёта ИП будет читать «Закупку» напрямую. Колонка B sku «Закупки» — идентификатор Ozon Кипариса внутри общей книги, то есть свойство кабинета: при копировании расчёта для ИП склеивать по колонке A (наш артикул), колонку B не читать. Открытый вопрос STATE.md «закупочная цена живёт в двух домах» закрыт записью Р-73 — интегратору вычеркнуть, перечень старых листов к отключению — ниже.
3. **Перенос дома списка артикулов в базу** — решение области 1; до него Artikel не трогать (инвариант 1).
4. **Бренд артикула и список Lopal** — решение Андрея (пункт 13.6).
5. **Ручные исключения связи артикул ↔ карточка** — карточки без нашего артикула первым словом остаются с article = NULL; таблица исключений была бы вторым местом связи, её решает область 1.
6. **Физический остаток своего склада и его связь с остатками двух юрлиц.** Гипотеза (не проверена): один склад кормит FBS обоих юрлиц. Проверить: вопрос Андрею, откуда выставляются остатки.
7. **Реклама, воронка, конверсия** — вне задачи пилота (для Ozon, вероятно, нужен ключ Performance API — `meta/OZON_UE_INPUTS_MAP.md`, строка 74).
8. **Свод для Андрея в книгах** — решение этапа 2 после пилота (RES-006, строка 10); агент читает базу воркфлоу `MKT2 SQL Read`.
9. **Данные Кипариса** — с 01.01.2027 (запись Р-12), строки кабинетов есть, сбор выключен.
10. **Срок хранения версий** — после первого замера объёма ИП (диск: 116 ГБ свободно на 13.10, RES-006, утверждение 8).
11. **Целевая цена** — область 2; для ИП и WB Кипариса дома нет (раздел 2).
