# Каталог файлов — планы этапов, точки переосмысления, Контролёр

Дата: 2026-10-21. Опирается на `projects/file-catalog/PLAN.md`.

Как читать. У каждого этапа: цель, шаги с исполнителем и наблюдаемым результатом, критерии приёмки (их проверяет Контролёр), точки переосмысления. **Точка переосмысления** — заранее названный наблюдаемый факт, при котором план этапа не продолжают по инерции, а останавливаются и решают заново. Без такого факта план не пересматривают.

Исполнители: **Андрей** — подключает диски, отвечает на вопросы, подтверждает удаление. **Исполнитель** — сессия Claude Code на Windows-компьютере, пишет и запускает код. **Контролёр** — отдельная сессия Opus, только на воротах.

## Этап 0. Подготовка

**Цель:** на Windows-компьютере работает среда, в которой Claude сам пишет и запускает код против подключённых дисков, и создана пустая база.

| Шаг | Кто | Наблюдаемый результат |
|---|---|---|
| 0.1 Проверить, какой путь работы с компьютером рабочий: Claude Code, установленный на Windows, или мост к компьютеру из облачного чата | Исполнитель с Андреем | Одна команда, выполненная Claude на компьютере, вернула список подключённых дисков |
| 0.2 Установить Python и библиотеки (чтение документов, определение кодировок, хэширование) | Исполнитель | Команда проверки версий выводит все библиотеки без ошибок |
| 0.3 Завести рабочую папку проекта на внутреннем диске компьютера (не на внешнем) | Исполнитель | Папка существует; в ней файл базы и папка кода |
| 0.4 Схема базы, версия 1: таблицы «диски», «файлы», «сканирования», «ошибки чтения» | Исполнитель | База создаётся скриптом с нуля одной командой |
| 0.5 Решить, где хранить код: закрытый репозиторий на GitHub или только папка на компьютере | Андрей | Решение записано в журнал проекта |
| 0.6 Пробный прогон сканера по тестовой папке из 1–2 тысяч файлов разных типов | Исполнитель | В базе ровно столько строк, сколько файлов в папке (сверка со счётом Windows) |

**Критерии приёмки:** число файлов в базе совпадает со счётом Windows для тестовой папки; повторный прогон не создаёт дублей строк; на тестовом диске ничего не изменено (время изменения папки до и после совпадает); Claude по базе отвечает на вопрос «где лежит файл с именем …».

**Точки переосмысления:**
- П0.1. Ни Claude Code на Windows, ни мост из облачного чата не дают Claude выполнять команды на компьютере → переосмыслить среду: подсистема Linux внутри Windows, или Андрей запускает готовые скрипты сам по инструкции. Это меняет ритм всего проекта.
- П0.2. Антивирус или политика Windows блокирует чтение дисков скриптом → решить, добавлять ли исключение.

## Этап 1. Инвентаризация шести дисков

**Цель:** по любому файлу на любом из шести дисков известно, где он лежит, даже когда диск отключён.

| Шаг | Кто | Наблюдаемый результат |
|---|---|---|
| 1.1 Паспорт каждого диска: серийный номер тома, метка, ёмкость, свободное место, файловая система, примерный год (со слов Андрея) | Исполнитель при подключении; Андрей называет год | Шесть строк в таблице «диски» |
| 1.2 Порядок: сначала самый старый диск | Андрей | Записан порядок подключения |
| 1.3 Сканирование диска только на чтение: путь, имя, расширение, размер, даты создания и изменения. Системные папки (корзина, системные тома) пропускаются по списку | Исполнитель | Строки в таблице «файлы»; отчёт сканирования: число файлов, объём, время, число ошибок чтения |
| 1.4 Ошибки чтения (файл не открылся, сбой сектора) записываются отдельно и не останавливают сканирование | Исполнитель | Таблица «ошибки чтения»; если ошибки есть — Андрею называется диск и их число |
| 1.5 Разметка типа по расширению: документ, PDF, изображение, видео, аудио, электронная книга, архив, программа, прочее | Исполнитель | У каждого файла заполнена категория |
| 1.6 Сводка по всем дискам: объём и число файлов по категориям и по дискам | Исполнитель | Одна таблица, которую Андрей читает за минуту |
| 1.7 Резервная копия базы после последнего диска | Исполнитель | Копия базы лежит на одном из внешних дисков |

**Критерии приёмки:** шесть паспортов дисков; по каждому диску число файлов в базе совпадает со счётом Windows с точностью до пропущенных системных папок; Контролёр выбирает случайно 20 файлов из базы и отвечает, где они, а Андрей (или мост к компьютеру) подтверждает, что файлы там; Claude отвечает на 5 реальных вопросов Андрея вида «где у меня лежит …» по именам.

**Точки переосмысления:**
- П1.1. **После первого диска:** замерены скорость сканирования и число файлов. Если сканирование одного диска дольше 2 часов или файлов больше 5 миллионов на диск — пересмотреть способ обхода (параллельное чтение, пропуск папок вида «node_modules» и кешей программ).
- П1.2. На старом диске ошибок чтения больше нескольких десятков → остановить инвентаризацию остальных и решить: сначала спасать содержимое этого диска (копировать), потом каталогизировать.
- П1.3. **После всех шести дисков:** известны число и объём документов. Это главная развилка Этапа 3: если документов меньше примерно 50 тысяч — содержимое обрабатывается целиком на компьютере; если сотни тысяч — нужен отбор (сначала дубли, потом мусор по размеру и типу) и пересчёт стоимости работы модели.
- П1.4. Внутри архивов (zip, rar) лежит заметная доля документов → решить, раскрывать ли архивы при сканировании.

## Этап 2. Дубли и сохранность

**Цель:** известно, что лежит в одной копии и под угрозой, что задублировано, и выполнена первая подтверждённая чистка.

| Шаг | Кто | Наблюдаемый результат |
|---|---|---|
| 2.1 Воронка отпечатков: файлы группируются по размеру; у совпавших по размеру считается отпечаток начала и конца файла; полный хэш содержимого — только у совпавших и на втором шаге | Исполнитель | У каждого файла, имеющего пару по размеру, есть отпечаток; полный хэш — у кандидатов в дубли |
| 2.2 Для документов (приоритетная категория) полный хэш считается у всех, независимо от пары по размеру — они маленькие | Исполнитель | Полный хэш у всех документов и PDF |
| 2.3 Число копий каждого содержимого и на скольких разных физических дисках они лежат | Исполнитель | Поле «копий» и «дисков» у каждого файла |
| 2.4 Поиск папок-двойников: папка целиком повторяет другую (типично для «копия резервной копии») | Исполнитель | Список пар папок с долей совпадения |
| 2.5 Отчёт сохранности: ценное в одной копии (документы, фото, личное), отдельно по каждому диску и с учётом возраста диска | Исполнитель | Отчёт Андрею: что и сколько под угрозой |
| 2.6 Отчёт дублей: что лежит в трёх и более копиях и сколько места освободится | Исполнитель | Отчёт с объёмом освобождаемого места |
| 2.7 Список на удаление: только копии сверх двух на разных физических дисках; Андрей подтверждает списком или по папкам | Исполнитель составляет, Андрей подтверждает | Подтверждённый список в журнале |
| 2.8 Перемещение подтверждённого в папку «_quarantine» на том же диске; через срок, назначенный Андреем, — удаление | Исполнитель после подтверждения | Файлы в карантине; база отражает новое расположение |

**Критерии приёмки:** Контролёр проверяет на выборке 20 пар, что файлы с одинаковым полным хэшем действительно одинаковы (побайтовое сравнение); для каждого файла из списка на удаление в базе есть не менее двух других копий на разных физических дисках, и Контролёр проверяет это запросом, а не на слово; ни один файл не удалён без строки подтверждения Андрея в журнале.

**Точки переосмысления:**
- П2.1. Папки-двойники дают больше половины объёма дублей → переключить чистку на уровень папок: Андрей подтверждает папку целиком, а не тысячи файлов.
- П2.2. Отчёт сохранности показывает много ценного в одной копии на старом диске → перед чисткой — шаг копирования этого ценного на другой диск. Удаление ждёт.
- П2.3. Полный хэш больших файлов идёт дольше суток на диск → оставить для видео сравнение по размеру плюс отпечатку начала и конца, а полный хэш считать только перед удалением конкретного файла.
- П2.4. Андрей не готов подтверждать удаление списками → удаление откладывается; ценность этапа — отчёт сохранности, это уже полезный результат.

## Этап 3. Документы: содержимое (главный этап)

**Цель:** по любому документу известно, что внутри: поиск по тексту, тип документа, тема, дата, организация, ценность; Андрей может оставить к нему комментарий.

| Шаг | Кто | Наблюдаемый результат |
|---|---|---|
| 3.1 Решение о связи с archive-recon (точка П3.1) | Андрей по предложению Исполнителя | Записано в журнал |
| 3.2 Отбор: только уникальные документы (одна копия на каждое содержимое), без явного мусора по признакам (нулевой размер, временные файлы Office вида «~$…», системные) | Исполнитель | Число документов к обработке |
| 3.3 Извлечение текста по формату: txt, rtf, doc, docx, odt, xls, xlsx, pdf с текстовым слоем; определение кодировки для старых файлов (Windows-1251, DOS-866) | Исполнитель | У каждого документа есть текст или отметка «текста нет» с причиной |
| 3.4 PDF без текстового слоя и изображения документов — распознавание Tesseract (русский, немецкий, английский); две версии текста страницы, как в archive-recon | Исполнитель | Распознанный текст у сканов |
| 3.5 **Пилот на 500 документах** разных лет и форматов: модель присваивает тип (статья, приказ или распоряжение, инструкция, письмо, бланк, личный документ, черновик, мусор), тему по списку тем archive-recon с расширением, дату документа, организацию, язык, короткое описание в одну-две строки, ценность (важно, справочно, мусор) | Исполнитель | Метки у 500 документов; замер стоимости и времени |
| 3.6 Проверка пилота: Контролёр берёт 50 случайных документов из пилота и сверяет метки с текстом | Контролёр | Доля верных меток типа; число ценных документов, ошибочно помеченных как мусор |
| 3.7 Полный прогон по всем документам — только после принятого пилота | Исполнитель | Метки у всех документов |
| 3.8 Полнотекстовый поиск в базе (модуль FTS5) по тексту и описаниям | Исполнитель | Поиск по слову отвечает быстрее секунды |
| 3.9 Комментарии Андрея: таблица «комментарии», Андрей говорит Claude «пометь этот приказ: важно, …», Claude записывает | Исполнитель | Комментарий виден при следующем поиске |
| 3.10 Тест реальными вопросами: Андрей даёт 20 вопросов («приказ о дежурствах 2019 года», «статья про вазопрессоры у детей», «инструкция к …»), Claude ищет | Андрей задаёт, Контролёр (Opus) прогоняет | Число найденных из 20 |

**Критерии приёмки:** в пилоте тип документа верен не менее чем у 85 процентов из 50 проверенных, и не более 1 ценного документа ошибочно помечен как мусор; в тесте реальными вопросами найдено не менее 17 из 20; у каждого документа без текста названа причина (зашифрован, повреждён, пустой, неизвестный формат).

**Точки переосмысления:**
- П3.1. **Начало этапа:** сливать ли с archive-recon. Слить, если окажется, что большая часть ценных документов — медицинские статьи, и цепочка archive-recon на сервере обрабатывает их лучше. Не сливать, если медицинских статей — меньшинство среди документов.
- П3.2. **После пилота:** точность ниже порога → не прогонять всё, а менять способ: другие подсказки модели, модель сильнее, другой список типов. Два круга правок без сходимости — вопрос Андрею, от чего отказаться (например, от метки «ценность» в пользу только типа и темы).
- П3.3. **После пилота:** стоимость полного прогона по замеру пилота выше суммы, которую Андрей готов потратить → отбор жёстче (только документы определённых лет или папок) или более дешёвая модель для первого прохода.
- П3.4. Доля сканов без текста больше трети → распознавание на компьютере идёт слишком медленно; решить, переносить ли распознавание на сервер (там Tesseract уже работает в контейнере).
- П3.5. В тесте реальными вопросами меньше 17 из 20, и промахи — из-за того, что вопрос сформулирован не теми словами, что в документе → добавить поиск по смыслу (векторный), который сознательно вычеркнут из первой поставки.

## Этап 4. Доступ отовсюду (по нужде)

**Цель:** Claude находит файл из любого чата, в том числе с телефона, когда компьютер выключен.

Этап запускается только при наблюдаемом факте: Андрей хотя бы трижды хотел найти что-то в каталоге, когда компьютер был выключен или недоступен. Без этого факта этап не делается.

| Шаг | Кто | Наблюдаемый результат |
|---|---|---|
| 4.1 Копия базы на сервер Hetzner после каждого обновления (передача файла по защищённому каналу) | Исполнитель | На сервере актуальная копия; дата копии видна |
| 4.2 Инструмент поиска только на чтение: воркфлоу n8n или сервер MCP на сервере, который принимает вопрос и возвращает строки | Исполнитель | Claude из обычного чата находит файл |
| 4.3 Тест: 10 вопросов из обычного чата при выключенном компьютере | Контролёр | Найдено не менее 9 из 10 |

**Точки переосмысления:**
- П4.1. Копия на сервере регулярно отстаёт от главной → решить, переносить ли главную базу на сервер (тогда сканер пишет на сервер напрямую).

## Этап 5. Медиа

**Цель:** фильмы, музыка, фото и электронные книги узнаны как произведения.

| Шаг | Кто | Наблюдаемый результат |
|---|---|---|
| 5.1 Видео: технические параметры (длительность, разрешение, кодек) через ffprobe; разбор имени файла библиотекой guessit; название, год, жанр из базы фильмов TMDB | Исполнитель | У фильма — название и год |
| 5.2 Музыка: теги через библиотеку mutagen; треки без тегов — распознавание по акустическому отпечатку AcoustID и MusicBrainz | Исполнитель | У трека — исполнитель, альбом, название |
| 5.3 Фото: дата съёмки и место из метаданных EXIF | Исполнитель | У фото — дата |
| 5.4 Электронные книги (epub, fb2, djvu, mobi): автор и название из метаданных файла | Исполнитель | У книги — автор и название |

Порядок типов внутри этапа выбирает Андрей.

**Критерии приёмки:** по каждому типу на выборке 30 файлов не менее 90 процентов распознано верно (проверяет Контролёр); на вопрос «какие фильмы такого-то режиссёра у меня есть» Claude отвечает списком с дисками.

**Точки переосмысления:**
- П5.1. Распознавание фильмов по именам файлов ниже порога → использовать готовую программу Jellyfin только как распознаватель и читать её базу.
- П5.2. Музыки без тегов больше половины → распознавание по отпечатку станет долгим этапом; решить, стоит ли оно того.

## Этап 6. Коллекционирование

**Цель:** творческие инструменты поверх каталога. План этапа пишется после Этапа 5 по интересу Андрея. Кандидаты: почти-дубли (тот же фильм в другом качестве, та же песня в другом битрейте, то же фото уменьшенное); пробелы в коллекциях (недостающие серии, альбомы, главы книг); подборки по запросу.

## Контролёр — как работает

**Кто.** Отдельная сессия Claude на модели Opus. Не та, что исполняла этап; с исполнителем не переписывается. Получает только: файл состояния проекта, раздел этого плана для своего этапа, доступ к базе на чтение.

**Когда.** Только в двух случаях:
1. На воротах — исполнитель записал в состояние проекта «этап N готов к приёмке».
2. По команде Андрея «контроль» — в любой момент, если Андрею кажется, что работа застряла или ушла в сторону.

Между этими случаями Контролёра нет: ни расписания, ни напоминаний, ни панели.

**Что делает.**
1. Прогоняет критерии приёмки своего этапа — проверочными запросами к базе и выборками, а не по отчёту исполнителя.
2. Проверяет точки переосмысления этапа: сработал ли какой-то наблюдаемый факт, который исполнитель пропустил.
3. Проверяет неизменные правила проекта: диски не менялись без подтверждения; ничего не удалено без строки подтверждения Андрея; в публичный репозиторий не ушли данные каталога.
4. При вызове по команде «контроль» дополнительно: какой этап идёт, что сделано с прошлой записи журнала, есть ли шаг, который стоит без движения, и почему.

**Вердикт — один из трёх:**
- «Принято» — следующий этап можно начинать.
- «Не принято» — названо, какой критерий не выполнен и каким запросом это видно.
- «Переосмыслить» — названа сработавшая точка и факт; решение принимает Андрей.

**Запись.** Одна запись в журнал проекта: дата, этап, вердикт, факты. Ничего больше.
