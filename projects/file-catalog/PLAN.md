# Каталог файлов — глобальный план

Дата: 2026-10-21. Редакция после ревизии замысла (файл `projects/file-catalog/REVISION_2026-10-21.md`).

## 1. Цель

Знать, что лежит на шести внешних дисках за двадцать лет, и находить нужное за секунды — без перекладывания файлов по папкам. Порядок важности:

1. **Содержимое документов** — статьи, приказы по работе, инструкции, письма, и отличие их от мусора.
2. **Где что лежит** — по любому файлу: на каком диске, в какой папке, в скольких копиях.
3. **Сохранность** — всё ценное минимум в двух копиях на разных физических дисках; лишние копии сверх этого удаляются.
4. **Медиа** — фильмы, музыка, фото, электронные книги: что это за произведения.
5. **Коллекционирование** — инструменты с ИИ поверх каталога: чего не хватает, почти-дубли, подборки.

Каталог — это база данных, которую читает Claude и находит ответ на вопрос Андрея обычными словами.

## 2. Что не является целью

- Единая система папок и переименование файлов. Файлы остаются там, где лежат.
- Медиатека для просмотра и прослушивания (плеер). Если понадобится — отдельное решение.
- Резервное копирование как сервис. Каталог только показывает, что лежит в одной копии; копировать будет Андрей или отдельный шаг по его решению.

## 3. Неизменные правила проекта

1. **Диски только читаются**, пока Андрей не подтвердил конкретную операцию записи или удаления. Сканер ничего на дисках не создаёт и не меняет.
2. **Ни одного удаления, пока не просканированы все доступные носители** (редакция записи Р-5: сломанный и недоступный носители не просканировать). Удаляется только копия сверх двух копий на разных живых физических дисках, через карантинную папку, по списку, который подтвердил Андрей. Отчёты сохранности честно говорят «в одной копии среди просканированных носителей».
3. **Данные каталога не попадают в публичный репозиторий**: ни имена файлов, ни пути, ни содержимое, ни выгрузки. В репозитории — только планы, решения и код без личных данных.
4. **Сначала работа, потом приборы.** Никаких панелей, расписаний и детекторов раньше, чем просканирован первый диск. Контролёр — роль на воротах этапов (раздел 7).
5. **Каждый этап заканчивается полезным результатом**, которым Андрей может пользоваться, даже если следующий этап не начнётся.

## 4. Архитектура

```
 Шесть внешних дисков
        │ (подключаются по одному)
        ▼
 Windows-компьютер
   ├─ Сканер (Python)         — читает диск, пишет в базу
   ├─ Хэшер                   — отпечатки файлов для поиска дублей
   ├─ Извлекатель текста      — текст из документов, распознавание сканов
   ├─ Классификатор (модель)  — тип документа, тема, дата, ценность
   └─ База каталога: файл SQLite (главная копия)
        │
        │ Claude Code на этом компьютере читает базу напрямую
        ▼
 Ответ Андрею: «что это, где лежит, сколько копий»

 Позже, по отдельному решению:
   копия базы на сервере Hetzner → поиск из любого чата, когда компьютер выключен
```

Почему SQLite на компьютере, а не база на сервере: сканер работает там, где диски; локальная база не требует открывать сервер в интернет; один файл легко копировать и восстанавливать; SQLite спокойно держит десятки миллионов строк и имеет встроенный полнотекстовый поиск (модуль FTS5).

## 11. Копия Google Диска: особенности переноса и наши приёмы

Решение — запись Р-12 журнала. Скрипт `gdrive_backup.ps1` и подробная памятка с командами `ПРАВИЛА копии Google Диска.md` лежат в рабочей папке проекта на компьютере Андрея. Здесь — то, обо что споткнётся любая сессия, работающая с копией или с Диском:

1. Документы, Таблицы, Презентации и Рисунки Google — не файлы: на G: это ярлыки-ссылки в пару сотен байт. Копия проводником переносит ссылки, не содержимое. rclone через API выгружает их в docx, xlsx, pptx, svg; Формы, Мои карты и Сайты не выгружаются вовсе. Выгрузка теряет комментарии, историю версий и скрипты.
2. В одной папке Google бывает несколько файлов с одинаковым именем, в Windows — нет. rclone кладёт один и пишет в журнал «Duplicate object found». Приём: полный список Диска (`rclone lsjson -R`), повторы пути — копирование каждого по ID (`rclone backend copyid`) в папку `_одноимённые` с первыми 8 знаками ID в имени. В основной копии лежит один из тёзок, какой — не гарантировано.
3. Ярлыки Google не копируются (`--drive-skip-shortcuts`): иначе двойники и петли.
4. Копируется только «Мой диск»: «Доступные мне», общие диски, Корзина и Google Фото в копию не попадают.
5. Диск не читается через G:: чтение скачивает файлы в кэш на C:. Поэтому каталог Google Диск не хэширует, но содержимое Диска можно каталогизировать и хэшировать по копии на Elements — это обычный диск.
6. Знаки, запрещённые в именах Windows, rclone заменяет похожими знаками Юникода: имя в копии выглядит так же, но побайтно не совпадает с именем в Google. Сличать копию с Диском — по содержимому, не по имени.
7. Сверка — `rclone check --one-way` по MD5, который Google хранит у каждого настоящего файла; у выгрузок из п. 1 MD5 нет, они проверяются только на наличие.
8. Папка прежних версий сама не чистится и растёт; чистка — по решению Андрея.
9. Проект OAuth Андрея должен оставаться в статусе «In production»: в статусе «Testing» Google отзывает вход через 7 дней, и прогоны падают с ошибкой авторизации — Андрей переподключает вход сам (`rclone config reconnect`). Ключ входа — секрет, в repo не пишется.

## 12. Модель сессии и граница этапа

Какая модель на какую работу (предложение Клода 2026-10-27, по просьбе Андрея; не замер, проверяется опытом):
- **Opus** — всё, где решается новое: устройство источника истины, правила строения описи, разбор спорных строк с Андреем, ревизии, Контролёр (раздел 7);
- **Sonnet** — работа по готовым правилам и скриптам: `media_probe.py` и `media_report.py` на следующих папках, повторные сканы и хэши, обновление `STATE.md` по итогам прогона, сверки;
- **Haiku** — не брать: канон, журнал и описи по-русски длинные, правила записи строгие, экономия не окупает ошибок.
Сессия, которой досталась работа не своего класса, говорит об этом Андрею одной строкой в первом ответе.

Граница этапа объявляется вслух (решение Андрея 2026-10-27, запись Р-16). Когда закрыт этап или крупный шаг — опись папки собрана, устройство утверждено, приёмка проведена, — и канон записан и сверен, агент тем же ответом пишет отдельной строкой: «Шаг «<что>» завершён, канон записан и сверен — можно открывать новый чат. Следующему чату: <модель>». Тем же действием первая строка раздела «Следующий шаг» в `STATE.md` переписывается так, чтобы новый чат начал с неё. Посреди незаписанной операции эта строка не пишется.
