# Каталог файлов — ревизия замысла (denken)

Дата: 2026-10-21. Объект ревизии: глобальный план «пять слоёв» из обсуждения в чате.

Ревизия Р3 — план предполагает удаление дублей, то есть разрушительную операцию над файлами двадцати лет.

## Исходный замысел (что проверялось)

Цель: знать, что лежит на шести внешних дисках (до 16 терабайт, в основном фильмы, много музыки, много документов), уметь быстро это найти, безопасно хранить важное в двух копиях и удалять лишние дубли. Плюс база данных, по которой Claude ищет по запросу Андрея. Двигатель проекта — интерес к созданию инструментов с ИИ.

Исходный план из пяти слоёв:
- слой 0 — инвентаризация: список всех файлов всех дисков;
- слой 1 — дубли и сохранность;
- слой 2 — обогащение по типу файла (видео, музыка, фото, книги и PDF);
- слой 3 — смысл: описания, темы, векторный поиск, комментарии Андрея;
- слой 4 — доступ для Claude.

## Барьеры

### Жёсткие (только сообщаю)

1. Диски физически подключаются только к Windows-компьютеру. Сервер Hetzner и облачная сессия Claude их не видят. Всё, что читает файлы, работает на Windows-компьютере.
2. Репозиторий second-brain-canon публичный, и запись в него необратима (правило И-7 Skill second-brain-git). Имена файлов, пути к ним, содержимое документов и статей в репозиторий не попадают никогда. Сама база каталога — личные данные; её место — только компьютер Андрея и его сервер.
3. Чужие охраняемые тексты (статьи, книги) не копируются в открытые места — только название, автор и где лежит.
4. Облачная песочница Claude не может делать прямой git push — это граница платформы.

### Барьеры Андрея (называю цену снятия)

1. «Не наращивать приборы наблюдения и контрольные механизмы вокруг работы» — и одновременно просьба предусмотреть Контролёра. Это противоречие, а не барьер к снятию; оно развязано ниже, в разделе «Противоречие и развязка». Снимать барьер не нужно.
2. «Удалить ненужные дубли». Цена — риск потерять единственную копию. Барьер не снимается, а получает правило безопасности (ниже).

### Свои — что я додумал сам, Андрей этого не требовал

1. База данных — Postgres на сервере. Андрей этого не просил. После ревизии заменено: главная база — локальный файл SQLite на Windows-компьютере, копия на сервере — позже и по отдельному решению (причина — в разделе «Дефекты»).
2. Сканирование запускается само при подключении диска. Удобно, но это автоматизация, которую никто не заказывал. Оставлено как возможность этапа инвентаризации, не как обязательное.
3. Разработка через Claude Code прямо на Windows-компьютере. Это мой выбор среды. Альтернатива — мост к компьютеру из облачной сессии (с сегодняшнего вечера чат связан с компьютером). Решается на подготовительном этапе по факту, что работает.
4. Внешние базы метаданных (TMDB для фильмов, MusicBrainz и AcoustID для музыки). Мой выбор, касается только медиа, поэтому сдвинут на поздний этап.
5. Разделение на два проекта (новый каталог и archive-recon). Мой выбор, обоснование — в глобальном плане.
6. Проверка здоровья дисков (SMART — встроенный в диск журнал ошибок и износа). Предлагал мысленно; в план не включаю как обязательное — это прибор наблюдения. Допускаю одно разовое чтение при сканировании, если Андрей согласится.

## Вердикт решаемости

**Решение есть.** Оно обходит жёсткий барьер «диски видит только Windows», перенося всю работу с файлами на Windows-компьютер, а барьер «публичный репозиторий» — разделением носителей: в репозитории только планы и код, данные каталога — только локально и на сервере.

Опасность вырожденного решения названа явно: **каталог имён файлов без содержимого документов — это вырожденное решение.** Он формально отвечает «что где лежит», но для главного приоритета Андрея — знать, что внутри документов и статей, — почти бесполезен: имена файлов двадцатилетней давности вида «Документ1.doc», «scan_0034.pdf» ничего не говорят. Поэтому первая полезная поставка обязана включать содержимое документов, а не только список.

## Дефекты плана

**Самое слабое звено:** слой содержимого документов. Двадцать лет документов — это смесь форматов (doc, docx, rtf, txt, odt, xls, pdf с текстом и сканы без текста), кодировок (старые русские файлы в кодировках Windows-1251 и DOS-866, их программа без проверки покажет как мусор из знаков вопроса и крякозябр), трёх языков (русский, немецкий, английский). Отличить мусор от ценного (статья или приказ по работе против временного черновика) может только модель, и точность этого различения неизвестна. В исходном плане этот слой стоял третьим и был описан одной строкой. После ревизии он стал главным этапом с пилотом и измерением точности.

**Разрывы цепи «если — то — потому что»:**
1. «Если хранить базу в Postgres на сервере, то Claude найдёт файл из любого чата, потому что…» — разрыв: чтобы Windows-сканер писал в Postgres на сервере, порт базы нужно открыть в интернет или строить туннель. Это лишняя работа и риск безопасности в самом начале. Исправление: главная база — SQLite-файл на компьютере; Claude Code на компьютере читает её напрямую. Копия на сервере нужна только для поиска с телефона при выключенном компьютере, и это решается позже по факту потребности.
2. «Если найдены дубли, то лишние можно удалить» — разрыв: число копий файла известно только после того, как просканированы все шесть дисков. Удаление после сканирования части дисков может уничтожить копию, которую сочли лишней, а единственная другая копия — на ещё не просканированном диске, который тем временем умер. Исправление: **ни одного удаления до полной инвентаризации всех шести дисков.**
3. «Если сначала сделать видео, то будет быстрый видимый результат» — разрыв относительно цели: Андрей прямо назвал приоритетом документы. Исправление: видео и музыка сдвинуты в конец.

**Нефальсифицируемое (шаги, у которых не было наблюдаемого факта провала):**
1. «Слой смысла: описания, темы» — переписан: классификация документов принимается по выборке, где Контролёр проверяет правильность меток, и порог точности задан числом (в плане этапа).
2. «Доступ для Claude» — переписан: принимается набором реальных вопросов Андрея, на которые Claude должен найти файл.

**Вычёркивается:**
1. Автоматический запуск сканирования при подключении диска как обязательная часть первой поставки. Шесть дисков — это шесть запусков руками за всё время инвентаризации; автоматика здесь не окупается. Возвращается, только если Андрей начнёт регулярно подключать диски для обновления каталога.
2. Векторный поиск (поиск по смыслу через эмбеддинги) в первой поставке документов. Полнотекстовый поиск плюс метки модели закрывают большинство вопросов; векторный поиск добавляется, если тест реальными вопросами покажет, что без него не находится.

## Обратный ход — как гарантированно провалить проект (ТРИЗ, короткий режим)

1. Начать с фильмов, потому что их больше всего и это интереснее, и не дойти до документов. Проверка реальностью: **дрейфуем** — в моём прошлом ответе видео стояло примером первого типа.
2. Сначала построить идеальную схему базы, панели и контролёров, и только потом просканировать первый диск. Проверка: **дрейфуем** — просьба о Контролёре в первый же день и опыт Second Brain, где приборы росли быстрее работы.
3. Разрешить автоматическое удаление дублей. Проверка: **пока нет** — в плане запрещено.
4. Положить в публичный репозиторий выгрузку каталога с именами файлов и путями. Проверка: **уже случалось** в archive-recon (пути личных папок и тексты статей пойманы перед записью 2026-10-10).
5. Дать документации проекта разрастись до объёма, который агенты не могут прочитать. Проверка: **уже делаем** в системе в целом — это главная названная Андреем проблема Second Brain.

Три вещи, которые прекращаем:
- приборы и контроль раньше первого просканированного диска;
- любые данные каталога в репозитории;
- рост документов проекта сверх необходимого: этот план — полный, дальше в него дописываются только решения.

Закономерность за всеми пятью: аппарат вокруг работы растёт быстрее самой работы.

## Противоречие и развязка

**Противоречие 1 (физическое).** Контролёр должен следить за прогрессом — и не должен быть прибором наблюдения, который Андрей не хочет.
Развязка — **разделение во времени и по условию.** Контролёр — это не детектор, не расписание и не панель, а роль: отдельная сессия Claude, которая вызывается только в момент приёмки этапа (ворота) или по команде Андрея. Между воротами её не существует. Она читает файл состояния проекта и выполняет фиксированные проверочные запросы к базе, выносит вердикт и пишет одну запись в журнал.

**Противоречие 2 (техническое).** Чем больше удаляем дублей, тем больше места — и тем выше риск потерять единственную копию.
Развязка — **разделение во времени и по условию.** Во времени: удаление разрешено только после полной инвентаризации всех шести дисков. По условию: удаляется только копия сверх двух, лежащих на разных физических дисках; удаление идёт через карантинную папку, а не сразу; список на удаление подтверждает Андрей.

## Решение о проекте

Новый проект **file-catalog** («Каталог файлов»). Archive-recon не поглощается и не закрывается, а становится **источником готовых решений для документов**: двухтекстовая модель страницы (сырой текст распознавания и текст для поиска со склеенными переносами), список тем, приёмка поиска реальными вопросами силами модели Opus. Основание: у archive-recon другой носитель (папка на Google Диске и сервер), другой объём (медицинские статьи) и уже налаженная цепочка; у каталога — шесть дисков на Windows и все типы файлов. Сливать их сейчас — переписывать работающее ради красоты. Точка переосмысления этого решения — начало этапа документов (подробно в плане этапов).

## В журнал

- Принято: новый проект file-catalog; приоритет документов; главная база — SQLite на Windows-компьютере; удаление только после полной инвентаризации и только сверх двух копий на разных дисках, через карантин, с подтверждением Андрея; Контролёр — роль на воротах, а не прибор.
- Отклонено: Postgres на сервере как главная база (причина — открытие порта или туннель ради того, что решается локально); видео первым типом (противоречит приоритету Андрея); автозапуск сканирования в первой поставке (не окупается на шести запусках); векторный поиск в первой поставке (не доказана нужда); слияние с archive-recon сейчас.
- Барьеры класса «твой» не снимались.
- Вердикт решаемости: решение есть; вырожденная форма (каталог только имён) названа и исключена.
