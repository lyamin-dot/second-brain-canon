# Почему вырос ночной дамп базы n8n — результат наряда Н-04.11-01 (проект SERVER, 2026-11-04)

Кто и как. Наряд Н-04.11-01, исполнитель — сессия проекта SERVER (Claude Project «01_Развитие сервера»), 2026-11-04. Только чтение: запросы к базе n8n в контейнере Postgres выполнял Андрей по SSH и присылал вывод в чат. Содержимое исполнений не выводилось — только размеры и счётчики. Замер снят в 09:43–09:46 по часам сервера (UTC), до обновления n8n с 2.42.4 до 2.46.4.
Носитель канона проекта SERVER — Google Doc SERVER_INDEX (ID — `registry/documents.md`); этот файл — отчёт-результат, а не задачи проекта. Пути на сервере сюда не пишутся (репозиторий публичный), они в снимке сервера в базе знаний Claude Project SERVER.

## Коротко

Размер ночного дампа делает одна таблица — `public.execution_data` (сохранённые входы и выходы узлов каждого сохранённого исполнения). С 31 октября основную её массу дают исполнения воркфлоу MKT2 Collect Engine (pd2K2KtImWlFfueW, проект marketplace-rebuild): в его собственных настройках включено сохранение успешных исполнений, а одно исполнение весит до 238 МБ.

2. Почему база 0,8 ГБ, а дамп 3,9 ГБ. Postgres хранит длинные значения сжатыми, pg_dump выгружает их несжатым текстом. Несжатый объём столбца `data` — 4 158 164 242 байта при 685 999 446 хранимых (сжатие примерно в 6 раз); столбец `workflowData` — 52 880 640 несжатых байт. Вместе 4,21 миллиарда байт против 3,91 миллиарда дампа, снятого в 03:00 по часам сервера; разница около 8% — исполнения, набежавшие с ночи, за вычетом удалённых очисткой. Самое тяжёлое одно исполнение — 238 214 092 несжатых байта.
Следствие для любой будущей проверки: размер таблицы на диске с размером дампа не сравнивается, сравнивается несжатый объём (`sum(octet_length(...))`).

3. Очистка истории исполнений работает. Настройки в живом контейнере n8n совпали со снимком сервера от 2026-10-07: очистка включена, срок хранения 336 часов (14 суток), предел 50 000 записей, общая настройка «успешные исполнения не сохранять». Самая старая строка таблицы — 2026-10-21, ровно 14 суток назад.

## Вывод

Прирост дампа объясняет одна таблица, `execution_data`. Сумма сходится по несжатому объёму (4,21 миллиарда байт в таблице против 3,91 миллиарда в дампе) и не сходится по размеру на диске (0,74 ГБ) — из-за сжатия. С 31 октября 72% объёма — тяжёлые исполнения MKT2 с включённым сохранением успешных исполнений.
Прогноз простой арифметикой, не наблюдение: пока тяжёлые дни продолжаются, дамп растёт примерно на 0,5 ГБ в сутки до 13–14 ноября (31 октября выйдет за срок хранения), затем выравнивается около 7–8 ГБ. Google Диск копии не чистит, свободного места (около 200 ГБ на 2026-10-16) хватит примерно на месяц таких дампов.

Не объяснено: рост с 377 МБ (2026-09-14) до около 1,1 ГБ (середина октября). Строки того времени удалены очисткой. Гипотеза (не проверена): этот рост дали сохраняемые ручные запуски — сейчас они составляют 1,14 ГБ за 14 суток, то есть уровень октябрьских дампов. Проверить напрямую нельзя; косвенно — по сохранившимся дампам сентября, если они где-то есть.

## Меры (не исполнены, решение за Андреем)

А. Выключить сохранение успешных исполнений у MKT2 Collect Engine и трёх посредников MKT2 API. Даст: дамп за 14 суток меньше примерно на 2,6 ГБ. Цена: успешные запуски MKT2 пропадут из истории исполнений, отлаживать их по ней будет нельзя; ошибочные сохраняться будут. Правка воркфлоу проекта marketplace-rebuild — по правилу о воркфлоу, с «да» Андрея.
Б. Переделать MKT2 Collect Engine так, чтобы полные ответы площадок сразу уходили в базу mkt2, а по цепочке узлов шли только счётчики. Даст: лёгкие исполнения. Цена: переделка воркфлоу, работа marketplace-rebuild.
В. Не выгружать строки таблицы исполнений в ночной дамп (ключ pg_dump `--exclude-table-data=execution_data`). Даст: дамп порядка десятков мегабайт. Цена: при восстановлении пропадёт история исполнений; воркфлоу и входы восстановятся. Правка одной строки скрипта резервной копии — проект SERVER, с «да» Андрея.
Г. Сократить срок хранения, например до 7 суток. Даст: объём примерно вдвое меньше. Цена: правка настройки и перезапуск n8n, короче история для всех воркфлоу.
Не делать: отключать сохранение ручных запусков целиком — инструменты Claude для Google Docs и Sheets (gdocs-*, gsheets-*) отдают ответ через сохранённое ручное исполнение, и путь работы Claude с ними перестанет работать.
Рекомендация исполнителя: В сейчас, А сразу после; Б — правильный путь, но долгий; Г бьёт по всем воркфлоу ради одного.

## Находки вне рамки наряда

- Одно ручное исполнение числится в статусе «выполняется». Если зависло, очистка его не тронет. Проверить запросом к `execution_entity` по `status='running'`.
- У воркфлоу MKT2 и WB Cards → Price Master в настройках часовой пояс Europe/Moscow, у инстанса — Europe/Berlin; их расписания считаются по Москве. Намеренно ли — не проверено.
- Исполнение весом в сотни мегабайт означает, что воркфлоу держит столько же в памяти за запуск; у контейнера n8n нет отдельного предела памяти, у машины 8 ГБ без подкачки. Гипотеза (не проверена): риск остановки n8n из-за нехватки памяти при параллельных запусках. Проверить: замер памяти контейнера n8n во время запуска MKT2 Collect Engine.
- Гипотеза в строке «⚡ от N8N» от 2026-10-28 в `projects/marketplace-rebuild/STATE.md` — «успешные прогоны по расписанию не сохраняются» — для воркфлоу с собственной настройкой `saveDataSuccessExecution: "all"` неверна: такие прогоны сохраняются (WB Cards → Price Master — 14 успешных по расписанию за 14 суток).
