<domain_rules>
Each rule has a reason; apply the reason to cases the rule does not name.
1. Article vs card. Declaration and other document numbers, document dates, ТН ВЭД, ОКПД 2 and «КИЗ required» are properties of the ARTICLE (our article number), the same for all four shops. What actually sits in a card, the marketplace verdict, needKiz and kizMarked are properties of the CARD and its legal entity. Never copy a card value from one shop to another: the WB main shop has errors, and kizMarked is a legal statement of one specific legal entity. Data flows source → reference → each shop, never shop → shop, never shop → reference.
2. Sources of truth (full table: PLAN.md, section «Целевая архитектура», part 2; details: meta/PROTOCOL_wb-card-write.md part 1). Values in the shops are never the truth. Declaration number — Liqui Moly site via LM_DECL_MASTER; dates — the extract (выписка), not «end minus one year»; ТН ВЭД — the extract; ОКПД 2 — only a document (extract, «Честный знак» national catalogue, importer), never by analogy unless Andrei names the cards. Exception for now: «КИЗ required» comes from the WB main shop, where staff checked it by hand.
3. kizMarked is set only on Andrei's direct word for named cards. needKiz goes into EVERY card write, equal to the value just read from the card (another value only on Andrei's word): if the body omits it, WB recomputes it to false and drops kizMarked too, even when kizMarked true is sent (case 3 of meta/CASES_wb-api-card-write.en.md, cards 1929 and 1787, 2026-10-17). A sent needKiz true keeps an existing mark; switching the mark ON is done by staff in the seller UI — neither the API nor an ОКПД 2 code turns it on (case 4).
4. A write to a WB card replaces the whole card: any characteristic not sent is erased, and kizMarked not sent becomes false. Work as read fresh card → change → compare «sending vs read» → send whole. After our writes of 04–07.10 needKiz and kizMarked dropped on 29 main-shop cards; staff restored them by hand. The most likely mechanism is the omitted needKiz (rule 3; case 3 calls it likely, not proven for those 29); the version «we erased a hidden ОКПД 2» was a conclusion recorded as fact. An ОКПД 2 written via the API is returned on read and survives the next write; one typed in the UI may be absent from the read (case 10). Writing an ОКПД 2 from the mandatory-marking list can switch needKiz on and get the card blocked if the legal entity is not registered in «Честный знак» for that group (WB ИП motor oils, 2026-10-08); registration lifts the block, a write does not.
5. Declaration into a WB card. Characteristics 15001135 (number), 15001137 and 15001138 (dates) carry dates as an array of string ДД.ММ.ГГГГ, e.g. ["18.09.2026"]; ММ-ДД-ГГ or a document without dates gives a document without a term and WB answers «Вы не приложили документ» (case 5). On a card that already has a document the characteristics alone are answered 200 and NOT applied: send them together with documents.items [{type: 2, number, startDate: "ГГГГ-ММ-ДДT00:00:00Z", endDate: "ГГГГ-ММ-ДДT00:00:00Z", isEndless: false}] in the same request — WB then creates a new document (new id) and gives a verdict in seconds (case 1). Dates in documents.items without the time part are refused with 400 «Invalid request format» (case 2). A PDF of the declaration is not uploaded to WB. The registration date comes only from the extract (выписка): never «end minus one year» (case 6); an empty date is a parser or workflow error to fix at the source, not to fill by arithmetic.
6. A 200 response is not acceptance: it means «queued». WB acceptance has two steps: (1) about 45 s after the write, re-read the card and the error list (POST /content/v2/cards/error/list) — success is a new document id with our number and both dates, the intended needKiz and kizMarked, no characteristic lost, empty error list; (2) the next day, after the night robot, the staging sheet still shows it. If at 45 s there is no new document, the write FAILED — do not wait for hours: «the WB ИП shop applies changes hours later» was a false diagnosis, the real cause was case 1 (case 7). The overall card verdict (overallVerdict) is recalculated late even when the document itself is already valid (case 7). Ozon — per-product status of the document, not the document status: an «approved» document can still have products under check for about 10 days.
6a. «Card OK» means the number AND both dates equal the source of truth; a check by number alone let cards with the right number and no dates pass as OK (case 8). The WB verdict valid proves only that the document exists and is in force, not that it covers this product: seven ИП cards had a valid РОСС 01582/26 whose item list contained none of them (case 9). Correctness is checked against the source of truth (Liqui Moly site, the declaration item list), never against the WB verdict or another shop.
6b. The WB checkbox «Документы, подтверждающие безопасность, не требуются» (documents.excludeDocuments) is a legal statement of the seller. It is set only for nmIDs Andrei names; its source in 2.0 is column docs_not_required of sheet «Ввод» (Andrei fills it, the project never computes it); it is never inferred from a missing declaration; write robots skip such cards (case 12; Andrei 2026-10-17).
7. Join by key (our article number), never by row position or IMPORTRANGE chains: a positional join once gave article 1000 someone else's Liqui Moly number. In a sheet holding several shops the key is «article + shop»: a lookup by article alone takes the first row and silently substitutes another shop's card. An error value or an empty cell is not data («пусто» in ОКПД 2 does not mean «no ОКПД 2»); a zero in an ID column (ozon_sku 0) is not data either — it makes false matches. Two Liqui Moly numbers on one article are one physical product: duplicate rows for them are intentional, do not clean them. A card's vendorCode can point to another product (ИП 1709 Marder-Spray carries 39032, a motor-oil number, case 13): a write tool compares the first word of vendorCode with our article and stops on mismatch; vendorCode is fixed by hand in the seller UI, never via the API without Andrei's decision, because it is the matching key.
8. In 2.0 books, manual input and robot output live on different sheets, because a robot rebuilding a sheet wipes manual columns (root cause R18).
9a. A Liqui Moly product page is confirmed by its identity field `<span itemprop="sku">N</span>`, never by the number appearing somewhere in the text (the page «Zentralhydraulik-Oil 2500» contains 2500). If the page is foreign, 404 or missing — search the site itself (liquimoly.ru/search) by both LM numbers and check each hit the same way. Taking the first search hit unchecked (the old Serper method) bound declarations to foreign products — rejected.
9. Garbage is something that has a better version of itself. Data kept in several places stays a source until the assembled version is built and verified; only then the old places become garbage. Probes and trial workflows are tools, never garbage: never delete or archive them. Nothing is deleted before the rebuild ends. Your own 2.0 workflows and tables carry «2.0» in the name.
</domain_rules>
