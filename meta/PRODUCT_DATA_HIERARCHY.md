# Иерархия таблиц товарных данных (Liqui Moly, Ozon, Wildberries)

Читатель: любая сессия любого проекта, которой нужен список товаров, их ключи или номера деклараций. Мастер-промпт проекта для этого не нужен: файл самодостаточен. Решение Андрея от 2026-10-02, подтверждено 2026-10-06. Обоснование — Google Doc DESIGN_единая_модель_данных_товара (1hhO6Vd5WNNmxzPfIEvvcfWeaehf0ns0FdI6imSrpNVM, 2026-10-02). Состояние описано на 2026-10-06. Ведёт лаборатория ozon-ue, задача labs/ozon-ue/t-product-data-model.md. Если файл расходится с живой таблицей, прав таблица, а расхождение записывается в эту задачу.

## 1. Главное правило

Список товаров и связь «наш артикул → номера Liqui Moly → SKU Ozon → nmID Wildberries → номер декларации» читается из ОДНОЙ таблицы: Price Master (1mntwAaplJSn3bHczqGDrzmBjotrsHe3MZ78ChViCDVk), лист Artikel. Ключ товара — наш артикул (число из 4 и более цифр). Другие копии этой связи источником не являются.

Значения: Да / Нет. Пусто = WB поле не прислал или строка не обновлялась последним прогоном; пусто не значит «Нет».
Правила чтения:
1. Маркировку КИЗ карточки брать ТОЛЬКО из колонок N и O этих двух листов. Кабинет определяется листом; колонка cabinet — контроль того, что лист выбран верно.
2. Строки двух листов не смешивать и не склеивать по our_sku: у одного артикула в двух кабинетах две разные карточки с разными nmID и разными галками. Сводка по артикулу допустима только с кабинетом в имени поля (например need_kiz_main и need_kiz_ip), никогда одним полем на два кабинета.
3. Строка с updated_at старше последнего ночного прогона — карточка, которую WB больше не отдаёт (удалена, в корзине или перенесена в другой кабинет); робот такие строки не удаляет. Пример 2026-10-09: nm_id 192910553, артикул 1108, лист WB_Cards_Staging, колонки M–O пусты.
4. kiz_marked — заявление продавца о нанесённой маркировке. Ставить его через API можно ТОЛЬКО по прямому слову Андрея на названные карточки (`projects/deklaration-wb/LOG.md` Р-7 — общий запрет; Р-10 — карточка 212515921; Р-12 — 105 карточек кабинета ИП 2026-10-09); листы только отражают карточку и в карточки не пишут.
Снимок 2026-10-09 (прогоны n8n 77462 и 77464): основной кабинет — 456 карточек, Да/Да 340, Нет/Нет 116; кабинет ИП — 215 карточек, Да/Да 2, Да/Нет 104 (все 96 карточек «Масла моторные» и 8 «Автохимия»), Нет/Нет 109.
4в. ЛИСТ СРАВНЕНИЯ WB_Compare в Price Master (введено 2026-10-09 по задаче Андрея; решение — `projects/deklaration-wb/LOG.md` Р-11). Строка на наш артикул листа Artikel; по четырём критериям (декларация, ТН ВЭД, ОКПД 2, маркировка КИЗ) — эталон, основной кабинет, кабинет ИП и итог проверки. Только формулы в строке 2 (ARRAYFORMULA до строки 1000); ничего не пишет ни в WB, ни в другие листы; обновляется сам после ночных прогонов обоих роботов карточек.
Колонки: A sku, B product_name (Artikel H), C nm_main, D nm_ip (nmID карточки в кабинете; пусто — карточки нет), E ref_decl (эталон: декларация по номеру Liqui Moly из LM_DECL, Artikel X), F main_decl, G ip_decl (декларация карточки: колонка Q листа карточек, если не пуста, иначе F), H decl_check, I main_tnved, J ip_tnved, K tnved_check (эталона ТН ВЭД в таблицах пока нет — сравниваются только кабинеты между собой), L ref_okpd2 (эталон: ARTIKEL_PROPS okpd2, только из документов), M main_okpd2, N ip_okpd2, O okpd2_check, P ref_kiz_required (ARTIKEL_PROPS kiz_required), Q main_need_kiz, R main_kiz_marked, S ip_need_kiz, T ip_kiz_marked, U kiz_check.
Значения проверок: «ок»; «нет эталона» — сравнивать не с чем; «нет карточек» — артикула нет ни в одном кабинете; «осн: пусто» и «ИП: пусто» — карточка есть, поле пустое; «осн≠эталон» и «ИП≠эталон» — поле заполнено другим значением; в tnved_check — «одинаково», «осн≠ИП», «карточка в одном кабинете»; в kiz_check — «осн: КИЗ нужен, не подтверждён», «ИП: КИЗ нужен, не подтверждён», «метка КИЗ разная» («Нужна маркировка КИЗ» в кабинетах различается). Несколько находок в одной ячейке идут через пробел.
Правила:
1. Эталон — не основной кабинет. Копировать значения из одного кабинета в другой нельзя: в основном кабинете есть ошибки, а галка kiz_marked — заявление конкретного юрлица. Правильный поток — эталон → оба кабинета.
2. «пусто» в okpd2_check не доказывает, что ОКПД 2 в карточке нет: введённое руками в кабинете API не показывает.
3. Лист берёт по нашему артикулу первую карточку кабинета. На 2026-10-09 повторов our_sku нет ни в одном листе карточек; если появятся, вторая карточка артикула в листе не видна. Строка карточки, которую WB больше не отдаёт (правило 3 раздела 4б), попадает в сравнение как живая: пример — артикул 1108, «метка КИЗ разная» из-за старой строки 192910553.
4. ИСТОЧНИКИ ИСТИНЫ для карточек WB (решение Андрея 2026-10-09, `projects/deklaration-wb/LOG.md` Р-12): декларация — сайт Liqui Moly (лист LM_DECL книги LM_DECL_MASTER, здесь — колонка E ref_decl); даты декларации — лист «Декларации» книги LM_DECL_MASTER (date_from, date_to); ТН ВЭД — та, что в выписке декларации (по артикулам записана пока только для 68827/26 по блокам: первый блок 3403199000, второй 3403990000 — журнал того же проекта Р-4); значения в личных кабинетах WB истиной НЕ считаются. Исключение — признак «нужен КИЗ»: на этом этапе он берётся из ОСНОВНОГО кабинета (колонка Q main_need_kiz), потому что там его недавно проверили руками по каждому товару. Эталон P ref_kiz_required (ARTIKEL_PROPS kiz_required) УСТАРЕЛ: на 2026-10-09 у части автохимии там «Нет» при «Да» в основном кабинете — по нему не решать, пока колонка не перестроена на основной кабинет. ## 4. Правила чтения

- Склеивать данные по ключу «наш артикул», не по номеру строки. 2026-10-06 прогон 76252 показал артикул 1000 с LM_ID_1 = 1015 вместо 1340, а причину не удалось доказать; позиционная склейка двух цепочек IMPORTRANGE допускает такой сдвиг. Колонки F:G Artikel с 2026-10-06 (правка Андрея) берутся по ключу.
- Ошибка и пустая ячейка не данные. #N/A в wb_nm_id не значит «карточки нет» (см. раздел 5).
- Изменять таблицы можно только с явного «да» Андрея. Действующую декларацию в карточке не заменять: заполняются только пустые и просроченные. Даты в карточках WB — ММ-ДД-ГГ (01-27-27 = 27.01.2027).
