# Контракт содержания STATE.md — что остаётся в файле состояния проекта

Записан 2026-10-30 сессией SYS по решению Андрея 2026-10-30 (ревизия системы, шаг 1 плана после ревизии; ход — `labs/sys/t-system-revision.md`). Один файл, два читателя: уборка файла состояния (шаг 5 ревизии) и проверка при записи. Проверку исполняет скрипт `meta/scripts/state_split.py` (режим `check` — отчёт без записи, режим `split` — разбор по ролям с приёмкой по строкам); его зовут три входа: шаг !save по проекту в репозитории, контракт автопилота, любой скрипт переноса. Отдельный воркфлоу-монитор не заводится — решение Андрея 2026-10-30.

Читатель STATE.md — старт каждой сессии проекта (Skill second-brain-git, раздел 4: бюджет чтения 8 192 байта). Бюджет ограничивает читателя, не запись; отказа в записи по размеру не существует (references/write.md, 5.5). Этот контракт задаёт не число, а содержание.

## Правило

Строка остаётся в STATE.md, если она относится к одной из четырёх категорий — то, что меняет действие следующей сессии:

1. **Следующий шаг** — что делать первым; один раздел, не три.
2. **Открытый вопрос с критерием закрытия** — вопрос Андрею или владельцу объекта и признак, по которому он считается закрытым (CORE Р.6, шаг 0.3: вопрос без критерия не пишется).
3. **Блокер** — что стоит прямо сейчас и из-за чего.
4. **Состояние объекта с датой проверки** — «на такую-то дату объект проверен и находится в таком-то состоянии» (CORE Р.6, шаг 0.2: дата и предмет проверки, не статус).

Раздел «От соседнего проекта» — четвёртой категории: факт, который сессия проекта ещё не прочитала. Прочитав и приняв решение, сессия тем же шагом переносит строку в журнал или в открытый вопрос — иначе раздел растёт без предела (на 2026-10-30 — 20 096 байт в deklaration-v2, 8 616 в n8n). Момент разбора — любая запись своего STATE.md, а не команда !save: летописи пишут шаг сразу. Кандидатов называет `state_split.py check` (с 2026-11-06): строки раздела старше 7 дней по первой дате в строке и строки длиннее 500 Б (форма — одна строка, подробности — в журнале отправителя); правка Skills — `meta/EDITS_skills_2026-11-06.md`, позиция AJ-85 очереди.

Всё остальное — не по роли и уезжает тем же save:

| Что | Куда | Чем |
|---|---|---|
| сделанное с датой, перекрытый или прежний «следующий шаг», сверка, проба, снимок чисел | LOG.md — блок хроники по форме second-brain-git 11.5 | Git Append File (references/write.md, 8.3) |
| правило проекта («как отвечать», «источники истины», «как устроено») | PLAN.md проекта | Git Replace или Git Write |
| факт домена, нужный другим проектам (поведение API, свойство площадки) | файл кейсов `meta/CASES_<тема>.md` | то же |
| таблица товаров, список паспортов, перечень документов | PLAN.md или реестр; в STATE.md — одна строка-указатель | то же |
| предложения сессии, не принятые Андреем | задача лаборатории или открытый вопрос с критерием; иначе — не пишется | — |

Ужимать формулировки ради бюджета ЗАПРЕЩЕНО (references/write.md, 5.1): уборка — перенос, не удаление; удаляется только дубль того, что уже живёт в журнале, Skill или реестре, и снимок чисел, устаревший к моменту записи.

## Парное правило: исполнил — закрой запись

Исполнив задачу, решение или правку, сессия тем же шагом закрывает запись, которая этого ждала: строку STATE.md, задачу лаборатории, позицию очереди. Это правило внесено в Skill second-brain-engineer позицией AJ-57 (`meta/EDITS_skills_2026-10-27.md`, пункт А1) и действует после заливки — залито: ВНЕСЕНО 2026-10-31, живой second-brain-engineer SKILL.md, Р6, «Исполненная работа закрывает запись» (`registry/maintenance-queue.md`, AJ-57; принято по снимку) (сверка харвеста 2026-10-31).

## Признак провала уборки

Следующая сессия проекта после уборки спрашивает о факте, который из STATE.md убран, или принимает решение, противоречащее убранной строке. Проверяется по журналу проекта и по первому старту после уборки. Такой случай записывается в `labs/sys/t-system-revision.md` с адресом убранной строки — и правило правится, а не отменяется уборка.

## Пилот 2026-11-07: короткая строка вместо абзаца (только projects/deklaration-v2/)

Решение Андрея 2026-11-07 (чат SYS): «Я даю добро на все твои предложения, но пока только для пилотного проекта». Область правила — только `projects/deklaration-v2/` до решения Андрея по итогам пилота; в остальных проектах правило не действует. Ход и итог — `labs/sys/t-system-revision.md`, разделы «Предложение 2026-11-07» и «Итог пилота 2026-11-07».

1. Строка STATE.md пилотного проекта не длиннее 500 байт (UTF-8).
2. Строка длиннее 500 байт заменяется короткой строкой той же категории (четыре категории выше). Короткая строка называет категорию, суть открытого дела, условия-ограничения действия (например, «только по слову Андрея», «ничего не отправлять без подтверждения») и несёт указатель: «(полностью — LOG.md, хроника ГГГГ-ММ-ДД, строка, начинающаяся словами «…»)». Слова в кавычках начинают ровно одну строку журнала; дата — дата блока хроники. Открытый вопрос в короткой строке сохраняет критерий закрытия, состояние объекта — дату проверки.
3. Сама длинная строка уезжает без изменения в блок хроники в конце LOG.md скриптом `meta/scripts/state_apply.py` (действие «replace»; приёмка скрипта по мультимножеству строк). Руками и моделью длинная строка не набирается.
4. Дело, закрытое или отменённое, уезжает без короткой строки, но только с адресом доказательства — объектом, прочитанным в той же сессии, — в записи журнала проекта или в разделе итога пилота; строка соседа принимается записью Р журнала проекта-получателя.
5. Это не «ужимание формулировок»: короткая строка — новый текст сессии, а прежний абзац остаётся в журнале проекта целиком, без изменений, и достижим по указателю. Запрет «Ужимать формулировки ради бюджета ЗАПРЕЩЕНО» и правило «уборка — перенос, не удаление» действуют без изменений. Строка, которую нельзя уложить в 500 байт без потери условия или дела, остаётся длинной с названной причиной в итоге пилота.
6. Размер STATE.md пилот фиксирует как факт, не как порог: бюджет 8 192 байта — прежний, превышение называется прямо.

## Что контракт не делает

- Не ограничивает размер файла числом: файл над бюджетом после разбора по ролям остаётся над бюджетом, и это не дефект (references/write.md, 5.5, пункт 3).
- Не трогает LOG.md: журнал только дописывается и читается по оглавлению.
- Не отменяет сам скрипт разбора: заголовки разделов — подсказка скрипту, спорные разделы скрипт откладывает в UNDECIDED, решает сессия или Андрей.
