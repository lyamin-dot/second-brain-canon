# План: цена чтения Skills — ревизия denken и шаги

Автор: сессия SYS (Аргус, модель Claude Opus 5.5), 2026-10-20. Замысел, предпосылки и доказательства — `meta/PROPOSAL_skill-reading-cost_2026-10-20.md`; этот файл без него не читается. Назначение: второе мнение до начала работы. Ничего из плана не исполнено.

Ревизия Р2 — затронуты несколько файлов двух Skills и таблица маршрута; синтез неочевидный; операция обратимая (живой Skill меняет только Андрей заливкой, прежняя версия лежит в зеркале `skills/`).

## Барьеры

Жёсткие:
- Сессия не может изменить живой Skill: она видит его только для чтения, правит и заливает zip-архив Андрей (Customize → Skills). Значит, каждый шаг, меняющий Skill, заканчивается действием Андрея.
- В сессиях claude.ai без репозитория в источниках прямая отправка в репозиторий (`git push`) закрыта; в этой сессии попытка добавить репозиторий отклонена системой безопасности харнесса. Нарезка файла — перенос существующего текста, поэтому делается только скриптом с отправкой в репозиторий (маршрут 9.4(б) Skill `second-brain-git`), то есть в сессии, открытой на репозитории (Claude Code), или руками Андрея.

Твои:
- Номера пунктов Skill сохраняются при нарезке (решение Р-12 журнала `projects/kontext-reduktion/LOG.md`). Цена снятия — правка ссылок во всех файлах репозитория и журналах. Не снимаем: нарезка с сохранением номеров уже делалась дважды.
- Сокращение — не цель (предпочтение Андрея 2026-09-26). План ему не противоречит: ни одно правило не сокращается, меняется только то, какой файл читается для какого действия. Снимать не нужно.
- Порядок синтеза: следующий — `second-brain-engineer`. Цена снятия — нарезка `second-brain-git` встаёт раньше синтеза `second-brain-engineer`; сам синтез от неё не зависит. Предлагаю нарезку вести параллельно, синтез не останавливать.

Свои (что сессия додумала сама, Андрей этого не требовал):
- что цена чтения Skills вообще существенна для расхода лимита Андрея (не проверено — см. самое слабое звено);
- что мерило «килобайты на вид действия» лучше других;
- что нарезать нужно именно write.md, а не основные файлы;
- что повторный тест после нарезки нужен в объёме теста 1, а не меньше.

## Вердикт решаемости

Решение есть: нарезка write.md по видам записи с сохранением номеров, уточнение строк таблицы, перенос проверяемых правил в код Канала. Жёсткие барьеры обходятся тем, что сессия готовит скрипт и архив, а исполняют их Андрей или сессия с открытой отправкой.

Показание к операции по каждому объекту:
- write.md (59 775 байт) — читается перед любой записью, а пишущей сессии с одной дозаписью нужно около 25 КБ (доказательство Д6 замысла). Показание есть.
- delivery.md — строка «несколько записей подряд» требует файл, чьё правило продублировано в write.md 8.6 (Д3). Показание есть, только на строку таблицы, не на файл.
- Основные файлы `SKILL.md` обоих Skills — показания нет: не измерено, какая их часть не нужна большинству сессий. Из плана выведены.
- design.md, migration.md и прочие — читаются редко и только по делу (Д4). Показания нет.

## Дефекты плана

Самое слабое звено: выигрыш не доказан в том, ради чего он нужен. Нарезка уменьшает байты в контексте, но неизвестно, какую долю лимита Андрея эти байты стоят: повторное чтение контекста в длинной сессии частично идёт из кеша и обходится дешевле. Поэтому шаг 1 ниже — замер, и план разрешено остановить на нём.

Разрывы «если — то»:
- «Если таблица точнее, то сессии прочитают меньше, потому что они исполняют таблицу буквально» — основание есть (Д4, восемь сессий). Но оно получено на старой таблице; на новой, где строк больше, сессия может выбрать не ту строку. Закрывается шагом 6 (повторный тест).
- «Если правило в коде Канала, то его текст можно убрать из Skill» — разрыв: текст правила нужен и как объяснение, почему воркфлоу отказал. Исправлено: из Skill убирается механика, остаётся одна строка «Канал отбивает такую запись, потому что…».

Нефальсифицируемое в исходном замысле: «версия станет экономичной». Переписано в проверяемое: «для каждого вида действия число килобайт Skill уменьшилось, нарушений в повторном тесте ноль».

Вычёркивается: отдельная сводка запретов (раздел 14 write.md, 4 300 байт) кажется дублем, но её снятие — сокращение содержания, а не маршрута. Решение о ней — синтез, не этот план.

## План после ревизии

Шаг 0. Второе мнение. Исполнитель — Андрей. Результат — ответ на вопросы раздела 9 замысла. Если второе мнение опровергает рычаг, план останавливается здесь.

Шаг 1. Замер цены. Исполнитель — сессия SYS. Скрипт считает по таблицам «Что читать дальше» обоих Skills и размерам файлов, сколько килобайт Skill читает сессия для каждого вида действия (дозапись в Очередь, запись в журнал, задача лаборатории, !save, правка Skill, ротация). Отдельно — сколько токенов из итога тестовых сессий приходится на текст Skills, по их журналам. Результат — таблица в файле `meta/` с отметкой blob sha прочитанных Skills. Остановка: если Skills меньше пятой части контекста пишущей сессии, план дальше не идёт.

Шаг 2. Схема нарезки write.md. Исполнитель — сессия SYS. Каждому пункту write.md назначается вид записи, которому он нужен; пункты, нужные всем, остаются в write.md. Черновик разреза: write.md (общая механика: 2.1–2.5, 4.5, 8.1–8.3, 8.6, 8.7, 14, около 30 КБ); skill-edit.md (2.6, около 10 КБ); log-form.md (11, около 7 КБ); project-save.md (4.6, 4.7, 5.x, 10, около 12 КБ). Новые строки таблицы «Что читать дальше». Строка «несколько записей подряд» удаляется: её правило живёт в write.md 8.6. Результат — файл схемы в `meta/` с килобайтами на вид действия до и после.

Шаг 3. Приёмка схемы. Исполнитель — субагент высокого класса, схему не делавший. Вопрос: для каждого вида записи — есть ли правило, которое ему нужно, а по новой таблице окажется в файле, который он не откроет. Ответ — список с адресами пунктов или NOT_FOUND. Не более двух кругов правок.

Шаг 4. Нарезка скриптом. Исполнитель — сессия, где проходит `git push --dry-run` (Claude Code на репозитории), или Андрей вручную по инструкции. Скрипт режет по границам пунктов, номера не меняются, приёмка — каждая непустая строка исходника ровно в одном файле результата (правило 9.4 Skill `second-brain-git`). Результат — зеркало `skills/second-brain-git/` обновлено коммитом и собран zip.

Шаг 5. Заливка. Исполнитель — Андрей. Результат — снимок Skill в новой сессии совпадает с зеркалом (сверка в обе стороны, пункт 2.6).

Шаг 6. Повторный тест. Исполнитель — сессия SYS. Те же пять задач, что в тесте 1, свежие сессии, сухой прогон, счёт скриптом по журналам. Критерий: нарушений правил ноль; открыты все файлы, которых требует новая таблица; килобайты на вид действия меньше, чем в шаге 1. Опровержение — хотя бы одно нарушение правила, переехавшего в новый файл: тогда возврат прежней версии из зеркала и запись тупика.

Шаг 7. Правила в код Канала (отдельная дорожка, каждое — по «да» Андрея на правку воркфлоу). Первым — вход Git Replace из файла Google Drive (решение Андрея Б1 от 2026-10-18, задача `labs/sys/t-git-replace-escape.md`). Результат — в Skill вместо механики правила одна строка о том, что Канал делает сам.

Синтез `second-brain-engineer` идёт параллельно и от шагов 1–6 не зависит; строка основания — в форме решения 5 от 2026-10-20.

## Ручные действия Андрея

Шаг 0 (второе мнение); шаг 4, если нет сессии с открытой отправкой; шаг 5 (заливка zip); «да» на каждую правку воркфлоу в шаге 7.

## В журнал

Отклонено: перестройка по цене пропуска — два теста повода не дали; нарезка основных файлов `SKILL.md` — показание не измерено; снятие сводки запретов write.md в этом плане — это сокращение содержания, решается синтезом; утверждение «версия экономичная» — без замера альтернативы не проверяемо.
Барьеры класса «твой» не снимались.
Вердикт решаемости: решение есть; самое слабое звено — неизмеренная доля чтения Skills в реальном расходе лимита (шаг 1 может остановить план).
