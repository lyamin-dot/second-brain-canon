## 5. Корневые причины — индекс-роутер

**Закон раздела.** Корень — это место, где отчёт n8n о себе расходится с объектом воздействия *(A1)* или где движок теряет данные молча *(A2)*. Поэтому каждый корень записан одинаково: симптом → механизм → адрес фикса, а доказательство фикса — всегда объект или факт исполнения, никогда ответ инструмента. Копируемые артефакты — в references/templates.md (§6, T1–T5).

Строки «Основание» называют номер правила; адреса случаев — в отчёте синтеза 2026-10-20 по этому номеру.

**Поиск по смыслу сравнения (правило §5.1).** Место, где воркфлоу берёт параметр из таблицы, ищется по смыслу сравнения — какое поле с каким сравнивается, — а не по значению параметра. Почему: поиск по значению находит совпадения и потому систематически прячет как раз расхождения, ради которых ищут.
Основание: 1 случай, последний 2026-08-08 — отчёт синтеза, правило §5.1.

**R1a. Привязка ключа доступа (credential): промах автопривязки, узел без ключа, разрыв при переименовании.**

Закон корня. Привязка ключа — свойство узла, которое движок хранит в сохранённой версии воркфлоу и переносит в следующую запись по имени узла. Она переживает `update_workflow` и публикацию, но сама не возникает: её создаёт либо адресная операция с id ключа, либо владелец руками в редакторе, либо автопривязка MCP, которая выбирает ключ сама и может выбрать чужой. Отсюда правило для любой записи, которая создаёт узел с ключом или переименовывает его: после записи сверить, какой ключ у какого узла, прямыми показаниями (ниже), а не текстом предупреждения.

Частные формы:

- **Адресная привязка через MCP (правило R1a.1).** В точечной форме `update_workflow` есть операция `setNodeCredential` (поля `nodeName`, `credentialKey`, `credentialId`, `credentialName`): она привязывает ключ к узлу по id. Операция `addNode` с полем `credentials` (`{id, name}`) привязывает ключ новому узлу тем же вызовом. Операции одного вызова применяются атомарно: если падает одна, не сохраняется ничего. Значит, ключ новому узлу ставится в том же вызове, где узел создаётся, а не «потом руками». Не путать: «MCP не умеет привязывать ключ адресно» — так было, пока запись шла только кодом SDK с `newCredential('Name')`; схема и пробы точечной формы это опровергли.
  Основание: 3 случая, последний 2026-10-18 — отчёт синтеза, правило R1a.1.
- **Промах автопривязки (правило R1a.2).** Где ключ подставляет автопривязка, она берёт самый недавно отредактированный ключ подходящего типа; если ключей этого типа на инстансе несколько (Google, маркетплейсы, Header Auth), попадание случайно. Имя в `newCredential('Name')` при `create_workflow_from_code` автопривязку не направляет: вебхук получил ключ совсем другого сервиса. Правило: после `create_workflow_from_code` и после каждого `update_workflow` прочитать поле `autoAssignedCredentials` ответа; непустое — проверить, какой ключ подставлен, и чужой заменить операцией `setNodeCredential`.
  Признак: межворкфлоушный вызов или вызов внешнего API отбит аутентификацией сразу после создания, хотя в коде стоит правильное имя ключа.
  Основание: 3 случая, последний 2026-10-18 — отчёт синтеза, правило R1a.2.
- **Узел остался без ключа (правило R1a.3).** Узел, которому ключ не поставили ни операцией, ни владелец, падает с «Credentials not found». Это штатный шаг, а не авария: в плане правки заранее пишется, кто и каким путём привязывает ключ к каким узлам (сессия сама, операцией `setNodeCredential` в той же записи; участие владельца не нужно — решение Андрея 2026-10-20), и узел не включается в боевую цепочку до привязки. Запись кодом целиком (`create_workflow_from_code`, реконструкция чужого воркфлоу — §2.6) новым HTTP-узлам ключ не создаёт.
  Основание: 6 случаев, последний 2026-10-06 — отчёт синтеза, правило R1a.3.
- **Переименование узла с ключом (правило R1a.4).** Точечная операция `renameNode` привязку ключа сохраняет. При записи кодом целиком (R1b) привязка переносится по имени узла с последней сохранённой версии, поэтому узел, переименованный в переданном коде, остаётся без ключа, и возврат прежнего имени привязку не чинит. Правило: узел с ключом переименовывать операцией `renameNode`, а не в переданном коде; ключ, пропавший у узла по любой причине, сессия привязывает сама операцией `setNodeCredential` — участие владельца не нужно. Не путать: «переименование рвёт привязку» — верно только для записи кодом целиком, не для операции `renameNode`.
  Основание: 2 случая, последний 2026-10-14 — отчёт синтеза, правило R1a.4; проба не нужна — решение Андрея 2026-10-20.

Ручная привязка в редакторе тянет за собой риски R17 (нормализация конфига и побочная публикация при Save). Секрет при любой привязке не проходит через чат, текст узла или репозиторий: ключ создаёт сам владелец и присылает в чат только его название *(§2.1, R13)*. Миграция ключа у многих узлов — запрет в §2.3 (references/write.md, правило §2.3.7).

**Как проверять привязку (правило R1a.5).** Текст предупреждения MCP «…credentials must be configured manually» — шаблон, печатается всегда и состояния не отражает *(A1)*. Прямых показаний два:
- поле `autoAssignedCredentials` в ответе записи — единственное место, где промах автопривязки виден в момент записи *(§2.3 пункт 4)*;
- поле `credentials` у узла в ответе `get_workflow_details` — приходит с id и именем ключа (впервые замечено 2026-10-08; когда поведение инструмента изменилось, неизвестно; проверено на HTTP-узлах двух воркфлоу, на остальных типах узлов не проверено).
Отсутствие поля `credentials` у узла ещё не значит «ключа нет», а имя ключа в поле не доказывает, что ключ рабочий и бьёт в свой домен *(R13)*: окончательное доказательство — реальный прогон по объекту *(R4)*.
Не путать: «`get_workflow_details` не показывает `credentials` никогда» — так наблюдалось на 2026-09-17; на 2026-10-08 поле пришло, а когда поведение сменилось, неизвестно. Поэтому ни отсутствие, ни наличие поля в старых записях сессий не говорит о нынешнем поведении — читать свежий ответ.
Основание: 2 случая, последний 2026-10-08 — отчёт синтеза, правило R1a.5.
→ **§2.3**, **T4 гейт 6.**

**R1b. Запись воркфлоу кодом целиком пересобирает его из переданного кода и молча теряет всё, что код не несёт или что SDK не умеет передать.**

Закон корня. Запись кодом целиком — `create_workflow_from_code` и любая запись, передающая воркфлоу кодом SDK целиком, — не правит воркфлоу точечно: она собирает каждый узел заново из переданного кода и сохраняет результат целиком. Поэтому теряется не «то, что правили», а всё, чего в коде нет или что SDK отбрасывает по дороге, и цена записи не зависит от размера правки. Ошибки при этом нет: `validate_workflow` и инструмент записи отвечают успехом *(A1, A2)*.

**Граница корня — форма `update_workflow` (правило R1b.0).** `update_workflow` принимает не код, а список точечных операций (`setNodeParameter`, `updateNodeParameters`, `addNode`, `removeNode`, `renameNode`, `addConnection`, `removeConnection`, `setNodeSettings`, `setWorkflowSettings`, `setNodeCredential` и другие) и применяет их атомарно. Пробами установлено: замена кода узла Code сохранила настройки воркфлоу, аутентификацию вебхука, `webhookId` и привязки ключей; `setWorkflowSettings` ставит `timezone`; `setNodeSettings` сохраняет `retryOnFail`, `maxTries`, `waitBetweenTries`; нетронутые узлы и их id остаются прежними; правка условия IF операцией оставляет выражение живым. Механизм этого корня к точечной правке не относится. Не проверено точечной правкой: узлы Switch и правка самого узла-вебхука — для них сверка §2.3 обязательна.
Не путать: «`update_workflow` пересобирает воркфлоу из переданного кода» — так инструмент работал, когда корень записывали; для точечной формы опровергнуто.
Основание: 2 случая, последний 2026-10-12 — отчёт синтеза, правило R1b.0.

Наблюдавшиеся потери записи кодом целиком, все — без предупреждения:
- **Настройки воркфлоу (правило R1b.1).** Часовой пояс (`settings.timezone`) и воркфлоу ошибок (`errorWorkflow`) сбрасываются, даже когда записаны в коде. Метода `.settings()` в SDK нет; настройки, переданные третьим аргументом `workflow(id, name, {settings})`, проходят `validate_workflow` и всё равно не применяются. Следствие: расписание без часового пояса уезжает по R7, а отказ становится немым, потому что воркфлоу ошибок больше не назначен. Лечение — после каждой записи кодом целиком прочитать настройки и выставить их операцией `setWorkflowSettings` (точечная форма `update_workflow`) или руками в редакторе (Settings воркфлоу), и только потом публиковать.
  Основание: 7 случаев, последний 2026-10-17 — отчёт синтеза, правило R1b.1.
- **Повторные попытки узла (правило R1b.2).** `node({config:{retryOnFail:true, maxTries:N, waitBetweenTries:M}})` сохраняется как один `retryOnFail:true`; `maxTries` и `waitBetweenTries` SDK отбрасывает, в силе умолчания n8n (3 попытки, интервал около секунды). Заявленный бюджет повторов и фактический расходятся.
  Основание: 2 случая, последний 2026-10-02 — отчёт синтеза, правило R1b.2.
- **Выражения в условиях IF и Switch (правило R1b.3).** Выражение превращается в строковый литерал: условие сравнивает буквальный текст вместо значения поля и не срабатывает никогда. Воркфлоу, скопированный с дефектного воркфлоу другой площадки, наследует тот же дефект. Признак на графе — в поле условия нет двойных фигурных скобок `{{ … }}`.
  Основание: 1 случай, последний 2026-10-05 — отчёт синтеза, правило R1b.3.
- **Сопоставление колонок Sheets (`matchingColumns`) сбрасывается (правило R1b.4).**
  Основание: 1 случай, последний 2026-06-30 — отчёт синтеза, правило R1b.4.
- **Связи (правило R1b.5).** Теряются ветки IF; второй выход `.to([a,b])` молчит навсегда *(§4.5)*; ветка, которую уже чинили, пропадает снова.
  Основание: 4 случая, последний 2026-07-23 — отчёт синтеза, правило R1b.5.
- **Аутентификация вебхука (правило R1b.6)**, если параметра `authentication` нет в коде триггера *(R12, §2.2 пункт 4)*.
- **`webhookId` узла, которого не правили (правило R1b.7).** Полная пересборка сменила его у нетронутого узла-вебхука; вызывающие по старому пути получают отказ.
  Основание: 1 случай, последний 2026-09-05 — отчёт синтеза, правило R1b.7.
- **Гонка с открытой вкладкой редактора** — побеждает последний сохранивший *(R17)*.

**Что НЕ теряется (правило R1b.8):** привязка ключей доступа у существующих узлов. Она переживает запись и публикацию, MCP наследует её по имени узла; рвётся при переименовании, а новому узлу при записи кодом не создаётся — это корень R1a, а не R1b.
Не путать: «после записи слетают credentials» — опровергнуто трижды; подозрение на сброс ключа после записи значит искать другую причину (эта ложная версия уже уводила диагноз мимо настоящей причины).
Основание: 4 случая, последний 2026-10-05 — отчёт синтеза, правило R1b.8.

**Рецидив (правило R1b.9).** Одна и та же потеря повторяется при следующей записи кодом целиком, поэтому сверка нужна после КАЖДОЙ такой записи, а не только первой. Правку одного узла боевого воркфлоу кодом целиком не делать вовсе — выбор пути записи в §2.4.
Основание: 2 случая, последний 2026-08-04 — отчёт синтеза, правило R1b.9.
→ **§2.2**, **§2.3**, **§2.4**, **T4 гейт 6.**

**R2. У воркфлоу две версии, и исполняется не та, что видна в редакторе.**

Закон корня. Воркфлоу живёт двумя версиями: черновик (`versionId`, его видно в редакторе и его исполняет ручной запуск) и опубликованная (`activeVersionId`, её исполняют расписание, вебхук и запуск `execute_workflow` в режиме `production`). `active:true` говорит только, что что-то опубликовано, а не что именно *(A1)*. Поэтому любое утверждение «воркфлоу делает X» проверяется по той версии, которая будет исполняться, а публикация отправляет в работу весь черновик, а не только свою правку.

- **Триггер не перерегистрируется (правило R2.1).** После правки и публикации поверх активного воркфлоу cron или вебхук может не создавать исполнений — без ошибок и предупреждений, при целом конфиге и `active:true`. Лечение — только полный тумблер `unpublish_workflow` → `publish_workflow`.
  Диагностика: сравнить `versionId` и `activeVersionId` из `get_workflow_details`; при расхождении — сверить верхнеуровневые `nodes` с `activeVersion.nodes` по триггерному узлу. Тот же вид расхождения даёт ручная правка интервала Schedule Trigger в редакторе: черновик показывает новый час (`triggerAtHour`), опубликованная версия остаётся с умолчанием `rule.interval:[{}]`.
  Основание: 3 случая, последний 2026-07-23 — отчёт синтеза, правило R2.1.
- **Живость расписания без сохранённых успехов (правило R2.2).** Грубая эвристика «`updatedAt` против времени последнего исполнения» допустима, только когда версии недоступны и только у воркфлоу, у которого сохраняются успешные прогоны: если успехи не сохраняются (`EXECUTIONS_DATA_SAVE_ON_SUCCESS=none` на инстансе или `saveDataSuccessExecution` в настройках воркфлоу, *R4*), отсутствие исполнения в списке ничего не значит. Живость такого расписания видна по счётчикам `production_success` и `production_error` таблицы `workflow_statistics` базы n8n — прунинг их не чистит. Запрос готовит сессия, выполняет Андрей на сервере (`psql` в контейнере базы).
  Основание: 1 случай, последний 2026-07-23 — отчёт синтеза, правило R2.2.
- **Какой запуск какую версию исполняет (правило R2.3).** Ручной запуск через MCP (`execute_workflow`, режим `manual`) исполняет черновик; расписание и `execute_workflow` в режиме `production` — опубликованную версию. Отсюда: пробный прогон правки делается черновиком, без публикации; зелёный ручной прогон ничего не говорит о том, что ночью исполнит расписание; тест в режиме `production` даёт зелёный отчёт на старом коде. Исключение для воркфлоу с триггером расписания — §2.4 и T5 (пробность задаётся только явным параметром режима).
  Основание: 3 случая, последний 2026-09-25 — отчёт синтеза, правило R2.3.
- **Остановить можно только снятием публикации (правило R2.4).** Выключение триггера, сохранённое только в черновике, воркфлоу не останавливает — расписание продолжает исполнять опубликованную версию. Остановка — `unpublish_workflow`, и проверяется она чтением `active:false`, а не словами «выключил», в том числе словами владельца *(§2.5)*.
  Основание: 2 случая, последний 2026-10-05 — отчёт синтеза, правило R2.4.
- **Черновик, расходящийся с опубликованной версией, — ловушка для следующей публикации (правило R2.5).** `publish_workflow` отправляет в работу весь черновик. Если в черновике раньше выключили триггер (`disabled: true`) или оставили незаконченную правку, попутная публикация молча остановит расписание или сменит поведение воркфлоу, ошибки не будет *(A2)*. Правило: перед `publish_workflow` воркфлоу, у которого `versionId` не равен `activeVersionId`, сравнить версии инструментом `get_workflow_versions_diff` (опубликованная версия → черновик) и публиковать, только если все различия — свои. Чужое различие — вопрос проекту-владельцу воркфлоу, а не попутная публикация. Инструмент сравнения даёт тот же результат, что ручная сверка полей `activeVersion.nodes` и `nodes`.
  Признак: `versionId ≠ activeVersionId` у воркфлоу, которое сессия не правила.
  Основание: 2 случая, последний 2026-10-17 — отчёт синтеза, правило R2.5.
→ **T4 качество 10.**

**R3. 0 items тихо обрывают цепочку.**
Для n8n 0 items — штатная остановка, не ошибка *(A2)*: всё ниже такого узла молча не исполняется. Причины:
- `alwaysOutputData` выключен ИЛИ положен внутрь `parameters` вместо верхнего уровня узла (тихо игнорируется);
- неподключённая ветка IF, которую ждёт Merge или петля цикла;
- выключенный (disabled) узел пропускает item насквозь;
- обрыв трассировки pairedItem на пачке *(механика — §4.4)*;
- узел Google Sheets с операцией «create» на уже существующем листе отдаёт 0 items.
Основание: 5 случаев, последний 2026-10-08 — отчёт синтеза, правило R3.1.
→ **T1** (шаблон и дискриминатор терминала).

**R4. Статус `success` и код 200 не доказывают реального успеха; журнал исполнений ненадёжен и дорог.**

Закон корня. Исполнение «успешно», если движок не упал; данные при этом могли не прийти и не записаться. Поэтому итог любой правки и любого прогона проверяется по объекту воздействия и по числу прогонов узла записи, а не по итоговому статусу *(A1)*.

Почему журнал не помогает:
- **Успехи не хранятся (правило R4.1).** При `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none` вместе с прунингом успешные прогоны не хранят данных узлов вообще. Запуски через MCP в режиме `production` в журнале не видны *(§1.1)*. Проверка любой правки — только ручным запуском `manual` *(какую версию он исполняет — R2.3)*.
- **Цепочка оборвалась тихо** *(R3)*; `neverError:true` маскирует ошибку API под валидный item (явная проверка после него — T2 слой 3).
Основание: 3 случая, последний 2026-07-24 — отчёт синтеза, правило R4.1.

**Ошибка в теле при коде 200 (правило R4.2).** Ни HTTP-код 200, ни статус `success` не доказывают, что данные пришли или записались: внешние API кладут отказ в тело успешного ответа (например, отключённый метод отвечает 200 с кодом ошибки в теле, и воркфлоу месяц пишет ноль строк со статусом `success`); запись карточки может ответить 200, сменить метку изменения и оставить прежний документ; одна ошибочная карточка в пачке может отклонить всю пачку. Правило: первым узлом после внешнего вызова тело проверяется на признак ошибки *(T2 слой 3)*, а итог записи — перечитыванием объекта и, где API это даёт, его журналом ошибок. Конкретные поля ошибок и журналы ошибок по эндпоинтам — n8n-workflow-registry §3.
Основание: 4 случая, последний 2026-10-05 — отчёт синтеза, правило R4.2.

**Свой вебхук отвечает раньше цепочки (правило R4.3).** Ответ с зашитым `{"success":true}` или ответ «сразу» в настройке вебхука говорит вызывающему «готово» до исполнения, и вызывающий (кнопка Apps Script, другой воркфлоу) об отказе не узнаёт. Ответ вебхука строится из результата последнего значимого узла.
Основание: 1 случай, последний 2026-07-28 — отчёт синтеза, правило R4.3.

**`neverError` не перехватывает таймаут (правило R4.4).** При обрыве по времени (`ECONNABORTED`) узел всё равно падает с ошибкой и останавливает прогон. Отказ по таймауту обрабатывается выходом ошибки *(T2 слой 2)*, а не этой опцией.
Основание: 1 случай, последний 2026-10-05 — отчёт синтеза, правило R4.4.

**Цена `get_execution(includeData:true)` — два независимых слагаемых, лечатся по-разному (правило R4.5).**
- Дублирование по узлам графа: без `nodeNames` тело крупного ответа повторяется столько раз, сколько узлов его касалось (каждый узел загрузки, сборки ответа и Respond несёт свою копию). Лечится сужением `nodeNames:["<терминальный узел>"]`.
- Сырой ответ внешнего API, осевший в `executionData.contextData`. Сужение его НЕ режет, потому что это свойство типа узла: `n8n-nodes-base.httpRequest` оставляет сырое тело при любых параметрах, встроенный `n8n-nodes-base.github` не оставляет никогда.
Следствие для проектирования: если воркфлоу существует РАДИ экономии контекста, узел загрузки выбирается по этому свойству, а не по удобству; готовый воркфлоу с утечкой чинится заменой узла загрузки, а не параметрами вызова. Если заменить HTTP-узел нечем, его выносят в опубликованный подворкфлоу: сырой ответ остаётся в исполнении подворкфлоу, и `contextData` вызывающего воркфлоу пуст. Граница приёма: выход узла Execute Workflow в вызывающем воркфлоу по-прежнему несёт то, что вернул подворкфлоу, поэтому подворкфлоу перед возвратом оставляет только нужное поле (узел-«сужатель»), а вызывающая сессия читает ответ с `nodeNames` терминального узла.
Польза того же свойства: сырой ответ в `contextData` позволяет проверить поля, отброшенные кодом, без нового вызова API.
Основание: 2 случая, последний 2026-10-18 — отчёт синтеза, правило R4.5.

**Ответ больше предела MCP (правило R4.6).** Ответ `get_workflow_execution` бывает больше предела MCP даже при сужении: тогда клиент сохраняет его в файл, и разбирать его надо скриптом по файлу, а не читать в контекст. Почему: сессия, которая не смогла прочитать узел отказа, записала неверную причину.
Основание: 3 случая, последний 2026-10-05 — отчёт синтеза, правило R4.6.
→ **T4 качество 11**, **T2 слой 3**.

**R6. Google Sheets: хрупкая привязка, типы, квоты.**

Закон корня. Узел Google Sheets связывает воркфлоу с листом через имена колонок, позиции строк, типы значений и общий счётчик квоты — и ни одно их изменение не даёт ошибки там, где теряются данные. Корневое лечение — не использовать Sheets как базу данных: служебное состояние (курсоры, маркеры повторов, реестры, сопоставления) — в Data Table, витрина для человека — в Sheets *(T1)*. Пока Sheets остаётся носителем, каждая частная ловушка ниже лечится своей сверкой.

**Короткие симптомы (правило R6.1).** gid врёт в интерфейсе (`cachedResultName` — старый снимок); несоответствие типа в `matchingColumns` даёт дубли без ошибки; составной `matchingColumns` сопоставляет только по первой колонке (подробно — правило R6.7); чтение без `executeOnce` = N запросов = 429; `batchUpdate` без `sendBody` = 400.
Основание: 2 случая, последний 2026-07-07 — отчёт синтеза, правило R6.1.

**`null` не очищает ячейку (правило R6.2).** При `appendOrUpdate` в режиме update поле, которому передан `null`, молча не записывается — старое значение остаётся; поля с настоящим значением, включая пустую строку `""`, перезаписываются штатно. Чтобы физически очистить ячейку — писать `""`.
Основание: 1 случай, последний 2026-09-18 — отчёт синтеза, правило R6.2.

**Квота чтения (правило R6.3).** `ReadRequestsPerMinutePerUser` = **60 в минуту** по умолчанию, и считается она **на потребителя ключа** (проект GCP), а НЕ на воркфлоу и не на узел: все воркфлоу и все узлы на одном сервисном аккаунте делят один счётчик. Поэтому «интервал между двумя конкретными вызовами слишком мал» — ложный диагноз: 429 бывает и при разрыве больше 5 минут между записью и чтением.
- Диагностика 429 — до любых гипотез о внешнем потребителе квоты. Google кладёт в тело ошибки всё нужное, читается через `get_execution(includeData:true, nodeNames:["<упавший узел>"])`: `quota_limit`, `quota_limit_value`, `quota_unit`, `consumer` (project_number). `consumer` с номером собственного проекта значит, что квоту выбрали сами, и искать чужого потребителя бессмысленно.
- Второй дискриминатор — режим запуска: `manual` того же воркфлоу даёт success, а `integrated` (вызов из родителя) — 429 → дело не в квоте инстанса и не во времени суток, а в числе входных items *(R16)*. Признак: `executionTime` упавшего узла около 59000 мс — узел ровно минуту отстреливал разрешённые 60 чтений.
- Повтор при 429 по квоте допустим только после ожидания дольше минутного окна: выход ошибки узла (`continueErrorOutput`) ведёт в Wait не меньше 60 секунд, затем повтор. `retryOnFail` и пауза в 2 секунды окна не переживают: движок ограничивает повтор пятью попытками и пятью секундами между ними, все попытки ложатся в ту же минуту и ускоряют исчерпание *(T2 слой 1)*. Пауза 1–2 секунды между вызовами как профилактика остаётся. Корневое лечение — меньше вызовов (пакеты, `executeOnce`, служебное состояние вне Sheets).
Основание: 3 случая, последний 2026-10-19 — отчёт синтеза, правило R6.3.

**Строка заголовков — договор со всеми узлами-читателями (правило R6.4).** Добавленная колонка роняет узел с заданной схемой («Column names were updated after the node's setup»); переименованная молча ломает автоматическое сопоставление полей; удалённая строка заголовков сдвигает данные и роняет всех, кто читает по имени колонки. Перевод читателя на другой лист с теми же данными, но другими именами колонок даёт узлу пустые поля без ошибки.
- Правило: перед правкой шапки перечислить узлы-читатели этого листа, после правки — обновить их схему; при смене листа сопоставить имена колонок до переключения.
- То же — до первой записи строк нового вида в общий лист (строки другого бренда, строки без поля, которое у прежних строк было всегда): каждого читателя проверить по коду его узла чтения и первой обработки — что он делает с такой строкой: пропускает, останавливается или пишет неверное. Почему: читатель, написанный под прежний вид строк, может принять пустое поле за значение и записать чужие данные. Читателей в n8n дают строки D снимка `registry/n8n-map.md` по ID книги; скрипты других книг снимок не показывает, их ищут отдельно.
- Ошибка в самой строке заголовков (например `#ERROR!` в первой ячейке) даёт мусорные имена полей, и значения листа параметров читаются пустыми — пороги становятся нулём *(R19)*. Такой лист читать узким диапазоном (Data Location → Range, строка заголовков задана явно), а не целиком.
- Дубли заголовков на одном листе: узел чтения собирает item по именам, и при одинаковых именах побеждает правая колонка — подменяет левую чужими данными. На таком листе задавать Data Location → Range с границей до дублей.
Основание: 5 случаев, последний 2026-10-14 — отчёт синтеза, правило R6.4.

**Выбор листа в режиме `list` (правило R6.5).** Значение `gid=0` работает, `gid=<ID листа>` даёт «Sheet with ID gid=… not found»; писать голый ID листа.
Основание: 1 случай, последний 2026-10-03 — отчёт синтеза, правило R6.5.

**Колонка с формулой (правило R6.6).** Узел при добавлении строк (append) считает ячейку с формулой занятой даже при пустом результате формулы — новые строки ложатся ниже разлива ARRAYFORMULA, а не в первую пустую строку. Писать значения в колонку, которую заполняет формула (ARRAYFORMULA, IMPORTRANGE, построчная формула), нельзя вовсе: запись даёт `#REF!` или молча расходится с формулой. Перед первой записью в лист колонки читать в режиме FORMULA. Механика формул самой книги — Skill apps-script-sheets.
Основание: 3 случая, последний 2026-10-07 — отчёт синтеза, правило R6.6.

**Автоматическое сопоставление (autoMapInputData) и составной ключ (правило R6.7).** Узел записывает ровно те поля входного элемента, у которых есть одноимённая колонка, и не трогает колонки, которых во входе нет: частичное обновление — не потеря (дискриминатор «затёрто или не было»: целы ли поля того же источника). Поле с именем колонки-формулы заменяет формулу значением — такие поля во вход записи не включать. Составной `matchingColumns` (`["k1","k2"]`) сопоставляет по первой колонке и перезаписывает вторую колонку ключа у найденной строки — на листе возникает дубль ключа; составной ключ собирать заранее в одну колонку.
Основание: 1 случай, последний 2026-10-12 — отчёт синтеза, правило R6.7.

**Тип и чистота ключа (правило R6.8).** Сравнение ключей даёт ноль совпадений без ошибки, а `appendOrUpdate` по такому ключу плодит дубли, если стороны расходятся хоть в чём-то:
- тип: ключ в одном источнике хранится числом, в другом текстом («1058.0» против «1058») — перед любым сравнением и в `matchingColumns` обе стороны приводятся к одному типу в Code-узле;
- уникальность: если у ключа в источнике две строки, поиск молча берёт первую — источник проверяется на уникальность ключа до сравнения;
- символы: двойной пробел, кириллические «Т» и «С» вместо латинских дают ноль совпадений — символы ключа сравниваются по коду, а не глазом;
- число в текстовой по смыслу колонке: значение из листа может прийти числом — перед `.trim()` и сравнением писать `String(x ?? '')`;
- пустой ключ: `matchingColumns` по колонке, которая может быть пустой, сопоставляет пустое с пустым, и запись уходит в первую чужую строку с пустым ключом — строки без ключа отсекаются до записи и до первого платного вызова модели.
Основание: 6 случаев, последний 2026-10-04 — отчёт синтеза, правило R6.8.

**Таблица параметров — горизонтальная (правило R6.9).** Лист параметров воркфлоу хранится строкой имён и строкой значений (строка 1 — имена, строка 2 — значения), а не парами «имя — значение» по строкам. Почему: вертикальная пара с `row_number` при `appendOrUpdate` перезаписала соседний порог, и неверные надбавки копились без единой ошибки.
Основание: 1 случай, последний 2026-06-24 — отчёт синтеза, правило R6.9.

**`appendOrUpdate` по строке с жизненным циклом (правило R6.10).**
- Если строка проходит статусы (new → shipped → cancelled), повторная запись того же ключа возвращает статус назад в начальный. Защита от повтора для таких строк — множество уже известных ID (новое пишется, только если ID нет в множестве), а не upsert.
- Поле первого наблюдения (время первой детекции) в такой строке не перезаписывается на каждом прогоне — иначе производная метрика («часов с момента») растёт по часам прогона и теряет смысл.
- Обратная ловушка: накопитель на `appendOrUpdate` никогда не удаляет объект, исчезнувший из источника, — читатель такого накопителя фильтрует по свежести (`updated_at`), иначе видит мёртвые записи.
Основание: 3 случая, последний 2026-10-02 — отчёт синтеза, правило R6.10.

**Простой append при повторяемом прогоне (правило R6.11).** Запись в архив перед удалением простым append при каждом упавшем и перезапущенном прогоне дописывает те же строки ещё раз; для повторяемой записи — только `appendOrUpdate` с `matchingColumns` (тот же класс — T1-D, дефект дублирования).
Основание: 1 случай, последний 2026-10-05 — отчёт синтеза, правило R6.11.

**Удаление строк (правило R6.12).** Узел «delete» без явных `startIndex` и `numberToDelete` — не пустая операция: удаляет одну строку, начиная со второй, то есть первую строку данных. Поле номера строки (startIndex в typeVersion 4.7) ждёт номер строки как есть — «The first row is 2»; передача `row_number − 1` удаляет строку над целевой, а для первой записи — строку заголовков (защита заголовка листа скрывает эту ошибку, пока её не снимут). В коде удаления — барьер: номер строки меньше 2 → остановиться с ошибкой.
Основание: 3 случая, последний 2026-10-06 — отчёт синтеза, правило R6.12.

**Запись и удаление по номеру строки (правило R6.13)** — только после повторного чтения ключевой колонки в момент записи и сравнения с первым чтением; расхождение — остановка без записи. Почему: номер строки сдвигают ручная правка владельца, ошибка на единицу, удаление без явного диапазона.
Основание: 3 случая, последний 2026-10-05 — отчёт синтеза, правило R6.13.

**Порядок диапазонов в ответе batchGet не гарантирован (правило R6.14).** Google может вернуть листы в другом порядке, чем запрошены; диапазон выбирается по имени листа в поле `range` ответа, никогда по позиции.
Основание: 1 случай, последний 2026-10-05 — отчёт синтеза, правило R6.14.
→ **T1 шаг 0 и T1-C**.

**R7. Cron плывёт без явной таймзоны (DST).**
Без `settings.timezone` Schedule Trigger трактует cron как локальное время таймзоны сервера (SKILL.md §1), а не как время задачи. Фикс: явный `settings.timezone` той зоны, в которой названо время задачи (для времени по Москве — `Europe/Moscow`), и cron сразу в часах этой зоны. Таймзону ставить операцией `setWorkflowSettings` или руками в редакторе: заданная в коде воркфлоу целиком (SDK) она не применяется, а запись кодом целиком сбрасывает уже стоящую; точечные операции `update_workflow` её не трогают *(R1b)*.
Смещение не пересчитывать в голове: зона, переводящая часы, против зоны без перевода даёт разное смещение летом и зимой — Берлин переводит часы, Москва нет, поэтому Берлин → МСК даёт +1 час летом и +2 зимой, — и расписание, выставленное пересчётом, уезжает дважды в год *(механика и проверенный пример — §4.10)*.
Отсутствие явной таймзоны — не исключение, а состояние по умолчанию: у любого воркфлоу «со временем по Москве» его надо предполагать до проверки. Сколько расписаний без явной таймзоны сейчас — считать по строкам W снимка `registry/n8n-map.md`, поле 8 (поле 10 — воркфлоу ошибок); последний пересчёт — `labs/sys/t-failure-visibility.md`.
Основание: 3 случая, последний 2026-10-02 — отчёт синтеза, правило R7.1.
→ **T4 качество 8.**

**R11. Сетевая нода без timeout.**
Каждому узлу HTTP Request задаётся `options.timeout` явно. Без поля запрос ждёт минутами и держит воркер инстанса, пока не кончится отказом соединения операционной системы (`connect ETIMEDOUT`), а не таймаутом n8n. Значение 10000 мс в описании узла — умолчание поля в момент его добавления, а не действующее значение, когда поля нет.
`options.timeout` ограничивает только ожидание заголовков ответа: медленное тело он не обрывает (таймаут 5 секунд, тело шло 12,6 секунды и пришло целиком), а ответ без тела обрывает вовремя. Признак — HTTP-узел с таймаутом отработал дольше таймаута: значит, медленно шло тело.
Полный таймаут есть только у HTTP Request. У Postgres — только `connectionTimeout`: время на подключение, по умолчанию 30 секунд, на зависший запрос не действует; у Telegram поля таймаута нет вовсе (описания узлов Postgres 2.7 и Telegram 1.2). Для них защита — выход ошибки *(T2 слой 2)* и воркфлоу ошибок.
Не путать: «дефолтный таймаут 5 минут, и он касается любой сетевой ноды» — на деле число не измерялось, а полный таймаут есть только у HTTP Request.
Основание: 1 случай, последний 2026-10-12 — отчёт синтеза, правило R11.1 (поведение таймаута); 1 случай, последний 2026-10-12 — отчёт синтеза, правило R11.2 (чтение описаний узлов).
→ **T2 слой 1**.

**Закон периметра (R12–R15).** У воркфлоу несколько независимых входов — вебхук, форма, вызов из сессии Claude через MCP, межворкфлоушный вызов по адресу — и несколько мест, где может лежать секрет. Каждый вход закрывается своим средством, каждый секрет живёт только в credential, и всё это проверяется по объекту отдельно: закрытие одного входа ничего не говорит о другом, а отсутствие литерала в узле ничего не говорит о том, верный ли ключ привязан.

**R12. Webhook-триггер без аутентификации.**
Вебхук без аутентификации запускает воркфлоу для любого, кто знает адрес. Это класс, а не единичный случай. Диапазон последствий: от публикации на маркетплейсе по произвольному id до перезаписи произвольного файла Drive и постановки файла в очередь на необратимое удаление; в класс входят и служебные инструменты, которыми Claude пишет и читает Google Docs. Поэтому новый вебхук создаётся закрытым с первой записи — порядок шагов в §2.1.
Второй путь потери аутентификации — не забытая настройка, а запись воркфлоу кодом целиком (`create_workflow_from_code` и любая запись, передающая воркфлоу кодом): она пересобирает каждый узел, включая триггер, и если в коде триггера нет параметра `authentication`, аутентификация слетает без предупреждения, вебхук становится открытым *(R1b.6, §2.2 п.4)*. Точечная форма `update_workflow` (операции над отдельными узлами) аутентификацию нетронутого вебхука сохраняет — проверено пробой правки другого узла *(R1b.0)*. Правка самого узла-вебхука операцией не проверена: после неё, как и после любой записи кодом целиком, сверить `triggerInfo` — строка «This webhook requires a header…» должна остаться *(§2.3 п.2)*. Поэтому гейт T4 остаётся обязательным при любом текущем состоянии периметра; само состояние в Skill не записывается — его дают строки HOOK закрытой части снимка (адрес — §10), и оно верно только для своего чтения.
**Как закрывать.** Вебхук закрывается отдельным ключом типа Header Auth, заведённым под этот вебхук или эту группу вебхуков, а не общим ключом другого назначения. Почему: ключ вебхука становится паролем входа, и утечка чужого ключа через вебхук отдаёт то, что этот ключ открывает (токен GitHub, поставленный паролем вебхука, дал бы при утечке прямую запись в репозиторий). Признак ошибки — на вебхуке стоит ключ, совпадающий с токеном внешнего сервиса; так бывает после промаха автопривязки — сверить `autoAssignedCredentials` и заменить ключ операцией `setNodeCredential` *(R1a.2)*.
Проверку заголовка на узле-вебхуке включать только после того, как вызывающий код уже умеет его отправлять, — иначе закрытие ломает собственный вызов.
У Header Auth два противоположных смысла: на узле-вебхуке это то, что обязан предъявить звонящий; на HTTP-узле — то, что узел сам отправляет наружу. Один и тот же тип ключа в двух местах графа делает разное.
**Форма — вход того же класса.** Узел-триггер формы (Form Trigger) у опубликованного воркфлоу принимает запуск с адреса формы от любого, кто этот адрес знает, если у формы не включена аутентификация. У воркфлоу, пишущего во внешний кабинет, открытая опубликованная форма — это запуск боевого режима записи вовне любым, кто знает адрес; такую запись из n8n не откатить *(T5, R18)*. Правило: воркфлоу с формой либо не публикуется (для любого воркфлоу, пишущего вовне, — T5), либо форма закрывается аутентификацией до публикации. Какие виды аутентификации есть у узла формы, смотреть в описании узла (`get_node_types`) в момент правки — на инстансе не проверялось. Счёт периметра по строкам HOOK видит только вебхуки: формы ищутся отдельно, по триггеру `formTrigger` в строках W снимка `registry/n8n-map.md`. Граница та же, что у вебхука: вызов из сессии Claude через `execute_workflow` аутентификацию формы не проходит вовсе *(R15)*.
Основание: 1 случай, последний 2026-07-23 — отчёт синтеза, правило R12.1 (аудит, класс и последствия); 1 случай, последний 2026-09-18 — отчёт синтеза, правило R12.2 (отдельный ключ, два смысла Header Auth); 1 случай, последний 2026-09-24 — отчёт синтеза, правило R12.3 (порядок включения проверки); 1 случай на двух воркфлоу, последний 2026-10-17 — отчёт синтеза, правило R12.4 (форма).

**R13. Секрет в параметрах ноды или в константе Code-ноды.**
Живой ключ в открытом виде в узле — тот же класс, что обход системы credentials через `require` в Code-ноде. Перевод литерала в credential по форме заголовка: `Bearer <token>` → `httpBearerAuth` (хранит без префикса); прочие заголовки → `httpHeaderAuth`; несколько заголовков или заголовки и query → `httpCustomAuth`.
Общее правило против этого корня — секрет не проходит через чат, текст узла и репозиторий вовсе — в §2.1.
**Находка аудита о литерале — не текущий факт.** Снимок `registry/n8n-map.md` привязывает тип credential к воркфлоу, а не к узлу: появление типа `httpHeaderAuth` у воркфлоу не доказывает, что литерал из узла убран. Проверять по узлу — полем `credentials` в `get_workflow_details` (R1a) или глазами в редакторе; до такой проверки находку не тащить дальше ни как закрытую, ни как текущую.
**Литерал остаётся в истории версий.** Ключ, хоть раз сохранённый литералом в теле узла, лежит в истории версий воркфлоу (`workflow_history`) и после перевода в credential: перевод утечку не закрывает. Такой ключ перевыпускается у сервиса-выдавателя.
**Ключ и домен.** Отсутствие литерала ключа в узле не значит, что привязан верный ключ: узел может слать ключ на чужой домен. Правило разовой сверки, а не постоянный инструмент: по всем HTTP-узлам — домен адреса узла против имени и id привязанного ключа (поле `credentials` в `get_workflow_details`, R1a). Верный ключ для узла определяется по живым соседям, которые бьют в тот же домен и имеют успешные прогоны, а не по документации — она может называть истёкший ключ. У ключа типа Header Auth поле Allowed HTTP Request Domains при значении «All» отправит ключ на любой домен, куда укажет адрес узла — при заведении и ротации сужать до домена сервиса.
**Ротация.** Перед ротацией ключа — перебор всей базы n8n на его литерал (все текстовые и JSON-колонки всех таблиц, включая историю версий `workflow_history`): список потребителей по снимку литерал в тексте узла и в старых версиях не ловит, и потребитель вне списка падает после ротации. Запрос готовит сессия, выполняет Андрей через `docker exec … psql`. Удаление ключа в n8n сам ключ у сервиса не отзывает — отзыв у сервиса-выдавателя (n8n-workflow-registry, раздел «Ключ к собственному API n8n»).
Основание: 1 случай, последний 2026-07-23 — отчёт синтеза, правило R13.1 (аудит: литералы в узлах; привязка типа к воркфлоу в снимке); 1 случай, последний 2026-10-17 — отчёт синтеза, правило R13.2 (история версий); 2 случая, последний 2026-07-23 — отчёт синтеза, правило R13.3 (ключ на чужой домен, ключ по документации); 1 случай, последний 2026-10-10 (дата разбора корпуса; день самого случая в источнике не записан) — отчёт синтеза, правило R13.4 (Allowed HTTP Request Domains); 1 случай, последний 2026-07 (день в источнике не записан) — отчёт синтеза, правило R13.5 (перебор базы перед ротацией, удаление не отзывает). **R14. Вызов своего же вебхука через публичный домен вместо internal-адреса.**
HTTP Request-узел, вызывающий сервисный вебхук этого же инстанса, адресуется по `http://<имя-docker-сервиса>:<порт>/...`, а не по публичному домену инстанса (§1). Почему: запрос по публичному домену физически уходит на reverse-proxy и возвращается тем же путём, что настоящий внешний запрос, — граница между «своим» и «чужим» трафиком пропадает на уровне сети. Любая защита периметра (remote_ip-матчинг, файрвол, аутентификация на reverse-proxy) блокирует в равной мере и атаку, и собственный межворкфлоушный вызов: снаружи их не разделить, если оба вошли одним путём. Признак — своя защита периметра блокирует и чужой, и свой вызов.
Проверять при создании КАЖДОЙ HTTP-ноды, целящей в `/webhook/` этого инстанса: хост в URL — имя docker-сервиса, не домен. Текущее состояние вызовов — строки H и HOOKCALL снимка (адрес — §10).
Основание: 1 случай, последний 2026-09-14 — отчёт синтеза, правило R14.1.
→ **T4 гейт 5.**

**R15. Аутентификация вебхука не защищает от вызова через MCP `execute_workflow`.**
Header Auth (и любой другой тип аутентификации вебхука или формы) проверяется на уровне HTTP-запроса к n8n. `execute_workflow` идёт через API, минуя HTTP-слой вебхука, и заголовок не передаёт и не проверяет. Воркфлоу с закрытым вебхуком остаётся вызываемым из сессий Claude как прежде: вызов через MCP без заголовка проходит штатно, прямой HTTP-вызов без заголовка получает отказ.
→ Учитывать при любой оценке «кто может вызвать этот воркфлоу»: список включает все сессии Claude на инстансе. «Вебхук защищён» ≠ «воркфлоу защищён» — это два разных периметра.
Основание: 1 случай, последний 2026-09-16 — отчёт синтеза, правило R15.1.

**R16. Execute Workflow возвращает в родителя весь выход саб-воркфлоу.**
Узел `executeWorkflow` с `waitForSubWorkflow:true` отдаёт дальше все items последнего узла саб-воркфлоу *(§4.7)*. Если ниже стоит второй `executeWorkflow`, он получает эту пачку на вход и передаёт её следующему саб-воркфлоу целиком — **даже когда маппинг входа собран из выражения, не зависящего от items** (`$("Нода").first().json.поле`). Снаружи выглядит как «передаю одну дату», внутри приходит N одинаковых items, и каждый узел до первой `runOnceForAllItems`-ноды отрабатывает N раз: справочник Sheets делает N чтений и упирается в квоту 60 чтений в минуту (429, R6).
Признаки: саб-воркфлоу получил N одинаковых items вместо одного; `manual` того же воркфлоу даёт success, а `integrated` (вызов из родителя) — ошибку на том же узле; `pairedItemNoInfo` после Execute Workflow *(§4.4)*.
Проверять при КАЖДОЙ цепочке из двух и более Execute Workflow подряд: что именно саб-воркфлоу возвращает последним узлом. Если родителю нужен только факт завершения — либо `waitForSubWorkflow:false`, либо терминальный узел-квитанция (Set со статусом, один item), либо `executeOnce` на первом узле следующего звена (механика — §4.3).
Основание: 1 случай, последний — дата в источнике не записана — отчёт синтеза, правило R16.1.
→ **R6** (симптом 429), **§4.3** (лечение).

**R17. Ручная правка в UI нормализует конфиг, записанный SDK; имя параметра не доказывает семантику.**
Три сцепленных эффекта (наблюдались на googleSheets typeVersion 4.7).
(а) Инверсия смысла. Имя ключа в JSON может описывать ВЫКЛЮЧЕННОЕ состояние тумблера: у read-ноды лежало `"returnAllMatches": "returnAllMatches"`, а в UI это поле называется **«Return only First Matching Row»** и живёт в блоке Options. Вывод «параметр пропал → вернётся одна строка» ровно обратен истине: отсутствие ключа — умолчание, то есть вернуть все совпадения. Правило: семантику флага брать из UI или из прогона; если имя ключа — единственный источник, писать «не знаю», а не достраивать.
(б) Нормализация при Save. Воркфлоу, собранный через MCP/SDK, хранит часть параметров в форме, которую редактор не отрисовывает. Ручное открытие ноды и Save переписывают конфиг под то, что видит UI: параметры верхнего уровня без поля на панели из JSON исчезают. Это зеркало R1b — там MCP портит настроенное руками, здесь руки нормализуют записанное MCP. Расхождение конфига до и после ручной правки — ожидаемое поведение, а не порча; прежде чем объявлять баг, проверить в UI, отрисовывается ли исчезнувший параметр вообще.
(в) Побочная активация. Save из редактора может заодно опубликовать воркфлоу: `active:false, activeVersionId:null` → `active:true, activeVersionId:<новый>`. На воркфлоу без расписаний безвредно, с Schedule Trigger — незапланированный запуск, а у воркфлоу, пишущего во внешний кабинет и обязанного стоять неопубликованным, — боевой режим без вызова *(T5)*. Сверять `active` после каждой ручной правки.
→ Проверка любой ручной правки — прогоном по объекту *(R4)*, не чтением JSON.
Основание: 1 случай, последний 2026-09-19 — отчёт синтеза, правило R17.1.

**Закон пропуска (R18–R19).** То, чего код не видит — поле, которое чтение не вернуло, значение, которое не пришло, данные, устаревшие с момента написания, — он молча заменяет законным: пустым, нулём, умолчанием площадки, «прочим» или старым числом. Ошибки нет нигде *(A1, A2)*, потеря видна только на объекте. Защита — явное состояние «неизвестно» и запрет в коде узла, а не в тексте; проверка — по объекту.

**R18. Запись «заменить целиком» стирает то, что чтение не вернуло; текстовый запрет этого не останавливает.**
Механизм: эндпоинт, который заменяет объект целиком, получает обратно только то, что вернуло чтение. Поле, которого чтение не вернуло, в записанном объекте отсутствует: было заполнено — стирается; у флага встаёт значение по умолчанию; площадка может и вычислить не переданное поле заново по своим правилам. Повторная запись правильного значения при этом может быть принята с кодом 200 и не примениться. Воркфлоу ведёт себя «верно»: узел отчитался успехом *(A1)*, ошибки нет *(A2)*. Текстовый запрет «не запускать боевой режим» в STATE не защищает: его читает только тот, кто открыл STATE.
Частный случай Wildberries — запись карточки заменяет её целиком, ОКПД 2 чтение не отдаёт, не переданный `needKiz` площадка решает заново и снимает отметку маркировки — n8n-workflow-registry, `references/cards-and-declarations.md`, и файл кейсов `meta/CASES_wb-api-card-write.md` (кейс 3).
Правило: когда запись заменяет объект целиком, перед первой боевой записью выяснить, что чтение не возвращает, и вынести запрет в код узла (фильтр в воротах боевого режима), а не в текст. Проверка — чтение записанного объекта на одном пробном объекте до массовой записи.
**Снимок до записи.** Перед массовой записью сохраняется снимок объекта, и у снимка записывается адрес: номер исполнения, узел, время. Только по снимку можно установить, что именно изменила запись. Признак, который сама запись меняет, эталоном «как должно быть» не годится: после записи он показывает уже испорченное состояние. Сравнивать — со снимком до записи.
**Данные в коде — снимок на дату написания.** Одноразовый воркфлоу, у которого записываемые данные зашиты в код, не перезапускается как есть: он перезапишет новые значения старыми. Повторную запись делать инструментом, который берёт данные из входных строк; сам одноразовый воркфлоу оставлять образцом (снятым с публикации — §2.5).
Шаблон воркфлоу, пишущего во внешний кабинет, с режимами «проверка» и «боевой» — T5 в references/templates.md.

**R19. Неизвестное значение молча становится допустимым.**
Значение, которое не прочиталось, не распозналось или не пришло, код превращает в законное: ноль, пустую строку, категорию «прочее», «пустой день», запасную константу. Дальше оно ведёт себя как настоящее, и ошибки нет нигде *(A2)*.
Правило: у каждого значения, которое может не прийти, есть явное состояние «неизвестно» (`unknown`, `ERROR`, пустое с флагом) и сигнал о нём; ноль, «прочее» и запасная константа им не являются. Ронять весь поток из-за одного неизвестного тоже неверно, если поток делает и другую работу: `throw` при отсутствии порогов остановил бы и соседнюю запись статусов, поэтому верная форма — флаг (`paramsOk`) и состояние `unknown` у зависимого поля, а остальная работа идёт дальше.

| Вид случая | Как выглядит | Что делать |
| :-- | :-- | :-- |
| Параметр из листа не прочитался (сломанная шапка листа параметров) | пороги стали нулём, все объекты попали в первую зону, скидка не ставилась ни разу | до расчёта проверить, что параметры прочитаны; иначе `unknown` и сигнал *(R6, строка заголовков)* |
| Новое значение справочника (новое имя операции площадки), пустое поле в расчёте | новое ушло в «прочее», пустая себестоимость посчитана нулём, прибыль завышена молча | неизвестная категория и пустое поле — отдельное состояние с сигналом, не «прочее» и не 0 |
| Отказ ключа или API на служебной строке | отказ записан строкой «пустой день» (`EMPTY_`) | отказ пишется как `ERROR` |
| Инкрементальная загрузка берёт «вчера» от даты прогона | упавшая ночь не догружается никогда: следующий прогон тоже берёт своё «вчера» | окно — от последней успешной метки в целевой таблице, а не от даты запуска *(§4.9)* |
| Производный признак собран по накопителям одного источника (одного кабинета) | признак ложен для объекта, который есть только в другом источнике | перед вычислением проверить, что входы покрывают все источники (все кабинеты) |
| Отчёт по снимку при нуле объектов | снимок не пишет ничего, отчёт молча показывает ноль — «объектов нет» неотличимо от «снимок не создан» | снимок при нуле объектов пишет строку-маркер (например `__empty__`) |
| Запасная константа в коде: параметр читается из листа, а при пустом чтении код подставляет число, вписанное когда-то в узел (`|| <число>`) | дефект не виден, пока число в листе совпадает с константой; после смены значения в листе пустое чтение даёт расчёт по устаревшему числу без ошибки | константу убрать; пустое чтение — `unknown` и сигнал |

Частная форма для полных списков и пагинации — §4.9; для робота, перезаписывающего накопитель, — T1-C, абзац «Накопитель из внешнего API».
Основание: 7 случаев, последний 2026-10-18 — отчёт синтеза, правила R19.1–R19.7 (по строкам таблицы); 1 случай, последний 2026-10-02 — отчёт синтеза, правило R19.8 (флаг и `unknown` вместо `throw`).
→ **§4.9**, **T1-C**, **T4 гейт 2**.
