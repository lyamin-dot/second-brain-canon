# Запись карточек Wildberries через API: где запись не проходила, почему и какой выход найден

Версия для человека. Копия для агента на английском — `meta/CASES_wb-api-card-write.en.md`; содержание одно и то же, при правке менять оба файла. Заведён 2026-10-17 по просьбе Андрея: сборник проверенных на живых карточках случаев неудачной передачи данных в карточки WB, для использования вне проекта deklaration-wb (любой проект, который пишет в карточки WB через Content API). Каждый кейс подтверждён записью и последующим чтением карточки; номера исполнений n8n и карточек — для проверки. Решения и хроника — журнал `projects/deklaration-wb/LOG.md` (записи Р-11, Р-14, Р-15, Р-16, Р-19, Р-20, Р-21); каждое действие с карточками — `projects/deklaration-wb/CARD_WRITES.md`. Порядок работы с карточками в проекте деклараций — `meta/PROTOCOL_wb-card-write.md`.

Запрос записи во всех кейсах один: POST https://content-api.wildberries.ru/content/v2/cards/update, тело — массив карточек. Чтение: POST /content/v2/get/cards/list (фильтр textSearch = nmID), список ошибок карточек: POST /content/v2/cards/error/list.

## Главные правила (выжимка из кейсов ниже)

1. Ответ 200 с пустой ошибкой означает «принято в обработку», а не «применено». Приёмка — только чтение карточки после записи: блок documents (номер, startDate, endDate, verdict), needKiz, kizMarked, характеристики, плюс список ошибок карточек. Чтения через 45 секунд достаточно.
2. cards/update заменяет карточку целиком: передавать все характеристики, которые нужно сохранить, размеры (sizes с chrtID и skus), габариты (dimensions), title, description, brand, vendorCode. Чего нет в теле — того не будет в карточке.
3. Поле needKiz («Нужна маркировка КИЗ») передавать в каждой карточке, по умолчанию как в прочитанной карточке (кейс 3).
4. Номер и даты документа передавать двумя способами в одном запросе: характеристиками и блоком documents.items с датами вида ГГГГ-ММ-ДДT00:00:00Z (кейсы 1 и 2).
5. Даты в характеристиках — строкой в массиве, вид ДД.ММ.ГГГГ: ["18.09.2026"] (кейс 5).
6. «Проверено и верно» значит: совпадает номер И обе даты с источником истины, а не только номер (кейс 8). Вердикт WB «valid» правильность не доказывает (кейс 9).

Образец тела для одной карточки с декларацией (значения условные):

```
[{ "nmID": 1473232361, "vendorCode": "...", "brand": "...", "title": "...", "description": "...",
   "needKiz": true, "kizMarked": true,
   "dimensions": { "length": 6, "width": 6, "height": 19, "weightBrutto": 0.3 },
   "characteristics": [ ...все прежние характеристики...,
     { "id": 15001135, "value": ["ЕАЭС N RU Д-DE.РА08.В.56094/26"] },
     { "id": 15001137, "value": ["18.09.2026"] },
     { "id": 15001138, "value": ["18.09.2027"] } ],
   "sizes": [ { "chrtID": 0, "techSize": "0", "wbSize": "", "skus": ["..."] } ],
   "documents": { "items": [ { "type": 2, "number": "ЕАЭС N RU Д-DE.РА08.В.56094/26",
       "startDate": "2026-09-18T00:00:00Z", "endDate": "2027-09-18T00:00:00Z", "isEndless": false } ] } }]
```

type 2 — декларация соответствия (так WB возвращает её при чтении).

## Кейс 1. Ответ 200, но номер и даты декларации в карточке не меняются

- Симптом: в карточке уже есть документ (созданный раньше, часто бессрочный и без дат). Пишем номер и даты характеристиками 15001135 (номер), 15001137 (дата регистрации), 15001138 (дата окончания). WB отвечает 200, ошибок нет, updatedAt карточки меняется, но через 45 секунд, через 2 часа и на следующий день в блоке documents прежний документ.
- Причина: характеристики 15001135/15001137/15001138 уже созданный документ не меняют. Документ меняется только блоком documents.items.
- Что не помогло: повтор записи (1928: исполнения 80649, 80664 от 10.10 и 81436, 81437 от 17.10); предварительное удаление трёх характеристик отдельной записью (1745, исполнение 81463 — тоже не применилось).
- Решение: в том же запросе передать и характеристики, и блок documents.items = [{ type 2, number, startDate, endDate, isEndless false }]. WB создаёт новый документ (новый id) и через 3–11 секунд ставит ему вердикт.
- Доказательство: 1745 (исполнение 81465) — первая удачная запись; затем 1907, 1731, 1345, 1929, 1923, 1337, 1711, 1755, 1359, 1709, 1746, 1787 — 13 из 13, вердикт valid (у 1337 и 1711 через 45 секунд вердикта ещё не было). Ручная правка того же документа в личном кабинете тоже работает (1928, 17.10 14:00).

## Кейс 2. Ответ 400 «Invalid request format» на блок documents.items

- Симптом: передаём documents.items с датами "18.09.2026" или "2026-09-18" — WB отвечает 400 Invalid request format, карточка не меняется.
- Причина: даты в блоке documents принимаются только в формате RFC3339 со временем: "2026-09-18T00:00:00Z". Формат найден подбором по тому, как WB отдаёт даты при чтении; в документации WB он не описан.
- Доказательство: 1929, исполнение 81461 (400); 1745, исполнение 81465 (200, применено).
- Правило: в характеристиках даты — ДД.ММ.ГГГГ; в documents.items — ГГГГ-ММ-ДДT00:00:00Z.

## Кейс 3. После записи слетает «Нужна маркировка КИЗ» и вместе с ней «маркировка нанесена»

- Симптом: у карточки стоят обе галки — needKiz («Нужна маркировка КИЗ», чаще всего поставлена сотрудником руками в кабинете) и kizMarked («Подтверждаю, что на товар нанесена необходимая маркировка»). Пишем в карточку только декларацию, kizMarked передаём true, как было. После записи needKiz = false и kizMarked = false.
- Причина: если поле needKiz в теле запроса не передано, WB при записи решает заново и ставит «не нужна»; при needKiz = false он не принимает и kizMarked.
- Решение: передавать needKiz в каждой карточке, по умолчанию как в прочитанной карточке; менять — только сознательно.
- Доказательство: 1929 — запись без needKiz (исполнение 81510) сняла обе галки; после ручной отметки в кабинете холостая запись с needKiz true (исполнение 81533) — обе галки удержались; 1787 (исполнения 81544, 81546) — needKiz сохранён, kizMarked поставлен.
- Последствие для прошлого: этим, по всей видимости, объясняется пропажа отметок КИЗ у 1345 и 1745 после записей 10.10 (журнал Р-19).

## Кейс 4. «Маркировка нанесена» через API не принимается, хотя код ОКПД 2 записан

- Симптом: записываем в карточку ОКПД 2 (характеристика 15004292) и kizMarked true. ОКПД 2 встаёт, а needKiz и kizMarked остаются false.
- Причина: WB не включает needKiz по одному коду ОКПД 2 — с кодом 19.20.29.170 он КИЗ не требует (у 1928 с этим кодом needKiz тоже false). Без needKiz галка kizMarked не принимается.
- Что работает: сотрудник ставит «Нужна маркировка КИЗ» руками в личном кабинете (принимается и при этом коде), после чего запись через API с needKiz true и kizMarked true держит обе галки (кейс 3).
- Доказательство: 1929, исполнение 81526 (код записан, галки нет); ручная отметка 17.10 (чтение 81531: needKiz true, kizMarked true).
- Вывод: код ОКПД 2 сам по себе отметку КИЗ не удерживает и не включает; удерживает её только переданный needKiz.

## Кейс 5. WB пишет «Вы не приложили документ» (documents_missing) из-за вида дат

- Симптом: документ в карточке есть, а вердикт documents_missing, в кабинете — «Вы не приложили документ».
- Причины, найденные на объекте: (а) даты записаны в виде ММ-ДД-ГГ ("01-27-26") — WB создаёт документ без срока (журнал Р-14; у 1755 и 1777 такие даты нашлись 15.10); (б) документ создан бессрочным и без дат (1731, 1907 — номер верный, дат нет, вердикт document_missing с 02.10).
- Решение: характеристики дат — только ДД.ММ.ГГГГ; документ — блоком documents.items с обеими датами и isEndless false (кейсы 1, 2). Файл выписки в WB загружать не нужно.
- Доказательство: 1907 (исполнение 81489) и 1731 (исполнение 81502) — documents_missing → valid.

## Кейс 6. Неверная дата регистрации: «окончание минус год»

- Симптом: в карточке дата регистрации декларации на год раньше даты окончания, а в выписке другая.
- Причина: прежний разбор PDF деклараций и роботы WB Sync при пустой дате регистрации вычисляли её как «дата окончания минус год». Реальный срок деклараций бывает 181, 216, 339 дней (журнал Р-16).
- Решение: дату регистрации брать только из выписки декларации — она в каждой декларации указана. Пустая дата в таблице — ошибка разбора деклараций или воркфлоу, её нужно исправить в источнике, а не вычислять.
- Состояние на 2026-10-17: в роботах WB Sync (ИП 9Qhnkz9E6mjidqs5, основной QCQI6utFFH3dvTJT) вычисление ещё стоит; решение Андрея — исправить в будущем.

## Кейс 7. Ложный диагноз «WB применяет запись с задержкой в часы»

- Симптом: после записи через 45 секунд и через 4 минуты карточка старая; на следующий день часть карточек исправлена, часть нет.
- Ошибочный вывод (журнал Р-11, пункт 5): «WB применяет правки с задержкой в часы». Он держался неделю и прятал настоящую причину.
- Настоящая причина: запись, меняющая уже созданный документ одними характеристиками, не применяется вовсе (кейс 1). Карточки, где документа ещё не было, применялись сразу.
- Что на самом деле медленно: вердикт нового документа WB ставит через 3–11 секунд; общий вердикт карточки (overallVerdict) пересчитывает не сразу — у 1787 документ valid, а общий вердикт ещё documents_missing от 10.10 (исполнение 81546).
- Правило: если через 45 секунд в documents нет нового документа (новый id, наши номер и даты) — запись не применилась, ждать не нужно, искать причину.

## Кейс 8. Проверка «ОК» по одному номеру прячет пустые даты

- Симптом: робот сверки считает карточку правильной, а WB её документ не принимает.
- Причина: сверка сравнивала только номер декларации; у 1731 и 1907 номер верный, дат нет — статус «ОК».
- Решение: «ОК» = совпадают номер и обе даты; номер верный, а даты нет или другие — отдельный статус (DATES_MISMATCH), такая карточка исправляется. Внесено в оба робота WB Sync 2026-10-17.

## Кейс 9. Вердикт WB «valid» не значит, что декларация правильная

- Симптом: у семи карточек кабинета ИП стояла РОСС RU Д-DE.РА01.В.01582/26, WB считал её действующей (verdict valid).
- Причина: WB проверяет, что документ существует и действует, но не то, что он относится к этому товару. По сайту Liqui Moly (лист LM_DECL, номера 4087, 20000, 23096, 1540, 1515, 4086, 3350) эти товары покрывает РОСС 20237/26; в перечне 01582/26 нет ни одного из них.
- Решение: правильность определяет источник истины (сайт производителя, перечень декларации), а не вердикт WB и не значение в соседнем кабинете. Переписано 17.10, исполнения 81538–81544.
- Похожий случай в основном кабинете: у 1176 стоит 15088/26, в перечень которой товар (номер 21604) не входит; правильная — ЕАЭС 68827/26.

## Кейс 10. Полная перезапись карточки стирает то, чего API не показывает

- Симптом: после записи у карточки пропал ОКПД 2 и слетела отметка «нужен КИЗ» (07.10, 29 карточек основного кабинета).
- Причина: cards/update заменяет карточку целиком (правило 2). Инструмент передаёт характеристики из чтения; ОКПД 2, введённый руками в личном кабинете, при чтении через API может не приходить — инструмент его не передаёт, и он пропадает. ОКПД 2, записанный через API, при чтении приходит (1745, 1928).
- Решение: перед записью в карточки, где КИЗ поставлен руками, проверять, виден ли ОКПД 2; передавать needKiz (кейс 3). Подробности и порядок — `meta/PROTOCOL_wb-card-write.md`, раздел «Ловушки».

## Кейс 11. Запись ОКПД 2 из перечня маркировки может заблокировать товары

- Симптом: после записи у товаров включилась обязательная маркировка, продавец не зарегистрирован в «Честном знаке» по этой товарной группе — WB заблокировал карточки (моторные масла кабинета ИП, 08.10).
- Правило: код ОКПД 2 из перечня обязательной маркировки писать только после проверки регистрации продавца в «Честном знаке» по этой группе.

## Кейс 12. Галка «Документы, подтверждающие безопасность, не требуются»

- Запись: блок documents = { excludeDocuments: true } в cards/update работает (16 карточек кабинета ИП, исполнение 81433 — галка true, список ошибок пуст).
- Это юридическое заявление продавца: ставить только по названному владельцем списку карточек; автоматически по отсутствию декларации не ставить (решение Андрея 2026-10-17). Роботы карточки с этой галкой не перезаписывают.

## Кейс 13. Артикул продавца указывает на другой товар

- Симптом: у карточки 1709 (Marder-Spray) в артикуле продавца стоит номер 39032 (это номер моторного масла), а в характеристике «Артикул производителя» и в описании — правильный 39021.
- Опасность: роботы сопоставляют карточку с таблицей по артикулу продавца; чужой номер ведёт к чужой декларации и чужому ТН ВЭД.
- Решение: исправить артикул продавца в кабинете руками; запись через API этого поля без решения владельца не делать — это ключ сопоставления.

## Как проверять запись (порядок, который сработал)

1. Перед записью — прогон без записи: что именно уйдёт в карточку (было → станет), сколько характеристик остаётся нетронутыми.
2. Запись по одной карточке; через 45 секунд — чтение карточки и списка ошибок; сравнение поле за полем.
3. Признаки успеха: в documents новый документ (новый id) с нашими номером и датами, verdict valid; needKiz и kizMarked как задумано; лишние характеристики не пропали; в списке ошибок карточки пусто.
4. На следующий день после ночного робота — повторная сверка по листу карточек: держится ли.
5. Каждое действие с карточкой — строкой в журнал действий (дата, кабинет, артикулы и nmID, что изменено, по чьему слову, чем проверено, результат).

Технически (n8n): ответ исполнения с полными данными весит сотни килобайт; узлы HTTP Request оставляют сырой ответ WB в contextData — сужать nodeNames, большие ответы разбирать скриптом или отдельным агентом.
