### references/write.md, строки 19–24
2.5. Сдвиг адреса. Правка, после которой прежний адрес ведёт не туда или никуда, тем же действием пересчитывает все ссылки на прежний адрес — в своём файле и во всех файлах, которые на него ссылаются, включая STATE.md и PLAN.md проектов, файлы meta/ и registry/. Такая правка — любая из четырёх: сдвиг номера пункта, раздела или записи (перенумерация); перенос раздела или правила в другой файл или другой Skill; снятие файла, раздела или Skill; переименование файла или папки.
Ссылки ищутся механически, не по памяти: прежний адрес в квалифицированной форме — путь файла, «<файл>, <номер>», «пункт <номер>», а не голый номер вида «2.5», который даёт шум, — командой `git fetch && grep -rnF '<прежний адрес>' <клон> /mnt/skills/plugins` (среда без клона — Git Read Lines с pattern по каждому известному файлу-читателю, а то, что поиск по всему репозиторию не выполнен, называется в отчёте). Записи журналов LOG.md, отчёты синтеза и харвеста (meta/SYNTHESIS_*, meta/HARVEST_*) и прежний текст статусов Очереди не правятся — они история (11.1); находка в Skill — текстом «было → стало» владельцу и позицией Очереди (10.5).
Почему: после сдвига старый номер обычно существует — он теперь принадлежит другому пункту, и ссылка ведёт не туда, оставаясь целой; после переноса, снятия или переименования ссылка ведёт в пустоту, а сессия проекта, читающая свой PLAN.md, этого не видит.
Признак: проверка битых ссылок ничего не находит, а ссылка приводит к пункту о другом; или PLAN.md проекта отсылает к файлу или Skill, которых в живом Skill нет.

### references/write.md, строки 39–48
Исключение — вычёркивание из наличного текста. Существующий файл разрешено записать заново целиком, когда выполнены три условия сразу:
1. полный текст файла пришёл в контекст этой сессии ответом чтения — Канала или клона — и не восстанавливается по памяти, пересказу или прошлой сессии;
2. правка — удаление или вставка целых строк, все остальные строки переносятся без изменения;
3. запись целиком нужна ради атомарности, которую правкой фрагмента не получить: сейчас это ровно один случай — создание и закрытие задачи лаборатории (4б.5), где файл задачи и INDEX.md обязаны уйти одним вызовом Git Commit Files.

Приёмка — по объекту, не по ответу инструмента:
- в среде с клоном `git diff` против родителя коммита показывает ровно намеренные строки и ни одной другой;
- в среде без клона сходится байтовая арифметика (размер после = размер до − байты удалённых строк + байты вставленных, каждая строка с переводом строки) и один вызов Git Read Lines с pattern по удалённой строке возвращает count = 0, по вставленной — count = 1.
Исключение временное: оно снимается, когда Git Commit Files научится заменять фрагмент на сервере так же, как Git Replace, — тогда атомарность получается без перенабора.

8.2. Текст записи ОБЯЗАН существовать файлом до вызова записи: файлом на диске сессии либо файлом Drive в папке _git_staging (8.3, Git Append File). Набор в теле вызова по памяти или плейсхолдером ЗАПРЕЩЁН.

Кириллица набирается как есть: последовательности \uXXXX модель в теле вызова не набирает — ни вручную, ни копированием вывода json.dumps с настройкой по умолчанию.
Почему — цена, а не порча: каждая кириллическая буква в виде \uXXXX — шесть символов вместо одного, и выход модели растёт в разы. Замер 2026-09-24 на одном и том же тексте 3 439 Б: 6 165 токенов выхода, когда модель набрала его последовательностями \uXXXX в теле Git Append, и 1 260 — набранный кириллицей в textContent файла Drive.
Признак: содержимое файла от этого не портится, поэтому ошибку легко не заметить — видна она только в наборе параметров вызова.
Почему запрет текстом не держится: тело параметра-объекта execute_workflow (inputs) харнесс сам хранит в контексте последовательностями \uXXXX, как бы модель его ни набрала; модель видит свои прошлые вызовы экранированными и начинает так же набирать следующие. Сессия подражает тому, что видит выше по разговору, а прочитанный раньше запрет с подражанием не конкурирует — нарушение повторяет и сессия, прочитавшая этот пункт за минуты до вызова. Удорожание контекста от экранирования харнессом самоконтролем не снимается — его снимают два пути: перенос тела в файл Drive (Git Append File, 8.3) или запись клоном в сессии, где прошёл `git push --dry-run` (9.1), — тогда тело не идёт через вызов инструмента вовсе (решение Андрея 2026-10-20; путь проверен 2026-10-19, отчёт meta/SYNTHESIS_second-brain-git_2026-10-19.md, раздел «Случаи без адреса», пункт 5). Поэтому правило не опирается на самоконтроль там, где его можно заменить устройством:

| (а) читающие вызовы | русский текст в них не набирается вообще — шаблоны поиска по пункту 7.6 SKILL.md, без русских букв |
| (б) дозапись | устройством: Git Append File берёт текст из файла Drive (8.3), набора \uXXXX он не допускает |

### references/project-save.md, строки 43–57
Статус позиции Очереди начинается одним словом из закрытого словаря; всё прочее — после точки с запятой.

| Слово | Когда | После слова |
|---|---|---|
| ОТКРЫТА | позиция заведена, текст правки владельцу ещё не выдан | — |
| ЖДЁТ | текст выдан или работа сделана, ждёт действия владельца (заливки, решения, вставки в промпт) или харвеста | чего именно |
| ВНЕСЕНО | правка стоит в целевом носителе и проверена по объекту | дата и адрес |
| СНЯТА | не вносится | дата и причина |
| ДУБЛЬ | содержание уже живёт в носителе, в другой открытой позиции или задаче лаборатории | адрес |

Форма: «ВНЕСЕНО 2026-10-13 — <адрес>; отложено 2026-10-10 до пакета Архивариуса». При смене статуса новое слово с датой встаёт в начало, прежний текст уходит после точки с запятой и не стирается. Других первых слов нет: «ждёт» строчными, «отложено», «частично», «ЗАКРЫТО», «ВЫПОЛНЕНО», «СНЯТ» — нарушение формы.
Почему: открыта ли позиция, решает разбор по первому слову, и скрипт делает его без ошибок; слово в середине истории («до внесения», «внесено в составе») такой разбор обманывает.
[основание: GIT-61]

Позиция, которая ссылается словом ДУБЛЬ на другую позицию, держит своё содержание только пока та открыта или внесла его в носитель. Поэтому при снятии позиции те, что ссылаются на неё словом ДУБЛЬ, тем же действием получают статус заново. Почему: содержание, переданное по ссылке позиции, которую потом сняли, выпадает из Очереди молча — первым словом статуса оно закрыто, а в носителе его нет. Признак: позиция со статусом ДУБЛЬ указывает на позицию со статусом СНЯТА. [основание: GIT-62]

### references/log-form.md, строки 17–21
11.1. Статус впереди текста. Записи append-only: решение не редактируется — отменяется новой записью со ссылкой. Статус прежней записи меняется одной правкой Git Replace по её строке-заголовку, и форм две:
- ОТМЕНЕНО Р-NN — новая запись отменяет прежнюю целиком;
- ЧАСТИЧНО ОТМЕНЕНО Р-NN (пункт X) — новая запись заменяет один или несколько пунктов прежней, остальные её пункты в силе; пункты называются так, как пронумерованы в прежней записи.

### references/skill-edit.md, строки 5–41
2.6. Правка Skill: канон, зеркало, копии старой формулировки.

Канон Skills — живой Skill в аккаунте владельца (Customize → Skills). Правит его только владелец; сессия видит его снимком в /mnt/skills/plugins/<имя>/ и только читает. Зеркало skills/<имя>/ репозитория — резервная копия и единственная история версий Skills: у Customize истории версий нет, поэтому зеркало, не обновлённое после правки, — потерянная версия. Расхождение зеркала с живым Skill значит «зеркало отстало», а не «Skill испорчен».
Не путать: зеркало не канон и правка в нём ничего не меняет в живом Skill — до 2026-10-18 карта репозитория называла зеркало каноном («правка здесь, затем zip в Customize»), и ни одна правка этим путём не прошла (meta/CASES_skills-mirror-drift.md — текст закрытой задачи labs/sys/t-skills-mirror-drift.md; решение В12 файла meta/HARVEST_2026-10-18_answers.md).
Когда правка Skill начинает действовать и кто заливает zip — Skill second-brain-engineer, раздел Р13; здесь — механика приёмки, зеркала и поиска копий.

Правка Skill, которую внёс владелец, закрывается четырьмя шагами одной сессии, по порядку. Пропущенный шаг называется в отчёте, а не умалчивается.

Шаг 1. Приёмка по объекту. Правка принимается чтением снимка Skill, загруженного в сессию: по якорям правки (новый текст на месте) и на отсутствие старых формулировок, — а не словом «внёс».
Почему: слово владельца — память о действии, а не объект; приёмка по объекту ловит то, чего слово не видит.
[основание: GIT-48]

Шаг 2. Обновление зеркала.
(а) Сначала сверка в обе стороны, по каждому файлу Skill: `diff -rq skills/<имя> /mnt/skills/plugins/<имя>`. Если в зеркале есть файл или текст, которого нет в живом Skill (сессия подготовила правку, а владелец её ещё не залил), — стоп и вопрос владельцу: копия поверх стёрла бы незалитую правку.
(б) Затем файлы живого Skill проверяются на классы И-7 командой поиска признаков — `grep -rnE '@|/webhook/|Bearer|credential' /mnt/skills/plugins/<имя>` — и каждая находка читается глазами. Почему: копия переносит в публичный репозиторий всё, что лежит в живом Skill, а адрес почты или номер ключа, записанный в Skill, в историю repo попадёт навсегда. Находка класса И-7 — стоп: владелец убирает значение из живого Skill, зеркало пишется после.
(в) Иначе файлы живого Skill копируются в skills/<имя>/ командой (`cp`), не набираются моделью — это уже существующий текст (4.5); транспорт — маршрут 9.4(б) файла references/delivery.md, в среде, где прошёл `git push --dry-run`.
(г) Приёмка: после коммита и свежего fetch `diff -rq` этой папки пуст.
(д) Среда без открытого push зеркало не пишет — ни Каналом, ни частями: обновление называется в отчёте и ложится позицией в Очередь (10.5), иначе версия Skill пропадёт при следующей правке.
[основание: GIT-49]

Шаг 3. Поиск копий старой формулировки. Правило, изменённое в одном носителе, продолжает действовать в своих копиях — в других Skills, в файлах meta/, STATE.md и PLAN.md проектов, в текстах мастер-промптов meta/prompts/. Поэтому копии ищутся механически, не по памяти:
(а) из каждого заменённого фрагмента (БЫЛО) берётся одна характерная фраза из пяти–восьми слов в пределах одной строки;
(б) фраза ищется командой по клону репозитория и по папке Skills разом — `git fetch && grep -rnF '<фраза>' <клон> /mnt/skills/plugins`. Ключ -F ищет фразу как есть, без шаблона, поэтому русские буквы в ней работают и без настроенной локали (проверено 2026-10-18 при LC_ALL=C: фраза «правка здесь, затем zip» найдена в живом Skill и в зеркале);
(в) шаг идёт после шага 2: тогда находка в skills/ — копия в другом Skill, а не прежняя версия этого;
(г) каждая находка тем же действием либо правится (файл repo — по правилам записи этого файла; другой Skill или живой мастер-промпт — текстом «было → стало» владельцу и позицией в Очереди по 10.5), либо названа в отчёте с причиной, почему это не копия (запись журнала append-only не правится — она история, 11.1);
(д) в отчёте по каждой фразе — сама фраза, число находок и что сделано; ноль находок пишется явно;
(е) живой текст мастер-промптов поиску недоступен — он живёт в интерфейсе проекта; ищется его зеркало meta/prompts/, и находка там означает, что и живой промпт, скорее всего, несёт ту же копию;
(ж) среда без клона этот шаг не исполняет (Канал каталог не перечисляет, 3.2): шаг называется в отчёте невыполненным и ложится позицией в Очередь;
(з) тот же механический поиск — по имени, ID и пути носителя — обязателен при заморозке или переносе носителя (документа, журнала, файла): правило и порядок — references/migration.md, 13.5.
Правило «копии ищут и снимают тем же действием» — Skill second-brain-engineer, файл references/design.md, пункт 11; здесь — его механическое исполнение. Почему шагом процедуры, а не только правилом метода: стоя в методе проектирования, правило ни разу не исполнилось с 2026-10-09.
[основание: GIT-50]

Шаг 4. Сверка перед заливкой. Перед заливкой zip, собранного из зеркала или из текста сессии, зеркало сверяется с живым Skill в обе стороны, по каждому файлу. Расхождение, найденное сверкой, переносится в отстающий носитель до заливки.
Тем же шагом скрипт проверяет длину поля description во frontmatter SKILL.md: не больше 1024 знаков, иначе Customize отказывает в заливке ошибкой «field 'description' in SKILL.md must be at most 1024 characters». Команда: `python3 -c "import sys,yaml;t=open(sys.argv[1],encoding='utf-8').read();print(len(yaml.safe_load(t.split('---')[1])['description']))" <клон>/skills/<имя>/SKILL.md` — разбор YAML, а не поиск строки, потому что описание, записанное блоком «|» или «>», поиском строки считается как один знак и проходит проверку ложно. [основание: GIT-51]
Почему сверка в обе стороны: правка могла лечь мимо зеркала прямо в Customize, и заливка без сверки стирает её из живого Skill.
Признак: расхождение бывает в обе стороны сразу — один файл новее в зеркале, другой новее в живом Skill.
[основание: GIT-52]
