## Критерии

### К1. Изменены только разрешённые файлы

- **Что проверяется:** список файлов, изменённых в диапазоне пилота.
- **Как проверить:** `git -C /home/claude/sbc diff --name-only BASE END`. Разрешены: `projects/deklaration-v2/STATE.md`, `projects/deklaration-v2/LOG.md`, `meta/scripts/state_apply.py`, `meta/CONTRACT_state-content.md`, файлы в `labs/sys/` (запись итога, файл решений для скрипта). Если в диапазон попали коммиты других проектов, их отделить по `git log --format='%h %s' BASE..END` и проверить только коммиты пилота.
- **Провал:** коммиты пилота меняют что-либо ещё: файл состояния другого проекта (Андрей одобрил только этот), `projects/deklaration-v2/PLAN.md`, мастер-промпт `meta/prompts/deklaration-v2.md`, скрипт `meta/scripts/state_split.py` (его правка по плану — только после успешного пилота, пункт 5), любой Skill.
- **На сломанном результате:** исполнитель «заодно» убрал файл состояния deklaration-ozon или поправил проверку в `state_split.py` — провал. **На исправном:** только разрешённые файлы — прошёл.

### К2. Файл состояния и журнал изменены одним коммитом

- **Что проверяется:** нет промежутка, в котором строки уже удалены из файла состояния, но ещё не дописаны в журнал.
- **Как проверить:** `git -C /home/claude/sbc log --format=%h BASE..END -- projects/deklaration-v2/STATE.md` и то же для `LOG.md`. Каждый коммит пилота, удаляющий строки из файла состояния, должен сам дописывать их в журнал (или журнал дописан коммитом раньше).
- **Провал:** есть коммит пилота, где из файла состояния строки ушли, а в том же или более раннем коммите журнала их нет.
- **На сломанном:** запись двумя вызовами, второй упал — в репозитории файл без строк и журнал без блока — провал. **На исправном:** один коммит — прошёл.

### К3. Журнал только дописан

- **Что проверяется:** старый журнал — побайтовое начало нового; дописан ровно один блок хроники с одной строкой-шапкой.
- **Как проверить:** проверочный скрипт, признак «К3». Вручную: `git show P^:projects/deklaration-v2/LOG.md > /tmp/a; git show P:projects/deklaration-v2/LOG.md > /tmp/b; cmp -n $(stat -c%s /tmp/a) /tmp/a /tmp/b`.
- **Провал:** старый текст журнала изменён в любом месте; шапок хроники в дописанном куске не одна.
- **На сломанном:** исполнитель «поправил» запись журнала или вставил блок в середину — провал. **На исправном:** только дописка в конец — прошёл.

### К4. Ни одна старая строка не потеряна и не переписана

- **Что проверяется:** каждая непустая строка файла состояния в снимке `P^` находится либо в новом файле состояния без изменений, либо в дописанном блоке хроники без изменений (сравнение без учёта отступа по краям); в блоке хроники нет ничего, кроме этих строк и шапки.
- **Как проверить:** проверочный скрипт, признак «К4». Важно: проверка ведётся против `P^`, а не против снимка `20a526e`. Если между составлением критериев и пилотом соседний проект (marketplace-rebuild пишет сюда строки «⚡ Это затрагивает deklaration-v2») дописал строку, а исполнитель резал старую копию, — эта строка пропадёт и проверка это поймает.
- **Провал:** хотя бы одна потерянная или лишняя строка.
- **Почему это не повтор приёмки внутри скрипта:** приёмка `state_apply.py` выполняется на машине исполнителя над файлом, который исполнитель ей дал; контролёр проверяет то, что реально лежит в репозитории, своим кодом.
- **На сломанном:** строка удалена или в хронике лежит пересказ вместо оригинала — провал. **На исправном:** совпадение — прошёл.

### К5. Ушли только длинные строки и строки с доказанным закрытием

- **Что проверяется:** множество строк, ушедших из файла состояния.
- **Как проверить:** проверочный скрипт печатает «ушла короткая строка, нужна запись о закрытии» для каждой ушедшей строки не длиннее 500 байт. Каждая такая строка должна стоять в записи о закрытиях (критерий 9).
- **Провал:** ушла строка не длиннее 500 байт без записи о закрытии. План разрешает трогать только длинные строки и закрытые дела; всё остальное — самовольная уборка.
- **На сломанном:** исполнитель увёз в журнал шесть коротких строк раздела «На обсуждение с Андреем», «чтобы влезть в бюджет», — провал. **На исправном:** ушли только 29 длинных и доказанно закрытые — прошёл.

### К6. Длина строк и размер файла

- **Что проверяется:** в новом файле состояния нет непустой строки длиннее 500 байт (в кодировке UTF-8); ни одна из 29 длинных строк не осталась; новый файл меньше старого.
- **Как проверить:** проверочный скрипт, признак «К6»; он же печатает размер «было — стало» и соблюдён ли бюджет 8 192 байта.
- **Провал:** любая строка длиннее 500 байт; длинная строка осталась на месте; файл не уменьшился.
- **Прогноз плана «около 12 КБ» как условие приёмки отвергнут** — причина в разделе «Где план самый слабый»: при указателе той формы, что записана в плане, 12 КБ достижимы только массовым закрытием дел, и такое условие толкало бы исполнителя закрывать. Размер записывается как факт (критерий 16), а не как порог.
- **На сломанном:** «Эстафета 2026-11-04» сокращена до 900 байт и оставлена — провал. **На исправном:** все строки до 500 байт — прошёл.

### К7. Каждый указатель находит ровно одну строку журнала, и каждая ушедшая строка учтена

- **Что проверяется:** каждая новая строка файла состояния (которой не было в `P^`) содержит указатель формы, записанной в плане: «полностью — LOG.md, хроника ГГГГ-ММ-ДД, строка, начинающаяся словами «…»». Слова в кавычках-ёлочках начинают ровно одну строку во всём новом журнале, и эта строка лежит в дописанном блоке; дата указателя равна дате в шапке блока; на одну ушедшую строку указывает не больше одной короткой; ушедшая строка без указателя бывает только у закрытого дела из записи критерия 9.
- **Как проверить:** проверочный скрипт, признак «К7», и его список «ушедших строк без указателя». Особая ловушка: строки 87 и 88 снимка начинаются одинаково («- 2026-10-22, ⚡ Это затрагивает deklaration-v2 (от …»), а строки 83–85, 99, 102 и 104 — почти одинаково; указатель из первых трёх-пяти слов будет неоднозначным.
- **Провал:** указатель другой формы, слов не находится или находится больше одной строки, дата указателя не совпадает с датой блока (исполнили 2026-11-08, а в указателях осталось «2026-11-07»), на одну строку указывают две короткие, ушедшая строка без указателя не стоит в записи о закрытиях.
- Если исполнитель записал другую форму указателя в правке контракта `meta/CONTRACT_state-content.md`, контролёр меняет в скрипте только выражение поиска под эту форму; условие «ровно одна строка журнала» не меняется.
- **На сломанном:** «…начинающаяся словами «2026-10-22, ⚡ Это затрагивает»» — две строки — провал. **На исправном:** однозначные указатели — прошёл.

### К8. В короткой строке нет чисел, дат и кодов, которых нет в её абзаце

- **Что проверяется:** все номера (артикулы, номера деклараций вида 15088/26, коды ТН ВЭД, числа из трёх и более цифр), даты, номера записей журнала (Р-57), нарядов (Н-28.10-01) и шестнадцатизначные идентификаторы воркфлоу в короткой строке встречаются в той длинной строке, на которую она указывает (сам указатель из сравнения исключён).
- **Как проверить:** проверочный скрипт, признак «К8».
- **Провал:** в короткой строке есть число или код, которого нет в её абзаце. Это механический признак искажения: перепутанный артикул, сдвинутая дата, «12 карточек» вместо «23».
- Граница метода: критерий ловит выдуманное, но не потерянное (короткая строка вправе не перечислять все артикулы — они в журнале). Потерю ловит критерий 10.
- **На сломанном:** «1808 (ИП)» вместо «1807 (ИП)» — провал (проверено на испорченной копии). **На исправном:** числа взяты из абзаца — прошёл.

### К9. Каждое закрытие доказано объектом, а доказательство лежит в репозитории

- **Что проверяется:** для каждой строки, ушедшей без короткой строки, в репозитории на коммите END есть запись (в журнале проекта отдельной записью «Р-номер» или в `labs/sys/t-system-revision.md`), где названы: начальные слова строки; адрес доказательства (запись журнала этого или другого проекта с номером, файл с якорной строкой, объект с датой проверки); почему дело закрыто или отменено.
- **Как проверить:** контролёр сам открывает каждый адрес. Доказательство годится, если оно (а) говорит о том же объекте (тот же артикул, воркфлоу, лист, вопрос), (б) говорит «исполнено», «отменено», «снято» или фиксирует решение Андрея, (в) датировано не раньше даты в закрываемой строке, и (г) в оглавлении журнала после него нет записи, которая снова открывает это дело: `grep -nE '^(Р|Т)-[0-9]+ \|' projects/deklaration-v2/LOG.md`, затем поиск по номеру объекта в записях после найденной.
- **Провал:** записи о закрытии нет в репозитории (только в отчёте исполнителя); адрес не открывается; доказательство про другой объект; доказательство — «прочитано сессией SYS» или «строка соседа принята». Строку соседа может «принять» только сессия проекта deklaration-v2 записью в своём журнале; исполнитель из чата SYS принятие сам не создаёт.
- **Почему критерий ужесточает план:** по плану закрытая строка «получает вместо короткой строки адрес доказательства и уезжает в хронику», но в файлах этому адресу места нет: поле «note» в `state_apply.py` печатается только в отчёт и в файлы не пишется, а приёмка скрипта запрещает добавлять в блок хроники что-либо, кроме исходных строк и шапки. Без этого критерия адрес доказательства живёт только в чате исполнителя.
- **На сломанном:** строка «Руками Андрею: строки PASSPORT…» исчезла, в отчёте написано «закрыто», в репозитории доказательства нет — провал. **На исправном:** у каждого закрытия есть адрес, и он подтверждает закрытие — прошёл.

### К10. Ни одно открытое дело длинной строки не потеряно и не искажено (суждение контролёра, привязанное к объекту)

- **Что проверяется:** содержание каждой из ушедших длинных строк.
- **Как проверить, порядок обязателен:**
  1. До чтения нового файла состояния контролёр по каждой ушедшей строке из `P^` выписывает таблицу открытых дел: объект (артикул, карточка, воркфлоу, лист, вопрос); что не сделано; кто ждёт (Андрей, сотрудник, поддержка Wildberries, другой проект); признак закрытия, если он назван; дата проверки, если строка — состояние объекта. Одна длинная строка обычно несёт несколько дел (например, строка 8 — шесть пунктов «Ждёт Андрея»; строка 20 «Эстафета 2026-11-04» — несколько шагов).
  2. Затем по каждому делу находит, где оно в новом файле состояния (короткая строка или другая оставшаяся строка), или запись о его закрытии по критерию 9.
  3. Сверяет, что не изменились: кто ждёт, что именно ждёт, состояние («открыто» не стало «сделано», «гипотеза» не стала фактом, «по слову Андрея» не пропало), признак закрытия, дата проверки.
- **Провал:** хотя бы одно дело не найдено ни в новом файле, ни в закрытиях; или найдено с изменённым исполнителем, состоянием, условием, датой. Отдельно: условие-ограничение («только код из справочника предмета ИП и по слову Андрея», «на Wildberries ничего не отправлять без отдельного подтверждения», «запись в WB — пачкой на одну категорию») — это открытое правило действия; если оно выпало из файла состояния и не живёт в мастер-промпте или `PLAN.md` проекта, это провал.
- Таблица дел контролёра — часть его вердикта: она прикладывается к ответу.
- **На сломанном:** короткая строка вместо строки 44 говорит «12 карточек ИП без документа — ждёт решения», а в абзаце было ещё «и ответ сотрудника по регистрации в «Честном знаке»» — провал. **На исправном:** каждое дело найдено с тем же смыслом — прошёл.

### К11. Короткая строка относится к категории контракта и несёт её обязательную часть

- **Что проверяется:** каждая новая короткая строка называет одну из четырёх категорий `meta/CONTRACT_state-content.md` (следующий шаг; открытый вопрос с критерием закрытия; блокер; состояние объекта с датой проверки) — план сам требует писать категорию. Открытый вопрос содержит критерий закрытия; состояние объекта — дату проверки.
- **Как проверить:** контролёр читает новые строки (их печатает разница `git diff P^ P -- projects/deklaration-v2/STATE.md`, строки с «+»).
- **Провал:** категория не названа; вопрос без критерия закрытия; состояние без даты.
- **На сломанном:** «- Lopal — см. журнал (полностью — LOG.md…)» — ни категории, ни сути — провал. **На исправном:** «- Открытый вопрос: кто добывает новую декларацию Lopal на трансмиссионные масла; закрыт, когда номер внесён в лист «Декларации» (полностью — …)» — прошёл.

### К12. Блок для страницы обзора цел

- **Что проверяется:** блок obzor в начале файла состояния (форма — `projects/obzor/PLAN.md`, раздел «Устройство», пункт 2) по-прежнему разбирается скриптом страницы, и поля «Следующий шаг» и «Ждёт Андрея» не пусты. Две из 29 длинных строк — именно эти поля (строки 7 и 8 снимка).
- **Как проверить:** (а) проверочный скрипт, признак «К12»; (б) скрипт страницы: `printf '<script id="data" type="application/json">{"projects":[],"dues":[]}</script>' > /tmp/ob.html; cd /tmp && python3 -I /home/claude/sbc/meta/scripts/obzor_build.py /home/claude/sbc /tmp/ob.html --check; echo $?` — код 0 и нет строки «ОШИБКА: deklaration-v2…».
- **Почему нужны оба способа:** скрипт страницы при выпавшем поле молча подставляет пустую строку и ошибки не даёт; при короткой строке без «> » в начале блок обрывается и следующие поля пропадают тоже молча.
- **Провал:** поле пусто или выпало; ошибка скрипта страницы; метка блока не в первых 12 строках.
- **На сломанном:** строка «> Ждёт Андрея: …» уехала в журнал без замены — провал (проверено на испорченной копии). **На исправном:** — прошёл.

### К13. Строка старта и разделы, на которые опирается мастер-промпт, на месте

- **Что проверяется:** строка «Летопись без Claude Project (записи Р-6 и Р-8 журнала). Сразу после этого файла … прочитать целиком мастер-промпт `meta/prompts/deklaration-v2.md` …» сохранена побайтно — мастер-промпт проекта прямо говорит, что об этом чтении сообщает файл состояния. Заголовки «## Статус фаз», «## Следующий шаг», «## Открытые вопросы», «## Блокеры», «## От соседнего проекта» есть — мастер-промпт перечисляет эти части файла, а проект marketplace-rebuild (`meta/prompts/marketplace-rebuild.md`) читает этот файл перед работой в области деклараций.
- **Как проверить:** проверочный скрипт, признак «К13».
- **Провал:** строка изменена или пропала; заголовка нет.
- **На сломанном:** строка старта «укорочена» — провал. **На исправном:** — прошёл.

### К14. Скрипт переноса: старые действия работают как раньше, новое действие не пропускает потерю

- **Что проверяется:** изменённый `meta/scripts/state_apply.py`.
- **Как проверить (в своей папке, на копиях файлов, не в клоне):**
  1. Достать обе версии: `git show BASE:meta/scripts/state_apply.py > /home/claude/kontrol/apply_old.py`, `git show END:meta/scripts/state_apply.py > /home/claude/kontrol/apply_new.py`; файл состояния `git show P^:projects/deklaration-v2/STATE.md > /home/claude/kontrol/STATE.md`.
  2. Составить файл решений старой формы (перенос одного раздела «Lopal: состояние на 2026-10-21» в журнал и строк 28–30 в журнал), путь `state` — на копию, `expect_sha` — её blob sha. Запустить обе версии `python3 -I`, в разные папки вывода; `diff -r` двух папок — пусто.
  3. Запустить новое действие («заменить строку текстом из файла») с неверным `expect_sha` — скрипт должен остановиться словом «СТОП».
  4. Запустить новое действие так, чтобы одна строка пропала (например, указать замену двух строк одной вставкой, где вторая исходная строка нигде не учитывается; либо подменить текст заменяемой строки) — скрипт должен остановиться «ПРИЁМКА НЕ ПРОЙДЕНА» или «СТОП» и ничего не записать в папку вывода.
- **Провал:** вывод старого действия изменился; неверный снимок не останавливает; потеря строки не останавливает или папка вывода всё же заполнена.
- **На сломанном:** приёмка в новом действии вычитает «вставленные строки» из источника, а не из результата, и пропускает потерю — провал. **На исправном:** — прошёл.

### К15. Перенос сделал скрипт, и его можно повторить

- **Что проверяется:** файл решений и файл с короткими строками, по которым шёл перенос, лежат в репозитории (`labs/sys/` или рядом с записью итога), а повторный прогон скрипта даёт ровно то, что закоммичено.
- **Как проверить:** скопировать файл решений и файл коротких строк в свою папку, путь `state` направить на копию `P^`, запустить `python3 -I apply_new.py <решения> <папка>`; сравнить `<папка>/STATE.new.md` с `git show P:projects/deklaration-v2/STATE.md` (`diff` пуст) и `<папка>/LOG_append.md` с дописанным куском журнала (без учёта последнего перевода строки).
- **Почему критерий добавлен сверх плана:** план утверждает «перенос и вставку делает скрипт» — без файла решений это утверждение по объекту не проверяется, и коммит, собранный руками или моделью, был бы неотличим.
- **Провал:** файлов решений нет; прогон даёт другой результат.
- **На сломанном:** файл состояния набран моделью и записан целиком — повторить нечем — провал. **На исправном:** — прошёл.

### К16. Записанный итог совпадает с измеренным, правило контракта не ослаблено

- **Что проверяется:** (а) в `labs/sys/t-system-revision.md` (или в записи журнала пилота) записаны: размер файла состояния «было — стало» в байтах, соблюдён ли бюджет 8 192 байта, число коротких строк, число закрытий; (б) если изменён `meta/CONTRACT_state-content.md` — в нём остались фразы «Ужимать формулировки ради бюджета ЗАПРЕЩЕНО» и «уборка — перенос, не удаление», а рядом с правкой записана дата решения Андрея.
- **Как проверить:** числа (а) сверить с выводом проверочного скрипта; (б) `git diff BASE END -- meta/CONTRACT_state-content.md` и `grep -c` двух фраз в версии END.
- **Провал:** любое записанное число не совпадает с измеренным; итог не записан; записано «бюджет соблюдён», а файл больше 8 192 байт; из контракта убран запрет ужимать формулировки или правка контракта без даты решения Андрея.
- **На сломанном:** «STATE.md 11,8 КБ, цель достигнута», а по скрипту 16 800 байт — провал. **На исправном:** числа совпадают, превышение бюджета названо прямо — прошёл.

### К17. Отложенный: через семь дней обычной работы

- **Что проверяется:** состояние файла не раньше 2026-11-14 (семь дней после пилота; если пилот исполнен позже — через семь дней после даты коммита P).
- **Как проверить:** `git -C /home/claude/sbc pull`; размер `wc -c projects/deklaration-v2/STATE.md`; строки длиннее 500 байт — `awk 'length($0)>500{print NR": "length($0)}' projects/deklaration-v2/STATE.md` (запускать в окружении, где awk считает байты, например `LC_ALL=C awk …`); возврат уехавших строк — для каждой строки блока хроники пилота проверить, не появилась ли она снова в файле состояния (`grep -cF` по первым 60 знакам).
- **Провал:** файл больше 20 480 байт (порог плана «выше 20 КБ», принят); или в файле снова больше пяти строк длиннее 500 байт (ужесточение: размер может держаться за счёт закрытий, а форма — уже вернулась); или строка из хроники пилота вернулась в файл состояния — значит, следующей сессии она понадобилась на старте, и это признак провала уборки из самого контракта («следующая сессия спрашивает о факте, который убран»).
- **Признак плана «следующая сессия проекта спрашивает о факте, уехавшем в хронику» в исходной форме отвергнут:** вопрос сессии живёт в чате, которого в репозитории нет; проверяемая по объекту часть — возврат строки — взята выше.
- **На сломанном:** через неделю 24 КБ и восемь длинных строк — провал, принятие пилота отзывается. **На исправном:** — прошёл.

## Что контролёр получает на вход и чего не получает

**Получает:**
- этот файл критериев (вместе с проверочным скриптом из приложения);
- адрес репозитория и номер коммита P (или только диапазон, из которого он сам находит P по критерию «Подготовка», пункт 2);
- цель Андрея одной фразой (она в начале этого файла).

**Всё остальное берёт сам из репозитория:** старый и новый файл состояния — через `git show P^:…` и `git show P:…`; блок хроники — разницей журналов; адреса доказательств закрытий — открывая их в репозитории. Файлы, присланные исполнителем отдельно от репозитория, к рассмотрению не принимаются — проверяется то, что записано, а не то, что показали.

**Не получает:**
- отчёт исполнителя, его самооценку, вывод приёмки `state_apply.py` с машины исполнителя («приёмка пройдена, потерь 0»);
- разметку исполнителя — какая строка какой категории, что он считал закрытым и почему (кроме записи о закрытиях, которая сама является объектом проверки критерия 9 и лежит в репозитории);
- чат, в котором шёл пилот, и рассуждения сессии, писавшей план (`labs/sys/t-system-revision.md` контролёр может открыть только ради критериев 9 и 16, но раздел «Предложение 2026-11-07» с прогнозом читать до вердикта по критерию 10 не должен — прогноз «около 12 КБ» подсказывает, сколько дел «должно» уйти);
- предварительный вердикт любой другой проверки.

Контролёр — модель сильного класса, не исполнитель и не составитель плана. Он ничего не правит: найденный провал — в вердикт, не в исправление.

## Где план самый слабый

1. **Прогноз «около 12 КБ» арифметически недостижим без массового закрытия дел.** Объект: файл состояния, снимок `20a526e` — 42 строки, которые план не трогает, уже весят 8 052 байта, то есть сам бюджет; указатель той формы, что записана в плане («полностью — LOG.md, хроника 2026-11-07, строка, начинающаяся словами «…»»), с однозначными словами весит около 190 байт, на 29 строк — около 5,5 КБ. Итого не меньше 13,6 КБ ещё до сути дела; модель пилота у составителя с минимальной сутью дала 16 824 байта. Прогноз, принятый как мерило успеха, толкает исполнителя к самой рискованной ветке — закрытию дел без короткой строки. Поэтому прогноз выведен из условий приёмки (критерий 6), а закрытия проверяются строже всего (критерий 9). Бюджет 8 192 байта пилот не достигнет ни при каком исходе, кроме закрытия большей части дел, и это надо сказать Андрею до исполнения.
2. **Адресу доказательства закрытия нет места в файлах.** Объект: `meta/scripts/state_apply.py` — поле «note» в файлы не пишется, а приёмка скрипта не допускает в блоке хроники ничего, кроме исходных строк и шапки. Закрытая строка исчезает из файла состояния, а её доказательство остаётся только в чате исполнителя (закрыто критерием 9).
3. **Независимая приёмка по плану получает три файла, а не репозиторий** (пункт 3 предложения): ей нечем сверить адреса закрытий и нечем убедиться, что файлы — те, что закоммичены. Закрыто разделом «Что контролёр получает на вход».

## Приложение. Проверочный скрипт контролёра

Сохранить в собственную папку контролёра (не в клон), запускать `python3 -I`.

```python
#!/usr/bin/env python3
"""Проверка пилота deklaration-v2 по объектам репозитория. Только чтение.
Запуск: python3 -I pilot_check.py <клон> <коммит P>   (P — коммит, в котором изменились STATE.md и LOG.md)
Печатает факты для критериев 3-8 и 12-13; итог «ПРОВАЛ» по каждому сработавшему признаку."""
import re, subprocess, sys
from collections import Counter
R, P = sys.argv[1], sys.argv[2]
S, L = "projects/deklaration-v2/STATE.md", "projects/deklaration-v2/LOG.md"
def show(rev, path):
    return subprocess.run(["git", "-C", R, "show", f"{rev}:{path}"], capture_output=True, check=True).stdout
fails = []
def fail(k, msg): fails.append(f"{k}: {msg}")
old_b, new_b = show(P + "^", S), show(P, S)
logo_b, logn_b = show(P + "^", L), show(P, L)
old = old_b.decode().splitlines(); new = new_b.decode().splitlines()
# К3: журнал только дописан
if not logn_b.startswith(logo_b): fail("К3", "старый LOG.md не является началом нового — журнал изменён, а не дописан")
block = logn_b[len(logo_b):].decode().splitlines()
heads = [l for l in block if l.startswith("Хроника | ")]
if len(heads) != 1: fail("К3", f"строк-шапок хроники в дописанном куске: {len(heads)}, нужна 1")
hdate = re.search(r"\d{4}-\d{2}-\d{2}", heads[0]).group(0) if heads else None
blk = [l.strip() for l in block if l.strip() and not l.startswith("Хроника | ")]
# К4: мультимножество
src = Counter(l.strip() for l in old if l.strip())
newc = Counter(l.strip() for l in new if l.strip())
inserted = newc - src                      # строки нового STATE.md, которых не было
kept = newc - inserted
moved = src - kept                         # строки, ушедшие из STATE.md
if Counter(blk) != moved:
    fail("К4", f"блок хроники != ушедшим строкам: потеряно {sum((moved-Counter(blk)).values())}, лишних {sum((Counter(blk)-moved).values())}")
# К5: ушли только длинные строки (короткие — только с записью о закрытии, сверяется вручную по К9)
moved_short = [l for l in moved if len(l.encode()) <= 500]
long_old = [l.strip() for l in old if len(l.encode()) > 500]
stay_long = [l for l in long_old if l in kept]
print(f"строк в старом: {sum(src.values())}; длинных (>500 Б): {len(long_old)}; ушло: {sum(moved.values())}, из них коротких: {len(moved_short)}; вставлено новых: {sum(inserted.values())}")
for l in moved_short: print("  К5/К9 — ушла короткая строка, нужна запись о закрытии:", l[:90])
if stay_long: fail("К6", f"длинные строки остались: {len(stay_long)}")
# К6: длина
over = [(i, len(l.encode())) for i, l in enumerate(new, 1) if len(l.encode()) > 500]
if over: fail("К6", f"строки длиннее 500 Б в новом STATE.md: {over}")
if len(new_b) >= len(old_b): fail("К6", "новый файл не меньше старого")
print(f"размер: было {len(old_b)} Б, стало {len(new_b)} Б; бюджет 8192 Б {'соблюдён' if len(new_b) <= 8192 else 'превышен'}")
# К7: указатели
logtext_lines = [l.strip() for l in logn_b.decode().splitlines()]
target_of = {}
for l in inserted:
    m = re.search(r"хроника (\d{4}-\d{2}-\d{2}), строка, начинающаяся словами «(.+?)»", l)
    if not m: fail("К7", f"вставленная строка без указателя установленной формы: {l[:80]}"); continue
    if m.group(1) != hdate: fail("К7", f"дата указателя {m.group(1)} != дата шапки хроники {hdate}")
    words = m.group(2)
    hits_all = [x for x in logtext_lines if x.startswith(words)]
    hits_blk = [x for x in blk if x.startswith(words)]
    if len(hits_all) != 1 or len(hits_blk) != 1:
        fail("К7", f"слова «{words[:50]}» начинают {len(hits_all)} строк журнала, {len(hits_blk)} строк нового блока; нужна ровно одна")
        continue
    target_of[l] = hits_blk[0]
pointed = Counter(target_of.values())
for t, n in pointed.items():
    if n > 1: fail("К7", f"на одну ушедшую строку указывают {n} коротких: {t[:60]}")
unpointed = [l for l in moved if l not in pointed]
print(f"ушедших строк без указателя (должны быть ровно закрытые по К9): {len(unpointed)}")
for l in unpointed: print("  без указателя:", l[:90])
# К8: числа, даты, идентификаторы
TOK = re.compile(r"\d{4}-\d{2}-\d{2}|[РТНУ]-[\d.]+(?:-\d+)?|\b[A-Za-z0-9]{16}\b|\d+/\d+|\d{3,}")
for l, t in target_of.items():
    body = re.sub(r"\(?полностью — LOG\.md, хроника.*", "", l)
    extra = set(TOK.findall(body)) - set(TOK.findall(t))
    if extra: fail("К8", f"в короткой строке есть числа/коды, которых нет в её абзаце: {sorted(extra)} — {l[:60]}")
# К12: блок obzor
idx = next((i for i, l in enumerate(new[:12]) if l.startswith("<!-- obzor-блок")), None)
if idx is None: fail("К12", "метки obzor нет в первых 12 строках")
else:
    f = {}
    for l in new[idx + 1:]:
        if not l.startswith("> "): break
        k, _, v = l[2:].partition(":"); f[k.strip()] = v.strip()
    for k in ("Состояние", "Дата", "Что это", "Следующий шаг", "Ждёт Андрея"):
        if not f.get(k): fail("К12", f"поле блока obzor «{k}» пусто или выпало из блока")
# К13: строка старта и разделы
start = [l for l in old if l.startswith("Летопись без Claude Project")]
if not start or start[0] not in new: fail("К13", "строка старта (прочитать мастер-промпт) изменена или пропала")
for h in ("## Статус фаз", "## Следующий шаг", "## Открытые вопросы", "## Блокеры", "## От соседнего проекта"):
    if h not in new: fail("К13", f"нет заголовка {h}")
print("\n".join(fails) if fails else "признаков провала по К3-К8, К12, К13 нет")
```
