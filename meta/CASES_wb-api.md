## Отзывы, вопросы, заказы FBS, финансы

- Ответ на вопрос: PATCH `/api/v1/questions`, тело `{id, answer:{text}, state:"wbRu"}`. Поле `state` обязательно — без него ответ не появляется на сайте.
- Отзывы и вопросы — оба API на `feedbacks-api.wildberries.ru`, токен категории «Вопросы и отзывы». Credential — Header Auth, заголовок `Authorization`, значение — токен без слова `Bearer` (так работает с 2026-06-02; в спецификации — схема apiKey в заголовке `Authorization`; у Finance API ниже значение с `Bearer`, и оно тоже работает). Первый ответ на отзыв — POST `/api/v1/feedbacks/answer`, тело `{id, text}`, ответ 204. Правка уже опубликованного ответа — PATCH `/api/v1/feedbacks/answer` с тем же телом: один раз и только в течение 60 дней с момента отправки (цена этой единственной правки — следующая строка). Адрес `/api/v1/feedbacks` принимает только чтение: PATCH на него даёт 405 с заголовком `allow: GET, HEAD`. Список отзывов — GET `/api/v1/feedbacks`, обязательные параметры `isAnswered`, `take` (до 5 000), `skip` (до 199 990); воркфлоу WB Reviews Intake берёт `take` = 100 и `skip` = номер страницы × 100 и останавливается, когда пришло меньше 100. Отвеченные отзывы и вопросы Intake читает только за последние 60 дней (`dateFrom`, `dateTo`): без окна узел сборки отвеченных падал по памяти. Лимит частоты — 3 запроса в секунду, всплеск 6, на один аккаунт продавца на все методы категории «Вопросы и отзывы»: его делят все воркфлоу отзывов и вопросов. Методы и лимит сверены 2026-10-13 со спецификацией Wildberries `09-communications.yaml` (копия в репозитории eslazarev/wildberries-sdk, коммит 9885191). Основание: 2 случая, последний 2026-07-27 — 2026-06-02 при запуске Intake и Publication PATCH на `/feedbacks` дал 405 и был заменён на POST `/feedbacks/answer`; узел `04A_Rollback_Review` с 2026-06-02 бил PATCH в `/api/v1/feedbacks` и получал 405, то есть откат ответов не работал восемь недель, пока 2026-07-28 адрес не исправили на `/api/v1/feedbacks/answer` (WB_REVIEWS_INDEX, строки 927, 476, 1075, 1080; projects/wb-reviews/NOT_TAKEN.md, строка 56; урок У-129 журнала projects/archivarius/LOG.md, запись Р-28).

- `/orders/status`: поле называется `orders`, не `orderIds`; тело `{orders:[...]}` передаётся объектом, без stringify.
- `supplierStatus=confirm` включает и отгруженные заказы — фильтровать дополнительно по tracking status `shipped`.
- Пагинация статистики: курсор `rrdid`, между страницами узел Wait на 70 секунд из-за ограничения частоты.
- Finance API v1: POST `finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed`, токен категории «Финансы». Даты с зоной: `2026-05-26T00:00:00+03:00`. Пагинация: `rrdId` в теле, старт 0, до ответа 204. Денежные поля приходят строками. Credential — Header Auth, имя `Authorization`, значение `Bearer TOKEN`.
- Знак строки финансового отчёта задаёт поле `doc_type` («Возврат»), а не название операции `operation_name`; при возврате `revenue` и `for_pay` положительные (projects/wb-ue/LOG.md, Р-11). Wildberries молча переименовывает операции: с 01.09.2026 «Логистика» стала «Доставка», «Коррекция логистики» — «Коррекция стоимости доставки»; неизвестное название падает в категорию «прочее» и пропадает из витрины (там же, Р-12). Тождество выплаты: `forPay = retailAmount − vw − vwNds − acquiringFee − ppvzReward`, выполнено на всех 289 продажах недели 14–20.09.2026 (там же, Р-33). `commissionPercent` — номинал тарифа: в выплате он не участвует, и вычитать комиссию, посчитанную по нему, из `for_pay` нельзя — двойной счёт (там же, Р-18).
- Домены-ловушки, которые НЕ работают: `statistics-api` (старый v5), `common-api`, `finance-api/.../{reportId}`.
- Семантика статусов FBS (POST `/api/v3/orders/status`). `supplierStatus` меняет действие продавца: `new` — новое задание, `confirm` — на сборке (задание добавлено к поставке), `complete` — в доставке (поставка передана в доставку), `cancel` — отменено продавцом, `cancel_carrier` — отменено перевозчиком (только трансграничные поставки). `wbStatus` — статус системы Wildberries: рабочие `waiting` (в работе), `sorted` (отсортировано), `sold` (получено покупателем), `ready_for_pickup` (прибыло в пункт выдачи), `postponed_delivery`, `accepted_by_carrier`, `sent_to_carrier`; отмены — `canceled` (отмена сборочного задания), `declined_by_client` (покупатель отменил в первый час, пока задание не на сборке), `canceled_by_client` (покупатель отказался при получении), `defect` (отмена из-за брака), `canceled_by_carrier`. Отмена покупателем или самим Wildberries видна только в `wbStatus`, а `supplierStatus` при этом часто остаётся `new`. Детект отмены нужен отдельной ветвью по `wbStatus` со ВСЕМИ значениями отмены из этого списка, иначе висящий хвост вечно блокирует переход «поставка отгружена». Значение, которого нет ни среди отмен, ни среди рабочих статусов, — сигнал в отчёт, а не тихий пропуск: новый статус Wildberries иначе уходит не в ту ветвь. Значения сверены 2026-10-13 со спецификацией Wildberries `03-orders-fbs.yaml` (копия в репозитории eslazarev/wildberries-sdk, коммит 9885191, скачана с dev.wildberries.ru; напрямую документация из сессии не открывается). Основание: 2 случая, последний 2026-07-06 — 2026-06-29 около двадцати отказов `declined_by_client` и `canceled_by_client` висели в журнале со статусом `new` и блокировали закрытие поставок, ветку отмен в Order Close v2 (`DM26WhTJyCV0DhkP`) добавили 2026-06-30; 2026-07-06 заказ 5271100427, отменённый самим Wildberries, тем же путём держал поставку WB-GI-249910370, пока ветку не дополнили (projects/wb-logistics/LOG.md, записи Р-75, Р-83 и Р-89; урок У-120 журнала projects/archivarius/LOG.md, запись Р-27).

- Времени приёмки на уровне заказа не существует: `/orders/status` отдаёт только текущий статус, `/supplier/orders` — только `date` и `lastChangeDate`. Время приёмки есть только на уровне поставки: `scanDt` в GET `/supplies` плюс `/supplies/{id}/order-ids`.

## Карточки и маркировка — справочные факты; порядок записи и разобранные случаи — `meta/CASES_wb-api-card-write.md`

**Ответ 200 ничего не доказывает.** POST `/content/v2/cards/update` отвечает 200 и меняет `updatedAt` карточки, но документ в карточке может остаться прежним: так шесть карточек отказали поштучно 2026-10-05, хотя журнал ошибок был пуст (projects/deklaration-ozon/LOG.md, Т-7). Итог записи проверяется двумя способами, оба обязательны:
- перечитать карточку через POST `/content/v2/get/cards/list` и сравнить поле за полем;
- прочитать журнал ошибок асинхронной записи — POST `/content/v2/cards/error/list`, тело `{cursor:{limit:100}, order:{ascending:false}}`. Метод GET на этот адрес отвечает 405. Записи журнала сгруппированы по пакетам и `vendorCode`, поля `nmID` в них нет (projects/deklaration-wb/PLAN.md, абзац «Факты записи»).

**Одна ошибочная карточка отклоняет всю склейку.** Склейка — группа карточек с общим `imtID`. Если в ней есть карточка с ошибкой, Wildberries не применяет запись ни к одной карточке склейки (projects/deklaration-ozon/LOG.md, Р-30).

**Запись заменяет карточку целиком.** Характеристика, не переданная в запросе, стирается. Поэтому запись идёт только по схеме «прочитал свежую карточку в том же прогоне → поправил нужные поля → отправил целиком»; узел перед отправкой сравнивает отправляемое с прочитанным (projects/deklaration-wb/PLAN.md, абзац «Ловушка записи»). Поле `kizMarked`, не переданное в запросе, принимается равным false — передавать текущее значение из чтения (projects/deklaration-ozon/LOG.md, Р-44).

**Случайные отказы пачки.** Ответ 400 или 500 «Internal server error» на пачку карточек бывает случайно; повтор той же пачки проходит (projects/deklaration-wb/LOG.md, Р-12 пункт 6).

**Где лежит декларация.** Характеристики 15001135 «Номер декларации соответствия», 15001136 «Номер сертификата соответствия», 15001137 «Дата регистрации», 15001138 «Дата окончания действия». Характеристики для ссылки на запись реестра нет. Кроме характеристик, у карточки есть блок `documents`: `items[{type, number, startDate, endDate, verdict{verified, status, reason}}]` и `overallVerdict` — это собственная сверка Wildberries документа с реестром (projects/deklaration-ozon/LOG.md, Р-21). При каждой записи декларации Wildberries создаёт документ заново, с новым id; промежуточный вердикт вроде `supplier_not_registered` через несколько часов может смениться на `ok` (meta/PROTOCOL_wb-card-write.md, раздел 5). Даты документа Wildberries сверяет с реестром — расхождение даёт `document_dates_mismatch` (projects/deklaration-wb/PLAN.md).

**Форматы дат в карточках.** Встречаются разные, и разбирать их надо явно, по всем встреченным формам; неузнанная дата — ошибка с сигналом, а не пустое значение:
- ММ-ДД-ГГ: `01-27-27` значит 27.01.2027 (meta/PRODUCT_DATA_HIERARCHY.md, раздел 4). Воркфлоу «LM_DECL — WB Sync ИП» эту форму не понимал, пока разбор не исправили (projects/deklaration-wb/STATE.md);
- ДД.ММ.ГГГГ — в характеристиках 15001137 и 15001138 у карточек, снятых зондом 2026-10-02 (projects/deklaration-ozon/LOG.md, Р-21);
- в блоке `documents` даты приходят в виде ГГГГ-ММ-ДД с временем (код узла `03_Build_Rows` воркфлоу `fGHfVrI58Ws1wfTw`).
Основной «LM_DECL — WB Sync» разбирает три формата (projects/deklaration-wb/STATE.md).

**ОКПД 2 — характеристика 15004292.** ОКПД 2, введённый руками в личном кабинете, API не показывает, поэтому полная перезапись карточки (раздел 1) его стирает. Для предметов «Автохимия» и «Смазки автомобильные» вместе с ним Wildberries снимает `needKiz` и `kizMarked`, и повторная запись `kizMarked=true` без ОКПД 2 не принимается: так 2026-10-07 потеряли отметку маркировки 29 карточек основного кабинета (projects/deklaration-ozon/LOG.md, Р-44 и Т-9). ОКПД 2, записанный через API, API показывает, и он переживает следующую запись (projects/deklaration-wb/LOG.md, Р-7 и Р-11).
Не путать: причина, названная строкой выше («ОКПД 2 стёрт — поэтому снялась маркировка» у 29 карточек), не доказана (журнал `projects/deklaration-ozon/LOG.md`, запись Р-46): для этих 29 карточек вероятная причина — не переданный в записи `needKiz`, механизм доказан на других карточках (кейс 3 `meta/CASES_wb-api-card-write.md`; `meta/PROTOCOL_wb-card-write.md`, строка 50; разбор 5 файла `meta/SKILLS_MAP_resolution_2026-10-19.md`; позиция AJ-27 Очереди).

**Нужна ли маркировка (КИЗ).** Wildberries решает по паре «предмет + ТН ВЭД»: справочник `/content/v2/directory/tnved`, поле `isKiz`. Для части предметов («Автохимия», «Смазки автомобильные») маркировка нужна только при ОКПД 2 из перечня постановления Правительства № 1683 от 30.11.2024 (projects/deklaration-ozon/LOG.md, Р-44 пункт 2). Справочник ОКПД 2 — `/api/content/v2/directory/okpd` (взято из позиции очереди AH-25; вызовом в журналах не подтверждено).

**Два поля маркировки.**
- `needKiz` («Нужна маркировка КИЗ») — только чтение: Wildberries выводит его сам из предмета, ТН ВЭД и ОКПД 2. Через API без ОКПД 2 признак не включается; ручная галка сотрудника в личном кабинете включает.
Не путать: строка выше («`needKiz` только чтение, через API без ОКПД 2 не включается») противоречит кейсам 3 и 4 `meta/CASES_wb-api-card-write.md`: переданный в записи `needKiz` сохраняется, не переданный WB решает заново; действующее правило — там (позиция AJ-27 Очереди).
- `kizMarked` («Подтверждаю, что на товар нанесена маркировка») — записывается, но это юридическое заявление продавца по закону о маркировке (289-ФЗ). Ставить только по прямому слову владельца на названные им карточки (projects/deklaration-wb/LOG.md, Р-7 «отвергнуто»; meta/PROTOCOL_wb-card-write.md, раздел 1).
Не путать: правило о `kizMarked` в строке выше изменено 2026-10-21 — действующее правило живёт в `meta/PROTOCOL_wb-card-write.md`, раздел 1, и в мастер-промпте проекта deklaration-v2 (`meta/prompts/deklaration-v2.md`).
Блокировку карточки «подлежит обязательной маркировке» снимает не запись в карточку, а регистрация продавца в «Честном знаке» по этой товарной группе (projects/deklaration-wb/LOG.md, Р-7 пункт 3).
