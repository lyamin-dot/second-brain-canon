# Как исправлять карточки WB через API — порядок работы

Версия для человека. Копия для агента на английском — `meta/PROTOCOL_wb-card-write.en.md`; содержание одно и то же, при правке менять оба файла. Введено 2026-10-09 по задаче Андрея; решения — журнал `projects/deklaration-wb/LOG.md`, записи Р-7, Р-11, Р-12, Р-14, Р-15, Р-16.

## 1. Что считается правильным значением (источники истины)

| Поле карточки WB | Номер характеристики WB | Откуда брать правильное значение |
|---|---|---|
| Номер декларации соответствия | 15001135 | Сайт Liqui Moly: лист LM_DECL книги LM_DECL_MASTER. В книге Price Master это колонка X листа Artikel и колонка E (ref_decl) листа WB_Compare. |
| Дата регистрации декларации | 15001137 | Лист «Декларации» книги LM_DECL_MASTER, колонка date_from, сверенная с выпиской: дата регистрации берётся из выписки, а не считается как «окончание минус год» (бывает 181, 216, 339 дней; Р-16). Писать только в виде ДД.ММ.ГГГГ: «ММ-ДД-ГГ» создаёт документ без срока, WB отвечает «Вы не приложили документ» (Р-14). |
| Дата окончания декларации | 15001138 | Тот же лист, колонка date_to. Просроченную декларацию в карточку не писать. |
| ТН ВЭД | 15000001 | Выписка декларации. Эталон по артикулу — лист ARTIKEL_PROPS книги Price Master, колонка N tnved_decl; колонка O tnved_decl_src говорит, откуда взят код или почему пусто (журнал `projects/deklaration-wb/LOG.md`, запись Р-13). Пусто — эталона нет, поле карточки не трогать. Колонка C tnved того же листа — НЕ эталон, это ТН ВЭД из карточки основного кабинета. |
| ОКПД 2 | 15004292 | Только документ: выписка декларации, Национальный каталог «Честного знака», импортёр. Подбор по аналогии запрещён; 2026-10-09 Андрей временно снял запрет только для 11 карточек автохимии кабинета ИП (запись Р-12). Для любых других карточек — спросить Андрея. 2026-10-10 Андрей разрешил записать ОКПД 2 20.59.41.000 ещё в 1345 и 1745, где КИЗ стоит руками, — это опыт, исход смотреть в LOG (Р-16). |
| Галка «Подтверждаю, что на товар нанесена маркировка» (kizMarked) | поле карточки, не характеристика | Это заявление продавца по закону о маркировке. С 2026-10-21 (запись Р-39 журнала `projects/deklaration-v2/LOG.md`, пункт 9): в обоих кабинетах WB равна «Нужен КИЗ» основного кабинета — товар, которому нужен КИЗ, физически продаётся только маркированным. До 2026-10-21 ставилась только по прямому слову Андрея на названные карточки. |
| Признак «Нужна маркировка КИЗ» (needKiz) | поле карточки | Исправлено 2026-10-17 (запись Р-21, `meta/CASES_wb-api-card-write.md` кейсы 3 и 4): поле ОБЯЗАТЕЛЬНО передавать в каждой записи, равным «Нужен КИЗ» основного кабинета (с 2026-10-21, запись Р-39 журнала `projects/deklaration-v2/LOG.md`, пункт 10; до того — как в карточке): без него WB снимает признак и вместе с ним kizMarked. Включить признак через API по коду ОКПД 2 нельзя (с 19.20.29.170 WB его не включил); ручная галка сотрудника в личном кабинете включает, а переданный needKiz true её удерживает. Оба инструмента записи и оба робота WB Sync с 2026-10-17 передают needKiz как в карточке. Правильное значение на этом этапе берётся из основного кабинета («Кипарис»), потому что там его недавно проверили руками. |

То, что сейчас стоит в карточках любого из двух кабинетов, правильным значением НЕ считается. Копировать значения из основного кабинета в кабинет ИП нельзя: в основном кабинете есть ошибки, а галка kizMarked — заявление конкретного юридического лица.

## 2. Где смотреть, что сейчас в карточках

- Лист WB_Cards_Staging книги Price Master — карточки основного кабинета; заполняет робот fGHfVrI58Ws1wfTw каждую ночь в 04:10 по Москве.
- Лист WB_Cards_Staging_IP — карточки кабинета ИП; робот vIteQxGrqI7kLkb0, 04:25 по Москве.
- Лист WB_Compare — сравнение «эталон / основной кабинет / кабинет ИП» по декларации, ТН ВЭД, ОКПД 2 и маркировке; только формулы, обновляется сам.
- Правила чтения этих листов — `meta/PRODUCT_DATA_HIERARCHY.md`, разделы 4б и 4в.

## 4. Порядок работы

1. Составить список карточек и правильных значений по разделу 1. Значения считать по листам (WB_Compare, ARTIKEL_PROPS, лист «Декларации»), а не по памяти.
2. Отдельно выписать спорные случаи: эталона нет; эталонная декларация просрочена; два источника расходятся (например номера Liqui Moly нет в перечне декларации на листе «Декларации», хотя LM_DECL указывает эту декларацию); на карточке стоит другая действующая декларация.
3. Вписать строки в 01_Params, режим «проверка», запустить. Проверить ответ узла 03_Build: сколько карточек найдено, пуст ли список problems, что именно уйдёт в каждую карточку (поле report: «было → станет»).
4. Показать сводку Андрею вместе со спорными случаями. Писать — только после его согласия. В кабинете ИП действующую, но неверную декларацию заменяем по источнику истины (правило «не заменять» снято 2026-10-10, Р-15); в основном кабинете действующую декларацию не заменяем.
5. Перевести в режим «запись», запустить. Посмотреть узел 06_Report: статус каждой пачки. Ответ WB 200 с пустой ошибкой — принято в обработку. Ответ 400 или 500 «Internal server error» бывает случайно — повторить только упавшие пачки через ONLY.
6. Вернуть mode в «проверка» и очистить ONLY. В 01_Params дописать номера исполнений.
7. Проверить результат на СЛЕДУЮЩИЙ день по листам WB_Cards_Staging_IP и WB_Compare после ночного робота. Исправлено 2026-10-17: «задержка в часы» была ложным диагнозом (`meta/CASES_wb-api-card-write.md`, кейсы 1 и 7): если через 45 секунд в блоке documents карточки нет нового документа с нашими номером и датами — запись не применилась, ждать не нужно. Документ в карточке, где он уже создан, меняется только блоком documents.items с датами вида 2026-09-18T00:00:00Z вместе с характеристиками (оба инструмента записи так делают с 2026-10-17). Вердикт нового документа приходит через 3–11 секунд; общий вердикт карточки (overallVerdict) WB пересчитывает позже — его смотреть на следующий день.
8. Записать решение и итог в журнал проекта (`projects/deklaration-v2/LOG.md`; до 2026-10-21 — `projects/deklaration-wb/LOG.md`, проект закрыт записью Р-40 журнала deklaration-v2), следующий шаг — в `STATE.md`.

## 5. Ловушки

- Полная перезапись карточки стирает характеристику, не переданную в запросе. 07.10 у 29 карточек основного кабинета слетела отметка «нужен КИЗ»: вероятный механизм — непереданный needKiz (кейс 3 файла meta/CASES_wb-api-card-write.md), версия «стёрт ОКПД 2, введённый в кабинете» не доказана (запись Р-46 журнала projects/deklaration-ozon/LOG.md). ИСТОРИЯ ДИАГНОЗА: до 2026-10-18 здесь стояло «Полная перезапись карточки стирает ОКПД 2, введённый сотрудником в личном кабинете … Так 07.10 потеряли КИЗ 29 карточек основного кабинета» — поправлено харвестом 2026-10-18 (решение В14). Карточки основного кабинета из предметов «Автохимия» и «Смазки автомобильные» без ОКПД 2 из документа не перезаписывать.
- Запись ОКПД 2 из перечня обязательной маркировки может включить needKiz. Если продавец не зарегистрирован в «Честном знаке» по этой товарной группе, WB заблокирует карточку. Так были заблокированы моторные масла кабинета ИП 08.10.
- WB при записи декларации вместе с блоком documents.items создаёт документ заново (новый id); запись одними характеристиками уже созданный документ не меняет (кейс 1 файла кейсов; уточнено харвестом 2026-10-18, решение В14). Промежуточный вердикт документа, например supplier_not_registered, может смениться на ok через несколько часов.
- Значения характеристик передаются массивом строк: например ["3403990000"], ["01.06.2026"].
- В карточке, где характеристик мало (у 1053 их две), инструмент передаёт только то, что есть: недостающие характеристики он не придумывает.
- Ответ 200 и новый updatedAt применения не доказывают: смотреть блок documents карточки (verdict) на следующий день.
- Карточки, где КИЗ поставлен руками, а ОКПД 2 через API не виден: запись без ОКПД 2 рискует снять needKiz; итог пробы на 1345 и 1745 (Р-16, Р-19, Р-21): отметки КИЗ слетели не из-за ОКПД 2, а потому что запись не передавала needKiz; с переданным needKiz отметка держится при любом коде (`meta/CASES_wb-api-card-write.md`, кейсы 3 и 4). Подбор ОКПД 2 по аналогии — по-прежнему только по слову Андрея на названные карточки; коды ведутся в листе «Ввод» книги DEKL 2.0, колонки D–E и K–R.
- Даты читаются из WB в разном виде (в том числе «ММ-ДД-ГГ»), а записываются в характеристиках 15001137 и 15001138 только как ДД.ММ.ГГГГ, в блоке documents.items — только как ГГГГ-ММ-ДДT00:00:00Z (кейс 2 файла meta/CASES_wb-api-card-write.md; уточнено харвестом 2026-10-18, решение В14).
