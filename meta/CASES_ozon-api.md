## Общее, отзывы и вопросы

- Ozon кладёт ошибку в тело ответа при коде HTTP 200. Примеры: `{"code":9,"message":"obsolete method cannot be used"}` у отключённого `/v3/finance/transaction/list` — исполнение при этом success с нулём строк (labs/ozon-ue/t-n8n-ozon-workflow-defects.md); `PermissionDenied` «not available with existing subscription» на публикации ответа на отзыв (projects/n8n/STATE.md). Поэтому тело ответа проверяется на поля `code` и `message`, а итог — по объекту. Общее правило «результат по объекту, не по статусу» — корень R4 (успех по статусу при отказе по существу) в n8n-engineering-manual.
- Лимит частоты Seller API считается на Client-Id, а не на воркфлоу: все воркфлоу, которые ходят в Ozon с одним Client-Id, делят один счётчик; у второго кабинета (другое юрлицо) свой Client-Id, значит и свой счётчик. Общий лимит — 50 запросов в секунду на все методы с одного Client-Id, с 22.05.2025 (прежде 10); превышение даёт 429 «You have reached request rate limit per second». Источник — официальный канал новостей Seller API в Telegram (t.me/s/OzonSellerAPI, сообщения 485 и 491); саму документацию Ozon из сессии не прочитать (подраздел «Внешние источники» ниже). Сверх общего у отдельных методов свой, более низкий потолок, и он назван в тексте ответа 429: `/v1/analytics/data` в августе 2026 отвечал «rate limit exceeded for `seller-api` client, current max rate per sec.: 2». С 24.02.2026 операции с товарами (`/v3/product/import`, `/v1/product/update/offer-id`, `/v1/product/pictures/import`, `/v1/product/import-by-sku`) ограничены 30 000 товаров в минуту на все четыре метода вместе; запрос, в котором товаров больше остатка, отклоняется целиком с текстом «You have reached operation items limits» (пересказ avoshop.ru от 18.02.2026, первоисточник Ozon не прочитан). Поэтому 429 при одном запросе за прогон — не дефект этого воркфлоу и паузой внутри него не лечится: диагностика начинается с текста ошибки (какой лимит назван) и с суммы запросов всех воркфлоу того же Client-Id в том же окне времени; пауза между пакетами внутри воркфлоу уменьшает только его собственный вклад. Основание: 1 случай, 2026-08-25 — шесть из шести плановых прогонов OZON RAW Konversion Sync (`SElTcMg3BpY6pmdo`) 20–25.08.2026 упали 429 при одном HTTP-запросе за прогон, на том же Client-Id было ещё 12 активных воркфлоу (отчёт REPORT_H-25.08-01, раздел 2, ID — registry/documents.md; урок У-77 журнала projects/archivarius/LOG.md, запись Р-13).

- Поля `pros`, `cons`, `text` раздельные; статус `rejected` возможен.
- Публикация отзыва: POST `/v1/review/comment/create`, задержка 4 секунды между запросами.
- Маппинг `operation_type` → узел `06C_Map_Operation_Category`, обычный объект JS. Новый тип добавляется в словарь; неизвестные дают `'Не классифицировано: ' + opType`.
- Эндпоинты вопросов идут БЕЗ `/product/`: POST `/v1/question/list`, `/v1/question/answer/create`, `/v1/question/answer/delete`.
- Публичный ответ на карточке закрыт без тарифа Premium Plus (порядка 25 тысяч рублей в месяц); ответ через чат `/v3/chat/` виден только самому покупателю.
- Вебхука `TYPE_NEW_QUESTION` не существует.
- Стоп пагинации `/v1/review/list` — любое из трёх: пустой массив, `last_id` не изменился, длина меньше `limit`.
- Встроенная пагинация HTTP-узла для транзакций: `paginationCompleteWhen: other`, `completeExpression: ={{ $response.body.result.operations.length < 1000 }}`.
- Ограничение частоты примерно один запрос в секунду: Items per Batch = 1, Batch Interval = 4000 мс.

## Начисления (accrual)

- POST `/v1/finance/accrual/by-day`, тело `{date, last_id}` → ответ `{accruals:[...], last_id}`. Пагинация останавливается, когда `last_id` пришёл пустой строкой, НЕ по длине массива.
- `accrued_category` принимает `POSTING`, `ITEM`, `NON_ITEM`; у каждой своя вложенная форма объекта.
- Наблюдаемая формула нэттинга: `sale_amount + sale_commission + delivery.total_accrued = total_amount`.
- `container_fees` ни разу не приходило непустым; статус поля неизвестен.
- Ловушка совместимости с `/v3/posting/fbs/get` (вход `{posting_number}`): валидный `posting_number` даёт только `unit_number` из записей с `accrued_category=POSTING`. Взятый из `ITEM` или `NON_ITEM` даёт 404 в 85–91 проценте случаев.

## Декларации — дополнение к `projects/deklaration-ozon/PLAN.md`

- Для типа DECLARATION стандарт — только `NATIONAL` или `EAEU`. Что значение прошло проверку Ozon, не значит, что оно верное: `EAEU` для декларации РОСС Ozon принял (projects/deklaration-ozon/LOG.md, Т-5, Р-16) — стандарт выводится из номера документа.
- `page_size` у `/v1/product/certificate/list` — не больше 100. У `/v1/product/certificate/products/list` поле `limit` от 1 до 1000, `page_size` не годится; по товару он отдаёт только `product_id`, `sku`, `product_status_code`, причину отказа не отдаёт (projects/deklaration-ozon/LOG.md, Т-4).
- Статус документа `approved` не значит, что товары одобрены: Ozon проверяет каждый товар отдельно, порядка 10 дней; итог перечитывается отдельным режимом «статус» (projects/deklaration-ozon/LOG.md, Р-36). Вкладки кабинета «На проверке», «Отклонены», «Одобрены» фильтруют статус документа, а не товаров: документ с зависшими товарами стоит в «Одобрены», зависание видно только по колонке «Одобрено товаров» (projects/deklaration-ozon/PLAN.md).
- Факты этого раздела сняты с полного swagger.json, прочитанного в браузере 2026-10-01, и проверены вызовами; из сессии документацию Ozon прочитать нельзя (SKILL.md, «Внешние источники»).

## Создание товаров и штрихкоды

Проверено вызовами 2026-10-22 (кабинет ИП, инструмент `u06pa4u5sDYdQD3W`, исполнения 84187, 84193, 84205; независимая приёмка 84209; `labs/ozon-ue/t-ozon-ip-card-copy.md`, раздел «Итог автопилота 2026-10-22»):
- Тело `/v3/product/import`, собранное из ответа `/v4/product/info/attributes` другого кабинета, принято: статус imported, модерация approved за 1–2 минуты, свой SKU; `vat` "0.22" принят.
- Ловушка: `/v4` отдаёт `complex_attributes` плоским списком `{id, complex_id, values}`, а импорт ждёт группы `[{attributes:[...]}]`. Плоский список принимается без ошибки, видео молча теряется. Видео по ссылке хранилища Ozon (mp4) в группе принимается.
- `/v1/barcode/generate` отвечает `{"errors":[]}`; штрихкод вида `OZN<SKU>` появляется меньше чем через минуту. У немаркируемых товаров основного кабинета тоже штрихкод `OZN<SKU>` (артикул 1930).
- Повторный `/v3/product/import` с тем же offer_id обновляет товар и сохраняет переданный штрихкод.
- Фильтр `product_id` в `/v4/product/info/attributes` со значением "0" — ошибка валидации всего запроса.
- Характеристика 23536 «Нужен код маркировки» в ответе `/v4/product/info/attributes` хранится строкой `true` или `false`, не «да»/«нет»; в основном кабинете заполнена у всех 419 товаров (true 289, false 130; исполнение 84169, прочитано 2026-10-23).
  Не путать: «в большинстве карточек основного кабинета 23536 нет» — записано 2026-10-22 ошибочно: инструмент искал «да» и не узнавал `true`.
- Обновление существующего товара через `/v3/product/import` (проверено 2026-10-23, кабинет ИП, 170 товаров, исполнения 84839, 84841, 84843, 84849): товар ищется по offer_id, поэтому offer_id берётся из самого кабинета буква в букву (другой offer_id создаст новую карточку); без цены — ошибка уровня error `price_is_negative` при статусе imported, поэтому передаётся собственная текущая цена товара; непереданная старая цена очищается (10 товаров, у которых она равнялась цене); непереданный штрихкод НЕ удаляется; НДС передаётся числом ("0", "0.22"), а не "0.00". Код продавца 9024 Ozon держит равным offer_id своего кабинета. Класс опасности 9782 на одном товаре (1738) импортом не сменился. Предупреждение `video_cover_link_invalid` (21845) — уровень warning, видео при этом принимается.
- `pdf_list`: `/v4` отдаёт `[{file_name: <ссылка>, name}]`, импорт ждёт `[{index, name, src_url}]`; непереведённый список — 400 «PDFList: invalid URL» на весь запрос (ничего не записано, исполнение 84841).
- `/v1/barcode/add` с `{barcodes:[{barcode, sku}]}` отвечает `{"errors":[]}`, штрихкод виден в карточке через минуту (57 GTIN основного кабинета маркируемым товарам ИП, исполнения 84857, 84861).
- Исполнение n8n с узлами HTTP на полном ассортименте (около 400 карточек с рич-контентом) весит 10 МБ и больше в contextData; get_workflow_execution с includeData обрывает транспорт MCP — итог такого воркфлоу писать на лист.

Сняты с swagger.json (docs.ozon.ru/api/seller/swagger.json) и раздела «Штрихкоды» seller-edu.ozon.ru, прочитанных встроенным браузером 2026-10-21 и 2026-10-22; вызовами не проверены. Читатель — `labs/ozon-ue/t-ozon-ip-card-copy.md`.

- `/v1/product/import-by-sku` создаёт копию карточки другого продавца по SKU; свою скопировать нельзя; не работает, если продавец запретил копирование своих карточек; обновить товар по SKU нельзя; поля: sku (обязательно), name, offer_id, price, old_price, vat, currency_code.
- `/v3/product/import`: до 100 товаров в запросе; обязательны description_category_id, type_id, offer_id, price; реальные габариты и вес, не 0; при обновлении передаётся вся информация о товаре; видео — ссылкой на MP4 или MOV, complex_id 100001, атрибуты 21841 (ссылка) и 21837 (название); до 50 изображений JPG или PNG по общедоступной ссылке; после модерации товар виден в кабинете, но не покупателям, пока не выставлен на продажу; поле promotions с типом REVIEWS_PROMO (акция «Ускоренный сбор отзывов») — ENABLE, DISABLE или UNKNOWN по умолчанию. Статус задачи — `/v1/product/import/info`, статус модерации — `items.statuses.moderate_status` в `/v3/product/info/list`.
- Ответ `/v4/product/info/attributes` несёт почти ровно тело `/v3/product/import`: attributes, complex_attributes, barcode, barcodes, description_category_id, type_id, images, primary_image, color_image, pdf_list, model_info, габариты, вес, name, offer_id.
- `/v1/product/pictures/import` отключается с 1 октября 2026 года, замена — `/v2/product/pictures/import`.
- `/v1/barcode/generate` — до 100 товаров за запрос; `/v1/barcode/add` — до 100 штрихкодов на товар; оба — не больше 20 запросов в минуту с аккаунта. Лимиты на ассортимент, создание и обновление в сутки — `/v4/product/info/limit`.
- Штрихкод уникален на всей платформе: два продавца не могут использовать одинаковые штрихкоды, даже для одного и того же товара; один продавец не может дать один штрихкод разным товарам. Штрафов пока нет, правило закреплено в «Комиссиях и тарифах»; предупреждение приходит после создания карточки и после отгрузки на FBS. Не нарушение: магазин первым добавил штрихкод; у товара есть код маркировки в «Честном знаке»; есть УИН; realFBS; уценённый товар. Блог SelSup пишет о штрафе 5 ₽ за единицу с 01.12.2026 — первоисточником не подтверждено.


## Источник истины кажется ошибочным — сначала подозревать свои записи

Решение Андрея 2026-10-22 (наряд Н-22.10-01, пункт 5; вопрос J1#14 харвеста 2026-10-22). При работе с личным кабинетом продавца на маркетплейсе, когда источник истины (карточка в кабинете, ответ API кабинета, сайт производителя, с которым сверяется карточка) кажется ошибочным, сначала подозреваются собственные записи: таблицы, файлы кейсов, журналы, прочитанное раньше. Источник не исправляется; расхождение выносится на обсуждение с Андреем. Правило относится только к работе с кабинетом маркетплейса и в общие Skill не вносится. Первоисточник — запись Р-39, пункт 6 журнала `projects/deklaration-v2/LOG.md` (строка «подозрение на ошибку в источнике истины» таблицы `projects/deklaration-v2/PLAN.md`). Та же запись стоит в парном файле кейсов другого маркетплейса (`meta/CASES_wb-api.md`, `meta/CASES_ozon-api.md`).
