# Пределы файлов repo: чем они заданы на самом деле

Читатель — сессия, которой нужен предел: перед чтением, перед записью, перед ротацией, при споре о потолке.
Момент — до операции. Действует для `lyamin-dot/second-brain-canon`, ветка `main`.

Все числа сняты измерением 2026-09-17, наряд Н-17.09-02, среда Claude Code. Чем снято — в самой строке. Клетка без измерения помечена «не измерено» и рассуждением не заполняется. При расхождении с числом в `second-brain-git` действует число отсюда: там числа замера 2026-09-10, здесь — 2026-09-17.

## 1. Ограничителей три, и ни один из них не есть размер файла

О-1. Цена ЧТЕНИЯ задана транспортом и способом чтения. Один и тот же файл 17 930 Б стоит от 1 900 до 60 660 Б контекста — разброс в 32 раза при неизменном файле.
О-2. Цена ЗАПИСИ задана операцией: сколько байт текста проходит через модель. У правки фрагмента, дозаписи и сборки скриптом размер файла в тело вызова не входит вовсе.
О-3. Предел тела одного вызова записи в байтах на 32 768 Б не достигнут.

Следствие: число «байт на файл» ограничивает цену ровно одной операции из семи — полной перезаписи через модель. Для остальных шести оно не ограничивает ничего и при этом запускает ротации.

Транспорты: **К** — Канал n8n через MCP; **Г** — клон git в среде сессии (read-only); **С** — скрипт из Claude Code, маршрут §9.4(б).
Цена чтения дана в долях размера файла: 1,00× значит «в контекст пришло ровно столько байт, сколько в файле».

**Доступность С не выводится из имени среды.** В этой сессии Claude Code `git push --dry-run` отказан прокси: «lyamin-dot/second-brain-canon is not in this session's authorized repository set». `clone` и `fetch` при этом открыты. Предикат — входит ли репозиторий в authorized set сессии, а не то, как среда называется. Проверяется в самой сессии одной командой `git push --dry-run`, ДО выбора маршрута.

## 3. Три числа с протоколом

**(а) Чтение Каналом против клона.** Объект: `projects/git-migration/LOG.md`, 17 930 Б, blob `a2217f86`. Задача одна и та же — достать текст записи Р-97. Протокол: одинаковая задача, разные транспорты, считаются вызовы и байты, пришедшие в контекст. Результат — строки 1 и 2 таблицы §2. Клон дешевле Каналом читаемого целого файла в 17,8 раза; самый дешёвый путь Каналом (`Git Read Lines` при известном номере строки) дешевле клона, но номер строки сам стоит 1,50× через `Git Grep`.

**(б) Предел тела одного вызова записи.** Протокол: текст порождается скриптом на диске, его blob sha снимается `git hash-object` ДО вызова, текст уходит телом `git-write`, результат читается независимо с `origin/main` после `fetch` и сверяется построчным `diff` с эталоном. Путь зонда — только `test/probe-sizes.md`.
- 2 048 Б → blob `1a649ca1` = эталон. exec 63970.
- 32 768 Б → blob `3437f3bd` = эталон, `diff` пуст. exec 63973.

**Порог в байтах для реального текста НЕ ИЗМЕРЕН, и это не пробел зонда.** Т-66 наблюдал порчу на 32 768 Б реального текста; зонд наблюдал успех на 32 768 Б регулярного. Байты те же — различается воспроизводимость текста. Одна попытка на данном размере не устанавливает порога недетерминированного процесса, а оценка вместо измерения наряд не засчитывает. Поэтому порог в байтах не назначается ни сейчас, ни впредь: ограничитель здесь не «сколько байт», а «порождён ли текст этой сессией» — см. П-2 ниже.

**(в) Стоимость ротации.** Закрывает О-6 `STATE.md` и позицию P-1 очереди.
- Ротаций `LOG.md` за 13 рабочих дней (04.09–17.09): **25**. Считаны по объекту — коммиты, в которых `LOG.md` уменьшился, а `LOG_ARCHIVE.md` вырос; пять правок на −1/−2 Б из счёта исключены. Это 1,9 ротации в рабочий день.
- Сегодняшняя ротация, маршрут §9.4(б): **1 коммит** `e56effc`, 2 пути, перенесено 48 958 Б.
- Та же работа маршрутом через модель 13–14.09: **244 версии** `LOG_ARCHIVE.md` (213 за 13.09 + 31 за 14.09) и потеря 69 номеров — Р-79. Отношение 244 : 1.
- Байты `LOG.md`: бюджет 16 384 Б пробит в 7 днях из 12, максимум 98 575 Б (6,0× бюджета) 16.09.
- **Число чтений `LOG.md` измерению не поддаётся**: репозиторий хранит записи, а не чтения. Наблюдаемая нижняя граница — 13 (дней, в которые проект трогали, по коммитам в `projects/git-migration/`). Верхней границы объект не даёт. Третье число О-6 не будет получено этим путём никогда, и ждать его — значит держать позицию очереди вечно.

Что из (в) следует. Потолок 16 384 Б за 13 дней не удержал файл под собой ни разу подряд и произвёл 25 ротаций. Он ограничивал не цену читателя, а частоту служебной операции.

## 4. Потолки по трём классам файлов

**П-1. Летопись (`STATE.md`, `PLAN.md`, `LOG.md`, `NOT_TAKEN.md`). Потолок в байтах на файл не нужен.**
Заменяющий ограничитель — **бюджет читателя на момент чтения** (он уже объявлен в §4.5 и верен), плюс **способ чтения**. Измерено: та же запись стоит 0,11× файла при чтении срезом и 3,38× при чтении целиком. Пока способ чтения не назван, никакое число на файле бюджет читателя не удерживает — что и показали 7 дней превышения из 12.
Ротация остаётся, но её основание меняется: не «файл перерос число», а «запись отработана по признакам §5.2». Ротация по признакам — работа с содержанием; ротация по байтам — работа со счётчиком.

**П-2. Запись: ограничитель не байты, а происхождение текста.**
Если текст записи ПОРОЖДЁН этой сессией — он идёт через модель в любом случае, и его размер ограничен тем, сколько сессия написала; отдельное число излишне.
Если текст УЖЕ СУЩЕСТВУЕТ (ротация, возврат версии, перенос тела) — он через модель не идёт никогда, независимо от размера: `Git Replace`, `Git Append` или маршрут §9.4(б). Измерено: 177 Б через модель на файл 32 691 Б.
Это правило проверяемо одним вопросом и не требует ни одного измерения при исполнении.

**П-3. Лаборатория — см. §5.**

**П-4. Канон (`core/`, `meta/`, `registry/`). Потолок в байтах на файл не нужен; действует бюджет читателя CORE.**
Читатель CORE читает весь список Манифеста двумя вызовами `Git Read Batch` — его цена есть сумма, и раскладка суммы по файлам ему безразлична (это уже сказано в §4.5). Отдельные числа на `core/R-NN.md` и на `meta/*` ограничивают не его.
Замер 2026-09-17: список Манифеста — 11 файлов, целы все 11, мёртвых путей в списке нет; `meta/header.md` 650 + `core/MANIFEST.md` 9 921 + файлы списка 27 722 = **38 293 Б**. Признак старта по §7.2: 11 / `core/R-15.md` / `02548052`.
Разрез `core/` по §6.3 остаётся — но его основание не байты, а тема: файл делится там, где меняется предмет. Это в §6.3 уже написано верно и правки не требует.

## 5. Лаборатория `labs/sys/`: вердикт по семи файлам — один на все семь

**Потолок 2 048 Б на файл лаборатории снимается.** Не поднимается и не обходится разрезом.

Объект: за трое суток с заведения лаборатории (14.09) над потолком оказались 7 файлов из 17 — `INDEX.md` 5 976 (2,92×), `t-maintenance-audit.md` 3 854 (1,88×), `t-knowledge-loop.md` 3 647 (1,78×), `t-gdocs-read-guard.md` 2 790 (1,36×), `t-monitors-no-reader.md` 2 460 (1,20×), `t-get-execution-context.md` 2 291 (1,12×), `t-git-migration.md` 2 098 (1,02×).

Почему не «поднять число»: поднятое число воспроизведёт то же событие позже. Числа 2 048 не было под чем измерять — оно не выведено ни из бюджета читателя, ни из транспорта.
Почему не «разрезать»: задача — единица смысла, а не байтов; §4б.7 уже говорит, что переросшая задача разворачивается в летопись, и это решение по существу, а не по весу. Резать задачу ради числа есть ужимание, запрещённое §5.1.
Почему «снять»: за трое суток потолок произвёл 7 объявлений о превышении, 0 действий и одну позицию очереди. Единственный ответ, к которому он подталкивает, запрещён §5.1, а отказать в записи по нему запрещено запретом 16. Ограничитель, у которого нет ни одного разрешённого следствия, ограничителем не является.

Что встаёт вместо него. Читатель лаборатории на старте читает `INDEX.md` и ничего больше (4б.3) — **5 976 Б**, при том что весь вес лаборатории 37 409 Б. Это и есть его цена, и она вчетверо меньше суммы файлов. Ограничитель лаборатории: **`INDEX.md` держит строку сути и не держит тел задач**. Он уже записан в 4б.3 словами и в числе не нуждается.
Строка «над потолком» в `INDEX.md` вместе с потолком теряет предмет и уходит при ближайшей правке списка.

## 7. Поведение Канала, вскрытое зондом и не записанное нигде

**Р-1. `Git Append` дописывает не `text`, а `"\n" + text`** — безусловно, в том числе когда файл уже оканчивается переводом строки. Замер: отправлено 42 Б, файл вырос на 43 Б, в хвосте образовалась пустая строка (exec 63975, `test/probe-sizes.md` 32 691 → 32 734 Б).
Следствие для §8.3: сверка `bytes_after − bytes_before = bytes_appended_expected` даёт расхождение ровно на 1 байт на КАЖДОМ вызове. Верная сверка — `bytes_after − bytes_before = bytes_appended_expected + 1`. Сессия, исполняющая §8.3 буквально, читает штатную работу как порчу и рискует повторить вызов — то есть удвоить запись.

**Р-2. `nodeNames` в `get_execution` не режет `executionData.contextData`.** У `Git Grep` туда попадает base64 всего файла и заголовки GitHub, поэтому «точечный» поиск по файлу 17 930 Б стоит 1,50× файла — дороже, чем прочитать файл клоном целиком. У `git-read` и `Git Read Lines` `contextData` пуст. Класс тот же, что Р-74 у `git-commit`; теперь он измерен и на `Git Grep`.
Следствие: `Git Grep` — не инструмент экономии контекста. Экономит `Git Read Lines`, и только при уже известном номере строки.
