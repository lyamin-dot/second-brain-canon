## 3. ЛОВУШКИ САМОЙ КНИГИ

### 3.1. Управляющие ячейки живут где угодно

В книге `WB_Аналитика` весь аналитический слой держался на трёх ячейках листа `dashboard`: `K3` (начало периода), `K4` (конец периода), `I4` (числовой параметр). На `K3` и `K4` ссылались девять формул `FILTER` в строке 2 листа `sales_unit_economics`. Лист выглядел пустым, потому что был прочитан диапазоном `A1:J24` — колонка `K` одиннадцатая, в чтение не попала.

Стирание `dashboard` обнулило границы периода → `FILTER` перестал отдавать строки → `sales_unit_economics` опустел → обнулились `cost_monitor` целиком и часть `weekly_history`.

**Решение** — зона параметров в первых строках листа, которая не очищается ни при какой операции, со сводным экраном ниже неё: правило в SKILL.md §4.2.

### 3.2. Затраты хранятся со знаком минус

В витринах Андрея комиссия, логистика, хранение, штрафы и себестоимость лежат отрицательными числами. Из этого следует простое и единое правило направления для светофоров и дельт: **ухудшение = отрицательная дельта, для всех строк без исключения**. Отдельная ветка «для затрат наоборот» — источник ошибок; в исходной таблице она стояла и красила рост затрат зелёным.

Исключение — строки, где рост означает ухудшение: §9.2.

### 3.3. Пустое окно SUMIFS возвращает 0, а не пусто

Будущие недели в понедельной витрине показывали нули, и любой график обрывался в ноль на последних колонках. Нулей нет — данных нет, это разные вещи.

**Решение:** обернуть каждую формулу периода в проверку по ОБЕИМ границам данных — и по последней дате, и по первой:

```
=IF(OR(B$3<FIRST_DATA_DATE,B$3>LAST_DATA_DATE),"", <исходная формула> )
```

Левая граница нужна не меньше правой. Гард только по последней дате оставил в `oz_weekly_history` нули во всех периодах ДО начала реальных данных. Ряд наполовину из нулей ушёл в бэктест порогов, и пол материальности вышел 0 ₽ — то есть не гасил ничего (задачи РЫЧАГ Зоны А INDEX OZON_UE, 2026-09).

Вторая ловушка того же места: в Google Sheets `""=0` даёт `FALSE`. Знаменатель проверять И на пустую строку, И на ноль, иначе деление на пустую строку даёт `#DIV/0!` на всех будущих периодах.

Третья ловушка знаменателя: `AND` и `OR` вычисляют ВСЕ аргументы, а не останавливаются на первом ложном. Защита вида `AND(E>0, R/(F/E)>порог)` при E=0 даёт `#DIV/0!` всей формуле, а внутри цепочки `IF` — и всем следующим веткам (книга «Товары», колонка «Диагноз», 2026-09-28, позиция AH-10). Деление ставить только в ветку `IF` после проверки:

```
=IF(IF(AND(N(E11)>0,N(F11)>0),R11/(F11/E11),0)>P_LOG, "логистика дорога для цены", … )
```

`N()` вокруг проверяемых ячеек нужен, если там может стоять пустая строка из формулы: по правилу сравнения Google Sheets текст больше любого числа, поэтому `"">0` должно давать TRUE, и проверка пропустит пустоту к делению (в книгах Андрея не проверялось; `N()` безвреден в любом случае). В книге «Товары» E и F — числа, записанные скриптом, и там формула стоит без `N()`.

### 3.4. Диапазоны с жёстким потолком

Классика: формулы считают по `A3:A5000`, а на листе 15 000 строк. Суммы недосчитываются молча, без ошибки. То же у именованных диапазонов: `_data!B1:B50000` при листе в 50 589 строк.

**Решение:** открытый диапазон от первой строки данных — `sales_unit_economics!$P$2:$P`, без нижней границы. Первая строка — та, где данные реально начинаются: диапазон с третьей строки при данных со второй терял себестоимость одной продажи в каждой неделе, где она стояла во второй строке (1 526 ₽ за неделю 14–20.09.2026, `projects/wb-ue/STATE.md`, раздел «Открытый риск»).

ИСТОРИЯ ДИАГНОЗА: прежде здесь стояло «границу вычислять при каждом прогоне от `getLastRow()` и подставлять в текст формулы; открытая запись менее предсказуема при межлистовых ссылках — для витрин Андрея выбран вычисляемый потолок». Опровергнуто листом `sales_unit_economics`: `getLastRow()` на нём ответил 5000 при 12 382 заполненных строках (прецедент 14.09.2026), и вычисленный потолок молча недосчитал себестоимость, а следом завысил прибыль. `getLastRow()` возвращает последнюю строку с содержимым по мнению Google, и на листе, который заполняет формула-разлив (`FILTER`), это число ненадёжно. Совет сам порождал дефект (противоречие В15 харвеста 2026-10-08). Если открытый диапазон где-то всё же неприменим, потолок брать с запасом от `getMaxRows()` и сверять сумму диапазона с суммой всей колонки.

**Построчные формулы не растут вместе с листом.** Формулы, стоящие в каждой строке отдельно, кончаются там, где их когда-то протянули. Строки, добавленные внизу листа, приходят пустыми: в `sales_unit_economics` формулы колонок D, J, K, L, N–U кончались строкой 12 999, и продажи, которые `FILTER` вывел ниже, получили пустую себестоимость — `SUMIFS` счёл её нулём, прибыль завысилась молча (`projects/wb-ue/LOG.md`, Р-56). Добавить строки мало — нужно продлить формулы. Долговременное лечение: одна `ARRAYFORMULA` в первой строке данных на всю колонку с открытым диапазоном, тогда рост данных не требует ручных действий.

**Лист-хаб: колонки только в конец.** На лист, на который другие книги ссылаются по адресам ячеек (через `IMPORTRANGE` с адресом вида `Лист!X2:X`), колонки в середину не вставляются: внешняя ссылка — это текст адреса в чужой книге, вставка его не сдвигает, и чужая формула начинает читать соседнюю колонку. Новую колонку добавлять последней. Построчные формулы и диапазоны с жёстким потолком на вставленные строки тоже не распространяются (абзацы выше). Источник — колонки X, Y, Z и sku_cost в Price Master!Artikel, `labs/ozon-ue/t-product-data-model.md`, записи 2026-10-02…04.

**Зеркало из склейки `IMPORTRANGE` имеет две границы.** Первая — сетка листа (число строк и колонок), вторая — последний диапазон, жёстко записанный в формуле склейки. Автоматическое расширение сетки снимает только первую; рост источника за вторую не попадает в зеркало без ошибки (удалённая задача лаборатории OZON_UE `t-ozon-raw-mirror-grid`, источник — харвест 2026-10-08). При росте источника проверять обе.

Отдельно: расширение чужих именованных диапазонов (в которые пишет n8n) — только отдельным пунктом меню и по явному решению, никогда заодно с оформлением.

### 3.5. Один источник ≠ все статьи

`cost_monitor` считался целиком из `sales_unit_economics`, где лежат только строки с категорией `sale`. Поэтому «Хранение» там структурно всегда ноль: хранение приходит отдельной категорией в `_data`. Прежде чем чинить «странный ноль», проверить, есть ли для этой статьи источник в этом листе вообще.

### 3.6. ARRAYFORMULA не разворачивает MAXIFS

`MAXIFS`, `MINIFS` и подобные агрегаторы с условиями внутри `ARRAYFORMULA` не считаются построчно, а возвращают ОДНО значение на всю колонку — без ошибки и без предупреждения.

В sku_cost_Шаблон формула `sales_unit_economics!U3` так выдаёт всем строкам одну дату действия закупки — 01.01.2026. Товары, чья история закупки начинается позже января, получают нулевую закупку, остальные — январскую. Себестоимость недели 21.09.2026 занижена на 299 728 ₽; прибыль в `weekly_commissions`, `dashboard`, рейтингах и `loss_analyzer` завышена (сверка с книгой «Деньги» по 39 неделям, 2026-09-28, позиция AH-9).

**Признак:** колонка одинаковых чисел там, где они обязаны различаться.

**Решение:** «значение на дату» по строкам считать скриптом и писать значениями — так считают книги «Деньги» и «Товары», сверенные до копейки (SKILL.md §8). Вариант формулой через `BYROW` или `MAP` с `LAMBDA` в книгах Андрея не проверялся: применять только после сверки с расчётом скрипта на тех же строках.

### 3.7. Тяжёлая книга: flush, чтение после записи, снимок

Тяжёлая книга — та, где пересчёт идёт минутами: sku_cost_Шаблон (33 листа, несколько по 45–50 тысяч строк с массивными формулами и зеркалом через `IMPORTRANGE`). В ней три вещи, безобидные в лёгкой книге, срывают прогон (прогоны Фазы 5, 2026-09-26/27, позиция AH-3):

1. **`SpreadsheetApp.flush()` гарантированно даёт `Service timed out: Spreadsheets`.** Причина не в объёме вызова: flush ждёт, пока книга закончит ВЕСЬ отложенный пересчёт. Следствие: определять что-либо опытным зондом, который пишет в книгу и ждёт результата, здесь нельзя — только чтением того, что в книге уже записано и уже считается правильно. Как так определить разделитель формул — SKILL.md §4.8.
2. **Чтение после записи** (механизм и правило — SKILL.md §4.8) здесь упирается в потолок выполнения. Нарушение дважды дало `Exceeded maximum execution time`, во второй раз без указания на функцию в стеке — диагноз по одному логу не ставится. Оговорка 2026-09-28: та же ошибка в книгах «Цена» и «Деньги» оказалась модальным окном, а не чтением (SKILL.md §2.2). Были ли в прогонах Фазы 5 модальные окна, не проверено; механизм сброса записей при чтении от этого не отменяется, но при повторе ошибки сначала исключить модальное окно.
3. **Снимок листа средствами Apps Script неисполним** — чем его заменить, сказано в SKILL.md §4.3.

Практический вывод 2026-09-28: новые книги не читают расчётные листы тяжёлой книги вовсе, а берут сырой источник (`sales_raw_operations` в файле OzonRawАналитика) и только один справочный лист (`cost_price_history`). Если книге всё же нужен расчётный лист тяжёлой книги — только отдельным пунктом меню (SKILL.md §4.7).

### 3.8. Колонку, которую заполняет формула, не писать значениями

В колонку, которую заполняет формула — `ARRAYFORMULA`, `IMPORTRANGE`, `FILTER` или построчная формула, — значения не пишутся ни скриптом, ни n8n, ни руками:
- запись в зону разлива массивной формулы ломает её: формула показывает `#REF!` («массив не может быть развёрнут, так как перезапишет данные»);
- число, вписанное поверх построчной формулы, молча расходится с ней: ячейка больше не считается, а выглядит как остальные.

Узел Google Sheets в n8n при добавлении строк (append) считает ячейку с формулой занятой, даже когда формула вернула пустую строку. Поэтому строки, которые дописывает робот, ложатся ниже конца разлива, а не сразу под данными (`projects/deklaration-ozon/LOG.md`, Р-4: лист «Декларации» сделан без формул — счётчик и список пишет робот, светофор даёт условное форматирование).

**Правило:** перед любой записью в существующую колонку прочитать её через `gsheets-read` с `render:"FORMULA"` и убедиться, что там значения, а не формулы. Колонку, которую дописывает робот, строить без формул: вычисление — либо в роботе, либо в отдельной колонке правее, куда робот не пишет.

### 3.9. Ключ сравнения: один тип с обеих сторон и уникальность

**Тип.** Ключ, который в одном источнике хранится числом, а в другом текстом, не совпадает ни разу и без ошибки: в выгрузке листов staging артикул пришёл числом `1058.0`, в Artikel — целым `1058`; сравнение текстом дало 0 совпадений, сравнение после приведения к одному типу — все (`projects/card-content-sync/PLAN.md`). При обновлении-вставке по такому ключу вместо обновления появляются дубли. Перед сравнением обе стороны приводятся к одному типу — в формулах (`TO_TEXT` с обеих сторон) и в узлах n8n.

**Уникальность.** Если у ключа в источнике две строки, `VLOOKUP` молча берёт первую. В LM_DECL артикул 3326 стоял в двух строках (321 и 370), и сверка выдавала ложное «расходится» (`labs/ozon-ue/t-product-data-model.md`). Перед построением сверки по ключу проверить источник на повторы: `=COUNTA(A2:A)-COUNTUNIQUE(A2:A)` обязано дать 0.

**`IFERROR` прячет причину пустоты** (позиция AH-22 очереди). Формула вида `IFERROR(VLOOKUP(ключ;IMPORTRANGE("<ID книги>";"Лист!A2:E");5;FALSE);"")` показывает пустую ячейку без ошибки в двух случаях, которые на глаз неотличимы:
1. книге не выдан доступ к другой книге: `IMPORTRANGE` отдаёт ошибку «нужно разрешение», `IFERROR` её глотает, и кнопка «Разрешить доступ» не появляется никогда;
2. ключ в одной книге число, в другой текст (формат `@`): `VLOOKUP` не находит совпадения.
Порядок: доступ выдавать отдельной ячейкой без `IFERROR` — `=IMPORTRANGE("<ID>";"Лист!A1")`, нажать «Разрешить доступ», затем очистить ячейку; ключи с обеих сторон приводить к тексту через `TO_TEXT`; после вставки формулы читать результат через `gsheets-read`, а не довольствоваться отсутствием ошибки. Случай: Price Master!Artikel, колонка X, 2026-10-04 — первая версия пуста во всех строках (gsheets-read 74831), после выдачи доступа и `TO_TEXT` заполнена (gsheets-read 74834).

### 3.10. Склейка цепочек IMPORTRANGE — по ключу, не по номеру строки

Две цепочки `IMPORTRANGE`, поставленные рядом, совпадают построчно только до первого расхождения в числе или порядке строк. Склейка по позиции дала артикулу 1000 чужой номер Liqui Moly — 1015 вместо 1340 (прогон 76252, 2026-10-06; `meta/PRODUCT_DATA_HIERARCHY.md`, раздел 4). Соседние данные из другой цепочки подтягивать по ключу (артикулу) — `VLOOKUP`/`XLOOKUP` с ключом из правил §3.9, — а не ставить рядом.

`FILTER`, которому не хватает строк листа, отдаёт ошибку «Result was not automatically expanded, please insert more rows». Обёртка `IFERROR` превращает её в пустоту: себестоимость становится нулём, прибыль завышается молча (`projects/wb-ue/STATE.md`, пункт (C)). `IFERROR` вокруг `FILTER` оставлять только с проверкой числа строк: сколько строк в источнике прошло условие и сколько вывелось — в отчёт или в контрольную ячейку.

### 3.11. Сравнение текста: регистр и пустая строка

- `SUMIFS` и `COUNTIFS` регистр не различают («FBS» = «Fbs»); `QUERY` и сравнение `=` различают. Колонка с двумя написаниями одного значения даёт разные итоги в разных формулах (`sales_raw_operations`, колонка H: старая цепочка писала «FBS», новая с 18.08 — «Fbs», `labs/ozon-ue/t-raw-book-hygiene.md`). Лечение — привести написание к одному в источнике, а не подбирать функцию под данные.
- `COUNTIFS(диапазон;"<>")` считает непустой и пустую строку `""`, которую вернула формула. Пустые по смыслу ячейки, заполненные формулой, считать через `SUMPRODUCT(LEN(диапазон)>0)`.
