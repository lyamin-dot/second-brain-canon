# avtopilot

Автопилот: Андрей один раз согласует контракт запуска, дальше сессия-диспетчер ведёт работу до итогового отчёта без него. Здесь — кто держит работу, когда Андрея нет рядом, и где она обязана остановиться. Чужую механику Skill не повторяет: ревизия — `denken`, чтение и запись репозитория — `second-brain-git`, форма вопроса посреднику — `second-brain-engineer`.

## Стоп-правила

### Ворота и контракт
- Ворота проходятся по порядку; ворота не пройдены — дальше не идти.
- Критерий приёмки без наблюдаемого объекта — Ворота 1 не пройдены.
- Список ручных действий Андрея не собирать по ходу: он весь выдаётся в начале, в Воротах 1.
- Контракт записывается в канон до исполнения — и тогда, когда согласие дано заранее поручением «действуй максимально автономно».
- Молчание согласием на контракт не считается.

### Исполнение
- Наряды в формате `naryad` внутри автопилота не печатать: пакет контракта — не наряд. Вне автономного режима правила `naryad` не меняются.
- Лёгкий шаг (одно чтение файла, одно число, одна запись) субагенту не отдавать — его делает диспетчер.
- Работу, которой нужен второй уровень раздачи, субагенту не поручать — её раздаёт диспетчер.
- Читающее или тестовое задание не выдавать субагенту в сессии, где `git push --dry-run` прошёл, — кроме трёх способов из раздела «Ворота 4. Исполнение — Андрея нет», «Задание субагенту».
- Отключение push из клона у субагента инструменты записи GitHub не отнимает: их ловит только сверка `git ls-remote origin main`.
- Запись субагента, найденная сверкой `git ls-remote origin main` и `git status`, — стоп и откат.
- В канон пишет только диспетчер.
- Правила, которые диспетчер исполняет сам, он не читает через посредника.
- Перед правкой воркфлоу n8n — перечитать `updatedAt` и сверить с прочитанным в начале; расхождение — стоп.
- Запланированную задачу со свежей сессией без режима одобрения auto носителем автопилота не делать.
- Запланированной задаче со свежей сессией не поручать правку воркфлоу n8n, запуск субагентов, отправку сообщения Андрею и запись во внешние системы (кабинеты маркетплейсов).
- Массовую механическую работу не делать моделью — только скриптом.

### Приёмка
- Отчёты исполнителей и рассуждения диспетчера приёмщику не передавать.
- Вопросы приёмки не составляет исполнитель.
- Находку субагента сверх вопроса не писать в канон как факт, пока диспетчер не проверил её по объекту.
- Критерий приёмки не смягчать.
- Проверку STATE.md после прогона не откладывать в отдельную задачу — тем же прогоном.
- В итоговом отчёте шаги не пересказывать.

### Стоп-список — где работа останавливается сама
Остановка — сообщение Андрею с тем, на чём встало, и с подготовленным решением; тихое ожидание остановкой не считается.
1. Нужно действие из списка ручных действий Андрея, а он его не сделал.
2. Нужно необратимое решение, которое разумно принять в обе стороны.
3. Меняется цель или предмет работы. Признак: делается уже не то, что записано целью в контракте, и цель приходится переопределять задним числом.
4. Правка нужна вне списка разрешённых.
5. Два круга правок без сходимости (Skill `denken`, раздел «8. Стоп-линия»).
6. Жёсткий барьер: политика, закон, ограничение платформы (Skill `denken`, раздел «4. Э0 — Карта барьеров и вердикт решаемости»).
7. Время последнего изменения воркфлоу (`updatedAt`) разошлось с прочитанным в начале.
8. Критерий приёмки не выполнен.

Находка вне рамки контракта работу не прерывает (раздел «Остановка и находки»).

### Чего этот Skill не делает
- Не заводит мониторов, сигналов живости и журналов наблюдения за автопилотом.
- Не меняет `naryad` вне автономного режима.
- Не разрешает правку Skill, мастер-промпта, удаление данных или правку воркфлоу без контракта, где они названы.
- Не считает ответ субагента записью в канон: в канон идёт то, что диспетчер прочитал сам; вердикт приёмщика входит в канон, когда диспетчер сам прочитал адрес доказательства, который приёмщик назвал (одна строка файла, одно поле ответа инструмента), — без этого он гипотеза (Skill `second-brain-engineer`, раздел «Р21. Чтение через посредника»).

## Как делать

### Пять ворот
Работа проходит ворота по порядку: 1 — разговор, 2 — ревизия, 3 — контракт запуска, 4 — исполнение, 5 — приёмка и отчёт.

### Ворота 1. Разговор — Андрей здесь
Сессия добивается четырёх вещей, коротко и без лишнего контекста:
1. **Квитанция рамки.** Цели Андрея отдельно, его предположения о способе отдельно, по каждому предположению — «оставляю» или «предлагаю снять, потому что» (Skill `second-brain-engineer`, раздел «Р19. Метод проектирования», пункт 1).
2. **Критерий приёмки — наблюдаемый объект.** Не «проверено», а, например, «по каждому из восьми пунктов вердикт с адресом доказательства».
3. **Все ручные действия Андрея — одним списком сразу.** Это действия, которые сессия сделать не может: создать Claude Project, создать ключ доступа (credential) в редакторе n8n — привязывает его к узлам сама сессия, перезалить Skill, вставить мастер-промпт, открыть папку сервисному аккаунту.
4. **Стоп-список** (раздел «Стоп-список — где работа останавливается сама») дополняется особыми стопами этой работы.

### Ворота 2. Ревизия
1. Skill `denken`, уровень Р2; при необратимой или разрушительной операции — Р3. Ревизия идёт по написанному плану.
2. Отдельный пункт ревизии для автопилота: какие шаги действительно независимы. Все шаги строго последовательны — это говорится вслух до запуска: параллельности не будет.

### Ворота 3. Контракт запуска — одно «да»
Контракт — один текст, записанный в канон до исполнения:
- repo-проект — раздел «Контракт автопилота» в `PLAN.md` проекта;
- лаборатория — сам файл задачи `t-<имя>.md`;
- записать нельзя — блоком в чате, и тогда запись контракта — первый шаг исполнения.

Поля контракта: цель; критерий приёмки; пакеты работы (у каждого — объекты, вопрос, ожидаемый результат-объект, класс модели); разрешённые правки списком; особые стопы.

Список разрешённых правок и есть пакет разрешения на правки воркфлоу n8n (Skill `second-brain-engineer`, раздел «Р10. Воркфлоу n8n — полномочия», исключение 3): правка из списка исполняется без повторного «да», правка вне списка — по общему правилу. Пакет, заданный классом объектов, получает в контракте границу — признак, которого нет у чужих объектов (приставка проекта в имени плюс строка в описи пакета); признак проверяется до записи контракта.

Согласие — ответ Андрея на контракт: «да», «действуй», «запускай». Заранее данное поручение «действуй максимально автономно» («прими решение сам») тоже согласие на контракт, пока Андрей его не отозвал; контракт при этом всё равно записывается в канон до исполнения, и его стоп-список действует целиком.

### Ворота 4. Исполнение — Андрея нет
**Шина — сессия-диспетчер, а не Андрей.** В автономном режиме правило Skill `naryad` «Андрей — шина, роли между собой не общаются» не действует: диспетчер сам раздаёт работу субагентам и сам принимает их ответы. Обратная оговорка стоит в самом `naryad`, раздел «Роли».

**Когда раздавать субагенту.**
- субагенту отдаётся только тяжёлое чтение, которое нельзя сузить до попадания в контекст: полный граф воркфлоу, длинная выдача внешнего API, большая пачка файлов;
- лёгкий шаг (одно чтение файла, одно число, одна запись) диспетчер делает сам;
- объекты группируются так, чтобы один старт субагента обслуживал два-три объекта;
- независимые пакеты запускаются одним сообщением — тогда они идут параллельно;
- работа, которой нужен второй уровень раздачи, раздаётся диспетчером: субагент своих субагентов не запускает.

**Задание субагенту** — вопрос, а не файл, по форме посредника (Skill `second-brain-engineer`, раздел «Р21. Чтение через посредника»: вопрос без ожидаемого ответа, адрес доказательства при каждом факте, NOT_FOUND со списком мест, вопросы пакетом). Сверх неё:
- по умолчанию только чтение, и это написано в задании словами «READ-ONLY, ничего не менять»;
- в сессии, где `git push --dry-run` прошёл (Skill `second-brain-git`, раздел «Push: проверка и открытие»), читающее или тестовое задание даётся одним из трёх способов:
  1. в сессии без открытого push;
  2. субагенту, у типа которого нет ни командной строки, ни инструментов записи GitHub (состав инструментов типа — в списке типов агентов сессии);
  3. с защитой: на время работы субагентов отправка из клона отключена (`git remote set-url --push origin DISABLED`, после работы адрес возвращается); материалы субагенту даны копией вне клона; после каждого пакета диспетчер сверяет `git ls-remote origin main` и `git status` клона; запись субагента — стоп и откат;
- у вопроса закрытый набор вердиктов (например, ЖИВ / ИСПРАВЛЕН / ИЗМЕНЁН);
- задание пишется на английском и компактно.

**Пишет в канон только диспетчер.** Правила записи `second-brain-git` и другие правила, которые диспетчер исполняет сам, он читает сам.

**Перед правкой воркфлоу n8n** диспетчер перечитывает время последнего изменения воркфлоу (`updatedAt`) и сверяет его с прочитанным в начале. Расхождение — стоп (стоп-список, пункт 7).

**Долгое ожидание** (прогон воркфлоу на десятки минут или работа, которую нужно продолжить на следующий день) — два носителя:
- отложенное сообщение самому себе — возврат в ту же сессию. Берётся, когда продолжать должна та же сессия, с её контекстом;
- запланированная задача со свежей сессией. Её задание пишется самостоятельным текстом: какие объекты прочитать, что проверить, куда записать итог; всё остальное она берёт из канона, а не из чата. Режим одобрения задачи называет ответ на её создание: не auto — такую задачу носителем не делать.

**Массовая механическая работа** — скриптом, а не моделью (Skill `second-brain-engineer`, раздел «17. Массовую механическую работу делает скрипт, а не модель»; для файлов репозитория — Skill `second-brain-git`, разделы «Правило происхождения текста» и «Маршрут доставки в main»).

### Ворота 5. Приёмка и отчёт
**Приёмку делает отдельный субагент сильного класса, который работу не делал.** Он получает утверждения в виде списка проверяемых фраз и задачу их опровергнуть по объекту. Отчёты исполнителей и рассуждения диспетчера ему не передаются.

**Кто составляет утверждения.** Вопросы приёмки составляет не исполнитель: Андрей или отдельный субагент, не видевший построения. Диспетчер, который сам исполнял, передаёт составителю цель и объект, но не свои вопросы и отчёты. Утверждения документа о коде (паспорт, описание) приёмщик сверяет с самим кодом. Исправления по находке приёмщика проверяет повторно приёмщик (Skill `second-brain-engineer`, раздел «Проверка, которая не может соврать», пункты г и д).

**Находки любого субагента сверх вопроса — гипотезы.** Они идут в канон словами «Гипотеза (не проверена):», пока диспетчер не проверил их по объекту. Признак: субагент называет причину отказа воркфлоу, а сохранённый прогон упал раньше, на другом узле, — по прогону причина не проверена.

**Критерий приёмки не смягчается** (Skill `second-brain-engineer`, раздел «15. Критерий приёмки не подменяют задним числом»). Не выполнен — итог «не выполнено, вот почему».

**STATE.md после прогона.** Перед итоговым отчётом диспетчер запускает `python3 meta/scripts/state_split.py check` на STATE.md каждого проекта, в который прогон писал, и переносит отработавшее скриптом `meta/scripts/state_apply.py` (контракт `meta/CONTRACT_state-content.md`) — тем же прогоном.

**Итог.** Диспетчер пишет результат в канон, проверяет запись обратным чтением и выдаёт Андрею один отчёт: проблема, причина, что сделано, что сделать ему.

### Остановка и находки
1. Сработал пункт стоп-списка — сообщение Андрею: на чём встало и подготовленное решение.
2. Находка вне рамки контракта работу не прерывает. Она идёт захватом по правилу мастер-промпта проекта (Skill `second-brain-engineer`, раздел «Р6. Захват»): объектный блокер — сразу, кандидат и мелочь — на !save.

## Адреса и ловушки
- Субагент наследует от сессии право отправки в main: «READ-ONLY» в задании держится только словами — после каждого пакета сверяй `git ls-remote origin main` и `git status` клона.
- Правка воркфлоу в n8n молча перезаписывает граф без проверки версии, стирая правку параллельной сессии — сверяй `updatedAt` перед правкой.
- Запланированная задача без режима одобрения auto молча останавливается на первом действии, которое требует одобрения, — проверяй режим в ответе на создание задачи.
- Скрипты проверки STATE.md: `meta/scripts/state_split.py`, `meta/scripts/state_apply.py`; контракт — `meta/CONTRACT_state-content.md`.

## Куда писать результат
- Контракт: repo-проект — раздел «Контракт автопилота» в `PLAN.md`; лаборатория — файл задачи `t-<имя>.md`; иначе — блоком в чате и первым шагом исполнения в канон.
- Результат прогона — в канон, только диспетчером, с проверкой обратным чтением; непроверенные находки — словами «Гипотеза (не проверена):».
- Андрею — один итоговый отчёт: проблема, причина, что сделано, что сделать ему.
