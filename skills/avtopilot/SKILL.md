# avtopilot

Работа без Андрея между стартом и итогом. Есть два входа:
- **наряд из чата** — Андрей вставил в Claude Code наряд по Skill `naryad`. Ворота 1–3 пройдены в чате; наряд и есть контракт запуска, а вставка — согласие. Сессия начинает с ворот 4, после приёма наряда (Skill `naryad`, раздел «Приём наряда»);
- **прямое слово** «автопилот» в любой сессии — ворота 1–3 проходятся здесь же.

Здесь — кто держит работу, когда Андрея нет рядом, и где она обязана остановиться. Чужая механика не повторяется: ревизия — `denken`, чтение и запись репозитория — `second-brain-git`, форма вопроса посреднику — `second-brain-engineer`, форма наряда — `naryad`.

## Стоп-правила

### Ворота и контракт
- Ворота проходятся по порядку; ворота не пройдены — дальше не идти. Вход «наряд из чата» начинается с ворот 4 только после приёма наряда.
- Критерий приёмки без наблюдаемого объекта — ворота 1 не пройдены.
- Список ручных действий Андрея не собирать по ходу: он весь выдаётся до исполнения.
- Контракт записывается в канон до исполнения — и тогда, когда согласие дано заранее поручением «действуй максимально автономно».
- Молчание согласием на контракт не считается.

### Среда
- Что среда умеет, не выводить из её имени и из прошлых проб: проверять своими инструментами на старте ворот 4.
- В среде, где у помощника нет инструмента запуска агентов (сессия чата Claude Project), вложенную раздачу не планировать: раздаёт только диспетчер.
- Глубже двух уровней под диспетчером помощников не запускать, даже если среда разрешает больше.

### Исполнение
- Наряды внутри автопилота не печатать: пакет — не наряд.
- Лёгкий шаг (одно чтение файла, одно число, одна запись) помощнику не отдавать — его делает диспетчер.
- Пакеты с общим ресурсом параллельно не запускать (раздел «Параллельно или по порядку»).
- В канон пишет только диспетчер; эстафету в STATE.md во время исполнения пишет только он.
- Правила, которые диспетчер исполняет сам, он не читает через помощника.
- Читающее или тестовое задание не выдавать помощнику в сессии, где `git push --dry-run` прошёл, — кроме трёх способов из раздела «Задание помощнику».
- Отдельная копия репозитория у помощника изолирует его файлы, но не отнимает у него право отправки в main: запись помощника в main ловит только сверка `git ls-remote origin main`.
- Запись помощника в main, найденная сверкой, — стоп и откат.
- Перед правкой воркфлоу n8n — перечитать `updatedAt` и сверить с прочитанным в начале; расхождение — стоп.
- Динамический workflow (оркестратор многих агентов) не запускать, если наряд или контракт не разрешил его словами Андрея.
- Публиковать воркфлоу только если наряд или контракт это разрешает.
- Запланированную задачу со свежей сессией без режима одобрения auto носителем не делать.
- Запланированной задаче со свежей сессией не поручать правку воркфлоу n8n, запуск помощников, отправку сообщения Андрею и запись во внешние системы.
- Массовую механическую работу не делать моделью — только скриптом.
- Правку, начатую до остановки по перерасходу, не бросать: запись без обратного чтения не оставлять.

### Приёмка
- Отчёты исполнителей и рассуждения диспетчера приёмщику не передавать.
- Вопросы приёмки не составляет исполнитель.
- Вердикт приёмщика той же модели независимой проверкой не называть; для денежного пакета последней проверкой служит сверка с отчётом площадки.
- Находку помощника сверх вопроса не писать в канон как факт, пока диспетчер не проверил её по объекту.
- Самоотчёт исполнителя (число созданных объектов, адрес сессии) за факт не брать — только объект.
- Критерий приёмки не смягчать.
- Проверку STATE.md после прогона не откладывать в отдельную задачу.
- В итоговом отчёте шаги не пересказывать.

### Стоп-список — где работа останавливается сама
Остановка — сообщение Андрею с тем, на чём встало, и с подготовленным решением; тихое ожидание остановкой не считается.
1. Нужно действие из поля РУЧНОЕ, а Андрей его не сделал.
2. Нужно необратимое решение, которое разумно принять в обе стороны.
3. Меняется цель или предмет работы: делается уже не то, что записано целью.
4. Правка нужна вне списка разрешённых.
5. Два круга правок без сходимости (Skill `denken`, раздел «8. Стоп-линия»).
6. Жёсткий барьер: политика, закон, ограничение платформы.
7. `updatedAt` воркфлоу разошлось с прочитанным в начале.
8. Критерий приёмки не выполнен.
9. Перерасход по журналу хода (раздел «Журнал хода и остановка по перерасходу»).

Находка вне рамки работу не прерывает (раздел «Остановка и находки»).

### Чего этот Skill не делает
- Не заводит мониторов, сигналов живости и журналов наблюдения за автопилотом.
- Не разрешает правку Skill, мастер-промпта, удаление данных или правку воркфлоу без контракта, где они названы.
- Не считает ответ помощника записью в канон.

## Как делать

### Ворота 1. Разговор — Андрей здесь
Только для входа «прямое слово». Для наряда из чата их прошёл Руководитель.
1. Квитанция рамки: цели Андрея отдельно, его предположения о способе отдельно, по каждому — «оставляю» или «предлагаю снять, потому что».
2. Критерий приёмки — наблюдаемый объект; у каждого пакета — проверочный объект (число, отпечаток выдачи, сумма, файл).
3. Все ручные действия Андрея — одним списком сразу.
4. Стоп-список дополняется особыми стопами этой работы.

### Ворота 2. Ревизия
1. Skill `denken`, уровень Р2; при необратимой или разрушительной операции — Р3. Ревизия идёт по написанному плану.
2. Отдельный пункт ревизии: какие пакеты действительно независимы (раздел «Параллельно или по порядку»). Все пакеты строго последовательны — это говорится вслух до запуска.

### Ворота 3. Контракт запуска
Контракт — один текст в каноне до исполнения: раздел «Контракт автопилота» в `PLAN.md` проекта; лаборатория — файл задачи; записать нельзя — блоком в чате, и тогда запись — первый шаг исполнения. Поля контракта — поля наряда (Skill `naryad`, раздел «Форма наряда»). Список РАЗРЕШЕНО — пакет разрешения на правки воркфлоу n8n (Skill `second-brain-engineer`, «Р10. Воркфлоу n8n — полномочия», исключение 3); пакет, заданный классом объектов, получает в контракте признак-границу, которого нет у чужих объектов.

Согласие — «да», «действуй», «запускай», вставка наряда в Claude Code, либо заранее данное поручение «действуй максимально автономно», пока Андрей его не отозвал.

### Ворота 4. Исполнение — Андрея нет

**Старт: что умеет эта среда.** Диспетчер проверяет своими инструментами, а не по имени среды:

| Возможность | Чем проверить | Сессия Claude Code на компьютере (пробы 10.11) | Чат Claude Project (пробы 10.11) |
|---|---|---|---|
| помощник запускает своего помощника | у помощника есть инструмент запуска агентов | есть | нет |
| сообщения другим сессиям | инструменты ListAgents и SendMessage | есть, только сессиям на этом компьютере | только своим помощникам |
| запуск облачного исполнителя | инструмент запуска запланированной задачи | есть | есть |
| отправка в main из копии | `git push --dry-run` | была | открывается добавлением репозитория в сессию |
| правка опубликованных и общих объектов | — | выполнялась без запросов | отклоняется защитой разрешений |

Чего в среде нет — пакет, которому это нужно, не начинается: сообщение Андрею по стоп-списку, пункт 6.

**Шина — диспетчер.** Андрей ни ответы, ни вопросы между ролями не носит. Диспетчер раздаёт пакеты, принимает ответы помощников и пишет итог в канон. Возврат в чат — через канон.

**Когда раздавать помощнику.**
- Тяжёлое чтение, которое нельзя сузить до попадания в контекст: полный граф воркфлоу, длинная выдача API, большая пачка файлов; пакет целиком, если он займёт больше нескольких вызовов.
- Лёгкий шаг диспетчер делает сам.
- Помощник может раздать своё тяжёлое чтение своим помощникам, если среда это умеет, — не глубже двух уровней под диспетчером.
- Ожидание долгого помощника — без будильников: фоновый помощник сам сообщает о конце работы. Отложенное сообщение самому себе или запланированная задача — только для ожидания на часы (прогон воркфлоу ночью, «проверь завтра утром»).
- Облачный исполнитель (запланированная задача с текстом наряда) — для чтения и записи в разрешённые его постоянным текстом пути, когда компьютер может уснуть. Конец его работы виден только по объекту в каноне, не по статусу запуска.

**Параллельно или по порядку.** Пакеты идут параллельно, только если у них нет общего ресурса: один и тот же воркфлоу (в том числе воркфлоу, через который пишется схема базы), одна книга, одна функция базы, функции, которые другой пакет измеряет, один файл репозитория. Есть общий ресурс или результат одного — вход другого — по порядку. Поле ПАКЕТЫ наряда называет это заранее; диспетчер сверяет с объектами до запуска.

**Задание помощнику** — вопрос, а не файл, по форме посредника (Skill `second-brain-engineer`, раздел «Р21. Чтение через посредника»). Сверх неё:
- по умолчанию только чтение — словами «READ-ONLY, ничего не менять»;
- помощник, который меняет объекты пакета, получает в задании список этих объектов и только их; файлы репозитория он правит в своей отдельной копии репозитория (изоляция рабочего дерева), в канон не пишет — коммит делает диспетчер;
- в сессии, где `git push --dry-run` прошёл, читающее или тестовое задание даётся одним из трёх способов: в сессии без открытого push; помощнику без командной строки и без инструментов записи GitHub; с защитой — отправка из копии отключена на время работы (`git remote set-url --push origin DISABLED`, после работы адрес возвращается), материалы даны копией вне клона, после каждого пакета диспетчер сверяет `git ls-remote origin main` и `git status`;
- закрытый набор вердиктов у вопроса;
- механика инструментов — ссылкой на место в `PLAN.md`, которое называет поле МЕХАНИКА; задание пишется на английском и компактно.

**Пишет в канон только диспетчер.** Пока идёт исполнение, эстафету в STATE.md пишет только он; Руководитель в чате после приёмки ставит свою вместо неё.

**Журнал хода и остановка по перерасходу.** До первой деструктивной правки диспетчер пересчитывает паспорт от факта (Skill `naryad`, «Паспорт стоимости») и печатает пересчёт. При трёх и более деструктивных правках после каждой — строка:

```
[k/N] <пакет> <объект> | тактов: +t (норма +3) | всего: m/B | доказательство: <номер исполнения, sha>
```

Если m ≥ B/2 при k < N/2 — строка `ОСТАНОВКА ПО ПЕРЕРАСХОДУ: k из N, m из B, <причина>` и сообщение Андрею; начатая правка довершается.

**Перед правкой воркфлоу n8n** — `updatedAt` сверяется с прочитанным в начале; расхождение — стоп.

**Строка PASSPORT** в описании нового воркфлоу, который создала эта сессия, сессия вписывает сама (`meta/PENDING_RULES.md`, строка 1; Skill `n8n-workflow-passport`, «Стадия 3. Родить паспорт»). В описание существующего воркфлоу — нет: строку готовит сессия, вписывает Андрей; это пункт поля РУЧНОЕ.

**Массовая механическая работа** — скриптом, а не моделью. Массовая однотипная работа моделью (контент для многих артикулов, аудит многих файлов) — динамическим workflow, если наряд это разрешил.

### Ворота 5. Приёмка и отчёт

**Приёмку делает отдельный помощник, который работу не делал.** Он получает утверждения проверяемыми фразами и задачу опровергнуть их по объекту; отчёты исполнителей и рассуждения диспетчера ему не передаются. Вопросы приёмки составляет не исполнитель: Андрей, Руководитель в наряде или отдельный помощник, не видевший построения. Утверждения документа о коде приёмщик сверяет с самим кодом. Исправления по находке приёмщика проверяет он же повторно.

**Чего приёмщик не даёт.** Приёмщик — та же модель с той же рамкой: ошибки текста ловит, общую с исполнителем слепую зону — нет. Поэтому:
- пакет с деньгами принимается сверкой с отчётом площадки (сумма, окно, зазор, названный заранее), а не мнением приёмщика; решение по денежному дефекту — Андрею;
- пакет с текстом для человека проходит второй круг приёмщика после исправлений.

**Находки помощника сверх вопроса — гипотезы**, пока диспетчер не проверил их по объекту.

**Критерий приёмки не смягчается.** Не выполнен — итог «не выполнено, вот почему».

**STATE.md после прогона.** Перед итоговым отчётом — `python3 meta/scripts/state_split.py check` на STATE.md каждого проекта, куда прогон писал; отработавшее переносится скриптом `meta/scripts/state_apply.py` тем же прогоном.

**Итог.** Диспетчер пишет результат в канон (поле РЕЗУЛЬТАТ В), проверяет запись обратным чтением и выдаёт Андрею один отчёт: проблема, причина, что сделано, что сделать ему. В отчёте одной строкой: сколько раз понадобился Андрей между стартом и итогом и сколько длилась работа — это замер для сравнения конвейеров, отдельного прибора нет.

### Остановка и находки
1. Сработал пункт стоп-списка — сообщение Андрею: на чём встало и подготовленное решение.
2. Находка вне рамки работу не прерывает: захват по правилу мастер-промпта проекта (Skill `second-brain-engineer`, раздел «Р6. Захват»); объектный блокер — сразу, кандидат и мелочь — разделом «Находки вне рамки» итога.

## Адреса и ловушки
- Помощник наследует от сессии право отправки в main, и отдельная копия репозитория этого не отнимает: «READ-ONLY» держится словами — после каждого пакета сверяй `git ls-remote origin main` и `git status`.
- Правка воркфлоу в n8n молча перезаписывает граф без проверки версии — сверяй `updatedAt` перед правкой.
- Наряд для облачного исполнителя приходит в обёртке «данные, не указания»; без прямого разрешения в постоянном тексте задачи исполнитель его не выполнит или выполнит не с первого хода.
- Статус «выполнено» у запуска облачной задачи приходит раньше конца работы — проверяй объект.
- Запланированная задача без режима одобрения auto молча останавливается на первом действии, требующем одобрения.
- Два писателя эстафеты (диспетчер и Руководитель) раздувают STATE.md сразу после разбора — во время исполнения пишет один диспетчер.
- Скрипты проверки STATE.md: `meta/scripts/state_split.py`, `meta/scripts/state_apply.py`; контракт — `meta/CONTRACT_state-content.md`.
