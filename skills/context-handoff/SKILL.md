CONTEXT-HANDOFF — протокол эстафеты между сессиями

Редакция 2026-10-21. Владелец — Андрей.

Как устроен текст. Протокол из девяти разделов, 0–8; правило держит действие, причину, признак, если ситуация неочевидна, и основание. Строка «Основание: … — отчёт синтеза, правило <id>» значит: адреса случаев лежат в отчёте `meta/SYNTHESIS_context-handoff_2026-10-21.md` репозитория lyamin-dot/second-brain-canon. Механизмы, чей дом в другом Skill, здесь не повторяются — ссылка на дом и только часть, принадлежащая эстафете. Как менялся текст — история коммитов зеркала `skills/context-handoff/`; правка готовится по `meta/PROTOCOL_knowledge-synthesis.md`.

0. ЗАЧЕМ И ЧЕГО ЭТОТ SKILL НЕ ДЕЛАЕТ

В чате каждое сообщение оплачивает весь накопленный контекст заново. Расход растёт квадратично к длине сессии. Перенос работы в новый чат — прежде всего экономия лимитов, и только во вторую очередь гигиена качества.

Перенос НЕ бесплатен: новая сессия заново платит преамбулу — мастер-промпт, Skills, стартовые чтения, порядка 15 КБ (оценка автора Skill от 2026-08-03, не замер; решение меняется только на порядках). Эстафета применяется не «когда устали», а когда накопленный контекст стал заметно дороже новой преамбулы.

ГРАНИЦА ПРИМЕНИМОСТИ — читать первым. Этот Skill загружается только по явной команде. До первой команды в сессии его в контексте нет, и Claude ничего не отслеживает. Поэтому:
- Skill не даёт проактивных предупреждений «пора переносить». Это осознанная цена невидимости.
- Все оценки ниже выполняются в момент команды, ретроспективно.
- Если после команды «эстафета?» пользователь решил продолжить в этом же чате, Skill уже в контексте — и дальше Claude может добавлять одну строку статуса в конце ответа. До первой команды — нет.

СРЕДА. В claude.ai и Cowork нет /compact и /clear. Доступны ровно три исхода: ПРОДОЛЖАТЬ / ЭСТАФЕТА + новый чат / ВЫНЕСТИ в файл. Не предлагать компактизацию и очистку — этих механизмов здесь не существует.

КАНАЛ ПЕРЕНОСА — канон проекта, не буфер обмена: пользователь ничего не копирует. Носитель зависит от того, где идёт работа:

| Где идёт работа | Носитель эстафеты | Когда его читает новая сессия |
|---|---|---|
| проект с INDEX в Google Docs | блок ## ЭСТАФЕТА в Зоне А INDEX проекта | на старте, по мастер-промпту |
| проект в репозитории (папка projects/<имя>/) | первая строка раздела «Следующий шаг» в STATE.md проекта (раздел 8) | на старте, по мастер-промпту |
| лаборатория в репозитории (папка labs/<имя>/, в том числе SYS) | блок ## ЭСТАФЕТА в конце файла задачи t-<имя>.md, над которой шла работа, и пометка в строке этой задачи в INDEX.md (раздел 8) | при взятии этой задачи; на старте пометка в INDEX.md говорит, что блок есть |

1. КОМАНДЫ

| Команда | Действие |
|---|---|
| эстафета? | Только оценка по разделу 2. Вердикт по форме из 2.4. НЕ писать в носитель |
| эстафета | Стоп-линия → запись → верификация → «открывай новый чат» |
| эстафета в [ПРОЕКТ] | То же, в носитель указанного проекта |

Право решения — за пользователем. Claude оценивает и рекомендует; действует только по команде «эстафета». Единственное исключение — стоп-линия (раздел 4): она блокирует запись даже по прямой команде, до устранения блокера.

2. ОЦЕНКА: ДВЕ НЕЗАВИСИМЫЕ ШКАЛЫ

Шкалы измеряют разное и дают разные рекомендации. Считать обе, не смешивать.

2.1 Шкала СТОИМОСТЬ — сколько весит сессия

Оценивается всё, что вошло в контекст с начала сессии, а не только прочитанные файлы:
- документы, вставленные пользователем;
- прочитанные файлы и выхлопы инструментов;
- собственные развёрнутые ответы Claude;
- созданные в сессии артефакты.

Оценка грубая, в КБ, по порядку величины. Ориентир: экран плотного текста ≈ 3 КБ, крупная статья или выхлоп исследования ≈ 8–10 КБ, INDEX-файл — десятки КБ.

| Уровень | Объём сессии | Смысл |
|---|---|---|
| 🟢 | до ~30 КБ | Перенос убыточен: преамбула дороже накопленного |
| 🟡 | ~30–60 КБ | Перенос окупается, если фаза закрыта |
| 🔴 | свыше ~60 КБ | Перенос окупается заметно |

Пороги — эвристика, не закон: оценка автора Skill от 2026-08-03, не замер. Погрешность оценки в разы допустима: решение меняется только на порядках.

2.2 Шкала НАДЁЖНОСТЬ — можно ли доверять этой сессии

Считать только внешне наблюдаемые события. Собственное ощущение («кажется, я путаюсь») признаком НЕ является: сломанный прибор не измеряет свою поломку.

Признаки:
- перечитан файл, уже прочитанный в этой сессии;
- Claude противоречит решению, принятому ранее в этой же сессии;
- Claude спросил факт, который пользователь уже давал;
- пользователь сказал «мы это уже обсуждали» / «я тебе говорил»;
- две итерации без нового проверяемого результата.

| Уровень | Условие |
|---|---|
| 🟢 | признаков нет |
| 🟡 | один признак |
| 🔴 | два и более признака |

При 🟡 и выше по НАДЁЖНОСТИ — сначала re-anchor, до любой рекомендации. Re-anchor: вслух повторить ЦЕЛЬ, действующие ЗАПРЕТЫ и СЛЕДУЮЩИЙ ШАГ. Если воспроизвести не удалось или пользователь поправил — деградация подтверждена внешне. Если воспроизвелось точно — признак был ложным, уровень снижается.

2.3 Совмещение шкал

| СТОИМОСТЬ | НАДЁЖНОСТЬ | Рекомендация |
|---|---|---|
| 🟢 | 🟢 | ПРОДОЛЖАТЬ |
| 🟢 | 🔴 | ЭСТАФЕТА — контекст мешает, хотя и дёшев |
| 🟡 | 🟢/🟡 | ЭСТАФЕТА, если фаза закрыта; иначе — закрыть фазу |
| 🔴 | любая | ЭСТАФЕТА, если фаза закрыта; иначе — закрыть фазу |

«Фаза закрыта» = завершён шаг обслуживания, закрыта задача либо готов артефакт, и нет незавершённой записи.

Правило незакрытой фазы (перевешивает уровни шкал): посреди операции эстафета не рекомендуется. Рекомендуется завершить текущую фазу и после этого перенести. Формулировать именно так, не как «продолжаем».

Приоритет при конфликте: сохранность данных > точность работы > экономия контекста. Экономия никогда не оправдывает разрыв незавершённой операции.

2.4 Форма вердикта по команде «эстафета?»

Ровно четыре строки, без развёрнутых рассуждений:

```
СТОИМОСТЬ: 🟡 ~45 КБ
НАДЁЖНОСТЬ: 🟢 признаков нет
ФАЗА: закрыта / не закрыта — [что именно висит]
ВЕРДИКТ: ПРОДОЛЖАТЬ | ЭСТАФЕТА | ЗАКРЫТЬ ФАЗУ, ЗАТЕМ ЭСТАФЕТА
```

3. ФОРМАТ БЛОКА

Пишется ОДНОЙ строкой, поля разделены « | », перевода строки внутри нет. Лимит 1 КБ.

```
## ЭСТАФЕТА | СТАТУС: active | ОБНОВЛЕНО: YYYY-MM-DD HH:MM | ЧАТ: [короткая метка сессии] | ЦЕЛЬ: одна фраза — что должно быть достигнуто | СОСТОЯНИЕ: где остановились | ЗАПРЕТЫ: что нельзя делать в этой задаче (must-not, контракты, форматы) | ДОБЫТО [Ф/Г]: факты из дорогих чтений — ID, значения, результаты проверок | РЕШЕНО: решения сессии, ещё не попавшие в CORE/CHANGELOG | ТУПИКИ: что проверено и НЕ сработало — с причиной | СЛЕДУЮЩИЙ ШАГ: один исполнимый шаг, без «продолжить работу» | ЯКОРЯ: ID файлов, воркфлоу, номера строк
```

В ДОБЫТО каждый пункт несёт метку: Ф = проверено чтением, Г = гипотеза. Метки соответствуют меткам происхождения `second-brain-engineer`, раздел Р15, грубо: Ф — прочитано в этой сессии; Г — всё, что не прочитано (вспомнено, выведено, предположено).

Почему одна строка: инструменты записи в Google Docs заменяют только однострочный якорь (Skill `google-drive-docs`, `references/docs-write.md`, разделы 3.2 и 3.6), поэтому многострочный блок заменой по заголовку не перезаписать — заменится строка заголовка, тело старого блока останется. В файле репозитория правка фрагмента меняет одну строку так же чисто, поэтому форма одна для всех носителей. Почему 1 КБ: строка блока целиком служит якорем следующей замены и идёт телом вызова, а граница текста телом вызова — 1–2 КБ (там же, раздел 3.0). Основание: решение Андрея 2026-10-21 — отчёт синтеза, правило CH.форма.

Все поля обязательны. Пустое пишется как «нет», не удаляется: отсутствие поля неотличимо от забытого поля.

Порядок при превышении 1 КБ — резать снизу вверх в этом порядке:
1. ЯКОРЯ — сокращать до тех, что нужны для СЛЕДУЮЩЕГО ШАГА;
2. ТУПИКИ — оставить только последний;
3. ДОБЫТО — оставить только пункты, нужные для СЛЕДУЮЩЕГО ШАГА.

Не режутся никогда: ЦЕЛЬ, ЗАПРЕТЫ, РЕШЕНО, СЛЕДУЮЩИЙ ШАГ. Почему: при деградации многоходовых диалогов первыми теряются именно инварианты — обязательства, запреты и прошлые решения, а не общие идеи. Основание: исследования деградации многоходовых диалогов, на которые опирался автор Skill, — случай без адреса (отчёт синтеза, правило CH.инварианты).

Если после реза не влезает — содержимое переросло эстафету и должно жить в каноне проекта как задача. Сказать об этом пользователю.

4. СТОП-ЛИНИЯ

Запись эстафеты ЗАПРЕЩЕНА, пока верно любое:
- выполнена деструктивная запись (replace, overwrite) без обратного чтения;
- ожидается результат воркфлоу;
- есть незаписанные [ЗАХВАЧЕНО] — захваты записываются до эстафеты (`second-brain-engineer`, раздел Р6 и команда !save);
- открыта операция, разрыв которой оставит систему в промежуточном состоянии.

Порядок жёсткий: сначала закрыть стоп-линию, потом эстафета. Разорванная сессия посреди записи — тот класс потери данных, против которого построена вся система.

Стоп-линия ≠ незакрытая фаза. Стоп-линия запрещает запись. Незакрытая фаза меняет рекомендацию, но по прямой команде запись выполняется.

5. ПРОТОКОЛ ЗАПИСИ

Протокол один для всех носителей; шаги 2 и 5 для проекта в репозитории и для лаборатории читаются по разделу 8.

1. Проверить стоп-линию. Не прошла — назвать блокер и остановиться.
2. Прочитать текущий носитель: Зону А INDEX проекта.
3. Проверка конфликта. Если блок ## ЭСТАФЕТА уже есть и поле ЧАТ не совпадает с текущей сессией — НЕ перезаписывать. Показать пользователю существующий блок и спросить. Независимо от давности. Почему: одновременная работа в нескольких проектах — норма, и цена лишнего вопроса ничтожна против цены затёртой чужой эстафеты.
4. Собрать блок по разделу 3. Проверить объём, при необходимости резать по заданному порядку.
5. Записать заменой, не дозаписью: эстафета всегда одна, последняя.
   - Якорь замены — ВСЯ текущая строка блока, начинающаяся с «## ЭСТАФЕТА», в точности как она прочитана на шаге 2, а не одни слова «## ЭСТАФЕТА». Почему: замена меняет только совпавший текст. Перед заменой проверить уникальность якоря (text.count).
   - Инструмент — gdocs-apply-from-file в режиме replace: новая строка блока — файлом-источником в папке, доступной сервисному аккаунту, старая — полем search (Skill `google-drive-docs`, `references/docs-write.md`, раздел 3.6).
   - Блока нет — тем же инструментом по якорю строки SENTINEL: якорь заменяется на «строка эстафеты + перевод строки + та же строка SENTINEL»; строка SENTINEL остаётся последней строкой Зоны А.
   - Блок старой многострочной формы, найденный в документе, — вопрос Андрею: его тело одной заменой не убрать.
   - gdocs-append для эстафеты не годится: он пишет только в конец документа, то есть в Зону Б (Skill `google-drive-docs`, `references/docs-write.md`, раздел 3.1).
6. Верифицировать обратным чтением. success: true подтверждением не является (`second-brain-engineer`, раздел Р15).
7. Сказать: «Эстафета записана в [ПРОЕКТ]. Открывай новый чат.»

6. ПОДХВАТ В НОВОЙ СЕССИИ

Отдельной команды не требуется: носитель читается по мастер-промпту — Зона А и STATE.md на старте, файл задачи лаборатории при взятии задачи (раздел 0, КАНАЛ ПЕРЕНОСА).

1. Проверка свежести. ОБНОВЛЕНО старше 7 дней либо СТАТУС: stale → объявить вслух: «Эстафета протухла, работаю с нуля». Данные из неё не использовать как факты. Почему: устаревшая эстафета опаснее отсутствующей — она выглядит как знание. Это частный случай правила об условии, записанном раньше (`second-brain-engineer`, раздел Р15, «Условие, записанное раньше»).
2. Проверка расшифровки. Первым сообщением назвать вслух ЦЕЛЬ, ЗАПРЕТЫ и СЛЕДУЮЩИЙ ШАГ — тремя строками. Почему: это внешняя валидация — пользователь сразу видит, если эстафета расшифрована неверно. Не пересказывать блок целиком.
3. Пункты с меткой [Г] — гипотезы. Не строить на них выводы без перепроверки.
4. Отработать СЛЕДУЮЩИЙ ШАГ, не переизобретать план.

Кто ставит stale: новая сессия — сразу после первого содержательного шага, если она отклонилась от СЛЕДУЮЩЕГО ШАГА или обнаружила, что состояние изменилось. Пользователь — командой «эстафета устарела». Автоматически по 7 дням статус не меняется: срок проверяется при чтении.

7. АНТИ-ПАТТЕРНЫ

- Раздувание. Эстафета > 1 КБ = второй INDEX. Резать по разделу 3.
- Протухание. Блок не обновлён после новых решений, но используется как живой.
- Ложная уверенность. Пункт без метки Ф/Г.
- Ссылки вместо фактов. «См. CORE §12» заставляет новую сессию перечитывать дорогой источник — экономии нет. Нести добытое значение, а не адрес.
- Свалка. Всё в одном уровне важности, инварианты не видны.
- Эстафета вместо канона. Задачи живут в каноне проекта как задачи (Зона А, STATE.md, файлы задач лаборатории); эстафета несёт только то, что нужно для продолжения этой работы.
- Экономия против сохранности. Перенос ради лимитов посреди незавершённой операции. Приоритет обратный.

8. ГРАНИЦЫ

- Skill не срабатывает сам и не читается по собственной инициативе.
- Skill не пишет в CORE и CHANGELOG. Эстафета — оперативный чекпоинт, не летопись.
- Эстафета живёт в каноне проекта, где идёт работа, — носитель по таблице раздела 0. SYS — лаборатория: эстафета работы над задачей SYS пишется по правилу лаборатории ниже; работа над проектом из папки projects/, которая ведётся в чате SYS, пишет эстафету в STATE.md этого проекта. Основание: решение Андрея 2026-10-21 — отчёт синтеза, правило CH.SYS.
- Skill не отменяет !save. Захваты записываются до эстафеты, не вместо неё (раздел 4).
- Skill не предлагает /compact и /clear — в claude.ai и Cowork их нет.

**Проект в репозитории** (папка projects/<имя>/; своего INDEX в Google Docs у него нет — `second-brain-git`, пункт 10.5): эстафета не пишется отдельным блоком по разделу 3. Роль СОСТОЯНИЯ и СЛЕДУЮЩЕГО ШАГА несёт первая строка раздела «Следующий шаг» в STATE.md проекта — команда «эстафета» для такого проекта означает обновить STATE.md по маршруту `second-brain-git`, пункт 10.3 (сдвинулось состояние → STATE.md), записью по пункту 10.4 и разделу 8 Skill `second-brain-git`. Стоп-линия (раздел 4) и протокол записи (раздел 5, шаги 1, 3, 4, 6, 7) действуют без изменений; шаг 2 читается как «прочитать STATE.md проекта», шаг 5 — как «записать по `second-brain-git`, пункт 10.4 и раздел 8 того Skill».

**Лаборатория в репозитории** (папка labs/<имя>/, `second-brain-git`, раздел 4б; в том числе labs/sys/): у неё нет ни Зоны А, ни STATE.md — только INDEX.md со строкой на задачу и файл t-<имя>.md на каждую задачу. Поэтому:
- Блок ## ЭСТАФЕТА пишется в конец файла той задачи, над которой шла работа; поля и лимит — раздел 3 без изменений.
- В строке этой задачи в INDEX.md ставится пометка «активная эстафета «<метка из поля ЧАТ>»». Почему: на старте лаборатории читается только INDEX.md, и без пометки новая сессия не узнает, у какой задачи есть блок, пока не откроет файлы задач.
- Обе записи — правкой фрагмента, файл целиком не переписывается. Почему: перезапись существующего файла целиком `second-brain-git` (пункт 4.5) разрешает только ради атомарности создания и закрытия задачи; перенабор файла моделью теряет строки молча. Блок есть — заменяется вся его строка целиком (якорь — строка, прочитанная на шаге 2); блока нет — последняя непустая строка файла заменяется ею же плюс переводом строки и блоком; если такая строка встречается в файле не один раз, якорем берутся две последние непустые строки (правка фрагмента принимает только текст, встречающийся в файле ровно один раз).
- Транспорт: в сессии, где прошла проба `git push --dry-run` (`second-brain-git`, пункт 9.1), обе правки уходят одним коммитом клоном прямо в main и проверяются чтением с origin/main после свежего fetch (`second-brain-git`, пункты 8.7 и 9.4; коммит, оставленный в ветке, доставкой не считается) — запись клоном там разрешена для текста, порождённого сессией, и снимает набор тела через вызов инструмента (пункт 8.2, абзац «Почему запрет текстом не держится»: второй путь — запись клоном в сессии, где прошёл `git push --dry-run`, решение Андрея 2026-10-20). Через Канал — Git Replace (`second-brain-git`, пункт 8.3) по очереди, не одновременно (пункт 8.10): сначала блок, потом пометка. Блок пишется по-русски, и у Git Replace с русским текстом есть известное слабое место — набор последовательностями \uXXXX; что с ним делать — `second-brain-git`, пункт 8.2. Почему такой порядок: обрыв между вызовами оставляет блок без пометки — его найдёт сессия, взявшая задачу; обратный обрыв оставил бы пометку, обещающую несуществующий блок.
- Конфликт записи — как в разделе 5, шаг 3: блок с другим полем ЧАТ не перезаписывать, показать и спросить. Блок старой многострочной формы в файле задачи — вопрос Андрею, как в Google Docs (раздел 5, шаг 5): заменой одной строки его тело не убрать.
- Протокол записи (раздел 5): шаг 2 читается как «прочитать файл задачи и её строку в INDEX.md», шаг 5 — как «записать правкой фрагмента по этому разделу». Стоп-линия (раздел 4), проверка свежести и проверка расшифровки (раздел 6) — без изменений.
- Новая сессия читает блок при взятии задачи, а не на старте лаборатории; пометка в INDEX.md говорит, что блок есть. Задача закрывается по `second-brain-git`, пункт 4б.6 — файл удаляется вместе с блоком, строка INDEX.md вместе с пометкой; отдельно снимать не нужно.
