# n8n-engineering-manual

Как сессия создаёт, правит, публикует, проверяет и диагностирует воркфлоу на инстансе n8n Андрея через MCP: что движок и инструменты теряют молча, в каком порядке писать и сверять, как строить запись во внешний кабинет. Адреса деталей инстанса — Skill `n8n-workflow-registry`; паспорта — Skill `n8n-workflow-passport`.

## Стоп-правила

### Доказательство и состояние
- Не прочитав файл, который «Что читать» называет для действия, действие не начинать.
- Состояние воркфлоу, записи и прогона не утверждать по отчёту инструмента о себе (ответ записи, статус `success`, код 200, `active:true`, текст предупреждения) — только по объекту воздействия (строка, документ, таблица) или по факту исполнения (`get_execution` реального прогона) и по числу прогонов узла записи.
- Правило «запись недостоверна, пока её не перечитали независимо» не пересматривать, пока не предъявлен наблюдённый случай, который оно не объясняет; закрытое повторно не перепроверять.
- `description` воркфлоу не принимать за его поведение; веб-сниппет, память сессии, вчерашний ID — не принимать за факт без свежего чтения.
- Факт об экземпляре (адрес, версия n8n, часовой пояс сервера, способ развёртывания) не брать из этого Skill или памяти — с экземпляра в момент использования: адрес и сервер — `registry/projects.md` (строка SERVER) и канон SERVER; часовой пояс сервера — поле tz снимка `registry/n8n-map.md` (значение `instance` — пояс сервера); версия — `get_instance_context` или окно About.
- Старые записи сессий о том, приходит ли поле `credentials` в `get_workflow_details`, признаком не считать — читать свежий ответ.
- «not found» от `get_execution` не записывать как «исполнение не видно», не проверив, что переданы оба параметра — `workflowId` и `executionId`.
- «В коде есть перечитывание результата» не выдавать за «я видел результат перечитывания».
- Подозрение «после записи слетели ключи» не принимать — искать другую причину.
- Место, где воркфлоу берёт параметр из таблицы, не искать по значению параметра — только по смыслу сравнения (какое поле с каким сравнивается).
- Семантику флага не выводить из имени ключа в JSON: только из интерфейса или из прогона; если имя ключа — единственный источник, писать «не знаю».
- Ручную правку в редакторе не проверять чтением JSON — только прогоном по объекту.
- Находку аудита о литерале ключа в узле не считать ни закрытой, ни текущей до проверки по самому узлу (поле `credentials` в `get_workflow_details` или редактор).
- «Вебхук защищён» не считать «воркфлоу защищён»: вызов из сессий Claude через `execute_workflow` аутентификацию вебхука и формы не проходит; закрытие одного входа не считать закрытием другого.
- Критерий приёмки задним числом не смягчать.

### Вызов воркфлоу из сессии
- Вебхук своего инстанса из сессии Claude не вызывать через curl или bash — только `n8n:execute_workflow` через MCP.
- `executionMode: "production"` не использовать — только `manual`.
- Имя узла-триггера не угадывать — брать из `get_workflow_details` или из сигнатуры в `registry/tools.md`.
- Описанию инструмента в клиенте Claude, если оно расходится с ошибкой сервера MCP о форме вызова, не верить — верить ошибке сервера.
- Незнакомый воркфлоу не вызывать, не проверив флаг `availableInMCP` через `get_workflow_details`.

### Запись и публикация воркфлоу
- Меняющий вызов (`create_workflow_from_code`, `update_workflow`, `publish_workflow`, `unpublish_workflow`) не делать, пока в чате не видно «да» Андрея на эту правку или записанного пакета разрешения; иначе сначала вопрос: «Воркфлоу [имя], узел [имя]. Планирую: [описание]. Подтверждаешь?».
- Просьбу Андрея изменить воркфлоу не считать «да» на конкретную правку.
- Привязку ключа к узлу (в том числе пропавшего) не перекладывать на владельца: сессия привязывает сама, `setNodeCredential`, участие владельца не нужно.
- Запись до согласования варианта не делать: сначала вариант, потом запись.
- Больше трёх затрагиваемых узлов за раз — только после подтверждения Андрея.
- Миграцию ключа у многих узлов сразу не делать.
- Запись не считать сделанной, пока сверка по объекту не показала, что изменилось ровно задуманное и ничего больше.
- Правку одного узла боевого воркфлоу не делать записью кодом целиком — только точечной операцией `update_workflow`.
- Узлы Switch и сам узел-вебхук после точечной правки не оставлять без сверки «после записи».
- Предложенную замену кода узла не принимать без дословного текущего кода и построчного сравнения старого и нового.
- Код Code-узла не править частичной заменой — только полной.
- Неизменяемые узлы при пересборке не перенабирать моделью — переносить скриптом из сохранённого JSON.
- Не писать в воркфлоу при открытой вкладке редактора этого воркфлоу.
- Подготовку правки (план, наряд), снятую с другого `versionId`, к правке не применять.
- Воркфлоу, у которого `versionId` не равен `activeVersionId`, не публиковать, не сравнив версии `get_workflow_versions_diff` (опубликованная → черновик); чужое различие не публиковать попутно — вопрос проекту-владельцу.
- Воркфлоу по расписанию с потерянной таймзоной не публиковать.
- Правку не закрывать, пока свежий `get_workflow_details` не показал `versionId` равным `activeVersionId`.
- Остановку воркфлоу не делать выключением триггера в черновике — только `unpublish_workflow`.
- Снятие с публикации не принимать по слову «деактивировал», в том числе от владельца, — только чтением `active:false`.
- Ненужный воркфлоу (зонд, пробный, разовый инструмент) не архивировать и не удалять — снимать с публикации; исключение — устаревшая версия инструмента, вытесненная новой: её можно архивировать.
- Пометки «временный — архивировать после снимка» в описаниях воркфлоу и журналах не исполнять.
- Воркфлоу, чьи падения — единственный сигнал о сломанном ключе или источнике, не снимать с публикации, пока не названо, по какому другому воркфлоу виден сбой этого ключа или источника; нового монитора ради этого не заводить.
- После публикации не делать автономных действий: ни publish, ни unpublish, ни update, ни archive, ни «запущу посмотреть» — проблему вынести, фикс предложить, ждать «да» на каждый шаг.
- Обрыв ответа создающего вызова (`create_workflow_from_code`, создание документа) не считать «не создано»: не повторять, пока `search_workflows` по имени не подтвердил отсутствие.
- Копию активного воркфлоу не оставлять активной: сразу проверить `active` и снять с публикации; то же — старую версию, оставшуюся активной рядом с новой.
- Воркфлоу с формой (Form Trigger) не публиковать с открытой формой: либо не публикуется (пишущий вовне — не публикуется вовсе), либо форма закрывается аутентификацией до публикации; форма — вход того же класса, что вебхук: открытая — только по прямому решению Андрея.

### Ключи и периметр
- Значение ключа не пропускать через чат, тело узла, константу Code-узла, файл репозитория — никогда, даже временно.
- Новый ключ не заводить молча: если `n8n-workflow-registry` ничего не говорит о нужном ключе — спросить Андрея.
- Ключ не выдавать шире нужного права: воркфлоу, который только читает, — ключ только на чтение.
- Право ключа не проверять в боевом режиме — проверять до него.
- Второй кабинет (другое юридическое лицо) не делать переключателем внутри существующего воркфлоу — только отдельным воркфлоу со своим ключом.
- Узел с ключом не переименовывать в переданном коде — только операцией `renameNode`.
- Узел без ключа не включать в боевую цепочку до привязки.
- Воркфлоу с webhook-триггером без `authentication: "headerAuth"` в коде триггера не создавать вовсе; открытый вебхук — только по прямому решению Андрея.
- Вебхук не закрывать общим ключом другого назначения — только отдельным ключом Header Auth под этот вебхук или группу.
- Проверку заголовка на узле-вебхуке не включать, пока вызывающий код не отправляет этот заголовок.
- Вебхук не публиковать с «No credentials required».
- Чек-лист перед публикацией не пропускать при любом текущем состоянии периметра.
- Первую запись сервисным аккаунтом в файл не делать, не проверив `get_file_permissions` (файл расшарен ему как Editor).
- HTTP-узел, вызывающий вебхук этого же инстанса, не адресовать по публичному домену — только `http://<имя-docker-сервиса>:<порт>/...`.
- Верный ключ узла не определять по документации — по живым соседям, которые бьют в тот же домен и имеют успешные прогоны.
- Поле Allowed HTTP Request Domains ключа Header Auth не оставлять «All» — при заведении и ротации сужать до домена сервиса.
- Ключ не ротировать без перебора всей базы n8n на его литерал (все текстовые и JSON-колонки всех таблиц, включая `workflow_history`).
- Ключ модели в параметрах узла не держать; для API модели (и эмбеддингов) — только credential.
- Векторы базы знаний не писать и не искать моделью эмбеддингов, отличной от модели, которой база проиндексирована.

### Поток, Code-узел, выражения
- В RAW-слое не фильтровать по типу операции; аналитика — только отдельным слоем поверх RAW; RAW-слои разных источников не объединять, сравнение между источниками — по Артикулу.
- Внутри цикла SplitInBatches не бросать `throw` на один элемент (в том числе на пустой ответ модели) — возвращать item со статусом ошибки и разбирать его отдельной ветвью.
- В Code-узле не ставить `catch`, который не передаёт ошибку дальше; вызов с ключом не делать из Code-узла — только отдельным узлом HTTP Request.
- На встроенном модуле Node (`crypto` и подобных) не строить без пробного прогона, показавшего, что модуль доступен.
- Ручной пробный прогон воркфлоу с памятью между прогонами (static data) не делать без предупреждения владельца; где повтор сообщения недопустим — не делать вовсе.
- `.first()` не ставить, если узел-источник по конструкции не гарантирует ровно один item за итерацию — тогда `.all()` с матчингом по ключу.
- Ответ модели не сопоставлять по id из ответа — по позиции (`orig = items[i]`), пока выход узла стоит к входу один к одному; после Merge, фильтра, Switch и любого узла, меняющего число или порядок элементов, — только по ключу объекта.
- Полную историю или HTML не материализовать в один item.
- С размножением потока ниже Code-узла в режиме `runOnceForAllItems` не бороться (он схлопывает поток в один item) — проверять участок от триггера до первой такой ноды.
- Цепочку из двух и более Execute Workflow подряд не оставлять без проверки, что именно саб-воркфлоу возвращает последним узлом.
- Неподключённый выход IF не оставлять терминалом без оформления: ложная ветка — в именованный NoOp, либо узел Filter с говорящим именем; Filter — только если отброшенным items некуда идти, ложной ветке нужна обработка — IF с подключёнными обоими выходами.
- Параметры воркфлоу не выносить в общую панель на все воркфлоу — держать в книге или листе того воркфлоу, который их читает.
- Статическое тело HTTP (Raw + `application/json`) в легаси-узлах не трогать.

### HTTP, пагинация, время
- `options.timeout` не оставлять пустым ни на одном узле HTTP Request.
- `retryOnFail` не ставить на запрос, меняющий внешнее состояние (публикация на маркетплейсе, ответ покупателю, запись в чужую таблицу).
- 429 по квоте не лечить `retryOnFail` и короткими паузами — только выход ошибки → Wait не меньше 60 секунд → повтор.
- Таймаут не обрабатывать через `neverError` — только выходом ошибки.
- `neverError:true` не ставить без явной проверки тела следующим узлом.
- `continueErrorOutput` не оставлять с неподключённым output(1); выход ошибки не заводить в no-op или в обработчик, чей выход никуда не ведёт; `continueRegularOutput` не ставить «чтобы не падало».
- Поля для дальнейших узлов не брать из выхода Sheets-узла — из именованной исходной ноды.
- Страницу, найденную поиском, не принимать без проверки поля идентичности на самой странице (например артикула в `itemprop="sku"`).
- Список не записывать полным, пока перечень неоткрывшихся частей не выведен явно и не пуст.
- Пагинацию не вести фиксированным числом страниц: читать до пустой страницы или отсутствия курсора; срабатывание аварийного предела — ошибка прогона, не предупреждение.
- Курсор пагинации не начинать с пустого значения — со значения из целевой таблицы (`max(raw_id)`); окно дат инкрементальной загрузки не брать «вчера» от даты прогона — от последней успешной метки в целевой таблице.
- На `neverError` против ошибки внутри `completeExpression` пагинации не полагаться: при ошибке API тело undefined — проверку на undefined ставить в самом выражении.
- Условие остановки пагинации не переносить с одного эндпоинта на другой по аналогии.
- Смещение часового пояса в голове не пересчитывать: расписание — только явным `settings.timezone` зоны, в которой названо время задачи, и cron в часах этой зоны.
- Явную таймзону у воркфлоу «со временем по Москве» не предполагать до проверки.
- Читателя не ставить на ту же минуту cron, что писателя, от которого он зависит, — на несколько минут позже.
- Даты из внешних источников не разбирать через `new Date(строка)` — явно, по всем встреченным форматам.
- Идентификатор модели Anthropic не брать из примера или записи — из документации Anthropic в момент правки.

### Google Sheets
- Служебное состояние (курсоры, маркеры повторов, реестры, сопоставления) не держать в Sheets — в Data Table; Sheets — витрина для человека.
- На append без `matchingColumns` при повторяемой записи не полагаться; простой append при повторяемом прогоне не делать — только `appendOrUpdate` с `matchingColumns`.
- Значения не писать в колонку, которую заполняет формула (ARRAYFORMULA, IMPORTRANGE, построчная); поле с именем колонки-формулы во вход записи не включать.
- `columns` узла Sheets не оборачивать в `expr()`-строку — только литеральный объект.
- Составной ключ не задавать мультивыбором `matchingColumns` — собирать заранее в Code в одну колонку.
- Ячейку не очищать передачей `null` — только `""`.
- Строки без ключа не пускать в запись и в первый платный вызов модели.
- Ключи не сравнивать без приведения обеих сторон к одному типу в Code-узле (и перед `.trim()` — `String(x ?? '')`); символы ключа сверять по коду, а не глазом.
- Строку со статусами жизненного цикла не защищать от повтора через `appendOrUpdate` — только множеством уже известных ID; поле первого наблюдения не перезаписывать на каждом прогоне.
- Узел «delete» не ставить без явных `startIndex` и `numberToDelete`; в коде удаления — барьер: номер строки меньше 2 → остановка с ошибкой.
- Запись и удаление по номеру строки не делать без повторного чтения ключевой колонки в момент записи и сравнения с первым чтением; расхождение — остановка без записи.
- Диапазон из ответа batchGet не выбирать по позиции — только по имени листа в поле `range`.
- Многоколоночный фильтр Data Table не оставлять без явного `matchType:"allConditions"`.
- Отбор очереди к обработке не делать чёрным списком статусов («не `done`») — только белым («пусто» или `new`); очередь без конечного статуса для необрабатываемого (`rejected`) не строить; «уже виденное» не определять по отсутствию поля — только по ключу из множества виденных.
- Схему «Sheets + delete» не применять, если задача решается `appendOrUpdate` по ключу; ложную ветку IF перед Merge в нём не оставлять неподключённой; подключённость проверять по `connections`, а не по `description`.
- `appendOrUpdate` по ключу не применять, если нужно физическое удаление строк, исчезнувших из источника.

### Неизвестное значение
- Значение, которое не прочиталось, не распозналось или не пришло, не превращать в ноль, пустую строку, «прочее», «пустой день» или запасную константу — явное состояние «неизвестно» (`unknown`, `ERROR`, пустое с флагом) и сигнал.
- Весь поток из-за одного неизвестного не ронять, если он делает и другую работу: флаг (`paramsOk`) и `unknown` у зависимого поля.
- Расчёт по параметрам листа не начинать, не проверив, что параметры прочитаны.
- Отказ ключа или API на служебной строке не писать «пустым днём» (`EMPTY_`) — писать `ERROR`.
- Производный признак не вычислять, пока не проверено, что входы покрывают все источники (все кабинеты).
- Снимок при нуле объектов не оставлять пустым — писать строку-маркер (например `__empty__`).
- Запасную константу `|| <число>` к параметру из листа не ставить.
- Накопитель списком из внешнего API не перезаписывать, если объём входа меньше порога от прошлого объёма, — остановка без записи.
- Признак «событие обработано» не писать раньше всех веток записи — только последним.
- Запрет записи не держать текстом в STATE — только в коде узла (фильтр в воротах боевого режима).
- Признак, который сама запись меняет, не брать эталоном «как должно быть» — сравнивать со снимком до записи.
- Одноразовый воркфлоу с данными, зашитыми в код, не перезапускать как есть.

### Запись во внешний кабинет
- Боевой режим не запускать без явного «да» владельца на конкретный список из режима «проверка» (номер декларации, перечень карточек); «да» на режим вообще не считается.
- Режим не делать отдельным воркфлоу — только параметром входа одного воркфлоу.
- Режим не строить на признаке «ручной запуск» (`$('Manual').isExecuted`, `$execution.mode === 'manual'`) — только явным параметром входа со значением по умолчанию «проверка».
- Пишущий во внешний кабинет воркфлоу не публиковать.
- Пишущий инструмент после пробы не оставлять в боевом режиме или с непустым набором объектов.
- Параметр запроса не выбирать из списка допустимых значений API — выводить из данных; расхождение параметра с данными — блокер, а не предупреждение.
- Идентификатор в форму запуска (номер декларации, nmID) не набирать по памяти — копировать из колонки листа или из входа прошлого исполнения.
- Если три записи подряд приняты с кодом 200, а объект при чтении не изменился, — боевые запросы не продолжать, пока причина не найдена.
- Код 200 итогом записи не считать — итог по перечитанному объекту.

### Проверка, тест, мониторинг
- Тест с побочными эффектами не запускать без вопроса Андрею.
- Правку не считать доказанной прогоном, в котором нет случая, обязанного пройти, и случая, обязанного отказать, или путь которого не идёт через исправленную ветку; ветка «истина» каждого условия должна исполниться хотя бы раз и дать объект.
- Негативный тест на сбойный элемент не ставить последним в проверочном списке — только в середину.
- Детектор и монитор не принимать без красного на подсаженном дефекте; смену конструкции подсадки не делать без согласования до исполнения; стенд, на котором дефект нечем вызвать, не использовать.
- Проверка, не способная отличить норму от незнания, не отвечает «расхождение» — только «нет данных»; проверку на источнике не строить, не убедившись, что признак здорового объекта в нём может появиться.
- Условие защитной ветки не удалять, не выяснив, какой инвариант оно держит, и не проверив защиту на плохом случае; прибор по расписанию для редкой защитной ветки не строить.
- Эвристику «`updatedAt` против времени последнего исполнения» не применять, если версии доступны или успешные прогоны не сохраняются.
- Монитор множества объектов не строить на списке, вписанном в код, — список охвата из источника истины на каждом прогоне.
- В воркфлоу ошибок не ставить внешних вызовов, способных упасть, и медленных шагов; канал уведомления не совпадает с мониторимыми.
- Ограничитель частоты алертов не строить: постоянно падающий воркфлоу чинить или выключать в тот же день.
- Внешний сторож падения самого n8n не строить и не предлагать заново без нового основания.

## Как делать

### Вызов воркфлоу из сессии
1. Имя узла-триггера — из `get_workflow_details` или из сигнатуры `registry/tools.md`.
2. `execute_workflow`: `triggerNodeName` — точное имя узла-триггера; `inputs` — `{webhookData: {method: "POST", body: {...}}}` для вебхука или `{formData: {...}}` для формы, без поля `type`; `executionMode: "manual"`.
3. Ответ без тела — номер исполнения; результат читать `get_execution` с обоими параметрами `workflowId` и `executionId`.
4. Факты, недоступные из облачной сессии (публичный API собственного инстанса `/api/v1/` и ряд внешних сайтов закрыты прокси, ответ 403), снимает воркфлоу-зонд на сервере, а не сессия; перечень недоступных источников — `n8n-workflow-registry`.
5. До опоры на параметр, описанный в документации n8n, — сверить версию инстанса (`get_instance_context` или окно About) или проверить параметр зондом.

### Диагностика
1. Сначала факт исполнения и объект воздействия (`get_execution` по реальному прогону, целевая таблица, документ), потом гипотезы по `get_workflow_details.nodes` и тексту предупреждений.
2. Воркфлоу, который правишь, читаешь сам; ответ о чужом воркфлоу — через посредника (см. «Что читать»).
3. `get_execution(includeData:true)`: сужать `nodeNames:["<терминальный или упавший узел>"]` — без него тело ответа повторяется по каждому узлу, который его касался. Ответ больше предела MCP клиент сохраняет в файл — разбирать скриптом по файлу, не читать в контекст. Исполнение от ~10 МБ обрывает транспорт MCP — итог тяжёлого воркфлоу писать на лист и читать оттуда.
4. 429 Sheets: до гипотез о чужом потребителе прочитать тело ошибки упавшего узла (`get_execution(includeData:true, nodeNames:["<упавший узел>"])`): `quota_limit`, `quota_limit_value`, `quota_unit`, `consumer`. `consumer` с номером собственного проекта — квоту выбрали сами. Второй дискриминатор: `manual` того же воркфлоу даёт success, а `integrated` (вызов из родителя) — 429, `executionTime` упавшего узла около 59000 мс → дело в числе входных items (цепочка Execute Workflow).
5. Расписание `active`, а исполнений нет: сравнить `versionId` и `activeVersionId`; при расхождении — сверить верхнеуровневые `nodes` с `activeVersion.nodes` по триггерному узлу. Лечение нерегистрирующегося триггера — полный тумблер `unpublish_workflow` → `publish_workflow`.
6. Живость расписания без сохранённых успехов — счётчики `production_success` и `production_error` таблицы `workflow_statistics` базы n8n (прунинг их не чистит): запрос готовит сессия, выполняет Андрей на сервере (`psql` в контейнере базы).
7. Расхождение конфига до и после ручной правки в редакторе: прежде чем объявлять баг, проверить в интерфейсе, отрисовывается ли исчезнувший параметр вообще.
8. Записанные данные не совпадают с ожиданием при частичном обновлении `autoMapInputData`: целы ли поля того же источника — затёрто или не было.

### Порядок создания и правки
1. `get_sdk_reference` — документация; форму `update_workflow` проверять по его схеме в момент работы.
2. `search_nodes` + `get_node_types` — точные параметры узлов (виды аутентификации узла формы — тоже здесь, в момент правки).
3. «Перед записью» (ниже).
4. `validate_workflow`.
5. Запись путём по таблице «Выбор пути записи».
6. «После записи» (ниже).
7. `publish_workflow` — `update_workflow` не публикует; для активного воркфлоу — полный тумблер `unpublish_workflow` → `publish_workflow`. Перед публикацией при `versionId ≠ activeVersionId` — `get_workflow_versions_diff`.
8. Последний шаг: свежий `get_workflow_details`, `versionId` равен `activeVersionId`; результат — по объекту воздействия.
9. Паспорт — по Skill `n8n-workflow-passport`.

**Выбор пути записи** — по тому, что путь теряет, а не по размеру правки:

| Правка | Путь |
|---|---|
| один или несколько узлов существующего воркфлоу | точечные операции `update_workflow` (`setNodeParameter`, `updateNodeParameters`, `setNodeSettings`, `setWorkflowSettings`, `setNodeCredential`, `addNode`, `renameNode` и другие; применяются атомарно) со сверкой до и после; второй путь — ручная вставка кода Андреем в редакторе |
| новый воркфлоу или пересборка многих узлов | `create_workflow_from_code` с полной сверкой до и после и установкой настроек воркфлоу после записи (`setWorkflowSettings` или руками в редакторе) |
| неизменяемые узлы при пересборке | сохранённый воркфлоу из `get_workflow_details` (большой ответ — файлом), нужные узлы вырезать скриптом и вставить в новый код как есть; после записи сверить их с исходником байт в байт тем же скриптом |
| пробный прогон правки | черновиком, без публикации (ручной запуск исполняет черновик); у воркфлоу с триггером расписания пробность — только явным параметром режима |

### Перед записью
Выписать до записи — без записи «до» потерю не увидеть «после»:
1. Ветки `connections.<IF/Switch>.main`.
2. `matchingColumns` и реальный gid (`sheetName.value`) у Sheets-узлов.
3. Выражения в IF/Switch.
4. `authentication` у webhook-триггера — при записи кодом целиком перенести значение в передаваемый код; `webhookId` каждого узла-вебхука.
5. Настройки воркфлоу: `settings.timezone`, `errorWorkflow`, `saveDataSuccessExecution`.
6. Имена узлов с привязанным ключом и их ключи (поле `credentials` в `get_workflow_details`).
7. Закрыть вкладку редактора этого воркфлоу.
8. Прочитать `description`: при `PASSPORT: <id>` — прочитать паспорт до правки; нет `PASSPORT:` — записать долг, работу не блокировать.
9. Кто вызывает воркфлоу — найти по факту, а не по реестру: узлы Execute Workflow с его ID; HTTP-узлы, в URL которых стоит путь его вебхука (поиск по строке пути в URL узлов на инстансе); при замене воркфлоу-инструмента — его ID в `meta/prompts/`, Skills, `registry/` и текстах выданных нарядов. Если правка меняет выход — снять набор полей выхода до правки и сравнить поле в поле после. Перевод с ответа `success:false` на исключение (`throw`) — сначала вызывающие получают обработку исключения, потом меняется сам воркфлоу.
10. Документ подготовки правки несёт `versionId`, с которого снят; сверить его с живым.
11. В плане правки записать, кто и каким путём привязывает ключ к каким узлам: сессия сама, `setNodeCredential` в той же записи.

### После записи
После каждой записи, не только первой:
1. Сверить выписанное «перед записью» со свежим `get_workflow_details`.
2. У вебхука с аутентификацией `triggerInfo` содержит «This webhook requires a header…», а не «No credentials required».
3. Нестандартные поля (`retryOnFail`, `maxTries`, `waitBetweenTries`) — по сохранённому JSON узла.
4. Настройки воркфлоу (`settings.timezone`, `errorWorkflow`) — при расхождении выставить `setWorkflowSettings` или руками в редакторе до публикации.
5. Каждое поле с выражением — в виде `={{ … }}`; дефект найден в одном воркфлоу — тем же действием проверить его копии (тот же воркфлоу другой площадки или кабинета).
6. `webhookId` каждого узла-вебхука — тот же, что до записи.
7. Ключи: поле `autoAssignedCredentials` в ОТВЕТЕ `create_workflow_from_code` и `update_workflow` — непустое: проверить подставленный ключ, чужой заменить `setNodeCredential`; пустое вместе с «their credentials must be configured manually» — новые узлы без ключа, привязать `setNodeCredential`. Затем поле `credentials` у узлов в свежем `get_workflow_details`; окончательно — реальный прогон.
8. `versionId` и `activeVersionId` — расхождение значит «не опубликовано».
9. Результат — по объекту воздействия.
10. После ручной правки в редакторе — `active` (Save может опубликовать).

### Ключи доступа
1. Ключ создаёт владелец в редакторе n8n (Credentials) и присылает в чат только название.
2. Сессия привязывает ключ сама, по id: новому узлу — `addNode` с полем `credentials` (`{id, name}`) в том же вызове, где узел создаётся; существующему — `setNodeCredential` (`nodeName`, `credentialKey`, `credentialId`, `credentialName`). Пропавший у узла ключ — тоже `setNodeCredential`.
3. Смена ключа у узла Google Sheets — точечно: `setNodeParameter` (поле `authentication`) и `setNodeCredential`; первый прогон после смены читает лист и сверяет результат.
4. Разовая сверка ключей и доменов: по всем HTTP-узлам — домен адреса узла против имени и id привязанного ключа.
5. Ротация: перебор всей базы n8n на литерал ключа — запрос готовит сессия, выполняет Андрей через `docker exec … psql`; перед ротацией — привязка по узлам (поле `credentials`); после — отзыв у сервиса-выдавателя (`n8n-workflow-registry`).
6. Ключ, хоть раз сохранённый литералом в теле узла, перевыпускается у сервиса-выдавателя.
7. Вебхук закрыт ключом, совпадающим с токеном внешнего сервиса, — сверить `autoAssignedCredentials`, заменить `setNodeCredential`.

### Новый вебхук
1. В коде триггера `authentication: "headerAuth"` с первого `create_workflow_from_code`; при каждой записи кодом целиком — заново в код.
2. Ключ Header Auth привязать к триггеру сразу после создания и до первого `publish_workflow` — сессией, `setNodeCredential`; сверить `autoAssignedCredentials`.
3. Каждый HTTP-узел, вызывающий этот вебхук, — адрес по имени docker-сервиса и тот же ключ через `httpHeaderAuth`.
4. После публикации `triggerInfo` содержит «This webhook requires a header…».
5. Открытый вебхук по решению Андрея — причина в паспорт воркфлоу.

### Копия воркфлоу
1. Инструмента копирования в n8n MCP нет (проверять состав инструментов в момент работы): `create_workflow_from_code` по тексту чужого воркфлоу — реконструкция.
2. После реконструкции сверить с оригиналом по сохранённому JSON узлов ключи и поля с выражениями.
3. Точная копия — ручное действие Андрея в интерфейсе (Duplicate).

### Снятие с публикации
1. `unpublish_workflow` — тем же действием, которым инструмент объявлен устаревшим.
2. Проверить чтением: `search_workflows` или `get_workflow_details` → `active:false`.
3. Записать ID, назначение, паспорт, как вернуть (`publish_workflow`) туда, где проект хранит невзятое и снятое: для проектов в репозитории — `NOT_TAKEN.md` проекта или его журнал.
4. В паспорт — строка о снятии (дата, причина, как вернуть) по форме Skill `n8n-workflow-passport`.

### Воркфлоу ради экономии контекста
1. Узел загрузки выбирать по свойству типа: `n8n-nodes-base.httpRequest` оставляет сырое тело ответа в `executionData.contextData` при любых параметрах, `n8n-nodes-base.github` не оставляет никогда.
2. Воркфлоу с утечкой чинить заменой узла загрузки, а не параметрами вызова.
3. HTTP-узел заменить нечем — вынести его в опубликованный подворкфлоу; подворкфлоу перед возвратом оставляет только нужное поле (узел-«сужатель»), вызывающая сессия читает ответ с `nodeNames` терминального узла.

### Цепочка Execute Workflow
1. При каждой цепочке из двух и более Execute Workflow подряд — проверить, что саб-воркфлоу возвращает последним узлом.
2. Родителю нужен только факт завершения — `waitForSubWorkflow:false`, или терминальный узел-квитанция (Set со статусом, один item), или `executeOnce` на первом узле следующего звена.

### Google Sheets
1. Перед первой записью в лист — прочитать шапку и колонки в режиме FORMULA.
2. Шапка и лист параметров — по «Соглашениям» ниже.
3. До первой записи строк нового вида в общий лист (другой бренд, строки без поля, которое у прежних было всегда) — каждого читателя проверить по коду его узла чтения и первой обработки: пропускает, останавливается или пишет неверное. Читатели в n8n — строки D `registry/n8n-map.md` по ID книги; скрипты других книг искать отдельно.
4. Лист с ошибкой в строке заголовков или с дублями заголовков — читать узким диапазоном (Data Location → Range, строка заголовков задана явно, граница до дублей).

### Соглашения, от которых зависят другие части
- Строка заголовков листа — договор со всеми узлами-читателями: перед правкой шапки перечислить узлы-читатели листа, после правки обновить их схему; при переводе читателя на другой лист сопоставить имена колонок до переключения.
- Лист параметров воркфлоу (его читает воркфлоу) — горизонтальный: строка 1 — имена, строка 2 — значения; не пары «имя — значение» по строкам.

### Идемпотентная запись
1. Выбор хранилища: нужен только факт «уже видели этот ключ», объём до ~10k, без TTL — Remove Duplicates; нужно состояние (запрос, TTL, статус, история) — Data Table; данные читает человек — Google Sheets (`appendOrUpdate` по ключу).
2. Data Table Get: `alwaysOutputData:true` и `executeOnce:true` на уровне config узла; форма Get+IF — `returnAll:true` + матчинг по ключу в Code-узле.
3. Накопитель из внешнего API: объём входа против порога до записи; чтение до пустой страницы; признак «обработано» последним; читатель накопителя на `appendOrUpdate` фильтрует по свежести (`updated_at`).

### HTTP и обработка ошибок
1. Область: таймаут — каждый узел HTTP Request; выбор onError — везде, где есть внешний вызов; поля из узлов выше — везде, где после HTTP они используются; воркфлоу ошибок — все активные, деструктивные (delete, публикация вовне) в первую очередь.
2. Первым узлом после внешнего вызова — проверка тела на признак ошибки (code/error); после вызова с потерей элементов — сверка длины входа и выхода с `throw`.
3. Выбор onError: ошибка реально обрабатывается дальше (алерт, фолбэк, запись статуса) — `continueErrorOutput` и output(1) в реальный узел; ошибка не критична и ниже явно читают code/error — `continueRegularOutput` (ниже код с try/catch и фолбэком, выводящим «ошибка API» в сообщение); осмысленной обработки нет — `stopWorkflow` и воркфлоу ошибок.
4. Ретрай по коду — выход ошибки + IF по `$json.error.status` + Wait; явный ретрай — всеми тремя полями `retryOnFail`, `maxTries`, `waitBetweenTries`.
5. Запрос, меняющий внешнее состояние, защищают выход ошибки и воркфлоу ошибок; повторяет его самовосстанавливающийся флаг (метка «обработано» в строке объекта ставится только при успехе — следующий прогон подхватывает).
6. Узлам без полного таймаута (Postgres — только `connectionTimeout` на подключение; Telegram — нет поля) — выход ошибки и воркфлоу ошибок.
7. Вызов Anthropic API: Body Content Type JSON, Specify Body — Use Expression, значение через fx без ведущего `=` и без `JSON.stringify()`; credential `httpHeaderAuth`; сверху — таймаут и проверка code/error.
8. Длинное сообщение Telegram (дайджест, список находок) — делить на несколько или считать длину до отправки; урезанный список помечать в самом сообщении.

### Воркфлоу ошибок и живость
1. Воркфлоу ошибок назначается в настройках каждого воркфлоу; массово — `setWorkflowSettings`; после любой записи — сверить.
2. Две ступени. Ступень 1 — воркфлоу, молчание которых стоит денег или решений: воркфлоу ошибок + `settings.saveDataSuccessExecution = all` + строка в мониторе ежедневной живости. Ступень 2 — все остальные активные: только воркфлоу ошибок. Список ступени 1 — `projects/n8n/LOG.md`, запись Р-4.
3. Сколько воркфлоу без воркфлоу ошибок и без явной таймзоны — считать заново по строкам W `registry/n8n-map.md` (поле 10, поле 8).

#### Проверка после настройки
Заведомо падающий воркфлоу (HTTP на битый URL, без обработки) → прогнать → убедиться по факту прихода сообщения, не по логу, что алерт дошёл.

#### Воркфлоу по расписанию считается работающим только по объекту
1. Таймзона: явный `settings.timezone` (для времени по Москве — `Europe/Moscow`), cron в часах этой зоны; ставить `setWorkflowSettings` или руками в редакторе.
2. До закрытия задачи у воркфлоу задан воркфлоу ошибок, доводящий сбой до Telegram; без него — сначала задать, прогоны до этого не считаются.
3. Первый плановый прогон после каждой новой публикации — прочитать по объекту: метка последнего прогона на объекте (строка в целевой таблице, «Снимок сделан» на листе) показывает дату планового прогона.
4. Для триггеров Apps Script — то же правило, видимость даёт проверка возраста метки (Skill `apps-script-sheets`).

### Тест правки
1. `prepare_test_pin_data` + `test_workflow`.
2. Целевой случай и контрольный, обязанный пройти; путь теста — через исправленную ветку; ветка «истина» каждого условия исполнилась и дала объект.
3. Детектор и монитор — красный на подсаженном дефекте, потом зелёный.
4. Редкая защитная ветка (откат ответов маркетплейсу, белый список автопубликации) — прогоном на строке `TEST_` при приёмке и при каждой правке этой ветки, на хорошем и плохом случае.

### Чек-лист перед публикацией
Гейты 1–6: провалил — не публикуется.
1. `validate_workflow` — ноль ошибок.
2. Скан того, чего `validate_workflow` не видит: Set-узел с 0 или 1 потребителем (удалить, выражение вписать в потребителя); Code-узел вместо нативного (ручной цикл пагинации → опция Pagination; ручной sleep → Wait; regex-парсинг → XML/JSON.parse; ретрай по статусу → retryOnFail); identity-узлы (`return $input.all()`); Merge — число проводов равно `numberOfInputs`, off-by-one; fan-out не параллелен; Switch без fallback (смотреть `connections` узла); `$json` в глубине ветвлений (заменять на `$('Node').item.json`); `$env` вообще; дубль провода (два одинаковых connection-объекта на один узел); узлы без входящих связей, disabled-узлы внутри цепочки; цепочка из двух и более Execute Workflow подряд.
3. Обработка ошибок по «HTTP и обработка ошибок»; нет `continueErrorOutput` с неподключённым output(1); нет места, где непрочитанное значение становится нулём, «прочим», «пустым днём» или `|| <число>`.
4. Секретов в текстовых полях нет: headerParameters, тело запроса и константы Code-узлов.
5. Периметр: ни один вебхук без аутентификации; оценить охват — вебхук с произвольным id объекта опаснее вебхука с фиксированным; узел формы — тот же класс; HTTP-узлы к своим вебхукам — internal-адрес docker-сети.
6. «После записи» — после каждого `update_workflow`.
Качество:
7. Тест по «Тест правки».
8. Явный `settings.timezone` у всего по расписанию; эталон — заданы и `Europe/Moscow`, и `errorWorkflow`.
9. Имя воркфлоу, `description` заполнен, узлы переименованы из дефолтных.
10. Вкладка редактора закрыта до записи; черновик, расходившийся с опубликованной версией, — `get_workflow_versions_diff`; последний шаг — `versionId` равен `activeVersionId`; воркфлоу по расписанию — по объекту.
11. Верификация — только по объекту воздействия.

### Запись во внешний кабинет: режимы «проверка» и «боевой»
Для воркфлоу, который пишет в кабинет площадки (Ozon, Wildberries): декларации, описания, характеристики карточек.
1. Режим — параметр входа (поле формы), по умолчанию «проверка». «Проверка» проходит тот же путь, что боевой: те же источники, те же тела запросов, все блокеры — и ничего не пишет вовне. Итог — список «что будет записано, куда, что заблокировано и почему».
2. Список «к записи», построенный по правилу-гипотезе, калибровать по объекту (тому, что видит сотрудник в кабинете) до просьбы о разрешении.
3. Показать список владельцу. Повтор Андреем фразы с названием объекта после показа проверки без записи — «да» на боевую запись по этому объекту.
4. Ворота боевого режима — фильтр в узле перед записью (предметы, которые писать нельзя; карточки без нужного поля); перед записью прочитать кабинет — то, что уже есть, не писать повторно (отдельный статус «уже есть в кабинете»).
5. Перед боевым режимом:
   1. право ключа на запись проверено;
   2. если запись заменяет объект целиком — выяснено, какие поля чтение API не возвращает, и запрет вынесен в код узла;
   3. сохранён снимок объекта до записи с адресом (номер исполнения, узел, время);
   4. настройки вывода каждого узла чтения сверены с ожиданием кода;
   5. ожидаемый результат первого прогона выведен из прочитанных данных и настроек узла чтения, а не из замысла правки;
   6. одна пробная запись в один объект и чтение его обратно — до массовой записи;
   7. каждый параметр запроса выведен из данных;
   8. идентификатор в форме запуска скопирован из колонки листа или входа прошлого исполнения.
6. Перед боевой записью список пересчитать заново: число в разрешении — не список.
7. Боевой запуск — вручную формой или `execute_workflow` в режиме `manual`; воркфлоу стоит `active:false`.
8. После боевого режима — перечитать записанные объекты и, где площадка даёт, её журнал ошибок. Где проверка площадки идёт отложенно — повторное чтение отдельным режимом позже (режим «статус»).
9. После пробы — вернуть инструмент в «проверку» с пустым набором объектов.
10. Повторная запись после одноразового воркфлоу с данными в коде — инструментом, который берёт данные из входных строк; одноразовый воркфлоу оставить образцом, снятым с публикации.
11. Сравнение «изменилось ли» по хэшу: хэш считать от канонизированной копии (порядок неупорядоченных массивов, переносы, пробелы), а не от сырого ответа API. При каждой смене правила нормализации — режим «пересчёт хэшей»: у пар, где текст совпадает по новому правилу, пересчитать сохранённые хэши, настоящие расхождения не трогать.

### Инструменты MCP и отчёты
- Предупреждение MCP «…credentials must be configured manually» печатается всегда — проверяй `autoAssignedCredentials` и поле `credentials`.
- `get_workflow_details` может не показать поле `credentials` у узла при живом ключе (проверено не на всех типах узлов), а имя ключа в поле не доказывает, что ключ рабочий и бьёт в свой домен — проверяй прогоном по объекту.
- `validate_workflow` и инструмент записи отвечают успехом, когда параметры не применились, — проверяй сохранённый JSON узла и настройки свежим чтением.
- `triggerInfo` сам себе противоречит («triggerCount 1» и «no production triggers» в одном ответе) — проверяй публикацию по `active` и `activeVersionId`.
- Список воркфлоу не несёт поля `description` — строку `PASSPORT:` ищи через `search_workflows` или `get_workflow_details`.
- `active:true` говорит, что что-то опубликовано, а не что именно, — проверяй `activeVersionId` и опубликованные узлы.
- У узла нет параметра (например `parameters.operation` у Google Sheets) — это умолчание интерфейса, а не «операции нет» — проверяй в редакторе или по прогону.
- Имя ключа в JSON может описывать ВЫКЛЮЧЕННОЕ состояние (`"returnAllMatches"` = «Return only First Matching Row»; отсутствие ключа — вернуть все совпадения) — проверяй смысл в интерфейсе или прогоном.
- `executionMode: "production"` из MCP не создаёт видимого исполнения и не возвращает тело ответа — проверяй через `manual`.
- `get_execution` без `workflowId` отвечает «not found» даже для реального успешного прогона — проверяй, что переданы оба параметра.
- Поле `inputs` с другим именем (`payload` вместо `webhookData`) даёт `status:error` без указания причины — проверяй имя поля.
- Воркфлоу, перечитывающий результат своей записи в коде, при production-запуске через MCP ответа не возвращает, а `get_execution` по такому запуску даёт «not found» — проверяй результат сам по объекту.
- Инструменты n8n MCP не перечисляют переменные инстанса (`$vars`) — смотри Settings → Variables в интерфейсе.
- При `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none` (или `saveDataSuccessExecution` в настройках воркфлоу) успешные прогоны не видны в списке исполнений — пустой список не значит, что воркфлоу не работал; проверяй объект и `workflow_statistics`.
- `nodeNames`, сужение `get_execution`, не режет сырой ответ внешнего API в `executionData.contextData` узла `httpRequest` — проверяй тип узла загрузки.
- Ответ `get_workflow_execution` больше предела MCP клиент молча сохраняет в файл; исполнение от ~10 МБ обрывает транспорт MCP — проверяй, прочитан ли узел отказа целиком.
- Publish отказывает без текста ошибки через MCP при пустой Workflow Input Schema у Execute Workflow Trigger — проверяй схему (одно необязательное поле-заглушка); ошибка видна только в редакторе.
- Новый воркфлоу не получает воркфлоу ошибок и явную таймзону сам; точечные операции `update_workflow` их не трогают, `setWorkflowSettings` ставит (в том числе массово) — проверяй настройки после создания.
- Бэкап базы n8n без `N8N_ENCRYPTION_KEY` не восстанавливает ключи доступа (они зашифрованы этим ключом) — проверяй, что ключ шифрования сохранён вместе с бэкапом.

### Запись воркфлоу кодом целиком (`create_workflow_from_code`, любая запись воркфлоу кодом SDK)
- Пересобирает каждый узел из переданного кода и молча теряет всё, чего в коде нет или что SDK отбрасывает; цена не зависит от размера правки — проверяй по «После записи» после каждой такой записи (потеря повторяется).
- Сбрасывает `settings.timezone` и `errorWorkflow`, даже записанные в коде (метода `.settings()` нет; третий аргумент `workflow(id, name, {settings})` проходит `validate_workflow` и не применяется) — проверяй настройки и выставляй `setWorkflowSettings`.
- `retryOnFail` с `maxTries`/`waitBetweenTries` сохраняется как один `retryOnFail:true` (в силе 3 попытки, около секунды) — проверяй сохранённый JSON.
- Выражения в условиях IF и Switch становятся строковым литералом, условие не срабатывает никогда; копия воркфлоу наследует дефект — проверяй `{{ … }}` в поле условия.
- Сбрасывает `matchingColumns` Sheets-узлов — проверяй по выписанному.
- Теряет ветки IF; ветка, которую уже чинили, пропадает снова — проверяй `connections`.
- Снимает аутентификацию вебхука, если `authentication` нет в коде триггера — проверяй `triggerInfo`.
- Меняет `webhookId` нетронутого узла-вебхука, вызывающие по старому пути получают отказ — проверяй `webhookId`.
- Новым HTTP-узлам ключ не создаёт; узел, переименованный в переданном коде, остаётся без ключа, возврат прежнего имени не чинит — проверяй `credentials` и привязывай `setNodeCredential`.
- Реконструкция чужого воркфлоу по тексту не переносит ключи, выражения вырождаются в текст — проверяй по сохранённому JSON оригинала.
- Литералы `\s \S \d \w` в regex ломаются при записи через SDK — проверяй сохранённый код; форма: `var anyChar='[\\s\\S]'; new RegExp('...'+anyChar+'...')`.
- SDK `.to([a,b])`: второй получатель молчит навсегда — пиши `.to(a).add(source).to(b)`.
- Вложенные `.to(merge.input(N))` дают регрессию связей Merge — собирай плоско, каждый вход отдельным `.add(source).to(merge.input(N))`.

### Версии, публикация, редактор
- Ручной запуск через MCP (`manual`) исполняет черновик (`versionId`), расписание, вебхук и `production` — опубликованную версию (`activeVersionId`): зелёный ручной прогон не говорит, что исполнит расписание, тест в `production` зеленеет на старом коде — проверяй версию, которую будут исполнять.
- После правки и публикации поверх активного воркфлоу cron или вебхук может не создавать исполнений при целом конфиге и `active:true` — проверяй первым плановым прогоном по объекту; лечение — полный тумблер.
- Ручная правка интервала Schedule Trigger в редакторе: черновик показывает новый час (`triggerAtHour`), опубликованная версия остаётся с `rule.interval:[{}]`, прогон уходит в полночь — проверяй триггер опубликованной версии через MCP.
- `publish_workflow` отправляет в работу весь черновик: выключенный там триггер (`disabled: true`) или чужая незаконченная правка молча останавливают расписание или меняют поведение — проверяй `get_workflow_versions_diff`.
- Save из редактора нормализует конфиг, записанный через MCP/SDK: параметры верхнего уровня без поля на панели исчезают — проверяй прогоном по объекту.
- Save из редактора может заодно опубликовать воркфлоу (`active:false` → `active:true`, новый `activeVersionId`) — проверяй `active` после каждой ручной правки.
- Сохранение из устаревшей вкладки редактора затирает правку, записанную через MCP (побеждает последний сохранивший), — закрывай вкладку до записи.
- Смена типа ключа в узле Google Sheets через редактор сбрасывает фильтры, опции и сопоставление колонок (не перепроверено) — проверяй узел и настраивай заново.
- Выключенный в черновике триггер не останавливает опубликованное расписание — проверяй `active:false` после `unpublish_workflow`.
- Копия активного воркфлоу создаётся сразу активной (не перепроверено) и задваивает внешние действия — проверяй `active` у копии.
- Воркфлоу ошибок и монитор-воркфлоу не видят прогона, который не начался (расписание не создало исполнения, n8n или контейнер лежит) — проверяй первым плановым прогоном по объекту после каждой публикации.
- Снятый с публикации воркфлоу не запускается и потому больше не сигналит о сбое ключа или источника — проверяй, где ещё виден этот сбой.
- Память воркфлоу между прогонами (`$getWorkflowStaticData`) сохраняется только в плановом прогоне опубликованной версии; ручной и пробный запуск её изменений не сохраняют, следующий плановый прогон повторит то же сообщение — проверяй первым плановым прогоном.
- `execute_workflow` через MCP запускает воркфлоу с триггером расписания через этот триггер, даже если рядом стоит ручной: признаки «ручной запуск» в коде не срабатывают, запуск идёт боевым — проверяй явный параметр режима.
- Два независимых триггера одного типа: MCP запускает только первый — проверяй, что второй путь пущен веткой от одного триггера.
- Обрыв ответа создающего вызова («transport closed», протух доступ) при состоявшемся создании даёт дубль при повторе — проверяй `search_workflows` по имени и что объект один.

### Поток элементов и Code-узел
- 0 items на узле молча обрывают всю цепочку ниже — проверяй выход каждого узла; причины: обрыв трассировки `pairedItem` на пачке; `alwaysOutputData` выключен или положен внутрь `parameters` вместо верхнего уровня узла (молча игнорируется); неподключённая ветка IF, которую ждёт Merge или петля; узел Google Sheets «create» на существующем листе.
- Выключенный (disabled) узел пропускает item насквозь — проверяй узлы ниже.
- Узел с Execute Once обрабатывает только первый входной элемент где угодно в цепочке (после Merge, в середине), остальные отбрасывает — проверяй число элементов на выходе.
- `$json` в Code-узле в режиме «для всех» молча берёт первый элемент — проверяй режим: `$json`/`$input.item` — «для каждого», `$input.all()` — «для всех».
- Item, собранный в Code-узле заново из перечисленных полей, теряет неперечисленные (в таблице — почти пустые строки) — проверяй spread `({ ...src, newField })`.
- `axios`/`fetch` без `NODE_FUNCTION_ALLOW_EXTERNAL=axios` в .env падают тихо — проверяй переменную; встроенные модули — только при `NODE_FUNCTION_ALLOW_BUILTIN`.
- `try/catch` вокруг вызова с ключом в Code-узле превращает отказ в зелёный прогон — проверяй, что вызов был.
- `ExpressionError: Multiple matches found` на пачке и `pairedItemNoInfo` (`Paired item data … is unavailable`) после узла, размножающего item (Execute Workflow fan-out), — обрыв трассировки `pairedItem` — проверяй `splitInBatches(batchSize:1)` вокруг per-item шагов или `.first()`/`.all()` с матчингом по ключу.
- `.first()` к узлу без гарантии одного item за итерацию даёт неверные данные вместо ошибки — проверяй конструкцию выше.
- Execute Workflow с `waitForSubWorkflow:true` отдаёт дальше все items последнего узла саб-воркфлоу; второй Execute Workflow ниже передаёт эту пачку целиком даже при маппинге, не зависящем от items: внутри N одинаковых items, справочник Sheets делает N чтений и упирается в 429 — проверяй, сколько items получает саб-воркфлоу.
- Число проводов в Merge меньше или больше `numberOfInputs` — лишние источники отбрасываются молча (третий вход при `numberOfInputs` по умолчанию) — проверяй число проводов.
- `parameters.useDataOfInput` считается с 1, `connections.main[index]` — с 0 — проверяй номер входа.
- Switch без `options.fallbackOutput:"extra"` + `renameFallbackOutput` теряет items, не попавшие ни в одну ветку, — проверяй `connections` узла Switch.
- Дубль провода (два одинаковых connection-объекта на один узел) — каждый item проходит пайплайн дважды — проверяй `connections`.
- Data Table `get` с per-item фильтром `keyValue={{$json.field}}` при N>1 items схлопывает в 1 без ошибки, даже с `executeOnce:false` — проверяй: `returnAll:true` + матчинг по ключу в Code.
- Data Table `returnAll:false` без явного `limit` молча обрезает до 50 — проверяй `limit`.
- Режим Merge при пустых `parameters` через `get_workflow_details` не виден — проверяй подключение обеих веток IF.
- Один огромный item (полная история, HTML) роняет исполнение по памяти сервера — проверяй размер item; средства: date-фильтр в запросе, `this.helpers.httpRequest` с HTML локальной переменной, `runOnceForAllItems` + `$input.first()`, изоляция через Execute Workflow.

### Выражения и HTTP
- Поле с `=` без двойных фигурных скобок (`"=1+1"`) сохраняется и исполняется как текст, `validate_workflow` этого не ловит — проверяй сохранённый JSON: `"={{ … }}"`.
- Динамическое тело HTTP (с выражениями) через Raw даёт двойную сериализацию, запрос тихо битый (наблюдалось начиная с 2.20.9) — проверяй: JSON mode + Use Expression, `{{ {} }}` без ведущего `=` и без `JSON.stringify()`.
- `=[object Object]` в ошибке тела запроса значит, что выражение обёрнуто дважды — проверяй, что `=` и `{{ }}` стоят один раз.
- Скобки `{{ }}` внутри выражения не вычисляются: `={{ "x{{ 1+1 }}y" }}` падает «invalid syntax» — проверяй, что строка собрана сложением строк JavaScript внутри одной пары скобок.
- Явный Response Format JSON на HTTP-узле даёт ошибку circular — проверяй: Response Format = Autodetect, Include Headers выключен.
- Узел Telegram без `parse_mode` разбирает текст как Markdown и падает «can't parse entities» на подчёркивании в именах воркфлоу, листов, полей — проверяй `parse_mode` HTML.
- Токен, вставленный прямо в поле Value, не используется («never used») — проверяй ввод через fx (Expression).
- HTTP-узел заменяет `json`: поля предыдущих узлов пропадают — бери их через `$('Нода').all()[i]` по позиции.
- После второй Sheets-ноды в цепочке выход несёт только её схему — бери поля предыдущих узлов через `$('Имя').item`.
- Сопоставление по позиции после Merge, фильтра, Switch или узла, меняющего число или порядок элементов, молча путает результаты двух потоков; модель может вернуть неверный id — проверяй сопоставление по ключу объекта (например `review_id`).
- `onError=continueErrorOutput` с неподключённым output(1) молча выбрасывает сбойный элемент: 7 ответов на 8 конфигов, сопоставление по индексу съезжает, `pairedItem` этого не ловит — проверяй длину входа и выхода с `throw`.
- `continueRegularOutput` делает ошибку «обработанной»: воркфлоу ошибок по этому узлу не сработает никогда — проверяй, что ниже читают code/error.
- `neverError:true` пропускает ошибку внешнего API как валидный item (при 401, 429, 5xx код ниже получает undefined, фолбэк даёт пустой массив, сбой читается как «новых объектов нет») — проверяй тело следующим узлом.
- HTTP 200 и статус `success` не доказывают, что данные пришли или записались: отказ лежит в теле (отключённый метод отвечает 200 с ошибкой в теле, воркфлоу месяцами пишет ноль строк), запись карточки отвечает 200, меняет метку изменения и оставляет прежний документ, одна ошибочная карточка отклоняет всю пачку — проверяй тело и перечитывай объект и журнал ошибок API.
- Ответ своего вебхука с зашитым `{"success":true}` или режим «ответить сразу» говорит вызывающему «готово» до исполнения — проверяй, что ответ строится из результата последнего значимого узла.
- Кода ответа в выходе HTTP-узла нет без `options.response.response.fullResponse: true` (тогда `statusCode`, `statusMessage`, `headers`, тело; с `neverError: true` можно ветвиться по коду); объект ошибки при `continueRegularOutput` несёт `message`, `code`, `status`, поля `httpCode` нет — проверяй, по какому полю ветвишься.
- Пустое тело ответа даёт элемент `{}` без поля вовсе — проверяй «чтение не состоялось» как «поля нет» или «поле пустое».
- Настройки ответа с одной вложенностью (`options.response.responseFormat`) сохраняются без ошибки и не действуют — проверяй двойную: `options.response.response.{responseFormat, fullResponse, neverError, outputPropertyName}`.
- Встроенный узел GitHub при правке файла сам берёт `sha` перед записью: чужая дозапись между чтением и записью теряется без конфликта — пиши файл HTTP-узлом с явным `sha` прочитанной версии.
- Длинное сообщение Telegram (больше 4096 знаков) доходит без хвоста без ошибки — проверяй число перечисленных объектов против найденных.
- Без `options.timeout` HTTP-запрос ждёт минутами и держит воркер до `connect ETIMEDOUT` операционной системы; 10000 мс в описании узла — умолчание поля при добавлении, а не действующее значение — проверяй поле в JSON.
- `options.timeout` ограничивает только ожидание заголовков: медленное тело не обрывает (узел отработал дольше таймаута) — проверяй время тела.
- `connectionTimeout` Postgres на зависший запрос не действует, у Telegram поля таймаута нет — проверяй выход ошибки.
- `retryOnFail` ретраит на любую ошибку без фильтра по коду; движок режет до 5 попыток и 5000 мс между ними — при 429 по квоте все попытки ложатся в ту же минуту и ускоряют исчерпание — проверяй ветку Wait ≥60 секунд.
- n8n не отличает «запрос не дошёл» от «дошёл, а ответ потерян»: повтор при обрыве и таймауте даёт двойное действие — проверяй, что повтор выключен на меняющем запросе.
- Параметр пагинации типа body с именем вложенного поля через точки (`settings.cursor.updatedAt`) молча повторяет первую страницу — проверяй число разных ключей против числа строк; форма: один параметр с именем верхнего поля тела и выражением, отдающим объект целиком, курсор из `$response.body.cursor`.
- `last_id=""` тянет с начала — проверяй стартовое значение курсора.
- Запись в Postgres `INSERT … ON CONFLICT DO UPDATE SET` без какой-то колонки в `SET` оставляет её старой при отчёте об успехе — проверяй перечень колонок (признак — устаревшая метка у живых объектов).
- `not_found_error` от API Anthropic значит «модель снята с обслуживания», а не «ключ неверен» — проверяй идентификатор модели.

### Время
- Без `settings.timezone` Schedule Trigger трактует cron как время часового пояса сервера; смещение зоны с переводом часов против Москвы разное летом и зимой — расписание уезжает дважды в год — проверяй явную таймзону.
- `new Date(строка)` неизвестного формата даёт `Invalid Date` без ошибки, запись молча выпадает из окна; Google Sheets в FORMATTED_VALUE отдаёт час без ведущего нуля («2026-09-28 6:53:35») — проверяй разбор регулярным выражением по всем встреченным форматам.
- Дата, легшая в таблицу текстом, выключает условное форматирование и сортировку без ошибки — проверяй, что Sheets распознал дату (текст ГГГГ-ММ-ДД распознаётся).
- Два воркфлоу на одном cron-времени не синхронизированы: читатель в начале минуты читает раньше, чем писатель дописал, — проверяй, нет ли нехватки записей последних минут.

### Google Sheets
- Квота чтения `ReadRequestsPerMinutePerUser` (60 в минуту) считается на потребителя ключа (проект GCP): все воркфлоу и узлы на одном сервисном аккаунте делят один счётчик, 429 бывает и при разрыве больше 5 минут; чтение без `executeOnce` = N запросов — проверяй тело ошибки и число входных items.
- Выбор листа в режиме `list` со значением `gid=<ID листа>` отвечает «Sheet with ID gid=… not found», хотя лист есть (работает только `gid=0`) — проверяй, что передан голый ID листа.
- `batchUpdate` к Sheets API без `sendBody` отвечает 400 без указания причины — проверяй, что `sendBody` включён.
- gid в интерфейсе врёт (`cachedResultName` — старый снимок) — проверяй реальный gid в `sheetName.value`.
- Несоответствие типа ключа в `matchingColumns` даёт дубли без ошибки; сравнение ключей даёт ноль совпадений («1058.0» против «1058», двойной пробел, кириллические «Т» и «С», число в текстовой колонке) — проверяй тип и коды символов обеих сторон.
- Составной `matchingColumns` (`["k1","k2"]`) сопоставляет по первой колонке и перезаписывает вторую колонку ключа у найденной строки — на листе дубль ключа — проверяй одну колонку ключа.
- Две строки с одним ключом в источнике — поиск молча берёт первую — проверяй уникальность ключа до сравнения.
- `matchingColumns` по колонке, которая может быть пустой, сопоставляет пустое с пустым и пишет в первую чужую строку с пустым ключом — проверяй ключ до записи.
- `null` при `appendOrUpdate` в режиме update молча не записывается, старое значение остаётся — проверяй `""` для очистки.
- Переименованная колонка молча ломает автоматическое сопоставление полей; удалённая строка заголовков сдвигает данные; читатель, переведённый на лист с другими именами колонок, получает пустые поля без ошибки — проверяй читателей по шапке.
- Ошибка в строке заголовков (`#ERROR!` в первой ячейке) даёт мусорные имена полей: значения листа параметров читаются пустыми, пороги становятся нулём — проверяй шапку листа параметров.
- Дубли заголовков на листе: при одинаковых именах побеждает правая колонка и подменяет левую чужими данными — проверяй заголовки на уникальность.
- Append считает ячейку с формулой занятой даже при пустом результате: новые строки ложатся ниже разлива ARRAYFORMULA; запись в колонку с формулой даёт `#REF!` или молча расходится с формулой — проверяй колонки в режиме FORMULA.
- `autoMapInputData`: поле с именем колонки-формулы заменяет формулу значением — проверяй состав полей входа.
- `columns` как `expr()`-строка даёт 1 error-item вместо всех строк — проверяй литеральный объект.
- `appendOrUpdate` по строке со статусами (new → shipped → cancelled) возвращает статус в начальный при повторной записи — проверяй защиту множеством известных ID.
- Накопитель на `appendOrUpdate` не удаляет объект, исчезнувший из источника, — проверяй, что читатель фильтрует по `updated_at`.
- Простой append при упавшем и перезапущенном прогоне дописывает те же строки ещё раз — проверяй `matchingColumns`.
- Узел «delete» без `startIndex`/`numberToDelete` удаляет одну строку начиная со второй, то есть первую строку данных; `startIndex` (typeVersion 4.7) ждёт номер строки как есть («The first row is 2»): `row_number − 1` удаляет строку над целевой, для первой записи — заголовок (защита заголовка скрывает это, пока её не снимут) — проверяй номер строки.
- Номер строки сдвигают ручная правка владельца, ошибка на единицу, удаление без явного диапазона — проверяй ключевую колонку повторным чтением в момент записи.
- batchGet может вернуть листы в другом порядке, чем запрошены, — проверяй имя листа в поле `range`.
- Вертикальная пара «имя — значение» с `row_number` при `appendOrUpdate` перезаписывает соседний порог без ошибки — проверяй, что лист параметров горизонтальный.

### Неизвестное значение и запись «заменить целиком»
- Код молча заменяет то, чего не видит (поле, которое чтение не вернуло; значение, которое не пришло; данные, устаревшие с момента написания), законным: пустым, нулём, умолчанием площадки, «прочим», старым числом — проверяй по объекту.
- Новое значение справочника (новое имя операции площадки) уходит в «прочее», пустая себестоимость считается нулём, прибыль завышена молча — проверяй отдельное состояние для неизвестной категории и пустого поля.
- Признак, собранный по накопителям одного источника (кабинета), ложен для объекта, который есть только в другом, — проверяй покрытие источников.
- Отчёт по снимку при нуле объектов молча показывает ноль: «объектов нет» неотличимо от «снимок не создан» — проверяй строку-маркер.
- Запасная константа `|| <число>` прячет пустое чтение, пока число в листе совпадает с константой; после смены значения расчёт идёт по устаревшему числу — проверяй, что константы нет.
- «Вчера» от даты прогона: упавшая ночь не догружается никогда — проверяй окно от последней успешной метки.
- Эндпоинт, заменяющий объект целиком, стирает поле, которого чтение не вернуло; у флага встаёт умолчание; площадка может вычислить непереданное поле заново; повторная запись правильного значения может быть принята с 200 и не примениться — проверяй чтение записанного объекта на одном пробном объекте.
- Одноразовый воркфлоу с данными в коде при перезапуске перезаписывает новые значения старыми — проверяй источник данных записи.
- Смена правила нормализации меняет хэши всех затронутых текстов: проверка «изменилось ли» показывает ложные изменения с обеих сторон — проверяй режим «пересчёт хэшей».

### Ключи и периметр
- Автопривязка MCP берёт самый недавно отредактированный ключ подходящего типа; при нескольких ключах типа (Google, маркетплейсы, Header Auth) попадание случайно; имя в `newCredential('Name')` её не направляет — проверяй `autoAssignedCredentials`.
- Ручная привязка в редакторе тянет нормализацию конфига и побочную публикацию при Save — проверяй `active` и прогон.
- Снимок `registry/n8n-map.md` привязывает тип credential к воркфлоу, а не к узлу: тип `httpHeaderAuth` у воркфлоу не доказывает, что литерал из узла убран, — проверяй по узлу.
- Ключ, хоть раз сохранённый литералом в теле узла, остаётся в истории версий (`workflow_history`) и после перевода в credential — проверяй и перевыпускай у выдавателя.
- Отсутствие литерала в узле не значит верный ключ: узел может слать ключ на чужой домен; Allowed HTTP Request Domains «All» отправит ключ куда угодно — проверяй домен узла против ключа.
- Список потребителей ключа по снимку не ловит литерал в тексте узла и в старых версиях: потребитель вне списка падает после ротации — проверяй перебором базы.
- Удаление ключа в n8n не отзывает ключ у сервиса — отзывай у выдавателя.
- Один ключ в нескольких воркфлоу — ротация затрагивает все сразу — проверяй всех потребителей.
- Вебхук без аутентификации запускает воркфлоу для любого, кто знает адрес; опубликованная форма без аутентификации — то же (у пишущего вовне воркфлоу — боевая запись любым) — проверяй периметр; счёт по строкам HOOK видит только вебхуки, формы ищи по `formTrigger` в строках W.
- Header Auth (и любая аутентификация вебхука или формы) проверяется на HTTP-запросе: вызов через MCP `execute_workflow` без заголовка проходит штатно — проверяй «кто может вызвать» с учётом всех сессий Claude.
- Запрос к своему вебхуку по публичному домену уходит на reverse-proxy, как внешний: своя защита периметра блокирует и чужой, и свой вызов — проверяй хост в URL.
- Право ключа видно часто лишь при первой записи (403 «read-only token») — проверяй до боевого режима.

## Куда писать результат

- Правило, привязанное к версии n8n, — записывать вместе с версией, на которой его наблюдали.
- Сведения о снятом с публикации воркфлоу — `NOT_TAKEN.md` проекта или его журнал; строка о снятии — в паспорт (Skill `n8n-workflow-passport`).
- Открытый по решению Андрея вебхук — причина в паспорт воркфлоу.
- Отсутствие `PASSPORT:` в `description` — записать как долг.
- Особенности конкретного воркфлоу, сервера, книги, кабинета — в паспорт и канон их проекта; адреса — по Skill `n8n-workflow-registry`.
