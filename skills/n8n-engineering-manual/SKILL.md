## 0. Две аксиомы

Всё остальное в этом Skill — частные случаи двух утверждений. Если правило кажется странным, оно выводится из одной из этих аксиом; если новый факт не выводится ни из одной — это кандидат в новый корень.

### A1. Ни один отчёт инструмента не является доказательством состояния

Доказательство существует в двух видах и только в двух: **объект воздействия** (строка появилась в целевой таблице, изменился Doc, выросла таблица в БД) и **факт исполнения** (`get_execution` по реальному прогону). Всё прочее — отчёт инструмента о себе, а не о системе.

**A1 — закрытая константа, а не вывод, который каждая сессия обсуждает заново.** Правило «запись недостоверна, пока её не перечитали независимо» пересмотру не подлежит, пока не предъявлен объект-опровержение — наблюдённый случай, который эта аксиома не объясняет. Повторная проверка того, что уже закрыто, — лишняя цена, а не осторожность. [основание: MAIN-01]

Наблюдавшиеся частные случаи — все до единого приводили к ложному выводу:

| Отчёт, который врёт | Что он на самом деле значит | Корень |
| :-- | :-- | :-- |
| MCP пишет «...credentials must be configured manually» | Безусловный шаблонный текст, печатается всегда | R1a |
| `get_workflow_details` не показывает поле `credentials` у узла | Отсутствие поля не доказывает отсутствие ключа: поле приходит с id и именем ключа, но проверено не на всех типах узлов. А имя ключа в поле не доказывает, что ключ рабочий | R1a |
| `validate_workflow` и `update_workflow` прошли без ошибок | Схема валидна; применились ли параметры — неизвестно. Настройки воркфлоу, переданные в коде воркфлоу целиком, не применяются вовсе | R1b |
| HTTP 200 от внешнего API | Запрос дошёл; отказ может лежать в теле, запись может не примениться | R4 |
| `triggerInfo` от MCP | Сам себе противоречит: в одном ответе «triggerCount 1» и «no production triggers». Публикацию проверять по `active` и `activeVersionId` | R2 |
| Список воркфлоу без поля `description` | Ответ списка поля не несёт; строку `PASSPORT:` искать через `search_workflows` или `get_workflow_details` | §2.2 |
| `active: true` | Что-то исполняется; совпадает ли оно с видимым в редакторе — неизвестно | R2 |
| execution со статусом `success` | Движок не упал; данные могли не записаться | R4 |
| Имя параметра в JSON | Не описывает семантику флага, иногда описывает выключенное состояние | R17 |
| У узла нет параметра (например `parameters.operation` у Google Sheets) | Отсутствие параметра — не «операции нет», а умолчание интерфейса; что узел делает, смотреть в редакторе или по прогону (не перепроверено) | R17 |
| `description` воркфлоу | Гипотеза автора о воркфлоу, не его поведение | §9 |
| Веб-сниппет, память сессии, вчерашний ID | Кэш неизвестного возраста | §9 |

[основание: MAIN-02]

**Практическое следствие для диагностики: диагностика по факту исполнения всегда приоритетнее диагностики по конфигурации.** Читать `get_execution` и объект воздействия прежде, чем строить гипотезы по `get_workflow_details.nodes` и по тексту предупреждений. Когда о воркфлоу нужен ответ на вопрос, а не его текст для правки, описание воркфлоу целиком (при сумме узлов всех воркфлоу задачи больше 100) и выдача исполнения грязного воркфлоу отдаются посреднику — решение до вызова (`second-brain-engineer`, Р21); воркфлоу, который правишь, читаешь сам. Почему: конфигурация и предупреждения — тоже отчёт инструмента о себе.

Частный случай — тест правки: прогон доказывает правку, только если в нём есть случай, который обязан пройти, и случай, который обязан отказать, и путь прогона идёт через исправленную ветку *(T4 качество 7)*.

### A2. Штатный режим отказа n8n — тишина, а не ошибка

Для движка «ноль items», «поле пропущено», «параметр не применился» — не аварии, а нормальные исходы. Ошибка приходит громко; потеря приходит молча. Поэтому каждая запись и каждая правка требуют отдельной сверки того, что предполагалось изменить.

| Что теряется молча | Корень |
| :-- | :-- |
| Вся цепочка ниже, если на ноде 0 items | R3 |
| Сбойный item на `continueErrorOutput` с неподключённым output(1) | R5 |
| Поле, которому передан `null`, при Sheets `appendOrUpdate` | R6 |
| `maxTries` / `waitBetweenTries`, записанные кодом SDK | R1b |
| Ветка IF/Switch и fx-режим выражения после записи воркфлоу кодом целиком | R1b |
| Таймзона и воркфлоу ошибок после записи воркфлоу кодом целиком, даже записанные в коде | R1b |
| Поле с `=` без двойных фигурных скобок — исполняется как текст | §4.8 |
| Все элементы, кроме первого, на узле с Execute Once | §4.3 |
| Непрочитанное значение, ставшее нулём, «прочим» или «пустым днём» | R19 |
| Третий вход Merge при `numberOfInputs` по дефолту | R9 |
| Items, не попавшие ни в одну ветку Switch без fallback | R8 |

## 1. Инфраструктура

**Факт об экземпляре — с экземпляра, в момент использования.** Адрес инстанса, версия n8n, часовой пояс сервера, способ развёртывания здесь не записываются: адрес и сервер — `registry/projects.md` (строка SERVER) и канон SERVER; часовой пояс сервера — поле tz снимка `registry/n8n-map.md` (значение `instance` значит «пояс сервера», расшифровка — `projects/n8n-map/PLAN.md` раздел 4); версия — `get_instance_context` или окно About в редакторе. Правило, привязанное к версии, пишется вместе с версией, на которой его наблюдали, — как в §4.8 про двойную сериализацию тела. Почему: число, набитое руками, устаревает незаметно, и решение, принятое по нему, оказывается неверным. Часовой пояс сервера — причина R7. [основание: MAIN-03]

Инвентарь подключений (ID таблиц, Client-Id, параметры credential, состояние pgvector) — **n8n-workflow-registry**, здесь не дублируется. Одно правило здесь всё же стоит, потому что ошибка необратима: модель эмбеддингов, которой пишутся и ищутся векторы базы знаний, совпадает с моделью, которой база проиндексирована, — какая это модель и размерность у конкретной базы, назначает n8n-workflow-registry. Почему: другая модель даёт другую размерность векторов, и база требует полной переиндексации. [основание: MAIN-04]

### 1.1 Webhook — никогда через curl/bash

**Вебхук своего инстанса из сессии Claude вызывается только `n8n:execute_workflow` через MCP.** Почему: egress-прокси облачной сессии блокирует домен инстанса; curl и bash до вебхука не доходят. [основание: MAIN-05]

**Форма вызова:** параметр `triggerNodeName` — точное имя узла-триггера в этом воркфлоу (например `01_Webhook`, `Webhook`, `01_Form`), плюс `inputs` вида `{webhookData: {method: "POST", body: {...}}}` для вебхука или `{formData: {...}}` для формы, БЕЗ поля `type`. Признаки неверной формы: вызов с `inputs.type` отвергается ошибкой «Unrecognized key(s) in object: 'type'», вызов без `triggerNodeName` — ошибкой «Provide triggerNodeName when passing inputs». Описание инструмента в клиенте Claude может ещё показывать старую схему с `type` — верить ошибке сервера, а не описанию: сервер MCP меняет форму раньше, чем клиент обновляет описание. Имя триггера брать из `get_workflow_details` или из сигнатуры в `registry/tools.md`, не угадывать. Не путать: `inputs.type=webhook` без `triggerNodeName` — прежняя форма, сервер её больше не принимает; поле с другим именем (например `payload` вместо `webhookData`) давало молчаливый `status:error`. [основание: MAIN-06]

**`executionMode` — только `manual`.** В `production` webhook-воркфлоу не создаёт видимого execution: ни `get_execution`, ни `search_executions` его не находят, тело ответа не возвращается. Наблюдаемость есть только в manual *(→ R4)*. [основание: MAIN-07]

**`get_execution` требует ОБА параметра — `workflowId` и `executionId`.** Без `workflowId` сервер отдаёт «not found» даже для реального успешного прогона в любом режиме, включая manual. Симптом неотличим на глаз от истинной нетрейсируемости R4, поэтому прежде чем записать «not found» как подтверждение R4 — проверить, что переданы оба параметра. [основание: MAIN-08]

## 3. Соглашения именования

Почему соглашение: имя — единственное, что видно в списке воркфлоу и на графе без открытия узла; по нему ищут вызывающих, читателей и паспорт.

- Воркфлоу: `[Источник] [Тип] [Действие]` — например «<площадка> RAW <данные> Sync», «<площадка> Reviews Response».
- Ноды: `NN_Название` (двузначный номер). Параллельные ветки — `06A_`, `06B_`.
- Google Sheets: snake_case — например `<источник>_raw_report_V2`, `<сущность>_history`.

[основание: MAIN-09]
- `raw_key` — композитный ключ строки RAW, свой на каждый источник. Форматы намеренно разные, RAW-слои не объединяются, сравнение между источниками — по Артикулу. Конкретные формулы ключа по источникам и эндпоинтам — n8n-workflow-registry §3.

## 8. Неустранимые особенности платформы

Дизайном не убираются, помнить.

- **Прунинг исполнений обязателен (`EXECUTIONS_DATA_PRUNE`).** Без него база данных исполнений растёт без предела. Следствие для отладки: инстанс, который не сохраняет данные успешных прогонов (`EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`), не показывает их в списке исполнений вовсе — пустой список не значит, что воркфлоу не работал *(R4)*. Какие значения стоят на инстансе сейчас — `projects/n8n/STATE.md`. [основание: MAIN-10]
- **Второго канала верификации записи не существует.** Воркфлоу, перечитывающий результат записи у себя в коде, при production-запуске через MCP не возвращает ответ вызывающему, а `get_execution` по такому запуску отдаёт «not found». Не путать «в коде есть read-back» с «я видел результат read-back» *(A1)*. [основание: MAIN-11]
- **Воркфлоу ошибок и явная таймзона — не по умолчанию.** Новый воркфлоу их не получает сам; запись воркфлоу кодом целиком снова сбрасывает уже стоящие, точечные операции `update_workflow` их не трогают, а операция `setWorkflowSettings` их ставит — в том числе массово *(R1b)*. Поэтому T2 слой 4 и гейт T4 качество 8 — правило, а не факт об инстансе: сколько воркфлоу их не имеют, считать заново по строкам W снимка `registry/n8n-map.md` — поле 8 таймзона, поле 10 воркфлоу ошибок; последний пересчёт — задача `labs/sys/t-failure-visibility.md`, снята 2026-10-21 (текст — в истории коммитов). Не путать: массовое назначение `setWorkflowSettings.errorWorkflow` доступно — прежняя запись «только с версии 2.29.0» опровергнута исполнением. [основание: MAIN-12]
- **Воркфлоу ошибок не ограничивает частоту алертов** — падающий каждые 15–30 минут воркфлоу засыпает Telegram *(T2 слой 4)*. [основание: MAIN-13]
- **Drive MCP `create_file`:** write-scope коннектора периодически отваливается (чтение при этом работает) → создать Doc вручную, заполнить через gdocs-overwrite (у него независимый OAuth); переподключение коннектора — только в новой сессии. Дом правила — google-drive-docs, references/failures.md, строка E14. [основание: MAIN-14]
- **Файл, куда пишет сервис-аккаунт, должен быть ему расшарен (Editor).** Признак: `success:false`, `bytesRead:0`, «file not found OR not shared to SA». Проверять `get_file_permissions` ДО первой записи. Дом правила — google-drive-docs, references/infra.md, раздел 6.2. [основание: MAIN-15]
- **Квота Sheets — на потребителя credential, не на воркфлоу** *(R6)*.
- **Переменные инстанса (`$vars`) инструментами n8n MCP не перечисляются** — список виден только в интерфейсе (Settings → Variables). [основание: MAIN-16]
- **Бэкап базы n8n без ключа шифрования (`N8N_ENCRYPTION_KEY`) не восстанавливает ключи доступа: credentials в базе зашифрованы этим ключом.** Основание: решение Андрея 2026-10-20.

## 9. Принципы проектирования

Не правила механики (те в §4–§6), а решения о форме системы. [основание: MAIN-17]

- **RAW first, separation of concerns.** RAW ≠ аналитика, разные слои и разные воркфлоу. Почему: фильтр в RAW теряет данные безвозвратно, а аналитику поверх RAW можно пересчитать *(§4.1)*.
- **Propose before implement.** Вариант на согласование раньше записи. Почему: запись в воркфлоу меняет больше, чем видно в правке (A2), и откат дороже обсуждения; полномочия — second-brain-engineer, раздел Р10.
- **Параметры там, где используются** — в книге или листе того воркфлоу, который их читает, а не в общей панели управления на все воркфлоу. Почему: общая панель связывает несвязанные воркфлоу и прячет, кто читает параметр.
- **Намерение должно читаться на графе.** Сознательный терминал ведёт в именованный NoOp или оформляется узлом Filter с говорящим именем, а не висит в пустоте *(T1-D)*; один путь лучше fan-in, который потом надо объяснять словами. Почему: неподключённый выход и забытый провод на графе выглядят одинаково.
- **Неизвестное — не ноль.** Значение, которое не пришло или не распозналось, получает явное состояние «неизвестно» и сигнал, а не становится нулём, «прочим» или «пустым днём»; и не роняет основной поток, если тот делает другую нужную работу *(R19)*.
- **Ненужный воркфлоу снимается с публикации, но не архивируется и не удаляется**: зонд и пробный воркфлоу — это инструмент, который понадобится снова. Снятие проверяется чтением `active:false` *(§2.5)*.
- **Запись во внешний кабинет — два режима на одном пути**: «проверка» без записи и «боевой» по «да» на конкретный список; воркфлоу не публикуется *(T5)*.
- **Секрет — только в credential.** Ключ создаёт владелец и присылает название; значение не проходит через чат, узел и репозиторий *(§2.1)*.
- **Узел выбирается по свойствам, а не по удобству**, когда воркфлоу существует ради конкретного ресурса (контекст, квота, память) — см. R4 про `contextData` и R6 про счётчик квоты.
- **Негативный тест на сбойный элемент ставить в СЕРЕДИНУ проверочного списка, не последним:** поставленный последним, сдвиг индексов не проявляется, и тест физически не может провалиться по нужной причине *(R5)*.
- **Правило Skill — рамка, а не закон.** Если рамку нужно сдвинуть и это обосновано — сдвигать, зафиксировав чем именно; стопориться на формулировке хуже, чем осознанно от неё отступить. Граница: рамку сдвигают открыто и с названной причиной, а критерий приёмки задним числом не смягчается (second-brain-engineer, references/design.md, пункт 15). [основание: MAIN-18]
