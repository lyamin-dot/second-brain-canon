## 2. Запись через MCP

### 2.1 Порядок создания и правки

1. `get_sdk_reference` — документация
2. `search_nodes` + `get_node_types` — точные параметры нод
3. `validate_workflow` — схема
4. `create_workflow_from_code` / `update_workflow`
5. `publish_workflow` — обязательно, иначе исполняется старый код

**Вебхук создаётся закрытым — с первой записи, а не «закрою потом».** Любой новый воркфлоу с webhook-триггером уже в первом `create_workflow_from_code` несёт в коде триггера параметр `authentication: "headerAuth"`. Воркфлоу с триггером без этого параметра не создаётся вовсе — не «не публикуется», а именно не создаётся. Причина: гейт 5 чек-листа T4 стоит у публикации и работает, только если T4 прогнан; Git Write, созданный 01.09, по летописи git-migration на 16.09 всё ещё был открыт. Порядок для нового вебхука:
- в коде триггера `authentication: "headerAuth"`; при каждом последующем `update_workflow` параметр переносится в код заново *(§2.2 п.4, R12)*;
- credential типа Header Auth привязывается к триггеру руками в редакторе сразу после создания и до первого `publish_workflow` — адресно привязать credential через MCP нельзя *(R1a)*. Ключ — отдельный, под этот вебхук или эту группу, а не общий ключ другого назначения *(R12)*. Какой credential брать — n8n-workflow-registry §2; если там о нём ничего нет — спросить Андрея, а не заводить новый молча;
- каждый HTTP Request-узел, вызывающий этот вебхук, адресуется по имени docker-сервиса *(R14)* и несёт тот же credential через `httpHeaderAuth` *(R13)* — иначе закрытие вебхука ломает собственный межворкфлоушный вызов;
- после публикации `triggerInfo` содержит «This webhook requires a header…» *(§2.3 п.2)*.
Открытый вебхук допустим только по прямому решению Андрея — например, для внешнего сервиса, который не умеет слать заголовок; причина записывается в паспорт воркфлоу. Граница: закрытый вебхук не закрывает вызов из сессий Claude через `execute_workflow` *(R15)* — защищается интернет-периметр, а не сам воркфлоу.

**Секрет не проходит через чат, текст узла и репозиторий — никогда.** Ключ доступа создаёт сам владелец в редакторе n8n (Credentials) и присылает в чат только его название; сессия привязывает ключ к узлу по названию (руками владельца, если узел новый, — R1a). Значение ключа в теле узла, в константе Code-узла, в сообщении чата или в файле репозитория (он публичный) — долг безопасности, даже если «временно» (`projects/deklaration-wb/STATE.md`, договорённость 2026-10-07 о ключе «Честного знака»; `projects/n8n/STATE.md` — литералы ключей Ozon и Anthropic в узлах, ключ до сих пор не ротирован). Механизм и формы перевода литерала в credential — R13. Имя нового ключа — по правилу имени и его исключениям, которые описаны в n8n-workflow-registry (книга учёта ключей), здесь не повторяются.
Ключ выдаётся с минимально нужным правом: для воркфлоу, который только читает, — ключ только на чтение. Право ключа часто видно лишь при первой записи (ответ 403 «read-only token»), поэтому проверяется до боевого режима, а не в нём (журнал `projects/deklaration-ozon/LOG.md` записи Р-22, Р-30, Р-40; `projects/deklaration-wb/LOG.md` записи Р-5, Р-6). Как узнать права ключа по каждой площадке — n8n-workflow-registry §3. Второй кабинет (другое юридическое лицо) — отдельный воркфлоу со своим ключом, а не переключатель внутри существующего: ключ узла задан статически, и сбой одного кабинета остановил бы другой (deklaration-ozon Р-40).

`availableInMCP` включается только на опубликованном воркфлоу. Перед вызовом незнакомого воркфлоу — проверить флаг через `get_workflow_details`.

`update_workflow` **не публикует**: черновик живёт до `publish_workflow`. Для активного воркфлоу одного `publish` недостаточно — нужен полный тумблер *(R2)*.

### 2.2 Пред-полётный чек-лист

Прогонять ПЕРЕД `update_workflow`, не после публикации. Смысл — зафиксировать текущее состояние полей, уязвимых к перезаписи, чтобы после записи было с чем сверять.

1. Выписать ветки `connections.<IF/Switch>.main` — до правки. *(R1b)*
2. Выписать `matchingColumns` и реальный gid у Sheets-нод. *(R6)*
3. Выписать fx-выражения в IF/Switch — они могут стать строковыми литералами. *(R1b)*
4. Выписать `authentication` у webhook-триггера И перенести это значение в передаваемый код: `update_workflow` пересобирает КАЖДЫЙ узел из переданного кода, включая триггер, и если в коде узла нет параметра `authentication`, аутентификация слетает и вебхук становится открытым без предупреждения. *(R12)* Там же выписать `webhookId` каждого узла-вебхука — полная пересборка может сменить его и у нетронутого узла. *(R1b)*
4а. Выписать настройки воркфлоу: `settings.timezone`, `errorWorkflow`, `saveDataSuccessExecution` — SDK их не применяет, даже если они в коде, и после записи их придётся выставить руками в редакторе. *(R1b)*
4б. Выписать имена узлов с привязанным ключом и их ключи (поле `credentials` в `get_workflow_details`). Узел с ключом в переданном коде не переименовывать — привязка рвётся по имени. *(R1a)*
5. Закрыть вкладку редактора этого воркфлоу — гонка в обе стороны, last-write-wins: MCP перетирает ручную настройку *(R1b)*, ручной Save нормализует MCP-конфиг и может заодно опубликовать воркфлоу *(R17)*.
6. Прочитать `description` целевого воркфлоу: при `PASSPORT: <id>` — прочитать паспорт до правки (шаблон — n8n-workflow-passport). Отсутствие `PASSPORT:` — зафиксировать как долг, работу не блокировать.
7. Больше трёх затрагиваемых нод за раз — требует подтверждения Андрея (владелец правила — second-brain-engineer, ЗАПРЕТ 2).

### 2.3 Пост-полётная сверка

Обязательна после КАЖДОГО `update_workflow`, не только первого: потери R1b рецидивируют — одна и та же ветка теряется повторно.

1. Сверить всё, что выписано в §2.2, со свежим `get_workflow_details`.
2. У webhook с аутентификацией — сверить `triggerInfo`: строка «This webhook requires a header…» должна остаться, а не смениться на «No credentials required».
3. Нестандартные поля (`maxTries`, `waitBetweenTries` и подобные) — сверить сохранённый JSON узла напрямую: SDK молча отбрасывает часть ключей при валидной записи. *(R1b)*
3а. Настройки воркфлоу (`settings.timezone`, `errorWorkflow`) — сверить с выписанным в §2.2 пункт 4а и при расхождении выставить руками в редакторе ДО публикации. Публиковать воркфлоу по расписанию с потерянной таймзоной нельзя: расписание уедет *(R7)*. *(R1b)*
3б. Условия IF и Switch — каждое выражение должно остаться в двойных фигурных скобках `{{ … }}`; без них условие сравнивает буквальный текст и не срабатывает никогда. Если дефект найден в воркфлоу одной площадки, тем же действием проверить его копии на другой площадке: воркфлоу Ozon, скопированные с WB, наследуют дефекты оригинала. *(R1b)*
3в. `webhookId` каждого узла-вебхука — тот же, что до записи. *(R1b)*
4. Привязку ключей сверить по полю `credentials` у узлов в свежем `get_workflow_details` (с 2026-10-08 поле приходит с id и именем ключа — R1a). Отсутствие поля у узла не доказывает отсутствие ключа: поведение подтверждено не на всех типах узлов. Окончательная проверка — реальный прогон.
   Второе прямое показание, и оно единственное место, где промах автопривязки виден в момент записи: в ОТВЕТЕ `update_workflow` есть поле `autoAssignedCredentials`. Непустое — MCP сам подставил credential, и надо смотреть, какой именно: при нескольких credential одного типа он берёт самый недавно правленный *(R1a)*. Пустое вместе с фразой «their credentials must be configured manually» — автопривязки не было, существующие привязки не тронуты, а НОВЫЕ узлы остались без credential и требуют ручной привязки владельцем. Проверено 2026-09-26 на воркфлоу `gFFiBPm1OomOzJOj`: поле пришло пустым, привязки двух прежних HTTP-узлов уцелели, два новых узла пришлось привязывать руками.
5. `versionId` vs `activeVersionId` — расхождение означает, что правка не опубликована. *(R2)*
6. Результат — по объекту воздействия, не по статусу. *(R4)*

Отдельный запрет: `update_workflow` **не использовать для миграции credential** — перетирает `cachedResultName` ссылок на листы Sheets.

### 2.4 Выбор пути записи

`update_workflow` пересобирает воркфлоу целиком *(R1b)*, поэтому цена правки через него не зависит от её размера: правка одной строки рискует теми же настройками, условиями и `webhookId`, что и переписывание всего воркфлоу. Отсюда выбор пути.

- **Правка одного узла боевого воркфлоу — не полной перезаписью через SDK.** Сессия готовит полный текст кода узла (весь код узла, не фрагмент — §4.2), Андрей вставляет его руками в редакторе. Условия IF и Switch правятся только в редакторе. Источник: журнал `projects/wb-logistics/LOG.md` записи Р-94 и Р-95 (перезапись Order Close, Supply Sync и Order Intake ради одного узла отвергнута — код отдан на ручную вставку), `projects/wb-reviews/LOG.md` запись Р-6 (правка условий эскалации внесена в браузере, потому что MCP превращает выражения IF в строки).
- **Новый воркфлоу или пересборка многих узлов — через MCP**, с полной пред- и пост-полётной сверкой (§2.2, §2.3) и ручной установкой настроек после записи.
- **Неизменяемые узлы и фрагменты при пересборке переносятся скриптом из JSON сохранённого воркфлоу, а не перенабираются моделью.** Модель, набирающая чужой код заново, вносит в него незаметные расхождения. Сохранённый воркфлоу берётся из `get_workflow_details` (большой ответ — файлом), нужные узлы вырезаются скриптом и вставляются в новый код как есть; после записи — сверка этих узлов с исходником байт в байт тем же скриптом (журнал `projects/deklaration-ozon/LOG.md` запись Р-32; `projects/deklaration-wb/LOG.md` запись Р-1).
- **Пробный прогон правки — черновиком, без публикации:** ручной запуск через MCP исполняет черновик, расписание — опубликованную версию *(R2)*. Оговорка: у воркфлоу с триггером расписания `execute_workflow` через MCP идёт через этот триггер, и признаки «ручной запуск» внутри кода не срабатывают — пробность такого прогона задаётся только явным параметром режима *(T5)*.

### 2.5 Снятие с публикации вместо архивации

Воркфлоу, ставший ненужным (зонд, пробный, разовый инструмент, вытесненный новым), **снимается с публикации (`unpublish_workflow`), но не архивируется и не удаляется**. Это инструмент, который, скорее всего, понадобится снова; архивированный воркфлоу MCP не умеет вернуть, его возвращает владелец руками. Сведения о нём — ID, назначение, паспорт, как вернуть (`publish_workflow`) — пишутся туда, где проект хранит невзятое и снятое (для проектов в репозитории — файл `NOT_TAKEN.md` проекта или его журнал). Зонд при этом называется как инструмент: пометки «временный — архивировать после снимка» в описаниях воркфлоу и в журналах не исполняются.
Снятие проверяется чтением: после `unpublish_workflow` — `search_workflows` или `get_workflow_details` показывает `active:false`. Слово «деактивировал», в том числе от владельца, проверкой не является: 2026-10-01 владелец сообщил, что деактивировал воркфлоу, а чтение показало `active:true` (журнал `projects/git-migration/LOG.md` запись Р-126).
Источник правила: решение владельца 2026-10-08 (журнал `projects/deklaration-wb/LOG.md` запись Р-6, строка 6 `meta/PENDING_RULES.md`), по образцу git-migration записи Р-109. Прежняя практика архивации зондов (git-migration Р-101, Р-114; deklaration-ozon Р-15, Р-32; deklaration-wb Р-2, Р-3) этим правилом отменена. В паспорт снятого воркфлоу пишется строка о снятии — дата, причина, как вернуть; форма строки — Skill n8n-workflow-passport.
