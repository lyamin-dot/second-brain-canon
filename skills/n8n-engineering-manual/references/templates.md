## 6. Golden Templates — T1–T5

Общий закон шаблонов: **запись, которую можно повторить, обязана давать тот же объект; отказ, который можно не заметить, обязан стать видимым.** T1 закрывает первое (повтор не плодит дубли и не теряет поля), T2–T4 — второе (ни один отказ не уходит в тишину, ни одна правка не считается сделанной без объекта), T5 — оба сразу для записи, которую нельзя откатить.

### T1 — Идемпотентная запись

**Когда применять T1:** любая повторяемая запись, где возможен повторный прогон (ретрай, backfill, пересечение окон расписания). На append без `matchingColumns` не полагаться — повторный запуск дублирует историю (признак: `matchingColumns:[]` на узле записи истории; основание: 1 случай, последний 2026-07-23 — отчёт синтеза, правило T1.0).

**Шаг 0. Выбор инструмента.**
- Нужен только факт «уже видели этот ключ», объём до ~10k, без TTL и метаданных → Remove Duplicates (T1-A).
- Нужно состояние: запрашиваемое, с TTL, со статусом, с историей → Data Table (T1-B).
- Данные читает человек глазами (витрина) → Google Sheets (T1-C).

Принцип: служебное состояние (курсоры, dedup-маркеры, реестры, sku-маппинг) не обязано жить в Sheets — это налог за использование Sheets как БД *(R6)*. Разделение «состояние → Data Table, витрина → Sheets» устраняет корень, а не лечит симптом.

**T1-A. Remove Duplicates.**
```json
{
  "type": "n8n-nodes-base.removeDuplicates",
  "parameters": {
    "operation": "removeItemsSeenInPreviousExecutions",
    "dedupeValue": "={{ $json.raw_key }}",
    "options": { "historySize": 10000 }
  }
}
```
Применять: поток однотипных item, нужен только факт «уже обрабатывали». Нельзя: нужен запрос по состоянию, TTL, ветка «вернуть из кэша».

**T1-B. Data Table.** Форма: Get → IF → [обработать новое / вернуть известное].
1. На Get: `alwaysOutputData:true` на уровне config ноды, не внутри `parameters` — иначе no-match даёт 0 items *(R3)*. Эталонная форма узла Get: `executeOnce:true` вместе с `alwaysOutputData:true` на уровне config.
2. Обе ветки IF отдают одинаковую форму JSON — нужен нормализующий anchor-узел.
3. Многоколоночный фильтр — явно `matchType:"allConditions"`.
4. `returnAll:false` без явного `limit` → дефолт 50 → тихое обрезание.
5. Форму Get+IF реализовывать как `returnAll:true` + матчинг в Code-ноде *(§4.12)*.
6. Идемпотентные маркеры требуют TTL-уборки: отдельный воркфлоу, удаляющий строки старше окна ретраев.

**T1-E. Очередь со статусами** (строка ждёт обработки: отзыв, заказ, задание). Буква E — следующая свободная: нумерация append-only.
- **T1-E.1** Отбор к обработке — белым списком статусов («пусто» или `new`), не чёрным («не `done`»). Почему: новый статус, появившийся позже, иначе молча уходит в обработку не той веткой. [основание: TPL-01 · правило T1-E.1]
- **T1-E.2** У очереди есть конечный статус для того, что обрабатывать не нужно (`rejected` — спам, неисправимые данные). Почему: без него строка остаётся в промежуточном статусе, и каждый прогон берёт её снова. [основание: TPL-02 · правило T1-E.2]
- **T1-E.3** «Уже виденное» отличается по ключу из множества виденных, а не по отсутствию поля. Почему: если в лист виденного пишется полная строка, признак «поля нет» не срабатывает никогда, и множество всегда пусто. [основание: TPL-03 · правило T1-E.3]
- **T1-E.4** Запись в Postgres через `INSERT … ON CONFLICT DO UPDATE SET` перечисляет в `SET` все обновляемые колонки. Почему: пропущенная колонка остаётся старой при отчёте об успехе. Признак: устаревшая метка у живых объектов. [основание: TPL-04 · правило T1-E.4]

**T1-C. Google Sheets — витрина (предпочтительная форма).**
```json
{
  "operation": "appendOrUpdate",
  "columns": {
    "matchingColumns": ["raw_key"],
    "mappingMode": "autoMapInputData"
  }
}
```
Предпочитать T1-C над T1-D всегда, когда бизнес-логика допускает upsert по ключу: `appendOrUpdate` по ключу без связки delete+merge проще и безопаснее той же задачи через find→IF→delete→wait→merge (основание: 1 случай, аудит 2026-07-23 — отчёт синтеза, правило T1-C.0). T1-C нельзя, если нужно физическое удаление строк, исчезнувших из источника.

Обязательно:
- `columns` передавать ТОЛЬКО литеральным JS/JSON-объектом (`{mappingMode, matchingColumns, schema, attemptToConvertTypes, convertFieldsToString}`) — НИКОГДА не оборачивать в `expr()`-строку. Воспроизводимо: columns как expr-строка → 1 error-item вместо всех строк (272 строки в воспроизведении); литеральный объект → все строки, 0 ошибок.
- `matchingColumns` заданы всегда + приведение типов (parseInt/String) — строка ≠ число не матчится, ошибки нет, растут дубли.
- Составной ключ собирать заранее в Code в одну колонку — мультивыбор `matchingColumns` матчит только по первой.
- Сверять реальный gid (`sheetName.value`), не подпись в UI.
- Read-нода: `executeOnce` + узкий фильтр *(§4.3, R6)*.
- Per-item шаги оборачивать в `splitInBatches(batchSize:1)` *(§4.4)*.
- Поля предыдущих нод после Sheets-ноды брать через `$('Имя').item` — вторая Sheets-нода в цепочке отдаёт только свою схему.
- Очистка ячейки — `""`, не `null` *(R6)*.
- В Code-узлах внутри пайплайна ВСЕГДА spread `({ ...src, newField })`. Собирать item заново из перечисленных полей — тихая потеря: каждую неделю в историю пишется почти пустая строка *(§4.2.2)*.
- Перед первой записью в лист — прочитать шапку и колонки в режиме FORMULA: колонки с формулой не пишутся, шапка — договор с читателями *(R6)*.
- Запись или удаление по номеру строки — только после повторного чтения ключевой колонки в момент записи и сравнения с первым чтением; расхождение — остановка без записи *(R6)*.
- Строка с жизненным циклом статусов — защита от повтора множеством известных ID, а не `appendOrUpdate` *(R6)*.

**Накопитель из внешнего API.** Робот, перезаписывающий накопитель (лист или таблицу, где лежит текущий список объектов площадки) списком из внешнего API, держит четыре правила — прикладная форма R19 и §4.9:
1. Проверяет объём входа до записи: меньше порога (заданного от прошлого объёма) — остановка без записи. Пустой или обрезанный ответ API иначе превращается в «объектов стало мало».
2. Читает до пустой страницы или до отсутствия курсора, а не фиксированным числом страниц *(§4.9)*.
3. Признак «событие обработано» пишет последним, после всех веток записи. Почему: детектор изменений с несколькими независимыми ветками записи не атомарен — прогон, упавший между ветками, иначе теряет событие навсегда: следующий прогон считает его уже обработанным.
4. На `appendOrUpdate` накопитель не удаляет исчезнувшие объекты; читатель фильтрует по свежести (`updated_at`) *(R6)*.
[основание: TPL-05 · правило T1-C.1]

**T1-D. Google Sheets + delete — только если нужна физическая перезапись диапазона.**
```
Find (executeOnce:true, alwaysOutputData:true — top-level)
  → IF (row_number exists?)
       true  → Delete → Wait → Merge input(1)
       false →                 Merge input(1)   ← ОБЯЗАТЕЛЬНО ПОДКЛЮЧЕНА
  → appendOrUpdate
```
**T1-D.1 False-ветку подключать без исключений.** Почему: безопасность неподключённого варианта держится на режиме узла Merge, а режим при пустых `parameters` через `get_workflow_details` НЕ ВИДЕН; архитектуру, корректность которой нельзя подтвердить чтением, нельзя держать шаблоном. Поэтому T1-D и не стал шаблоном по умолчанию.
- Признак дефекта: ветка IF, которую ждёт Merge, отсутствует в `connections`. Проверять по `connections`, а не по `description` воркфлоу: описание может утверждать, что ветка подключена, когда её нет.
- Дефект рецидивирует: ветка, которую чинили, пропадает снова после следующей записи *(R1b)*; воркфлоу-сиблинг с той же архитектурой и обоими подключёнными выходами показывает, что дефект — в связях, а не в архитектуре.
- [основание: TPL-06 · правило T1-D.1]

**T1-D.2 Дискриминатор терминала.** Неподключённый выход IF допустим ТОЛЬКО если он терминал — ниже него никто не ждёт данных (ни вход Merge, ни петля цикла). Сознательный терминал оформляется одним из двух способов, чтобы «терминал» отличался от «забыли провод» прямо на графе:
- IF, ложная ветка которого ведёт в именованный NoOp (`STOP_No_Rows`, `No_New_Items`);
- узел Filter с говорящим именем (`Снимок изменился`): то, что не проходит условие, отбрасывается, ноль items на выходе штатно останавливает цепочку. Один узел вместо двух, и у него нет второго выхода, который можно забыть подключить; правило SDK тоже называет Filter инструментом для отбрасывания items.
Filter годится, только когда отброшенным items действительно некуда идти; если ложной ветке нужна своя обработка — IF с подключёнными обоими выходами.
[основание: TPL-07 · правило T1-D.2]

**T1-D.3 Писатель, который пишет только при изменении.** Гейт записи (Filter) перед записью снимка в хранилище оправдан, когда строитель снимка детерминирован (строки отсортированы): при неизменном источнике текст совпадает с прочитанным байт в байт — и записи нет; свежесть снимка читатель сверяет одним полем (меткой последнего изменения источника). Почему: такой писатель не плодит пустых коммитов и не скрывает, что источник не менялся. [основание: TPL-08 · правило T1-D.3]

### T2 — HTTP и обработка ошибок в проде

**Слой 1. Timeout всегда, retry — по типу ошибки.**
```json
{
  "retryOnFail": true,
  "maxTries": 3,
  "waitBetweenTries": 5000,
  "options": { "timeout": 30000 }
}
```
- **T2.1.1** `options.timeout` — на каждом узле HTTP Request каждого активного воркфлоу: без него запрос ждёт минутами *(R11)*. Он ограничивает только ожидание заголовков ответа. У Postgres и Telegram полного таймаута нет — их защищает выход ошибки (слой 2) *(R11)*.
- **T2.1.2** `retryOnFail` — только на чтении и на записи, которую безопасно повторить. На запросе, который меняет внешнее состояние (публикация на маркетплейсе, ответ покупателю, запись в чужую таблицу), повтор при сбое выключен.
  - Почему: n8n не отличает «запрос не дошёл» от «дошёл, а ответ потерян» — при обрыве и таймауте возможен как раз второй случай, и повтор даёт двойное действие.
  - Такой узел защищают выход ошибки и воркфлоу ошибок, а повторяет его самовосстанавливающийся флаг (T2.1.4).
  - [основание: TPL-09 · правило T2.1.2]
- **T2.1.3** На чтении `retryOnFail` ретраит на любую ошибку без фильтра по коду и лечит только транзиентные сбои (обрыв соединения, таймаут, 5xx). Против 429 по квоте он вреден: попытки ложатся в то же минутное окно и ускоряют исчерпание *(R6)*. Нужен ретрай по коду — делать через выход ошибки + IF по `$json.error.status` + Wait, а не флагом ноды (поля `httpCode` в объекте ошибки нет — §4.8.9). При 429 по квоте Wait в этой ветке — не меньше 60 секунд, дольше минутного окна квоты; пауза в несколько секунд окна не переживает *(R6)*. [основание: TPL-10 · правило T2.1.3]
- **T2.1.4** Записанные через SDK `maxTries` и `waitBetweenTries` сверять в сохранённом JSON *(R1b)*. Движок режет: максимум 5 попыток, максимум 5000мс между. Явный ретрай задаётся всеми тремя полями (`retryOnFail`, `maxTries`, `waitBetweenTries`), а не одним флагом.
- **T2.1.5** Часто лучше ретрая — самовосстанавливающийся флаг: при частом расписании дешевле идемпотентный флаг «обработано» (например метка времени отправки в строке объекта), при сбое объект просто не помечается и подхватывается следующим прогоном.

**Слой 2. Выбор onError.**
- Ошибка реально обрабатывается дальше (алерт, фолбэк, запись статуса) → `continueErrorOutput` И обязательно развести output(1) в реальную ноду. Одно без другого = items испаряются *(R5)*.
- Ошибка не критична, downstream явно читает code/error → `continueRegularOutput`. Ценой того, что нода выпадает из-под глобального errorWorkflow: для n8n ошибка при `continueRegularOutput` считается ОБРАБОТАННОЙ, и errorWorkflow по этой ноде не сработает никогда. Правильная форма: ниже стоит код с try/catch и явным фолбэком, который выводит «ошибка API» прямо в сообщение пользователю.
- Осмысленной обработки нет → оставить дефолт `stopWorkflow` и дать errorWorkflow отработать. Это не лень, а правильный выбор.
- Запрещено: `continueErrorOutput` с неподключённым output(1); выход ошибки, заведённый в no-op или в обработчик, чей собственный выход никуда не ведёт (статус ошибки не записывается никогда); `continueRegularOutput` «чтобы не падало» — единственный способ гарантированно ослепить мониторинг.
- Признаки дефектов: узлы на `continueRegularOutput`, ниже которых никто не читает code/error, при заданном в settings `errorWorkflow` — дыра в мониторинге при формально настроенном мониторинге; голый `continueErrorOutput` — при сбое строка молча исчезает из пайплайна без записи статуса.
- [основание: TPL-11 · правило T2.2]

**Слой 3. Сохранность данных.**
- Поля предыдущих нод после HTTP брать через `$('ИмяНоды').all()[i]` по позиции *(R5)*.
- Первой нодой после HTTP — явная проверка code/error.
- `neverError:true` без последующей явной проверки запрещён: маскирует ошибку внешнего API под валидный item *(R4)*. Признак: при 401, 429 или 5xx код ниже читает поле из тела ошибки, получает undefined, фолбэк даёт пустой массив, и воркфлоу трактует сбой как «новых объектов нет» и молчит. [основание: TPL-12 · правило T2.3]
- `neverError` не гасит ошибку внутри `completeExpression` пагинации *(§4.9.6)*.
- Сверка длины входа и выхода с `throw` — единственная защита от испарившегося item *(R5)*.
- Не полагаться на output Sheets-ноды как на источник полей — читать из именованной исходной ноды (`$('<узел подготовки>')`), а не из выхода Sheets-узла.

**Слой 4. Глобальный error-workflow.**
- **T2.4.1** Назначается в настройках каждого воркфлоу; массово — операцией `setWorkflowSettings`. Запись воркфлоу кодом целиком назначение сбрасывает; после любой записи — сверять *(R1b, §2.3 пункт 3а)*. [основание: TPL-13 · правило T2.4.1]
- **T2.4.2** Контроль живости — в две ступени, а не одним прибором на всех. Ступень 1 — воркфлоу, молчание которых стоит денег или решений: воркфлоу ошибок плюс сохранение успешных прогонов (`settings.saveDataSuccessExecution = all`) плюс строка в мониторе ежедневной живости. Ступень 2 — все остальные активные: только воркфлоу ошибок.
  - Почему: n8n по умолчанию не хранит успешные прогоны *(R4)*, поэтому проверка «был ли успех за сутки» без сохранения успехов даёт ложные тревоги, а сохранять успехи всем — рост архива сервера и цены его ежедневной резервной копии.
  - Список ступени 1 — запись Р-4 журнала `projects/n8n/LOG.md`, здесь не дублируется.
  - [основание: TPL-14]
- **T2.4.3** Граница монитора внутри n8n: падение самого n8n (сервер, контейнер) не ловит ни воркфлоу ошибок, ни монитор-воркфлоу — они молчат вместе с n8n. Внешний сторож не строится — это остаток риска, принятый владельцем; не предлагать его заново без нового основания. [основание: TPL-15]
- **T2.4.4** Монитор множества объектов берёт список охвата из источника истины на каждом прогоне, а не из списка, вписанного в код. Почему: объект вне списка выглядит здоровым. [основание: TPL-16 · правило T2.4.4]
- **T2.4.5** Правила самого error-воркфлоу: никаких внешних вызовов, способных упасть; быстрый (выполняется синхронно и тормозит исходный сбой); канал уведомления отличный от мониторимых.
- **T2.4.6** Минимальный алерт: имя воркфлоу, ID, ссылка на редактор, ссылка на прогон, `lastNodeExecuted`, реальный `error.message`, время. Что фактически несёт алерт воркфлоу ошибок инстанса — паспорт этого воркфлоу и канон проекта n8n.
- **T2.4.7** Проверка после настройки: заведомо падающий воркфлоу (HTTP на битый URL, без обработки) → прогнать → убедиться, что алерт дошёл. По факту прихода сообщения, не по логу.
- **T2.4.8** Воркфлоу ошибок не ограничивает частоту алертов: воркфлоу, падающий каждые 15–30 минут, засыпает канал уведомлений (SKILL.md §8). Ограничитель частоты алертов не строится: постоянно падающий воркфлоу чинится или выключается в тот же день. Почему: правка единственной точки тревоги ради редкого случая дороже пользы. [основание: TPL-17 · правило T2.4.8]
- **T2.4.9** Покрытие воркфлоу ошибок и явной таймзоны — состояние инстанса, а не текст этого Skill: считать заново по строкам W снимка `registry/n8n-map.md` (поле 10 — воркфлоу ошибок, поле 8 — таймзона); последний пересчёт — задача `labs/sys/t-failure-visibility.md`, снята 2026-10-21 (текст — в истории коммитов). [основание: TPL-18 · правило T2.4.9]

Область: слой 1 — все сетевые ноды всех активных воркфлоу; слой 2 — везде, где есть внешний вызов; слой 3 — везде, где после HTTP используются поля из нод выше; слой 4 — все активные воркфлоу, деструктивные (delete, публикация вовне) в первую очередь.

### T3 — HTTP-нода к Anthropic API

Body Content Type = JSON, Specify Body = Use Expression, значение через fx, БЕЗ ведущего `=`, БЕЗ `JSON.stringify()`:
```
{{ {
  "model": "claude-haiku-4-5-20251001",
  "max_tokens": 600,
  "system": $json.system_prompt,
  "messages": [{ "role": "user", "content": $json.user_content }]
} }}
```
- **T3.1** Raw + `JSON.stringify()` сломан на 2.20.9+ (после апгрейда с 2.9.4): двойная сериализация, запрос тихо битый *(§4.8.1)*.
- **T3.2** Идентификатор модели в примере выше — образец формы; действующие идентификаторы здесь не записываются: их снимают с обслуживания, и узел получает `not_found_error`. Брать текущий идентификатор из документации Anthropic в момент правки; `not_found_error` от API значит «модель снята», а не «ключ неверен». [основание: TPL-19 · правило T3.2]
- **T3.3** Credential: `genericCredentialType`/`httpHeaderAuth` — ключ в параметрах ноды запрещён *(R13)*; та же форма — для любого API модели (эмбеддинги тоже).
- **T3.4** Сверху накатывается T2 слой 1 (timeout) и слой 3 (проверка code/error).
- **T3.5** Обработка пустого или невалидного ответа модели — обязательная часть шаблона: внутри цикла SplitInBatches вместо `throw` возвращать item со статусом ошибки *(§4.2.5)*. Признак дефекта: `throw Error` при пустом ответе модели останавливает весь цикл, один плохой ответ прерывает обработку всего батча.
- **T3.6** Один и тот же ключ в нескольких воркфлоу — ротация затронет все сразу. Снимок `registry/n8n-map.md` привязывает тип credential к воркфлоу, а не к узлу, поэтому наличие типа `httpHeaderAuth` в снимке не доказывает, что литерала в узле больше нет: перед ротацией смотреть привязку по узлу (поле `credentials` в `get_workflow_details`, R1a) и искать литерал по всей базе *(R13)*. [основание: TPL-20 · правило T3.6]

### T4 — Чеклист перед публикацией

Пункты 1–6 — гейты: провалил → не публикуем. 7–12 — качество.

**Гейт 1.** `validate_workflow` — ноль ошибок схемы и формы.

**Гейт 2. Антипаттерн-скан** (то, чего `validate_workflow` не видит):
- Set-нода с 0 или 1 потребителем → удалить, выражение вписать в потребителя.
- Code-нода делает то, для чего есть нативная: ручной цикл пагинации → опция Pagination; ручной sleep → нода Wait; regex-парсинг → XML/JSON.parse; ретрай по статусу → retryOnFail.
- Identity-ноды (`return $input.all()`) — признак кривой формы воркфлоу.
- Merge: число проводов = `numberOfInputs`, off-by-one *(R9)*.
- Fan-out: параллельности нет *(R10)*.
- Switch без `fallbackOutput` *(R8)* — смотреть в `connections` узла Switch, есть ли выход fallback.
- `$json` в глубине ветвлений; `$env` вообще *(§4.2, §4.4)*.
- Дубль провода: два одинаковых connection-объекта на один целевой узел = каждый item проходит пайплайн дважды.
- Орфаны и мёртвый груз: ноды без входящих связей, disabled-ноды внутри цепочки.
- Цепочка из двух и более Execute Workflow подряд *(R16)*.

**Гейт 3.** Обработка ошибок разведена по T2 для всего по расписанию и продакшн-важного. Отдельно: нет ни одной ноды с `continueErrorOutput` и неподключённым output(1). Нет ни одного места, где непрочитанное значение молча становится нулём, «прочим», «пустым днём» или запасной константой вида `|| <число>` *(R19)*.

**Гейт 4.** Секретов в текстовых полях нет — проверять headerParameters, тело запроса И константы внутри Code-нод *(R13)*.

**Гейт 5.** Периметр вебхука. Ни один webhook не публикуется с «No credentials required»; оценивать blast radius — вебхук, принимающий произвольный id объекта, опаснее вебхука с фиксированным объектом *(R12)*. Узел формы (Form Trigger) — вход того же класса *(R12)*. Отдельно и независимо: HTTP-ноды, вызывающие свои сервисные вебхуки, обязаны использовать internal-адрес docker-сети *(R14)*. Помнить границу: аутентификация вебхука не закрывает вызов из сессии Claude *(R15)*.

**Гейт 6.** Сверка по §2.3 — после КАЖДОГО `update_workflow`, не только первого *(R1a, R1b, R2)*.

**Качество 7. Тест.** `prepare_test_pin_data` + `test_workflow` дали ожидаемый результат. Автопиннятся триггеры, ноды с credentials, HTTP Request. Выполняются по-настоящему: Code, Edit Fields, If, Data Tables, файловые операции, вызовы сабворкфлоу. При побочных эффектах — спросить Андрея до запуска.
Тест доказывает правку только при четырёх условиях:
1. Есть целевой случай и контрольный, обязанный пройти, и путь теста идёт через исправленную ветку. Почему: один целевой случай с ответом «0 из 0» неотличим от «сломано целиком». [основание: TPL-21 · правило T4.7.1]
2. Ветка «истина» каждого условия исполнилась хотя бы раз и дала объект. Почему: условие, которое не бывает истинным (два взаимоисключающих условия через И; сравнение со строкой времени после сдвига расписания), прогон не ловит — он зелёный. [основание: TPL-22 · правило T4.7.2]
3. Детектор и монитор принимаются только после красного на подсаженном дефекте: зелёный, ни разу не проверенный красным, — не доказательство. Класс доказательства задаётся конструкцией подсадки — почти дословная пара доказывает доставку, а не чувствительность к реальному дрейфу; смена конструкции согласуется до исполнения; стенд, на котором дефект нечем вызвать, не используется. Проверка, не способная отличить норму от незнания, отвечает «нет данных», а не «расхождение»; прежде чем строить проверку на источнике, убедиться, что признак здорового объекта в нём вообще может появиться. [основание: TPL-23 · правило T4.7.3]
4. Редкая защитная ветка (откат ответов маркетплейсу, белый список автопубликации) проверяется прогоном на строке TEST_ при приёмке и при каждой правке этой ветки, на хорошем и на плохом случае; прибор по расписанию для неё не строится. Перед удалением условия выяснить, какой инвариант оно держит, и проверить защиту на плохом случае. Почему: такие поломки находит внешний аудит, а не текущая работа — откат не работал 6–8 недель, белый список сняла правка. [основание: TPL-24 · правило T4.7.4]

**Качество 8. Timezone.** `settings.timezone` задан явно для всего по расписанию *(R7)*. Смещение в голове не считать: Берлин → МСК даёт +1 летом и +2 зимой *(§4.10)*. Эталон: заданы и таймзона `Europe/Moscow`, и `errorWorkflow`. Признак дефекта: расписание без явной таймзоны, чей последний прогон стоит у дедлайна по Москве, — зимой уедет за дедлайн *(§4.10.1)*.

**Качество 9. Именование и description.** Имя воркфлоу с глагола, `description` заполнен, ноды переименованы из дефолтных в `NN_Название` *(§3)*.

**Качество 10. Публикация.**
- **T4.10.1** Вкладка редактора закрыта до MCP-записи. Почему: сохранение из устаревшей вкладки браузера затирает правку, записанную через MCP *(R17)*.
- **T4.10.2** Если черновик уже расходился с опубликованной версией (`versionId` не равен `activeVersionId` до твоей правки) — до публикации сравнить версии `get_workflow_versions_diff` и публиковать, только если все различия свои *(R2)*. Для активного воркфлоу — полный тумблер *(R2)*.
- **T4.10.3 Последний шаг любой правки воркфлоу — обязательный, без него правка не закрыта, хотя пункт стоит в разделе качества:** свежий `get_workflow_details`, `versionId` равен `activeVersionId` *(§2.3 пункт 5)*. Не равен — правка лежит только в черновике, расписание исполняет старую версию *(R2)*.
  - Почему шаг стоит здесь, а не только в R2: корень читают при поиске причины, а не при правке.
  - Признак: Save без Publish — правка сделана и сохранена, а активная версия исполняет прежнее.
  - [основание: TPL-25 · правило T4.10.3]
- **T4.10.4 Воркфлоу по расписанию считается работающим только по объекту:** метка последнего прогона на объекте (строка в целевой таблице, «Снимок сделан» на листе) показывает дату планового прогона. Документация, черновик, ручной прогон и слова «триггер включён» доказательством не являются. Задача о воркфлоу по расписанию закрывается успешным ПЛАНОВЫМ прогоном, а не ручным запуском — ручной исполняет черновик, а не опубликованную версию *(R2)*. Одного планового прогона достаточно, только если сбой следующих прогонов будет виден сам: у воркфлоу задан воркфлоу ошибок (errorWorkflow), который доводит сбой до Telegram; без него сначала задаётся воркфлоу ошибок, а прогоны не считаются. Почему: срыв расписания бывает перемежающимся, и никакое число удачных прогонов подряд его не исключает — исключает только то, что следующий сбой будет замечен. Для триггеров Apps Script — то же правило, видимость там даёт проверка возраста метки, механика в Skill apps-script-sheets. Не путать: воркфлоу ошибок не видит прогона, который не начался (расписание не создаёт прогонов, инстанс остановлен — R2.1), поэтому после каждой новой публикации снова нужен первый плановый прогон, прочитанный по объекту. [основание: TPL-26 · правило T4.10.4]

**Качество 11. Верификация — только по объекту воздействия** *(A1, R4)*.

**Качество 12. После публикации — никаких автономных действий.** Ни publish, ни unpublish, ни update, ни archive, ни «запущу посмотреть». Проблему вынести, фикс предложить, ждать явного «да» на каждый шаг *(§2.2 пункт 7)*.

### T5 — Воркфлоу записи во внешний кабинет: режимы «проверка» и «боевой»

Для воркфлоу, который пишет в кабинет площадки (Ozon, Wildberries) — декларации, описания, характеристики карточек. Закон шаблона: **ошибочную запись во внешний кабинет откатить из n8n нельзя, поэтому каждая боевая запись идёт по пути, уже показанному владельцу без записи, и заканчивается чтением объекта.** Почему: ошибочная запись массово скрывает товары или снимает отметки, которые потом возвращают руками (R18). Шаблон собран из трёх проектов записи во внешний кабинет — декларации Ozon, декларации Wildberries, описания карточек; основание: 3 проекта, последний 2026-10-08 — отчёт синтеза, правило T5.0.

**T5.1 Два режима на одном пути.**
- **«Проверка»** проходит тот же путь, что боевой: читает те же источники, строит те же тела запросов, считает все блокеры — и ничего не пишет вовне. Итог — список «что будет записано, куда, и что заблокировано и почему».
- **«Боевой»** запускается только после явного «да» владельца на КОНКРЕТНЫЙ список из проверки (номер декларации, перечень карточек), а не на режим вообще. Повтор Андреем фразы с названием объекта после показа проверки без записи считается «да» на боевую запись по этому объекту. [основание: TPL-27]
- Режим — параметр входа (поле формы), а не отдельный воркфлоу: два воркфлоу расходятся, а один путь с одними воротами — нет.
- После пробы пишущий инструмент возвращается в безопасное состояние: режим «проверка», пустой набор объектов. Почему: следующий запуск, кем бы он ни был сделан, не пишет вовне сам. [основание: TPL-28 · правило T5.1]

**T5.2 Ворота боевого режима — в коде, не в тексте.** Запреты (предметы, которые писать нельзя; карточки без нужного поля) — фильтр в узле перед записью, а не строка в STATE *(R18)*. Сюда же защита от повтора: перед записью прочитать кабинет, и то, что там уже есть, не писать повторно («уже есть в кабинете» — отдельный статус в итоге).

**T5.3 Режим нельзя строить на признаке «ручной запуск».** `$('Manual').isExecuted`, `$execution.mode === 'manual'` и подобные признаки из сессии Claude не срабатывают: `execute_workflow` через MCP запускает воркфлоу с триггером расписания через этот триггер, даже если рядом стоит ручной, — запуск идёт боевым. Режим задаётся только явным параметром входа, и его значение по умолчанию — «проверка». [основание: TPL-29 · правило T5.3]

**T5.4 Не публикуется.** Такой воркфлоу стоит неопубликованным (`active:false`) и запускается только вручную формой или через `execute_workflow` в режиме `manual` *(SKILL.md §1.1)*. Опубликованная форма без аутентификации запускает боевой режим с адреса формы *(R12)*. После любой ручной правки в редакторе проверить, что он не стал активным: Save может сам опубликовать воркфлоу *(R17 (в))*.

**T5.5 Перед боевым режимом:**
1. Право ключа на запись проверено (ответ 403 «read-only token» иначе придёт только на первой боевой записи) *(§2.1)*.
2. Выяснено, какие поля чтение API не возвращает, если запись заменяет объект целиком *(R18)*.
3. Сохранён снимок объекта до записи с адресом (исполнение, узел, время) *(R18)*.
4. Одна пробная запись в один объект и чтение его обратно — до массовой записи *(R18)*.
5. Каждый параметр запроса выведен из данных, а не выбран из списка допустимых значений API. Почему: значение, которое API принял, ещё не верное — неверный по данным параметр проходит проверку API. Расхождение параметра с данными — блокер в проверке, а не предупреждение. [основание: TPL-30 · правило T5.5.5]
6. Идентификатор, который вводится в форму запуска (номер декларации, nmID), не набирается по памяти: он копируется из колонки листа или из входа прошлого исполнения. Признак: номер с чужим кодом органа, остановленный проверкой до записи. [основание: TPL-31 · правило T5.5.6]

**T5.6 Остановка пробы.** Если три записи подряд приняты с кодом 200, а объект при чтении не изменился, — проба останавливается, боевые запросы вслепую не продолжаются, пока причина не найдена. Почему: продолжать значит гонять боевые запросы без понимания результата; ещё записи к диагнозу ничего не добавят. Признак: «карточка не изменилась при чтении» после ответа 200 *(R4)*. [основание: TPL-32 · правило T5.6]

**T5.7 Сравнение по хэшу.** Если воркфлоу решает «изменилось ли» по сохранённому хэшу нормализованного текста, любая смена правила нормализации меняет хэши всех затронутых текстов, и проверка покажет ложные изменения с обеих сторон. Нужен отдельный режим «пересчёт хэшей»: у пар, где текст совпадает по новому правилу, пересчитать сохранённые хэши, а настоящие расхождения не трогать; запускается при каждой смене правила. [основание: TPL-33 · правило T5.7]

**T5.8 Итог записи — по объекту.** После боевого режима — перечитать записанные объекты и, где площадка это даёт, её журнал ошибок; код 200 итогом не является *(R4)*. Где у площадки проверка идёт отложенно (например, проверка товаров по документу), повторное чтение делается отдельным режимом позже (режим «статус»).
