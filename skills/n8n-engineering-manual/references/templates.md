### T1 — Идемпотентная запись

**Шаг 0. Выбор инструмента.**
- Нужен только факт «уже видели этот ключ», объём до ~10k, без TTL и метаданных → Remove Duplicates (T1-A).
- Нужно состояние: запрашиваемое, с TTL, со статусом, с историей → Data Table (T1-B).
- Данные читает человек глазами (витрина) → Google Sheets (T1-C).

Принцип: служебное состояние (курсоры, dedup-маркеры, реестры, sku-маппинг) не обязано жить в Sheets — это налог за использование Sheets как БД *(R6)*. Разделение «состояние → Data Table, витрина → Sheets» устраняет корень, а не лечит симптом.

Эталон выбора: `Skills Drift Detector (Nightly)` (`Htrj0Kyj7eT5SEhR`) держит sync-состояние в Data Table, а не в Sheets — одно из немногих корректных применений Data Tables на инстансе.

**T1-A. Remove Duplicates.**
```json
{
  "type": "n8n-nodes-base.removeDuplicates",
  "parameters": {
    "operation": "removeItemsSeenInPreviousExecutions",
    "dedupeValue": "={{ $json.raw_key }}",
    "options": { "historySize": 10000 }
  }
}
```
Применять: поток однотипных item, нужен только факт «уже обрабатывали». Нельзя: нужен запрос по состоянию, TTL, ветка «вернуть из кэша».

**T1-B. Data Table.** Форма: Get → IF → [обработать новое / вернуть известное].
1. На Get: `alwaysOutputData:true` на уровне config ноды, не внутри `parameters` — иначе no-match даёт 0 items *(R3)*.
2. Обе ветки IF отдают одинаковую форму JSON — нужен нормализующий anchor-узел.
3. Многоколоночный фильтр — явно `matchType:"allConditions"`.
4. `returnAll:false` без явного `limit` → дефолт 50 → тихое обрезание.
5. Форму Get+IF реализовывать как `returnAll:true` + матчинг в Code-ноде *(§4.12)*.

Эталон: `Skills Drift Detector` (`Htrj0Kyj7eT5SEhR`), узел `05_Get_All_Synced` — `executeOnce:true` вместе с `alwaysOutputData:true` на уровне config.
6. Идемпотентные маркеры требуют TTL-уборки: отдельный воркфлоу, удаляющий строки старше окна ретраев.

**T1-C. Google Sheets — витрина (предпочтительная форма).**
```json
{
  "operation": "appendOrUpdate",
  "columns": {
    "matchingColumns": ["raw_key"],
    "mappingMode": "autoMapInputData"
  }
}
```
Обязательно:
- `columns` передавать ТОЛЬКО литеральным JS/JSON-объектом (`{mappingMode, matchingColumns, schema, attemptToConvertTypes, convertFieldsToString}`) — НИКОГДА не оборачивать в `expr()`-строку. Воспроизводимо: columns как expr-строка → 1 error-item вместо 272 строк; литеральный объект → 272 строки, 0 ошибок.
- `matchingColumns` заданы всегда + приведение типов (parseInt/String) — строка ≠ число не матчится, ошибки нет, растут дубли.
- Составной ключ собирать заранее в Code в одну колонку — мультивыбор `matchingColumns` матчит только по первой.
- Сверять реальный gid (`sheetName.value`), не подпись в UI.
- Read-нода: `executeOnce` + узкий фильтр *(§4.3, R6)*.
- Per-item шаги оборачивать в `splitInBatches(batchSize:1)` *(§4.4)*.
- Поля предыдущих нод после Sheets-ноды брать через `$('Имя').item` — вторая Sheets-нода в цепочке отдаёт только свою схему.
- Очистка ячейки — `""`, не `null` *(R6)*.
- В Code-узлах внутри пайплайна ВСЕГДА spread `({ ...src, newField })`. Собирать item заново из перечисленных полей — тихая потеря *(§4.2)*.

Эталон: `WB RAW History Load V.3 CLEAN` (`Iis5dlRS1GWZqQXD`), узел `11_Write_RAW_To_Sheets` — `appendOrUpdate` по `raw_key`, без связки delete+merge вообще. Аудит отметил это как более простое и безопасное решение той же задачи, которую сиблинги решают через find→IF→delete→wait→merge.

Дефект утраты данных при неверном маппинге: `SKU Category Weekly Snapshot` (`qZWrl0MkRnZBipXA`), узел `06_Is_Snapshot_Duplicate` возвращает новый объект из двух полей вместо spread — каждую неделю в историю пишется почти пустая строка, счётчики категорий теряются молча.

**T1-D. Google Sheets + delete — только если нужна физическая перезапись диапазона.**
```
Find (executeOnce:true, alwaysOutputData:true — top-level)
  → IF (row_number exists?)
       true  → Delete → Wait → Merge input(1)
       false →                 Merge input(1)   ← ОБЯЗАТЕЛЬНО ПОДКЛЮЧЕНА
  → appendOrUpdate
```
False-ветку подключать без исключений: безопасность неподключённого варианта держится на режиме Merge, который через API не проверяется, а архитектуру, корректность которой нельзя подтвердить чтением, нельзя держать шаблоном.
Дискриминатор: неподключённый выход IF допустим ТОЛЬКО если он терминал — ниже него никто не ждёт данных (ни вход Merge, ни петля цикла). Сознательный терминал ведёт в именованный NoOp (`STOP_No_Rows`, `No_New_Items`), а не висит в пустоте, чтобы «терминал» отличался от «забыли провод» прямо на графе.

Когда применять: любая повторяемая запись, где возможен повторный прогон (ретрай, backfill, пересечение окон расписания). Предпочитать T1-C над T1-D всегда, когда бизнес-логика допускает upsert по ключу. T1-C нельзя, если нужно физическое удаление строк, исчезнувших из источника. На append без `matchingColumns` не полагаться — повторный запуск дублирует историю.

Дефект дублирования: `SKU Category Historical Backfill` (`VWyXmCPJevCnbkZT`), узлы `05_Write_Snapshots_History` и `07_Write_Detail_History` — append с `matchingColumns:[]`, повторный запуск дублирует всю историю.

Почему T1-D не стал шаблоном по умолчанию: безопасность варианта с неподключённой false-ветвью держится на режиме узла Merge, а режим при пустых `parameters` через `get_workflow_details` НЕ ВИДЕН. Архитектуру, корректность которой нельзя подтвердить чтением, шаблоном держать нельзя. Открытый вопрос по двум узлам — `11_Wait_For_Delete` в `OzonRawАналитика` и `10B_Merge_Before_Write` в `WB RAW Finance Sync V.3` — до сих пор ждёт скриншота поля Mode (INCIDENT_LOG, раздел 4).

Терминал, корректно: `WB FBS Order Close v2` (`DM26WhTJyCV0DhkP`) узел `02E_IF_Has_Orders`; `WB Reviews Intake` (`mAaWSmoXDH9Ofgg3`) узлы `09_IF_Has_New` и `17_IF_Has_Updates`.
Терминал с говорящим NoOp, эталон: `WB_WF_sku-mapping-loader` (`qrZw8bxIEpRAUwEe`) `03_IF_Has_Rows` → `STOP_No_Rows`; `WB Reviews Full History Load` (`ss0QkY9V8YEMHf2B`) `09_IF_Has_New` → `11_No_New_Items`.
Баг, ветвь ждёт Merge: `OzonRawАналитика` (`MPzPrtsnPtf0sVQo`) `09_IF_RAW_Rows_Exist` — в connections один массив, false-ветвь отсутствует, а description воркфлоу утверждает обратное. Рецидив: чинили 2026-07-04, вернулось к 07-23, подтверждено живым чтением 2026-08-04. Тот же класс — `WB RAW Finance Sync V.3` (`IvgysDKrq3UISYEY`) `08_IF_RAW_Rows_Exist`.
Эталон самой связки T1-D: `OzonRawАналитика_Monat` (`FnB2Imp7thMKuwnD`) — та же архитектура, что в сломанном сиблинге, но оба выхода `09_IF_RAW_Rows_Exist` в connections присутствуют.

### T2 — HTTP и обработка ошибок в проде

**Слой 1. Timeout всегда, retry — по типу ошибки.**
```json
{
  "retryOnFail": true,
  "maxTries": 3,
  "waitBetweenTries": 5000,
  "options": { "timeout": 30000 }
}
```
- `options.timeout` — безусловно на каждой сетевой ноде каждого активного воркфлоу: без него дефолт 5 минут *(R11)*.
- `retryOnFail` — не безусловно. Он ретраит на любую ошибку без фильтра по коду и лечит только транзиентные сбои (обрыв соединения, таймаут, 5xx). Против 429 по квоте он вреден: попытки ложатся в то же минутное окно и ускоряют исчерпание *(R6)*. Нужен ретрай по коду — делать через выход ошибки + IF по `$json.error.httpCode` + Wait, а не флагом ноды.
- Записанные через SDK `maxTries` и `waitBetweenTries` сверять в сохранённом JSON *(R1b)*. Движок режет: максимум 5 попыток, максимум 5000мс между.
- Часто лучше ретрая — самовосстанавливающийся флаг: при частом расписании дешевле идемпотентный флаг «обработано», при сбое объект просто не помечается и подхватывается следующим прогоном.

Эталон явного ретрая: `Deklaration_Hydraulisches_Oil_V.4` (`EH2JaB8WGa0JsBqs`), узел `03_Load_Product_Page` — `retryOnFail:true`, `maxTries:5`, `waitBetweenTries:5000` заданы явно.
Эталон самовосстанавливающегося флага: `WB FBS Supply Accepted` (`7x9wPrugdbseaEp2`) — флаг `summary_sent_at` в листе `wb_fbs_supplies`; при сбое узла `05_Fetch_Order_Ids` поставка пропускается и повторяется через час.

**Слой 2. Выбор onError.**
- Ошибка реально обрабатывается дальше (алерт, фолбэк, запись статуса) → `continueErrorOutput` И обязательно развести output(1) в реальную ноду. Одно без другого = items испаряются *(R5)*.
- Ошибка не критична, downstream явно читает code/error → `continueRegularOutput`. Ценой того, что нода выпадает из-под глобального errorWorkflow: для n8n ошибка при `continueRegularOutput` считается ОБРАБОТАННОЙ, и errorWorkflow по этой ноде не сработает никогда.
- Осмысленной обработки нет → оставить дефолт `stopWorkflow` и дать errorWorkflow отработать. Это не лень, а правильный выбор.
- Запрещено: `continueErrorOutput` с неподключённым output(1); выход ошибки, заведённый в no-op; `continueRegularOutput` «чтобы не падало» — единственный способ гарантированно ослепить мониторинг.

Правильный `continueRegularOutput`: `WB FBS Morning Forecast` (`6M9nS9iKQzMdztUs`), узел `05_Fetch_WB_New` — ниже `06_Calculate_Forecast` имеет try/catch с явным фолбэком и выводит «— ошибка API» прямо в сообщение пользователю.
Неправильный: `WB RAW Finance Sync V.3` (`IvgysDKrq3UISYEY`) — узлы `07_Find_RAW_Rows_By_Date`, `09_Delete_RAW_Rows`, `11_Write_RAW_To_Sheets` все три на `continueRegularOutput`, и никто ниже не читает code/error. При этом `errorWorkflow` в settings задан — и не сработает никогда. Дыра в мониторинге при формально настроенном мониторинге.
Голый `continueErrorOutput`: `Projekt_OCR OEM_V.5` (`DWyvoJYkCodJxMg1`), узел `06_Extract_Text_From_PDF` — ветвь ошибки не подключена, при сбое OCR строка молча исчезает из пайплайна без записи статуса. Тот же класс — `LM_DECL_MASTER V.2` (`VMPxWzXPefKT2R1B`): узлы `05A`/`05C_Error_Handler_*` ошибку корректно ПОЛУЧАЮТ, но их собственный выход никуда не ведёт, и статус `PAGE_LOAD_ERROR` не записывается никогда.

**Слой 3. Сохранность данных.**
- Поля предыдущих нод после HTTP брать через `$('ИмяНоды').all()[i]` по позиции *(R5)*.
- Первой нодой после HTTP — явная проверка code/error.
- `neverError:true` без последующей явной проверки запрещён: маскирует ошибку внешнего API под валидный item *(R4)*.
- Сверка длины входа и выхода с `throw` — единственная защита от испарившегося item *(R5)*.
- Не полагаться на output Sheets-ноды как на источник полей — читать из именованной исходной ноды.

Дефект `neverError`: `OZON Fetch Reviews → Queue` (`IHn3Bmyh1VeHf4Ya`), узел `02_Fetch_Ozon_Reviews` с `neverError:true` — при 401, 429 или 5xx ниже читается `body?.reviews` из тела ошибки, получается undefined, фолбэк даёт пустой массив, и воркфлоу трактует сбой как «новых отзывов нет» и молчит.
Отдельная ловушка: `neverError` НЕ гасит ошибку внутри `completeExpression` пагинации — при ошибке API тело может быть undefined, и `.length` на нём бросит ошибку в самом выражении. Замечено в `WB Reviews Intake` (`mAaWSmoXDH9Ofgg3`).
Эталон обхода: `LM_DECL — Watch` (`OnEludZYMusvFxTS`) — узлы `07B_Append_History` и `08_Build_Telegram_Msg` читают данные напрямую из `$('07A_Prepare_Update')`, а не из выхода Sheets-узла.

**Слой 4. Глобальный error-workflow.**
- На 2.20.9 назначается вручную в настройках каждого воркфлоу, mass-assign невозможен *(§8)*.
- Правила самого error-воркфлоу: никаких внешних вызовов, способных упасть; быстрый (выполняется синхронно и тормозит исходный сбой); канал уведомления отличный от мониторимых.
- Минимальный алерт: имя воркфлоу, ID, ссылка на редактор, ссылка на прогон, `lastNodeExecuted`, реальный `error.message`, время.
- Проверка после настройки: заведомо падающий воркфлоу (HTTP на битый URL, без обработки) → прогнать → убедиться, что алерт дошёл. По факту прихода сообщения, не по логу.

Текущее состояние слоя. `Error Notifier` (`M5BLqclKBjGTpz33`) не включает `error.message` в текст алерта — только имя воркфлоу, время и `lastNodeExecuted`, поэтому для диагностики всё равно приходится открывать UI; решение «добавлять ли» владельцем не принято (INCIDENT_LOG, раздел 4). Масштаб на 2026-09-26: из 39 реально тикающих активных расписаний `errorWorkflow` не задан у 26. Слой 4 описывает должное, а не сущее.

Область: слой 1 — все сетевые ноды всех активных воркфлоу; слой 2 — везде, где есть внешний вызов; слой 3 — везде, где после HTTP используются поля из нод выше; слой 4 — все активные воркфлоу, деструктивные (delete, публикация вовне) в первую очередь.

### T3 — HTTP-нода к Anthropic API

Body Content Type = JSON, Specify Body = Use Expression, значение через fx, БЕЗ ведущего `=`, БЕЗ `JSON.stringify()`:
```
{{ {
  "model": "claude-haiku-4-5-20251001",
  "max_tokens": 600,
  "system": $json.system_prompt,
  "messages": [{ "role": "user", "content": $json.user_content }]
} }}
```
Raw + `JSON.stringify()` сломан на 2.20.9+ (после апгрейда с 2.9.4): двойная сериализация, запрос тихо битый. Модели: тест `claude-haiku-4-5-20251001`, prod `claude-sonnet-4-6`. Credential: `genericCredentialType`/`httpHeaderAuth` — ключ в параметрах ноды запрещён *(R13)*.
Сверху накатывается T2 слой 1 (timeout) и слой 3 (проверка code/error).
Обработка пустого или невалидного ответа модели — обязательная часть шаблона: внутри цикла SplitInBatches вместо `throw` возвращать item со статусом ошибки *(§4.2)*.

Дефект: `KB TO — Annotation Preprocessor` (`wWFfPIAfLd7yunU8`) и `KB AC — Annotation Preprocessor` (`5Iyr82zmzCeievFv`), узел `07_Extract_Result` — `throw Error` при пустом ответе модели останавливает весь цикл, один плохой ответ прерывает обработку всего батча.
Эталон конфигурации credential: `OZON QA Response` (`R8w94X0mT0Fa2Oil`) — `genericCredentialType`/`httpHeaderAuth` и для Anthropic, и для Voyage, хардкода нет.
Ротация ключа Anthropic: аудит 2026-07-23 нашёл один и тот же живой ключ в `Ozon_Hashtag_Generator` и `WB+Ozon News Filter` — ротация затронет оба сразу. На 2026-09-26 у обоих в снимке есть тип `httpHeaderAuth`, то есть ключ, похоже, уже переведён в credential; снимок привязывает тип к воркфлоу, а не к узлу, поэтому перед ротацией смотреть глазами *(R13)*.

### T4 — Чеклист перед публикацией

Пункты 1–6 — гейты: провалил → не публикуем. 7–12 — качество.

**Гейт 1.** `validate_workflow` — ноль ошибок схемы и формы.

**Гейт 2. Антипаттерн-скан** (то, чего `validate_workflow` не видит):
- Set-нода с 0 или 1 потребителем → удалить, выражение вписать в потребителя.
- Code-нода делает то, для чего есть нативная: ручной цикл пагинации → опция Pagination; ручной sleep → нода Wait; regex-парсинг → XML/JSON.parse; ретрай по статусу → retryOnFail.
- Identity-ноды (`return $input.all()`) — признак кривой формы воркфлоу.
- Merge: число проводов = `numberOfInputs`, off-by-one *(R9)*.
- Fan-out: параллельности нет *(R10)*.
- Switch без `fallbackOutput` *(R8)*. Пример: `Deklaration_TransmissionOil_V.4` (`GDI35U36bBRzKZp5`), `connections["02B_Extract_Product_URL"]`.
- `$json` в глубине ветвлений; `$env` вообще *(§4.2, §4.4)*.
- Дубль провода: два одинаковых connection-объекта на один целевой узел = каждый item проходит пайплайн дважды.
- Орфаны и мёртвый груз: ноды без входящих связей, disabled-ноды внутри цепочки.
- Цепочка из двух и более Execute Workflow подряд *(R16)*.

**Гейт 3.** Обработка ошибок разведена по T2 для всего по расписанию и продакшн-важного. Отдельно: нет ни одной ноды с `continueErrorOutput` и неподключённым output(1).

**Гейт 4.** Секретов в текстовых полях нет — проверять headerParameters, тело запроса И константы внутри Code-нод *(R13)*.

**Гейт 5.** Периметр вебхука. Ни один webhook не публикуется с «No credentials required»; оценивать blast radius — вебхук, принимающий произвольный id объекта, опаснее вебхука с фиксированным объектом *(R12)*.
