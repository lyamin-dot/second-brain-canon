## 5. Корневые причины (продолжение): Google Sheets

**R6. Google Sheets: хрупкая привязка, типы, квоты.**

Закон корня. Узел Google Sheets связывает воркфлоу с листом через имена колонок, позиции строк, типы значений и общий счётчик квоты — и ни одно их изменение не даёт ошибки там, где теряются данные. Корневое лечение — не использовать Sheets как базу данных: служебное состояние (курсоры, маркеры повторов, реестры, сопоставления) — в Data Table, витрина для человека — в Sheets *(T1)*. Пока Sheets остаётся носителем, каждая частная ловушка ниже лечится своей сверкой.

**Короткие симптомы (правило R6.1).** gid врёт в интерфейсе (`cachedResultName` — старый снимок); несоответствие типа в `matchingColumns` даёт дубли без ошибки; составной `matchingColumns` сопоставляет только по первой колонке (подробно — правило R6.7); чтение без `executeOnce` = N запросов = 429; `batchUpdate` без `sendBody` = 400.
[основание: ROOT-29]

**`null` не очищает ячейку (правило R6.2).** При `appendOrUpdate` в режиме update поле, которому передан `null`, молча не записывается — старое значение остаётся; поля с настоящим значением, включая пустую строку `""`, перезаписываются штатно. Чтобы физически очистить ячейку — писать `""`.
[основание: ROOT-30]

**Квота чтения (правило R6.3).** `ReadRequestsPerMinutePerUser` = **60 в минуту** по умолчанию, и считается она **на потребителя ключа** (проект GCP), а НЕ на воркфлоу и не на узел: все воркфлоу и все узлы на одном сервисном аккаунте делят один счётчик. Поэтому «интервал между двумя конкретными вызовами слишком мал» — ложный диагноз: 429 бывает и при разрыве больше 5 минут между записью и чтением.
- Диагностика 429 — до любых гипотез о внешнем потребителе квоты. Google кладёт в тело ошибки всё нужное, читается через `get_execution(includeData:true, nodeNames:["<упавший узел>"])`: `quota_limit`, `quota_limit_value`, `quota_unit`, `consumer` (project_number). `consumer` с номером собственного проекта значит, что квоту выбрали сами, и искать чужого потребителя бессмысленно.
- Второй дискриминатор — режим запуска: `manual` того же воркфлоу даёт success, а `integrated` (вызов из родителя) — 429 → дело не в квоте инстанса и не во времени суток, а в числе входных items *(R16)*. Признак: `executionTime` упавшего узла около 59000 мс — узел ровно минуту отстреливал разрешённые 60 чтений.
- Повтор при 429 по квоте допустим только после ожидания дольше минутного окна: выход ошибки узла (`continueErrorOutput`) ведёт в Wait не меньше 60 секунд, затем повтор. `retryOnFail` и пауза в 2 секунды окна не переживают: движок ограничивает повтор пятью попытками и пятью секундами между ними, все попытки ложатся в ту же минуту и ускоряют исчерпание *(T2 слой 1)*. Пауза 1–2 секунды между вызовами как профилактика остаётся. Корневое лечение — меньше вызовов (пакеты, `executeOnce`, служебное состояние вне Sheets).
[основание: ROOT-31]

**Строка заголовков — договор со всеми узлами-читателями (правило R6.4).** Добавленная колонка роняет узел с заданной схемой («Column names were updated after the node's setup»); переименованная молча ломает автоматическое сопоставление полей; удалённая строка заголовков сдвигает данные и роняет всех, кто читает по имени колонки. Перевод читателя на другой лист с теми же данными, но другими именами колонок даёт узлу пустые поля без ошибки.
- Правило: перед правкой шапки перечислить узлы-читатели этого листа, после правки — обновить их схему; при смене листа сопоставить имена колонок до переключения.
- То же — до первой записи строк нового вида в общий лист (строки другого бренда, строки без поля, которое у прежних строк было всегда): каждого читателя проверить по коду его узла чтения и первой обработки — что он делает с такой строкой: пропускает, останавливается или пишет неверное. Почему: читатель, написанный под прежний вид строк, может принять пустое поле за значение и записать чужие данные. Читателей в n8n дают строки D снимка `registry/n8n-map.md` по ID книги; скрипты других книг снимок не показывает, их ищут отдельно.
- Ошибка в самой строке заголовков (например `#ERROR!` в первой ячейке) даёт мусорные имена полей, и значения листа параметров читаются пустыми — пороги становятся нулём *(R19)*. Такой лист читать узким диапазоном (Data Location → Range, строка заголовков задана явно), а не целиком.
- Дубли заголовков на одном листе: узел чтения собирает item по именам, и при одинаковых именах побеждает правая колонка — подменяет левую чужими данными. На таком листе задавать Data Location → Range с границей до дублей.
[основание: ROOT-32]

**Выбор листа в режиме `list` (правило R6.5).** Значение `gid=0` работает, `gid=<ID листа>` даёт «Sheet with ID gid=… not found»; писать голый ID листа.
[основание: ROOT-33]

**Колонка с формулой (правило R6.6).** Узел при добавлении строк (append) считает ячейку с формулой занятой даже при пустом результате формулы — новые строки ложатся ниже разлива ARRAYFORMULA, а не в первую пустую строку. Писать значения в колонку, которую заполняет формула (ARRAYFORMULA, IMPORTRANGE, построчная формула), нельзя вовсе: запись даёт `#REF!` или молча расходится с формулой. Перед первой записью в лист колонки читать в режиме FORMULA. Механика формул самой книги — Skill apps-script-sheets.
[основание: ROOT-34]

**Автоматическое сопоставление (autoMapInputData) и составной ключ (правило R6.7).** Узел записывает ровно те поля входного элемента, у которых есть одноимённая колонка, и не трогает колонки, которых во входе нет: частичное обновление — не потеря (дискриминатор «затёрто или не было»: целы ли поля того же источника). Поле с именем колонки-формулы заменяет формулу значением — такие поля во вход записи не включать. Составной `matchingColumns` (`["k1","k2"]`) сопоставляет по первой колонке и перезаписывает вторую колонку ключа у найденной строки — на листе возникает дубль ключа; составной ключ собирать заранее в одну колонку.
[основание: ROOT-35]

**Тип и чистота ключа (правило R6.8).** Сравнение ключей даёт ноль совпадений без ошибки, а `appendOrUpdate` по такому ключу плодит дубли, если стороны расходятся хоть в чём-то:
- тип: ключ в одном источнике хранится числом, в другом текстом («1058.0» против «1058») — перед любым сравнением и в `matchingColumns` обе стороны приводятся к одному типу в Code-узле;
- уникальность: если у ключа в источнике две строки, поиск молча берёт первую — источник проверяется на уникальность ключа до сравнения;
- символы: двойной пробел, кириллические «Т» и «С» вместо латинских дают ноль совпадений — символы ключа сравниваются по коду, а не глазом;
- число в текстовой по смыслу колонке: значение из листа может прийти числом — перед `.trim()` и сравнением писать `String(x ?? '')`;
- пустой ключ: `matchingColumns` по колонке, которая может быть пустой, сопоставляет пустое с пустым, и запись уходит в первую чужую строку с пустым ключом — строки без ключа отсекаются до записи и до первого платного вызова модели.
[основание: ROOT-36]

**Таблица параметров — горизонтальная (правило R6.9).** Лист параметров воркфлоу хранится строкой имён и строкой значений (строка 1 — имена, строка 2 — значения), а не парами «имя — значение» по строкам. Почему: вертикальная пара с `row_number` при `appendOrUpdate` перезаписала соседний порог, и неверные надбавки копились без единой ошибки.
[основание: ROOT-37]

**`appendOrUpdate` по строке с жизненным циклом (правило R6.10).**
- Если строка проходит статусы (new → shipped → cancelled), повторная запись того же ключа возвращает статус назад в начальный. Защита от повтора для таких строк — множество уже известных ID (новое пишется, только если ID нет в множестве), а не upsert.
- Поле первого наблюдения (время первой детекции) в такой строке не перезаписывается на каждом прогоне — иначе производная метрика («часов с момента») растёт по часам прогона и теряет смысл.
- Обратная ловушка: накопитель на `appendOrUpdate` никогда не удаляет объект, исчезнувший из источника, — читатель такого накопителя фильтрует по свежести (`updated_at`), иначе видит мёртвые записи.
[основание: ROOT-38]

**Простой append при повторяемом прогоне (правило R6.11).** Запись в архив перед удалением простым append при каждом упавшем и перезапущенном прогоне дописывает те же строки ещё раз; для повторяемой записи — только `appendOrUpdate` с `matchingColumns` (тот же класс — T1-D, дефект дублирования).
[основание: ROOT-39]

**Удаление строк (правило R6.12).** Узел «delete» без явных `startIndex` и `numberToDelete` — не пустая операция: удаляет одну строку, начиная со второй, то есть первую строку данных. Поле номера строки (startIndex в typeVersion 4.7) ждёт номер строки как есть — «The first row is 2»; передача `row_number − 1` удаляет строку над целевой, а для первой записи — строку заголовков (защита заголовка листа скрывает эту ошибку, пока её не снимут). В коде удаления — барьер: номер строки меньше 2 → остановиться с ошибкой.
[основание: ROOT-40]

**Запись и удаление по номеру строки (правило R6.13)** — только после повторного чтения ключевой колонки в момент записи и сравнения с первым чтением; расхождение — остановка без записи. Почему: номер строки сдвигают ручная правка владельца, ошибка на единицу, удаление без явного диапазона.
[основание: ROOT-41]

**Порядок диапазонов в ответе batchGet не гарантирован (правило R6.14).** Google может вернуть листы в другом порядке, чем запрошены; диапазон выбирается по имени листа в поле `range` ответа, никогда по позиции.
[основание: ROOT-42]
