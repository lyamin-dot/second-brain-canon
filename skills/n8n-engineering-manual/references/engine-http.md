## 4. Механика движка (продолжение): HTTP и пагинация

**4.8 HTTP — общие правила.** Специфика эндпоинтов (пути, тела, поля ответа, ловушки совместимости) — n8n-workflow-registry §3.

- **4.8.1 Форма тела — по его типу.** Статическое → Raw + `application/json` (легаси не трогать); динамическое (с выражениями) через Raw даёт двойную сериализацию — запрос тихо битый (наблюдалось начиная с 2.20.9, после апгрейда с 2.9.4; на текущей версии инстанса не перепроверялось — SKILL.md §1) → JSON mode + Use Expression, `{{ {} }}` без ведущего `=` и без `JSON.stringify()`. [основание: ENG-16 · правило §4.8.1]
- **4.8.2 Три вида выражения — одно правило.** Выражение выглядит по-разному в трёх местах, и это одно правило, а не три противоречащих: в поле редактора в режиме выражения пишется `{{ … }}`; в сохранённом JSON узла и в коде SDK то же поле хранится как `"={{ … }}"` — ведущий `=` и есть признак режима выражения. Отсюда три отказа:
  - `=` без двойных фигурных скобок (`"=1+1"`) сохраняется и исполняется как текст «1+1», без ошибки; `validate_workflow` этого не ловит;
  - скобки внутри выражения не вычисляются: `={{ "x{{ 1+1 }}y" }}` падает «invalid syntax» — строку собирать сложением строк JavaScript внутри одной пары скобок;
  - `=[object Object]` в ошибке тела запроса — выражение обёрнуто дважды.
  После создания или правки через MCP поля с выражениями сверяются по сохранённому JSON узла *(§2.3 пункт 3б)*. Совет «ведущий `=`» в google-drive-docs (`references/failures.md`, правка jsonBody в браузере) говорит о сохранённом JSON и с этим правилом совпадает.
  [основание: ENG-17 · правило §4.8.2]
- **4.8.3 Токен — только через fx (Expression).** Прямая вставка в поле Value даёт «never used». [основание: ENG-18 · правило §4.8.3]
- **4.8.4 Response Format = Autodetect.** Явный JSON даёт circular; Include Headers выключить. [основание: ENG-19 · правило §4.8.4]
- **4.8.5 Rate limit держится на узле:** Items per Batch = 1 + Batch Interval, а не на ретраях *(R6, R11)*. [основание: ENG-20 · правило §4.8.5]
- **4.8.6 После HTTP-ноды поля предыдущих нод пропадают** — брать через `$('Нода').all()[i]` по позиции *(R5)*. [основание: ENG-21 · правило §4.8.6]
- **4.8.7 Сопоставление по позиции — только пока выход стоит к входу один к одному.** Маппинг ответа LLM — по позиции, не по id из ответа: модель может вернуть неверный id, и данные уедут к чужому объекту; `orig = items[i]`, id из ответа игнорировать. Граница этого правила и правила 4.8.6: позиция годится, только пока выход узла стоит к его входу один к одному. После Merge, фильтра, Switch и любого узла, меняющего число или порядок элементов, сопоставлять по ключу объекта (например `review_id`). Признак: результаты двух потоков перепутаны между собой без ошибки. [основание: ENG-22 · правило §4.8.7]
- **4.8.8 Ответ HTTP 200 не значит успех:** отказ бывает в теле *(R4, «Ошибка в теле при коде 200»)*. [основание: ENG-23 · правило §4.8.8]
- **4.8.9 Код ответа в выходе узла есть только с опцией «полный ответ».** `options.response.response.fullResponse: true` даёт поля `statusCode`, `statusMessage`, `headers` и тело; вместе с `neverError: true` по коду можно ветвиться в следующем узле. Без опции кода в выходе нет, а объект ошибки при `continueRegularOutput` несёт `message`, `code` и `status` — поля `httpCode` в нём нет. [основание: ENG-24 · правило §4.8.9]
- **4.8.10 Пустое тело ответа даёт элемент `{}`** — без поля вовсе, а не с пустым полем. Поэтому проверка «чтение не состоялось» ловит оба случая — «поля нет» и «поле пустое» — как одно событие *(R19)*. Признак: ответ 200 на несколько байт, а ветка «пусто» не сработала. [основание: ENG-25 · правило §4.8.10]
- **4.8.11 Настройки ответа лежат с двойной вложенностью:** `options.response.response.{responseFormat, fullResponse, neverError, outputPropertyName}` (описание узла HTTP Request 4.5). Путь с одной вложенностью `options.response.responseFormat` сохраняется без ошибки и не действует (HTTP Request 4.4). [основание: ENG-26 · правило §4.8.11]
- **4.8.12 Запись файла в GitHub — HTTP-узлом с явным `sha`, не встроенным узлом GitHub.** Почему: встроенный узел при правке файла сам берёт `sha` перед записью, поэтому чужая дозапись между нашим чтением и нашей записью теряется молча, без конфликта. С явным `sha` прочитанной версии такая гонка становится отказом записи, а не потерей. [основание: ENG-27 · правило §4.8.12]
- **4.8.13 Страница, найденная поиском (первая ссылка выдачи), не принимается без проверки поля идентичности на самой странице** — например артикула в разметке `itemprop="sku"`. Почему: проверка «номер встречается где-то в тексте» пропускает чужие товары. [основание: ENG-28 · правило §4.8.13]
- **4.8.14 Узел Telegram без `parse_mode` разбирает текст как Markdown** и падает на подчёркивании («can't parse entities»). Для текста с подчёркиванием в именах (имена воркфлоу, листов, полей) ставить `parse_mode` HTML. [основание: ENG-29 · правило §4.8.14]
- **4.8.15 Длинное сообщение Telegram молча теряет хвост.** Сообщение, которое не помещается в предел длины одного сообщения Telegram (4096 знаков текста по документации Telegram Bot API), доходит без хвоста или без части находок, и ошибки нет нигде. Длинный дайджест (список находок, список объектов) делится на несколько сообщений или его длина считается до отправки; если список урезан, это помечается в самом сообщении.
  - Почему: пропажу видно только по счёту — получатель не знает, что находок было больше *(A2)*.
  - Признак: число перечисленных объектов меньше числа найденных при том же прогоне.
  - [основание: ENG-30 · правило §4.8.15]
- **4.8.16 Факты, недоступные из облачной сессии Claude, снимает воркфлоу-зонд на сервере.** Публичный API собственного инстанса (`/api/v1/`) и ряд внешних сайтов из облачной сессии закрыты прокси (ответ 403) — такие факты снимает воркфлоу-зонд, а не сессия. Перечень недоступных внешних источников — n8n-workflow-registry. [основание: ENG-31 · правило §4.8.16]

**4.9 Пагинация — общая форма.**

**Закон пункта: список считается полным, только если неоткрывшиеся части явно перечислены и перечень пуст.** Почему: неполный список, записанный как полный, дальше выглядит полным для всех читателей.

- **4.9.1 Неполная пагинация роняет прогон ошибкой**, а не превращается в предупреждение внутри результата: курсор следующей страницы ещё есть, а предел страниц исчерпан — это ошибка. Читать до пустой страницы или до отсутствия курсора, а не фиксированным числом страниц; фиксированный предел — только как аварийный ограничитель, срабатывание которого и есть ошибка. [основание: ENG-32 · правило §4.9.1]
- **4.9.2 Курсор хранить персистентно.** `last_id=""` тянет с начала, поэтому стартовое значение читать как `max(raw_id)` из целевой таблицы. То же для окна дат: инкрементальная загрузка берёт начало от последней успешной метки в целевой таблице, а не «вчера» от даты прогона — иначе упавшая ночь не догружается никогда *(R19)*. [основание: ENG-33 · правило §4.9.2]
- **4.9.3 Курсор во встроенной пагинации HTTP-узла.** Параметр пагинации типа body не записывает вложенное поле тела по имени с точками (`settings.cursor.updatedAt`): запрос молча повторяет первую страницу. Рабочая форма — один параметр с именем верхнего поля тела (например `settings`) и значением-выражением, которое отдаёт объект целиком, с курсором из `$response.body.cursor`. Признак дефекта — число разных ключей в результате меньше числа строк. [основание: ENG-34 · правило §4.9.3]
- **4.9.4 Две формы пагинации.** Свой цикл по курсору (0 → fetch → has_more? → update → loop), с узлом Wait между страницами по ограничению частоты API; или встроенный механизм HTTP-ноды (`paginationCompleteWhen:other` + `completeExpression`). Какая форма, какой курсор и какая пауза у какого источника — n8n-workflow-registry §3. [основание: ENG-35 · правило §4.9.4]
- **4.9.5 Условие остановки у каждого эндпоинта своё, и перенос условия с одного эндпоинта на другой — отдельный класс ошибки.** Наблюдались как минимум три несовместимых варианта: пустой массив; `length < limit`; пустая строка в `last_id` ответа. Какой вариант у какого эндпоинта — смотреть в n8n-workflow-registry §3, не угадывать по аналогии. [основание: ENG-36 · правило §4.9.5]
- **4.9.6 `neverError` не гасит ошибку внутри `completeExpression`:** при ошибке API тело может быть undefined, и `.length` на нём бросит ошибку в самом выражении. [основание: ENG-37 · правило §4.9.6]
