## 4. Механика движка

Раздел про то, как n8n считает поток. Специфика конкретных API и эндпоинтов — в n8n-workflow-registry §3; здесь только то, что верно для любого эндпоинта.

**4.1 RAW-слой.** RAW = данные как есть, без фильтрации. Никогда не фильтровать по типу операции в RAW. Аналитика — только поверх RAW, отдельным слоем.

**4.2 Code node — форма.**

```js
const result = [];
result.push({ json: { field: value } });
return result;
```

- Run Once for All Items → `$input.all()` → массив (агрегация, expand). Run Once for Each Item → item (маппинг).
- В Code-нодах внутри пайплайна ВСЕГДА spread: `({ ...src, newField })`. Собирать item заново из перечисленных полей — тихая потеря данных *(A2)*.
- Полная замена кода при правке, не частичная.
- Regex: литералы `\s \S \d \w` ломаются через SDK → `var anyChar='[\\s\\S]'; new RegExp('...'+anyChar+'...')`.
- Внутри цикла SplitInBatches `throw` останавливает весь батч, а не одну строку. Вместо throw — вернуть item со статусом ошибки и разобрать статус отдельной ветвью. *(→ T3)*
- `axios`/`fetch` заблокированы без `NODE_FUNCTION_ALLOW_EXTERNAL=axios` в .env, падают тихо.
- Встроенные модули Node (например `crypto` для хэша) доступны в Code-узле только при переменной окружения `NODE_FUNCTION_ALLOW_BUILTIN`; её наличие на инстансе не проверено, поэтому хэш в `projects/card-content-sync` считается чистым JavaScript без `crypto` (`projects/card-content-sync/PLAN.md`). Прежде чем строить на встроенном модуле — пробный прогон.
- `$env` не работает вообще, бросает в рантайме.

**4.3 executeOnce — где работает и где нет.** Правило двустороннее, и обратная сторона важнее прямой.

- На ПЕРВОМ узле после триггера работает штатно и является основным лечением раздувания потока: узел-справочник сразу за триггером с галочкой делает ровно один вызов вместо N.
- В середине цепочки A→B→C НЕ работает — узел всё равно отрабатывает на каждый item. Ставить галочку на промежуточный узел, чтобы «схлопнуть поток заранее», бессмысленно; лечить надо у источника (`$('node').all()` или порядок узлов).
- Code-нода в режиме `runOnceForAllItems` схлопывает поток в один item сама. Поэтому бороться с размножением ниже неё смысла нет — проверять надо только участок от триггера до первой такой ноды.
- Перед установкой галочки смотреть connections: узел сразу за триггером — лечим здесь; узел глубже — лечим у источника.

**4.4 pairedItem — трассировка и её границы.** `$('Node').item` резолвится через pairedItem-трассировку, и она рвётся в двух местах.

- На пачке трассировка схлопывается → `ExpressionError: Multiple matches found`. Лечение — `splitInBatches(batchSize:1)` вокруг per-item шагов.
- После узла, размножающего один item в N (`executeWorkflow` fan-out), выражение к узлу ВЫШЕ размножения резолвится только для output-item с индексом 0; для остальных — `ExpressionError: Paired item data for item from node '...' is unavailable` (`descriptionKey: pairedItemNoInfo`).
- Лечение второго случая: `.first()` — если референсный узел по конструкции гарантированно отдаёт ровно один item за итерацию (например `splitInBatches` с `batchSize:1` выше по цепочке); `.first()` не зависит от трассировки. **Если такой гарантии нет — `.first()` даст неверные данные вместо ошибки, что хуже;** тогда `.all()` с явным матчингом по ключу.
- `$json` в глубине ветвлений — заменять на `$('Node').item.json`.

**4.5 Fan-out и параллельность.** Ветки fan-out НЕ параллельны: выполняются последовательно сверху вниз по координате Y. Реальная параллельность — только Execute Workflow с `mode:"each"` и `waitForSubWorkflow:false` *(R10)*.

Fan-out одного выхода пишется как `.to(a).add(source).to(b)`, не `.to([a,b])` — второй получатель в форме `.to([a,b])` молчит навсегда *(R1b)*. Тот же приём — единственный способ запустить две ветки от триггера: два независимых узла-триггера одного типа не работают, MCP запускает только первый *(R10)*.

**4.6 Merge и Switch.** Основная цепочка merge собирается плоско: каждый вход отдельным `.add(source).to(merge.input(N))`. Число проводов обязано равняться `numberOfInputs`, иначе лишние источники отбрасываются молча *(R9)*. Off-by-one: `parameters.useDataOfInput` считается с 1, `connections.main[index]` — с 0. Switch без `options.fallbackOutput:"extra"` + `renameFallbackOutput` теряет items *(R8)*.

**4.7 Execute Workflow — что возвращается в родителя.** С `waitForSubWorkflow:true` узел отдаёт дальше не квитанцию «готово», а ВСЕ items, которые саб-воркфлоу вернул последним узлом. Это главный источник неожиданного размножения потока — полный разбор в R16.

**4.8 HTTP — общие правила.** Специфика эндпоинтов (пути, тела, поля ответа, ловушки совместимости) — n8n-workflow-registry §3.

- Критерий выбора формы тела — его тип: статическое → Raw + `application/json` (легаси не трогать); динамическое (с выражениями) через Raw даёт двойную сериализацию (наблюдалось начиная с 2.20.9, после апгрейда с 2.9.4; на текущей версии инстанса не перепроверялось — SKILL.md §1) → JSON mode + Use Expression, `{{ {} }}` без ведущего `=` и без `JSON.stringify()`.
- Токен — только через fx (Expression). Прямая вставка в поле Value даёт «never used».
- Response Format = Autodetect. Явный JSON даёт circular; Include Headers выключить.
- Rate limit держится на узле: Items per Batch = 1 + Batch Interval, а не на ретраях *(R6, R11)*.
- После HTTP-ноды поля предыдущих нод пропадают — брать через `$('Нода').all()[i]` по позиции *(R5)*.
- Маппинг ответа LLM — по позиции, не по id из ответа: модель может вернуть неверный id, и данные уедут к чужому SKU. `orig = items[i]`, id из ответа игнорировать.
- Ответ HTTP 200 не значит успех: отказ бывает в теле *(R4, «Ошибка в теле при коде 200»)*.
- Запись файла в GitHub — HTTP-узлом с явным `sha`, не встроенным узлом GitHub: встроенный узел при правке файла сам берёт `sha` перед записью, поэтому чужая дозапись между нашим чтением и нашей записью теряется молча, без конфликта (журнал `projects/kontext-reduktion/LOG.md` запись Р-16). С явным `sha` прочитанной версии такая гонка становится отказом записи, а не потерей.
- Страница, найденная поиском (первая ссылка выдачи), не принимается без проверки поля идентичности на самой странице — например артикула в разметке `itemprop="sku"`. Проверка «номер встречается где-то в тексте» пропускает чужие товары (журнал `projects/deklaration-ozon/LOG.md` записи Р-28, Р-31, Р-32; labs/ozon-ue `t-product-data-model.md`, проверка по `"sku">номер<`).
- Узел Telegram без `parse_mode` разбирает текст как Markdown и падает на подчёркивании («can't parse entities»); для текста с именами вида `LM_DECL` ставить `parse_mode` HTML (исполнения 74384–74387 воркфлоу `LM_DECL Intake` `qKgc8hhOLwehejYp`, позиция очереди AH-20).
- Публичный API собственного инстанса (`/api/v1/`) и ряд внешних сайтов из облачной сессии Claude закрыты прокси (ответ 403) — такие факты снимает воркфлоу-зонд на сервере, а не сессия (`projects/n8n-map/PLAN.md`, зонд Z-12). Перечень недоступных внешних источников — n8n-workflow-registry.

**4.9 Пагинация — общая форма.** Курсор хранить персистентно: `last_id=""` тянет с начала, поэтому стартовое значение читать как `max(raw_id)` из целевой таблицы. То же для окна дат: инкрементальная загрузка берёт начало от последней успешной метки в целевой таблице, а не «вчера» от даты прогона — иначе упавшая ночь не догружается никогда *(R19)*.

**Список считается полным, только если неоткрывшиеся части явно перечислены и перечень пуст.** Неполная пагинация (курсор следующей страницы ещё есть, а предел страниц исчерпан) роняет прогон ошибкой, а не превращается в предупреждение внутри результата: неполный список, записанный как полный, дальше выглядит полным для всех читателей (журнал `projects/n8n-map/LOG.md` запись Р-7, пункт 5 — Registry Sync падает при `nextCursor` после десяти страниц; `projects/archive-recon/LOG.md` записи Т-3 и Р-11). Читать до пустой страницы или до отсутствия курсора, а не фиксированным числом страниц; фиксированный предел — только как аварийный ограничитель, срабатывание которого и есть ошибка.

**Курсор во встроенной пагинации HTTP-узла.** Параметр пагинации типа body не записывает вложенное поле тела по имени с точками (`settings.cursor.updatedAt`): запрос молча повторяет первую страницу — 30 страниц, 3000 записей и только 100 разных. Рабочая форма — один параметр с именем верхнего поля (`settings`) и значением-выражением, которое отдаёт объект целиком (с курсором из `$response.body.cursor`) (журнал `projects/deklaration-ozon/LOG.md` запись Т-6, WB `/content/v2/get/cards/list`). Признак дефекта — число разных ключей в результате меньше числа строк.

Механика по источникам: WB — курсор `rrdid` циклом (0 → fetch → has_more? → update → loop) с Wait 70с по rate limit; Ozon — встроенный механизм HTTP-ноды (`paginationCompleteWhen:other` + `completeExpression`).

**Условие остановки у каждого эндпоинта своё, и перенос условия с одного эндпоинта на другой — отдельный класс ошибки.** Наблюдались как минимум три несовместимых варианта: пустой массив; `length < limit`; пустая строка в `last_id` ответа. Какой вариант у какого эндпоинта — смотреть в n8n-workflow-registry §3, не угадывать по аналогии. Отдельно: `neverError` не гасит ошибку внутри `completeExpression` — при ошибке API тело может быть undefined, и `.length` на нём бросит ошибку в самом выражении.

**4.10 Время.** Таймзона сервера — Europe/Berlin. Москва часы не переводит и стоит на UTC+3 постоянно, Берлин переводит: летом UTC+2, зимой UTC+1. Значит **смещение Берлин → МСК равно +1 час летом и +2 часа зимой**, а не +3. Формула «МСК = now+3ч» верна только если `now` — часы UTC; рядом с записью «tz сервера = Europe/Berlin» она даёт ошибку в один-два часа. Именно в такой форме она стояла в этом пункте до 2026-09-26.

Дедлайн WB FBS — 16:00 МСК всегда.

**Даты из внешних источников разбирать явно, по всем встреченным форматам**, а не через `new Date(строка)`: неизвестный формат даёт `Invalid Date` без ошибки, и запись молча выпадает из окна. Наблюдались:
- Google Sheets в режиме FORMATTED_VALUE отдаёт час без ведущего нуля («2026-09-28 6:53:35»); `new Date('…T6:53:35+03:00')` — Invalid Date, все заказы 00:00–09:59 МСК выпали из дайджеста (журнал `projects/wb-logistics/LOG.md` запись Р-95). Разбирать регулярным выражением;
- Wildberries в карточках отдаёт даты как ММ-ДД-ГГ (01-27-27 = 27.01.2027) (`meta/PRODUCT_DATA_HIERARCHY.md` раздел 4; `projects/deklaration-wb/STATE.md`). Форматы конкретных эндпоинтов — n8n-workflow-registry §3.
Дату в таблицу писать так, чтобы Sheets распознал её как дату (текст ГГГГ-ММ-ДД Sheets разбирает как дату): дата, легшая текстом, выключает условное форматирование и сортировку без ошибки (`meta/DECLARATION_SCAN.md` ловушка 6).

**Гонка расписаний в одну минуту.** Два воркфлоу на одном и том же cron-времени не синхронизированы: читатель в :00:00 читает раньше, чем писатель той же минуты дописал к :00:26. Наблюдалось трижды за сутки (Morning Forecast против Order Intake в 07:00, Evening Report против Order Intake в 18:00 — журнал `projects/wb-logistics/LOG.md` запись Р-95). Читателя ставить на несколько минут позже писателя, от которого он зависит.

Чем это кончается на объекте. Воркфлоу `WB FBS Decision Engine` (`S4rZMUkI21dVu3ML`) стоит на cron `0 11,13,15 * * *` и явной таймзоны не имеет, то есть считается по Берлину. Проверено 2026-09-26: три прогона приходятся на 12:00, 14:00 и 16:00 МСК — последний совпадает с дедлайном, а зимой сдвинется на 17:00 МСК, то есть за дедлайн. Воркфлоу принимает решения о поставке относительно этого дедлайна. У него же не задан `errorWorkflow`, поэтому отказ не будет виден никому.

Отсюда правило: расписание задаётся явным `settings.timezone`, и НИКОГДА пересчётом смещения в голове *(R7)*. Если время в задаче названо по Москве, в `settings.timezone` пишется `Europe/Moscow`, а часы в cron — сразу московские. Смещение не считать ни при какой погоде: оно меняется дважды в год, а cron — нет.

**4.11 Память и OOM (CPX32).** Не материализовать полную историю или HTML в один item. Средства: date-фильтр в запросе (например последние 60 дней); `this.helpers.httpRequest` с HTML как локальной переменной; `runOnceForAllItems` + `$input.first()`; изоляция тяжёлого шага через Execute Workflow.

**4.12 Data Table.** `get` с per-item фильтром `keyValue={{$json.field}}` ненадёжен при N>1 items: схлопывает в 1 без ошибки, даже с `executeOnce:false`. Рабочая форма — `returnAll:true` + матчинг по ключу в Code-ноде *(→ T1-B)*.
