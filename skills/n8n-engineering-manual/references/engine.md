## 4. Механика движка

Раздел про то, как n8n считает поток. Специфика конкретных API и эндпоинтов — в n8n-workflow-registry §3; здесь только то, что верно для любого эндпоинта и любого инстанса.

**Закон раздела.** Движок считает поток элементами (items) и при несовпадении формы — режим узла, число элементов, вид выражения, формат значения, вложенность параметра — не падает, а молча берёт первое, пустое или буквальное. Поэтому форма задаётся явно, а результат проверяется по выходу узла и по объекту, а не по конфигурации *(A2, A1)*. Все пункты ниже — частные случаи: где именно движок подменяет, и какая явная форма это закрывает.

**4.1 RAW-слой.** RAW = данные как есть, без фильтрации. Никогда не фильтровать по типу операции в RAW. Аналитика — только поверх RAW, отдельным слоем. Почему: отфильтрованное при загрузке уже не восстановить из своего слоя, а новый тип операции, о котором фильтр не знал, исчезает молча. Основание: случай не записан; принцип «RAW first» — SKILL.md §9 — правило §4.1.

**4.2 Code node — форма.**

```js
const result = [];
result.push({ json: { field: value } });
return result;
```

**4.2.1 Режим выбирают по тому, чем пользуется код.** Run Once for All Items → `$input.all()` → массив (агрегация, expand). Run Once for Each Item → item (маппинг). `$json` и `$input.item` — режим «для каждого», `$input.all()` — режим «для всех».
- Почему: в режиме «для всех» `$json` не падает, а молча берёт первый элемент (три элемента на входе — код видит один из трёх).
- Обратная сторона: `$input.all()` в режиме «для каждого» падает ошибкой «Can't use .all() here».
- Основание: 3 случая, последний 2026-10-12 — отчёт синтеза, правило §4.2.1.

**4.2.2 В Code-нодах внутри пайплайна ВСЕГДА spread: `({ ...src, newField })`.** Почему: item, собранный заново из перечисленных полей, теряет все неперечисленные — без ошибки *(A2)*. Признак: в целевой таблице появляются почти пустые строки, счётчики теряются молча. Основание: 1 случай, последний 2026-07-23 — отчёт синтеза, правило §4.2.2.

**4.2.3 Полная замена кода при правке, не частичная.** Принятие предложенной замены — по §2.4 (дословный текущий код и построчное сравнение). Основание: случай не записан — отчёт синтеза, правило §4.2.3.

**4.2.4 Regex через SDK.** Литералы `\s \S \d \w` ломаются при записи через SDK → `var anyChar='[\\s\\S]'; new RegExp('...'+anyChar+'...')`. Основание: случай не записан — отчёт синтеза, правило §4.2.4.

**4.2.5 Внутри цикла SplitInBatches `throw` останавливает весь батч, а не одну строку.** Вместо `throw` — вернуть item со статусом ошибки и разобрать статус отдельной ветвью *(→ T3)*. Признак: один плохой элемент (например пустой ответ модели) прерывает обработку всей пачки. Основание: 1 случай (на двух воркфлоу), последний 2026-07-23 — отчёт синтеза, правило §4.2.5.

**4.2.6 `axios`/`fetch` заблокированы** без `NODE_FUNCTION_ALLOW_EXTERNAL=axios` в .env и падают тихо. Основание: случай не записан — отчёт синтеза, правило §4.2.6.

**4.2.7 Встроенные модули Node** (например `crypto` для хэша) доступны в Code-узле только при переменной окружения `NODE_FUNCTION_ALLOW_BUILTIN`. Прежде чем строить на встроенном модуле — пробный прогон, который показывает, что модуль доступен; без такой пробы считать без встроенного модуля (хэш — чистым JavaScript). Основание: 1 случай, дата не записана — отчёт синтеза, правило §4.2.7.

**4.2.8 `$env` не работает вообще**, бросает в рантайме. Основание: случай не записан — отчёт синтеза, правило §4.2.8.

**4.2.9 Ключ доступа (credential) Code-узлу недоступен.** `this.helpers.httpRequestWithAuthentication` отвечает ошибкой «The function "helpers.httpRequestWithAuthentication" is not supported in the Code Node». Вызов с ключом — только отдельным узлом HTTP Request; `catch`, который не передаёт ошибку дальше, в Code-узле не ставить.
- Почему: `try/catch` вокруг такого вызова превращает отказ в зелёный прогон — вызова не было, а исполнение `success`.
- Основание: 2 случая, последний 2026-10-12 — отчёт синтеза, правило §4.2.9.

**4.2.10 Память воркфлоу между прогонами (static data) меняется только в плановом прогоне.** Память, которую код ведёт через `$getWorkflowStaticData` («последняя отправленная неделя», «уже виденные ID»), сохраняется только в плановом прогоне опубликованной версии. Ручной и пробный запуск (`execute_workflow` в режиме `manual`, кнопка в редакторе) её изменений не сохраняет. Запуск боевым вебхуком не проверялся.
- Следствие 1: после ручного запуска сводки следующий плановый прогон пришлёт ту же сводку ещё раз. Это ожидаемое поведение, а не дефект: причину повтора не искать, владельца предупредить до ручного запуска.
- Следствие 2: «сдвинуть» память ручным пробным прогоном нельзя. Ручной прогон проверяет код, память проверяется плановым прогоном; где повтор сообщения недопустим, ручной пробный прогон не делается вовсе.
- Признак: повтор уже отправленного сообщения в первом плановом прогоне после ручного.
- Основание: 2 случая (два независимых воркфлоу Telegram-сводок), последний 2026-10-15 — отчёт синтеза, правило §4.2.10.

**4.3 executeOnce — что делает.** Узел с галочкой Execute Once обрабатывает только ПЕРВЫЙ входной элемент и выдаёт один результат, где бы он ни стоял: сразу за триггером, в середине цепочки, после Merge. Проверено на узлах Set (после Merge — 5 элементов на входе, 1 на выходе, первый; в середине цепочки — 3 и 1); на других типах узлов (HTTP Request, Google Sheets) не перепроверено.

- **4.3.1** Ставить галочку, когда узел должен сработать один раз за прогон: справочник сразу за триггером, одно чтение листа, одно уведомление. Это основное лечение раздувания потока — один вызов вместо N *(R16)*.
- **4.3.2** Не ставить, когда нужно обработать каждый элемент: остальные отбрасываются молча, без ошибки *(A2)*. Признак: из многих страниц или записей после узла дошла одна.
- **4.3.3** Code-нода в режиме `runOnceForAllItems` схлопывает поток в один item сама. Поэтому бороться с размножением ниже неё смысла нет — проверять надо только участок от триггера до первой такой ноды.

Не путать: «в середине цепочки Execute Once не работает, лечить у источника» — на деле работает в любом месте цепочки, проверено пробой.

Основание §4.3: 2 случая, последний 2026-10-12 — отчёт синтеза, правило §4.3.

**4.4 pairedItem — трассировка и её границы.** `$('Node').item` резолвится через pairedItem-трассировку, и она рвётся в двух местах.

- **4.4.1** На пачке трассировка схлопывается → `ExpressionError: Multiple matches found`. Лечение — `splitInBatches(batchSize:1)` вокруг per-item шагов.
- **4.4.2** После узла, размножающего один item в N (`executeWorkflow` fan-out), выражение к узлу ВЫШЕ размножения резолвится только для output-item с индексом 0; для остальных — `ExpressionError: Paired item data for item from node '...' is unavailable` (`descriptionKey: pairedItemNoInfo`).
- **4.4.3** Лечение второго случая: `.first()` — если референсный узел по конструкции гарантированно отдаёт ровно один item за итерацию (например `splitInBatches` с `batchSize:1` выше по цепочке); `.first()` не зависит от трассировки. **Если такой гарантии нет — `.first()` даст неверные данные вместо ошибки, что хуже;** тогда `.all()` с явным матчингом по ключу.
- **4.4.4** `$json` в глубине ветвлений — заменять на `$('Node').item.json`.

Основание §4.4: 1 случай, последний 2026-07-21 — отчёт синтеза, правило §4.4.

**4.5 Fan-out и параллельность.** Ветки fan-out НЕ параллельны: выполняются последовательно сверху вниз по координате Y. Реальная параллельность — только Execute Workflow с `mode:"each"` и `waitForSubWorkflow:false` *(R10)*.

Fan-out одного выхода пишется как `.to(a).add(source).to(b)`, не `.to([a,b])` — второй получатель в форме `.to([a,b])` молчит навсегда *(R1b)*. Тот же приём — единственный способ запустить две ветки от триггера: два независимых узла-триггера одного типа не работают, MCP запускает только первый *(R10)*.

Основание §4.5: 1 случай, последний 2026-07-03 — отчёт синтеза, правило §4.5.

**4.6 Merge и Switch.** Основная цепочка merge собирается плоско: каждый вход отдельным `.add(source).to(merge.input(N))` — вложенные `.to(merge.input(N))` дают регрессию связей. Число проводов обязано равняться `numberOfInputs`, иначе лишние источники отбрасываются молча *(R9)*. Off-by-one: `parameters.useDataOfInput` считается с 1, `connections.main[index]` — с 0. Switch без `options.fallbackOutput:"extra"` + `renameFallbackOutput` теряет items *(R8)*. Основание: 1 случай, последний 2026-07-05 — отчёт синтеза, правило §4.6.

**4.7 Execute Workflow — что возвращается в родителя.** С `waitForSubWorkflow:true` узел отдаёт дальше не квитанцию «готово», а ВСЕ items, которые саб-воркфлоу вернул последним узлом. Это главный источник неожиданного размножения потока — полный разбор в R16.

**4.8 HTTP — общие правила.** Специфика эндпоинтов (пути, тела, поля ответа, ловушки совместимости) — n8n-workflow-registry §3.

- **4.8.1 Форма тела — по его типу.** Статическое → Raw + `application/json` (легаси не трогать); динамическое (с выражениями) через Raw даёт двойную сериализацию — запрос тихо битый (наблюдалось начиная с 2.20.9, после апгрейда с 2.9.4; на текущей версии инстанса не перепроверялось — SKILL.md §1) → JSON mode + Use Expression, `{{ {} }}` без ведущего `=` и без `JSON.stringify()`. Основание: 1 случай, дата не записана (наблюдение версии 2.20.9) — отчёт синтеза, правило §4.8.1.
- **4.8.2 Три вида выражения — одно правило.** Выражение выглядит по-разному в трёх местах, и это одно правило, а не три противоречащих: в поле редактора в режиме выражения пишется `{{ … }}`; в сохранённом JSON узла и в коде SDK то же поле хранится как `"={{ … }}"` — ведущий `=` и есть признак режима выражения. Отсюда три отказа:
  - `=` без двойных фигурных скобок (`"=1+1"`) сохраняется и исполняется как текст «1+1», без ошибки; `validate_workflow` этого не ловит;
  - скобки внутри выражения не вычисляются: `={{ "x{{ 1+1 }}y" }}` падает «invalid syntax» — строку собирать сложением строк JavaScript внутри одной пары скобок;
  - `=[object Object]` в ошибке тела запроса — выражение обёрнуто дважды.
  После создания или правки через MCP поля с выражениями сверяются по сохранённому JSON узла *(§2.3 пункт 3б)*. Совет «ведущий `=`» в google-drive-docs (`references/failures.md`, правка jsonBody в браузере) говорит о сохранённом JSON и с этим правилом совпадает.
  Основание: 6 случаев, последний 2026-10-12 — отчёт синтеза, правило §4.8.2.
- **4.8.3 Токен — только через fx (Expression).** Прямая вставка в поле Value даёт «never used». Основание: случай не записан — отчёт синтеза, правило §4.8.3.
- **4.8.4 Response Format = Autodetect.** Явный JSON даёт circular; Include Headers выключить. Основание: случай не записан — отчёт синтеза, правило §4.8.4.
- **4.8.5 Rate limit держится на узле:** Items per Batch = 1 + Batch Interval, а не на ретраях *(R6, R11)*. Основание: случай не записан — отчёт синтеза, правило §4.8.5.
- **4.8.6 После HTTP-ноды поля предыдущих нод пропадают** — брать через `$('Нода').all()[i]` по позиции *(R5)*. Основание: см. R5 (дом механизма — корень R5) — отчёт синтеза, правило §4.8.6.
- **4.8.7 Сопоставление по позиции — только пока выход стоит к входу один к одному.** Маппинг ответа LLM — по позиции, не по id из ответа: модель может вернуть неверный id, и данные уедут к чужому объекту; `orig = items[i]`, id из ответа игнорировать. Граница этого правила и правила 4.8.6: позиция годится, только пока выход узла стоит к его входу один к одному. После Merge, фильтра, Switch и любого узла, меняющего число или порядок элементов, сопоставлять по ключу объекта (например `review_id`). Признак: результаты двух потоков перепутаны между собой без ошибки. Основание: 1 случай, последний 2026-06 — отчёт синтеза, правило §4.8.7.
- **4.8.8 Ответ HTTP 200 не значит успех:** отказ бывает в теле *(R4, «Ошибка в теле при коде 200»)*. Основание: см. R4 (дом механизма — корень R4) — отчёт синтеза, правило §4.8.8.
- **4.8.9 Код ответа в выходе узла есть только с опцией «полный ответ».** `options.response.response.fullResponse: true` даёт поля `statusCode`, `statusMessage`, `headers` и тело; вместе с `neverError: true` по коду можно ветвиться в следующем узле. Без опции кода в выходе нет, а объект ошибки при `continueRegularOutput` несёт `message`, `code` и `status` — поля `httpCode` в нём нет. Основание: 1 случай (проба), последний 2026-10-12 — отчёт синтеза, правило §4.8.9.
- **4.8.10 Пустое тело ответа даёт элемент `{}`** — без поля вовсе, а не с пустым полем. Поэтому проверка «чтение не состоялось» ловит оба случая — «поля нет» и «поле пустое» — как одно событие *(R19)*. Признак: ответ 200 на несколько байт, а ветка «пусто» не сработала. Основание: 2 случая, последний 2026-10-12 — отчёт синтеза, правило §4.8.10.
- **4.8.11 Настройки ответа лежат с двойной вложенностью:** `options.response.response.{responseFormat, fullResponse, neverError, outputPropertyName}` (описание узла HTTP Request 4.5). Путь с одной вложенностью `options.response.responseFormat` сохраняется без ошибки и не действует (HTTP Request 4.4). Основание: 2 случая, последний 2026-10-12 — отчёт синтеза, правило §4.8.11.
- **4.8.12 Запись файла в GitHub — HTTP-узлом с явным `sha`, не встроенным узлом GitHub.** Почему: встроенный узел при правке файла сам берёт `sha` перед записью, поэтому чужая дозапись между нашим чтением и нашей записью теряется молча, без конфликта. С явным `sha` прочитанной версии такая гонка становится отказом записи, а не потерей. Основание: 1 случай, последний 2026-09-24 — отчёт синтеза, правило §4.8.12.
- **4.8.13 Страница, найденная поиском (первая ссылка выдачи), не принимается без проверки поля идентичности на самой странице** — например артикула в разметке `itemprop="sku"`. Почему: проверка «номер встречается где-то в тексте» пропускает чужие товары. Основание: 3 случая, последний 2026-10-04 — отчёт синтеза, правило §4.8.13.
- **4.8.14 Узел Telegram без `parse_mode` разбирает текст как Markdown** и падает на подчёркивании («can't parse entities»). Для текста с подчёркиванием в именах (имена воркфлоу, листов, полей) ставить `parse_mode` HTML. Основание: 1 случай, последний 2026-10-03 — отчёт синтеза, правило §4.8.14.
- **4.8.15 Длинное сообщение Telegram молча теряет хвост.** Сообщение, которое не помещается в предел длины одного сообщения Telegram (4096 знаков текста по документации Telegram Bot API), доходит без хвоста или без части находок, и ошибки нет нигде. Длинный дайджест (список находок, список объектов) делится на несколько сообщений или его длина считается до отправки; если список урезан, это помечается в самом сообщении.
  - Почему: пропажу видно только по счёту — получатель не знает, что находок было больше *(A2)*.
  - Признак: число перечисленных объектов меньше числа найденных при том же прогоне.
  - Основание: 1 случай, последний 2026-10-08 — отчёт синтеза, правило §4.8.15.
- **4.8.16 Факты, недоступные из облачной сессии Claude, снимает воркфлоу-зонд на сервере.** Публичный API собственного инстанса (`/api/v1/`) и ряд внешних сайтов из облачной сессии закрыты прокси (ответ 403) — такие факты снимает воркфлоу-зонд, а не сессия. Перечень недоступных внешних источников — n8n-workflow-registry. Основание: 1 случай, дата не записана — отчёт синтеза, правило §4.8.16.

**4.9 Пагинация — общая форма.**

**Закон пункта: список считается полным, только если неоткрывшиеся части явно перечислены и перечень пуст.** Почему: неполный список, записанный как полный, дальше выглядит полным для всех читателей.

- **4.9.1 Неполная пагинация роняет прогон ошибкой**, а не превращается в предупреждение внутри результата: курсор следующей страницы ещё есть, а предел страниц исчерпан — это ошибка. Читать до пустой страницы или до отсутствия курсора, а не фиксированным числом страниц; фиксированный предел — только как аварийный ограничитель, срабатывание которого и есть ошибка. Основание: 2 случая, последний 2026-09-27 — отчёт синтеза, правило §4.9.1.
- **4.9.2 Курсор хранить персистентно.** `last_id=""` тянет с начала, поэтому стартовое значение читать как `max(raw_id)` из целевой таблицы. То же для окна дат: инкрементальная загрузка берёт начало от последней успешной метки в целевой таблице, а не «вчера» от даты прогона — иначе упавшая ночь не догружается никогда *(R19)*. Основание: 1 случай, дата не записана — отчёт синтеза, правило §4.9.2.
- **4.9.3 Курсор во встроенной пагинации HTTP-узла.** Параметр пагинации типа body не записывает вложенное поле тела по имени с точками (`settings.cursor.updatedAt`): запрос молча повторяет первую страницу. Рабочая форма — один параметр с именем верхнего поля тела (например `settings`) и значением-выражением, которое отдаёт объект целиком, с курсором из `$response.body.cursor`. Признак дефекта — число разных ключей в результате меньше числа строк. Основание: 1 случай, последний 2026-10-02 — отчёт синтеза, правило §4.9.3.
- **4.9.4 Две формы пагинации.** Свой цикл по курсору (0 → fetch → has_more? → update → loop), с узлом Wait между страницами по ограничению частоты API; или встроенный механизм HTTP-ноды (`paginationCompleteWhen:other` + `completeExpression`). Какая форма, какой курсор и какая пауза у какого источника — n8n-workflow-registry §3. Основание: 2 источника, дата не записана — отчёт синтеза, правило §4.9.4.
- **4.9.5 Условие остановки у каждого эндпоинта своё, и перенос условия с одного эндпоинта на другой — отдельный класс ошибки.** Наблюдались как минимум три несовместимых варианта: пустой массив; `length < limit`; пустая строка в `last_id` ответа. Какой вариант у какого эндпоинта — смотреть в n8n-workflow-registry §3, не угадывать по аналогии. Основание: 3 эндпоинта, дата не записана — отчёт синтеза, правило §4.9.5.
- **4.9.6 `neverError` не гасит ошибку внутри `completeExpression`:** при ошибке API тело может быть undefined, и `.length` на нём бросит ошибку в самом выражении. Основание: 1 случай, последний 2026-07-23 — отчёт синтеза, правило §4.9.6.

**4.10 Время.**

**Закон пункта: расписание задаётся явным `settings.timezone`, и НИКОГДА пересчётом смещения в голове *(R7)*.** Если время в задаче названо по Москве, в `settings.timezone` пишется `Europe/Moscow`, а часы в cron — сразу московские. Смещение не считать ни при какой погоде. Почему: смещение меняется дважды в год, а cron — нет.

- **4.10.1 Арифметика смещения.** Москва часы не переводит и стоит на UTC+3 постоянно, Берлин переводит: летом UTC+2, зимой UTC+1. Значит **смещение Берлин → МСК равно +1 час летом и +2 часа зимой**, а не +3. Формула «МСК = now+3ч» верна только если `now` — часы UTC; при часовом поясе сервера Europe/Berlin она даёт ошибку в один-два часа (часовой пояс своего сервера — с экземпляра в момент использования, SKILL.md §1). Признак: воркфлоу без явной таймзоны, чьё расписание стоит у дедлайна по Москве, летом попадает на дедлайн, а зимой уезжает на час за него; если у него же нет воркфлоу ошибок, отказ не видит никто. Основание: 1 случай, 2026-09-26 — отчёт синтеза, правило §4.10.1.
  Не путать: «МСК = now+3ч» — верно только для часов UTC, а не для времени сервера.
- **4.10.2 Даты из внешних источников разбирать явно, по всем встреченным форматам**, а не через `new Date(строка)`. Почему: неизвестный формат даёт `Invalid Date` без ошибки, и запись молча выпадает из окна. Наблюдалось: Google Sheets в режиме FORMATTED_VALUE отдаёт час без ведущего нуля («2026-09-28 6:53:35»); `new Date('…T6:53:35+03:00')` — Invalid Date, и все записи с часом 0–9 выпали из окна. Разбирать регулярным выражением. Форматы дат конкретных API (например дат в карточках Wildberries) — n8n-workflow-registry (§3 и `references/cards-and-declarations.md`). Основание: 1 случай, последний 2026-10-02 — отчёт синтеза, правило §4.10.2.
- **4.10.3 Дату в таблицу писать так, чтобы Sheets распознал её как дату** (текст ГГГГ-ММ-ДД Sheets разбирает как дату). Почему: дата, легшая текстом, выключает условное форматирование и сортировку без ошибки. Основание: 1 случай, дата не записана — отчёт синтеза, правило §4.10.3.
- **4.10.4 Гонка расписаний в одну минуту.** Два воркфлоу на одном и том же cron-времени не синхронизированы: читатель, стартовавший в начале минуты, читает раньше, чем писатель той же минуты дописал. Читателя ставить на несколько минут позже писателя, от которого он зависит. Признак: в отчёте читателя не хватает записей последних минут перед прогоном. Основание: 3 наблюдения за одни сутки, последнее 2026-10-02 — отчёт синтеза, правило §4.10.4.

**4.11 Память и OOM.** Не материализовать полную историю или HTML в один item. Почему: у сервера ограниченная память, и один огромный item роняет исполнение. Средства: date-фильтр в запросе (например последние 60 дней); `this.helpers.httpRequest` с HTML как локальной переменной; `runOnceForAllItems` + `$input.first()`; изоляция тяжёлого шага через Execute Workflow. Основание: случай не записан — отчёт синтеза, правило §4.11.

**4.12 Data Table.** `get` с per-item фильтром `keyValue={{$json.field}}` ненадёжен при N>1 items: схлопывает в 1 без ошибки, даже с `executeOnce:false`. Рабочая форма — `returnAll:true` + матчинг по ключу в Code-ноде *(→ T1-B)*. Основание: случай не записан — отчёт синтеза, правило §4.12.
