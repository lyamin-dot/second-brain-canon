## 4. Механика движка (продолжение): время, память, Data Table

**4.10 Время.**

**Закон пункта: расписание задаётся явным `settings.timezone`, и НИКОГДА пересчётом смещения в голове *(R7)*.** Если время в задаче названо по Москве, в `settings.timezone` пишется `Europe/Moscow`, а часы в cron — сразу московские. Смещение не считать ни при какой погоде. Почему: смещение меняется дважды в год, а cron — нет.

- **4.10.1 Арифметика смещения.** Москва часы не переводит и стоит на UTC+3 постоянно, Берлин переводит: летом UTC+2, зимой UTC+1. Значит **смещение Берлин → МСК равно +1 час летом и +2 часа зимой**, а не +3. Формула «МСК = now+3ч» верна только если `now` — часы UTC; при часовом поясе сервера Europe/Berlin она даёт ошибку в один-два часа (часовой пояс своего сервера — с экземпляра в момент использования, SKILL.md §1). Признак: воркфлоу без явной таймзоны, чьё расписание стоит у дедлайна по Москве, летом попадает на дедлайн, а зимой уезжает на час за него; если у него же нет воркфлоу ошибок, отказ не видит никто. [основание: ENG-38 · правило §4.10.1]
  Не путать: «МСК = now+3ч» — верно только для часов UTC, а не для времени сервера.
- **4.10.2 Даты из внешних источников разбирать явно, по всем встреченным форматам**, а не через `new Date(строка)`. Почему: неизвестный формат даёт `Invalid Date` без ошибки, и запись молча выпадает из окна. Наблюдалось: Google Sheets в режиме FORMATTED_VALUE отдаёт час без ведущего нуля («2026-09-28 6:53:35»); `new Date('…T6:53:35+03:00')` — Invalid Date, и все записи с часом 0–9 выпали из окна. Разбирать регулярным выражением. Форматы дат конкретных API (например дат в карточках Wildberries) — n8n-workflow-registry (§3 и `references/cards-and-declarations.md`). [основание: ENG-39 · правило §4.10.2]
- **4.10.3 Дату в таблицу писать так, чтобы Sheets распознал её как дату** (текст ГГГГ-ММ-ДД Sheets разбирает как дату). Почему: дата, легшая текстом, выключает условное форматирование и сортировку без ошибки. [основание: ENG-40 · правило §4.10.3]
- **4.10.4 Гонка расписаний в одну минуту.** Два воркфлоу на одном и том же cron-времени не синхронизированы: читатель, стартовавший в начале минуты, читает раньше, чем писатель той же минуты дописал. Читателя ставить на несколько минут позже писателя, от которого он зависит. Признак: в отчёте читателя не хватает записей последних минут перед прогоном. [основание: ENG-41 · правило §4.10.4]

**4.11 Память и OOM.** Не материализовать полную историю или HTML в один item. Почему: у сервера ограниченная память, и один огромный item роняет исполнение. Средства: date-фильтр в запросе (например последние 60 дней); `this.helpers.httpRequest` с HTML как локальной переменной; `runOnceForAllItems` + `$input.first()`; изоляция тяжёлого шага через Execute Workflow. [основание: ENG-42 · правило §4.11]

**4.12 Data Table.** `get` с per-item фильтром `keyValue={{$json.field}}` ненадёжен при N>1 items: схлопывает в 1 без ошибки, даже с `executeOnce:false`. Рабочая форма — `returnAll:true` + матчинг по ключу в Code-ноде *(→ T1-B)*. [основание: ENG-43 · правило §4.12]
