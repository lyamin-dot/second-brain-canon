# second-brain-git — запись

Часть Skill second-brain-git. Читать: перед первой записью в repo в сессии, целиком. Номера пунктов — прежние, общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md.

2. Имя объекта

2.1. Имя проекта = имя папки: нижний регистр, слова через дефис (git-migration). Одно написание везде: путь, текст, коммит, чат. Вариантов с подчёркиванием, пробелом, заглавными не существует.

2.2. У файла нет имени, отличного от пути. Первая строка файла — его путь (projects/git-migration/PLAN.md).

2.3. Исключение 2.2 — файл с провенанс-маркером в любой папке: маркер остаётся первой строкой, путь — второй. Сдвиг маркера ломает адресацию блока.

2.4. Ссылка на запись чужого файла пишется с именем файла: «Т-05 журнала PROJECT_LOG_SYS», не «класс Т-05». Номера уникальны внутри файла.
Исключение — сквозная нумерация. Проект, чьи файлы делятся по теме и чьи записи при разрезе переезжают между файлами, объявляет в своём PLAN.md сквозную нумерацию по проекту вместо нумерации внутри файла. Тогда ссылка пишется голым номером без имени файла, а последний выданный номер каждой последовательности хранится в файле-списке этого проекта и правится тем же действием, что и сама запись.
Почему: при разрезе по 6.3 запись меняет файл, и ссылка с именем файла указывает на файл, которого больше нет.

2.5. Сдвиг адреса. Правка, после которой прежний адрес ведёт не туда или никуда, тем же действием пересчитывает все ссылки на прежний адрес — в своём файле и во всех файлах, которые на него ссылаются, включая STATE.md и PLAN.md проектов, файлы meta/ и registry/. Такая правка — любая из четырёх: сдвиг номера пункта, раздела или записи (перенумерация); перенос раздела или правила в другой файл или другой Skill; снятие файла, раздела или Skill; переименование файла или папки.
Ссылки ищутся механически, не по памяти: прежний адрес в квалифицированной форме — путь файла, «<файл>, <номер>», «пункт <номер>», а не голый номер вида «2.5», который даёт шум, — командой `git fetch && grep -rnF '<прежний адрес>' <клон> /mnt/skills/plugins` (среда без клона — Git Read Lines с pattern по каждому известному файлу-читателю, а то, что поиск по всему репозиторию не выполнен, называется в отчёте). Записи журналов LOG.md, отчёты синтеза и харвеста (meta/SYNTHESIS_*, meta/HARVEST_*) и прежний текст статусов Очереди не правятся — они история (11.1); находка в Skill — текстом «было → стало» владельцу и позицией Очереди (10.5).
Почему: после сдвига старый номер обычно существует — он теперь принадлежит другому пункту, и ссылка ведёт не туда, оставаясь целой; после переноса, снятия или переименования ссылка ведёт в пустоту, а сессия проекта, читающая свой PLAN.md, этого не видит.
Признак: проверка битых ссылок ничего не находит, а ссылка приводит к пункту о другом; или PLAN.md проекта отсылает к файлу или Skill, которых в живом Skill нет.

2.6. Правка Skill: канон, зеркало, копии старой формулировки.

Канон Skills — живой Skill в аккаунте владельца (Customize → Skills). Правит его только владелец; сессия видит его снимком в /mnt/skills/plugins/<имя>/ и только читает. Зеркало skills/<имя>/ репозитория — резервная копия и единственная история версий Skills: у Customize истории версий нет, поэтому зеркало, не обновлённое после правки, — потерянная версия. Расхождение зеркала с живым Skill значит «зеркало отстало», а не «Skill испорчен».
Не путать: зеркало не канон и правка в нём ничего не меняет в живом Skill — до 2026-10-18 карта репозитория называла зеркало каноном («правка здесь, затем zip в Customize»), и ни одна правка этим путём не прошла (labs/sys/t-skills-mirror-drift.md; решение В12 файла meta/HARVEST_2026-10-18_answers.md).
Когда правка Skill начинает действовать и кто заливает zip — Skill second-brain-engineer, раздел Р13; здесь — механика приёмки, зеркала и поиска копий.

Правка Skill, которую внёс владелец, закрывается четырьмя шагами одной сессии, по порядку. Пропущенный шаг называется в отчёте, а не умалчивается.

Шаг 1. Приёмка по объекту. Правка принимается чтением снимка Skill, загруженного в сессию: по якорям правки (новый текст на месте) и на отсутствие старых формулировок, — а не словом «внёс».
Почему: слово владельца — память о действии, а не объект; приёмка по объекту ловит то, чего слово не видит.
[основание: GIT-48]

Шаг 2. Обновление зеркала.
(а) Сначала сверка в обе стороны, по каждому файлу Skill: `diff -rq skills/<имя> /mnt/skills/plugins/<имя>`. Если в зеркале есть файл или текст, которого нет в живом Skill (сессия подготовила правку, а владелец её ещё не залил), — стоп и вопрос владельцу: копия поверх стёрла бы незалитую правку.
(б) Затем файлы живого Skill проверяются на классы И-7 командой поиска признаков — `grep -rnE '@|/webhook/|Bearer|credential' /mnt/skills/plugins/<имя>` — и каждая находка читается глазами. Почему: копия переносит в публичный репозиторий всё, что лежит в живом Skill, а адрес почты или номер ключа, записанный в Skill, в историю repo попадёт навсегда. Находка класса И-7 — стоп: владелец убирает значение из живого Skill, зеркало пишется после.
(в) Иначе файлы живого Skill копируются в skills/<имя>/ командой (`cp`), не набираются моделью — это уже существующий текст (4.5); транспорт — маршрут 9.4(б) файла references/delivery.md, в среде, где прошёл `git push --dry-run`.
(г) Приёмка: после коммита и свежего fetch `diff -rq` этой папки пуст.
(д) Среда без открытого push зеркало не пишет — ни Каналом, ни частями: обновление называется в отчёте и ложится позицией в Очередь (10.5), иначе версия Skill пропадёт при следующей правке.
[основание: GIT-49]

Шаг 3. Поиск копий старой формулировки. Правило, изменённое в одном носителе, продолжает действовать в своих копиях — в других Skills, в файлах meta/, STATE.md и PLAN.md проектов, в текстах мастер-промптов meta/prompts/. Поэтому копии ищутся механически, не по памяти:
(а) из каждого заменённого фрагмента (БЫЛО) берётся одна характерная фраза из пяти–восьми слов в пределах одной строки;
(б) фраза ищется командой по клону репозитория и по папке Skills разом — `git fetch && grep -rnF '<фраза>' <клон> /mnt/skills/plugins`. Ключ -F ищет фразу как есть, без шаблона, поэтому русские буквы в ней работают и без настроенной локали (проверено 2026-10-18 при LC_ALL=C: фраза «правка здесь, затем zip» найдена в живом Skill и в зеркале);
(в) шаг идёт после шага 2: тогда находка в skills/ — копия в другом Skill, а не прежняя версия этого;
(г) каждая находка тем же действием либо правится (файл repo — по правилам записи этого файла; другой Skill или живой мастер-промпт — текстом «было → стало» владельцу и позицией в Очереди по 10.5), либо названа в отчёте с причиной, почему это не копия (запись журнала append-only не правится — она история, 11.1);
(д) в отчёте по каждой фразе — сама фраза, число находок и что сделано; ноль находок пишется явно;
(е) живой текст мастер-промптов поиску недоступен — он живёт в интерфейсе проекта; ищется его зеркало meta/prompts/, и находка там означает, что и живой промпт, скорее всего, несёт ту же копию;
(ж) среда без клона этот шаг не исполняет (Канал каталог не перечисляет, 3.2): шаг называется в отчёте невыполненным и ложится позицией в Очередь;
(з) тот же механический поиск — по имени, ID и пути носителя — обязателен при заморозке или переносе носителя (документа, журнала, файла): правило и порядок — references/migration.md, 13.5.
Правило «копии ищут и снимают тем же действием» — Skill second-brain-engineer, файл references/design.md, пункт 11; здесь — его механическое исполнение. Почему шагом процедуры, а не только правилом метода: стоя в методе проектирования, правило ни разу не исполнилось с 2026-10-09.
[основание: GIT-50]

Шаг 4. Сверка перед заливкой. Перед заливкой zip, собранного из зеркала или из текста сессии, зеркало сверяется с живым Skill в обе стороны, по каждому файлу. Расхождение, найденное сверкой, переносится в отстающий носитель до заливки.
Тем же шагом скрипт проверяет длину поля description во frontmatter SKILL.md: не больше 1024 знаков, иначе Customize отказывает в заливке ошибкой «field 'description' in SKILL.md must be at most 1024 characters». Команда: `python3 -c "import sys,yaml;t=open(sys.argv[1],encoding='utf-8').read();print(len(yaml.safe_load(t.split('---')[1])['description']))" <клон>/skills/<имя>/SKILL.md` — разбор YAML, а не поиск строки, потому что описание, записанное блоком «|» или «>», поиском строки считается как один знак и проходит проверку ложно. [основание: GIT-51]
Почему сверка в обе стороны: правка могла лечь мимо зеркала прямо в Customize, и заливка без сверки стирает её из живого Skill.
Признак: расхождение бывает в обе стороны сразу — один файл новее в зеркале, другой новее в живом Skill.
[основание: GIT-52]

4.5. Правило происхождения текста (продолжение 4.5 из SKILL.md).

ПОТОЛКА ЗАПИСИ В БАЙТАХ НЕ СУЩЕСТВУЕТ НИ ДЛЯ ОДНОГО ФАЙЛА. Вместо него действует ПРАВИЛО ПРОИСХОЖДЕНИЯ ТЕКСТА. Перед любой записью задаётся один вопрос: порождён ли записываемый текст этой сессией?

| Текст | Примеры | Через модель | Транспорт |
|---|---|---|---|
| порождён этой сессией | решение, запись журнала, новый абзац, новый файл | идёт, и это нормально | таблица 8.3 |
| уже существует | ротация, возврат версии из истории, перенос тела файла, пересборка большого файла, копия живого Skill в зеркало | НЕ идёт НИКОГДА, независимо от размера | маршрут 9.4(б) |

Почему: размер порождённого текста ограничен тем, сколько сессия написала, — отдельного числа не нужно, потому что сессия не может отправить больше, чем сочинила; существующий текст модель, перенабирая, теряет и искажает молча. Правило проверяемо одним вопросом и не требует ни одного измерения при исполнении.
Признак нарушения — не превышение числа, а класс Р-79: уже существовавший текст набран моделью заново, и файл расходится с оригиналом.
[основание: GIT-53]

Исключение — вычёркивание из наличного текста. Существующий файл разрешено записать заново целиком, когда выполнены три условия сразу:
1. полный текст файла пришёл в контекст этой сессии ответом чтения — Канала или клона — и не восстанавливается по памяти, пересказу или прошлой сессии;
2. правка — удаление или вставка целых строк, все остальные строки переносятся без изменения;
3. запись целиком нужна ради атомарности, которую правкой фрагмента не получить: сейчас это ровно один случай — создание и закрытие задачи лаборатории (4б.5), где файл задачи и INDEX.md обязаны уйти одним вызовом Git Commit Files.
Почему исключение безопасно: класс Р-79 родился там, где сессия восстанавливала текст, которого в её контексте не было; здесь строка вычёркивается из текста, который в контексте есть.
Приёмка — по объекту, не по ответу инструмента:
- в среде с клоном `git diff` против родителя коммита показывает ровно намеренные строки и ни одной другой;
- в среде без клона сходится байтовая арифметика (размер после = размер до − байты удалённых строк + байты вставленных, каждая строка с переводом строки) и один вызов Git Read Lines с pattern по удалённой строке возвращает count = 0, по вставленной — count = 1.
Исключение временное: оно снимается, когда Git Commit Files научится заменять фрагмент на сервере так же, как Git Replace, — тогда атомарность получается без перенабора.
[основание: GIT-54]

Превышение бюджета чтения сообщается как превышение бюджета чтения. Слова «потолок записи» в этом контракте не значат ничего и в отчётах не употребляются.

Массовая механическая работа (опись, нарезка, пересборка, перенос большого тела) — частный случай того же правила; общий принцип «её делает скрипт, а не модель» и его причина — Skill second-brain-engineer, файл references/mass-transfer.md, пункт 17; транспорт для файлов репозитория и приёмка механического переноса — маршрут 9.4(б) файла references/delivery.md.

4.6. Дополнительные роли и отступления от бюджета чтения. Проект может иметь роли сверх четырёх и бюджет чтения, отличный от таблицы 4, если выполнены три условия сразу:
1. материал не ложится ни в одну из четырёх ролей по правилу 4.2;
2. роль или изменённый бюджет объявлены в PLAN.md этого проекта с содержанием, числом, читателем и моментом чтения;
3. решение записано в LOG.md этого проекта с основанием, по которому его можно оспорить.
Отступление действует только в объявившем его проекте.

Агентская копия на английском (предпочтение Андрея — две версии рабочих документов) — частный случай дополнительной роли. Её шапка называет парный файл; для пары в meta/, у которой нет своего журнала, условие 3 этого пункта не требуется — пару объявляет шапка. Правка одного файла пары — тем же коммитом правка другого; перед записью копии сверяются по составу: разделы, правила, числа, исключения. Расхождение, найденное позже, — стоп и вопрос Андрею, какая копия права; тихо выравнивать нельзя, и ни одна копия не главная автоматически. Почему: агент исполняет английскую копию, Андрей решает по русской, и каждый считает свою верной. Признак: шапки пары объявляют главной разные копии, или в одной копии больше разделов, чем в другой. [основание: GIT-55]

4.7. Правила записи PLAN.md. Аномалия, которую признали нормой (ожидаемое постоянное состояние, намеренный дубль, известное расхождение), записывается с пометкой «не дефект, не расследовать» и причиной — там, где на неё наткнётся следующий читатель: в PLAN.md рядом с описанием объекта или в файле meta/, который описывает этот объект.
Почему: без пометки каждая следующая сессия заново принимает норму за дефект и тратит ход на расследование.
Образцы — «ожидаемое постоянное состояние» в projects/wb-reviews/PLAN.md, «дубли article_1 намеренные» в meta/DECLARATION_SCAN.md.

5. Превышение бюджета чтения

Закон раздела: бюджет чтения ограничивает читателя, а не запись и не файл. Превышение — не отказ, не блок и не дефект; лечение — разбор по роли, а не сокращение смысла.

5.1. Ужимание текста ради бюджета чтения ЗАПРЕЩЕНО. Ужимание — сокращение формулировки с потерей содержания.
Не ужимание, а разбор по роли (4.2), и бюджетом он не ограничен:
- удаление дубля того, что живёт в LOG.md, Skill, реестре или очереди (остаётся указатель);
- вынос закрытого с датой в LOG.md;
- удаление снимка чисел, устаревшего к моменту записи.
Рабочий вопрос к каждой строке при разборе: изменит ли она действие следующей сессии; нет — строка не по роли.

7.5. Утверждение об истории репозитория — чего в истории не было, когда и чем удалена запись, была ли перезапись ветки, «файл никогда не превышал N» — пишется в любой файл repo только вместе с двумя величинами, снятыми в той же сессии: `git rev-parse --is-shallow-repository` = false и `git rev-list --count origin/main`. Вывод «не существует», «перезаписано», «не превышал» по клону с ограниченной глубиной ЗАПРЕЩЁН.
Почему: клон с ограниченной глубиной показывает самый старый скачанный коммит как корень без предков и скрывает всё, что старше.
[основание: GIT-56]

5.5. STATE.md, PLAN.md, meta/* — переливной клапан. Порядок обязателен:
1. Запись выполняется целиком по 8 вне зависимости от бюджета чтения. Отказа в записи по бюджету не существует: бюджет ограничивает читателя (4.5), не запись; лишний килобайт на старте дешевле потерянной строки.
2. Той же сессией, тем же нарядом — разбор по 5.1: закрытое с датой → блок хроники в LOG.md по форме 11.5 через Git Append File (запасной путь — Git Append); дубль → указатель; снимок чисел → удаляется. Это вторая запись по 8, не часть первой.
3. Файл после разбора над бюджетом — остаётся над бюджетом, и это не повод ни для правки, ни для позиции в Очереди: превышение бюджета чтения само по себе проблемой не является. Критерий для файлов, читаемых на старте сессии, — по содержанию: каждая строка меняет действие следующей сессии; строка, которая не меняет, уезжает в журнал разбором по 5.1.
Не путать: позиция в Очереди «с числом и датой смерти» при каждом превышении — прежнее требование этого пункта, отменённое 2026-10-01: такие позиции никто не исполнял.
[основание: GIT-57]

8. Запись

8.1. Что такое запись и чем она доказывается. Запись — изменение файла в main, доказанное независимым перечитыванием. Транспорт выбирается по таблице 8.3; «собрать новый текст целиком» транспортом по умолчанию НЕ является и для существующего файла запрещено правилом происхождения текста (4.5).

Доказательство обязательно и снимается так:

| Среда | Чем доказывать |
|---|---|
| с клоном | `git fetch` и `git hash-object` — сверить blob sha записанного с намеренным |
| без клона | один вызов Git Read Lines с pattern по первой строке записанного: вернёт sha, byteLength и сам фрагмент разом |

Для Git Append дополнительно сходится арифметика: `bytes_after − bytes_before = bytes_appended + 1`. Единица не запас и не погрешность: Git Append дописывает не text, а перевод строки плюс text, безусловно, в том числе когда файл уже оканчивается переводом строки.
Признак ошибки счёта: сессия, считающая по формуле без единицы, читает штатную работу как порчу и рискует повторить вызов, то есть удвоить запись.
[основание: GIT-58]

Ответ инструмента доказательством не является (И-2). Серия успешных ответов — тоже не является.

8.2. Текст записи ОБЯЗАН существовать файлом до вызова записи: файлом на диске сессии либо файлом Drive в папке _git_staging (8.3, Git Append File). Набор в теле вызова по памяти или плейсхолдером ЗАПРЕЩЁН.

Кириллица набирается как есть: последовательности \uXXXX модель в теле вызова не набирает — ни вручную, ни копированием вывода json.dumps с настройкой по умолчанию.
Почему — цена, а не порча: каждая кириллическая буква в виде \uXXXX — шесть символов вместо одного, и выход модели растёт в разы. Замер 2026-09-24 на одном и том же тексте 3 439 Б: 6 165 токенов выхода, когда модель набрала его последовательностями \uXXXX в теле Git Append, и 1 260 — набранный кириллицей в textContent файла Drive.
Признак: содержимое файла от этого не портится, поэтому ошибку легко не заметить — видна она только в наборе параметров вызова.
Почему запрет текстом не держится: тело параметра-объекта execute_workflow (inputs) харнесс сам хранит в контексте последовательностями \uXXXX, как бы модель его ни набрала; модель видит свои прошлые вызовы экранированными и начинает так же набирать следующие. Сессия подражает тому, что видит выше по разговору, а прочитанный раньше запрет с подражанием не конкурирует — нарушение повторяет и сессия, прочитавшая этот пункт за минуты до вызова. Удорожание контекста от экранирования харнессом самоконтролем не снимается — его снимают два пути: перенос тела в файл Drive (Git Append File, 8.3) или запись клоном в сессии, где прошёл `git push --dry-run` (9.1), — тогда тело не идёт через вызов инструмента вовсе (решение Андрея 2026-10-20; путь проверен 2026-10-19, отчёт meta/SYNTHESIS_second-brain-git_2026-10-19.md, раздел «Случаи без адреса», пункт 5). Поэтому правило не опирается на самоконтроль там, где его можно заменить устройством:

| Вид вызова | Чем снята причина |
|---|---|
| (а) читающие вызовы | русский текст в них не набирается вообще — шаблоны поиска по пункту 7.6 SKILL.md, без русских букв |
| (б) дозапись | устройством: Git Append File берёт текст из файла Drive (8.3), набора \uXXXX он не допускает |
| (в) правка фрагмента с русским текстом (Git Replace) | устройство — вход из файлов Drive, из которых воркфлоу берёт oldStr и newStr, как текст у Git Append File; владелец решил его строить 2026-10-18 (решение Б1 файла meta/HARVEST_2026-10-18_answers.md), построение — нарядом на правку воркфлоу n8n с «да» владельца (Skill second-brain-engineer, раздел Р10); задача labs/sys/t-git-replace-escape.md. Довод против, записанный там же: для короткой замены лишние шаги create_file и trash_file дороже набора |
| (г) пока устройства из (в) нет | самоконтроль: перед каждым пишущим вызовом Канала сессия ищет в наборе параметров последовательность \u и при находке переписывает вызов русскими буквами как есть. Это слабое звено, оно названо слабым, и положиться на него одного нельзя |

[основание: GIT-59]

Форма вызова Git Append File.
Шаг 1 — create_file Google Drive: title любой, parentId — папка _git_staging (ID в registry/tools.md, строка Git Append File), contentMimeType text/plain, disableConversionToGoogleType true, textContent — текст записи целиком, включая ведущий перевод строки, если запись отделяется от предыдущей пустой строкой.
Шаг 2 — execute_workflow в режиме manual с телом {path, fileId}, в форме вызова из термина «Канал» SKILL.md (triggerNodeName "01_Webhook", inputs {webhookData: {method: "POST", body: {path, fileId}}}, без поля type).
Шаг 3 — проверка по 8.1; арифметика та же, что у Git Append: прирост файла равен размеру файла-источника плюс 1.
Шаг 4 — после проверки файл-источник в корзину (trash_file Google Drive).
Для этого действия Skill google-drive-docs читать не нужно: форма вызова целиком здесь.

Четыре правила внутри таблицы:

(1) Серия вызовов Git Append ради ОДНОЙ записи ЗАПРЕЩЕНА.
Почему: Git Append дописывает перевод строки перед каждым телом, поэтому второй и следующие вызовы вставляют пустые строки ВНУТРЬ тела записи, и запись приходит в main рваной.
Размер не повод дробить: тело одного вызова через MCP в известных пределах по байтам не ограничено — замер 2026-09-17: 32 768 Б одним телом байт-в-байт (запись Р-99 журнала projects/git-migration/LOG_ARCHIVE.md), а размер записи и так ограничен тем, сколько сессия сочинила.
Если серия всё же была начата и оборвана, следующая сессия дописывает хвост, не переписывает голову.

(2) Append-only файл целиком не перезаписывается и по кускам не пересобирается, в том числе ради исправления одной строки: дефект внутри такого файла исправляется Git Replace фрагмента. Замок стоит в самом Канале с 2026-09-16 — Git Write и Git Commit Files такой файл не перезаписывают и не удаляют (запись Р-86 журнала projects/git-migration/LOG_ARCHIVE.md).

(3) Номер записи. Уникальность номера Git Append не проверяет, поэтому номер берётся из СВЕЖЕГО чтения непосредственно перед вызовом. В среде без клона это один вызов Git Read Lines с pattern по шаблону номера — не чтение файла целиком. После записи — тот же вызов ещё раз: номер должен встречаться ровно один раз.
Признак столкновения: две строки-заголовка с одним номером — параллельная сессия заняла его между чтением и записью (8.9); своя запись перенумеровывается правкой Git Replace её строки-заголовка.

(4) Число позиций реестра (Очереди и любого файла-таблицы) получается пересчётом строк самого файла, а не сложением приращений из разделов «Счёт после добавления».
Почему: приращения, сложенные разными сессиями, расходятся с файлом — сложение дало в registry/maintenance-queue.md пять разных чисел.
[основание: GIT-60]

8.6. Составной save — несколько независимых записей, каждая со своей гонкой.
Порядок: LOG.md раньше STATE.md — состояние выводимо из журнала, обратное неверно.
Каждая следующая запись запускается только после результата предыдущей, даже если файлы разные: две записи, запущенные одновременно, GitHub отбивает отказом «is at … but expected …» (пункт 8.10, references/delivery.md).
Save не закрыт, пока каждый затронутый файл не перечитан по 8.1; частичный отказ досдаётся в той же сессии, иначе в LOG.md — запись о рассинхроне с именем недописанного файла.

8.7. Результат записи доказывается чтением с origin/main после свежего fetch — не локальным состоянием, не ответом инструмента. Требование, которое среда может не исполнить по своему устройству, закрепляется проверкой результата, а не повторением требования.

- Факт, требующий правки Skill или мастер-промпта, — позиция в Очереди через Git Append File (запасной путь — Git Append) с датой смерти. «Отложить до харвеста» без позиции ЗАПРЕЩЕНО.

Статус позиции Очереди начинается одним словом из закрытого словаря; всё прочее — после точки с запятой.

| Слово | Когда | После слова |
|---|---|---|
| ОТКРЫТА | позиция заведена, текст правки владельцу ещё не выдан | — |
| ЖДЁТ | текст выдан или работа сделана, ждёт действия владельца (заливки, решения, вставки в промпт) или харвеста | чего именно |
| ВНЕСЕНО | правка стоит в целевом носителе и проверена по объекту | дата и адрес |
| СНЯТА | не вносится | дата и причина |
| ДУБЛЬ | содержание уже живёт в носителе, в другой открытой позиции или задаче лаборатории | адрес |

Форма: «ВНЕСЕНО 2026-10-13 — <адрес>; отложено 2026-10-10 до пакета Архивариуса». При смене статуса новое слово с датой встаёт в начало, прежний текст уходит после точки с запятой и не стирается. Других первых слов нет: «ждёт» строчными, «отложено», «частично», «ЗАКРЫТО», «ВЫПОЛНЕНО», «СНЯТ» — нарушение формы.
Почему: открыта ли позиция, решает разбор по первому слову, и скрипт делает его без ошибок; слово в середине истории («до внесения», «внесено в составе») такой разбор обманывает.
[основание: GIT-61]

Позиция, которая ссылается словом ДУБЛЬ на другую позицию, держит своё содержание только пока та открыта или внесла его в носитель. Поэтому при снятии позиции те, что ссылаются на неё словом ДУБЛЬ, тем же действием получают статус заново. Почему: содержание, переданное по ссылке позиции, которую потом сняли, выпадает из Очереди молча — первым словом статуса оно закрыто, а в носителе его нет. Признак: позиция со статусом ДУБЛЬ указывает на позицию со статусом СНЯТА. [основание: GIT-62]

11. Форма записи в LOG.md

```
Р-NN | В СИЛЕ | дата | вопрос
  принято: …    почему: …    кто подтвердил: …          ← обязательны
  отвергнуто: …    обратимость: …    допущение: …        ← по наличию

Т-NN | дата | что пробовали
  почему не вышло: …    условие возврата: …             ← обязательны
  стоимость попытки: …                                  ← по наличию
```

11.1. Статус впереди текста. Записи append-only: решение не редактируется — отменяется новой записью со ссылкой. Статус прежней записи меняется одной правкой Git Replace по её строке-заголовку, и форм две:
- ОТМЕНЕНО Р-NN — новая запись отменяет прежнюю целиком;
- ЧАСТИЧНО ОТМЕНЕНО Р-NN (пункт X) — новая запись заменяет один или несколько пунктов прежней, остальные её пункты в силе; пункты называются так, как пронумерованы в прежней записи.
Почему вторая форма: без неё прежняя запись либо ложно помечается отменённой целиком, либо её мёртвый пункт читается как живой.
[основание: GIT-63]

11.2. Условие возврата у тупика обязательно; без него тупик — вечный запрет. Записанное раньше условие перед исполнением перепроверяется по объекту и по журналу: оно могло устареть, а вопрос — оказаться уже решённым. Это касается любого условия из прошлого — записи журнала, снимка в памяти чата, слов владельца по памяти, обещания в шапке документа «старые записи уезжают туда-то» (объект ищут, прежде чем на него сослаться); общее правило — Skill second-brain-engineer, Р15 (условие, записанное раньше).
[основание: GIT-64]

11.3. Ретроспективная запись ЗАПРЕЩЕНА: пишется только то, что произошло в этой сессии. Единственное исключение — блок хроники, который разбор по 5.1 и 5.5 вывозит из STATE.md, PLAN.md или meta/* в LOG.md: он по определению описывает прежние сессии и пишется только по форме 11.5, которая это называет.

11.4. Поле по наличию, которого источник не содержит, не пишется — ни прочерком, ни заглушкой «не зафиксировано при записи»; отсутствие поля и есть запись о том, что данных не было. Обязательное поле без содержания — запись не пишется, наряд возвращается выдавшему за недостающим.
Одно значение заглушкой не считается и разрешено в обязательном поле «кто подтвердил»: «не зафиксировано в источнике — самопроверка Клода». Оно пишется, когда решение принято сессией (или перенесено из источника, где подтверждения нет) без слова владельца, и отличает самопроверку от подтверждения владельца. Приписать владельцу подтверждение, которого не было, ЗАПРЕЩЕНО (решение владельца; практика журналов git-migration Р-115…Р-117, wb-logistics, wb-ue).
Вывод сессии ДОПУСКАЕТСЯ при двух условиях сразу: назван выводом и проверяем внутри самой записи (арифметика, цитата, два известных факта).
[основание: GIT-65]

11.5. Форма блока хроники (исключение 11.3). Первая строка обязательна и называет происхождение:

```
Хроника | дата разбора | перенесено из <путь> разбором по 5.1 — не свидетельство этой сессии
  <перенесённые строки без изменения смысла, каждая со своей датой>
```

Номера Р или Т блок хроники не получает и в оглавление журнала (7.6) не попадает — это не решение и не тупик. Строки переносятся из файла-источника, а не пересказываются; содержание, которое уже живёт в записи журнала, не переносится, а заменяется в источнике указателем на запись (5.1).
[основание: GIT-66]

11.6. Отвергнутое пишется в журнал вместе с причиной отказа — поле «отвергнуто: …» называет вариант и почему он не взят. Отвергнутое без причины не пишется.
Почему: следующая сессия не сможет понять, отпало ли основание отказа.
[основание: GIT-67]

11.7. Новый стандарт записи действует только вперёд. Старые записи на формат, которого в момент их записи не было, не проверяются и задним числом не переписываются.
Почему: результат такой проверки — заранее известный ноль, а правка нарушила бы append-only.
[основание: GIT-68]
