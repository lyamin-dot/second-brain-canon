# second-brain-git — запись

Часть Skill second-brain-git. Читать: перед первой записью в repo в сессии, целиком. Номера пунктов — прежние, общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md.

2. Имя объекта

2.1. Имя проекта = имя папки: нижний регистр, слова через дефис (git-migration). Одно написание везде: путь, текст, коммит, чат. Вариантов с подчёркиванием, пробелом, заглавными не существует.

2.2. У файла нет имени, отличного от пути. Первая строка файла — его путь (projects/git-migration/PLAN.md).

2.3. Исключение 2.2 — файл с провенанс-маркером в любой папке: маркер остаётся первой строкой, путь — второй. Сдвиг маркера ломает адресацию блока.

2.4. Ссылка на запись чужого файла пишется с именем файла: «Т-05 журнала PROJECT_LOG_SYS», не «класс Т-05». Номера уникальны внутри файла. Исключение: проект, чьи файлы делятся по теме и чьи записи при разрезе переезжают между файлами, объявляет в своём PLAN.md сквозную нумерацию по проекту вместо нумерации внутри файла. Тогда ссылка пишется голым номером без имени файла, а последний выданный номер каждой последовательности хранится в файле-списке этого проекта и правится тем же действием, что и сама запись. Основание: при разрезе по 6.3 запись меняет файл, и ссылка с именем файла указывает на файл, которого больше нет.

2.5. Перенумерация. Правка, сдвигающая номер пункта, раздела или записи, тем же действием пересчитывает все ссылки на этот номер — в своём файле и в файлах, которые на него ссылаются (поиск по номеру клоном или Git Read Lines с pattern). Проверка битых ссылок этого не ловит: после сдвига старый номер обычно существует — он теперь принадлежит другому пункту, и ссылка ведёт не туда, оставаясь целой. Прецедент — шесть ссылок контракта на 7.1 вместо 7.6 после промежуточной перестановки (записи Р-89, Р-103 и тупик Т-71 журнала projects/git-migration/LOG_ARCHIVE.md, Р-122 журнала projects/git-migration/LOG.md).

2.6. Зеркало skills/ и живой Skill. Правка Skill, которую владелец внёс сам, принимается чтением снимка Skill, загруженного в сессию: по якорям правки (новый текст на месте) и на отсутствие старых формулировок — а не словом «внёс» (запись Р-103 журнала projects/git-migration/LOG_ARCHIVE.md: такая приёмка нашла шесть ссылок, ведших не на тот пункт). Перед заливкой zip из зеркала skills/<имя>/ зеркало сверяется с живым Skill в обе стороны, по каждому файлу: правка могла лечь мимо зеркала прямо в Customize. 2026-10-01 расхождение было в обе стороны сразу — references/write.md новее в зеркале, references/migration.md новее в живом Skill, и заливка без сверки стёрла бы из живого Skill пункт 13.6 (запись Р-32 журнала projects/kontext-reduktion/LOG.md). Расхождение, найденное сверкой, переносится в отстающий носитель до заливки.

4.5. Правило происхождения текста (продолжение 4.5 из SKILL.md).

ПОТОЛКА ЗАПИСИ В БАЙТАХ НЕ СУЩЕСТВУЕТ НИ ДЛЯ ОДНОГО ФАЙЛА. Вместо него действует ПРАВИЛО ПРОИСХОЖДЕНИЯ ТЕКСТА. Перед любой записью задаётся один вопрос: порождён ли записываемый текст этой сессией?

Порождён этой сессией — решение, запись журнала, новый абзац, новый файл — текст идёт через модель, и это нормально. Его размер ограничен тем, сколько сессия написала; отдельного числа не нужно, потому что сессия не может отправить больше, чем сочинила.

Уже существует — ротация, возврат версии из истории, перенос тела файла, пересборка большого файла — текст через модель не идёт НИКОГДА, независимо от размера. Транспорт по 8.3.

Правило проверяемо одним вопросом и не требует ни одного измерения при исполнении. Нарушение — не превышение числа, а класс Р-79: 244 версии LOG_ARCHIVE.md за сутки и потеря 69 номеров, потому что уже существовавший текст набирался моделью заново.

Исключение — вычёркивание из наличного текста. Существующий файл разрешено записать заново целиком, когда выполнены три условия сразу:
1. полный текст файла пришёл в контекст этой сессии ответом чтения — Канала или клона — и не восстанавливается по памяти, пересказу или прошлой сессии;
2. правка — удаление или вставка целых строк, все остальные строки переносятся без изменения;
3. запись целиком нужна ради атомарности, которую правкой фрагмента не получить: сейчас это ровно один случай — создание и закрытие задачи лаборатории (4б.5), где файл задачи и INDEX.md обязаны уйти одним вызовом Git Commit Files.
Приёмка — по объекту, не по ответу инструмента: в среде с клоном `git diff` против родителя коммита показывает ровно намеренные строки и ни одной другой; в среде без клона сходится байтовая арифметика (размер после = размер до − байты удалённых строк + байты вставленных, каждая строка с переводом строки) и один вызов Git Read Lines с pattern по удалённой строке возвращает count = 0, по вставленной — count = 1. Основание различения: класс Р-79 родился там, где сессия восстанавливала текст, которого в её контексте не было; закрытие задачи лаборатории 2026-09-25 перенабором INDEX.md целиком вышло побайтово чистым — diff показал одну удалённую строку и ни одной добавленной (Р-28 журнала projects/kontext-reduktion/LOG.md). Исключение временное: оно снимается, когда Git Commit Files научится заменять фрагмент на сервере так же, как Git Replace, — тогда атомарность получается без перенабора.

Превышение бюджета чтения сообщается как превышение бюджета чтения. Слова «потолок записи» в этом контракте не значат ничего и в отчётах не употребляются.

4.6. Дополнительные роли и отступления от бюджета чтения. Проект может иметь роли сверх четырёх и бюджет чтения, отличный от таблицы 4, если выполнены три условия сразу: материал не ложится ни в одну из четырёх по правилу 4.2; роль или изменённый бюджет объявлены в PLAN.md этого проекта с содержанием, числом, читателем и моментом чтения; решение записано в LOG.md этого проекта с основанием, по которому его можно оспорить. Отступление действует только в объявившем его проекте.

4.7. Правила записи PLAN.md. Аномалия, которую признали нормой (ожидаемое постоянное состояние, намеренный дубль, известное расхождение), записывается с пометкой «не дефект, не расследовать» и причиной — там, где на неё наткнётся следующий читатель: в PLAN.md рядом с описанием объекта или в файле meta/, который описывает этот объект. Без пометки каждая следующая сессия заново принимает норму за дефект и тратит ход на расследование. Образцы — «ожидаемое постоянное состояние» в projects/wb-reviews/PLAN.md, «дубли article_1 намеренные» в meta/DECLARATION_SCAN.md.

5. Превышение бюджета чтения

5.1. Ужимание текста ради бюджета чтения ЗАПРЕЩЕНО. Ужимание — сокращение формулировки с потерей содержания. Не ужимание: удаление дубля того, что живёт в LOG.md, Skill, реестре или очереди (остаётся указатель); вынос закрытого с датой в LOG.md; удаление снимка чисел, устаревшего к моменту записи. Это разбор по роли (4.2), и он бюджетом не ограничен. Рабочий вопрос к каждой строке при разборе: изменит ли она действие следующей сессии; нет — строка не по роли.

7.5. Утверждение об истории репозитория — чего в истории не было, когда и чем удалена запись, была ли перезапись ветки, «файл никогда не превышал N» — пишется в любой файл repo только вместе с двумя величинами, снятыми в той же сессии: `git rev-parse --is-shallow-repository` = false и `git rev-list --count origin/main`. Клон с ограниченной глубиной показывает самый старый скачанный коммит как корень без предков и скрывает всё, что старше; вывод «не существует», «перезаписано», «не превышал» по такому клону ЗАПРЕЩЁН. Основание: Р-80 — два ложных вывода подряд.

5.5. STATE.md, PLAN.md, meta/* — переливной клапан. Порядок обязателен:
1. Запись выполняется целиком по 8 вне зависимости от бюджета чтения. Отказа в записи по бюджету не существует: бюджет ограничивает читателя (4.5), не запись; лишний килобайт на старте дешевле потерянной строки.
2. Той же сессией, тем же нарядом — разбор по 5.1: закрытое с датой → блок хроники в LOG.md по форме 11.5 через Git Append File (запасной путь — Git Append); дубль → указатель; снимок чисел → удаляется. Это вторая запись по 8, не часть первой.
3. Файл после разбора над бюджетом — остаётся над бюджетом, и это не повод ни для правки, ни для позиции в Очереди: превышение бюджета чтения само по себе проблемой не является. Критерий для файлов, читаемых на старте сессии, — по содержанию: каждая строка меняет действие следующей сессии; строка, которая не меняет, уезжает в журнал разбором по 5.1. Основание — запись Р-125 журнала projects/git-migration/LOG.md (Андрей, 2026-10-01).

ИСТОРИЯ ДИАГНОЗА: до 2026-10-09 этот пункт требовал заводить позицию в Очереди с числом и датой смерти при каждом превышении. Отменено записью Р-125 журнала projects/git-migration/LOG.md: такие позиции никто не исполнял (позиция AH-18 очереди висела без движения), а на Р-125 уже опирался перенос проекта n8n (запись Р-3 журнала projects/n8n/LOG.md).

8. Запись

8.1. Что такое запись и чем она доказывается. Запись — изменение файла в main, доказанное независимым перечитыванием. Транспорт выбирается по таблице 8.3; «собрать новый текст целиком» транспортом по умолчанию НЕ является и для существующего файла запрещено правилом происхождения текста (4.5).

Доказательство обязательно и снимается так:

| Среда | Чем доказывать |
|---|---|
| с клоном | `git fetch` и `git hash-object` — сверить blob sha записанного с намеренным |
| без клона | один вызов Git Read Lines с pattern по первой строке записанного: вернёт sha, byteLength и сам фрагмент разом |

Для Git Append дополнительно сходится арифметика: `bytes_after − bytes_before = bytes_appended + 1`. Единица не запас и не погрешность: Git Append дописывает не text, а перевод строки плюс text, безусловно, в том числе когда файл уже оканчивается переводом строки. Сессия, считающая по формуле без единицы, читает штатную работу как порчу и рискует повторить вызов, то есть удвоить запись.

Ответ инструмента доказательством не является (И-2). Серия успешных ответов — тоже не является.

8.2. Текст записи ОБЯЗАН существовать файлом до вызова записи: файлом на диске сессии либо файлом Drive в папке _git_staging (8.3, Git Append File); набор в теле вызова по памяти или плейсхолдером ЗАПРЕЩЁН. Кириллица набирается как есть: последовательности \uXXXX модель в теле вызова не набирает — ни вручную, ни копированием вывода json.dumps с настройкой по умолчанию. Причина — цена, а не порча: каждая кириллическая буква в виде \uXXXX — шесть символов вместо одного, и выход модели растёт в разы (замер 2026-09-24 на одном и том же тексте 3 439 Б: 6 165 токенов выхода, когда модель набрала его последовательностями \uXXXX в теле Git Append, и 1 260 — набранный кириллицей в textContent файла Drive). Содержимое файла от этого не портится, поэтому ошибку легко не заметить. Ловушка в том, что тело параметра-объекта execute_workflow (inputs) харнесс сам хранит в контексте последовательностями \uXXXX, как бы модель его ни набрала; модель видит свои прошлые вызовы экранированными и начинает так же набирать следующие. Поэтому перед каждым вызовом Канала с кириллицей в теле — проверить, что в набираемом теле нет \u. Удорожание контекста от экранирования харнессом этим не снимается — его снимает только перенос тела в файл Drive (Git Append File, 8.3). Основание — записи Р-15 и Р-16 журнала projects/kontext-reduktion/LOG.md; нарушение повторилось при харвесте 2026-10-08 на шести вызовах Git Replace.

8.3. ЧЕМ ПИСАТЬ. Вход в таблицу — один вопрос: набирает ли модель текст, который уже существует?

| Что делаю | Инструмент | Почему так |
|---|---|---|
| дозапись одной записи в append-only файл (LOG.md, LOG_ARCHIVE.md, NOT_TAKEN.md, registry/maintenance-queue.md) | **Git Append File, ОДИН вызов**: текст — файлом в папку _git_staging, форма вызова — абзац «Форма вызова Git Append File» под таблицей; запасной путь — Git Append {path, text} | склейку и PUT с expectedSha делает воркфлоу, старый текст через сессию не проходит; тело в параметре-объекте execute_workflow хранится в контексте последовательностями \uXXXX и стоит около 1,8 токена на байт, в textContent файла Drive — около 0,45 (Р-15…Р-17 журнала projects/kontext-reduktion/LOG.md) |
| правка фрагмента существующего файла, в том числе внутри append-only | **Git Replace** | через модель идёт только фрагмент; цена не зависит от размера файла |
| новый файл или замена целиком | Git Write | новый файл — без expectedSha; замена — expectedSha = blob sha из свежего чтения. Замена целиком существующего файла допустима, только если его текст порождён этой сессией или подпадает под исключение 4.5 |
| несколько путей одним коммитом; любое удаление | Git Commit Files | единственный способ удалить путь; проходит целиком или не проходит |
| файл собирается из УЖЕ СУЩЕСТВУЮЩЕГО текста: ротация, возврат версии из истории, перенос большого тела, пересборка | **не Каналом** — маршрут 9.4(б) | иначе модель набирает существующий текст: класс Р-79 |

Форма вызова Git Append File. Шаг 1 — create_file Google Drive: title любой, parentId — папка _git_staging (ID в registry/tools.md, строка Git Append File), contentMimeType text/plain, disableConversionToGoogleType true, textContent — текст записи целиком, включая ведущий перевод строки, если запись отделяется от предыдущей пустой строкой. Шаг 2 — execute_workflow в режиме manual с телом {path, fileId}, в форме вызова из термина «Канал» SKILL.md (triggerNodeName "01_Webhook", inputs {webhookData: {method: "POST", body: {path, fileId}}}, без поля type). Шаг 3 — проверка по 8.1; арифметика та же, что у Git Append: прирост файла равен размеру файла-источника плюс 1. Шаг 4 — после проверки файл-источник в корзину (trash_file Google Drive). Для этого действия Skill google-drive-docs читать не нужно: форма вызова целиком здесь.

Три запрета внутри таблицы:

Серия вызовов Git Append ради ОДНОЙ записи ЗАПРЕЩЕНА: Git Append дописывает перевод строки перед каждым телом, поэтому второй и следующие вызовы вставляют пустые строки ВНУТРЬ тела записи, и запись приходит в main рваной. Размер не повод дробить — тело одного вызова через MCP в известных пределах по байтам не ограничено (замер 2026-09-17: 32 768 Б одним телом байт-в-байт), а размер записи и так ограничен тем, сколько сессия сочинила. Если серия всё же была начата и оборвана, следующая сессия дописывает хвост, не переписывает голову.

Append-only файл целиком не перезаписывается и по кускам не пересобирается, в том числе ради исправления одной строки: дефект внутри такого файла исправляется Git Replace фрагмента. Замок стоит в самом Канале с 2026-09-16 — Git Write и Git Commit Files такой файл не перезаписывают и не удаляют.

Уникальность номера записи Git Append не проверяет: номер берётся из СВЕЖЕГО чтения непосредственно перед вызовом. В среде без клона это один вызов Git Read Lines с pattern по шаблону номера — не чтение файла целиком. После записи — тот же вызов ещё раз: номер должен встречаться ровно один раз; две строки-заголовка с одним номером — параллельная сессия заняла его между чтением и записью (8.9), и своя запись перенумеровывается правкой Git Replace её строки-заголовка.

Число позиций реестра (Очереди и любого файла-таблицы) получается пересчётом строк самого файла, а не сложением приращений из разделов «Счёт после добавления»: сложение приращений дало в registry/maintenance-queue.md пять разных чисел (labs/sys/t-queue-count.md).

8.6. Составной save — несколько независимых записей, каждая со своей гонкой. Порядок: LOG.md раньше STATE.md (состояние выводимо из журнала, обратное неверно). Save не закрыт, пока каждый затронутый файл не перечитан по 8.1; частичный отказ досдаётся в той же сессии, иначе в LOG.md — запись о рассинхроне с именем недописанного файла.

8.7. Результат записи доказывается чтением с origin/main после свежего fetch — не локальным состоянием, не ответом инструмента. Требование, которое среда может не исполнить по своему устройству, закрепляется проверкой результата, а не повторением требования.

11. Форма записи в LOG.md

```
Р-NN | В СИЛЕ | дата | вопрос
  принято: …    почему: …    кто подтвердил: …          ← обязательны
  отвергнуто: …    обратимость: …    допущение: …        ← по наличию

Т-NN | дата | что пробовали
  почему не вышло: …    условие возврата: …             ← обязательны
  стоимость попытки: …                                  ← по наличию
```

11.1. Статус впереди текста. Записи append-only: решение не редактируется — отменяется новой записью со ссылкой. Статус прежней записи меняется одной правкой Git Replace по её строке-заголовку, и форм две:
- ОТМЕНЕНО Р-NN — новая запись отменяет прежнюю целиком;
- ЧАСТИЧНО ОТМЕНЕНО Р-NN (пункт X) — новая запись заменяет один или несколько пунктов прежней, остальные её пункты в силе; пункты называются так, как пронумерованы в прежней записи.
Без второй формы прежняя запись либо ложно помечается отменённой целиком, либо её мёртвый пункт читается как живой (основание — Р-22 журнала projects/kontext-reduktion/LOG.md, заменивший пункт 2а записи Р-21 при действующих остальных).

11.2. Условие возврата у тупика обязательно; без него тупик — вечный запрет. Условие, записанное раньше, перед исполнением перепроверяется по объекту и по журналу: оно могло устареть, а вопрос — оказаться уже решённым. Это касается любого условия из прошлого — «тот же ключ, что у git-write», снимок в памяти чата, слова владельца по памяти, обещание в шапке документа «старые записи уезжают туда-то» (объект ищут, прежде чем на него сослаться). Основание — записи Р-104, Р-107, Р-124 и тупики Т-08, Т-18, Т-37 журнала projects/git-migration.

11.3. Ретроспективная запись ЗАПРЕЩЕНА: пишется только то, что произошло в этой сессии. Единственное исключение — блок хроники, который разбор по 5.1 и 5.5 вывозит из STATE.md, PLAN.md или meta/* в LOG.md: он по определению описывает прежние сессии и пишется только по форме 11.5, которая это называет.

11.4. Поле по наличию, которого источник не содержит, не пишется — ни прочерком, ни заглушкой «не зафиксировано при записи»; отсутствие поля и есть запись о том, что данных не было. Обязательное поле без содержания — запись не пишется, наряд возвращается выдавшему за недостающим. Одно значение заглушкой не считается и разрешено в обязательном поле «кто подтвердил»: «не зафиксировано в источнике — самопроверка Клода». Оно пишется, когда решение принято сессией (или перенесено из источника, где подтверждения нет) без слова владельца, и отличает самопроверку от подтверждения владельца; приписать владельцу подтверждение, которого не было, ЗАПРЕЩЕНО (решение владельца, практика журналов git-migration Р-115…Р-117, wb-logistics, wb-ue). Вывод сессии ДОПУСКАЕТСЯ при двух условиях сразу: назван выводом и проверяем внутри самой записи (арифметика, цитата, два известных факта). Основание: Р-56…Р-59 — четыре записи подряд с пятью заглушками из шести полей.

11.5. Форма блока хроники (исключение 11.3). Первая строка обязательна и называет происхождение:

```
Хроника | дата разбора | перенесено из <путь> разбором по 5.1 — не свидетельство этой сессии
  <перенесённые строки без изменения смысла, каждая со своей датой>
```

Номера Р или Т блок хроники не получает и в оглавление журнала (7.6) не попадает — это не решение и не тупик. Строки переносятся из файла-источника, а не пересказываются; содержание, которое уже живёт в записи журнала, не переносится, а заменяется в источнике указателем на запись (5.1). Основание — Р-24 журнала projects/kontext-reduktion/LOG.md, где такой блок пришлось пометить договорённостью одной записи.

11.6. Отвергнутое пишется в журнал вместе с причиной отказа — поле «отвергнуто: …» называет вариант и почему он не взят. Отвергнутое без причины не пишется: следующая сессия не сможет понять, отпало ли основание отказа. Основание — инвариант 5 projects/kontext-reduktion/PLAN.md (слово владельца 2026-09-24), раздел «Отвергнуто» projects/n8n-map/PLAN.md.

11.7. Новый стандарт записи действует только вперёд. Старые записи на формат, которого в момент их записи не было, не проверяются и задним числом не переписываются: результат такой проверки — заранее известный ноль, а правка нарушила бы append-only (журнал PROJECT_LOG_SYS, записи Р-17, Р-18 и тупик Т-10).
