# second-brain-git — доставка записи и граница Канала

Часть Skill second-brain-git. Читать: при отказе сервера по expectedSha, по таймауту правил репозитория или отказом «is at … but expected …», при работе двух сессий одновременно, перед несколькими записями одной сессии подряд, перед записью уже существующего текста, перед массовой механической работой, перед выбором маршрута 9.4. Номера пунктов — прежние, общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md.

8.4. Git Commit Files {branch, message, expectedSha (sha HEAD), files[], deletes[]}. Требование заголовка Authorization действует для прямого HTTP-вызова; при вызове через MCP execute_workflow в режиме manual заголовок не требуется — гейт parent_check работает. Аутентификация вебхука вообще закрывает только внешний HTTP-вызов: вызов из сессии через MCP идёт мимо неё и работает всегда. Не путать «вебхук защищён» с «воркфлоу защищён от вызова сессией».

8.5. Отказ сервера по expectedSha — начало процедуры, а не повод переписать: свежий fetch и полное перечитывание → построчный diff намеренного текста с текущим → расхождения не пересекаются построчно — собрать заново поверх актуальной версии, записать с новым sha → пересекаются — стоп, вопрос человеку. Оценка «пересекаются по смыслу» ЗАПРЕЩЕНА как критерий: она всегда разрешается в пользу уже написанного. Слепая перезапись поверх отказа ЗАПРЕЩЕНА особо для LOG.md.

Отказ GitHub с текстом «Repository rule violations found / Timed out validating rule» — не конфликт версий, а временный таймаут проверки правил репозитория на стороне GitHub. Процедуру выше он не запускает: ответ сам доказывает, что файл не тронут (sha_before равен sha_after, bytes_before равен bytes_after). Сверить эти поля и повторить тот же вызов без единой правки. Прецедент — тупик Т-02 журнала projects/anis-evidence/LOG.md: повтор прошёл в той же сессии.

8.8. Ветка — шаг механики: «PR не используются» не обещает отсутствия промежуточной ветки. Если запись легла не в main, слияние — подшаг того же действия; не покрыто Каналом — И-4.

8.9. Параллельные сессии. Два наряда или два чата, работающие одновременно, называют непересекающиеся наборы путей repo в поле РАМКА своих нарядов; запись в путь, не названный в своём наряде, ЗАПРЕЩЕНА. Непересечение путей не снимает гонку за голову ветки: expectedSha у Git Commit Files — голова main, и чужой коммит в любой путь отбивает запись на parent_check. Если чужая сессия двигает голову чаще, чем длится оборот инструмента, Git Commit Files неприменим — используется Git Write пофайлово, у которого expectedSha есть blob sha самого файла. Плата — потеря атомарности по нескольким файлам, поэтому для пары, чьё рассогласование Каналом не обнаруживается (файл и список, в котором он должен быть назван), этот обход ЗАПРЕЩЁН: там ждём освобождения ветки.

Непересечение путей не спасает и от столкновения номеров: две сессии, дописывающие в один и тот же файл-реестр или журнал (Очередь, LOG.md соседнего проекта), могут взять один и тот же следующий номер позиции или записи. Номер сверяется свежим чтением непосредственно перед записью и пересчитывается после неё — правило в references/write.md, абзац о номере под таблицей 8.3. Прецеденты — SYS_INDEX 2026-08-31, OZON_UE_INDEX 2026-09-24.

8.10. Записи одной сессии — строго по очереди. Следующий пишущий вызов Канала (Git Write, Git Replace, Git Append, Git Append File, Git Commit Files) запускается только после того, как предыдущий вернул результат, — в том числе когда записи идут в разные файлы и в разные папки. Чтения (Git Read, Git Read Batch, Git Read Lines) запускаются параллельно без ограничения. Причина — устройство GitHub, а не Канала: каждая запись — отдельный коммит, сдвигающий голову main, и документация GitHub (REST API, раздел «Repository contents», операции создания, изменения и удаления файла) прямо говорит, что одновременные запросы конфликтуют и должны идти последовательно. Проверка blob sha у Git Write и Git Replace от этого не защищает: она ловит чужую правку того же файла между чтением и записью, а не второй коммит, ушедший в ту же секунду в другой файл. Поэтому обход 8.9 «Git Write пофайлово вместо Git Commit Files» помогает против головы, сдвинувшейся между оборотами инструмента, но не против двух записей, запущенных одновременно; это правило — о вызовах внутри одной сессии, 8.9 — о параллельных сессиях.

Признак столкновения: ответ success=false с причиной вида «PUT rejected by GitHub: is at <sha коммита> but expected <sha коммита>» и пустым bytesAfter. Это не отказ по expectedSha самого файла, и процедура 8.5 не запускается: дождаться результата другой записи, проверить по 8.1, что затронутый файл не изменился, и повторить тот же вызов один раз. Если за это время файл изменился, повтор отобьётся уже по expectedSha — тогда действует 8.5. Повтор без проверки запрещён тем же доводом, что в 9.3: если запись всё же легла, она удвоится.

Основание: 1 случай, последний 2026-10-12, плюс документация GitHub (прочитана 2026-10-13, редакция GitHub Enterprise Server 3.16) — сессия Архивариуса запустила правку projects/archivarius/STATE.md через Git Replace одновременно с дозаписью в projects/archivarius/LOG.md через Git Append File: дозапись легла, правка отбита отказом «is at … but expected …» и легла следующим коммитом через 24 секунды. Строка 9 файла meta/PENDING_RULES.md, подтверждена владельцем 2026-10-12 (после вычистки строки — в истории этого файла).

9. Граница Канала

9.1. Доступность прямого git push контрактом не задаётся и из имени среды не выводится. Предикат — не среда, а список репозиториев, авторизованных для конкретной сессии. Проверяется в самой сессии одной командой `git push --dry-run` ДО выбора маршрута, и вывод одной сессии на другую не переносится, даже если обе называются одинаково: в одной и той же среде наблюдались обе стороны в один и тот же день. Отказ приходит дословно как «… is not in this session's authorized repository set», при полностью открытых clone и fetch.

Список авторизованных репозиториев задаётся при создании сессии, но у идущей сессии он может быть расширен — если среди её инструментов есть добавление репозитория в сессию (в облачной сессии на основе Claude Code это add_repo с доступом push). Порядок: `git push --dry-run` отбит текстом «not in this session's authorized repository set» → вызвать добавление репозитория lyamin-dot/second-brain-canon с доступом на запись → повторить `git push --dry-run`. Проба 2026-09-26, одна и та же сессия: до добавления — отказ 403 с этим текстом, после add_repo с доступом push — `git push --dry-run` прошёл, записей не делалось. Если такого инструмента в сессии нет — push открывается только созданием новой сессии НА этом репозитории (Т-2 и Р-23 журнала projects/kontext-reduktion/LOG.md); переключателя у идущей сессии тогда нет. Прежний вывод «push из облачной песочницы закрыт прокси» верен только как описание сессии без репозитория в источниках и границей платформы не является.

Следствие для 9.4: маршрут (б) планируется только после успешного `git push --dry-run` в этой сессии. Наряд, назначающий ГДЕ по имени среды в расчёте на открытый push, отбивается на приёме — среда о себе достоверно знает только проверкой.

Клон ДОПУСКАЕТСЯ как read-only подложка для diff, git hash-object (8.1) и чтения (7.6) в любой среде; репозиторий публичный, учётных данных для клона не нужно.

9.2. Граница 9.1 на Канал не распространяется: воркфлоу вызываются по HTTP или через MCP, PUT исполняет сервер n8n. Канал работает из любой среды. Формулировка «писать из этой среды нельзя» ЗАПРЕЩЕНА применительно к Каналу.

9.3. Чего Канал не делает. Git Write не удаляет. Git Read не перечисляет каталог. Git Append не проверяет номера — и может ответить успехом, не записав ничего: исполнение 60575 завершилось статусом success, а файл не изменился, повтор тем же телом записал штатно (Т-69 журнала projects/git-migration/LOG_ARCHIVE.md). Поэтому дозапись закрывается только сверкой по 8.1 — байтами файла до и после с origin/main, — а не ответом инструмента; повтор делается только после того, как сверка показала, что записи нет, иначе запись удвоится. Git Write и Git Commit Files не перезаписывают и не удаляют существующий append-only файл. Следствие: ротацию такого файла, его возврат к версии из истории и удаление тестового файла с защищённым именем Канал не выполняет ни при каком payload — только маршрут 9.4(б). Отсюда же правило гигиены: тестовый файл никогда не называется LOG.md, LOG_ARCHIVE.md или NOT_TAKEN.md, иначе он остаётся в репозитории навсегда.

Встреченная и не записанная граница возвращается в следующую сессию под видом поломки — пополнять этот пункт тем же действием, что и встречу.

9.4. Маршрут доставки правки в main. Единица доставки — состояние main на origin (8.7). Коммит в ветке claude/* доставкой не является: другая сессия его не видит, а номер записи append-only журнала он занимает, не отдавая. Маршрут выбирается по одному вопросу: набирает ли модель текст записи.

(а) Правка — фрагмент (Git Replace) или дозапись одной записи (Git Append File, запасной путь — Git Append; 8.3), и текст — продукт самой сессии → писать Каналом. Запись на GitHub выполняет сервер n8n прямо в main, ветка в записи не участвует. Маршрут по умолчанию в любой среде.

(б) Файл собирается из уже существующего текста → скрипт в среде, где `git push --dry-run` прошёл (9.1), собирает файлы из объектов git, сверяет их blob sha с эталоном, посчитанным до коммита и зашитым в скрипт, коммитит в ветку claude/* и переводит main перемоткой, без merge-коммита и PR. Несовпадение sha — стоп без коммита. Принудительная отправка (force-push) в main ЗАПРЕЩЕНА без исключений. Для ветки claude/* своей сессии разрешена только принудительная отправка с проверкой прежнего значения, `git push --force-with-lease=<ветка>:<прежний sha>` — когда ветку пришлось перебазировать на свежий main перед перемоткой; чужую ветку так не отправлять (прецедент — запись Р-120 журнала projects/git-migration/LOG.md, решение владельца по противоречию харвеста 2026-10-08).

Тот же маршрут — для любой массовой механической работы: опись файлов Drive или PDF, нарезка текста на файлы, пересборка, перенос большого тела. Её делает скрипт, а не модель: модель, набирающая или перекладывающая сотни строк, теряет и искажает их молча. Приёмка механического переноса — по мультимножеству непустых строк: каждая непустая строка исходника попала в результат ровно один раз и ни одной лишней (скрипт сравнивает счётчики строк исходника и результата; пустой остаток в обе стороны — перенос принят). Совпадение суммы байт приёмкой не является. Полный текст PDF через read_file_content Google Drive — только прицельно, по одному файлу: одна статья стоила около 25 000 токенов. Основание — тупик Т-1 и запись Р-15 журнала projects/archive-recon/LOG.md, записи Р-12, Р-18…Р-23 журнала projects/kontext-reduktion/LOG.md, тупик Т-01 журнала projects/anis-evidence/LOG.md.

(в) Ни (а), ни (б) в среде недоступны → остановиться и назвать операцию (И-4). Частый случай — удалить или переписать крупный существующий фрагмент: Git Replace требует привести фрагмент целиком в вызове, то есть набрать его моделью, а правило происхождения текста (references/write.md, 4.5) это запрещает. Выходов два: (1) дождаться среды, где `git push --dry-run` проходит, и сделать правку маршрутом (б); (2) владелец правит файл сам в веб-редакторе GitHub — сессия отдаёт ему путь, точные границы фрагмента (первая и последняя строка дословно) и что останется на месте, а после правки принимает её по объекту чтением файла (8.1). Прецедент — шаг 3 projects/n8n-map/STATE.md (удаление разделов 1 и 9 PLAN.md, около одиннадцати килобайт). Молча оставить запись в ветке ЗАПРЕЩЕНО: незакрытая доставка называется в отчёте и позицией Очереди. Ветка claude/*, не переведённая в main той же сессией или ближайшим нарядом, — незакрытая доставка, а не «ждёт ревью»: ревьюера в этой системе нет. Ветка с ошибочным содержанием в main не сливается.
