# second-brain-git — новый проект и перенос из Docs

Часть Skill second-brain-git. Читать: перед заведением проекта в repo или переносом документа из Docs. Номера пунктов — прежние, общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md.

12. Новый проект в repo

12.1. Проверить, что имя свободно на обоих носителях: строки в registry/projects.md нет и INDEX в Docs нет. Проверка разовая, при создании.

12.2. Создать projects/<имя>/ по 2; STATE.md и PLAN.md сразу; LOG.md — по 4.4.

12.3. Внести строку в registry/projects.md: проект | папка | носитель | статус — тем же действием.

12.4. Закрытие проекта — смена статуса в registry/projects.md, не удаление. Отдельного протокола архивации нет.

12.5. Выбор носителя для нового проекта — Skill second-brain-engineer, файл references/onboarding.md, раздел Р4, пункт 0.

13. Перенос из Docs в repo

Здесь — то, что обязан знать выдающий задание на перенос, и правила приёмки целиком. Подробные правила разбора задач и записей — этапы 0а, 0б, 0в и 5 файла meta/PROTOCOL_file-migration.md (редакция 5 от 2026-10-05). Раздел «Контракт записи» и пункт 10.5 «потолок размера» того же файла, а также шаблон meta/NARYAD_file-migration.md целиком написаны до правила происхождения текста и до правила «перенос закончен только в main»: они велят писать каждый файл через Git Write, запрещают push, требуют схождения суммы байт и называют потолок записи, которого нет. При расхождении с ними действует этот файл и references/write.md; по ним самим переноса не вести (противоречие В20 харвеста 2026-10-08, решение о переписывании этих файлов — за владельцем).

13.1. Переносится смысл, не буквы: действующие правила, состояние, опыт едут; след, отменённое, пересказ чужого носителя — строка в NOT_TAKEN.md с адресом. Источник замораживается, не удаляется.

13.2. Требовать одновременно перенос по буквам и результат по смыслу ЗАПРЕЩЕНО: разбор по ролям включает право чинить перекрёстные ссылки, заголовки и разрывы фраз.

13.2а. Перед переносом записи о багах, задачах и состоянии сверяются с живой системой (воркфлоу n8n, таблица, файл): что уже исправлено или снято, едет как история с датой исправления, а не как действующее. Устаревшая запись о баге, перенесённая как живая, отправит следующую сессию чинить исправленное. Основание — записи Р-36 журнала projects/wb-ue/LOG.md (прод падал дважды, баг к переносу уже исправлен), Р-1 журнала projects/wb-reviews/LOG.md, Р-44 и Р-45 журнала projects/wb-logistics/LOG.md.

13.2б. Предмет, существующий только из-за механики прежнего носителя — поля и зоны документа Docs, пароли-канарейки, мониторы размера зон, счётчики байт Docs, — при переезде не переносится, а снимается строкой в NOT_TAKEN.md с адресом: в repo у него нет ни читателя, ни смысла (записи Р-71, Р-90, Р-92, Р-93, Р-108 журнала projects/git-migration).

13.3. Вход задания лежит в repo или целиком в тексте задания; ссылка на результат прошлой сессии входом не является. Выход выносится по постоянному адресу раньше, чем улучшается способ доставки.

13.4. Приёмка — две независимые проверки, ни одна в одиночку приёмкой не является.

Снимок источника снимается дважды: в начале переноса и ещё раз в начале приёмки (у документа Docs — byteLength и checkSum ответа gdocs-read). Расхождение называется в отчёте, и выдающий задание решает, заморожен ли источник; адресацию по номерам строк расхождение само не отменяет — проверяется, совпало ли содержание адресованных строк. Если перенос режет файл на блоки, карта разбиения до записи проверяется на сплошность и непересечение: блоки покрывают файл от первой строки до последней без дыр и без наложений — текст вне блоков теряется молча, и ни одна проверка ниже этого не увидит.

(а) Транспорт: построчное сравнение записанного с эталоном из версии до записи, исполнителем внутри задания, каждое расхождение объяснено; совпадение размеров и сумм приёмкой не является. Плюс инвентаризация идентификаторов: все ID источника (Drive fileId, ID воркфлоу n8n, номера Р/Т/Н, номера нарядов вида Н-ДД.ММ-NN, номера исполнений в формах «execution N», «executions N–M» и каждый номер внутри такого диапазона, ссылки вида «CORE Р.N») извлекаются регулярным выражением, и каждый найден либо в цели, либо в NOT_TAKEN.md с адресом. Выражение для исполнений принимает форму множественного числа и диапазон через тире или дефис. Непустой diff — транспорт не принят.

(б) Смысл: Контролёр — независимая сессия, читающая только замороженный источник и цель, поштучно по каждой записи: вопрос, решение, «почему», все отвергнутые (счётом), «кто подтвердил», «обратимость», «допущение», «условие возврата», статус; не появилось ли утверждений, которых нет в источнике; не искажены ли числа, ID, даты, имена. Вердикт: цело / потеря / искажение / не найдено.

Задание Контролёру выдаётся вместе с заданием на перенос и не содержит выводов и итоговых чисел переносившего: Контролёр считает и судит сам. Контролёр — отдельный агент (субагент сессии через Agent tool или отдельная сессия) без доступа к рассуждениям переноса и к вердиктам прошлых кругов. Изоляцию держит и способ выдачи записей: Git Read Lines с from без to возвращает остаток файла целиком и вместе с нужной записью раскрывает чужие вердикты, поэтому записи Контролёру выдаются диапазоном с верхней границей to (запись Р-85 журнала projects/git-migration/LOG_ARCHIVE.md). Если переносимый материал читается сессией целиком на старте (CORE, список задач), Контролёр получает экзамен — вопросы, составленные после разбора, до переноса, и только по переезжающему материалу. Помимо вердиктов Контролёр выдаёт раздел ПРЕДЛОЖЕНИЯ: по каждому классу найденных дефектов — правку протокола или Skill с файлом, якорем и полным текстом «было → стало».

Круги. Контролёр прогоняется заново после каждого круга исправлений, включая сверку самих исправлений. Сессия прогоняет МИНИМУМ ТРИ круга подряд сама, не обращаясь к владельцу между кругами и не докладывая после первого и второго; если третий или следующий круг ещё находит новые дефекты транспорта или смысла — правит и запускает следующий, пока какой-нибудь круг не пройдёт без новых дефектов, но не меньше трёх кругов, даже если первый ничего не нашёл. Владельцу докладывается один раз — по итогам круга, которым процесс остановился. Вердикт Контролёра-субагента своей сессии — проверка, а не подтверждение владельца: в поле «кто подтвердил» он не пишется как слово Андрея (references/write.md, 11.4). Основание — запись Р-119 журнала projects/git-migration/LOG.md и раздел 8 projects/git-migration/PLAN.md (решение владельца 2026-09-28); ряды находок по кругам: wb-ue 6→2→0 блокирующих, n8n 13, 4, 1, 0 дефектов (запись Р-3 журнала projects/n8n/LOG.md).

Основание, по которому проверок именно две: сверка по diff однажды дала ноль расхождений на переносе, в котором Контролёр нашёл тринадцать дефектных записей из двадцати.

13.5. Обе проверки — пока источник доступен; заморозка или удаление — после предъявленной приёмки (13.4).

13.6. Перенос закончен только в main. Коммит в ветке claude/* — черновик: Git-канал n8n читает и пишет только main, другие сессии содержимого ветки не видят, а проверки внутри самой сессии (клон, git log, blob sha) смотрят на её ветку и показывают успех. Порядок строгий: проверки 13.4 → доставка в main по 9.4 → чтение Каналом → заморозка источника → объявление приёмки и доклад владельцу. Доставка проверяется только снаружи ветки — чтением projects/<имя>/STATE.md через Git Read или Git Read Batch; ответ «could not be found» означает, что доставки нет. В отчёте о переносе обязательна строка «main <sha головы> содержит projects/<имя>/STATE.md, blob <sha> — прочитано Каналом, исполнение <номер>». Не удалось доставить — сказать «перенос НЕ доставлен в main, лежит в ветке <имя>»; объявлять приёмку в этом состоянии ЗАПРЕЩЕНО. Прецедент и полный текст правила — projects/git-migration/PLAN.md §9, запись Р-121 журнала projects/git-migration/LOG.md.
