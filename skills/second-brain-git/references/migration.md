# second-brain-git — новый проект и перенос из Docs

Часть Skill second-brain-git. Читать: перед заведением проекта в repo или переносом документа из Docs. Номера пунктов — прежние, общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md.

12. Новый проект в repo

Проект существует для читателя через строку registry/projects.md: сессия, которая ищет проект, ищет его там, а не перечислением папок (3.2). Поэтому строка реестра заводится, меняется и никогда не удаляется вместе с жизнью проекта.

12.1. Проверить, что имя свободно на обоих носителях: строки в registry/projects.md нет и INDEX в Docs нет. Проверка разовая, при создании: занятое имя дало бы два носителя одного проекта (И-1).

12.2. Создать projects/<имя>/ по 2; STATE.md и PLAN.md сразу; LOG.md — по 4.4 (первой квалифицирующей записью, не заранее).

12.3. Внести строку в registry/projects.md: проект | папка | носитель | статус — тем же действием, что создание папки.

12.4. Закрытие проекта — смена статуса в registry/projects.md, не удаление. Отдельного протокола архивации нет: содержимое закрытого проекта читается из истории, строка реестра остаётся адресом.

12.5. Выбор носителя для нового проекта — Skill second-brain-engineer, файл references/onboarding.md, раздел Р4, пункт 0.

13. Перенос из Docs в repo

Здесь — то, что обязан знать выдающий задание на перенос, и правила приёмки целиком. Подробные правила разбора задач и записей — этапы 0а, 0б, 0в и 5 файла meta/PROTOCOL_file-migration.md (редакция 5 от 2026-10-05). Раздел «Контракт записи» и пункт 10.5 «потолок размера» того же файла, а также шаблон meta/NARYAD_file-migration.md целиком написаны до правила происхождения текста и до правила «перенос закончен только в main»: они велят писать каждый файл через Git Write, запрещают push, требуют схождения суммы байт и называют потолок записи, которого нет. При расхождении с ними действует этот файл и references/write.md; по ним самим переноса не вести (противоречие В20 харвеста 2026-10-08 — пометки в первых строках обоих файлов; решение о переписывании этих файлов — за владельцем).

ЗАКОН ПЕРЕНОСА. Перенос принят, только когда смысл подтвердил читатель, независимый от переносившего и видящий лишь источник и цель, а цель доступна из main. Почему: любая проверка, замкнутая на собственный выход сессии, — diff с тем, что сессия собиралась записать, проверка, которой дали выводы переносившего, проверка внутри своей ветки, — подтверждает намерение сессии, а не источник, и показывает успех там, где смысл потерян. Частные случаи этого закона — 13.4–13.6; пункты 13.1–13.3 задают, что и из чего переносится.

13.1. Переносится смысл, не буквы: действующие правила, инварианты, контракты, состояние, открытые вопросы, опыт едут; след, отменённое, пересказ чужого носителя — строка в NOT_TAKEN.md с адресом. Источник замораживается, не удаляется: поэтому невзятое восстановимо по адресу, и дословность страховкой не нужна.
Основание — запись Р-36 журнала projects/git-migration/LOG_ARCHIVE.md (2026-09-03).

13.2. Требовать одновременно перенос по буквам и результат по смыслу ЗАПРЕЩЕНО: разбор по ролям включает право чинить перекрёстные ссылки, заголовки и разрывы фраз. Признак нарушения: Контролёр выносит дефект «не дословно» на синониме, круги не сходятся, а правила после каждого круга только ужесточаются. Побайтово переносятся идентификаторы, пути, номера параграфов, собственные названия, числа, даты, метки приоритета.
Основание — 1 случай, 2026-09-16: три круга без сходимости (10, 5, 10 дефектов), запись Р-83 журнала projects/git-migration/LOG_ARCHIVE.md.

13.2а. Перед переносом записи о багах, задачах и состоянии сверяются с живой системой (воркфлоу n8n, таблица, файл): что уже исправлено или снято, едет как история с датой исправления, а не как действующее. Почему: устаревшая запись о баге, перенесённая как живая, отправит следующую сессию чинить исправленное.
Основание — 3 переноса, последний 2026-10-05: запись Р-36 журнала projects/wb-ue/LOG.md (прод падал дважды, баг к переносу уже исправлен), запись Р-1 журнала projects/wb-reviews/LOG.md, записи Р-44 и Р-45 журнала projects/wb-logistics/LOG.md.

13.2б. Предмет, существующий только из-за механики прежнего носителя — поля и зоны документа Docs, пароли-канарейки, мониторы размера зон, счётчики байт Docs, — при переезде не переносится, а снимается строкой в NOT_TAKEN.md с адресом: в repo у него нет ни читателя, ни смысла. Признак: предмет умирает вместе с носителем.
Основание — 5 записей журнала projects/git-migration/LOG_ARCHIVE.md, последняя 2026-09-23: Р-71, Р-90, Р-92, Р-93; запись Р-108 журнала projects/git-migration/LOG.md.

13.3. Вход задания лежит в repo или целиком в тексте задания; ссылка на результат прошлой сессии входом не является: рабочая среда сессии не переживает саму сессию. Выход выносится по постоянному адресу раньше, чем улучшается способ доставки: невынесенный результат теряется при закрытии чата целиком.
Основание — 2 случая, последний 2026-09-06: запись Р-11 и тупик Т-31 журнала projects/git-migration/LOG_ARCHIVE.md.

13.4. Приёмка — две независимые проверки, (а) и (б); ни одна в одиночку приёмкой не является. При переносе проекта к ним добавляется контрольный набор вопросов (в).

Снимок источника снимается дважды: в начале переноса и ещё раз в начале приёмки (у документа Docs — byteLength и checkSum ответа gdocs-read). Расхождение называется в отчёте, и выдающий задание решает, заморожен ли источник; адресацию по номерам строк расхождение само не отменяет — проверяется, совпало ли содержание адресованных строк. Почему: адреса NOT_TAKEN.md и вердиктов привязаны к снимку, и невоспроизводимый снимок делает их непроверяемыми.

Если перенос режет файл на блоки, карта разбиения до записи проверяется на сплошность и непересечение: блоки покрывают файл от первой строки до последней без дыр и без наложений. Почему: текст вне блоков теряется молча, и ни одна проверка ниже этого не увидит — обе сверяют то, что попало в блоки.

(а) Транспорт. Построчное сравнение записанного с эталоном из версии до записи, исполнителем внутри задания; каждое расхождение объяснено. Совпадение размеров и сумм приёмкой не является. Плюс инвентаризация идентификаторов: все ID источника извлекаются регулярным выражением, и каждый найден либо в цели, либо в NOT_TAKEN.md с адресом. Что входит в инвентаризацию:

| Вид идентификатора | Форма |
|---|---|
| Drive | fileId |
| n8n | ID воркфлоу |
| записи и задачи | номера Р/Т/Н |
| наряды | Н-ДД.ММ-NN |
| исполнения n8n | «execution N», «executions N–M» и каждый номер внутри такого диапазона; выражение принимает форму множественного числа и диапазон через тире или дефис |
| ссылки на канон | «CORE Р.N» |

Непустой diff — транспорт не принят.

(б) Смысл. Контролёр — независимая сессия, читающая только замороженный источник и цель, поштучно по каждой записи: вопрос, решение, «почему», все отвергнутые (счётом), «кто подтвердил», «обратимость», «допущение», «условие возврата», статус; не появилось ли утверждений, которых нет в источнике; не искажены ли числа, ID, даты, имена. Вердикт по записи: цело / потеря / искажение / не найдено.

Изоляция Контролёра — чем она держится:
- Задание Контролёру выдаётся вместе с заданием на перенос и не содержит выводов и итоговых чисел переносившего: Контролёр считает и судит сам.
- Контролёр — отдельный агент (субагент сессии через Agent tool или отдельная сессия) без доступа к рассуждениям переноса и к вердиктам прошлых кругов.
- Способ выдачи записей: Git Read Lines с from без to возвращает остаток файла целиком и вместе с нужной записью раскрывает чужие вердикты, поэтому записи Контролёру выдаются диапазоном с верхней границей to.

Если переносимый материал читается сессией целиком на старте (CORE, список задач), Контролёр получает ещё экзамен — вопросы, составленные после разбора, до переноса, и только по переезжающему материалу. Не путать: экзамен, составленный до разбора по всему источнику, бьёт по правомерно отсеянному материалу и даёт ложный отказ.

Помимо вердиктов Контролёр выдаёт раздел ПРЕДЛОЖЕНИЯ: по каждому классу найденных дефектов — правку протокола или Skill с файлом, якорем и полным текстом «было → стало».

Круги. Контролёр прогоняется заново после каждого круга исправлений, включая сверку самих исправлений: исправление само вносит дефекты. Сессия прогоняет МИНИМУМ ТРИ круга подряд сама, не обращаясь к владельцу между кругами и не докладывая после первого и второго; если третий или следующий круг ещё находит новые дефекты транспорта или смысла — правит и запускает следующий, пока какой-нибудь круг не пройдёт без новых дефектов, но не меньше трёх кругов, даже если первый ничего не нашёл. Владельцу докладывается один раз — по итогам круга, которым процесс остановился. Вердикт Контролёра-субагента своей сессии — проверка, а не подтверждение владельца: в поле «кто подтвердил» он не пишется как слово Андрея (references/write.md, 11.4).

(в) Контрольный набор вопросов — при приёмке переноса проекта в repo, рядом с проверкой Контролёра, а не вместо неё: пять вопросов о проекте («где ID книги X», «какой следующий шаг»), на которые незнакомая сессия должна ответить только по канону. Неверный или ненайденный ответ — дефект переноса. Почему: обе проверки выше сверяют цель с источником, а набор проверяет, найдёт ли нужное сессия, которая будет читать только цель; повреждённый идентификатор прошёл приёмку переноса без такого набора. Это приёмка, а не монитор. Условие снятия: три приёмки подряд набор не нашёл ни одного дефекта — набор снимается.

13.5. Обе проверки — пока источник доступен: они сверяют цель с источником; заморозка или удаление — после предъявленной приёмки (13.4).

13.6. Перенос закончен только в main. Коммит в ветке claude/* — черновик: Git-канал n8n читает и пишет только main, другие сессии содержимого ветки не видят, а проверки внутри самой сессии (клон, git log, blob sha) смотрят на её ветку и показывают успех.

Порядок строгий:
1. проверки 13.4;
2. доставка в main по 9.4;
3. чтение Каналом;
4. заморозка источника;
5. объявление приёмки и доклад владельцу.

Доставка проверяется только снаружи ветки — чтением projects/<имя>/STATE.md через Git Read или Git Read Batch; ответ «could not be found» означает, что доставки нет. В отчёте о переносе обязательна строка «main <sha головы> содержит projects/<имя>/STATE.md, blob <sha> — прочитано Каналом, исполнение <номер>». Не удалось доставить — сказать «перенос НЕ доставлен в main, лежит в ветке <имя>»; объявлять приёмку в этом состоянии ЗАПРЕЩЕНО.
Основание — 1 случай, 2026-09-28: записи Р-120 и Р-121 журнала projects/git-migration/LOG.md; полный текст правила — projects/git-migration/PLAN.md, раздел 9.
