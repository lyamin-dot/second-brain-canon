# second-brain-git — цены и бюджеты в байтах

Часть Skill second-brain-git. Читать: когда решение опирается на цену транспорта или бюджет старта в байтах. Номера пунктов — прежние, общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md.

Бюджеты, снятые с объекта 2026-09-26 клоном (замер при обходе Skill). Старт сессии repo-проекта — meta/PENDING_RULES.md 2 917 Б плюс STATE.md своего проекта: от 2 332 Б (anis-evidence) до 9 309 Б (git-migration), то есть от 5 249 до 12 226 Б; PENDING_RULES.md на эту дату несёт только строки, уже внесённые в Skill, и после их вычистки владельцем (И-6) старт дешевеет почти на всю его величину. Команда, читающая CORE (!save, харвест и прочие по мастер-промпту), — core/MANIFEST.md 7 529 Б плюс 4 файла таблицы «Список» 8 234 Б = 15 763 Б, двумя вызовами Git Read Batch; файлы таблицы «По событию» в эту сумму не входят и оплачиваются только сессией, у которой событие наступило (Р-111 журнала git-migration, Р-3 журнала kontext-reduktion). Признак старта CORE по 7.2 на эту дату: 4 / core/R-07.md / 21e479d. Прежние замеры: 2026-09-24 — старт 10 232 Б (PENDING_RULES 1 377 + STATE git-migration 8 855), CORE 15 833 Б; 2026-09-18 — CORE 38 293 Б, 11 файлов и meta/header.md, до решений о таблице «Список».

Оба числа — гипотезы от даты замера, а не нормы, и сверяются с объектом при каждой ревизии контракта. Повторять их по памяти или переносить из прошлой редакции ЗАПРЕЩЕНО: CORE и STATE меняются, и перенесённое число врёт молча.

Опровергаются эстафетой, в которой вердикт ЭСТАФЕТА вынесен по исчерпанию контекста до закрытия наряда и старт либо чтение CORE названы в строке СТОИМОСТЬ среди потребителей. Такая эстафета записывается в LOG.md тупиком по форме 11. Первый такой тупик — запись без пересмотра; второй — пересмотр бюджета при ближайшем харвесте. Превышение бюджета ростом файлов — сигнал харвесту по 5.5, не отказ и не блок.

Цена транспортов. Читатель — сессия; задача — «достать одну запись из журнала»; даты снятия названы. Доказательства (номера исполнений) — записи Р-100 и Р-102 журнала git-migration.

Сплошное чтение суженным вызовом и клон стоят почти одинаково по байтам — 1,0×: тело файла приходит один раз и там, и там. Разница — конверт ответа Канала. Замер в токенах 2026-09-24 (Р-20 журнала projects/kontext-reduktion/LOG.md): пакет старта SYS 26 438 Б стоил 9 598 токенов через Git Read Batch с сужением до 05_Respond и 8 083 токена чтением из клона — Канал дороже примерно на 19 процентов. Поэтому там, где клон есть, файл целиком читается клоном (7.6), а не Каналом «потому что одинаково». А вот на ИЗВЛЕЧЕНИИ ФРАГМЕНТА клон стоит 0,19×, и сплошное чтение проигрывает впятеро и больше — поэтому «прочитать файл целиком и найти нужное глазами» правильным ответом не является нигде, кроме случая, когда нужен весь файл.

Конверт в 1,1 КБ — оценка по составу ответа, а не измерение: харнесс не отдаёт размер своего ответа в байтах. Названа оценкой и повторению как измерение не подлежит.

Цена тела записи (читатель — сессия, пишущая в append-only файл; дата 2026-09-24; основание — Р-15…Р-17 журнала projects/kontext-reduktion/LOG.md): тело в параметре-объекте execute_workflow хранится в контексте последовательностями \uXXXX и стоит около 1,8 токена на байт, тело в textContent файла Drive — около 0,45 токена на байт, сам вызов Git Append File — около 260 токенов. На этих числах стоит выбор Git Append File основным путём дозаписи в 8.3.

Снимок registry/n8n-map.md (2026-09-26) новых цен транспорта не даёт: он не хранит ни размеров ответов, ни типов узлов. Он подтверждает только число узлов загрузки у каждого грязного воркфлоу (7.6), то есть кратность утечки при ошибочном includeData:true. Цены таблицы выше повторным замером не пересняты.

Приём, разделяющий две причины дороговизны: вызвать `get_execution(includeData:true)` с заведомо несуществующим именем узла в `nodeNames`. Тогда `runData` придёт пустым, и всё, что осталось в ответе, — это утечка узла, а не дублирование по графу.
