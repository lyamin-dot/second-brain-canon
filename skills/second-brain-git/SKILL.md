# second-brain-git

Как сессия физически читает и записывает файл репозитория lyamin-dot/second-brain-canon (ветка main): Каналом (воркфлоу n8n Git Read, Git Read Batch, Git Read Lines, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files, Git Log) или клоном, чем доказывает запись и как доставляет её в main. Что делать, когда и с чьего согласия — Skill `second-brain-engineer`; при расхождении с ним по вопросу о файле в repo действует этот Skill.

## Стоп-правила

### Носитель и данные
- Второго носителя у документа не заводить: канонический носитель один — Docs или repo.
- Дубль того, что уже живёт в журнале, Skill, реестре или Очереди, в repo не везти — строка в NOT_TAKEN.md с адресом (при переносе) или указатель.
- В repo не писать (запись необратима: коммит остаётся в истории; вопрос «можно ли» — до записи, по классу данных): (1) секреты и их признаки — пути вебхуков n8n, признаки их аутентификации (в том числе «у этого входа авторизации нет»), имена и номера ключей доступа (credentials), адреса сервисных аккаунтов, токены, пароли, ключи API; (2) личные данные владельца и других людей — почта, телефоны, банковские реквизиты, номера документов, PIN-коды и номера бронирований, домашние адреса, имена и пути личных папок на дисках владельца; (3) чужие охраняемые тексты — тексты и оглавления статей, книг, руководств, выдержки из платных баз (пишутся название, автор, ссылка); (4) код книг Google Sheets (проекты Apps Script) — в этот репозиторий не кладётся в любом случае. Материал этих классов лежит на Google Диске владельца или в закрытом носителе; в repo — только где он лежит, без значения.
- Классы 1 и 2 не публиковать и в странице-артефакте и её данных; проверка — до публикации, по классу.
- Перед каждым пишущим вызовом Канала проверять текст на классы 1–4 (фильтра в воркфлоу записи Канала пока нет).
- Нарушение классов, найденное в текущей версии файла, не оставлять: снять правкой тем же действием, что и находка, и назвать в отчёте вместе с тем, что история коммитов его хранит; закрыть историю может только перевод репозитория в приватный — вопрос владельцу.
- Воркфлоу, автоматически публикующий в repo данные с инстанса, не строить без защиты в коде до записи: строка с «/webhook/», «http:» или «https:», «Bearer» или «@» роняет прогон; идентификаторы — только из ключей по белому списку, не регулярным выражением по всему тексту.
- Адреса, ID воркфлоу, номера исполнений, состав проектов в Skill не хранить — они в `registry/`.
- `registry/n8n-map.md` руками не править — его строит воркфлоу.
- Правила вики в этот Skill не копировать — они в `wiki/DESIGN.md`.
- В документ SYS_INDEX (Google Docs, заморожен) не писать; своего INDEX в Docs у repo-проекта нет.

### Вызов Канала
- `executionMode: "production"` не использовать: `"manual"` — в каждом вызове явно.
- Поле `type` в `inputs` не передавать; описанию инструмента со старой схемой не верить — верить ошибке сервера.
- Имя триггера `01_Webhook` не переносить на воркфлоу вне Канала (gdocs-* и другие) — их имя из сигнатуры в `registry/tools.md` или `get_workflow_details`.
- Без реестра воркфлоу Канала не вызывать, не подтвердив ID и сигнатуру через `get_workflow_details`.
- Git Grep не вызывать ни для какой задачи.
- Операцию, не покрытую Каналом, в обход Канала не исполнять — назвать её и остановить шаг.
- О Канале не говорить «писать из этой среды нельзя»: он работает из любой среды.

### Чтение
- Транспорт чтения не выбирать иначе, чем по таблице «Чем читать», и не позже первого чтения в сессии.
- Через Канал не читать без сужения `get_execution(includeData:true, nodeNames:[<терминальный узел Respond>])`.
- У грязных воркфлоу (Git Log, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files) `get_execution` с `includeData:true` не звать — только `includeData:false`.
- Файл целиком ради одной записи не читать, когда доступен клон или Git Read Lines с pattern.
- Посредника (субагента, читающего вместо сессии) к файлам repo не применять.
- Русские буквы в шаблоне вызова Канала (pattern Git Read Lines) не набирать.
- В оболочке без настроенной локали точку вместо русской буквы и класс `[РТ]` в шаблоне grep не писать — только чередование `(Р|Т)`.
- Обрезанный вывод не считать прочитанным файлом; по частично прочитанному STATE.md или PLAN.md не работать.
- Git Read Batch с `returned < requested` или непустым `missing` — чтение набора не состоялось, стоп.
- Сверка `byteLength` с `text` против порчи внутри воркфлоу не помогает (сравнивает файл сам с собой).
- Пароль-канарейку, FNV и счётчики к файлам repo не применять и основанием для отказа не делать.
- `meta/header.md` на старте не читать; STATE.md на старте читать без записи (полей LAST_READ у repo-файлов нет).
- Git Log для пометки лежалости задач лаборатории при наличии клона не звать; Git Log — только с минимальным limit.
- Число цены, бюджета или множителя по памяти или из прошлой редакции не повторять — сверять с объектом; оценку конверта ответа Канала (около 1,1 КБ) не повторять как измерение; цену в токенах на байт, снятую с одного объекта, на другой не переносить.
- Вывод «не существует», «перезаписано», «не превышал» по клону с ограниченной глубиной не делать; утверждение об истории репозитория не писать в файл без двух величин той же сессии (раздел «Утверждение об истории репозитория»).

### Запись
- Запись не считать выполненной по ответу инструмента или серии успешных ответов — только по независимому перечитыванию с origin/main после свежего fetch и совпадению blob sha с намеренным.
- Текст записи не набирать в теле вызова по памяти или плейсхолдером: он существует файлом до вызова (файл на диске сессии или файл Drive в `_git_staging`).
- Уже существующий текст моделью не набирать — ротация, возврат версии из истории, перенос тела файла, пересборка, копия живого Skill в зеркало, разрез core/; единственное исключение — «Вычёркивание из наличного текста».
- «Собрать новый текст целиком» транспортом по умолчанию не считать; Git Write заменой целиком существующего файла не писать, если текст не порождён этой сессией и не подпадает под исключение.
- Текст с обратной косой чертой (пути Windows, кавычки внутри кавычек, регулярные выражения, перевод строки в литерале) не писать через оболочку (heredoc, echo) и строковый литерал скрипта — только инструментом записи файла (Write, Edit); скрипт замены берёт старый и новый текст из такого файла.
- Записанное с обратной косой чертой не коммитить и не считать записанным без перечитывания записанных байтов.
- Последовательности `\uXXXX` в теле вызова не набирать — ни вручную, ни копированием вывода `json.dumps` по умолчанию.
- Пишущий вызов Канала с русским текстом в параметрах не отправлять, не проверив набор параметров на `\u` (при находке — переписать русскими буквами); длинный русский фрагмент правки прежним входом `oldStr`/`newStr` не передавать — только входом `fileId`.
- Одну запись append-only файла серией вызовов Git Append не писать; размер не повод дробить.
- Append-only файл (LOG.md, LOG_ARCHIVE.md, NOT_TAKEN.md, `registry/maintenance-queue.md`) целиком не перезаписывать и по кускам не пересобирать, в том числе ради одной строки — только Git Replace фрагмента.
- Номер записи для Git Append File или Git Append не брать из чтения, сделанного не непосредственно перед вызовом.
- Число позиций реестра (Очереди, любого файла-таблицы) не получать сложением приращений — только пересчётом строк самого файла.
- Два пишущих вызова Канала одновременно не запускать, в том числе в разные файлы и папки: следующий — только после результата предыдущего.
- На проверку blob sha у Git Write и Git Replace против второй записи, ушедшей одновременно в другой файл, не полагаться: она не защищает, обход «Git Write пофайлово» против двух одновременных записей не помогает.
- Составной save не закрывать до перечитывания каждого затронутого файла.
- Поверх отказа по expectedSha не перезаписывать без построчного diff; «пересекаются по смыслу» критерием не делать; слепо поверх отказа не писать — особо LOG.md.
- Git Append не повторять, пока сверка байт не показала, что записи нет.
- После отказа «is at … but expected …» не повторять без проверки файла.
- Тестовый файл не называть LOG.md, LOG_ARCHIVE.md или NOT_TAKEN.md.
- В записи не отказывать и её не откладывать из-за бюджета чтения или размера файла; отказ — только при несовпадении expectedSha, пересекающемся diff, непокрытой Каналом операции; на потолок записи в байтах как основание отказа не ссылаться — его нет.
- Текст ради бюджета чтения не ужимать (сокращение формулировки с потерей содержания).
- Позицию в Очереди по одному превышению бюджета чтения или размера не заводить.
- Правило о возможности транспорта не писать до зонда транспорта.
- Слова «потолок записи» в отчётах не употреблять: превышение бюджета называется превышением бюджета чтения.
- Пятую роль файла проекта не заводить без условий раздела «Дополнительные роли файла проекта»; раздел, не ложащийся ни в одну роль, — стоп и вопрос владельцу.
- LOG.md не заводить заранее; NOT_TAKEN.md — только при переносе из Docs.
- Номер, раздел или запись не сдвигать, файл, раздел или Skill не переносить, не снимать и не переименовывать без пересчёта всех ссылок на прежний адрес тем же действием; ссылки не искать по памяти.
- При сдвиге адреса не править записи журналов LOG.md, отчёты синтеза и харвеста (`meta/SYNTHESIS_*`, `meta/HARVEST_*`), прежний текст статусов Очереди.
- Адрес, привязанный к коммиту («на коммите X», «на родителе коммита X»), и прежние номера в хрониках (карты харвеста, NOT_TAKEN.md) механической заменой не править.
- Расхождение пары «русская — английская копия» тихо не выравнивать — стоп и вопрос Андрею, какая права; ни одна копия не главная автоматически.
- При параллельной работе в путь, не названный в поле РАМКА своего наряда, не писать.
- Непересечение путей параллельных сессий от гонки за голову ветки не защищает.
- Обход «Git Write пофайлово вместо Git Commit Files» для пары «файл и список, в котором он назван» не применять — ждать освобождения ветки.

### Журнал
- Решение не редактировать: отмена — новой записью со ссылкой; статус прежней — одной правкой Git Replace её строки-заголовка.
- Поправку полем внутри записи не вносить, если она отменяет пункт, внесена не тем же днём или запись уже прочла другая сессия.
- Тупик без условия возврата не писать; записанное раньше условие не исполнять без перепроверки по объекту и журналу.
- Ретроспективную запись не писать — только произошедшее в этой сессии; исключение — блок хроники.
- Поле по наличию без данных не писать — ни прочерком, ни заглушкой; обязательное поле без содержания — запись не писать, наряд вернуть выдавшему.
- Владельцу не приписывать подтверждение, которого не было; вердикт Контролёра-субагента не писать в «кто подтвердил» словом Андрея.
- Вывод сессии не писать, если он не назван выводом и не проверяем внутри записи.
- Блок хроники не писать без первой строки происхождения; номер Р или Т ему не давать.
- Отвергнутое без причины не писать.
- Старые записи на стандарт, введённый после них, не проверять и задним числом не переписывать.

### Очередь
- Правку Skill или мастер-промпта до харвеста не откладывать без позиции в Очереди.
- Статус позиции не начинать не словом словаря (раздел «Статус позиции Очереди»).
- ВНЕСЕНО, СНЯТА или ДУБЛЬ не ставить, не проверив по объекту каждую часть позиции.
- Позицию не снимать, не дав тем же действием новый статус позициям, ссылающимся на неё словом ДУБЛЬ.
- Внутренних переводов строки в текст позиции Очереди не вставлять.

### Доставка, ветки, push
- Коммит в ветке claude/* доставкой не считать.
- Force-push в main — никогда; ветку claude/* своей сессии — только `git push --force-with-lease=<ветка>:<прежний sha>`; чужую ветку так не отправлять.
- Маршрут (б) не планировать без успешного `git push --dry-run` в этой сессии; вывод о push одной сессии на другую не переносить, из имени среды не выводить.
- Скрипт маршрута (б) при несовпадении blob sha с эталоном не коммитит.
- Запись в ветке молча не оставлять — незакрытая доставка называется в отчёте и позицией Очереди.
- Ветку с ошибочным содержанием в main не сливать.
- Наряд, назначающий ГДЕ по имени среды в расчёте на открытый push, на приёме отбивать.
- Ветку claude/* не удалять без слова Андрея; ветку, на коммит которой ссылается журнал или канон, — без тега на этот коммит; в среде без push — не удалять.
- Совпадение суммы байт приёмкой механического переноса не считать.

### Перенос, заморозка, разрез, ротация
- Стоп-правила переноса из Docs, заморозки носителя, разреза core/ и ротации журнала — файл `references/redkie-operacii.md`, раздел «Стоп-правила»; операцию не начинать, не прочитав этот файл целиком.

### Лаборатория
- STATE.md, PLAN.md, LOG.md, RULES.md, NOT_TAKEN.md в лаборатории не заводить.

## Как делать

### Вызов воркфлоу Канала
1. ID и сигнатура — `registry/tools.md`. Реестр недоступен или ID неизвестен — найти воркфлоу по имени через `search_workflows`, подтвердить ID и сигнатуру через `get_workflow_details` до первого вызова.
2. `execute_workflow`: `workflowId` из `registry/tools.md`; `executionMode: "manual"`; `triggerNodeName: "01_Webhook"` (у всех воркфлоу Канала); `inputs: {webhookData: {method: "POST", body: {…вход воркфлоу…}}}`, без поля `type`. Пример — Git Read Batch: `body: {paths: ["core/MANIFEST.md"]}`.
3. Ошибка «Unrecognized key(s) in object: 'type'» — убрать `type`; «Provide triggerNodeName when passing inputs» — добавить `triggerNodeName`.
4. Результат — `get_execution` по правилам «Сужение и грязные воркфлоу».

### Чем читать
Транспорт выбирается до первого чтения в сессии, по таблице.

| Что нужно | Среда с клоном | Среда без клона |
|---|---|---|
| файл целиком | `git fetch && cat` | Git Read; набор путей — Git Read Batch |
| запись или фрагмент, номер строки неизвестен | `git fetch && grep` | Git Read Lines с входом pattern, один вызов |
| фрагмент, номер строки известен | `git fetch && sed -n` | Git Read Lines без pattern |
| история коммитов, дата последней правки | `git log` | Git Log, минимальный limit (грязный) |
| перечислить каталог | `git ls-files` | не покрыто Каналом: файл-список внутри папки |
| blob sha для сверки | `git hash-object` | sha из ответа любого читающего воркфлоу |
| проверить отсутствие файла или записи | `git ls-files` и `grep` | Git Read Lines с pattern |
| оглавление журнала LOG.md | `git fetch && grep -nE` с шаблоном оглавления | Git Read Lines, pattern = шаблон оглавления, limit не меньше числа записей; если count больше числа возвращённых строк — повторить с limit = count |
| запись журнала по номеру | `git fetch && grep -nA10` с шаблоном записи | Git Read Lines, pattern = шаблон записи, after = 10; если последняя возвращённая строка — поле записи (начинается с двух пробелов), дочитать строки с to+1 без pattern |
| дочитать файл после обрезанного вывода | `sed -n '<N>,$p'` с первой непрочитанной строки | Git Read Lines без pattern, from = первая непрочитанная строка; при риске нового обрыва — кусками с явным to |

Среда с клоном — сессия с bash и сетью на github.com; репозиторий публичный, клон анонимный. Среда без клона — среда без bash (Claude Project). Клон — read-only подложка для чтения, diff и `git hash-object` в любой среде; blob sha в клоне после `git fetch` совпадает с тем, что отдаёт Канал.

### Шаблоны поиска записей журнала
Строка-заголовок записи обязательна по форме журнала, поэтому оглавление выводится из файла в момент чтения.
- Вход Git Read Lines: оглавление — `^.-[0-9]+ \|` (точка вместо Р или Т), запись по номеру — `^.-111 \|` с номером нужной записи. Во входе JSON обратная косая черта удваивается.
- Оболочка в среде с клоном (grep): оглавление — `^(Р|Т)-[0-9]+ \|`, запись по номеру — `^Р-111 \|`.
- Оглавление журналов всех проектов (поиск прецедента): с клоном — `grep -nE '^(Р|Т)-[0-9]+ \|' projects/*/LOG.md projects/*/LOG_ARCHIVE.md`; без клона — Git Read Lines с шаблоном оглавления, один вызов на журнал; журнал целиком не читается.
- Р и Т нумеруются независимо: шаблон записи с точкой может вернуть две строки (count = 2) — нужная выбирается по первой букве.

### Сужение и грязные воркфлоу
1. Любое чтение через Канал — `get_execution(includeData:true, nodeNames:["05_Respond"])` или как называется терминальный узел Respond у этого воркфлоу.
2. Пишущие и Git Log — статус `get_execution(includeData:false)`; факт записи — независимым чтением чистым воркфлоу или клоном («Доказательство записи»).

| Воркфлоу | Узел загрузки | contextData |
|---|---|---|
| Git Read, Git Read Batch, Git Read Lines | `n8n-nodes-base.github` | пуст всегда — ЧИСТЫЕ |
| Git Log, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files | `n8n-nodes-base.httpRequest` | сырой ответ GitHub, `nodeNames` не режет — ГРЯЗНЫЕ |

Кратность утечки при ошибочном `includeData:true` — по числу узлов загрузки: Git Log 1, Git Write 1, Git Replace 2, Git Append 3, Git Append File 4 (три к GitHub, один к Google Drive), Git Commit Files 6. Новый читающий воркфлоу получает узел загрузки по этому свойству — Skill `n8n-engineering-manual`, раздел «Воркфлоу ради экономии контекста».

### Контракт ответа читающих воркфлоу
- Git Read `{path, ref?}` → `{text, sha, byteLength}`; `byteLength` — из тех же декодированных байт, что `text` (узел `04_Build_Response`). То же — у каждого файла ответа Git Read Batch.
- Порча при декодировании видна сессии символом замены U+FFFD в `text`.
- Обрезание на пути к модели: явно меньший текст при большом `byteLength` — обрезанный вывод.
- Git Read Batch `{paths[]}` → `{requested, returned, files[], missing[]}`.

### Обрезанный вывод
Признаки: пометка харнесса об обрезке или о сохранении вывода в файл; текст кончается посреди строки или раздела; увиденный текст явно меньше `byteLength`; у Git Read Lines `to` меньше `totalLines` при запросе до конца файла.
1. Дочитать файл по строкам с места обрыва (строка «дочитать файл после обрезанного вывода» таблицы «Чем читать») до того, как действовать.
2. Не удалось — отчёт о чтении называет непрочитанное.
Чтение журнала оглавлением и записями по номеру обрывом не является.

### Старт repo-сессии
1. Первым действием — `meta/PENDING_RULES.md` (бюджет чтения 2 048 Б). Строка с полем «кто подтвердил: Андрей» действует как правило этого Skill до внесения в него; при расхождении со Skill действует строка. Файл append-only: пишется через Git Append File (запасной путь — Git Append) только по решению журнала, подтверждённому владельцем в чате; вычищает владелец при правке Skill. Строка «Контекст загружен» и порядок старта — Skill `second-brain-engineer`, раздел «Р1. Старт сессии — Правило Феникса».
2. STATE.md своего проекта — без записи; актуальность даёт `git log`.
3. Команда, которой нужен CORE: «CORE прочитан целиком» = прочитаны все файлы таблицы «Список» `core/MANIFEST.md`. Признак в отчёте — три величины: число прочитанных файлов таблицы, путь последнего, его blob sha.
4. Таблица «По событию» Манифеста в старт не входит: файлы её строки читаются одним вызовом в сессии, где событие наступило, до первой записи этого вида — Git Read (один файл), Git Read Batch (несколько), `cat` (клон). Размеры приходят в ответе Канала.

### Имена и ссылки
1. Имя проекта = имя папки: нижний регистр, слова через дефис (git-migration); одно написание в пути, тексте, коммите, чате.
2. Первая строка файла — его путь; у файла с провенанс-маркером (`<!-- T-NN | CORE байт X-Y | … -->`) маркер остаётся первой строкой, путь — второй. Зеркало `skills/` — исключение: первая строка — frontmatter.
3. Ссылка на запись чужого файла — с именем файла: «Р-109 журнала projects/git-migration/LOG.md».
4. Сквозная нумерация: проект, чьи записи при разрезе переезжают между файлами, объявляет в PLAN.md сквозную нумерацию по проекту; тогда ссылка — голым номером, а последний выданный номер каждой последовательности хранится в файле-списке проекта и правится тем же действием, что запись.

### Сдвиг адреса
Сдвиг — перенумерация пункта, раздела или записи; перенос раздела или правила в другой файл или Skill; снятие файла, раздела или Skill; переименование файла или папки.
1. Тем же действием пересчитать все ссылки на прежний адрес — в своём файле и во всех ссылающихся, включая STATE.md и PLAN.md проектов, `meta/`, `registry/`.
2. Искать прежний адрес в квалифицированной форме (путь, «<файл>, <номер>», «пункт <номер>», не голый номер): `git fetch && grep -rnF '<прежний адрес>' <клон> /mnt/skills/plugins`. Без клона — Git Read Lines с pattern по каждому известному файлу-читателю; невыполненный поиск по всему репозиторию называется в отчёте.
3. Находка в Skill — текстом «было → стало» владельцу и позицией Очереди.
4. Не правятся: журналы, отчёты синтеза и харвеста, прежний текст статусов Очереди, адреса на коммите (рядом с путём назван коммит), прежние номера в хрониках (карты харвеста, NOT_TAKEN.md).

### Роли файлов проекта

| Роль | Содержание | Бюджет чтения | Читатель и момент |
|---|---|---|---|
| STATE.md | только то, что меняет действие следующей сессии: следующий шаг, открытые вопросы с критерием закрытия, блокеры, состояние объекта с датой проверки; состав и проверка — `meta/CONTRACT_state-content.md` | 8 192 Б | старт каждой сессии проекта |
| PLAN.md | цель, инварианты, архитектура, фазы, риски этого проекта | 10 240 Б | сессия, берущаяся за проект, целиком |
| LOG.md | решения, тупики, ошибки; только дописывается | 16 384 Б на прочитанное, не на файл | та же сессия рядом с PLAN: оглавление одним вызовом, затем целиком только нужные записи — названные в STATE.md или PLAN.md либо выбранные по оглавлению; файл целиком не читается |
| NOT_TAKEN.md | что не взято при переносе из Docs, адрес восстановления | нет | по вопросу «где это было» |

Бюджет ограничивает читателя (сумму прочитанного за момент), не файл и не запись; предела размера у файла летописи и потолка записи нет.
1. Разбор: состояние → STATE, правила → PLAN, опыт → LOG.
2. Вопрос к материалу: «правило про этот проект или про любой?» Про любой — `meta/`; реестр ID — `registry/`; про этот — PLAN.md.
3. LOG.md заводится первой квалифицирующей записью.
4. Аномалия, признанная нормой (ожидаемое постоянное состояние, намеренный дубль, известное расхождение), пишется с пометкой «не дефект, не расследовать» и причиной — в PLAN.md рядом с описанием объекта или в файле `meta/`, описывающем объект.

### Дополнительные роли файла проекта
Роль сверх четырёх или иной бюджет чтения — только при трёх условиях сразу; действует только в объявившем проекте:
1. материал не ложится ни в одну из четырёх ролей;
2. роль или бюджет объявлены в PLAN.md проекта с содержанием, числом, читателем и моментом чтения;
3. решение записано в LOG.md проекта с основанием, по которому его можно оспорить.

Агентская копия на английском — частный случай: шапка называет парный файл; для пары в `meta/` без своего журнала условие 3 не требуется. Правка одного файла пары — тем же коммитом правка другого; перед записью копии сверяются по составу: разделы, правила, числа, исключения.

### Превышение бюджета чтения
Превышение — не отказ, не блок, не дефект; лечение — разбор по роли.
Разбор по роли (бюджетом не ограничен): удалить дубль того, что живёт в LOG.md, Skill, реестре или Очереди (остаётся указатель); вынести закрытое с датой в LOG.md; удалить снимок чисел, устаревший к моменту записи. Вопрос к строке: изменит ли она действие следующей сессии; нет — строка не по роли.

STATE.md, PLAN.md, `meta/*` — переливной клапан, порядок обязателен:
1. Запись выполняется целиком, вне зависимости от бюджета.
2. Той же сессией, тем же нарядом — разбор: закрытое с датой → блок хроники в LOG.md («Блок хроники») через Git Append File (запасной путь — Git Append); дубль → указатель; снимок чисел → удаляется. Это вторая запись, не часть первой.
3. Файл после разбора над бюджетом остаётся над бюджетом. Критерий для файлов старта — по содержанию: каждая строка меняет действие следующей сессии; для STATE.md — четыре категории (`meta/CONTRACT_state-content.md`).

Проверка STATE.md скриптом (после любой записи STATE.md — тем же шагом и тем же коммитом; летопись записывает шаг сразу, !save не ждётся):
1. `python3 meta/scripts/state_split.py check projects/<имя>/STATE.md` по клону (клон анонимный, командная строка есть почти в любой среде, в том числе в сессиях Claude Project).
2. Раздел, который скрипт отнёс к истории или правилам, переносится той же сессией скриптом `meta/scripts/state_apply.py` (решения — файл JSON, приёмка по строкам внутри скрипта): отработавшее — блоком хроники в LOG.md, правила и реестры — в PLAN.md; только после смысловой сверки каждой переносимой строки: строка с открытым делом остаётся в STATE.md (скрипт решает по заголовку раздела).
3. Приёмка по строкам внутри скрипта доказывает, что строка не потеряна, а не что она легла на своё место.
4. Решения по снимку применяются, только если blob sha STATE.md равен снимку (`expect_sha` в файле решений `state_apply.py`, `--expect-sha` у `state_split.py`); иначе стоп и новый снимок.
5. Сессия без командной строки сравнивает byteLength STATE.md из ответа Канала с бюджетом 8 192 Б и при превышении пишет в отчёт о записи строку «STATE.md выше бюджета, разбор — следующей сессией с командной строкой» — это сигнал, не проверка содержания.
6. Строки раздела «От соседнего проекта», которые скрипт назвал (старше 7 дней или длиннее 500 Б), сессия разбирает той же записью: факт — в свой LOG.md или PLAN.md, нерешённое — открытым вопросом с критерием закрытия; строка вычёркивается. Решить сейчас нельзя — строка остаётся, в отчёте о шаге — «строк соседей к решению: N».

core/R-NN.md над бюджетом — «Разрез core/» (файл `references/redkie-operacii.md`), не стоп. Оглавление LOG.md выше бюджета чтения — ротация журнала той же сессией, по разделу «Ротация журнала» того же файла.

### Правило происхождения текста
Перед любой записью — один вопрос: порождён ли записываемый текст этой сессией?

| Текст | Примеры | Через модель | Транспорт |
|---|---|---|---|
| порождён этой сессией | решение, запись журнала, новый абзац, новый файл | идёт | «Чем писать» |
| уже существует | ротация, возврат версии из истории, перенос тела файла, пересборка большого файла, копия живого Skill в зеркало | не идёт никогда, независимо от размера | «Маршрут доставки в main», (б) |

Потолка записи в байтах нет ни для одного файла. Массовая механическая работа (опись, нарезка, пересборка, перенос большого тела) — тот же случай: маршрут (б).

### Вычёркивание из наличного текста
Существующий файл можно записать заново целиком, только если выполнены три условия сразу:
1. полный текст файла пришёл в контекст этой сессии ответом чтения (Канал или клон), не восстановлен по памяти, пересказу или прошлой сессии;
2. правка — удаление или вставка целых строк, остальные строки переносятся без изменения;
3. запись целиком нужна ради атомарности: сейчас только создание и закрытие задачи лаборатории (файл задачи и INDEX.md одним Git Commit Files).

Приёмка — по объекту, обязательна:
- с клоном: `git diff` против родителя коммита показывает ровно намеренные строки;
- без клона: размер после = размер до − байты удалённых строк + байты вставленных (каждая строка с переводом строки), и Git Read Lines с pattern по удалённой строке возвращает count = 0, по вставленной — count = 1.

### Чем писать
Вход в таблицу — один вопрос: набирает ли модель текст, который уже существует?

| Что делаю | Инструмент |
|---|---|
| дозапись одной записи в append-only файл (LOG.md, LOG_ARCHIVE.md, NOT_TAKEN.md, `registry/maintenance-queue.md`) | Git Append File, один вызов («Git Append File»); запасной путь — Git Append `{path, text}` |
| правка фрагмента существующего файла, в том числе внутри append-only | Git Replace; русский фрагмент длиннее строки — входом `fileId` («Git Replace с русским текстом») |
| новый файл или замена целиком | Git Write: новый — без expectedSha; замена — expectedSha = blob sha свежего чтения, только для текста этой сессии или по «Вычёркиванию из наличного текста» |
| несколько путей одним коммитом; любое удаление | Git Commit Files — единственный способ удалить путь; проходит целиком или не проходит |
| файл из уже существующего текста: ротация, возврат версии, перенос большого тела, пересборка | не Каналом — «Маршрут доставки в main», (б) |

Номер записи append-only файла: Git Append его не проверяет — берётся свежим чтением непосредственно перед вызовом (без клона — один Git Read Lines с pattern по шаблону номера); после записи тот же вызов: номер встречается ровно один раз. Две строки-заголовка с одним номером — параллельная сессия заняла номер: своя запись перенумеровывается Git Replace её строки-заголовка.

Серия Git Append ради одной записи начата и оборвана — следующая сессия дописывает хвост, голову не переписывает.

### Git Append File
1. `create_file` Google Drive: title любой, `parentId` — папка `_git_staging` (ID — `registry/tools.md`, строка Git Append File), `contentMimeType: "text/plain"`, `disableConversionToGoogleType: true`, `textContent` — текст записи целиком, включая ведущий перевод строки, если запись отделяется от предыдущей пустой строкой.
2. `execute_workflow` по «Вызову воркфлоу Канала» с `body: {path, fileId}`.
3. Проверка по «Доказательству записи»: прирост файла = размер файла-источника + 1.
4. После проверки файл-источник — в корзину (`trash_file`).

Новый файл Git Append File не создаёт: сначала Git Write со строкой пути (без expectedSha), затем тело — Git Append File.

### Набор кириллицы в вызовах Канала
Кириллица набирается как есть. Способ по виду вызова:

| Вид вызова | Как |
|---|---|
| читающие вызовы | русский текст не набирается: шаблоны «Шаблонов поиска записей журнала» |
| дозапись | Git Append File (текст из файла Drive) |
| правка фрагмента с русским текстом | Git Replace входом `fileId` («Git Replace с русским текстом») |
| прежний вход Git Replace `oldStr`/`newStr`, Git Write, Git Commit Files, запасной Git Append | перед вызовом найти в наборе параметров `\u`; при находке переписать русскими буквами; для одного-двух слов прежний вход дешевле create_file и trash_file |

Тело не идёт через вызов инструмента вовсе при записи клоном в сессии, где прошёл `git push --dry-run`.

### Git Replace с русским текстом
1. Файл text/plain в `_git_staging`: oldStr, перевод строки, строка `=====GIT-REPLACE-NEW=====`, перевод строки, newStr.
2. Git Replace входом `{path, expectedSha, fileId, message}`; файл без разделителя воркфлоу отбивает.
3. После записи файл — в корзину.

### Доказательство записи
Запись — изменение файла в main, доказанное независимым перечитыванием с origin/main после свежего fetch.

| Среда | Чем доказывать |
|---|---|
| с клоном | `git fetch` и `git hash-object` — blob sha записанного равен намеренному |
| без клона | один вызов Git Read Lines с pattern по первой строке записанного: sha, byteLength и фрагмент разом |

Git Append и Git Append File: `bytes_after − bytes_before = bytes_appended + 1` — Git Append всегда дописывает перевод строки плюс текст, в том числе когда файл уже оканчивается переводом строки.

### Составной save
1. LOG.md раньше STATE.md.
2. Каждая следующая запись — после результата предыдущей.
3. Save закрыт, когда каждый затронутый файл перечитан по «Доказательству записи»; частичный отказ досдаётся в той же сессии, иначе в LOG.md — запись о рассинхроне с именем недописанного файла.

### Отказы и ответы при записи
До повтора читается объект: повтор без проверки удваивает легшую запись, перезапись без diff стирает чужую.

| Что видно | Что это | Что делать |
|---|---|---|
| отказ по expectedSha самого файла | файл изменился после чтения | 1) свежий fetch и полное перечитывание; 2) построчный diff намеренного с текущим; 3) не пересекаются построчно — собрать заново поверх актуальной версии, записать с новым sha; 4) пересекаются — стоп, вопрос человеку |
| «Repository rule violations found / Timed out validating rule» | временный таймаут правил GitHub, файл не тронут | сверить в ответе sha_before = sha_after и bytes_before = bytes_after; повторить тот же вызов без правки |
| «PUT rejected by GitHub: is at <sha> but expected <sha>», пустой bytesAfter | две записи одной сессии запущены одновременно | 1) дождаться результата другой записи; 2) проверить по «Доказательству записи», что файл не изменился; 3) повторить тот же вызов один раз; файл изменился — повтор отобьётся по expectedSha, тогда первая строка таблицы |
| отбит parent_check у Git Commit Files | чужой коммит сдвинул голову main | «Параллельные сессии» |
| Git Append ответил успехом | не доказательство | сверка байт с origin/main; повтор — только если записи нет |
| две строки-заголовка с одним номером | параллельная сессия заняла номер | перенумеровать свою запись Git Replace строки-заголовка |

Чтения (Git Read, Git Read Batch, Git Read Lines) запускаются параллельно без ограничения.

### Git Commit Files
`{branch, message, expectedSha (sha HEAD), files[], deletes[]}`. Через MCP `execute_workflow` в режиме manual заголовок Authorization не требуется, гейт parent_check работает; заголовок нужен прямому HTTP-вызову. Чем «вебхук защищён» отличается от «воркфлоу защищён» — Skill `n8n-engineering-manual`, раздел «Доказательство и состояние».

### Параллельные сессии
1. Два наряда или два чата, работающие одновременно, называют непересекающиеся наборы путей repo в поле РАМКА своих нарядов.
2. Гонка за голову ветки: чужой коммит в любой путь отбивает Git Commit Files на parent_check. Если чужая сессия двигает голову чаще, чем длится оборот инструмента, — Git Write пофайлово (expectedSha — blob sha файла); кроме пары «файл и список, в котором он назван» — там ждать освобождения ветки.
3. Столкновение номеров в общем реестре или журнале: номер — свежим чтением непосредственно перед записью, пересчёт после (раздел «Чем писать»).
4. Запись в папку соседнего проекта, чья сессия работает одновременно, — путь называется в РАМКЕ.

### Граница Канала

| Воркфлоу | Чего не делает | Следствие |
|---|---|---|
| Git Write | не удаляет | удаление — Git Commit Files |
| Git Read | не перечисляет каталог | файл-список внутри папки |
| Git Append | не проверяет номера; может ответить успехом, не записав | номер — по «Чем писать»; дозапись закрывается сверкой байт |
| Git Append File | не создаёт новый файл: путь, которого нет в main, роняет исполнение, ничего не записано | новый файл — Git Write со строкой пути, затем Git Append File |
| Git Write, Git Commit Files | не перезаписывают и не удаляют существующий append-only файл (замок не снимается ни при каком payload) | ротация, возврат версии, удаление тестового файла с защищённым именем — маршрут (б) |

Запись Каналом исполняет сервер n8n прямо в main, по HTTP или через MCP: граница push на Канал не распространяется. Встреченная и не записанная граница Канала пополняет этот раздел тем же действием, что встреча: текстом «было → стало» владельцу и позицией в Очереди.

### Push: проверка и открытие
1. До выбора маршрута — `git push --dry-run` в самой сессии.
2. Отказ «… is not in this session's authorized repository set» (clone и fetch открыты) — push закрыт.
3. Если среди инструментов сессии есть добавление репозитория (в облачной сессии Claude Code — `add_repo` с доступом push): добавить lyamin-dot/second-brain-canon с доступом на запись, повторить `git push --dry-run`.
4. Такого инструмента нет (отказ прокси — это отсутствие инструмента) — push открывается только новой сессией на этом репозитории.
5. Повторный отказ после добавления — обход не искать: маршрут (б) в этой сессии неисполним.

### Маршрут доставки в main
Единица доставки — состояние main на origin. Маршрут — по одному вопросу: набирает ли модель текст записи.

(а) Фрагмент (Git Replace) или одна запись (Git Append File, запасной путь — Git Append), текст — продукт сессии → Каналом. Маршрут по умолчанию в любой среде.

(б) Файл из уже существующего текста, массовая механическая работа (нарезка, пересборка, перенос большого тела) → скрипт в среде, где прошёл `git push --dry-run`:
1. собирает файлы из объектов git;
2. сверяет их blob sha с эталоном, посчитанным до коммита и зашитым в скрипт; несовпадение — стоп без коммита;
3. коммитит в ветку claude/* и переводит main перемоткой, без merge-коммита и PR; ветку пришлось перебазировать на свежий main — `git push --force-with-lease=<ветка>:<прежний sha>`.
Приёмка механического переноса — по мультимножеству непустых строк: скрипт сравнивает счётчики строк исходника и результата, пустой остаток в обе стороны — принято.
Опись файлов Drive или PDF — тоже скриптом (Skill `google-drive-docs`, разделы «Опись и отбор файлов Drive» и «Пути чтения»).

(в) Ни (а), ни (б) недоступны → остановиться и назвать операцию. Удалить или переписать крупный существующий фрагмент (Git Replace требует набрать его моделью):
1. дождаться среды с открытым push и сделать маршрутом (б); или
2. владелец правит файл сам в веб-редакторе GitHub: сессия отдаёт путь, точные границы фрагмента (первая и последняя строка дословно) и что останется на месте, затем принимает правку чтением файла.

Запись легла не в main — слияние подшаг того же действия; не покрыто Каналом — назвать и остановить шаг. Ветка claude/*, не переведённая в main той же сессией или ближайшим нарядом, — незакрытая доставка: отчёт и позиция Очереди.

Удаление ветки claude/*, на коммит которой ссылается журнал или канон: сначала тег — `git tag <имя> <sha> && git push origin refs/tags/<имя>` в среде с открытым push; само удаление — по слову Андрея.

### Утверждение об истории репозитория
Утверждение «чего в истории не было», «когда и чем удалена запись», «была ли перезапись ветки», «файл никогда не превышал N» пишется в файл repo только вместе с двумя величинами той же сессии: `git rev-parse --is-shallow-repository` = false и `git rev-list --count origin/main`.

- требует правки Skill или мастер-промпта — позиция в Очереди через Git Append File (запасной путь — Git Append) с датой смерти.

### Статус позиции Очереди
Статус начинается одним словом закрытого словаря; всё прочее — после точки с запятой.

| Слово | Когда | После слова |
|---|---|---|
| ОТКРЫТА | позиция заведена, текст правки владельцу ещё не выдан | — |
| ЖДЁТ | текст выдан или работа сделана, ждёт действия владельца (заливки, решения, вставки в промпт) или харвеста | чего именно |
| ВНЕСЕНО | правка стоит в целевом носителе и проверена по объекту | дата и адрес |
| СНЯТА | не вносится | дата и причина |
| ДУБЛЬ | содержание уже живёт в носителе, в другой открытой позиции или задаче лаборатории | адрес |

Форма: «ВНЕСЕНО 2026-10-13 — <адрес>; отложено 2026-10-10 до пакета Архивариуса». При смене статуса новое слово с датой встаёт в начало, прежний текст уходит после точки с запятой и не стирается. Других первых слов нет («ждёт» строчными, «отложено», «частично», «ЗАКРЫТО», «ВЫПОЛНЕНО», «СНЯТ» — нарушение формы).
1. ВНЕСЕНО, СНЯТА, ДУБЛЬ — когда каждая часть позиции (каждая правка, носитель, находка перечня) проверена по объекту, а не поиском одной формы старого адреса. Непокрытая часть тем же действием получает свою позицию, либо позиция остаётся открытой словом остатка, остаток назван после слова.
2. Снятие позиции: позиции, ссылающиеся на неё словом ДУБЛЬ, тем же действием получают статус заново.

### Форма записи в журнал
```
Р-NN | В СИЛЕ | дата | вопрос
  принято: …    почему: …    кто подтвердил: …          ← обязательны
  отвергнуто: …    обратимость: …    допущение: …        ← по наличию

Т-NN | дата | что пробовали
  почему не вышло: …    условие возврата: …             ← обязательны
  стоимость попытки: …                                  ← по наличию
```
1. Статус впереди текста. Смена статуса прежней записи — одной правкой Git Replace строки-заголовка, форм две: «ОТМЕНЕНО Р-NN» — новая запись отменяет прежнюю целиком; «ЧАСТИЧНО ОТМЕНЕНО Р-NN (пункт X)» — заменены названные пункты (как пронумерованы в прежней записи), остальные в силе.
2. Поправка полем внутри записи («поправка <дата>: …») — только если уточняет текст и не отменяет ни одного пункта, внесена тем же днём и до того, как запись прочла другая сессия; иначе — отдельная запись со ссылкой.
3. Условие возврата у тупика обязательно; любое условие из прошлого (запись журнала, снимок памяти чата, слова владельца по памяти, обещание в шапке документа) перед исполнением перепроверяется по объекту и журналу; общее правило — Skill `second-brain-engineer`, раздел «Р15. Провенанс и верификация — единый стандарт».
4. Поле «кто подтвердил» без слова владельца: «не зафиксировано в источнике — самопроверка Клода» — когда решение принято сессией (или перенесено из источника без подтверждения); заглушкой не считается.
5. Вывод сессии — только назван выводом и проверяем внутри записи (арифметика, цитата, два известных факта).
6. «отвергнуто: …» называет вариант и причину отказа.

### Блок хроники
Единственное исключение из запрета ретроспективы: разбор вывозит закрытое из STATE.md, PLAN.md или `meta/*` в LOG.md.
```
Хроника | дата разбора | перенесено из <путь> разбором по роли — не свидетельство этой сессии
  <перенесённые строки без изменения смысла, каждая со своей датой>
```
Номера Р или Т нет, в оглавление журнала блок не попадает. Строки переносятся из источника, не пересказываются; уже живущее в записи журнала не переносится — в источнике заменяется указателем на запись.

### Лаборатория
Лаборатория — `labs/<имя>/`: множество независимых задач без общего финиша. Различение одним признаком:

| Признак | Сущность | Роли файлов |
|---|---|---|
| финиш назван; достигнут — папка закрывается | проект-летопись, `projects/<имя>/` | четыре роли («Роли файлов проекта») |
| финиша нет; задачи друг в друга не переходят | лаборатория, `labs/<имя>/` | две роли (ниже) |

1. Имя папки — по «Именам и ссылкам», из того, как объект называет владелец, а не из имени файла-артефакта.
2. Роли — две:

| Роль | Содержание | Предел | Читатель и момент |
|---|---|---|---|
| INDEX.md | список живых задач: имя файла, одна строка сути, метка приоритета, возраст; у задачи с эстафетой — пометка «активная эстафета «<метка>»» (Skill `context-handoff`, раздел «Границы»); тел задач нет | одна строка на задачу | старт каждой сессии лаборатории, до выбора задачи |
| t-<имя>.md, по файлу на задачу | тело задачи: суть, следующий шаг или предложение, условие снятия, ссылки | не в байтах: задача — единица смысла | сессия, выбравшая задачу по INDEX.md |

3. INDEX.md — файл-список папки: состав для читателя без клона существует только в нём.
4. Создание и закрытие задачи — один Git Commit Files с файлом задачи и правкой INDEX.md; новый текст INDEX.md — вычёркиванием или вставкой строки в текст, прочитанный в этой сессии, приёмка — по «Вычёркиванию из наличного текста»: diff нового INDEX.md против прочитанного показывает ровно одну вставленную или вычеркнутую строку.
5. Закрытие — удаление файла задачи и её строки в INDEX.md; снятое читается из истории по ref родителя коммита удаления.
6. Перед закрытием — поиск пути задачи по всему клону: `git fetch && grep -rnF '<путь задачи>' <клон> /mnt/skills/plugins` (без клона — Git Read Lines по известным читателям, невыполненный поиск — в отчёт). Ссылка на путь в строке основания Skill, отчёте синтеза или харвеста (включая карты `_reports/`) или файле кейсов — текст задачи переносится скриптом без изменений, кроме строки-пути, в постоянный файл (`meta/CASES_<тема>.md` или файл проекта) с прежней нумерацией строк, в конец файла — строка о происхождении (путь закрытой задачи); ссылки в истории (пункт 4 «Сдвига адреса») не правятся — номера строк в них остаются верными по постоянному файлу; остальные ссылки на прежний путь переадресуются по «Сдвигу адреса» тем же коммитом, что закрытие.
7. Задача, в чьём файле появились фазы, общий следующий шаг или названный финиш, разворачивается в проект по «Новому проекту»; цель — то, ради чего она росла; признак — по тексту файла, не по размеру. Файл, переросший разумный размер, разбирается тем же вопросом — по существу, не по весу.
8. Старение: возраст = дата чтения минус дата последнего коммита, тронувшего файл задачи; не тронутая больше 30 суток — пометка «лежалая» в INDEX.md; читатель — сессия лаборатории на старте, до выбора задачи.

| Среда | Инструмент | Как |
|---|---|---|
| с клоном | `git log -1 --format=%cI -- <путь>` | один вызов на всю папку через `git log --name-only` |
| без клона | Git Log | только с limit, равным необходимому |

9. Новая лаборатория — строка в `registry/projects.md`, раздел «Лаборатории» (лаборатория | папка | носитель | статус) — тем же коммитом, что создание INDEX.md. Закрытие — смена статуса, не удаление.

## Адреса и ловушки
- Адреса Канала (ID воркфлоу, сигнатуры, ID папки `_git_staging`) — в реестре `registry/tools.md`; ID документов — `registry/documents.md`.
- Имя узла-триггера у всех воркфлоу Канала — `01_Webhook`; терминальный узел ответа читающих — `05_Respond` (у другого воркфлоу — свой узел Respond).
- Git Append молча отвечает успехом, не записав ничего — проверяй сверкой байт файла до и после с origin/main.
- Серия Git Append ради одной записи молча вставляет пустые строки внутрь тела записи — одна запись одним вызовом.
- Обратная косая черта в тексте молча искажается на любом слое, раскрывающем экранирование (оболочка, литерал скрипта, параметр `execute_workflow`): «\v» ложится управляющим символом, у кавычки лишняя косая, косая удваивается, образец регулярного выражения перестаёт находиться — проверяй перечитыванием записанных байтов.
- Запись целиком через Git Commit Files молча удваивает обратную косую черту в строках, которых правка не касалась, — проверяй diff против прочитанного.
- grep без настроенной локали: точка в шаблоне на месте русской буквы и класс `[РТ]` молча находят 0 строк — проверяй чередованием `(Р|Т)`.
- Харнесс обрезает вывод между инструментом и моделью без ошибки — проверяй `byteLength` и признаки обрыва.
- `nodeNames` не режет сырой ответ GitHub в `contextData` грязных воркфлоу — проверяй тип узла загрузки (таблица «Сужение и грязные воркфлоу»).
- Клон с ограниченной глубиной показывает самый старый скачанный коммит корнем без предков и молча скрывает старшую историю — проверяй `git rev-parse --is-shallow-repository`.
- «PUT rejected by GitHub: is at … but expected …» — не конфликт версий файла, а две одновременные записи одной сессии — проверяй, не шла ли параллельно другая запись.
- «Repository rule violations found / Timed out validating rule» — не конфликт версий, файл не тронут — проверяй sha и bytes до и после в ответе.
- Коммит в ветке claude/* другим сессиям и Каналу не виден, а проверки внутри сессии (клон, `git log`, blob sha) смотрят на её ветку и показывают успех — проверяй чтением Каналом из main.
- Коммит удалённой ветки без ветки и тега со временем удаляется сборкой мусора, ссылка журнала ведёт в пустоту — ставь тег до удаления.
- GitHub Contents API не отдаёт содержимое файла больше 1 МБ — такой файл Канал не прочитает.
- `search_workflows` ищет только по имени и описанию, а `registry/n8n-map.md` — снимок, где узел, берущий ID документа из выражения или входа, не виден — проверяй `get_workflow_details` кандидатов.
- Перевод строки внутри текста позиции Очереди молча разрывает строку таблицы: «Дата смерти» и «Статус» уезжают на другую физическую строку, харвест видит позицию без даты смерти — проверяй, что позиция — одна физическая строка.
- После перенумерации старый номер обычно существует и принадлежит другому пункту — ссылка ведёт не туда, оставаясь целой; проверяй смысл пункта по ссылке, а не её целость.

## Куда писать результат
- Результат записи — в main на origin; доказательство — по «Доказательству записи», в отчёте названы sha.
- Незакрытая доставка, не исполненный в среде шаг (зеркало, поиск копий, ротация, разрез) — в отчёте и позицией в `registry/maintenance-queue.md`.
- Правка Skill или мастер-промпта — текстом «было → стало» владельцу и позицией в Очереди.
- Факт соседнему проекту — STATE.md соседа, раздел «От соседнего проекта».
