КОНТРАКТ РАБОТЫ С КАНОНОМ В GIT

Редакция 2026-10-19.

Действует для любого файла репозитория lyamin-dot/second-brain-canon, ветка main. При расхождении с second-brain-engineer по вопросу о файле в repo приоритет у этого контракта: second-brain-engineer отвечает, что делать, когда и с чьего согласия, этот контракт — как физически прочитать и записать файл репозитория.

Как устроен этот текст. Он держит правило и число, а не рассказ о том, как правило добывалось. У каждого правила четыре элемента: что делать и когда; почему — механизм одной-двумя фразами; признак, если ситуация неочевидна; основание — число независимых случаев, дата последнего и адрес каждого случая. Сам случай — замеры, номера исполнений n8n, номера нарядов, что подумали сначала и как оказалось — живёт по адресу (запись журнала, позиция Очереди, файл задачи), а не здесь. Шапка — одна строка редакции; что и почему менялось, отвечают история коммитов зеркала skills/second-brain-git/ и журналы из строк основания. Опровергнутая версия, к которой сессия вернётся сама, остаётся одной строкой «Не путать: …». Правка этого Skill готовится по meta/PROTOCOL_knowledge-synthesis.md: урок не дописывается абзацем, а кластер, в который он входит, переписывается заново как правило. Состав Канала, ID воркфлоу и сигнатуры живут в registry/tools.md. Дубль запрещён, поэтому правило выбора инструмента существует ровно в двух местах — таблица 7.6 этого файла для чтения и таблица 8.3 файла references/write.md для записи.

Как устроен Skill. Этот файл читается всегда. Остальное лежит в папке references/ рядом с ним и читается один раз за сессию — перед первым действием своего вида, целиком, по таблице ниже. Номера пунктов общие для всех файлов Skill: ссылка «second-brain-git 8.3» означает пункт 8.3, где бы он ни лежал (8.3 — в references/write.md). Действие, для которого нужный файл не прочитан, — то же нарушение, что действие без этого Skill: правила этого действия лежат только в своём файле, а здесь от них остались одни указатели. Признак нарушения — в сессии сделано действие из левой колонки таблицы, а файл из средней колонки в этой сессии не открывался. Основание — решения Р-7 и Р-12 журнала projects/kontext-reduktion/LOG.md (обязательная часть и справка, нарезка скриптом с сохранением номеров).

Что где лежит. В этом файле — только то, что нужно любой сессии в момент чтения, какую бы операцию с репозиторием она ни делала. Новый пункт по умолчанию идёт в references/; в этот файл он попадает, только если без него ошибётся сессия, которая references/ не открывала. Основание — решения Р-3, Р-12, Р-18, Р-19, Р-22, Р-29 журнала projects/kontext-reduktion/LOG.md.

0. Термины

Канал — воркфлоу n8n, исполняющие операции с репозиторием по HTTP: Git Read, Git Read Batch, Git Read Lines, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files, Git Log. Состав, ID и сигнатуры — registry/tools.md.

Вызов Канала без реестра. Если реестр недоступен или ID ещё не известен — путь в обход: найти воркфлоу по имени через n8n:search_workflows, подтвердить ID и сигнатуру через get_workflow_details до первого вызова. Почему: иначе замкнутый круг — файл со списком инструментов сам требует инструмент для чтения.

Режим вызова. execute_workflow вызывается только в режиме manual, и executionMode: "manual" указывается в каждом вызове явно. Почему: режим production не регистрирует исполнение, и результат через get_execution не забрать, а сам инструмент по умолчанию ставит production. Механизм — Skill n8n-engineering-manual, корень R4.

Форма вызова execute_workflow для воркфлоу Канала: параметр triggerNodeName — имя узла-триггера, у всех воркфлоу Канала это 01_Webhook; параметр inputs — {webhookData: {method: "POST", body: {…вход воркфлоу…}}}, без поля type. Пример для Git Read Batch: workflowId из registry/tools.md, executionMode "manual", triggerNodeName "01_Webhook", inputs {webhookData: {method: "POST", body: {paths: ["core/MANIFEST.md"]}}}. Почему форма повторена здесь, хотя она свойство сервера n8n MCP и её дом — Skill n8n-engineering-manual: вызов Канала по готовой сигнатуре Skill n8n-engineering-manual читать не требует (так сказано в его описании), и сессия вызывает Канал, не открывая его. Признак старой формы: inputs {type: "webhook", webhookData: …} сервер отвергает ошибкой «Unrecognized key(s) in object: 'type'», вызов без triggerNodeName — ошибкой «Provide triggerNodeName when passing inputs». Описание инструмента в клиенте Claude может показывать старую схему с type (так было 2026-10-08) — верить ошибке сервера, а не описанию. Основание формы: 1 случай, 2026-10-08 — позиция AH-26 очереди registry/maintenance-queue.md. Основание имени триггера 01_Webhook: 2 проверки, последняя 2026-10-09 — registry/tools.md, абзац «Аутентификация вебхуков» (2026-09-18); живой вызов Git Read Batch 2026-10-09 — meta/SYNTHESIS_second-brain-git_2026-10-19.md, раздел «Случаи без адреса».

Git Grep в Канал не входит и не вызывается ни для какой задачи, хотя строка этого воркфлоу ещё стоит в registry/tools.md (на инстансе он архивирован — снимок registry/n8n-map.md). Почему: в contextData его исполнения лежит base64 всего файла, и сужение nodeNames этого не режет, поэтому поиск через него дороже чтения файла целиком. Его работу делает Git Read Lines с входом pattern (7.6). Основание — запись Р-21 журнала projects/kontext-reduktion/LOG.md, запись Р-2 файла meta/CONTRACT_file-limits.md.

Blob sha — контрольная сумма содержимого файла, вычисляемая git; возвращается Каналом на чтение и запись; воспроизводится локально командой git hash-object. expectedSha — blob sha (для Git Write, Git Replace) или sha коммита HEAD (для Git Commit Files), который вызывающий считает текущим; несовпадение — отказ сервера, ничего не записано.

Манифест — core/MANIFEST.md, файл-список состава core/. Роль файла — одно из фиксированных имён, заданных для сущности проекта: летопись — 4, лаборатория — 4б. Провенанс-маркер — первая строка вида <!-- T-NN | CORE байт X-Y | … --> в файле, перенесённом из CORE. Очередь — registry/maintenance-queue.md, реестр правок, которые сессия сделать не может.

Среда с клоном — сессия, где есть bash и сеть на github.com. Репозиторий публичный, поэтому клон доступен анонимно и никаких учётных данных не требует. Среда без клона — это ровно среда без bash (Claude Project), а не среда без прав на репозиторий. Различение важно: половина правил 7.6 и 8.3 ветвится по нему.

1. Инварианты

И-1. Документ имеет ровно один канонический носитель: Docs или repo. Второго носителя ЗАПРЕЩЕНО.

И-2. Запись считается выполненной только после независимого перечитывания записанного и совпадения blob sha с намеренным содержимым. Ответ инструмента доказательством не является; серия успешных ответов — тоже (8.1). Почему: воркфлоу может ответить успехом, не записав ничего. Как перечитывать — 8.1 (references/write.md). Тот же стандарт для Docs — second-brain-engineer, раздел Р15. Основание: Git Append ответил success и не изменил файл — тупик Т-69 журнала projects/git-migration/LOG_ARCHIVE.md (2026-09-13).

И-3. Правило, описывающее возможность транспорта, пишется после зонда транспорта, не до.

И-4. Операция, не покрытая Каналом, называется и останавливает шаг; исполнение в обход Канала ЗАПРЕЩЕНО. Что Канал не делает и куда тогда идти — 9.3 и 9.4 (references/delivery.md).

И-5. Число (бюджет, порог, множитель) в этом контракте существует только вместе с названным читателем и датой снятия. Число без них — не норма, а слух. Пример числа, которое ограничивало не того: потолок записи LOG.md 16 384 Б ограничивал не цену читателя, а частоту служебной операции, и был отменён 2026-09-17 — запись Р-99 журнала projects/git-migration/LOG_ARCHIVE.md.

И-6. Первым действием любой repo-сессии читается meta/PENDING_RULES.md (бюджет чтения 2 048 Б; читатель — старт каждой repo-сессии; предела размера у файла нет — 4.5). Строка с полем «кто подтвердил: Андрей» действует как положение этого контракта до внесения в Skill; при расхождении со Skill приоритет у строки. Почему: решение журнала входит в Skill только после правки и заливки владельцем, и до того сессии работали бы по старому тексту; файл — мост от решения к Skill. Файл append-only, пишется через Git Append только по решению журнала, подтверждённому владельцем в чате; вычищается владельцем при правке Skill. Как исполняется старт в целом (строка «Контекст загружен», молчание) — second-brain-engineer, раздел Р1. Основание — запись Р-62 журнала projects/git-migration/LOG_ARCHIVE.md (мост решение → Skill).

И-7. Репозиторий публичный, и запись в него необратима: коммит остаётся в истории навсегда. Правка или удаление файла убирают текст только из текущей версии — из истории коммитов он не уходит, его по-прежнему прочитает любой, кто откроет историю файла или старый коммит. Поэтому «потом исправим» защитой не является, а вопрос «можно ли это записать» задаётся до записи — по классу данных, а не по списку случаев, которые уже утекли. В repo не пишутся четыре класса:
1. Секреты и их признаки — всё, что облегчает доступ к инстансу n8n, серверу или аккаунтам владельца: пути вебхуков n8n; признаки их аутентификации, в том числе утверждение, что у конкретного входа авторизации нет; имена и номера ключей доступа (credentials); адреса сервисных аккаунтов; токены, пароли, ключи API.
2. Личные данные — владельца и любых других людей: адреса почты, номера телефонов, банковские реквизиты, номера документов, PIN-коды и номера бронирований, домашние адреса, имена и пути личных папок на дисках владельца.
3. Чужие охраняемые тексты: тексты и оглавления статей, книг и руководств, выдержки из платных баз. В repo идут название, автор и ссылка, не сам текст.
4. Код книг Google Sheets (проекты Apps Script). Где хранить его копию — предложение проекта sku-cost (закрытый репозиторий), ждёт решения Андрея: projects/sku-cost/STATE.md, раздел «Ждёт Андрея», пункт 3; в этот репозиторий код не кладётся в любом случае.

Материал этих классов, который всё же нужно хранить, лежит на Google Диске владельца или в закрытом носителе; в repo пишется только то, где он лежит, без самого значения.

Нарушение, найденное в текущей версии файла, снимается правкой тем же действием, что и находка, и называется в отчёте вместе с тем, что история коммитов его по-прежнему хранит; закрыть историю может только перевод репозитория в приватный — вопрос владельцу, задача labs/sys/t-private-repo.md.

Воркфлоу, публикующий в repo данные с инстанса автоматически, держит защиту в своём коде до записи: строка, содержащая «/webhook/», «http:» или «https:», «Bearer» или «@», роняет прогон, и в repo ничего не уходит; идентификаторы он извлекает только из ключей по белому списку, а не регулярным выражением по всему тексту. Образец — воркфлоу снимка registry/n8n-map.md (раздел 5 файла projects/n8n-map/PLAN.md; записи Р-1, Р-4, Р-6…Р-8 журнала projects/n8n-map/LOG.md). Такая же защита для воркфлоу записи Канала — задача labs/sys/t-git-channel-secret-filter.md; до её постройки класс проверяет сама сессия перед каждым пишущим вызовом.

Основание: 5 независимых случаев за десять дней в разных классах, последний 2026-10-16, и одно предложение 2026-10-18:
- пути личных папок и чужие тексты статей в выгрузках, предложенных к записи, пойманы до записи — тупик Т-5 журнала projects/archive-recon/LOG.md (2026-10-10);
- личные данные в данных артефакта поиска (артефакт, не repo, но тот же класс) — запись Р-31 того же журнала (2026-10-13);
- адрес сервисного аккаунта в projects/archive-recon/SERVER_TASKS.en.md — коммит 8f6d3bd (2026-10-13);
- адрес почты владельца в public/privacy-rclone.md — коммит f3b62c2 (2026-10-16);
- имя и номер ключа доступа с признаком аутентификации вебхука — labs/sys/t-webhook-key-reuse.md (2026-10-16);
- код книг — предложение проекта sku-cost, projects/sku-cost/STATE.md (2026-10-18).
Решение о перечне классов — А3 файла meta/HARVEST_2026-10-18_answers.md.

3.1. Адрес проекта — папка. Ничто из проекта не лежит снаружи.

3.2. Каталог Каналом не перечисляется: Git Read отдаёт файл по имени, на папку — отказ. Состав папки, обязательной к полному чтению, задаётся файлом-списком внутри неё; список правится тем же действием, что и состав. В среде с клоном каталог перечисляется клоном, и это не отменяет файл-список: список читает тот, у кого клона нет.

3.3. Ссылка «CORE Р.N» при более чем одном файле раздела разрешается через meta/MAP_core-sections.md; раздел без записи в карте = один файл core/R-NN.md.

| PLAN.md | цель, инварианты, архитектура, фазы, риски ЭТОГО проекта | 10 240 Б | сессия, берущаяся за проект, целиком |
| LOG.md | решения, тупики, ошибки; только дописывается | 16 384 Б на прочитанное, не на файл | та же сессия, рядом с PLAN: оглавление журнала одним вызовом по 7.6 (строка «оглавление журнала»), затем целиком только нужные записи — названные в STATE.md или PLAN.md либо выбранные по оглавлению (строка «запись журнала по номеру»). Файл целиком не читается (Р-10, Р-11 журнала projects/kontext-reduktion/LOG.md) |
| NOT_TAKEN.md | что не взято при переносе из Docs, адрес восстановления | нет | по вопросу «где это было» |

Колонка называется бюджетом чтения, а не потолком, потому что числа в ней ограничивают читателя, а не файл. Предела размера у файла летописи нет: он не выводится ни из транспорта, ни из читателя. Потолка записи для LOG.md тоже нет — он отменён (И-5, основание там же). Протокол замера пределов — meta/CONTRACT_file-limits.md.

4.1. Пятой роли по умолчанию не существует. Раздел, не ложащийся ни в одну, — стоп и вопрос владельцу. Владелец может разрешить проекту дополнительные роли по 4.6; без такого разрешения роль не заводится.

4.2. Правило разбора: состояние → STATE, правила → PLAN, опыт → LOG.

4.3. Вопрос разбора для любого материала: «это правило про ЭТОТ проект или про любой?» Про любой — meta/; реестр ID — registry/; про этот — PLAN.md. Дубль того, что уже живёт в LOG или Skill, в repo не едет — строка в NOT_TAKEN.md с адресом.

4.4. LOG.md заводится первой квалифицирующей записью, не заранее. NOT_TAKEN.md — только при переносе из Docs.

4.5. Бюджет чтения и правило происхождения текста.

Бюджет чтения относится к читателю и моменту, а не к файлу: читатель платит за сумму того, что читает, и ему безразлично, на сколько файлов она разложена. Он платит и за транспорт: одна и та же сумма байт приходит в контекст в разном объёме в зависимости от того, чем её читают (7.6).

Числа бюджетов старта, снятые с объекта, и порядок их опровержения — references/costs.md. Правило происхождения текста (что можно, а что нельзя набирать моделью при записи) — references/write.md, пункт 4.5.

4б. Лаборатория — папка labs/<имя>/ с темой без финиша; роли её файлов, атомарность, закрытие и старение задач — references/lab.md. Читать перед любой работой с папкой labs/.

5. Превышение бюджета чтения

Превышение бюджета чтения — не отказ и не блок. Разбор по роли (5.1) и переливной клапан для STATE.md, PLAN.md, meta/* (5.5) — references/write.md. Ротация журнала (5.2–5.4) — references/rotation.md. Разрез core/ (6) — references/core-split.md.

7. Чтение

7.1. Контракт ответа читающих воркфлоу. Прежде чем прочитать что-либо, открой 7.6 и выбери транспорт по таблице. Этот пункт задаёт только контракт ответа и не отвечает на вопрос «чем читать».

Git Read {path, ref?} → {text, sha, byteLength}. Поле byteLength воркфлоу считает из тех же декодированных байт, из которых получен text (узел 04_Build_Response, Buffer.from(base64).length). Поэтому:
- против порчи ВНУТРИ воркфлоу сверка byteLength с text ничего не доказывает — она сравнивает файл сам с собой, и для этой цели не выполняется; признак порчи при декодировании, который сессия может увидеть сама, — символ замены U+FFFD в text;
- против обрезания НА ПУТИ от инструмента к модели byteLength — как раз нужная мерка: его сообщил сервер, а увиденный текст видит сама модель; явно меньший текст при большом byteLength — обрезанный вывод по 7.7.
То же верно для каждого файла ответа Git Read Batch.

Git Read Batch {paths[]} → {requested, returned, files[], missing[]}: returned < requested или непустой missing — чтение набора не состоялось, стоп.

Полные сигнатуры, включая режимы Git Read Lines, — registry/tools.md.

Не путать: «сверка byteLength бесполезна вообще» — так считалось с 2026-09-24 (запись Р-5 журнала projects/kontext-reduktion/LOG.md); на деле она бесполезна только против порчи внутри воркфлоу, а против обрезания вывода нужна. Основание сужения: 1 случай, 2026-10-08 — позиция AH-28 очереди registry/maintenance-queue.md; задача labs/sys/t-truncated-read.md в коммите 065370f (из рабочего дерева удалена коммитом a832aac).

7.2. «CORE прочитан целиком» = прочитаны все файлы таблицы «Список» Манифеста. meta/header.md на старте не читается — оба его поля недействующие (запись Р-3 журнала projects/kontext-reduktion/LOG.md). Признак в отчёте — три величины: число прочитанных файлов таблицы, путь последнего файла таблицы, его blob sha. Две первые списываются с самого Манифеста и без третьей ничего не доказывают. Таблица «По событию» в чтение на старте и в признак не входит: файлы её строки читаются одним вызовом в той сессии, где событие наступило, до первой записи этого вида (запись Р-111 журнала projects/git-migration/LOG.md): Git Read — если в строке один файл, Git Read Batch — если несколько, `cat` — в среде с клоном. Размеров Манифест не хранит: размер приходит в ответе Канала.

7.3. Пароль-канарейка, FNV и счётчики к файлам repo не применяются и основанием для отказа не являются: у набора файлов нет конца, на котором держалась канарейка. Контракт чтения задаётся носителем объекта: Docs — канарейка и FNV по gdocs-read; repo — Манифест и blob sha.

7.4. Чтение STATE.md на старте repo-сессии — без записи: полей LAST_READ у repo-файлов нет, актуальность даёт git log. Почему: поля LAST_UPDATED и LAST_READ — механика носителя Google Docs, и при переносе в repo они сняты вместе с ним (запись Р-71 журнала projects/git-migration/LOG_ARCHIVE.md).

7.5. Утверждение об истории репозитория пишется в файл только с двумя величинами той же сессии — references/write.md, пункт 7.5.

7.6. ЧЕМ ЧИТАТЬ. Это правило, а не совет, и оно измерено. Выбор транспорта делается до первого чтения в сессии, по таблице, и никаким иным способом. Почему: цена чтения задаётся не файлом, а транспортом и способом чтения — одна и та же сумма байт приходит в контекст в разном объёме (4.5).

| Что нужно | Среда с клоном | Среда без клона |
|---|---|---|
| файл целиком | `git fetch && cat` | Git Read; набор путей — Git Read Batch |
| запись или фрагмент, номер строки НЕизвестен | `git fetch && grep` | **Git Read Lines с входом pattern, один вызов** |
| фрагмент, номер строки известен | `git fetch && sed -n` | Git Read Lines без pattern |
| история коммитов, дата последней правки | `git log` | Git Log, минимальный limit (грязный, см. ниже; цена — references/costs.md) |
| перечислить каталог | `git ls-files` | не покрыто Каналом: файл-список внутри папки (3.2) |
| blob sha для сверки | `git hash-object` | sha из ответа любого читающего воркфлоу |
| оглавление журнала LOG.md | `git fetch && grep -nE` с шаблоном оглавления (ниже) | Git Read Lines, pattern = шаблон оглавления, limit не меньше числа записей; если count больше числа возвращённых строк — повторить с limit = count |
| запись журнала по номеру | `git fetch && grep -nA10` с шаблоном записи (ниже) | Git Read Lines, pattern = шаблон записи, after = 10; если последняя возвращённая строка — поле записи (начинается с двух пробелов), дочитать строки с to+1 без pattern |
| дочитать файл после обрезанного вывода (7.7) | `sed -n '<N>,$p'` с первой непрочитанной строки | Git Read Lines без pattern, from = первая непрочитанная строка; при риске нового обрыва — кусками с явным to |

Шаблоны. Строка-заголовок записи обязательна по форме 11, поэтому оглавление не ведётся отдельно — оно выводится из файла в момент чтения. Шаблоны стоят вне таблицы: знак | внутри ячейки ломает таблицу (запись Р-11 журнала projects/kontext-reduktion/LOG.md). Шаблон зависит от того, где он набирается:
- Вход Git Read Lines (вызов Канала): оглавление журнала — `^.-[0-9]+ \|` (точка заменяет букву Р или Т), запись по номеру — `^.-111 \|` с номером нужной записи. Русские буквы в шаблоне вызова Канала не набираются: харнесс превращает их в последовательности \uXXXX, и вызов дорожает в несколько раз (пункт 8.2 файла references/write.md). Во входе Git Read Lines, который передаётся как JSON, обратная косая черта удваивается.
- Оболочка в среде с клоном (grep): прежние `^(Р|Т)-[0-9]+ \|` и `^Р-111 \|`. Почему не точка: точка в grep без настроенной локали занимает один байт, а русская буква два, и шаблон с точкой молча находит 0 строк. Буквы Р и Т в оболочке пишутся только чередованием `(Р|Т)`, не классом `[РТ]`: в среде без настроенной локали grep считает кириллическую букву двумя байтами, и класс молча находит 0 записей.
- Решения и тупики нумеруются двумя независимыми последовательностями (5.4), поэтому в журнале, где есть и Р, и Т с одним номером, шаблон записи по номеру с точкой возвращает обе строки (count = 2); нужная выбирается по первой букве строки в ответе.

Основание шаблонов: 3 проверки, последняя 2026-10-13 — projects/archivarius/TRIAGE.md, раздел «Стадия Б — Skill second-brain-git», подраздел «Пробы и проверки этой сессии», пункты 1–3 (запись Р-38 журнала projects/archivarius/LOG.md). Отказ класса `[РТ]`: 1 случай, 2026-09-24 — meta/SYNTHESIS_second-brain-git_2026-10-19.md, раздел «Случаи без адреса».

Две команды, обязательные при чтении через Канал.

**Сужать всегда.** Любое чтение через Канал сопровождается вызовом `get_execution(includeData:true, nodeNames:["05_Respond"])` — или как называется терминальный узел Respond у конкретного воркфлоу. Почему: без сужения результат приходит с каждого узла графа, через который прошли данные, и тело файла дублируется по числу узлов: та же операция стоит 3,38× вместо 1,0×. Основание — замер с номерами исполнений, записи Р-99 и Р-102 журнала projects/git-migration/LOG_ARCHIVE.md.

**У пишущих и у Git Log не звать includeData вовсе.** Шесть воркфлоу Канала тянут данные узлом `n8n-nodes-base.httpRequest`, у которого сырой ответ GitHub оседает в `executionData.contextData`, и сужение этого НЕ режет. Их статус берётся вызовом `get_execution(includeData:false)`; факт записи доказывается независимым чтением чистым воркфлоу либо клоном (8.1).

| Воркфлоу | Узел загрузки | contextData |
|---|---|---|
| Git Read, Git Read Batch, Git Read Lines | `n8n-nodes-base.github` | пуст всегда — ЧИСТЫЕ |
| Git Log, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files | `n8n-nodes-base.httpRequest` | сырой ответ GitHub, nodeNames не режет — ГРЯЗНЫЕ |

Во сколько раз ошибка обходится у грязного воркфлоу: сырой ответ оседает в contextData столько раз, сколько в воркфлоу узлов загрузки, — Git Log 1, Git Write 1, Git Replace 2, Git Append 3, Git Append File 4 (три к GitHub, один к Google Drive), Git Commit Files 6. Признак: вызов get_execution с includeData:true у Git Append приносит в контекст файл трижды вместо доказательства записи. Основание: карта узлов снята прямым чтением воркфлоу 2026-09-18 (registry/tools.md, раздел «Свойства канала целиком»); число узлов с credential по снимку registry/n8n-map.md 2026-09-26 с ней совпадает.

Свойство contextData принадлежит типу узла, а не назначению воркфлоу, и параметрами вызова не чинится — только сменой узла загрузки внутри воркфлоу; поэтому при заведении нового читающего воркфлоу узел выбирается по этому свойству, а не по удобству. Механизм и выбор узла — Skill n8n-engineering-manual, корень R4 (references/roots.md) и принцип «Узел выбирается по свойствам, а не по удобству».

Посредник (субагент, читающий вместо сессии) к файлам repo не применяется. Почему: таблица выше уже даёт ту же цену, а посредник добавляет к ней свой расход. Его ниша — ответ инструмента, который сузить нечем, например get_workflow_details; правило — second-brain-engineer, раздел Р21. Основание — записи Р-25 и Р-26 журнала projects/kontext-reduktion/LOG.md.

Цена транспортов, снятая с объекта, и способ её измерения — references/costs.md. Правило выше от неё не зависит: оно уже выбрано по этим числам.

Клон ДОПУСКАЕТСЯ как read-only подложка (9.1) и на достоверность не влияет: blob sha в клоне после git fetch совпадает с тем, что отдаёт Канал, — это свойство git, а не совпадение.

7.7. Обрезанный вывод означает «файл не прочитан». Почему: репозиторий отдаёт файл целиком; обрезать вывод может предел инструмента или клиента между инструментом и моделью.

Признаки обрыва:
- пометка харнесса об обрезке или о сохранении вывода в файл;
- текст кончается посреди строки или раздела;
- увиденный текст явно меньше byteLength (7.1);
- у Git Read Lines to меньше totalLines при запросе до конца файла.

Увидев обрыв, сессия дочитывает файл по строкам с места обрыва (строка «дочитать файл после обрезанного вывода» таблицы 7.6) до того, как действовать. Работать по частично прочитанному STATE.md или PLAN.md ЗАПРЕЩЕНО: следующий шаг, открытые вопросы и запреты лежат как раз в непрочитанной части. Отчёт о чтении называет непрочитанное, если дочитать не удалось. Чтение журнала LOG.md оглавлением и записями по номеру (таблица 4) обрывом не является — это штатный способ.

Основание: 1 случай, 2026-10-08 — тот же, что в 7.1 (позиция AH-28 очереди registry/maintenance-queue.md; задача labs/sys/t-truncated-read.md в коммите 065370f).
