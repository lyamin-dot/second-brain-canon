Действует для любого файла репозитория lyamin-dot/second-brain-canon, ветка main. При расхождении с second-brain-engineer по вопросу о файле в repo приоритет у этого контракта.

Как устроен этот текст. Он держит правило и число, а не рассказ о том, как правило добывалось. Доказательство каждого числа — запись журнала, названная номером; замеры, номера исполнений n8n и номера нарядов живут там. Состав Канала, ID воркфлоу и сигнатуры живут в registry/tools.md. 0. Термины

Канал — воркфлоу n8n, исполняющие операции с репозиторием по HTTP: Git Read, Git Read Batch, Git Read Lines, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files, Git Log. Состав, ID и сигнатуры — registry/tools.md. Если реестр недоступен или ID ещё не известен (замкнутый круг «файл со списком инструментов сам требует инструмент для чтения») — путь в обход: найти воркфлоу по имени через n8n:search_workflows, подтвердить ID и сигнатуру через get_workflow_details до первого вызова. Вызывать execute_workflow только в режиме manual: режим production не регистрирует исполнение, и результат через get_execution не забрать.

Blob sha — контрольная сумма содержимого файла, вычисляемая git; возвращается Каналом на чтение и запись; воспроизводится локально командой git hash-object. expectedSha — blob sha (для Git Write, Git Replace) или sha коммита HEAD (для Git Commit Files), который вызывающий считает текущим; несовпадение — отказ сервера, ничего не записано.

Манифест — core/MANIFEST.md, файл-список состава core/. Роль файла — одно из фиксированных имён, заданных для сущности проекта: летопись — 4, лаборатория — 4б. Провенанс-маркер — первая строка вида <!-- T-NN | CORE байт X-Y | … --> в файле, перенесённом из CORE. Очередь — registry/maintenance-queue.md, реестр правок, которые сессия сделать не может.

Среда с клоном — сессия, где есть bash и сеть на github.com. Репозиторий публичный, поэтому клон доступен анонимно и никаких учётных данных не требует. Среда без клона — это ровно среда без bash (Claude Project), а не среда без прав на репозиторий. Различение важно: половина правил 7.6 и 8.3 ветвится по нему.

1. Инварианты

И-1. Документ имеет ровно один канонический носитель: Docs или repo. Второго носителя ЗАПРЕЩЕНО.

И-2. Запись считается выполненной только после независимого перечитывания записанного и совпадения blob sha с намеренным содержимым. Ответ инструмента доказательством не является.

И-3. Правило, описывающее возможность транспорта, пишется после зонда транспорта, не до.

И-4. Операция, не покрытая Каналом, называется и останавливает шаг; исполнение в обход Канала ЗАПРЕЩЕНО.

И-5. Число (бюджет, порог, множитель) в этом контракте существует только вместе с названным читателем и датой снятия. Число без них — не норма, а слух.

И-6. Первым действием любой repo-сессии читается meta/PENDING_RULES.md (бюджет чтения 2 048 Б; читатель — старт каждой repo-сессии; предела размера у файла нет — 4.5). Строка с полем «кто подтвердил: Андрей» действует как положение этого контракта до внесения в Skill; при расхождении со Skill приоритет у строки. Файл append-only, пишется через Git Append только по решению журнала, подтверждённому владельцем в чате; вычищается владельцем при правке Skill.

3. Карта репозитория

```
core/            канон по нумерованным разделам R-NN.md; состав — core/MANIFEST.md
meta/            протоколы и контракты, действующие для любого проекта
registry/        реестры: projects.md (проекты и веса), documents.md (ID документов Drive),
                 protocols.md (протоколы), tools.md (Канал), maintenance-queue.md (очередь)
projects/<имя>/  папка проекта — четыре роли, 4
labs/<имя>/      папка лаборатории — две роли плюс файлы задач, 4б
```

3.1. Адрес проекта — папка. Ничто из проекта не лежит снаружи.

3.2. Каталог Каналом не перечисляется: Git Read отдаёт файл по имени, на папку — отказ. Состав папки, обязательной к полному чтению, задаётся файлом-списком внутри неё; список правится тем же действием, что и состав. В среде с клоном каталог перечисляется клоном, и это не отменяет файл-список: список читает тот, у кого клона нет.

3.3. Ссылка «CORE Р.N» при более чем одном файле раздела разрешается через meta/MAP_core-sections.md; раздел без записи в карте = один файл core/R-NN.md.

4. Файлы проекта: роли и бюджеты чтения

| Роль | Содержание | Бюджет чтения | Читатель и момент |
|---|---|---|---|
| STATE.md | статус фаз, следующий шаг, открытые вопросы, блокеры | 8 192 Б | старт каждой сессии проекта |
| PLAN.md | цель, инварианты, архитектура, фазы, риски ЭТОГО проекта | 10 240 Б | сессия, берущаяся за проект, целиком |
| LOG.md | решения, тупики, ошибки; только дописывается | 16 384 Б на прочитанное, не на файл | та же сессия, рядом с PLAN: оглавление журнала одним вызовом по 7.6 (строка «оглавление журнала»), затем целиком только нужные записи — названные в STATE.md или PLAN.md либо выбранные по оглавлению (строка «запись журнала по номеру»). Файл целиком не читается (Р-10, Р-11 журнала projects/kontext-reduktion/LOG.md) |
| NOT_TAKEN.md | что не взято при переносе из Docs, адрес восстановления | нет | по вопросу «где это было» |

Колонка называется бюджетом чтения, а не потолком, потому что числа в ней ограничивают читателя, а не файл. Предела размера у файла летописи нет: он не выводится ни из транспорта, ни из читателя. Попытка удержать LOG.md под 16 384 Б потолком записи была отменена 2026-09-17: она ограничивала не цену читателя, а частоту служебной операции. Основание — Р-99 журнала git-migration; протокол замера — meta/CONTRACT_file-limits.md.

4.1. Пятой роли по умолчанию не существует. Раздел, не ложащийся ни в одну, — стоп и вопрос владельцу. Владелец может разрешить проекту дополнительные роли по 4.6; без такого разрешения роль не заводится.

4.2. Правило разбора: состояние → STATE, правила → PLAN, опыт → LOG.

4.3. Вопрос разбора для любого материала: «это правило про ЭТОТ проект или про любой?» Про любой — meta/; реестр ID — registry/; про этот — PLAN.md. Дубль того, что уже живёт в LOG или Skill, в repo не едет — строка в NOT_TAKEN.md с адресом.

4.4. LOG.md заводится первой квалифицирующей записью, не заранее. NOT_TAKEN.md — только при переносе из Docs.

4.5. Бюджет чтения и правило происхождения текста.

Бюджет чтения относится к читателю и моменту, а не к файлу: читатель платит за сумму того, что читает, и ему безразлично, на сколько файлов она разложена. Он платит и за транспорт: одна и та же сумма байт приходит в контекст в разном объёме в зависимости от того, чем её читают (7.6).


Числа бюджетов старта, снятые с объекта, и порядок их опровержения — references/costs.md. Правило происхождения текста (что можно, а что нельзя набирать моделью при записи) — references/write.md, пункт 4.5.

4б. Лаборатория — папка labs/<имя>/ с темой без финиша; роли её файлов, атомарность, закрытие и старение задач — references/lab.md. Читать перед любой работой с папкой labs/.

5. Превышение бюджета чтения

Превышение бюджета чтения — не отказ и не блок. Разбор по роли (5.1) и переливной клапан для STATE.md, PLAN.md, meta/* (5.5) — references/write.md. Ротация журнала (5.2–5.4) — references/rotation.md. Разрез core/ (6) — references/core-split.md.

7. Чтение

7.1. Прежде чем прочитать что-либо, открой 7.6 и выбери транспорт по таблице. Этот пункт задаёт только контракт ответа и не отвечает на вопрос «чем читать».

Git Read {path, ref?} → {text, sha, byteLength}. Поле byteLength воркфлоу считает из тех же декодированных байт, из которых получен text (узел 04_Build_Response, Buffer.from(base64).length), поэтому сверка byteLength с длиной text сравнивает файл сам с собой и не выполняется; byteLength — оценка стоимости чтения, не проверка. Признак порчи при декодировании, который сессия может увидеть сама, — символ замены U+FFFD в text. То же верно для каждого файла ответа Git Read Batch. Git Read Batch {paths[]} → {requested, returned, files[], missing[]}: returned < requested или непустой missing — чтение набора не состоялось, стоп. Полные сигнатуры, включая режимы Git Read Lines, — registry/tools.md.

7.2. «CORE прочитан целиком» = прочитаны все файлы таблицы «Список» Манифеста; meta/header.md на старте не читается — оба его поля недействующие (Р-3 журнала kontext-reduktion). Признак в отчёте — три величины: число прочитанных файлов таблицы, путь последнего файла таблицы, его blob sha. Две первые списываются с самого Манифеста и без третьей ничего не доказывают. Таблица «По событию» в чтение на старте и в признак не входит: её файл читается одним вызовом Git Read в той сессии, где событие наступило, до первой записи этого вида (Р-111). Размеров Манифест не хранит: размер приходит в ответе Канала.

7.3. Пароль-канарейка, FNV и счётчики к файлам repo не применяются и основанием для отказа не являются: у набора файлов нет конца, на котором держалась канарейка. Контракт чтения задаётся носителем объекта: Docs — канарейка и FNV по gdocs-read; repo — Манифест и blob sha.

7.4. Чтение STATE.md на старте repo-сессии — без записи: полей LAST_READ у repo-файлов нет, актуальность даёт git log.

7.5. Утверждение об истории репозитория пишется в файл только с двумя величинами той же сессии — references/write.md, пункт 7.5.

7.6. ЧЕМ ЧИТАТЬ. Это правило, а не совет, и оно измерено. Выбор транспорта делается до первого чтения в сессии, по таблице, и никаким иным способом.

| Что нужно | Среда с клоном | Среда без клона |
|---|---|---|
| файл целиком | `git fetch && cat` | Git Read; набор путей — Git Read Batch |
| запись или фрагмент, номер строки НЕизвестен | `git fetch && grep` | **Git Read Lines с входом pattern, один вызов** |
| фрагмент, номер строки известен | `git fetch && sed -n` | Git Read Lines без pattern |
| история коммитов, дата последней правки | `git log` | Git Log, минимальный limit (дорог, см. ниже) |
| перечислить каталог | `git ls-files` | не покрыто Каналом: файл-список внутри папки (3.2) |
| blob sha для сверки | `git hash-object` | sha из ответа любого читающего воркфлоу |
| оглавление журнала LOG.md | `git fetch && grep -nE` с шаблоном оглавления (ниже) | Git Read Lines, pattern = шаблон оглавления, limit не меньше числа записей; если count больше числа возвращённых строк — повторить с limit = count |
| запись журнала по номеру | `git fetch && grep -nA10` с шаблоном записи (ниже) | Git Read Lines, pattern = шаблон записи, after = 10; если последняя возвращённая строка — поле записи (начинается с двух пробелов), дочитать строки с to+1 без pattern |

Шаблоны. Оглавление журнала: `^(Р|Т)-[0-9]+ \|` — строки-заголовки решений и тупиков. Запись по номеру: `^Р-111 \|` с номером нужной записи. Во входе Git Read Lines, который передаётся как JSON, обратная косая черта удваивается. Буквы Р и Т пишутся только чередованием `(Р|Т)`, не классом `[РТ]`: в среде без настроенной локали grep считает кириллическую букву двумя байтами и молча находит 0 записей (проверено 2026-09-24, Р-10 журнала projects/kontext-reduktion/LOG.md). Строка-заголовок записи обязательна по форме 11, поэтому оглавление не ведётся отдельно — оно выводится из файла в момент чтения.

Две команды, обязательные при чтении через Канал.

**Сужать всегда.** Любое чтение через Канал сопровождается вызовом `get_execution(includeData:true, nodeNames:["05_Respond"])` — или как называется терминальный узел Respond у конкретного воркфлоу. Без сужения результат приходит с каждого узла графа, через который прошли данные, и тело файла дублируется по числу узлов: та же операция стоит 3,38× вместо 1,0×.

**У пишущих и у Git Log не звать includeData вовсе.** Шесть воркфлоу Канала тянут данные узлом `n8n-nodes-base.httpRequest`, у которого сырой ответ GitHub оседает в `executionData.contextData`, и сужение этого НЕ режет. Их статус берётся вызовом `get_execution(includeData:false)`; факт записи доказывается независимым чтением чистым воркфлоу либо клоном (8.1).

| Воркфлоу | Узел загрузки | contextData |
|---|---|---|
| Git Read, Git Read Batch, Git Read Lines | `n8n-nodes-base.github` | пуст всегда — ЧИСТЫЕ |
| Git Log, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files | `n8n-nodes-base.httpRequest` | сырой ответ GitHub, nodeNames не режет — ГРЯЗНЫЕ |

Свойство принадлежит типу узла, а не назначению воркфлоу, и параметрами вызова не чинится — только сменой узла загрузки внутри воркфлоу. Поэтому при заведении нового читающего воркфлоу узел выбирается по этому свойству, а не по удобству.


Цена транспортов, снятая с объекта, и способ её измерения — references/costs.md. Правило выше от неё не зависит: оно уже выбрано по этим числам.

Клон ДОПУСКАЕТСЯ как read-only подложка (9.1) и на достоверность не влияет: blob sha в клоне после git fetch совпадает с тем, что отдаёт Канал, — это свойство git, а не совпадение.
