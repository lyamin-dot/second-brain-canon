0. Термины

Канал — воркфлоу n8n, исполняющие операции с репозиторием по HTTP: Git Read, Git Read Batch, Git Read Lines, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files, Git Log. Состав, ID и сигнатуры — registry/tools.md. Если реестр недоступен или ID ещё не известен (замкнутый круг «файл со списком инструментов сам требует инструмент для чтения») — путь в обход: найти воркфлоу по имени через n8n:search_workflows, подтвердить ID и сигнатуру через get_workflow_details до первого вызова. Вызывать execute_workflow только в режиме manual: режим production не регистрирует исполнение, и результат через get_execution не забрать. Сам инструмент по умолчанию ставит production, поэтому executionMode: "manual" указывается в каждом вызове явно.

Форма вызова execute_workflow для воркфлоу Канала (сервер n8n MCP сменил её 2026-10-08): параметр triggerNodeName — имя узла-триггера, у всех воркфлоу Канала это 01_Webhook; параметр inputs — {webhookData: {method: "POST", body: {…вход воркфлоу…}}}, без поля type. Пример для Git Read Batch: workflowId из registry/tools.md, executionMode "manual", triggerNodeName "01_Webhook", inputs {webhookData: {method: "POST", body: {paths: ["core/MANIFEST.md"]}}}. Прежняя форма inputs {type: "webhook", webhookData: …} отвергается сервером ошибкой «Unrecognized key(s) in object: 'type'», вызов без triggerNodeName — ошибкой «Provide triggerNodeName when passing inputs». Описание инструмента в клиенте Claude на 2026-10-08 ещё показывало старую схему с type — верить ошибке сервера, а не описанию. Основание — запись Р-5 журнала projects/deklaration-wb/LOG.md и позиция AH-26 очереди; имя триггера 01_Webhook у Git Read Batch подтверждено живым вызовом 2026-10-09.

Git Grep в Канал не входит и не вызывается ни для какой задачи, хотя воркфлоу с этим именем ещё описан в registry/tools.md (на инстансе он архивирован — снимок registry/n8n-map.md): в contextData его исполнения лежит base64 всего файла, и сужение nodeNames этого не режет, поэтому поиск через него дороже чтения файла целиком (запись Р-21 журнала projects/kontext-reduktion/LOG.md, запись Р-2 файла meta/CONTRACT_file-limits.md). Его работу делает Git Read Lines с входом pattern (7.6).

Blob sha — контрольная сумма содержимого файла, вычисляемая git; возвращается Каналом на чтение и запись; воспроизводится локально командой git hash-object. expectedSha — blob sha (для Git Write, Git Replace) или sha коммита HEAD (для Git Commit Files), который вызывающий считает текущим; несовпадение — отказ сервера, ничего не записано.

Манифест — core/MANIFEST.md, файл-список состава core/. Роль файла — одно из фиксированных имён, заданных для сущности проекта: летопись — 4, лаборатория — 4б. Провенанс-маркер — первая строка вида <!-- T-NN | CORE байт X-Y | … --> в файле, перенесённом из CORE. Очередь — registry/maintenance-queue.md, реестр правок, которые сессия сделать не может.

Среда с клоном — сессия, где есть bash и сеть на github.com. Репозиторий публичный, поэтому клон доступен анонимно и никаких учётных данных не требует. Среда без клона — это ровно среда без bash (Claude Project), а не среда без прав на репозиторий. Различение важно: половина правил 7.6 и 8.3 ветвится по нему.

1. Инварианты

И-1. Документ имеет ровно один канонический носитель: Docs или repo. Второго носителя ЗАПРЕЩЕНО.

И-2. Запись считается выполненной только после независимого перечитывания записанного и совпадения blob sha с намеренным содержимым. Ответ инструмента доказательством не является.

И-3. Правило, описывающее возможность транспорта, пишется после зонда транспорта, не до.

И-4. Операция, не покрытая Каналом, называется и останавливает шаг; исполнение в обход Канала ЗАПРЕЩЕНО.

И-5. Число (бюджет, порог, множитель) в этом контракте существует только вместе с названным читателем и датой снятия. Число без них — не норма, а слух.

И-6. Первым действием любой repo-сессии читается meta/PENDING_RULES.md (бюджет чтения 2 048 Б; читатель — старт каждой repo-сессии; предела размера у файла нет — 4.5). Строка с полем «кто подтвердил: Андрей» действует как положение этого контракта до внесения в Skill; при расхождении со Skill приоритет у строки. Файл append-only, пишется через Git Append только по решению журнала, подтверждённому владельцем в чате; вычищается владельцем при правке Skill.

И-7. Репозиторий публичный, и запись в него необратима: коммит остаётся в истории навсегда, даже если файл потом исправлен или удалён. Поэтому в repo не пишутся пути вебхуков n8n, признаки их аутентификации и имена ключей доступа (credentials) — то, что облегчает атаку на инстанс. Воркфлоу, публикующий в repo данные с инстанса автоматически, держит защиту в своём коде до записи: строка, содержащая «/webhook/», «http:» или «https:», «Bearer» или «@», роняет прогон, и в repo ничего не уходит; идентификаторы он извлекает только из ключей по белому списку, а не регулярным выражением по всему тексту. Образец — воркфлоу снимка registry/n8n-map.md (раздел 5 файла projects/n8n-map/PLAN.md; записи Р-1, Р-4, Р-6…Р-8 журнала projects/n8n-map/LOG.md).

4.5. Бюджет чтения и правило происхождения текста.

Бюджет чтения относится к читателю и моменту, а не к файлу: читатель платит за сумму того, что читает, и ему безразлично, на сколько файлов она разложена. Он платит и за транспорт: одна и та же сумма байт приходит в контекст в разном объёме в зависимости от того, чем её читают (7.6).


Числа бюджетов старта, снятые с объекта, и порядок их опровержения — references/costs.md. Правило происхождения текста (что можно, а что нельзя набирать моделью при записи) — references/write.md, пункт 4.5.

4б. Лаборатория — папка labs/<имя>/ с темой без финиша; роли её файлов, атомарность, закрытие и старение задач — references/lab.md. Читать перед любой работой с папкой labs/.

7. Чтение

7.1. Прежде чем прочитать что-либо, открой 7.6 и выбери транспорт по таблице. Этот пункт задаёт только контракт ответа и не отвечает на вопрос «чем читать».

Git Read {path, ref?} → {text, sha, byteLength}. Поле byteLength воркфлоу считает из тех же декодированных байт, из которых получен text (узел 04_Build_Response, Buffer.from(base64).length). Поэтому против порчи ВНУТРИ воркфлоу сверка byteLength с text ничего не доказывает — она сравнивает файл сам с собой, и для этой цели не выполняется; признак порчи при декодировании, который сессия может увидеть сама, — символ замены U+FFFD в text. Против обрезания НА ПУТИ от инструмента к модели byteLength — как раз нужная мерка: его сообщил сервер, а увиденный текст видит сама модель; явно меньший текст при большом byteLength — обрезанный вывод по 7.7. То же верно для каждого файла ответа Git Read Batch.

ИСТОРИЯ ДИАГНОЗА: с 2026-09-24 до 2026-10-09 сверка byteLength считалась бесполезной вообще (запись Р-5 журнала projects/kontext-reduktion/LOG.md); опровергнуто 2026-10-08, когда агент проекта wb-ue получил projects/wb-ue/STATE.md обрезанным до первых двух килобайт и продолжил работу — запрет был шире своего основания (labs/sys/t-truncated-read.md, позиция AH-28 очереди). Git Read Batch {paths[]} → {requested, returned, files[], missing[]}: returned < requested или непустой missing — чтение набора не состоялось, стоп. Полные сигнатуры, включая режимы Git Read Lines, — registry/tools.md.

7.2. «CORE прочитан целиком» = прочитаны все файлы таблицы «Список» Манифеста; meta/header.md на старте не читается — оба его поля недействующие (Р-3 журнала kontext-reduktion). Признак в отчёте — три величины: число прочитанных файлов таблицы, путь последнего файла таблицы, его blob sha. Две первые списываются с самого Манифеста и без третьей ничего не доказывают. Таблица «По событию» в чтение на старте и в признак не входит: файлы её строки читаются одним вызовом в той сессии, где событие наступило, до первой записи этого вида (Р-111): Git Read — если в строке один файл, Git Read Batch — если несколько, `cat` — в среде с клоном. Размеров Манифест не хранит: размер приходит в ответе Канала.

7.3. Пароль-канарейка, FNV и счётчики к файлам repo не применяются и основанием для отказа не являются: у набора файлов нет конца, на котором держалась канарейка. Контракт чтения задаётся носителем объекта: Docs — канарейка и FNV по gdocs-read; repo — Манифест и blob sha.

7.4. Чтение STATE.md на старте repo-сессии — без записи: полей LAST_READ у repo-файлов нет, актуальность даёт git log.

7.5. Утверждение об истории репозитория пишется в файл только с двумя величинами той же сессии — references/write.md, пункт 7.5.

7.6. ЧЕМ ЧИТАТЬ. Это правило, а не совет, и оно измерено. Выбор транспорта делается до первого чтения в сессии, по таблице, и никаким иным способом.

| Что нужно | Среда с клоном | Среда без клона |
|---|---|---|
| файл целиком | `git fetch && cat` | Git Read; набор путей — Git Read Batch |
| запись или фрагмент, номер строки НЕизвестен | `git fetch && grep` | **Git Read Lines с входом pattern, один вызов** |
| фрагмент, номер строки известен | `git fetch && sed -n` | Git Read Lines без pattern |
| история коммитов, дата последней правки | `git log` | Git Log, минимальный limit (грязный, см. ниже; цена — references/costs.md) |
| перечислить каталог | `git ls-files` | не покрыто Каналом: файл-список внутри папки (3.2) |
| blob sha для сверки | `git hash-object` | sha из ответа любого читающего воркфлоу |
| оглавление журнала LOG.md | `git fetch && grep -nE` с шаблоном оглавления (ниже) | Git Read Lines, pattern = шаблон оглавления, limit не меньше числа записей; если count больше числа возвращённых строк — повторить с limit = count |
| запись журнала по номеру | `git fetch && grep -nA10` с шаблоном записи (ниже) | Git Read Lines, pattern = шаблон записи, after = 10; если последняя возвращённая строка — поле записи (начинается с двух пробелов), дочитать строки с to+1 без pattern |
| дочитать файл после обрезанного вывода (7.7) | `sed -n '<N>,$p'` с первой непрочитанной строки | Git Read Lines без pattern, from = первая непрочитанная строка; при риске нового обрыва — кусками с явным to |

Шаблоны. Оглавление журнала: `^(Р|Т)-[0-9]+ \|` — строки-заголовки решений и тупиков. Запись по номеру: `^Р-111 \|` с номером нужной записи. Во входе Git Read Lines, который передаётся как JSON, обратная косая черта удваивается. Буквы Р и Т пишутся только чередованием `(Р|Т)`, не классом `[РТ]`: в среде без настроенной локали grep считает кириллическую букву двумя байтами и молча находит 0 записей (проверено 2026-09-24, Р-10 журнала projects/kontext-reduktion/LOG.md). Строка-заголовок записи обязательна по форме 11, поэтому оглавление не ведётся отдельно — оно выводится из файла в момент чтения.

Две команды, обязательные при чтении через Канал.

**Сужать всегда.** Любое чтение через Канал сопровождается вызовом `get_execution(includeData:true, nodeNames:["05_Respond"])` — или как называется терминальный узел Respond у конкретного воркфлоу. Без сужения результат приходит с каждого узла графа, через который прошли данные, и тело файла дублируется по числу узлов: та же операция стоит 3,38× вместо 1,0×.

**У пишущих и у Git Log не звать includeData вовсе.** Шесть воркфлоу Канала тянут данные узлом `n8n-nodes-base.httpRequest`, у которого сырой ответ GitHub оседает в `executionData.contextData`, и сужение этого НЕ режет. Их статус берётся вызовом `get_execution(includeData:false)`; факт записи доказывается независимым чтением чистым воркфлоу либо клоном (8.1).

| Воркфлоу | Узел загрузки | contextData |
|---|---|---|
| Git Read, Git Read Batch, Git Read Lines | `n8n-nodes-base.github` | пуст всегда — ЧИСТЫЕ |
| Git Log, Git Write, Git Replace, Git Append, Git Append File, Git Commit Files | `n8n-nodes-base.httpRequest` | сырой ответ GitHub, nodeNames не режет — ГРЯЗНЫЕ |

Во сколько раз ошибка обходится у грязного воркфлоу: сырой ответ оседает в contextData столько раз, сколько в воркфлоу узлов загрузки, — Git Log 1, Git Write 1, Git Replace 2, Git Append 3, Git Append File 4 (три к GitHub, один к Google Drive), Git Commit Files 6. Карта узлов снята прямым чтением воркфлоу 2026-09-18 (registry/tools.md, раздел «Свойства канала целиком»); число узлов с credential по снимку registry/n8n-map.md 2026-09-26 с ней совпадает. Вызов get_execution с includeData:true у Git Append приносит в контекст файл трижды вместо доказательства записи.

Свойство принадлежит типу узла, а не назначению воркфлоу, и параметрами вызова не чинится — только сменой узла загрузки внутри воркфлоу. Поэтому при заведении нового читающего воркфлоу узел выбирается по этому свойству, а не по удобству.

Посредник (субагент, читающий вместо сессии) к файлам repo не применяется: таблица выше уже даёт ту же цену, а посредник добавляет к ней свой расход. Его ниша — ответ инструмента, который сузить нечем, например get_workflow_details; правило — second-brain-engineer, пункт Р21, основание — Р-25 и Р-26 журнала projects/kontext-reduktion/LOG.md.


Цена транспортов, снятая с объекта, и способ её измерения — references/costs.md. Правило выше от неё не зависит: оно уже выбрано по этим числам.

Клон ДОПУСКАЕТСЯ как read-only подложка (9.1) и на достоверность не влияет: blob sha в клоне после git fetch совпадает с тем, что отдаёт Канал, — это свойство git, а не совпадение.

7.7. Обрезанный вывод означает «файл не прочитан». Репозиторий отдаёт файл целиком; обрезать вывод может предел инструмента или клиента между инструментом и моделью. Признаки обрыва: пометка харнесса об обрезке или о сохранении вывода в файл, текст кончается посреди строки или раздела, увиденный текст явно меньше byteLength (7.1), у Git Read Lines to меньше totalLines при запросе до конца файла. Увидев обрыв, сессия дочитывает файл по строкам с места обрыва (строка «дочитать файл после обрезанного вывода» таблицы 7.6) до того, как действовать. Работать по частично прочитанному STATE.md или PLAN.md ЗАПРЕЩЕНО: следующий шаг, открытые вопросы и запреты лежат как раз в непрочитанной части. Отчёт о чтении называет непрочитанное, если дочитать не удалось. Чтение журнала LOG.md оглавлением и записями по номеру (таблица 4) обрывом не является — это штатный способ. Основание — labs/sys/t-truncated-read.md, позиция AH-28 очереди.
