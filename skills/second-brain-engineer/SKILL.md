# second-brain-engineer

Регламент Второго мозга для всех Claude Project системы: что делать, когда и с чьего согласия — старт, захват, команды, !save, онбординг и мастер-промпт, права, провенанс, проектирование и приёмка. Как физически прочитать и записать файл репозитория — Skill `second-brain-git`; то же для Google Docs и Sheets — Skill `google-drive-docs`. Механика из них сюда не переписывается.

## Стоп-правила

### Общие
- Не прочитав файл, который «Что читать» называет для действия, действие не начинать.
- Блок не закрывать без его проверки (строка «Проверка» в конце процедуры).
- Шаги этого Skill не исполнять по памяти прошлой сессии.
- Механику записи из `second-brain-git` и `google-drive-docs` сюда не переписывать — только ссылка.
- Проект, которого нет в `registry/projects.md` и у которого нет INDEX в Docs, не угадывать: проекта не существует.
- Старый CORE в Docs для принятия решений не читать.

### Р14. Запреты
- Деструктивное действие (воркфлоу, строки Sheets, Drive, repo, больше трёх узлов) без подтверждения в форме «Собираюсь [действие] на [объект]. Это изменит [что]. Подтверждаешь?» не делать.
- Структуру INDEX и мастер-промпта попутно не менять — только отдельным действием, после явного «да» Андрея в чате и текстом «было → стало»; исключение — критический баг, ломающий систему прямо сейчас.
- Второй носитель одного документа не заводить: Docs или repo — одно.
- Правку Skill, мастер-промпта или CORE не «откладывать» без позиции в `registry/maintenance-queue.md` с датой смерти; прочую находку — без задачи в `labs/sys/`.
- Запись не считать выполненной по ответу инструмента (`success: true`, `occurrencesChanged`, номер исполнения, exec-ID) — только по обратному чтению.
- ID и адреса, у которых есть реестр, в Skill не хранить: документы Docs — `registry/documents.md`; git-канал и repo — `registry/`; таблицы Sheets и доменные детали — `n8n-workflow-registry`.
- Skill `n8n-workflow-registry` не править; таблицу или документ, созданные сессией, — в `registry/documents.md`.
- Секреты и их признаки и личные данные не публиковать в странице-артефакте и её данных; проверка — до публикации, по классам Skill `second-brain-git`, «Стоп-правила», раздел «Носитель и данные».
- Ветку `claude/*` не удалять без слова Андрея.

### Р10. Воркфлоу n8n — вопрос до вызова
- Вызов, меняющий воркфлоу n8n (`update_workflow`, `create_workflow_from_code` поверх существующего, `restore_workflow_version`, `publish_workflow`, `unpublish_workflow`, `archive_workflow`), не делать без вопроса в чате «Воркфлоу [имя], узел [имя]. Планирую: [описание]. Подтверждаешь?» и явного «да»; исключения — раздел «Р10. Воркфлоу n8n — полномочия» (прочитать до вызова).
- Просьбу Андрея изменить воркфлоу за «да» не принимать: просьба называет цель, вопрос показывает, что изменится и в каком узле.
- В одном сообщении не больше трёх вопросов, требующих «да».
- Действие в интерфейсе n8n или в браузере Андрея не поручать и не делать без явного «да» Андрея на эту строку; «не знаю», молчание, отсутствие возражений разрешением не считать; привязку ключа к узлу на Андрея не перекладывать — сессия делает её сама, `setNodeCredential`.

### Провенанс и запись в канон
- Решение на памяти, пересказе или старой записи не принимать: объект читается до решения, либо утверждение пишется словами «Гипотеза (не проверена):».
- Ответ посредника не писать в канон, пока сессия не прочитала источник сама (хотя бы адрес доказательства, названный посредником).
- Четвёртой метки происхождения не ставить; уверенность за происхождение не выдавать.
- Расхождение факта с ожиданием тихо не править — стоп и вопрос.
- На пустое чтение (пустота без ошибки) не отвечать по памяти — стоп и сообщение.
- Задачу по слову Андрея «сделал», «удалил», «внёс» не закрывать, пока объект не прочитан в этой сессии.
- В графе «что чтением не считается» таблицы раздела «Р15. Провенанс и верификация — единый стандарт» — то, на чём утверждение не строится; без чтения из графы «что прочитать» утверждение не писать.
- «Нет» не произносить и не писать без поиска в собственном носителе объекта и перечня, где искали; отсутствие в реестре, в CORE или в памяти сессии отсутствием объекта не считать.
- Правку объекта не начинать с локальной копии — только с его живой версии в собственном носителе.
- Опровергнутую причину не стирать.
- Факты (ID, пороги, версии) в задания не писать — правила поведения при неизвестном; конкретику брать из реестра в момент использования.
- Пакетную операцию не начинать без манифеста реальных объектов, полученных чтением в этой сессии.
- Идентификатор, число или дату не писать в канон по памяти, перепечаткой из другого текста или счётом в уме; дату — не из памяти модели.
- Число или вердикт о живом объекте не писать без отметки версии или времени снимка и определения счёта.
- Два числа об одном объекте не сравнивать и расхождение не называть дефектом или опровержением, если определение счёта разное или порядок снимков неизвестен.
- Критерий приёмки по числу о живом файле не задавать абсолютным числом — соотношением на свежем чтении.

### Старт и команды
- На первое сообщение не отвечать до старта (раздел «Р1. Старт сессии — Правило Феникса»); предметная задача в сообщении старт не сокращает.
- Строку старта не превращать в список или «кратко»; после неё — молчать до вопроса.
- В repo на старте ничего не писать.
- Тела задач лаборатории на старте не читать.
- `read_file_content` для Docs не применять (Skill `google-drive-docs`, раздел «Пути чтения»).
- Обрезанный вывод чтения прочитанным не считать (Skill `second-brain-git`, разделы «Контракт ответа читающих воркфлоу» и «Обрезанный вывод»).
- CORE целиком ни по одной команде и ни по !save не читать; `meta/header.md` для !save не читать.
- Метку задачи в !priority не угадывать; задачу без метки не оценивать.
- !map вне проекта N8N и харвест вне проекта SYS не исполнять.
- На вопрос «как дела с системой» реестр протоколов не отбирать по «интересности» — целиком.

### Захват и !save
- Проект захвата не угадывать: неясен — `[?] Не классифицировано`.
- Пересказ уже записанного захватом не считать.
- Строку «Трение» без трения не писать; в канон трение не записывать, пока Андрей его не подхватил.
- После смены предмета или цели работу по-новому не продолжать до захвата Решения, вопроса Андрею и записи в журнал решений проекта.
- К следующему шагу и к отправке Андрею в чат не переходить, пока созданный объект, нужный после сессии, не получил адрес в каноне.
- Отправку файла в чат, файл в рабочей папке сессии и сказанное в чате записью не считать.
- Строку, которую Андрей вычеркнул после !save, не править задним числом — отменять новой записью.
- Открытую задачу Docs-проекта не писать в хвост документа — в ОТКРЫТЫЕ ЗАДАЧИ Зоны А.
- Задачу лаборатории не закрывать (удаление файла и строки) без «да» Андрея.
- До первой записи в сессии не писать, не прочитав нужную часть Skill носителя целиком.
- Строку с открытым делом из STATE.md в LOG.md или PLAN.md не переносить; решения по снимку STATE.md не применять, если blob sha файла не равен снимку, — стоп и новый снимок.
- Приёмку по строкам внутри скрипта разбора STATE.md проверкой места строки не считать; размер STATE.md критерием содержания не считать; превышение бюджета после разбора дефектом не считать.
- Решение, противоречащее записи журнала, не писать до ответа Андрея.
- Ответ-исследование без названного читателя в репозиторий не подшивать.
- Значения ПРОЕКТ вида «A + B» в CHANGELOG не писать; статус вне словаря ЗАПУЩЕНО / СОЗДАНО / ЗАКРЫТО — не писать, приводить вслух.
- В SYS_INDEX не писать: он заморожен.
- Запись ЗАПУЩЕНО в CHANGELOG не делать, пока наблюдаемый объект не показал значение.
- Файл закрываемой задачи лаборатории не удалять, не перенеся превентив класса ошибки.
- Карту SYSTEM-MAP не вести и не читать как действующую.
- Полные списки ИДЕЙ и ВОПРОСОВ в Зоне А не держать — только указатели.
- Поле ENTRIES_COUNT в INDEX не искать.
- Блок «Устаревшее» в INDEX не чистить без подтверждения Андрея.

### Права и вопросы Андрею
- Необратимое (откат невозможен или дорог) не делать без «да» Андрея, видимого до действия в чате или в записанном каноне; где правило прямо требует «да», оно нужно, даже если откат возможен.
- Ответ «согласен со всем» на пакет вопросов решением по каждому не считать: вопросы без отдельного ответа остаются открытыми и в запись решения не идут.
- Пакет разрешения, заданный классом объектов, не записывать, не проверив поиском по инстансу и по канону, что его признак не носит ни один объект другого проекта.
- По поручению «реши сам» необратимое (удаление воркфлоу, удаление данных) не делать — оставить Андрею и перечислить в отчёте; поручение на другие задачи и сессии не переносить.
- Прежнее решение (запись журнала, строку `PLAN.md` или `STATE.md`, слово Андрея) поручением «реши сам» молча не отменять — только записью «этим заменено: <адрес прежнего решения>» с доводом.
- Секрет ключа доступа через сессию не передавать: ключ в редакторе n8n создаёт Андрей.
- Мастер-промпт не заменять, пока его старый текст не сохранён файлом; наряд с DoD «промпт переключён» без этого файла не выдавать.
- Правку Skill действующей не считать до заливки zip Андреем: текст в чате, в зеркале `skills/`, в файле Drive ничего не меняет.
- Андрей не меняет структуру INDEX напрямую, не переименовывает и не удаляет воркфлоу без согласования, не меняет колонки Sheets, не правит середину функций Apps Script (только полная замена).

### Посредник
- Решение отдать вызов посреднику не принимать по пришедшему ответу — до вызова.
- Файл посреднику не отдавать — сужать самой.
- Правила, которые сессия исполняет сама (контракт записи, контракт чтения, протокол, пункт Skill), посредником не читать никогда.
- Диагностику «почему не работает» исключением из порога не считать, пока правка не названа.
- В вопрос посреднику ожидаемый ответ и ожидаемую роль объекта не вкладывать.
- Факт посредника без адреса доказательства и без NOT_FOUND полученным не считать.
- Самую лёгкую модель посреднику не брать, кроме буквального извлечения с адресом доказательства.
- Расход посредника не замерять.

### Мастер-промпт и онбординг
- Мастер-промпт или блок Второго мозга не выдавать, если не выполнен хоть один пункт раздела «Р3. Валидация мастер-промпта».
- Блок Второго мозга не менять без явного «да» Андрея в чате и текста «было → стало»; правила, уже стоящие в Skill, в блок не вписывать.
- Регламент Второго мозга (строку старта, маршрут !save, таблицу команд, формат захвата, порядок записи) в промпте не пересказывать.
- Ссылки на общие документы (USER_PROFILE, INBOX, CHANGELOG), Docs-ID CORE и ID замороженных документов как источников состояния в блок и промпт не вписывать.
- Изменчивые факты (статусы, расписания, адреса ячеек, версии, числа замеров, список багов) и ID, у которых есть реестр, в промпт не писать; исключение — ID, без которых не прочитать реестр (воркфлоу Git-канала, gdocs-read, gsheets-read).
- Обрыв старого промпта не дописывать по догадке — спросить остаток; первую строку нового текста не писать, пока не получены все части инструкций.
- Знания, которых нет нигде, кроме промпта, не удалять как «изменчивые».
- Расхождение двух копий промпта тихо не выравнивать — стоп и вопрос Андрею, какая права.
- Обязательных фраз в конце ответа в промпт не ставить; лимиты самостоятельности по счёту вызовов не ставить.
- Поправку выданного промпта не оставлять только в чате — тем же шагом в зеркало `meta/prompts/<папка>.md`.
- Рассказ урока о промпте в метод не дописывать.
- Ничего не создавать при онбординге, пока выбор носителя не назван вслух.
- Отсутствие проекта в `registry/projects.md` не доказывать поиском подстроки — прочитать секцию целиком.
- Следующий шаг онбординга не начинать до независимого чтения результата предыдущего.
- INDEX без строки SENTINEL последней строкой Зоны А проверку старта прошедшим не считать.

### Проектирование, замер, приёмка
- Рамку Андрея молча не принимать: без квитанции рамки шаг не закрыт; гипотеза «оставляю» без слова проверки — непроверенная.
- Обратный ТРИЗ не закрывать без ранжированного списка из двух–четырёх слабых мест; слабое место без противоречия найденным не считать.
- Сущность (документ, корпус, реестр, журнал), не прошедшую хоть одни из пяти ворот, не строить.
- Живую сущность, у которой пропал читатель, не чинить постройкой нового наблюдения; процедуру не снимать без перечня объектов, у которых она была единственным читателем, и вердикта по каждому.
- Журнал целиком не читать — оглавление и записи по номеру; отдельный указатель решений (вида DECISIONS_MAP) не заводить; семантический поиск для оглавления решений не применять.
- Рекомендацию не дробить по трудоёмкости, если Андрей сам не спросил про сроки.
- «Выждал паузу и отчитался» отчётом не считать.
- Запись Р без отвергнутой альтернативы решением не считать.
- Правило, выведенное по одному образцу или малой выборке, на целое не переносить.
- Рамку приоритетов своего проекта не применять как отказ чужому.
- Защиту от разрушительных действий не строить доверием к сессии и скрытием механизма.
- Вторую копию данных не заводить, пока не переведены все читатели первой; правку не делать в копии — только в источнике.
- Решение без замера «до» не принимать; неизмеренное рассуждением не заполнять, а помечать «не измерено»; число без читателя не заводить.
- Прогноз не выводить из поведения проверяемого кода — из требования; разные числа на одном правиле «разбросом» не называть; совпадение чисел на разных множествах подтверждением не считать.
- Структурную переделку не начинать, не проверив пробой посылку о вреде.
- Эталон проверки не брать тем же путём, что проверяемое; перечень, составленный проверяемым скриптом, эталоном не считать; новую версию не проверять по старой.
- «0 расхождений» без перечня сверенных полей результатом не считать.
- Вопросы приёмки не составлять исполнителем работы; файл вопросов поведенческого теста не класть туда, куда тестируемая сессия дотянется поиском; отчёт сессии о себе и вопрос «перечисли свои вызовы» доказательством теста не считать.
- Мнение второго экземпляра той же модели с тем же мастер-промптом независимым не называть; ни один класс проверяющего не объявлять заменой другого.
- Правку после акта приёмки не закрывать исполнителем; прогон собственного скрипта повторной приёмкой не считать.
- Итог «находок 0» у скана, детектора или монитора не принимать без положительного контроля в том же прогоне.
- Работу, где текст составлялся или переписывался, не принимать одной механической сверкой.
- Пустое или странное значение не называть дефектом, не выяснив, что это за поле и кто его заполняет.
- Пробу с заранее известным исходом и настоящим риском (стереть данные, ключ, сведения о маркировке, скрыть карточку) не делать даже на одном объекте.
- Массовую запись во внешний кабинет не делать без одной пробной записи в один объект со снимком до записи и чтением обратно.
- Разрешение Андрея на число списком к записи не считать: перед записью во внешний мир список пересчитать по объекту; список по правилу-гипотезе не нести на разрешение, не сверив с кабинетом.
- Критерий приёмки, ставший неудобным, задним числом не смягчать.

### Массовая работа, скрипты
- Массовую механическую работу (опись файлов Drive или PDF, нарезку текста на файлы, пересборку, перенос большого тела) моделью не исполнять — только скриптом.
- Совпадение суммы байт приёмкой переноса не считать; самоприёмку, сравнивающую разбиение с самим собой, не делать.
- Строку таблицы при нарезке и пересборке вручную не переписывать — переносит скрипт.
- Механическое изменение не совмещать со смысловым в одном проходе.
- Текст, который скрипт вставляет от себя, не формулировать заново и не сверять с перечнем вставок самого скрипта.
- Простой `set -e` проверку каждого шага скрипта по расписанию не заменяет.
- На окружение входа человека и `sudo` под cron скрипт по расписанию не полагать.
- Код возврата скрипта результатом не считать; размер и свежесть файла дампа — наличие, а не целость и полнота.

### Правка Skill и каталог
- Пороги «свыше 90 % успеха до 20 навыков, деградация после 30» основанием решения о создании или объединении Skill не брать; довод «у нас почти 30 Skills» доводом не считать.
- Единый язык формулировок при массовой правке описаний Skills не вводить.
- Состояние и особенности конкретного проекта, таблицы, книги, воркфлоу, сервера или кабинета в Skill не писать; поведение API маркетплейса — тоже.
- Проверку, условие или счётчик, которые среда не исполняет, в правку Skill не вписывать без пометки «неисполнимо».
- Список неразобранных пересечений описаний молча на следующую карту каталога не переносить.
- Рассказы случаев, номера исполнений и историю правок в Skill не писать.
- Имена моделей в этот Skill не писать.
- Правило без триггера и момента действия в Skill не вносить.
- Номера разделов этого Skill (Р0–Р23, пункты Р19) не перенумеровывать.

### Р1. Старт сессии — Правило Феникса
Триггер: первое сообщение в Claude Project, мастер-промпт которого несёт блок Второго мозга (раздел «Р2. Эталонный блок Второго мозга в мастер-промпте»). Сначала старт, потом ответ на сообщение. Вне Project (Cowork, Claude Code) старт автоматически не применяется — раздел «Р16. Работа вне Claude Project и регистрация обязательств».

Старт доказывает чтение канона одной строкой с величинами, которые нельзя списать с текста промпта или Skill (blob sha прочитанных файлов), и замолкает.

`meta/PENDING_RULES.md` читается первым действием любой repo-сессии, не только старта в Project (бюджет чтения 2 048 Б). Строка PENDING_RULES с полем «кто подтвердил: Андрей» действует как положение Skill до внесения в него; при расхождении со Skill действует строка.

Тег, носитель и папку проекта называет блок мастер-промпта. При расхождении блока с `registry/projects.md` прав реестр; расхождение называется в строке старта.

Проект в repo (`projects/<папка>/`):
1. Одним чтением — `meta/PENDING_RULES.md` и `projects/<папка>/STATE.md`. Чем читать (клон или Git-канал) — Skill `second-brain-git`, разделы «Чем читать» и «Старт repo-сессии»; выбранный путь назвать одной строкой.
2. Вывести ровно одну строку:
   `Контекст загружен: <ТЕГ> | repo: STATE <sha7>, PENDING_RULES <sha7> | Следующий шаг: <из STATE.md>`
   ТЕГ — имя проекта прописными, как в весах `registry/projects.md` (WB_UE, N8N, WB_REVIEWS); sha7 — первые 7 знаков blob sha прочитанного файла.
3. Молчать, ждать вопроса. У файлов repo нет полей LAST_UPDATED и LAST_READ, свежесть — git log.

Лаборатория в repo (`labs/<папка>/`):
1. Одним чтением — `meta/PENDING_RULES.md` и `labs/<папка>/INDEX.md`. Строка задачи с пометкой «активная эстафета» значит: в конце файла задачи лежит блок `## ЭСТАФЕТА`; он читается при взятии задачи, проверка свежести и расшифровка — Skill `context-handoff`, раздел «Подхват в новой сессии».
2. Вывести ровно одну строку:
   `Контекст загружен: <ТЕГ> | repo: INDEX <sha7>, PENDING_RULES <sha7> | Задач: <число строк таблицы задач>`
3. Молчать, ждать вопроса.

Добавки проекта: блок мастер-промпта может добавить к старту свои шаги (например, чтение CORE по манифесту) и свой формат строки. Добавка выполняется после шагов выше; формат строки, заданный промптом, выводится вместо строки выше. Чтение по шагам и добавкам исполняется целиком до ответа на задачу из сообщения.

Проект в Docs (изолированный контур):
1. Прочитать INDEX проекта через gdocs-read — только Зону А, до разделителя ЗОНА Б, диапазоном строк (`fromLine`/`toLine`, Skill `google-drive-docs`, раздел «gdocs-read»); полнота среза доказывается строкой SENTINEL внутри него, а не числом.
2. Вывести одну строку: «Контекст загружен: [проект] | [LAST_UPDATED] | Следующий шаг: [шаг]». LAST_UPDATED старше 7 дней — добавить «⚠️ Данные не обновлялись 7+ дней».
3. Обновить LAST_READ_BY_CLAUDE через gdocs-replace.
4. Молчать, ждать вопроса.

Проверка: строка одна. В repo — в строке sha обоих прочитанных файлов; полнота чтения — по Skill `second-brain-git`, разделы «Контракт ответа читающих воркфлоу» (returned равен requested, missing пуст) и «Обрезанный вывод» («не прочитано»). Для Docs — gdocs-replace вернул `occurrencesChanged=1` и строка LAST_READ_BY_CLAUDE видна при обратном чтении.

### Р6. Захват
Триггер: любой ответ, в разговоре которого появилось то, чего ещё нет в каноне проекта: задача, идея, вопрос без ответа, решение, баг, результат, внешнее событие.

1. В конце того же ответа, не прерывая работу, одним блоком:
   ```
   [ЗАХВАЧЕНО]
   → [<ТЕГ>] <Тип>: <текст>
   ```
2. Типы: Задача, Идея, Вопрос, Решение (с датой), Баг (симптом | причина, если известна), Результат (что исправлено → что получилось), Событие (внешнее: тариф, API, квота, версия, поведение платформы).
3. Тег — проект, которому факт принадлежит, а не проект сессии. Баг n8n как платформы (узел, движок, SDK, MCP) — тег [N8N], адрес `projects/n8n/STATE.md`. Баг бизнес-воркфлоу другого проекта — тег того проекта и строка «⚡ Это затрагивает [ПРОЕКТ]: [что]» (раздел «Р9. Взаимосвязи и поиск документов»). Проект неясен — `[?] Не классифицировано: <текст>`.
4. Баг — сразу предложить записать. После трёх и более захватов подряд и в конце сессии с захватами — предложить !save.
5. Трение: когда правило, процедура или инструмент мешают результату, сессия вправе одной строкой «Трение: <что мешает> → <чему мешает>» — без разбора, вопроса и захвата; это не обязанность. В канон — захватом типа Идея с тегом [SYS], когда Андрей подхватил.

Находка при проверке релевантности Главной цели: кандидат в БЛОКЕРы фиксируется `[ЗАХВАЧЕНО → НОВЫЙ БЛОКЕР?: ...]`, статус — при следующем прямом контакте с Андреем, до решения — задача в `labs/sys/` с меткой «кандидат в БЛОКЕРы»; потеря данных прямо сейчас — сообщить немедленно, регистрация задним числом; мелочь — `[ЗАХВАЧЕНО → ...]` и при надобности задача в `labs/sys/`.

Три случая записываются тем шагом, на котором возникли, не ждут !save:
6. Смена предмета или цели работы посреди проекта — захват типа Решение, вопрос Андрею и запись в журнал решений проекта (Skill `second-brain-git`, раздел «Форма записи в журнал») до продолжения работы по-новому. Частное решение, принятое сессией «по аналогии» с прежним без вопроса, помечается в записи словами «по аналогии, владельцу не задано».
7. Созданный сессией объект, нужный после неё, получает адрес в каноне тем же шагом, которым создан; в ответе называется адрес.

   | Что создано | Куда тем же шагом |
   |---|---|
   | документ или таблица Google | строка в `registry/documents.md`; право — раздел «Р13. Права доступа» |
   | файл — пакет вопросов, отчёт, скрипт, выгрузка, данные — в рабочей папке сессии или на компьютере Андрея | репозиторий, по `second-brain-git`; файл, который публичному репозиторию запрещён (Skill `second-brain-git`, «Стоп-правила», раздел «Носитель и данные»), — Google Drive и строка в `registry/documents.md` |
   | воркфлоу n8n | строка в каноне своего проекта: ID, имя, назначение, опубликован или нет (repo-проект — `STATE.md`, маршрут — Skill `second-brain-git`, раздел «Save по проекту»; проект в Docs — его INDEX по разделу «Р7. !save»); паспорт и строка PASSPORT в описании воркфлоу — Skill `n8n-workflow-passport` |

8. Исполненная работа закрывает запись, которая её ждала, тем же шагом: строку «ждёт» в `STATE.md`, задачу лаборатории, позицию очереди (новым словом статуса), пометку «ждёт» в черновике; в ответе — адрес закрытой записи. Закрывается каждое упоминание того же дела: другие строки того же файла («Следующий шаг», строка ⚡, прежний «Итог»), каждая открытая позиция очереди, чей текст вошёл в тот же архив Skill, статус Skill в карте каталога `meta/SKILLS_MAP.md`; их находят поиском по имени дела в том же файле и по имени Skill в очереди и карте.
9. Факт, полезный соседнему проекту, — захват с тегом соседа и тем же шагом, на котором узнан, не дожидаясь !save, одна строка в `STATE.md` соседа «⚡ Это затрагивает <сосед>: что, где проверить»; адрес и форма строки — Skill `second-brain-git`, раздел «Факт соседнему проекту»; образец — `meta/DECLARATION_COMMON.md`, раздел 4.

Проверка: захват виден в том же ответе, где возник; у каждой строки тег и тип. Смена цели — запись в журнале названа номером до продолжения работы; созданный объект — адрес назван в ответе, строка в `registry/documents.md`, файл в репозитории или строка в каноне проекта видны обратным чтением.

### Р7. !save
Что, когда и куда записывается по !save и с чьего согласия решает этот раздел; как физически писать — Skill носителя (`second-brain-git` для репозитория, `google-drive-docs` для Docs). Триггер: команда !save; согласие Андрея на предложенный !save.

0. До первой записи прочитать файлы строки таблицы «По событию» `core/MANIFEST.md`, которая называет вид записи этого !save (запись в файлы репозитория; запись в INDEX Google Docs или в INBOX; запись в CHANGELOG — шаг 10).
1. Показать список [ЗАХВАЧЕНО] сессии одним блоком и сразу записывать, без ожидания: сама команда !save — согласие на запись этого списка.

### Р10. Воркфлоу n8n — полномочия
Вопрос до вызова и его форма — «Стоп-правила», раздел «Р10. Воркфлоу n8n — вопрос до вызова», и раздел «Форма вопроса, требующего «да» Андрея».
1. При отладке — сначала предложить копию воркфлоу. В вопросе о правке воркфлоу предложить сохранить копию перед правкой и назвать запись решения в паспорт после неё.
2. После правки — ADR в паспорт воркфлоу (Skill `n8n-workflow-passport`). Механика (параметры, ключи, шаблоны, ошибки, сбросы настроек при `update_workflow`) — Skill `n8n-engineering-manual`.

Исключения — повторного «да» не ждать:
3. Пакет правок, на который Андрей дал одно разрешение и который записан списком задач в `STATE.md` или `LOG.md` проекта: в пределах списка узел и изменение называются вслух; правка вне списка — по общему правилу. Граница пакета, заданного классом объектов, — признак, которого нет у чужих объектов (приставка проекта в имени плюс строка в описи пакета).
4. Андрей в этой задаче поручил решать самой («реши сам», «действуй автономно») — в пределах задачи обратимые правки воркфлоу без отдельного «да» (обратимое — снятие с публикации, правка с сохранённой копией прежней версии, новый воркфлоу-инструмент); необратимые перечисляются в отчёте.

Проверка: «да» Андрея в чате до вызова, либо задача названа в записанном пакете (адрес записи; у пакета по классу — признак границы), либо правка обратима и сделана по поручению «реши сам» в этой задаче — слова поручения названы, необратимое перечислено в отчёте.

### Форма вопроса, требующего «да» Андрея
О воркфлоу, о записи, об удалении, о правке документа — три строки простыми словами, коды и номера пунктов только в скобках после слов:
```
ВОПРОС: что меняется.
ЕСЛИ «ДА»: ближайшее наблюдаемое последствие для работы Андрея.
ЕСЛИ «НЕТ»: что останется как есть и чем это грозит.
```
Больше трёх вопросов — делятся на части; следующая часть — после ответа на предыдущую.

Проверка: в чате до меняющего вызова видны вопрос в этой форме и «да» Андрея, либо назван адрес записанного пакета разрешения.

### Р13. Права доступа
Триггер: перед действием, которое требует «да» Андрея или его рук (удаление данных, изменение воркфлоу n8n, структуры INDEX или мастер-промпта, правка Skill, действие, затрагивающее больше трёх узлов), перед записью, право на которую сессия не помнит, и перед выдачей наряда.

Сессия действует сама там, где ошибка откатывается тем же инструментом и не задевает чужую работу; где откат невозможен или дорог — «да» Андрея, видимое до действия.

- **Claude автономно:** создать INDEX / папку проекта; зарегистрировать проект в `registry/projects.md` и ID его INDEX в `registry/documents.md`; зарегистрировать в `registry/documents.md` документ или таблицу, созданные в сессии; подготовить мастер-промпт; записать захваты при !save; обновить LAST_UPDATED / LAST_READ_BY_CLAUDE / STATE.md; закрытую задачу Docs-проекта перенести в АРХИВ ЗАДАЧ; записать баг / прогресс; дописать позицию в `registry/maintenance-queue.md`.
- **Claude после «да»:** изменение воркфлоу n8n (исключения — раздел «Р10. Воркфлоу n8n — полномочия»); удаление данных из INDEX и repo, в том числе закрытие задачи лаборатории (удаление файла задачи и строки в `INDEX.md` одним вызовом); изменение структуры INDEX или мастер-промпта (отдельным действием, текстом «было → стало»); действие, затрагивающее больше трёх узлов.
- **Андрей обязан (блокирует систему):** создать Claude Project и прислать URL; создать ключ доступа (credential) в редакторе n8n — привязывает ключ к узлам сессия сама, `setNodeCredential` (Skill `n8n-engineering-manual`, раздел «Ключи доступа»); решить об удалении; подтвердить структурные изменения; перезалить Skill; сохранить старый текст мастер-промпта файлом до вставки нового.
- **Андрей может безопасно:** executions и ручные запуски в n8n; данные в строках Sheets.
- **Андрей не должен:** менять структуру INDEX напрямую; переименовывать или удалять воркфлоу без согласования; менять колонки Sheets; править середину функций Apps Script (только полная замена).

В `meta/PENDING_RULES.md` пишется только решение журнала, подтверждённое Андреем в чате; вычищает файл Андрей при правке Skill (транспорт — Skill `second-brain-git`).

Правка Skill действует только после перезаливки: живой Skill — в Customize → Skills; многофайловый Skill (SKILL.md и references/) Андрей заливает zip-архивом там же. Правка Skill закрывается приёмкой по снимку `/mnt/skills/` в той сессии, которая на него опирается — по якорю правки или побайтово; механика приёмки, зеркала и сверки перед заливкой — Skill `second-brain-git`, раздел «Правка Skill: приёмка, зеркало, копии, архив для заливки».

Проверка: перед действием из строки «после да» в чате видно «да» Андрея или названо исключение (пакет — с адресом записи, «реши сам» — со словами поручения); вопрос в форме трёх строк, не больше трёх в сообщении.

### Р15. Провенанс и верификация — единый стандарт
Триггер: любое утверждение о состоянии системы; любая запись. Утверждение верно только для того чтения объекта, из которого оно взято. Ответ посредника годится, чтобы выбрать следующий шаг.

1. Каждое утверждение несёт метку происхождения: ПРОЧИТАНО В ЭТОЙ СЕССИИ (файл), ПРОЧИТАНО ПОСРЕДНИКОМ (кто и какой объект) или ВСПОМНЕНО. Решение цитируется вместе со статусом: отметка об отмене часто стоит в хвосте записи. Кто читал источник, тот и прав — независимо от роли в наряде и класса модели.
2. Слово Андрея «сделал», «удалил», «внёс» — ВСПОМНЕНО; до чтения объекта задача открыта, в ответе — «по словам Андрея, объект не прочитан».
2а. Пустое чтение (пустота без ошибки) — стоп и сообщение; ответа по памяти вместо прочитанного нет.
3. Что считается чтением объекта — по виду утверждения:

| Вид утверждения | Что прочитать до решения или до записи в канон | Что чтением не считается |
|---|---|---|

| **Идентификатор, число или дата в канон; число или вердикт сверки о живом объекте** | раздел «Идентификатор, число или дата в канон» | — |

Поиск документа по просьбе Андрея — раздел «Р9. Взаимосвязи и поиск документов».
5. Правка объекта — с чтения его живой версии в собственном носителе: исходник страницы-артефакта — сам опубликованный артефакт (инструмент артефактов, action read); локальный файл сессии — прошлое чтение.
6. Опровергнутая причина сохраняется: в файлах канона, которые правятся на месте, — рядом с исправлением блоком ИСТОРИЯ ДИАГНОЗА (`core/R-06a.md`, пункт 0.4.1); в Skill — строкой «не путать: X — на деле Y».
7. Запись верифицируется только независимым перечитыванием, один стандарт для обоих носителей: Docs — gdocs-read, счёт вхождений якоря или совпадение текста; repo — Skill `second-brain-git`, раздел «Доказательство записи» (в среде с клоном `git fetch` и `git hash-object`, без клона — один вызов Git Read Lines с pattern по первой строке записанного); blob sha записанного равен sha намеренного. `success: true`, `occurrencesChanged`, номер исполнения, ответ инструмента — сигналы, не доказательства.

Проверка: в отчёте о записи — файл, способ обратного чтения и совпавшая величина. Каждая строка о состоянии и каждое причинное объяснение в записанном тексте несут способ проверки или слово «Гипотеза»; каждый внешний факт — первоисточник с датой чтения или «Гипотеза».

### Идентификатор, число или дата в канон
Триггер: запись в канон (файл repo, INDEX, реестр, позиция очереди, журнал) идентификатора, числа или даты: ID, sha, номера исполнения, порога, счёта, размера, даты записи; числа или вердикта сверки, аудита о живом объекте («держится», «совпадает», «N из M»); числа в критерий приёмки, контракт работы или ожидаемый результат проверки.

| Что пишется | Откуда берётся | Что источником не считается |
|---|---|---|
| Идентификатор, число или дата — ID, sha, номер исполнения, порог, счёт, дата | выдача объекта или поиска этой сессии — копированием | память, перепечатка из другого текста, счёт в уме |
| Число в критерии приёмки, в контракте работы, в ожидаемом результате проверки | чтение объекта до того, как критерий записан; рядом называется чтение, из которого число взято | выписанное заранее по памяти или счётом в уме |
| Дата записи — в журнале, в имени файла, в поле «создан» | инструмент текущего времени, дата, которую харнесс сообщил в контексте сессии, или ответ инструмента (время старта исполнения n8n, createdTime ответа Drive) | память модели |
| Число или вердикт о живом объекте, который меняется и без этой сессии: файл или документ, в который пишут и другие; лист, книга, кабинет площадки, выгрузка (размер, число строк, число записей, счёт карточек, «держится», «совпадает») | чтение — и вместе с числом две отметки. Версия этого чтения: blob sha для файла репозитория, checkSum ответа gdocs-read для документа Google; у листа, кабинета или выгрузки без версии — время снимка (когда объект прочитан; когда обновлён лист-снимок, из которого читали). Определение счёта: что считали, по какой колонке и какому признаку | число без отметки версии или времени снимка; число без определения счёта |

1. Расхождение двух чисел с разным определением или неизвестным порядком снимков пишется как есть — «снимок до записи такой-то», «пересчёт по определению этой сессии»; прежнее число без записанного определения этим пересчётом не опровергается и не подтверждается.
2. Вердикт сверки по снимку пишется со словами «в снимке <время>»: «держится» значит «держится в снимке».
3. Критерий приёмки по числу о живом файле — соотношение на свежем чтении в момент приёмки («зона не выросла», «в файл добавилась ровно одна запись»); абсолютное число — только база для сравнения.

Проверка: записанное совпадает с выдачей объекта, поиска или инструмента времени этой сессии; у числа о живом объекте — версия или время снимка и определение счёта; сравнение названо сравнением только при одном определении; у критерия — соотношение.

### Р16. Работа вне Claude Project и регистрация обязательств
Триггер: сессия в Cowork, Claude Code или GitHub Actions работает над проектом системы; либо любая сессия вскрыла факт, требующий правки CORE, задачи `labs/sys/`, INDEX, Skill или мастер-промпта. Обязательство существует для системы только записанным в канон: что сессия может исправить — исправляет до конца сессии; что не может — регистрирует позицией, которую прочтёт харвест.
1. Старт (раздел «Р1. Старт сессии — Правило Феникса») вне Project автоматически не срабатывает. Эстафета (Skill `context-handoff`) — ручной мост: пишет эстафету в канон, где идёт работа (Зона А INDEX Docs-проекта; проект в repo — `STATE.md`; лаборатория — конец файла задачи и пометка в её строке `INDEX.md`; носители — Skill `context-handoff`, раздел «Границы»), но автоматического старта не даёт.
2. Запись доступна из любой среды: git-канал и gdocs-* вызываются по HTTP, исполняет сервер n8n.
3. Правка, которую сессия может сделать (CORE, задачи `labs/sys/`, INDEX Docs-проектов, файлы repo), — до конца сессии, по правильному якорю, с верификацией (раздел «Р15. Провенанс и верификация — единый стандарт»). Зона А документа SYS_INDEX живёт в `labs/sys/`.
4. Правка, которую сессия не может сделать (Skill, мастер-промпт — аккаунтный слой, правит только Андрей), — позиция в `registry/maintenance-queue.md` через Git Append File (запасной путь — Git Append; Skill `second-brain-git`, разделы «Чем писать», «Git Append File»): № | что внести | куда | источник | дата смерти | статус. Номер позиции, статус и проверка после записи — Skill `second-brain-git`, «Стоп-правила», раздел «Очередь», и «Как делать», разделы «Git Append File», «Статус позиции Очереди». Текст позиции — без внутренних переводов строки. Очередь читает харвест.
5. Пересказ в чате и текст эстафеты регистрацией не являются; харвест внешних чатов не сканирует — незарегистрированное обязательство для системы не существует.

Проверка: позиция видна при обратном чтении очереди (Skill `second-brain-git`, раздел «Доказательство записи»; без клона — Git Read Lines с pattern по номеру позиции); в ответе назван её номер.

### Р21. Чтение через посредника
Триггер: перед вызовом инструмента, чей ответ нельзя сузить до попадания в контекст: `get_workflow_details` воркфлоу целиком, когда сумма узлов всех воркфлоу, которые задача требует прочитать целиком, больше 100; выдача исполнения грязного воркфлоу; длинная выдача внешнего API. То же — когда от справки Skill, архива или большого файла нужен ответ на вопрос, а не текст. Решение — до вызова, по одному признаку: можно ли сузить объект до попадания в контекст.
1. Файл, любой, сужает сама сессия по правилу «чем читать» (Skill `second-brain-git`, раздел «Чем читать»; в среде с клоном `grep` и `sed`).
2. Ответ инструмента, который приходит целиком и сужению не поддаётся, — посреднику.
3. Порог для воркфлоу: описание воркфлоу целиком — посреднику, только если сумма узлов всех воркфлоу, которые задача требует прочитать целиком, больше 100; до 100 включительно сессия читает сама. Число узлов каждого воркфлоу — до чтения: поле `nodeCount` в ответе `get_workflow_details` с `detailLevel: "execution"` (ответ около тысячи токенов, без узлов и кода).
4. Воркфлоу, правку которого Андрей поручил в этой задаче или которая стоит в записанном пакете разрешения (раздел «Р10. Воркфлоу n8n — полномочия»), сессия читает сама. Диагностика выше порога — сначала ответ посредника, затем чтение для правки.

Задание посреднику — вопрос, а не файл; вернуть ответ, а не текст:
5. Задание посреднику-ревизору (аудит, приёмка, ревизия справочника) несёт строку: «прежде чем назвать значение дефектом, назови, что это за поле, в каком режиме операции и таблицы оно используется и кто его заполняет».
6. При каждом факте ответа — адрес доказательства: для ответа инструмента — имя узла и путь в JSON или цитата до 80 знаков; для файла — путь и номер строки. Ничего не нашёл — NOT_FOUND и перечень, где искал.
7. Вопросы одному посреднику — пакетом.
8. Модель посредника по умолчанию — среднего класса.

Проверка: ответ посредника помечен ПРОЧИТАНО ПОСРЕДНИКОМ с именем объекта; он направляет следующий шаг. В канон (файл repo, INDEX, реестр, позицию очереди, запись журнала) — только после того, как сессия прочитала сама адрес доказательства (одну строку файла, одно поле ответа); тогда метка становится ПРОЧИТАНО В ЭТОЙ СЕССИИ.

### Р19. Метод проектирования
Триггер: Андрей просит спроектировать новый Skill, протокол, структуру документа или решение архитектурного вопроса — до первого варианта; решается судьба действующей процедуры, монитора или журнала (пункт 3); строится проверка, приёмка, аудит или замер (разделы «9. Замер до и после», «Проверка, которая не может соврать», «15. Критерий приёмки не подменяют задним числом»); у одних данных две копии и больше (пункт 19). Пункты 1–8 — по порядку начала работы; остальные — на всём протяжении проектирования.

1. **Квитанция рамки.** До проектирования разложить сказанное Андреем на два списка и выдать в ответе: ЦЕЛИ — чего он хочет добиться (не оспариваются); ГИПОТЕЗЫ О РЕШЕНИИ — перечисленные поля, выбранная форма, названный инструмент, названный носитель; по каждой — «оставляю» (со словом проверки) либо «предлагаю снять, потому что».
2. **Сцепка двух ТРИЗ.** Обратный ТРИЗ выдаёт ранжированный список из двух–четырёх слабых мест; каждое переформулируется как техническое или физическое противоречие и разрешается прямым ТРИЗ; порядок обязателен. Проверка реальностью: по каждой стратегии саботажа ответить, делает ли это система уже сейчас, с объектом или прецедентом; «уже делаем» — в работу первыми.
3. **Пять ворот сущности знания** — для любого документа, корпуса, реестра или журнала до постройки:
   1. ЧИТАТЕЛЬ — кто конкретно это прочитает.
   2. ТРИГГЕР — в какой момент, по какому слову или событию; при ситуационном триггере обязателен словесный дубль. Для правила — и «где»: правило стоит там, где сессия находится в момент его действия — в файле, который в этот момент уже открыт, в строке инструмента `registry/tools.md`, в контракте вызова или в скрипте-проверке; правило, чей момент наступает до открытия файла действия и чьё нарушение меняет работающую систему, — в постоянном слое Skill со стопом в начале файла действия. Места вне Skill названы шагом С4а `meta/PROTOCOL_knowledge-synthesis.md`.
   3. ЦЕЛОСТНОСТЬ ЧТЕНИЯ — чем доказывается, что текст доехал целиком и актуальным; у структур, которые только дописываются, ценность растёт к хвосту, а режется тоже хвост.
   4. ПИСАТЕЛЬ — кто пишет, в какой момент и что означает его молчание.
   5. НАБЛЮДАЕМЫЙ ОБЪЕКТ — одно число или один файл, по которому Андрей за тридцать секунд отличает живое от мёртвого.
   Ворота действуют и после постройки: у живой сущности пропал читатель — по умолчанию снять; снимая процедуру, до снятия перечислить объекты, у которых она была единственным читателем, и по каждому вердикт: снять вместе с ней, передать названному читателю или оставить с причиной. Вместе с воротами проверяются два признака мёртвой процедуры: в ней нет шага, ради которого её запускают; у правила не назван исполнитель — кто, в какой момент, каким действием.
4. **Поиск прецедента.** Каждый предлагаемый механизм называет прецедент или существующий инструмент, из которого выведен; изобретённое с нуля заявляется вслух. Порядок поиска: оглавление всех журналов repo-проектов, затем нужные записи по номеру (Skill `second-brain-git`, раздел «Чем читать»): в среде с клоном — `grep -nE '^(Р|Т)-[0-9]+ \|' projects/*/LOG.md projects/*/LOG_ARCHIVE.md`; без клона — Git Read Lines с тем же шаблоном, один вызов на журнал. У Docs-проекта журнал решений — раздел РЕШЕНИЯ Зоны Б INDEX.
5. **Механизм контроля до объявления о запуске:** не «воркфлоу создан», а «в отчёте появилось число»; не «Skill развёрнут», а «гейт сработал, и это видно в объекте».
6. **Форма рекомендации.** Одна рекомендация — с обоснованием, перечнем отвергнутых альтернатив и причин отказа, критерием приёмки.
7. **Отчёт из объектов.** Отчёт исполнителя — из свежих чтений объектов, а не из намерений; каждая запись проверяется обратным чтением немедленно, а не в конце серии.
8. **Связь с журналом решений.** При закрытии проектирования — запись Р в журнал проекта (Skill `second-brain-git`, раздел «Форма записи в журнал»): вопрос, что принято, почему, что отвергнуто и почему; хотя бы одна отвергнутая альтернатива обязательна.
10. **Выборка.** Сначала разведка — какие схемы, формы, случаи встречаются в целом; потом метод.
11. **Правило переживает свою причину.** Кто устраняет причину порога, запрета или обходного правила (ограничение старого инструмента, незаконченная работа, дефект), тем же действием снимает компенсирующий запрет — в коде, в Skill, в протоколе, в каноне проекта — или записывает его снятие в план с адресом. Запрет ради такой причины записывается с условием снятия: событием или датой и действием. С новым инструментом пересматриваются правила, державшиеся на старом; отмена правила в одном носителе (CORE) не отменяет копий в протоколах и Skills — их ищут и снимают тем же действием. Когда отменяется метод диагностики, тем же действием находятся все выводы, полученные им, и помечаются «требует перепроверки».
12. **Сомнительный случай.** Случай, подходящий и под строгое, и под слабое правило, относят под слабое; строгое — только при объектном основании (находка при сомнении — ветка «кандидат», а не «БЛОКЕР»).
13. **Единица контроля** — объект, к которому предъявляется требование, а не его отражение в справочнике (декларация — для каждой карточки на площадке, а не для строки справочника; признак «не продаётся» вычисляется из списков карточек Ozon и WB, а не ставится руками).
18. **Защита изоляцией и наименьшими правами** — технически: отдельная учётная запись без пароля и без sudo, повышенные права — только у нескольких названных обёрток, сервисный аккаунт с доступом только к своей папке, воркфлоу-инструмент без узла удаления. Как это устроено в n8n — Skill `n8n-engineering-manual`, раздел «Ключи и периметр».
19. **Один источник истины до правки и размножения.** Две копии и больше одних данных (ручная история и выгрузка, книга и её хаб, папка на двух дисках) разошлись или готовится их правка или размножение — опись копий → устройство источника → правка только в источнике → размножение из него. Ручная копия при появлении источника замораживается, её читатели тем же действием переключаются на источник. Какой файл источник у конкретных данных — канон их проекта.

Проверка: в ответе квитанция рамки; при закрытии — запись Р с отвергнутой альтернативой; при снятии процедуры — перечень объектов-читателей с вердиктом; у каждой меры — замер «до» или «не измерено»; у приёмки названо, кто составил вопросы, а правки после акта приёмки проверены приёмщиком повторно или названы непроверенными; при двух копиях — источник истины и что сделано с остальными.

### 9. Замер до и после
1. Каждая мера оценивается по объекту до и после; чего не измерили — «не измерено». Замер — ради решения, а не ради прибора.
2. Прежде чем читать объект после правки, записать ожидаемый результат; неоправдавшийся прогноз — сама находка. Прогноз выводится из требования чтением объектов до прогона и сверяется с фактом по каждому объекту, а не по сумме.
3. База замера «до» снимается до всей серии собственных изменений, а не с её середины.
4. Посылка структурной переделки — что переделываемое устройство вредит — проверяется пробой до переделки.

### Проверка, которая не может соврать
Проверка, по итогу которой принимается решение (приёмка, монитор, аудит, сверка, скан, проба на живом объекте), строится так, чтобы итог различал исправный объект и сломанный: «всё сходится» нельзя получить от сломанного объекта, «дефект» — от исправного, «ничего не найдено» — от сломанного детектора. Случай, которого нет ниже, решается вопросом: какой итог дала бы проверка на сломанном объекте и какой — на исправном; совпали — проверка не годится.
- **а. Эталон — путём, независимым от проверяемого.** Длина, сумма или прошлое чтение тем же инструментом обрежется вместе с ним (частный случай — Skill `second-brain-git`, разделы «Контракт ответа читающих воркфлоу» и «Обрезанный вывод»). Ожидаемые ответы приёмки — из источника, который проверяемая система не строила (оглавление книги, а не таблицы индекса; значения, собранные до теста вручную по каждому полю с адресом источника). Вопросы приёмки почти повторяют то, по чему система строилась (заголовки разделов, имена полей), — отчёт называет планку лёгкой. Новая версия системы проверяется по первоисточнику — отчёту площадки, кабинету, документу; расхождение со старой допустимо, если каждое объяснено. Мера «верно» при сверке с площадкой задаётся до сверки — допустимый зазор по каждому виду величины, — у каждого зазора в итоге названа причина.
- **б. Отчёт называет охват:** какие объекты и поля сверены, сколько их, откуда взят их список. Колонки разного смысла, совпавшие целиком, — сама находка. Выборка приёмки составляется по объекту: в неё входит главный случай, ради которого система построена, и классы, которые реально есть в объекте по его состоянию после прогона, а не придуманные до него.
- **в. Замер, от которого зависит следующая операция** (счёт единиц, байт, границ разреза), делает сохранённый скрипт — файл, адрес которого стоит в отчёте; второй исполнитель запускает тот же код.
- **г. Вопросы приёмки составляет не исполнитель** (список проверяемых утверждений, вопросы приёмочного теста, правила счёта для сверки): Андрей, приёмщик или другой субагент, не видевший построения; исполнитель передаёт ему цель и объект, но не свои вопросы и отчёты. Приёмку, закрывающую фазу или проект, проводит отдельный исполнитель, который работу не делал, — субагент сильного класса, получивший утверждения проверяемыми фразами и задачу опровергнуть их по объекту (форма — Skill `avtopilot`, раздел «Ворота 5. Приёмка и отчёт»); для промежуточной приёмки внутри фазы отдельный приёмщик не обязателен, кроме режима автопилота. Файл с вопросами поведенческого теста — у Андрея или в документе Drive, не названном тестируемой сессии; тест поведения — в живом чате проекта, доказательство — лента вызовов (снимок экрана), история версий воркфлоу и история коммитов. Независимое мнение даёт исполнитель без построения и без той же рамки: субагент, получивший только объект и проверяемые утверждения, без мастер-промпта проекта и отчётов исполнителя; модель другого класса; Андрей. Второй экземпляр той же модели с тем же мастер-промптом называется «мнение той же модели». Где один объект проверяли проверяющие разных классов, находки объединяются.
- **д. Правку после акта приёмки** (исправление по находке, добавка «попутно», механическая замена путей, новая строка таблицы) возвращают тому же приёмщику (или другому, не делавшему работу) с разностью до и после; до этой проверки итог — «принято, кроме изменённого после приёмки: <что>, повторно не проверено». Для переносов документов — строже, кругами Контролёра: Skill `second-brain-git`, раздел «Приёмка переноса».
- **е. «Ничего не найдено» — положительным контролем.** Итог «находок 0» у скана, детектора или монитора принимается, только если в том же прогоне: детектор нашёл заранее подложенные известные случаи (синтетические — каждый вид того, что ищется, и случаи, которые он находить не должен); число просмотренных объектов сверено с независимым счётом (снимок реестра, ответ другого инструмента); границы метода названы в отчёте. Синтетическое значение собирается из частей во время прогона, чтобы целиком оно в коде детектора не лежало. Ветка тревоги, которая ни разу не срабатывала, проверяется подменой входа, а не ожиданием сбоя.
- **ж. Механическая сверка доказывает форму, а не смысл.** Работа, где модель или скрипт составляли или переписывали текст (карта, синтез, раскладка со вставками, описание объекта), принимается ещё и смысловой проверкой — верно ли утверждение по его источнику; кто её делает — по букве г. Отчёт называет, какая проверка что доказала.
- **з. Находка проверки — тоже вердикт:** прежде чем назвать пустое или странное значение дефектом, выяснить, что это за поле (ручная колонка, копия другой колонки, вычисляемое поле, параметр, не используемый в этом режиме) и кто его должен заполнять.
- **и. Проба на живом объекте — только когда её исход неизвестен.** Устройство платформы, которое пробой с известным исходом хотели подтвердить, записывается по документации с пометкой «на объекте не проверялось». Одна пробная запись в один объект со снимком до записи и чтением обратно перед массовой записью обязательна — Skill `n8n-engineering-manual`, раздел «Запись во внешний кабинет: режимы «проверка» и «боевой»».
- **к. Список к записи во внешний мир** (площадка, чужая система), построенный по правилу-гипотезе, калибруется по объекту — тому, что показывает интерфейс площадки (кабинет продавца), — до просьбы о разрешении; разрешение называет правило отбора и число; перед записью список пересчитывается по объекту.

### 15. Критерий приёмки не подменяют задним числом
Критерий приёмки или закрытия не выполнен — закрытие с прямо названным невыполненным условием; менять ли критерий, решает Андрей отдельно («критерий не выполнен, работа не принята, вопрос о пороге — Андрею»).

### 17. Массовую механическую работу делает скрипт, а не модель
1. Опись файлов Drive или PDF, нарезка текста на файлы, пересборка, перенос большого тела — скриптом.
2. Приёмка механического переноса — по мультимножеству непустых строк: каждая непустая строка исходника попала в результат ровно один раз и ни одной лишней (скрипт сравнивает счётчики строк исходника и результата; пустой остаток в обе стороны — перенос принят).
3. Исходник сравнивается с выходными текстами до записи (расхождение — отказ без записи) и повторно с файлами, перечитанными после записи, а не с разбиением в памяти скрипта.
4. Таблицу при нарезке и пересборке (таблицу маршрута, таблицу пунктов) переносит скрипт из прежней таблицы; приёмка сверяет каждую её ячейку с прежней.
5. Перенос, раскладка по файлам или правка формы (восстановление строк и заголовков без изменения слов) — скриптом отдельным шагом до правки смысла, принимается механически; правка смысла — следующим шагом по принятому результату. Приёмка правки формы — текст без пробельных знаков совпадает с исходником побайтно; приёмка переноса — по шагу 2. Смысловая правка, найденная внутри механического шага, откатывается из него и идёт своим шагом.
6. Текст, который скрипт вставляет от себя (строка триггера, ссылка, заголовок), копируется из правила-источника; приёмка сверяет вставку с источником.
7. Частные случаи: файлы репозитория — Skill `second-brain-git`, разделы «Правило происхождения текста» и «Маршрут доставки в main»; опись файлов Google Drive и цена полного текста PDF — Skill `google-drive-docs`, раздел «Опись и отбор файлов Drive» и «Стоп-правила», раздел «Пути чтения»; узлы воркфлоу n8n — Skill `n8n-engineering-manual`, «Стоп-правила», раздел «Запись и публикация воркфлоу» (неизменяемые узлы переносить скриптом из сохранённого JSON) и «Как делать», раздел «Порядок создания и правки».
8. Приёмку, закрывающую такую работу, строят и по разделу «Проверка, которая не может соврать».

### Р20. Гигиена каталога Skill и правило в код (16)
Триггер: планируется новый Skill; готовится правка Skill (синтез по `meta/PROTOCOL_knowledge-synthesis.md`, правка харвеста, позиция очереди); ревизия каталога (харвест, любое «не завести ли отдельный Skill»); повтор правила после внесения.
1. Правило, которое может исполнить инструмент (проверка в узле воркфлоу, отказ в коде, замок в Канале), переносят в код, а текст правила тем же действием убирают из Skill, протокола и промпта, оставляя строку-указатель на код, если без неё сессия сделает лишнее действие. Частный случай в n8n — Skill `n8n-engineering-manual`, «Стоп-правила», раздел «Неизвестное значение» (запрет записи — только в коде узла).
2. Цель — ноль неразобранных пересечений областей `description` между Skills, а не число Skills.
3. Рабочий вопрос при новом Skill или ревизии: «с каким существующим Skill пересекается это описание, и как сессия и Андрей различат триггер одного от триггера другого». Разрешённое пересечение без слияния: `second-brain-engineer` и `second-brain-git` — разделение по носителю и по вопросу («что и когда» — здесь, «как физически» — там).
4. Массовая правка описаний: единый каркас полей (что делает, когда читать, чего не делает) допустим; каждое описание называет свои слова-триггеры своими словами, каждый Skill — своим стилем.
5. Слова-триггеры описания покрывают и вопрос без действия — диагностику, на которую Андрей правки не просит («почему ноль», «отработал зелёным, а данных нет»).
6. Поведение после правки описаний принимается по разделу «Проверка, которая не может соврать», буква г: вопросы теста составляет не автор описаний, тест — в живом чате проекта.
7. Skill держит инструкции, нужные любой сессии любого проекта. Носитель особенностей объекта — канон проекта или лаборатории (STATE.md, PLAN.md, INDEX), паспорт воркфлоу, реестр `registry/` или файл кейсов `meta/CASES_*.md`; в Skill — не более указателя. Свойство платформы или внешнего инструмента, верное для любого экземпляра (движок n8n, Google Sheets, Telegram, git), особенностью не является и идёт в Skill; поведение API маркетплейса (Wildberries, Ozon) — в файл кейсов своего маркетплейса.
8. Каждая проверка, условие и счётчик в правке Skill называют то, что среда отдаёт: инструмент, который отдаёт поле; шаблон, где есть эти поля; журнал, по которому считает счётчик. Чего среда не даёт — переписать другим средством (другим инструментом; вопросом харвеста вместо счётчика) или назвать неисполнимым вслух.
9. Новое правило называет триггер и момент действия; они определяют место (раздел «Р19. Метод проектирования», пункт 3, ворота 2).

Проверка: карта каталога `meta/SKILLS_MAP.md` (шаг К1 `meta/PROTOCOL_knowledge-synthesis.md`) называет число неразобранных пересечений description — «ноль» либо список; правка Skill не называет особенностей конкретного объекта, кроме указателя на носитель; у каждой проверки и условия правки назван инструмент, шаблон или журнал.

### Р23. Скрипт по расписанию
Триггер: написать, поправить или принять скрипт, который запускается по расписанию без человека (cron, таймер systemd).
1. Каждый шаг проверяет свой результат; ошибка шага завершает скрипт ненулевым кодом возврата и текстом причины.
2. Что нужно скрипту, задаётся в самом скрипте или в строке расписания.
3. Результат проверяется по объекту: для бэкапа — размер и свежесть каждого файла дампа (каждой базы); целость и полнота — Skill `google-drive-docs`, раздел «Копия и бэкап».
4. Приёмка — искусственным сбоем: один шаг ломается намеренно, скрипт обязан завершиться ненулевым кодом и дать сигнал.

Проверка: в отчёте о приёмке — прогон с искусственным сбоем, его код возврата и проверка объекта результата (размер и дата каждого файла).

- Кнопка Save skill в Cowork для многофайлового Skill молча заменяет только SKILL.md, references/ остаются старыми — заливать zip через Customize → Skills.
- gdocs-append молча кладёт текст в конец документа = Зона Б, невидимую на старте — открытую задачу писать gdocs-replace по якорю в Зону А.
- Инструменты записи Docs шапку INDEX не трогают: LAST_UPDATED остаётся старым — обновлять отдельным вызовом.
- Внутренний перевод строки в тексте позиции `registry/maintenance-queue.md` молча разрывает строку таблицы: «Дата смерти» и «Статус» уезжают на другую физическую строку, харвест видит позицию без даты смерти — проверять обратным чтением строки.
- Drive и вставка в чат молча режут хвост старого мастер-промпта — проверять закрывающую строку, разделы, на которые ссылается текст, конец истории версий.
- Скрипт без проверки каждого шага возвращает успех (EXIT=0) при ошибке выгрузки — проверять объект результата.
- Скрипт разбора STATE.md решает по заголовку раздела и молча уводит в LOG.md и PLAN.md строки с открытым делом — сверять каждую переносимую строку по смыслу.
- Параллельная сессия может дописать STATE.md во время разбора — решения по снимку применять только при равном blob sha.
- Сломанный детектор и чистый объект дают одинаковый ноль — различает только известный случай, найденный в том же прогоне.
- Самоприёмка скрипта, сравнивающая разбиение с самим собой, сходится тождественно — сверять с файлами, перечитанными после записи.
- Скрипт, пересказывающий правило в своём коде, молча меняет смысл («больше трёх» → «три и более») — копировать вставку из источника и сверять с ним.
- Эталон, полученный тем же инструментом, что проверяется, обрезается вместе с ним — сравнение сходится на сломанном объекте.
- Число снимка, снятого до дозаписи, выглядит как пропажа; число по другому признаку — как противоречие — записывать время снимка и определение счёта.

## Куда писать результат
- Захваты — по разделу «Р7. !save»; созданный объект — по таблице раздела «Р6. Захват», шаг 7; исполненное — закрытием ждавшей записи тем же шагом.
- Решение проектирования — запись Р в журнал проекта; Docs-проект — раздел РЕШЕНИЯ Зоны Б.
- Отложенная правка Skill, мастер-промпта или CORE — позиция `registry/maintenance-queue.md` с датой смерти; прочая находка — задача в `labs/sys/`.
- Класс повторной ошибки — по адресу носителя (раздел «Р12. Гигиена Зоны А»).
- Урок о мастер-промпте — журнал своего проекта; метод — синтезом.
- Свойства серверных инструментов — `meta/CASES_server-tools.md`; поведение API маркетплейса — `meta/CASES_*.md` своего маркетплейса.
