# second-brain-engineer — чтение через посредника

Часть Skill second-brain-engineer. Читать: нужен ответ на вопрос от тяжёлого объекта или чтение поручается посреднику, целиком. Номера пунктов — прежние, общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md. Файл выделен из SKILL.md раскладкой по триггеру 2026-10-20: текст разделов перенесён без изменения.

## Р21. Чтение через посредника

**ТРИГГЕР.** Нужен ответ на вопрос, а не текст, и объект тяжёлый: ответ инструмента, справка Skill, архив, большой файл.

**ДЕЙСТВИЕ.** Выбор делается по одному признаку — можно ли сузить объект ДО попадания в контекст.
- Файл, любой — сужает сама сессия по правилу «чем читать» (second-brain-git 7.6; в среде с клоном grep и sed). Посредник на файле почти ничего не добавляет: замер Р-25 журнала `projects/kontext-reduktion/LOG.md` — посредники прочли 2 и 24 процента файлов, то есть сделали тот же срез, а выигрыш поверх среза съедается проверкой их ответа.
- Ответ инструмента, который приходит целиком и сужению не поддаётся — `get_workflow_details`, выдача грязного воркфлоу, длинная выдача внешнего API — отдаётся посреднику. Это его единственная ниша: замер Р-25 даёт 5,7 раза, и правилом 7.6 такой выигрыш недостижим.
- Правила, которые сессия исполняет САМА — контракт записи, контракт чтения, протокол, пункт Skill — посредником не читаются НИКОГДА. Исполнять можно только прочитанное; пересказ правила исполнением не является.

Заданием посреднику назначается вопрос, а не файл, и вменяется вернуть ответ, а не текст. Форма задания и ответа (Р-29 журнала `projects/kontext-reduktion/LOG.md`, правка 2026-10-09):
- Вопрос не несёт ожидаемого ответа и ожидаемой роли объекта: посредник, которому назвали ответ, ищет доводы за него, и проверка становится подтверждением подсказки. Аудит роли воркфлоу с подсказкой «читатель, подтверждено» подтвердил ровно подсказанное. Основание: 1 случай, корпус N8N_JOURNAL_2026, строка 2896 (урок У-22 журнала `projects/archivarius/LOG.md`, записи Р-6 и Р-8; решение Андрея 2026-10-13, запись Р-39).
- При каждом факте ответа стоит адрес доказательства: для ответа инструмента — имя узла и путь в JSON или цитата до 80 знаков; для файла — путь и номер строки. Ничего не нашёл — пишет NOT_FOUND и перечисляет, где искал. Замер Р-29: лёгкая модель без адреса дала 7 верных из 8 и одно ложное «не найдено», с адресом — 8 из 8 при том же расходе.
- Вопросы одному посреднику задаются пакетом: основная цена посредника — его собственный старт, второй вопрос в том же задании обошёлся примерно в 10 процентов первого.
- Модель посредника по умолчанию — среднего класса. Самая лёгкая — только для буквального извлечения (имена, поля, ID, значения) и только с адресом доказательства. Имена моделей здесь не пишутся: они меняются чаще Skill.
Расход посредника замеру не подлежит: харнесс сообщает его не всегда (Р-25), а приборы наблюдения вокруг работы не наращиваются.

**ПРОВЕРКА.** Ответ посредника помечается ПРОЧИТАНО ПОСРЕДНИКОМ с именем объекта (Р15); факт без адреса доказательства и без NOT_FOUND считается не полученным. В таком виде он годится, чтобы направить следующий шаг сессии. В канон — файл repo, INDEX, реестр, позицию очереди, запись журнала — он не пишется, пока сессия не прочитала источник сама; тогда пометка становится ПРОЧИТАНО В ЭТОЙ СЕССИИ. Правило «кто читал источник, тот и прав» посредник не отменяет: прав тот, кто читал, а не тот, кто пересказал.
