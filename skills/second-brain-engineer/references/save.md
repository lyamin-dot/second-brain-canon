# second-brain-engineer — !save и гигиена Зоны А

Часть Skill second-brain-engineer. Читать: перед командой !save в проекте любого носителя (repo-проект, лаборатория, Docs), перед записью в Зону А INDEX и при повторе бага или паттерна в проекте (Р12, правило второго раза), целиком. Номера пунктов общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md.

## Р7. !save

ЗАКОН РАЗДЕЛА. Этот раздел решает, что, когда и куда записывается по !save и с чьего согласия; как физически писать — Skill своего носителя (`second-brain-git` для репозитория, `google-drive-docs` для Docs), здесь только ссылки. Почему: пересказ механики записи здесь — второй носитель того же правила, и он расходится с первым при первой правке.

**ТРИГГЕР.** Команда !save; согласие Андрея на предложенный !save (Р6).
**ДЕЙСТВИЕ.**
0. До первой записи прочитать файлы строки таблицы «По событию» `core/MANIFEST.md`, которая называет вид записи этого !save (запись в файлы репозитория; запись в INDEX Google Docs или в INBOX; запись в CHANGELOG — пункт 10). CORE целиком для !save не читается (Р8); `meta/header.md` не читается (`second-brain-git` 7.2).
1. Показать список [ЗАХВАЧЕНО] сессии одним блоком и сразу записывать: сама команда — согласие на запись этого списка. Строку, которую Андрей вычеркнет после, отменить новой записью, а не правкой задним числом.
2. Для каждой строки определить проект (тег захвата) и его носитель (Р0). Строка чужого проекта пишется в канон того проекта, с пометкой «⚡» в записи.

Проект в repo и лаборатория — как писать, решает `second-brain-git`, здесь не пересказывается:
3. Проект в repo — `second-brain-git` 10 (маршрут по файлам — 10.3, транспорт — 8.3, порядок нескольких файлов — 8.6, форма записи журнала — 11). Лаборатория — `second-brain-git` 4б: задача заводится и закрывается вместе с правкой `INDEX.md`; закрытие — удаление файла задачи и её строки одним вызовом, архивного файла нет (4б.5, 4б.6); удаление — после «да» Андрея (Р13). До первой записи в сессии прочитать нужную часть того Skill целиком.
3а. STATE.md проекта в repo после записи проверяется на содержание тем же !save: `python3 meta/scripts/state_split.py check projects/<имя>/STATE.md` по клону; раздел, который скрипт отнёс к истории или к правилам, переносится той же сессией скриптом `meta/scripts/state_apply.py` (решения — файл JSON, приёмка по строкам внутри скрипта) — отработавшее блоком хроники в LOG.md, правила и реестры в PLAN.md. Что остаётся в STATE.md — `meta/CONTRACT_state-content.md`. Клон для проверки есть почти в любой среде: репозиторий публичный, клон анонимный, командная строка есть и в сессиях Claude Project (проверено 2026-10-27, `meta/CASES_sys-lab-closed-2026-10-27.md`, раздел t-repo-search-unknown-path); сессия без командной строки сравнивает byteLength STATE.md из ответа Канала с бюджетом 8 192 Б и при превышении пишет в отчёт о !save строку «STATE.md выше бюджета, разбор — следующей сессией с командной строкой» — это сигнал, а не проверка содержания (размер критерием не является, `second-brain-git` 5.5, пункт 3). Почему: правило разбора по ролям (`second-brain-git` 5.1, 5.5) стояло в Skill с 2026-09-10, а дописывающая сессия его не исполняла — STATE.md wb-ue дорос до 79 403 Б, после разбора 2026-10-26 за четыре дня снова вышел за бюджет; проверка держится, когда стоит в точке записи, а не там, где ей «правильно» жить (ретроспектива `meta/RETRO_skill-rework_2026-10-23.md`). Превышение бюджета после разбора — не дефект: вопрос к каждой строке один — изменит ли она действие следующей сессии.
4. Находка лаборатории без своей задачи — туда, куда велит мастер-промпт лаборатории (например, Зона Б её Docs-документа); промпт не велит — предложить Андрею завести задачу. Это решение о месте, а не механика записи, поэтому оно здесь.

Проект в Docs (изолированный контур):
5. Прочитать `registry/documents.md` для актуальных ID.
6. Маршрут записи: новая ОТКРЫТАЯ задача → gdocs-replace по якорю прямо в ОТКРЫТЫЕ ЗАДАЧИ Зоны А (не в хвост!); нарратив (РЕШЕНИЯ / ПРОГРЕСС / БАГИ / АРХИВ) → gdocs-append в Зону Б. gdocs-append кладёт в конец файла = Зона Б = невидимо на старте.
7. Закрытие задачи, стоящей в Зоне А, — тем же вызовом перенести строку в АРХИВ ЗАДАЧ. Закрытие фазы или решение уровня СЛЕДУЮЩЕГО ШАГА — тем же вызовом обновить строку СЛЕДУЮЩИЙ ШАГ Зоны А.
8. Обновить LAST_UPDATED отдельным вызовом: инструменты записи шапку не трогают.

Для всех носителей:
8а. Строка о состоянии («работает», «выключен», «внесено», «удалено») и причинное объяснение («потому что», «из-за») пишутся по Р15: со способом проверки (номер исполнения, поле, строка объекта; для причины — проба на объекте), иначе словом «Гипотеза (не проверена):». Задача, которую Андрей назвал сделанной, закрывается только по объекту, прочитанному в этой сессии; иначе она остаётся открытой с пометкой «по словам Андрея, объект не прочитан». Правило, причина и основание — Р15.
8б. Объект, созданный в этой сессии и ещё не получивший адреса в каноне, — документ или таблица Google без строки в `registry/documents.md`, файл, лежащий только в рабочей папке сессии или отправленный только в чат, воркфлоу n8n без строки в каноне своего проекта, — записать сейчас, куда велит таблица правила Р6. Опоздание до !save уже нарушение, но запись всё равно делается.
8в. Перед записью решения в журнал проекта (запись Р в LOG.md или раздел РЕШЕНИЯ) — поиск по оглавлению журнала того же проекта двумя-тремя словами темы (`second-brain-git` 7.6, строка «оглавление журнала»). Нашлась запись на ту же тему — новая запись называет её в поле «почему»: «заменяет Р-N» (тогда статус прежней меняется по `second-brain-git` 11.1) либо «противоречит Р-N — вопрос Андрею» (тогда запись не пишется до ответа). Ничего не нашлось — в отчёте о save одна строка «пересечений с журналом нет». Почему: без поиска уже решённые вопросы задаются повторно, а противоречащие решения стоят в журнале рядом. [основание: save-01]
8г. Ответ сессии, стоивший исследования (веб-поиск, разбор источников, сводка по многим файлам), подшивается в репозиторий только вместе с названным читателем — задачей или проектом, которые его используют: внешнее исследование — заметкой `wiki/notes/RES-NNN.md` по `wiki/DESIGN.md`, со ссылкой на заметку из задачи или журнала читателя. Читателя нет — ответ остаётся в чате, и это не потеря: корпус без читателя запрещён формулой Главной задачи (`labs/sys/t-knowledge-loop.md`). [основание: save-02]
9. После правки воркфлоу n8n в этой сессии — ADR в паспорт воркфлоу (Skill `n8n-workflow-passport`).
10. Оценить CHANGELOG: было ли ЗАПУЩЕНО / СОЗДАНО / ЗАКРЫТО что-то, что теперь работает и используется; отдельные задачи и баги не в счёт. Если да — прочитать `core/R-13.md` (строка «запись в CHANGELOG» таблицы «По событию» манифеста) и дописать через gdocs-append в Google Doc CHANGELOG (ID — `registry/documents.md`, строка CHANGELOG) по форме:
    ```
    ДАТА | СТАТУС | ПРОЕКТ | Что достигнуто
      Что изменилось: <в чём польза, что стало лучше>
      Темп: <быстро / нормально / медленно + почему>
    ```
    СТАТУС только из словаря ЗАПУЩЕНО / СОЗДАНО / ЗАКРЫТО (один; «СОЗДАНО+ЗАПУЩЕНО» = ЗАПУЩЕНО); ПРОЕКТ только из списка весов `registry/projects.md`, значения «A + B» запрещены, изолированные контуры с пометкой off-CORE. Значение вне словаря приводится к ближайшему, и это говорится вслух. Андрей ничего дополнительного не пишет.
11. Если сущность именованная и переиспользуемая (PROTOCOL_*, §-пункт Skill, воркфлоу n8n многократного применения) — строка в РЕЕСТР ПРОТОКОЛОВ — отдельный документ SYS_PROTOCOL_REGISTRY, ID в `registry/documents.md` (не SYS_INDEX: тот заморожен 2026-09-30, решение 2026-09-23 — Р-109 и Р-123 журнала `projects/git-migration/LOG.md`): протокол | дата рождения | применений | последнее применение | статус 🟢 доказан / 🟡 внедрён / 🔴 не используется.
12. Если сессия вскрыла факт, требующий правки CORE / задачи `labs/sys/` / Skill / мастер-промпта — Р16.

[основание: save-03]
**ПРОВЕРКА.** Каждая запись — независимым обратным чтением: repo — `second-brain-git` 8.1 (blob sha записанного равен намеренному); Docs — gdocs-read, якорь найден ровно один раз, содержимое совпадает. В отчёте названы файл, способ обратного чтения и совпавшая величина (Р15). `success: true` и exec-ID проверкой не являются.

## Р12. Гигиена Зоны А

**ТРИГГЕР.** Запись в Зону А INDEX проекта в Docs или наведение в ней порядка; повтор бага или паттерна в одном проекте (правило второго раза).
**ДЕЙСТВИЕ.**
Правило A — аккумуляторы вне hot-path: ИДЕИ, ВОПРОСЫ, объёмный каталог ИНСТРУМЕНТЫ живут в Зоне Б, в Зоне А — указатели. Почему: Зона А читается на каждом старте, и всё, что в ней лежит, оплачивается в каждой сессии.
Правило B — маршрутизация захвата: см. Р7 п.4.
Правило Навигации — поведенческие правила, специфичные для проекта, вносятся в Зону А INDEX как проектный контент, не в замороженный промпт.
Правило второго раза — рецидив бага или паттерна в одном проекте: записать КЛАСС ошибки — симптом, причина класса, превентив и момент, в который превентив должен сработать. Адрес по носителю: проект с INDEX в Google Docs — раздел НАКОПЛЕННЫЙ ОПЫТ → Ошибки и решения его Зоны Б; проект в репозитории — PLAN.md, потому что превентив есть правило проекта (Skill second-brain-git, пункт 10.3), и запись в LOG.md о том, почему правило введено; лаборатория — файл задачи, в которой ошибка повторилась, а если класс шире одной задачи — новая задача лаборатории; при закрытии такой задачи превентив переносится до удаления её файла — в правило (PLAN.md проекта или позиция очереди на правку Skill по Р16) либо в новую задачу лаборатории, если класс остаётся открытым, потому что файл закрытой задачи удаляется (`second-brain-git` 4б.6) и класс иначе остаётся только в истории коммитов. Класс шире одного проекта — по правилу Р16: задача в labs/sys/ или позиция очереди на правку Skill. [основание: save-04]
Записывая класс, проверить соседние объекты того же устройства — другие скрипты, воркфлоу или книги, построенные тем же способом, — на тот же механизм и записать результат по каждому в поле «превентив» той же записи класса (отдельного поля в шаблоне INDEX нет): тот же класс — превентив распространяется и на него; другой класс — так и записать, с тем, чем он отличается. Почему: класс — свойство устройства, а не одного объекта, и соседний объект того же устройства, скорее всего, несёт тот же дефект; запись «у соседа другой класс» не даёт следующей сессии лечить его тем же средством. [основание: save-05]
Карта воркфлоу проекта — снимок `registry/n8n-map.md` (состав, расписания, связи между воркфлоу), паспорта — `n8n-workflow-passport`. Отдельная карта SYSTEM-MAP не ведётся и не читается как действующая: PROTOCOL_system-map не действует с 2026-10-09 (`registry/protocols.md`, строка PROTOCOL_system-map); прежние карты и сам протокол — исторические источники.
**ПРОВЕРКА.** В Зоне А после записи нет полных списков ИДЕЙ и ВОПРОСОВ — только указатели; запись класса ошибки несёт все четыре поля, в поле «превентив» назван результат проверки соседних объектов того же устройства, и запись лежит по адресу своего носителя.
