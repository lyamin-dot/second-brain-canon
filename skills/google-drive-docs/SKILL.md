# google-drive-docs

Как сессия читает и пишет Google Docs, Google Sheets и файлы Google Drive — коннектором Drive (от имени владельца) и инструментами gdocs-*, gsheets-*, Create Folder (воркфлоу n8n под ключом сервисного аккаунта), — чем доказывает результат записи и что доказывает копия файла. Механика движка n8n — Skill `n8n-engineering-manual`.

## Стоп-правила

- Не прочитав файл, который «Что читать» называет для действия, действие не начинать.

### Пути чтения
- Google Docs и текстовые файлы не читать ничем, кроме gdocs-read.
- Google Sheets не читать gdocs-read, `read_file_content` и экспортом в `text/csv` через `download_file_content` — gsheets-read; разбор всей книги — экспортом .xlsx на диск.
- `read_file_content` к Google Doc и Google Sheets не применять; исключения: (1) PDF — только ради распознавания текста отсканированного или графического PDF; (2) внешний исследовательский отчёт вики, хранящийся Google Doc с ID в `wiki/INDEX.md`, — только ради содержания (не для контрольной суммы, сверки, переписывания), и после чтения проверить, что последний раздел отчёта на месте. Системные документы (INDEX, журналы, реестры, паспорта) под исключение не подпадают.
- Полноту прочитанного `read_file_content` не оценивать по размеру — только по содержанию (последний раздел на месте).
- Полный текст PDF не читать ради обхода и описи многих файлов — только прицельно, когда нужно содержание именно этого файла.
- `download_file_content` для файла примерно 5–50 КБ не применять — читать gdocs-read.
- Синтаксис прежнего инструмента google_drive_search (`name contains`, `'ID' in parents`) в search_files нынешнего коннектора не применять — он не действует.
- PDF в Google Doc из Apps Script не конвертировать через Drive API v3 — не работает; только v2: `Drive.Files.insert(metadata, blob, {convert:true})`.
- Шаг «прочитать оформление через gsheets-read» в план и эстафету не ставить.
- Путь «экспорт .xlsx на диск» не ставить шагом плана, пока он не проверен в своей среде одним вызовом; в Claude Project без bash его нет.
- Число про объём ответа инструмента (порог «в файл или в контекст») не брать основанием для параметров и шагов плана — путь проверяется одним вызовом в своей среде.

### Утверждения о результате
- Запись не считать выполненной по ответу инструмента (`success:true`, `occurrencesChanged`, `match:true`, `executionId`, `started`, статус исполнения) — только по обратному чтению целевого файла через gdocs-read, независимо от инструмента записи.
- Утверждение «файла нет», «пусто», «список полон», «документ такого-то размера» не делать по ответу инструмента чтения или поиска («пусто», «не найдено», «найдено N», число из метаданных) — только по признаку, который это проверяет; иначе — «неизвестно».
- На пустой результат чтения не отвечать реконструкцией по памяти: явно сообщить «чтение вернуло пусто» и остановиться; исключение — gdocs-read с `fromLine` больше `totalLines` (см. «Адреса и ловушки»).
- Пустой срез gdocs-read не принимать за отказ чтения, не сверив `fromLine` с `totalLines`.
- Размер документа не определять по `fileSize`, `driveSize`, `contentSnippet` из метаданных — только gdocs-read (`byteLength`, `totalLines`).
- Отрывок (`contentSnippet`) из search_files для проверки содержимого не использовать.
- Экономию контекста диапазоном строк gdocs-read не обещать и не класть в основание правил.
- Обход папки или список файлов не записывать полным, пока перечень неоткрывшихся частей (подпапки, страницы ответа, файлы с ошибкой) не назван явно и не пуст.
- В своих скриптах и воркфлоу обхода оборванную на середине пагинацию не превращать в предупреждение — она роняет прогон; неоткрывшиеся части — отдельным списком.
- Файлы одного вида не отбирать по расширению в имени — только по типу (`mimeType`); найденный файл дальше не искать заново по имени — брать по fileId.
- Ответ «ineligible for generative AI contexts» не обходить и не считать признаком отсутствия файла — существование проверяет Андрей в интерфейсе Drive.
- «Битые» строки, меняющиеся от чтения к чтению неизменного источника, не чинить в данных — сверять по файлу на диске, по частям или глазами владельца в интерфейсе.
- Вывод «строка оборвана, содержания нет» не делать, пока не прочитана следующая строка.
- Контрольные числа (`byteLength`, `checkSum`) не снимать через субагента — только прямым вызовом gdocs-read.
- `length` и `returnedChars` gdocs-read не использовать для сверок между JS и Python — только байты и контрольную сумму.
- Числа сверки (длина, контрольная сумма) разных каналов не сравнивать; число не записывать без названия канала, которым оно снято.
- Совпадение контрольной суммы не принимать за «отправленное при записи легло» — запись проверяется построчной сверкой содержания.
- Текст крупного документа не сравнивать с источником без нормализации и не в контексте — программно, по файлу на диске.
- Хеши и контрольные суммы не считать через контекст сессии (base64 между инструментами) — на стороне (Apps Script, сервер).
- Кто и когда перенёс файл между папками, не утверждать по `modifiedTime` — только по истории действий или версий объекта либо по записи о переносе; без них — «не установлено».
- Файл в этой же сессии не читать во время активной записи в него.
- После замены Skill не предполагать и не опровергать без чтения, что сессия видит новый снимок: перечитать Skill и сверить по якорю правки или побайтно.

### Вызов инструментов-воркфлоу
- ID воркфлоу не брать по памяти, из старого текста или из похожей строки — только из прочитанной строки реестра по «ID воркфлоу инструмента»; ноль или больше одного совпадения — стоп и причина в ответе.
- Старые версии gdocs-append, gdocs-replace, gdocs-overwrite (без «v2» в имени) и архивные воркфлоу не вызывать.
- Инструмент, объявленный устаревшим, не оставлять опубликованным: тем же действием `unpublish_workflow` и проверка чтением `active:false`.
- Больше двух `execute_workflow` одновременно не запускать; серия правок документа — по одному-два вызова.
- Пока исполнение в статусе `running`, новый `execute_workflow` того же инструмента записи не запускать — ждать и спрашивать `get_execution` снова.
- Имена полей `body` не менять и не подставлять по аналогии с другим инструментом — только по контракту инструмента.
- Метод и поле вызова не оставлять по умолчанию: `method: "POST"` явно, поле — `inputs`, не `data`.
- Ключ, которым закрыты вебхуки воркфлоу-инструментов, до решения владельца не трогать и не переименовывать (задача `labs/sys/t-webhook-key-reuse.md`).
- В gsheets-read запись не добавлять.

### Повтор записи
- Запись не повторять вслепую при `success:false` со следами записи (`VERIFY-READ-FAILED`, `occurrencesChanged>0`, «content mismatch on first/last 100 chars», «request failed…» у gsheets-append) — сначала перечитать файл или лист.
- Запись не повторять, если чтение сразу после неё вернуло пусто или прежний текст, — подождать и перечитать.
- После «Too Many Requests» без чтения документа повторять только вызов, на который не пришло ни номера исполнения, ни ответа воркфлоу.
- После `started` в режиме `manual` вызов не повторять — ответ забирать `get_execution`.
- create_file с двоичным файлом (JPEG, zip) не повторять и параметры не подбирать — файл кладёт владелец вручную.

### Запись в Google Docs
- Цель перезаписи (overwrite, apply-from-file `overwrite`) и удаляющего replace не принимать по ID из памяти или старого текста: до вопроса Андрею и до вызова — ID из `registry/documents.md`, имя и время изменения из `get_file_metadata` по этому ID, содержимое из gdocs-read.
- Имя файла в отчёте и в вопросе Андрею не писать иначе, чем из метаданных.
- Архивную или замороженную копию документа не править.
- Текст крупнее примерно 1–2 КБ не передавать телом вызова gdocs-append, gdocs-replace, gdocs-overwrite v2 — путь по «Текст крупнее примерно 1–2 КБ».
- Текст, собранный дозаписями или порциями, не принимать по проверке каждой порции отдельно — только сверкой всего собранного текста или каждого стыка с источником.
- Многострочный `search` в gdocs-replace v2 и в gdocs-apply-from-file `replace` не использовать; при вынужденном отступлении — только одиночный `\n`; составные многострочные блоки — не пытаться.
- Якорь replace не брать неуникальным: одна короткая строка, встречается в документе ровно один раз и остаётся единственной после правки.
- Удаляющий replace (`replace=""`) не вызывать без подсчёта вхождений якоря программно по тексту gdocs-read (`text.count(search)`) — требуется ровно 1.
- Якорь для удаления не собирать по одной смысловой фразе — только с датой или уникальным хвостом строки.
- Уникальность якоря не проверять «пробой» безопасной заглушкой — только подсчётом.
- Guard K1 не обходить дроблением массового удаления на серию однострочных replace; многострочная чистка — только gdocs-overwrite v2 полным текстом, gdocs-apply-from-file `overwrite` или руки владельца.
- Строку не копировать внутри документа без уникальной пометки «[перенесено из <раздел> <ГГГГ-ММ-ДД>]» в начале или в конце копии.
- Символы в `search` и `replace` не набирать последовательностями `\uXXXX` — как есть (кириллица, тире, ёлочки); если всё же набраны — обратное чтение сверять по кодам символов программно.
- Якорь, видимый в экспорте, но дающий 0 вхождений, не подбирать вслепую — сначала посмотреть байты строки через gdocs-read.
- `newContent` gdocs-overwrite v2 не передавать объектом — только строкой.
- Красивый документ (`text/html`) не править через gdocs-overwrite v2 или apply-from-file — пересоздать через create_file с новым HTML или руками владельца; точечный gdocs-replace допустим.
- Поле LAST_UPDATED в шапке не оставлять прежним после записи gdocs-* в тело документа — обновить отдельным вызовом записи.
- Перед запуском разборщика по признаку «пустая строка = граница записи» не пропускать проверку, как собран документ (append много раз против единой вставки).

### create_file
- `application/vnd.google-apps.document` вместе с `textContent` не использовать.
- create_file не вызывать, не проверив, что файла с таким именем в папке ещё нет (`get_file_metadata` по ID или `search_files` по имени и папке).
- Содержимое существующего файла не менять create_file или update_file — только gdocs-* по сохранённому fileId.
- Вид документа (обычный или красивый) для человека не выбирать за владельца — по «Вопрос „обычный или красивый?“».
- append и replace к файлу `.md` (`disableConversionToGoogleType:true`) не применять — только overwrite.
- Конвертацию `text/html` не считать состоявшейся по `mimeType` в ответе — только по чтению без сырой разметки.

### Google Sheets
- Запись в книгу без чтения до и после не делать; писать только в своё; ответ инструмента записи не доказательство.
- В существующие листы файла, над которым по слову Андрея работает другой человек, не писать — только на отдельный лист, который создаёт сессия или робот.
- Ручной ввод и вывод робота не держать на одном листе.
- Защищённый диапазон листа не считать защитой от записи сервисного аккаунта.
- Структуру книги (листы, шапки, служебные колонки) не создавать руками в интерфейсе — только кодом (Apps Script или воркфлоу через Sheets API).
- Диапазон gsheets-read вслепую не запрашивать — сначала `mode:"meta"`.
- Ответ с `truncated:true` не принимать за весь диапазон — сузить диапазон или поднять `maxRows`.
- Вывод «файл удалён» по ошибке «Document … is missing» не делать, не повторив запрос и не проверив файл `get_file_metadata`.
- Лист тяжёлой книги (пересчитывается минутами) узлом n8n или запросом к Sheets API не читать — читать лёгкий источник, из которого лист собран.
- Ноль строк после долгого чтения не принимать за «данных нет» — сверять с размером листа (gsheets-read `mode:"meta"`).
- Отдельные ячейки книги (текст сводки, метка прогона, дата данных) воркфлоу не читает по адресам A1 — только по именам именованных диапазонов одним `values:batchGet`; несуществующее имя лечится в книге, не переходом на адреса.
- Режим узла Limit между узлами, сопоставляющими элементы по позиции через `$items`, не менять.
- Ошибку «Column to Match On required» не обходить переключением на Map Automatically — задать колонку сопоставления.
- Литерал массива `{…}` в формуле не писать через Sheets API с `USER_ENTERED` (узел Google Sheets, gsheets-append, `values.update`, `values.append`) — только из Apps Script; формулу, которую пишет воркфлоу, строить без литерала массива.
- Формулы не генерировать, не проверив язык имён функций по локали книги (`ЕСЛИ` или `IF`); разделитель аргументов формулы, которую пишет узел, — по локали книги.
- `IFERROR` вокруг `FILTER` не ставить там, где пустой результат не значит «нет данных»; рядом с обёрнутым `FILTER` — контрольная ячейка с числом строк источника.
- Порог из параметров не читать через `parseFloat(x)||0` — валидировать и падать при невалидном пороге.
- Условное форматирование не чинить в интерфейсе вручную — пересоздавать скриптом (`setupConditionalFormatting()`).
- Повтор запросов к Drive, Docs, Sheets в своих воркфлоу не делать больше 3 попыток; для 500 и 503 — пауза `wait = 2^attempt + random` секунд.

### Копия и бэкап
- Ни одно свойство копии (есть, свежая, полная, одинаковая, целая, переживёт потерю аккаунта, продолжит делаться) не выводить из другого и не считать доказанным, пока оно не проверено по самой копии своим способом (таблица в «Как делать»).
- Файл не удалять как дубль без полного хэша обоих файлов; быстрый отпечаток (размер, начало и конец) — только для отчёта и подсчёта кандидатов.
- Копию не называть резервной, пока полный хэш не совпал с оригиналом и целость не проверена чтением содержимого хотя бы одного экземпляра.
- Свежий файл бэкапа не называть рабочим бэкапом, пока он не скачан и не прочитан.
- Резкую смену размера файла бэкапа не толковать ни как «испорчен», ни как «база выросла», пока причина не выяснена по файлу или у того, кто делает бэкап.
- Полноту бэкапа не проверять наличием файлов и одним шаблоном имени — только вопросом «чего не хватит для восстановления», по каждому виду файла отдельно.
- Новое хранилище данных (база, том, папка сервиса) не заводить без включения в бэкап и в проверку свежести и размера тем же шагом.
- Бэкап в том же Google-аккаунте, что и оригиналы, не считать защитой от потери аккаунта.
- Копию Google Диска не сличать с Диском по имени — по содержимому.
- remote Google Drive в rclone не оставлять на общем client_id — только собственный client_id или сервисный аккаунт.

### Права и ключи
- При отказе Google не лечить, не определив, какой путь отказал: коннектор Drive (OAuth владельца) или воркфлоу n8n (ключ, привязанный к узлам).
- Тип ключа у воркфлоу не угадывать — строки C `registry/n8n-map.md`.
- При тихом неприменении записи не переавторизовываться первым делом — сначала `get_file_permissions` (сервисный аккаунт в writers).
- Первую запись сервисным аккаунтом в файл не делать, не проверив `get_file_permissions` — в том числе в новый файл вне уже расшаренных папок и в копию после `copy_file`.
- Файл для робота не создавать сервисным аккаунтом и не класть в корень «Мой диск».
- Шаг «расшарить на сервисный аккаунт» не оставлять человеку: воркфлоу или скрипт, создающий папку или документ для gdocs-*, выдаёт право редактора тем же прогоном.
- Ключ не менять на части узлов записи одного воркфлоу — на всех одним вызовом `update_workflow`, по операции `setNodeCredential` на каждый узел (больше трёх узлов — по Skill `n8n-engineering-manual`, «Стоп-правила», раздел «Запись и публикация воркфлоу»).
- Удалять и переносить в корзину не под сервисным аккаунтом — только под ключом владельца (`trash_file` коннектора) и с проверкой чтением после.

### ID воркфлоу инструмента
1. Имя воркфлоу — по таблице ниже; ID берётся в момент вызова из строки `registry/n8n-map.md` вида `W|<ID>|<имя>|<состояние>|…`: годится только строка с состоянием `active`, ID — второе поле.
2. Среда с клоном — поиск точной подстроки `|<имя>|active|` (`grep -F`), имя со стрелкой «→».
3. Без клона — один вызов Git Read Lines с `path: "registry/n8n-map.md"` и `pattern` из таблицы (регулярное выражение JavaScript: скобки и `|` экранированы, стрелка заменена точкой); внутри JSON-входа каждая обратная косая черта удваивается: `"pattern": "\\|Claude . Create Folder\\|active\\|"`.
4. Ровно одно совпадение — ID взят. Ноль или больше одного — стоп; в ответе причина (переименован, снят с публикации, второй активный с тем же именем).
5. Имя в карте скрыто «***» — ID из `registry/tools.md`, строка с названием инструмента.

Образцы ниже — сырой текст: обратная косая черта перед `|` и скобками — часть выражения.

### Вызов инструмента Google
1. ID — по «ID воркфлоу инструмента»; имя узла-триггера — из `get_workflow_details` этого воркфлоу или его сигнатуры в `registry/tools.md` (у gdocs-* и gsheets-* оно своё, не `01_Webhook` Канала git; ошибка о триггере ничего не исполнила, повтор с именем из её списка безопасен).
2. Форма вызова, `executionMode: "manual"` — по Skill `n8n-engineering-manual`, раздел «Вызов воркфлоу из сессии»; `inputs: {webhookData: {method: "POST", body: {…поля контракта…}}}`.
3. `execute_workflow` вернул номер исполнения и `started` — это не успех и не отказ: ответ воркфлоу читать `get_execution` с этим номером и `workflowId`; статус `running` — подождать около 10 секунд и спросить снова с тем же номером.
4. У gdocs-read и gdocs-apply-from-file (узлы загрузки `httpRequest`; карта — `registry/tools.md`) `get_execution(includeData:true)` приносит полный текст документа: нужен статус — `includeData:false`; нужно поле ответа — через субагента или сохранить ответ в файл и взять поле программно (jq); контрольные числа — только прямым вызовом.
5. Серия — не больше двух вызовов одновременно; после «Too Many Requests» — пауза около 20 секунд, дальше по одному-два.
6. Итог записи — обратным чтением по «Проверка записи».

### gdocs-read
body `{fileId, mode?: "full"|"tail", tailChars?: 2000, fromLine?, toLine?}` → `{success, fileId, name, mimeType, mode, length, returnedChars, driveSize, byteLength, checkSum, totalLines, fromLine, toLine, text, reason}`. Native Doc экспортируется text/plain, текстовый файл — alt=media, автоматически; без base64.
1. `byteLength`, `checkSum` и (когда заполнен) `totalLines` описывают весь документ и от среза, режима и параметров не зависят — целостность чтения проверяется ими при любом диапазоне; `text` и `returnedChars` — только то, что вернулось.
2. Диапазон: `fromLine`, `toLine` — целые от 1; без `toLine` — до конца. При `fromLine` `text` — срез строк по `\n`, `totalLines` заполнен; без `fromLine` `totalLines` всегда `null`.
3. Размер документа — вызов `fromLine:1, toLine:1`: `totalLines`, `byteLength`, `checkSum` при одной строке текста; цена — полный размер документа в контексте.
4. `byteLength` и `checkSum` — над сырым текстом экспорта (с `\r\n`, без нормализации), `checkSum` — FNV-1a 32 бита. Пересчёт в сессии — по байтам UTF-8 поля `text` полного чтения без изменений; файл в Python открывать в двоичном режиме (текстовый снимает `\r`).
5. `length` — байты UTF-8, `returnedChars` — UTF-16 code units; перед тревогой «обрезано» — `len(text.encode('utf-8')) == length`.
6. `mode` в ответе — эхо входа, не индикатор диапазона.

### Проверка записи

| Операция | Проверять | Провал |
|---|---|---|
| create_file | ответ `{id, title, mimeType}`, затем содержимое чтением (по «create_file») | id пуст |
| gdocs-append v2 | обратное чтение: строка в хвосте (на крупных — gdocs-read `mode:"tail"`) | строки нет |
| gdocs-replace v2 | обратное чтение: новый текст в файле | текста нет / склейка строк |
| gdocs-overwrite v2 | обратное чтение: начало и конец нового содержимого | не изменилось / пусто |
| gdocs-apply-from-file | `match:true` и обратное чтение gdocs-read | `match:false` / текст не совпал |
| удаляющий replace | исчезновение якоря при независимом перечитывании | якорь на месте |
| search_files | непустой список | пусто ≠ файла нет |
| обход папки, список файлов | перечень неоткрывшихся частей назван и пуст | перечня нет или он не пуст |
| gsheets-append | gsheets-read `mode:"range"` по `updatedRange`: число строк против `rowsRequested`, значения против отправленных | расхождение |
| Apps Script | книга открывается; значения — gsheets-read, оформление — дампом скрипта | ошибка в логе |
| запись gdocs-* в документ с LAST_UPDATED в шапке | LAST_UPDATED обновлён отдельным вызовом | тело изменилось, дата прежняя |

### Текст крупнее примерно 1–2 КБ
1. gdocs-apply-from-file: текст отдельным файлом на Drive, воркфлоу берёт его сам.
2. Если он недоступен — порции по 1–2 КБ; каждую подтвердить чтением до следующей; после последней — сверить весь собранный текст с источником по стыкам или побайтно после нормализации.
3. Ручная вставка владельцем (текст собран на диске, владелец вставляет в Doc, затем чтение) — только для объёма выше подтверждённого у gdocs-apply-from-file или при его отказе.
Короткие правки в несколько строк — одним вызовом.

### gdocs-append v2
body `{fileId, text}` → `{success, fileId, …}`. Встроенная проверка: документ без хвостовых пробелов оканчивается последними 200 знаками дописанного (пробелы схлопываются).
1. Пишет только в конец документа; вставка в середину (в конец зоны, перед маркером, в раздел) — gdocs-replace v2: однострочный якорь-маркер заменяется на «новый текст + перевод строки + тот же якорь».
2. Воркфлоу сам ставит один перевод строки перед текстом.
3. При `success:false` читать `reason`, итог — чтением хвоста gdocs-read.

### gdocs-replace v2
body `{fileId, search, replace}` → `{success, occurrencesChanged, context, reason}`; `context` — ±150 символов вокруг совпадения. Guard K1: якорь не ровно один раз — отказ.
1. По умолчанию — короткий однострочный якорь на каждую правку, даже если правок больше.
2. Многострочный `replace` на месте однострочного якоря допустим; блок крупнее примерно 2 КБ — gdocs-apply-from-file `replace` с тем же якорем; многострочный фрагмент самого документа — gdocs-overwrite v2 или gdocs-apply-from-file.
3. Удаление (`replace=""`): до вызова gdocs-read и `text.count(search)` = 1; после — независимое перечитывание (инструмент проверяет исчезновение якоря, `verifiedBy=absence-of-search` виден только внутри `reason`).
4. Удалилось больше задуманного — откат обратным replace тем же инструментом, подтвердить полным перечитыванием.
5. replace не заменяет — `reason` и `context` из manual-прогона; проверить разделители `\n\n` / `\r\n`.

### gdocs-overwrite v2
body `{fileId, newContent}` → `{success, fileId, bytesSent, bytesRead, reason}`. Работает с любым mimeType (native Doc, .md, .txt), пишет plain text. Встроенная проверка — первые и последние 100 символов с нормализацией `\r\n`.
1. Когда: замена всего содержимого; многострочная правка; пересоздание неприемлемо (ID меняется).
2. Текст крупнее примерно 1–2 КБ — gdocs-apply-from-file.
3. `bytesSent` и `bytesRead` побайтно не сравнивать: export может добавлять BOM и финальный перевод строки.

### gdocs-apply-from-file
ID и паспорт — `registry/tools.md`, строка GDOCS_APPLY_FROM_FILE. body `{targetId, sourceId, mode, search?}` → `{ok, mode, bytesWritten, targetByteLength, targetCheckSum, expectedCheckSum, match}`.
1. `targetId` — Google Doc, куда пишем; `sourceId` — файл на Drive с текстом (native Doc экспортируется text/plain, или текстовый файл).
2. `mode`: `append` — в конец; `overwrite` — стереть всё и записать источник (машинный путь многострочной чистки); `replace` — заменить единственное вхождение однострочного `search` текстом источника; вхождений не ровно одно — `REPLACE_ANCHOR_NOT_UNIQUE`, документ не тронут.
3. Источник — в папке, расшаренной сервисному аккаунту, или расшарить его до вызова (файл create_file владельца вне расшаренных папок сервисному аккаунту не виден, отказ `SOURCE_NOT_ACCESSIBLE`).
4. Пределы: заявлено 1 500 000 символов одним вызовом (не перепроверено); подтверждена запись 174 326 Б (мишень — строка TEST_GDOCS_APPLY `registry/tools.md`); отказ Docs API — на 1 900 000.
5. Статус — `get_execution` с `includeData:false`; итог — чтением gdocs-read.

### Create Folder
body: `folder_name` и `parent_id` — оба обязательны (корень My Drive — `parent_id:'root'`) → `{success, folder_name, folder_id, shared_with_sa}`. Повторный поиск не нужен. Тем же прогоном выдаёт сервисному аккаунту право редактора на папку; `shared_with_sa:true` — роль writer.

### create_file
1. До вызова — проверить, что файла нет (`get_file_metadata` по ID или `search_files` по имени и папке); решить вид документа.
2. `contentMimeType`: `text/plain` — обычный native Doc плоским текстом (черновик, рабочая запись, текст на вычитку); `text/html` — красивый native Doc с заголовками, таблицами, списками, цветом, разрывами страниц (печать и чтение человеком). Параметры: `title`, `contentMimeType`, `textContent`, `parentId`. Файл .md — `disableConversionToGoogleType:true` + `text/markdown`.
3. После вызова: ответ `{id, title, mimeType}`, id пуст — провал: повторить с `text/plain` + `textContent`, проверить права папки.
4. Прочитать созданное gdocs-read; для `text/html` в тексте не должно быть сырой разметки (`<table`, `style=`, `<div`) — иначе документ негоден и пересоздаётся.
5. Сверить содержимое со входом программно: символы вне ожидаемых алфавитов (например CJK посреди русского слова); ID, номера и даты — посимвольно против входа.
6. Дальше содержимое меняют только gdocs-* по сохранённому fileId.
7. Файл, в который потом пишет робот, создаёт владелец этим инструментом — по «Файл для робота».

### Вопрос «обычный или красивый?»
1. Перед созданием документа, который будет читать человек, — один короткий вопрос «обычный или красивый?», без объяснения разницы, если владелец о ней не спросил; один раз на документ; ждать ответа.
2. Вопрос не задаётся, и молча берётся `text/plain`, если: (а) владелец уже назвал вид в задаче («для печати», «красиво», «оформи», «черновиком», «просто текстом», «на вычитку» — по названному); (б) документ для машинного чтения; (в) служебная запись, лог, промежуточный или временный файл; (г) владельца нет на связи — тогда выбранный вид назван в отчёте прямой строкой.

### create_file отказал, а чтение работает
Протух доступ коннектора на запись. Фолбэк: создать документ вручную в интерфейсе Docs или копией существующего документа через `copy_file` и наполнить gdocs-overwrite v2 (независимая авторизация); либо переподключить коннектор и открыть новый чат.

### Чтение Google Sheets — только gsheets-read
body `{fileId, mode: "meta"|"range", sheetName?, range?, render?, maxRows?}` → `{success, fileId, mode, spreadsheetTitle, sheets, sheetName, range, render, rows, rowCount, returnedRows, truncated, maxRows, reason}`. Вызов — по «Вызов инструмента Google».
1. Сначала `mode:"meta"` — список листов с размерами; затем `mode:"range"` на конкретный лист.
2. `fileId` и `mode` — всегда; `sheetName` — обязателен при `range`, имя листа внутри `range` не работает, кавычки не подставлять; `range` — A1 без имени листа (`A1:G12`), без него — весь лист.
3. `render`: `UNFORMATTED_VALUE` (по умолчанию, числа числами), `FORMATTED_VALUE` (как в интерфейсе), `FORMULA` (текст формул — единственный путь увидеть формулу). Даты приходят сериальными числами.
4. Полноту доказывают поля: `truncated:false` — диапазон целиком; `truncated:true` — вернулись первые `maxRows` (по умолчанию 500), реальное число — `rowCount` и `reason`; `rows:[]` с EMPTY RANGE в `reason` — диапазон пуст, это не провал.
5. Ошибка «Document … is missing» при существующем файле (тяжёлая книга) — повторить запрос и проверить файл `get_file_metadata`.
6. Выбор пути: посмотреть структуру, диапазон, формулу — gsheets-read; посчитать по массиву в десятки тысяч строк или все листы разом — .xlsx на диске; оформление — дамп Apps Script, который запускает владелец.
7. Разовый разбор целиком: `download_file_content` с `exportMimeType: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` → файл на диске → `openpyxl` (`data_only=False` — формулы, `True` — значения); путь работает, только если среда сама кладёт ответ в файл — ответ пришёл в контекст, путь закрыт.

### gsheets-append
body `{fileId, sheetName, rows}` → `{success, fileId, sheetName, rowsRequested, updatedRange, updatedRows, reason}`. `sheetName` как есть (кавычки ставит воркфлоу); `rows` — непустой массив строк, строка — массив значений (`[["2026-09-27", "WB", 1250]]`). Вызов — по «Вызов инструмента Google».
1. Делает один `values:append` к `'<лист>'!A1` с `valueInputOption=USER_ENTERED`, `insertDataOption=INSERT_ROWS` под ключом сервисного аккаунта (`googleApi`); книга расшарена сервисному аккаунту редактором.
2. `success:true` — только при объекте `updates` в ответе Google; без него — `success:false`, «APPEND DID NOT HAPPEN…».
3. Текст, который должен остаться текстом, — с ведущим апострофом (`"'=A1"`); локаль книги — по самой книге.
4. Фактический адрес записи — `updatedRange`; проверка — по «Проверка записи».
5. `success:false` с «request failed…» — сначала прочитать лист, потом решать о повторе.

### Лист — единица владения
- Один лист пишет один хозяин — человек или робот.
- В книге, которую ведёт робот (воркфлоу или скрипт), всё, что человек вводит руками (пометки, поправки, ручные цены, параметры), живёт на отдельном листе; робот этот лист только читает, пишет только свои листы.
- Ячейки, которые робот не должен трогать, не входят ни в один диапазон записи воркфлоу и лучше лежат на другом листе.

### Создание книги
1. Apps Script: скрипт вставляется в script.google.com, владелец запускает его вручную (Run) — для книги, которую дальше перестраивает тот же скрипт (витрины, оформление, формулы).
2. Книга, которую ведёт робот n8n: сессия создаёт пустую книгу от имени владельца коннектором Drive в нужной папке и расшаривает её сервисному аккаунту редактором; листы, шапки и служебные колонки создаёт сам воркфлоу при первом запуске запросами к Sheets API. Результат — чтением, не ответом create_file.
3. Проверка обоих путей: gsheets-read `mode:"meta"` и `mode:"range"` по шапкам.
4. Перед любой переделкой существующей книги — Skill `apps-script-sheets`.

### Узел Google Sheets и запросы к Sheets API в n8n
1. Порцию чтения ограничивать отдельным узлом Limit после чтения (у чтения версии 4.7 опции ограничения строк нет).
2. Данные больше 18 000 строк писать в книгу напрямую из n8n, а не тянуть IMPORTRANGE.
3. Именованные ячейки: `values:batchGet` с `ranges=<имя>&ranges=<имя>`; диапазоны ответа — по полю `range` (Skill `n8n-engineering-manual`, раздел «Google Sheets» в «Стоп-правила»).
4. Поля, посчитанные выше по потоку, которые писать нельзя, — режим Map Each Column Below (`defineBelow`): пишет только сопоставленные колонки; через `create_workflow_from_code` сохраняется.
5. После структурных правок листа (колонки, шапка) — в узле Refresh columns list → Save → Publish.
6. Ошибка «Column to Match On required» у Update Row — задать колонку сопоставления (`matchingColumns` обязателен для update в обоих режимах).
7. Агрегация по дню — COUNTIFS/SUMIFS с границами суток (`">="&A2` и `"<"&(A2+1)`).
8. Ключ доступа в кэше узла отвечает «does not exist», хотя ключ на месте, — переключить узел на другой ключ и вернуть обратно → Save → Publish.
9. Скрипт, строящий книгу: условное правило — `whenFormulaSatisfied`; константы с префиксом, одна функция `onOpen` на проект.
10. Формула с массивом в автозаполнении: `TEXTJOIN(IF(...))` — в `ARRAYFORMULA()`; условие ИЛИ в `FILTER` — арифметикой `(усл1)+(усл2)>0`.

### Файл для робота
1. Файл создаёт владелец коннектором Drive (create_file) в нужной папке; для книги — по «Создание книги».
2. Папка или файл расшариваются сервисному аккаунту с правом редактора; воркфлоу или скрипт, создающий папку или документ для gdocs-*, выдаёт право сам тем же прогоном (Create Folder так и делает).
3. До первой записи — `get_file_permissions`: сервисный аккаунт в writers.
4. Дальше робот только перезаписывает содержимое по сохранённому ID.

### Правила сервисного аккаунта
1. Отказ записи или чтения — сначала определить путь: коннектор Drive (search_files, get_file_metadata, create_file, update_file, copy_file, trash_file, get_file_permissions, share_file, download_file_content, read_file_content — от имени владельца, OAuth claude.ai) или воркфлоу n8n (ключ узлов: тип по строкам C `registry/n8n-map.md`).
2. Отказ коннектора по авторизации — переподключить коннектор claude.ai и открыть новый чат.
3. Тихое неприменение записи, 404, 403, «not found or not shared to SA» — `get_file_permissions` (сервисный аккаунт в writers), затем расшарить.
4. Ключ OAuth (n8n или rclone), работавший около недели, отказывает `invalid_grant` или `EAUTH` — в Google Cloud Console, раздел Audience проекта клиента, перевести клиент из «Testing» в «In production» и подключить ключ заново.
5. Смена ключа у узлов записи — по стоп-правилу «на всех одним вызовом»; привязка и сверка — Skill `n8n-engineering-manual`, разделы «Ключи доступа» и «После записи».
6. «Не найден», а другие файлы читаются — проверить владельца (`owner`) и права; файл, который должен существовать и не находится нигде, — проверить Корзину вручную в интерфейсе Drive. Если цель действия — отсутствие файла (Корзина, удаление, снятие доступа), «not found» после действия — результат: назвать в отчёте ответ и инструмент, Корзину не проверять и владельца не спрашивать.

### Опись и отбор файлов Drive
1. Опись многих файлов (тип, тема, годится ли) — по имени, размеру и метаданным (get_file_metadata, search_files с `excludeContentSnippets: true`); массовую механическую работу (опись папок, нарезка текста) делает скрипт в среде с bash, не модель вызовами по одному файлу.
2. Отбор одного вида — `mimeType = '…'` в запросе search_files или поле типа в описи скрипта; дальше — по fileId.

### Сверка крупного документа
1. `download_file_content` с `exportMimeType text/plain` → ответ целиком на диск → программное сравнение (длина, начало и конец, счётчики подстрок, построчный diff).
2. Нормализация до сравнения: `\r\n`, BOM, лишний перевод строки на месте пустого абзаца, пустые абзацы от ведущих переводов строки при append, markdown-экранирование (`\#`, `\*\*`, `\-`, `\_`, `\[`, `1\.`).
3. Канонический канал чисел сверки — gdocs-read; число записывается с названием канала.
4. После правки последнего непустого абзаца ожидаемую контрольную сумму считать по нормализованному хвосту; прежние пустые абзацы не восстанавливать.

### Копия и бэкап

| Свойство копии | Чем доказывается | Что его не доказывает |
|---|---|---|
| есть | объект найден — по папке или по ID | код возврата скрипта копирования |
| свежая | дата создания файла | — |
| полная: восстановление пройдёт | ответ на вопрос «чего не хватит для восстановления» по составу копии | наличие и свежесть файлов; сводка по одному виду файла |
| одинаковая с оригиналом | полный хэш содержимого обоих файлов | совпавшие размер или имя; быстрый отпечаток; «0 расхождений» сверки, не сравнившей хэш у части файлов |
| целая, читается | чтение содержимого: у медиафайла — длительность и участки нулей внутри; у дампа базы — конец файла и пробное восстановление | совпавший полный хэш копий; «открывается, воспроизводится»; дата и размер в метаданных |
| переживёт потерю аккаунта | где копия лежит | успешное учение восстановления |
| продолжит делаться | ключ доступа и его срок | сегодняшний успешный прогон |

1. Шаг 0 любого восстановления — свежий бэкап есть (файл моложе суток, по дате создания и размеру) и известно, кто и где его делает.
2. Пока не доказано, отчёт пишет прямо: «совпадают размер и отпечаток, содержимое не сверено», «копии одинаковы, целость не проверена», «файл есть, целостность и читаемость не проверены».
3. Восстановление базы сервера: роли, базы, дампы (порядок не проверен восстановлением).
4. rclone и одноимённые файлы: полный список Диска `rclone lsjson -R`; каждый повтор пути — `rclone backend copyid` по ID в отдельную папку с началом ID в имени.
5. Отчёт сверки rclone называет отдельно: «N выгрузок проверены только на наличие» (документы, таблицы, презентации, рисунки Google).
6. Общий ли client_id: `rclone config show <remote>:` — пустые `client_id` и `client_secret` значат общий.

## Адреса и ловушки

- Адреса — в реестре: `registry/tools.md` (GDOCS_APPLY_FROM_FILE, TEST_GDOCS_APPLY, сигнатуры, свойства узлов загрузки), `registry/n8n-map.md` (ID по имени, строки C), `registry/documents.md` (ID документов). Имена воркфлоу инструментов — таблица «ID воркфлоу инструмента».

### Вызов инструментов
- Вызов без явного `method: "POST"` (по умолчанию GET) или с полем `data` вместо `inputs` молча не доносит тело: MCP отвечает `{"status":"started"}`, воркфлоу падает на «Missing fileId» — проверяй метод и имя поля.
- Инструмент, не проверяющий вход, получив текст в поле с другим именем, молча затирает файл пустотой (`modifiedTime` свежий, файл пуст) — проверяй имя поля по контракту (у overwrite — `newContent`, не `text`).
- Четыре и более одновременных `execute_workflow` получают «Too Many Requests», а вызов с номером исполнения мог уже записать — проверяй документ чтением до повтора.
- Обратное чтение запаздывает: после крупной записи оно бывало пустым десятки секунд или возвращало прежний текст — проверяй повторным чтением после паузы.
- Read-back внутри воркфлоу записи получает HTTP 500 «Unknown Error» от экспорта Drive API при состоявшейся записи — проверяй файл отдельным вызовом чтения.
- `get_execution(includeData:true)` через параллельного субагента даёт `byteLength`, расходящийся с прямым чтением, без ошибки — проверяй прямым вызовом gdocs-read.
- Единого порога «ответ инструмента в файл или в контекст» нет (58 тысяч символов ушли в файл, 82 тысячи байт — в контекст) — проверяй путь одним вызовом в своей среде.

### Чтение
- `read_file_content` молча обрезает хвост большого файла (порог неизвестен и меняется), искажает эмодзи двойной перекодировкой и отдаёт текст в своём представлении (`\_` вместо `_`) — проверяй содержание gdocs-read.
- `read_file_content` по PDF даёт артефакты распознавания (`$28a` вместо `§28a`, `0` и `O`) — для точного текста конвертируй PDF в Doc.
- gdocs-read по Google Sheets отдаёт `{success:false, length:0, text:null}` с сообщением, похожим на отказ по правам («Forbidden — perhaps check your credentials?»), — дело в виде объекта, проверяй, что читаешь таблицу gsheets-read.
- gdocs-read с `fromLine` больше `totalLines` отдаёт `success:true`, `text:""`, `returnedChars:0` — документ прочитан целиком, пуст только срез; проверяй пару `fromLine` против `totalLines`.
- gdocs-read с `mode:"tail"` и `fromLine` вместе: срез строк подменяет tail, `tailChars` молча игнорируется — проверяй, что задан один способ.
- Длинная строка документа может прийти несколькими строками ответа — проверяй следующую строку: строка без точки, терминального знака или маркера списка в конце, скорее всего, продолжается.
- `fileSize` нативного Doc отражает внутреннее представление (экспорт ≈ 3× в байтах UTF-8, ≈ 2× в символах на кириллице); `fileSize: "1"` сразу после create_file — кеш-заглушка; `contentSnippet` — кеш — проверяй gdocs-read.
- Байты через контекст сессии (base64 из одного инструмента в другой) портятся начиная примерно с 20–25 КБ — проверяй вторым независимым путём чтения.
- Чтение файла во время активной записи в него может вернуть пусто (гонка) — проверяй, подождав и перечитав.
- Файл в Корзине Drive на get_file_metadata, search_files, gdocs-read отвечает «not found» или пусто — так же, как несуществующий и нерасшаренный, — проверяй Корзину вручную в интерфейсе Drive.
- «Не найден» у get_file_metadata или чтения, когда другие файлы читаются, — файл в другом аккаунте или не расшарен аккаунту коннектора или сервисному аккаунту — проверяй владельца и права.
- `download_file_content` добавляет в начало BOM (3 байта), gdocs-read — нет — проверяй, что сравниваешь числа одного канала.
- Экспорт нативного Doc отдаёт `\r\n`, может добавлять BOM, превращать пустой абзац в лишний перевод строки и экранировать markdown (`\#`, `\*\*`, `\_`) — не всегда; проверяй после нормализации.
- Правка последнего непустого абзаца необратимо схлопывает пустые абзацы в хвосте документа, контрольная сумма не сходится — проверяй по нормализованному хвосту.
- `download_file_content` в диапазоне примерно 5–50 КБ возвращает base64 в контекст без декодирования — читай gdocs-read.

### Поиск и опись
- Свежесозданные PDF и двоичные файлы появляются в search_files с задержкой индексации, пустой ответ — проверяй get_file_metadata по ID или search_files по `parentId`.
- `search_files` не несёт перечня неоткрывшегося: «пусто» и «нашлось N» выглядят полным ответом — проверяй полноту другим признаком.
- Отбор по расширению в имени молча теряет файлы без расширения (497 PDF по типу против 483 по имени); два файла с одним именем — поиск по имени не выбирает между ними или берёт не тот — проверяй отбор по `mimeType` и работу по fileId.

### Запись в Google Docs
- gdocs-append v2: сбой проверочного чтения даёт `success:false` с `reason`, начинающимся `VERIFY-READ-FAILED`, при уже отправленной дозаписи — проверяй хвост чтением.
- gdocs-append v2: если между дозаписью и проверкой документ дописал кто-то ещё (две сессии в один документ), — `success:false` при состоявшейся записи — проверяй хвост чтением.
- gdocs-append: ведущий перевод строки в тексте становится лишними пустыми абзацами; документ, собранный многими дозаписями, несёт машинные пустые строки на границах вставок, и разборщик по пустым строкам делит по ним — проверяй способ сборки и нормализуй при сверке.
- gdocs-replace меняет все вхождения якоря: промах виден (`occurrencesChanged: 0`), лишнее попадание меняет чужое место и рапортует успех (`occurrencesChanged > 1`) — проверяй вхождения до вызова и перечитывай после.
- Многострочный `search`, пересёкший границу абзаца, склеивает хвост соседнего пункта с новым текстом и рапортует успех — проверяй обратным чтением.
- gdocs-replace v2: `success:false` при `occurrencesChanged>0` — замена (или удаление) состоялась, не прошла только проверка после неё — проверяй перечитыванием, не повтором.
- Последовательность `\uXXXX`, набранная моделью неверно, кладёт в документ чужой символ, который Guard K1 не ловит, — проверяй коды символов программно.
- Якорь виден в экспорте text/plain, а replace даёт 0 вхождений — вероятно, неразрывный пробел или иной невидимый символ (строки шапки, строка LAST_UPDATED) — проверяй байты строки.
- gdocs-overwrite v2 и gdocs-apply-from-file пишут plain text: форматирование красивого документа молча исчезает, текст на месте — проверяй вид документа до перезаписи.
- gdocs-append, gdocs-replace, gdocs-overwrite v2 с настоящим текстом телом вызова молча портят байты (случай — gdocs-overwrite v2, около 29 КБ); порча зависит от содержимого, а не только от объёма — проверяй чтением после записи.
- gdocs-overwrite v2 сверяет только первые и последние 100 символов: середина документа не проверена — проверяй обратным чтением.
- gdocs-overwrite v2 с `newContent` объектом кладёт в документ сжатый JSON и отвечает `success:false` «content mismatch on first/last 100 chars» при состоявшейся записи — проверяй файл чтением и тип поля.
- gdocs-apply-from-file `replace` с `\r\n` в `search` отвечает успехом, документ не меняется (с `\n` — отказ «0 вхождений») — проверяй чтением.
- `match:true` gdocs-apply-from-file доказывает «прочитанное = ожидаемое воркфлоу», не «текст = замысел» — проверяй независимым чтением.

### create_file
- `application/vnd.google-apps.document` с `textContent` даёт пустой или неоткрывающийся документ (без `textContent` — штатно пустой документ) — проверяй `text/plain`.
- create_file при совпадении имени молча создаёт дубль, а не обновляет файл — проверяй существование до вызова.
- `mimeType: "application/vnd.google-apps.document"` в ответе не доказывает конвертацию `text/html` — проверяй текст на сырую разметку.
- create_file портил текст без ошибки (иероглифы CJK посреди русского слова, испорченные число, дата, ID) — проверяй содержимое против входа программно.

### Google Sheets
- Экспорт таблицы в `text/csv` отдаёт только первый лист без предупреждения; `read_file_content` по таблице — образец около 5 строк на лист — проверяй путь чтения: gsheets-read или .xlsx.
- gsheets-read не отдаёт оформления (форматы, ширины, высоты, заливка, шрифт, условное форматирование, проверки данных, графики) — снимай дампом Apps Script.
- Тяжёлая книга (пересчитывается минутами) отвечает «Document … is missing (perhaps it was deleted…)», хотя файл на месте, — проверяй повтором и `get_file_metadata`.
- Узел чтения листа тяжёлой книги работает минутами и отдаёт успех с нулём строк или ответ Google 503 — проверяй размер листа `mode:"meta"`.
- `USER_ENTERED` (gsheets-append; `cellFormat` узла Google Sheets по умолчанию) разбирает значения как набранные руками: строка с `=` становится формулой, «1,5» и «1.5» по локали — числом, датой или текстом, «+49…» — числом — проверяй апостроф и локаль книги.
- `values:append` пишет после «таблицы», найденной от A1: пустая строка внутри данных уводит запись в середину листа — проверяй `updatedRange`.
- `values:append` не идемпотентен, узел запроса стоит с `retryOnFail`: при потерянном ответе повтор дописывает те же строки — проверяй лист чтением перед повтором.
- Get Row(s) без фильтров: колонка A:A может прийти под именем `'A: field'` — проверяй оба варианта имени.
- Без узла Limit каждая строка листа становится отдельным элементом, и следующий узел делает столько же параллельных вызовов внешнего API — проверяй число элементов после чтения.
- IMPORTRANGE ломается на таблицах больше 18 000 строк — проверяй размер источника.
- Адрес A1 сдвигается при перестройке листа, и узел молча читает соседнюю ячейку — проверяй чтение по именованному диапазону.
- Несуществующее имя в `values:batchGet` роняет весь запрос ошибкой 400, а не только свой диапазон — проверяй, завела ли книга это имя.
- Поле входа без колонки узел по умолчанию пишет в новую колонку (`handlingExtraData: insertInNewColumn`) — проверяй состав полей входа.
- Узел Google Sheets держит снимок схемы листа: после правки колонок или шапки пишет по старой — проверяй Refresh columns list.
- Значение даты со временем не равно дате: COUNTIFS/SUMIFS со сравнением на равенство молча не считают строку — проверяй границы суток.
- Имена функций не той локали дают `#NAME?` в ячейке — проверяй язык имён функций книги.
- `FILTER` с пустым результатом даёт ошибку в ячейке; `IFERROR` вокруг него прячет и «Result was not automatically expanded» при нехватке строк — себестоимость молча становится нулём — проверяй контрольную ячейку числа строк источника.
- `TEXTJOIN(IF(...))` при автозаполнении не вычисляется как массив без `ARRAYFORMULA()` — проверяй обёртку.
- Литерал массива `{…}` с колонками через обратную косую черту, записанный через Sheets API, дал `#ERROR!` при работающем `;` в той же книге — проверяй путь записи формулы.
- `parseFloat(x)||0` превращает невалидный или пустой порог в законный ноль — проверяй валидацию порога.
- Все файлы проекта Apps Script делят одну область видимости: одноимённые функции подменяют друг друга — проверяй префиксы и единственный `onOpen`.
- Сервисный аккаунт с правом редактора писал в защищённые ячейки без ошибки (не перепроверено) — проверяй, что ячейки вне диапазонов записи.

### Права, ключи, Drive API
- Файл, не расшаренный сервисному аккаунту, даёт 404 у gdocs-overwrite, 403 у gdocs-replace, «not found or not shared to SA» — похоже на опечатку в `fileId` — проверяй `get_file_permissions`.
- Сервисный аккаунт не создаёт файлы в папке документов: узел Drive от его имени отвечает Forbidden — проверяй, кто создаёт файл.
- Файл в корне «Мой диск» для воркфлоу не существует («not found or not shared to SA»), хотя владелец его видит, — проверяй папку файла.
- Копия `copy_file` из документа, расшаренного сервисному аккаунту, наблюдалась с ним в редакторах при нерасшаренной папке (не перепроверено) — проверяй `get_file_permissions` после копии.
- Ключ стоит не на всех узлах записи: один узел пишет, второй молча падает на авторизации — проверяй поле `credentials` каждого узла.
- Удаление и перенос в корзину через Drive API под сервисным аккаунтом возвращают HTTP 200 без эффекта (нужна роль владельца) — проверяй чтением после.
- Клиент OAuth в статусе «Testing» выдаёт токен обновления на 7 дней: ключ OAuth (n8n, rclone) через неделю отказывает `invalid_grant` или `EAUTH`; переподключение без смены статуса даёт ещё неделю — проверяй статус клиента.
- Ключ в кэше узла отвечает «does not exist», хотя ключ на месте, — проверяй переключением ключа туда и обратно.

### Копия и бэкап
- Одинаково испорченные копии совпадают размером, отпечатком и полным хэшем (видео воспроизводится, данные только в первых примерно 27 % файла, дальше нули, во всех копиях) — проверяй участки нулей и место на диске против заявленного размера.
- Размер и быстрый отпечаток совпадают у файлов, различающихся в середине, — проверяй полный хэш.
- Сводка свежести по одному шаблону имени остаётся зелёной, пока остальных баз в копии нет вовсе — проверяй каждый вид файла и наличие файла новой базы.
- Дамп одной базы не несёт ролей сервера баз и их паролей (pg_dump их не сохраняет) — проверяй, что роли сохранены отдельно.
- Прерванная или испорченная выгрузка может лечь в папку тем же файлом со свежей датой — проверяй скачиванием и чтением.
- rclone из одноимённых файлов папки кладёт один (какой — не гарантировано), остальные — только строкой «Duplicate object found» в журнале; код 0, `rclone check` расхождений не показывает — проверяй повторы путей по `rclone lsjson -R`.
- У документов, таблиц, презентаций и рисунков Google нет MD5: `rclone check` сверяет их выгрузки (docx, xlsx, pptx, svg) только на наличие, «0 расхождений» о них ничего не говорит — проверяй их число отдельно.
- rclone заменяет знаки, запрещённые в именах Windows, похожими знаками Юникода: имя выглядит так же, побайтно другое — проверяй по содержимому.
- Общий client_id rclone для Google планово выводится из обращения, бэкапы молча останавливаются — проверяй `rclone config show`.

## Куда писать результат

- Выбранный вид документа, когда владельца не было на связи, — прямой строкой в отчёте.
- Удаление, перенос в Корзину, снятие доступа: какой ответ получен и каким инструментом — в отчёте.
- Статус клиента OAuth («Testing» или «In production») — в канон задачи о ключе, не в Skill.
- Факты бэкапа сервера (где, чем, расписание, состояние) — в канон сервера.
- Число сверки — вместе с названием канала, которым снято.
