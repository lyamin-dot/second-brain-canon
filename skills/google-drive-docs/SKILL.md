## 0. ДВА ЖЁСТКИХ ПРАВИЛА (без исключений, кроме названных здесь)

Закон раздела: у каждого вида объекта один путь чтения, и выбирается он по виду объекта, а не по удобству вызова. Почему: остальные пути отдают не байты объекта, а своё представление — обрезанное, перекодированное или пустое, — и делают это молча, без ошибки; сессия, прочитавшая не тот путь, рассуждает над искажённым текстом и не знает об этом.

1. **Google Docs и текстовые файлы читаются ТОЛЬКО через gdocs-read** (контракт — §3.5). Он отдаёт полный текст экспорта без обрезки хвоста и без искажения символов вне базовой плоскости Юникода (эмодзи), с длиной и контрольной суммой всего документа.
   Цена: полный текст документа приходит в контекст сессии дважды — в ответе воркфлоу и в `contextData` его узла загрузки; диапазон строк этого не меняет. Механизм — свойство типа узла загрузки (n8n-engineering-manual, references/roots.md, правило R4.5); следствия для gdocs-read — §3.5 и §9.
   **Google Sheets через gdocs-read НЕ читаются.** Воркфлоу считает нативным документом только тип Google Docs; таблица уходит в ветку бинарной загрузки, Google отвечает «Only files with binary content can be downloaded. Use Export with Docs Editors files.», и воркфлоу возвращает `{success:false, length:0, text:null}`. Признак: сообщение выглядит как отказ по правам («Forbidden — perhaps check your credentials?»). Не путать: дело не в правах и не в расшаривании — дело в виде объекта. Путь чтения таблиц — gsheets-read (§4.0).
   [основание: MAIN-01 · правило A.0.1]

2. **`read_file_content` коннектора Google Drive ЗАПРЕЩЁН для Google Docs и Google Sheets.** Для любого Doc — gdocs-read, для любой таблицы — gsheets-read.
   Почему, три причины:
   - может молча обрезать хвост большого файла без признака ошибки, и порог обрезки неизвестен: однажды обрыв случился около 64 тысяч символов, а позже тот же документ, выросший примерно до 105 тысяч символов, пришёл целиком — поведение инструмента меняется со временем, число не держится;
   - искажает символы вне базовой плоскости (эмодзи) двойной перекодировкой UTF-8 на чтении — сам документ при этом не портится, портится только прочитанное;
   - непригоден как источник контрольных сумм и сверок: он отдаёт текст в своём представлении, а не байты экспорта — например, с экранированием разметки markdown (`\_` вместо `_`), отчего размер расходится с gdocs-read.
   Не путать: «read_file_content обрезает файлы выше примерно 130 КБ» — это число не было замером ни одного случая; полнота прочитанного этим инструментом проверяется только по содержанию (последний раздел на месте), а не по размеру.
   [основание: MAIN-02 · правило A.0.2]

   **Исключение 1 — PDF ради распознавания текста.** `read_file_content` разрешён для PDF, и только ради распознавания текста в отсканированных или графических PDF: это недокументированное побочное поведение инструмента, и оно даёт артефакты (`$28a` вместо `§28a`, путаница `0` и `O`). Для точного текста PDF конвертируется в Doc через Drive API v2 (§4.4). Цена полного текста PDF в контексте и правило прицельного чтения — §2.2 пункт 7.
   [основание: MAIN-03 · правило A.0.3]

   **Исключение 2 — внешний исследовательский отчёт вики.** Отчёт, который хранится Google Doc и чей ID стоит в `wiki/INDEX.md`, читается `read_file_content`: коннектор приносит текст в контекст один раз, а gdocs-read — дважды. Условия: документ читается ради содержания, а не ради контрольной суммы, сверки или переписывания; после чтения сверяется, что последний раздел отчёта на месте — описание коннектора само предупреждает, что содержимое очень больших файлов может прийти неполным. Системные документы — INDEX, журналы, реестры, паспорта — под исключение не подпадают.
   [основание: MAIN-04]

### ID воркфлоу — только из прочитанной строки реестра

**Skill называет инструмент n8n именем его воркфлоу; ID берётся в момент вызова из строки `registry/n8n-map.md` с этим именем, никогда по памяти и никогда из старого текста.** Строка воркфлоу имеет вид `W|<ID>|<имя>|<состояние>|…`; годится только строка с состоянием `active`, ID — второе поле.
Как искать:
- в среде с клоном репозитория — поиск точной подстроки `|<имя>|active|` (`grep -F`), имя со стрелкой «→» как в таблице ниже;
- без клона — один вызов Git Read Lines с `path: "registry/n8n-map.md"` и входом `pattern` из таблицы ниже. `pattern` — регулярное выражение JavaScript: скобки и вертикальная черта в нём экранированы обратной косой чертой, имя ограничено с двух сторон полями `|…|active|`, а стрелка «→» заменена точкой, чтобы вызов не нёс символов вне ASCII. Внутри JSON-входа вызова каждая обратная косая черта удваивается: `"pattern": "\\|Claude . Create Folder\\|active\\|"`.
**Найдено ровно одно совпадение — ID взят. Ноль совпадений или больше одного — стоп: ID по памяти, из старого текста или из похожей строки не подставляется;** причина называется в ответе (воркфлоу переименован, снят с публикации, появился второй активный с тем же именем).
Почему так строго: ID, прописанный в тексте, устаревает молча — воркфлоу пересоздают, архивируют, заменяют новой версией, и Skill, который держит ID, отправляет вызов в архивный или чужой воркфлоу. Имя без границ полей находит и архивные копии того же инструмента — с тем же именем и приставкой или суффиксом, а также первые версии без «v2». Файл `registry/n8n-map.md` строит воркфлоу инстанса ежедневно сам, руками его не правят, поэтому строка в нём — снимок инстанса, а не запись по памяти.
Образцы в таблице записаны сырым текстом: обратная косая черта перед `|` и скобками — часть регулярного выражения, а не разметка таблицы.
Если имя воркфлоу в карте скрыто знаками «***», по имени строку не найти — ID берётся из `registry/tools.md`, из строки с названием инструмента.
Признак ошибки: вызов уходит в воркфлоу, которого нет или который архивирован, либо ответ приходит не той формы, что в контракте.

### Устаревшие инструменты

**Старые версии gdocs-append, gdocs-replace и gdocs-overwrite (без «v2» в имени) не вызывать.** Не путать: «устаревший» в тексте Skill ≠ «неактивный» на инстансе — воркфлоу, объявленный устаревшим в Skill, может физически оставаться опубликованным и принимать вызовы. Поэтому инструмент, объявленный устаревшим, тем же действием снимается с публикации (`unpublish_workflow`), и снятие проверяется чтением: `get_workflow_details` или `search_workflows` показывает `active:false`. Почему: цель — чтобы устаревший инструмент нельзя было вызвать по ошибке; снятие с публикации этой цели достигает. Вытесненную новой версией копию инструмента можно и архивировать, но не обязательно; судьба ставшего ненужным воркфлоу вообще — n8n-engineering-manual, references/write.md, раздел 2.5.
[основание: MAIN-07 · правило A.1.2]

## 3. N8N — ЗАПИСЬ И ЧТЕНИЕ GOOGLE DOCS

Закон раздела: инструменты gdocs-* и gsheets-* — воркфлоу n8n, и сессия видит их только через MCP-сервер n8n; всё, что этот путь не показывает, считается неизвестным, а не успешным. Общая механика вызова живёт в n8n-engineering-manual, §1.1; здесь — то, что нужно для вызова инструментов Google без открытия того Skill.

**Вызов — только `n8n:execute_workflow`, никогда curl или bash.** Почему: egress-прокси облачной сессии блокирует домен инстанса. [основание: MAIN-08 · правило §1.1.0]

**Форма вызова:** параметр `triggerNodeName` — точное имя узла-триггера этого воркфлоу, плюс `inputs: {webhookData: {method: "POST", body: {…поля инструмента…}}}`; для воркфлоу с формой — `inputs: {formData: {…}}`; поля `type` внутри `inputs` нет. Имя триггера у каждого воркфлоу своё — его не угадывают и не переносят с другого воркфлоу, а берут из `get_workflow_details` этого воркфлоу или из его сигнатуры в `registry/tools.md`; вызов с неверным именем безвреден: сервер отвечает ошибкой со списком доступных триггеров, и вызов исправляется по этому списку. Тексты ошибок старой формы и правило «верить ответу сервера, а не описанию инструмента в клиенте» — n8n-engineering-manual, §1.1. Поля `body` каждого инструмента — его контракт в §3.1–3.6, §4.0, §4.0а.
Не путать: «у всех воркфлоу триггер называется `01_Webhook`» — это свойство воркфлоу Канала git (Skill second-brain-git, термин «Канал»), а не инструментов Google: у воркфлоу gdocs-* и gsheets-* имя триггера своё и бывает другим. Почему ловушка живучая: сессия, только что вызывавшая Канал, переносит его имя триггера по аналогии. Признак: первый вызов инструмента Google отвергнут ошибкой о триггере (имени нет среди доступных).
[основание: MAIN-09 · правило A.3.3]

**Метод POST указывается явно, поле называется `inputs`, а не `data`.** Почему: по умолчанию инструмент ставит метод GET; с полем `data` тело не доезжает до воркфлоу. Признак: разбор входа в воркфлоу падает на отсутствии обязательного поля («Missing fileId»), а MCP при этом отвечает `{"status":"started"}` — тихий отказ, который выглядит как ошибка параметров, а не формы вызова.
[основание: MAIN-10 · правило A.3.4]

**`executionMode` — обязательный параметр; ответ воркфлоу наблюдаем только в `manual`, и забирается он отдельным вызовом `get_execution`, а не из ответа `execute_workflow`.**
- Режим `production` исполняет опубликованную версию асинхронно: тело ответа не возвращается, исполнение не видно ни в `get_execution`, ни в `search_executions`; поля ответа воркфлоу `success`, `reason`, `context` наблюдаемы только в ручном режиме и в запуске с закреплёнными данными (pinData) — то есть при отладке. Поэтому в бою запись проверяется только обратным чтением целевого файла через gdocs-read (§7).
- Режим `manual`: сам `execute_workflow` может вернуть только номер исполнения и `{status:"started"}`, без тела ответа воркфлоу. Такой ответ — не успех и не отказ. Ответ воркфлоу читается затем вызовом `get_execution` с этим номером исполнения, с `workflowId` (без него сервер отвечает «not found» — n8n-engineering-manual, §1.1, правило §1.1.3), с `includeData:true` и с `nodeNames`, суженным до узла ответа. Пока статус исполнения `running` — подождать около 10 секунд и вызвать `get_execution` снова с тем же номером; новый `execute_workflow` не запускать: для инструмента записи это вторая запись.
- Цена такого чтения: у воркфлоу, чьи узлы загрузки имеют тип `n8n-nodes-base.httpRequest` (gdocs-read, gdocs-apply-from-file — §3.5, §3.6; карта узлов по воркфлоу — `registry/tools.md`), `get_execution(includeData:true)` приносит в контекст полный текст документа — сотни килобайт на крупном документе — при любом `nodeNames` (n8n-engineering-manual, references/roots.md, правило R4.5). Поэтому: нужен только статус — `includeData:false`; нужно поле ответа — ответ читается через субагента либо сохраняется в файл, и нужное поле берётся из него программно (например jq). Контрольные числа (`byteLength`, `checkSum`) через субагента не снимаются — только прямым вызовом (§9).
Не путать: «в `manual` ответ воркфлоу приходит прямо в ответе `execute_workflow`» — наблюдался только номер исполнения и `started`; при какой версии сервера MCP ответ приходил сразу, не установлено, поэтому на сразу пришедший ответ не рассчитывают.
Какую версию воркфлоу исполняет ручной запуск — n8n-engineering-manual, references/roots.md, правило R2.3.
[основание: MAIN-11 · правило §1.1.2]

**Серия вызовов — не больше двух одновременно.** Сервер n8n отвечает «Too Many Requests» на четыре и более одновременных `execute_workflow`; два параллельных вызова проходят, и пауза около 20 секунд после такого отказа снимает его. Поэтому серия правок документа идёт по одному-два вызова за раз; три одновременных вызова не измерены и считаются за риск. Повтор после «Too Many Requests»: если от самого воркфлоу ответа не было — ни номера исполнения, ни отказа воркфлоу, — вызов повторяется после паузы; если на вызов пришёл номер исполнения или ответ воркфлоу, запись могла состояться, и повтор допустим только после чтения документа (§7). Почему: повтор записи по ложному сигналу удваивает append и повторяет replace.
[основание: MAIN-12]

**Имена полей `body` — не косметика: каждый инструмент получает поля точно по своему контракту.** Почему: инструмент, не проверяющий вход, получив текст в поле с другим именем, отправляет в Google запрос с пустым телом — файл молча затирается пустотой. Признак: `modifiedTime` обновлён, файл пуст. Инструменты v2 от этого защищены — при отсутствии нужного поля они отказывают с ошибкой; старая версия overwrite ждала поле `newContent` и на поле `text` затирала файл.
[основание: MAIN-13 · правило A.3.2]

**Текст крупнее примерно 1–2 КБ через тело вызова gdocs-append, gdocs-replace или gdocs-overwrite v2 не передавать** — причина, порядок путей и сверка стыков порций: §3.0 (`references/docs-write.md`).
## 7. ВЕРИФИКАЦИЯ

**Любая запись недостоверна, пока целевой файл не перечитан независимо: обратное чтение через gdocs-read обязательно всегда, независимо от инструмента записи.** Ответ инструмента, `success:true`, `occurrencesChanged`, `executionId` и статус исполнения — сигналы, а не доказательства. Почему: в production ответ воркфлоу вообще не возвращается, а встроенная проверка каждого инструмента смотрит на узкий кусок результата (§3.1–3.6). Общий стандарт верификации для обоих носителей, Docs и репозитория, — second-brain-engineer, раздел Р15; здесь — его механика для Google.
[основание: MAIN-14 · правило A.7.1]

**Пустое или прежнее содержимое при чтении сразу после крупной записи не доказывает, что запись не легла: запись не повторять, подождать и перечитать.** Почему: обратное чтение запаздывает — после крупной записи оно бывало пустым десятки секунд или возвращало прежний текст, а повтор записи по такому ответу удваивает append и повторяет replace.
[основание: MAIN-15 · правило A.7.2]

| Операция | Проверять | Провал |
|---|---|---|
| create_file | ответ `{id,title,mimeType}`, затем содержимое чтением (§2.1) | id пуст |
| gdocs-append v2 | обратное чтение: строка в хвосте файла (gdocs-read `mode:"tail"` на крупных) | строки нет |
| gdocs-replace v2 | обратное чтение: новый текст в файле | текста нет / склейка строк |
| gdocs-overwrite v2 | обратное чтение: начало и конец нового содержимого | не изменилось / пусто |
| gdocs-apply-from-file | `match:true` в ответе и обратное чтение через gdocs-read | `match:false` / текст не совпал |
| search_files | непустой список | пусто ≠ файла нет (§2.3) |
| обход папки или список файлов («опись полная») | перечень частей, которые не открылись, назван явно и пуст | перечня нет или в нём что-то есть — обход неполный (§2.3) |
| Apps Script | таблица открывается; значения прочитаны через gsheets-read, оформление — выгрузкой самого скрипта (gsheets-read оформления не отдаёт, references/sheets.md) | ошибка в логе |
| любая запись gdocs-* в документ с полем LAST_UPDATED в шапке | поле LAST_UPDATED обновлено отдельным вызовом записи | тело изменилось, а дата в шапке осталась прежней |

**Поле LAST_UPDATED в шапке документа обновляется отдельным вызовом записи.** Почему: инструменты gdocs-* меняют только тот текст, который им передан, и шапку не трогают; правка тела без отдельной правки этого поля оставляет в шапке старую дату, и следующий читатель решит, что документ не менялся. Шаг «обновить LAST_UPDATED» в !save держит second-brain-engineer (references/save.md); причина шага — здесь.
[основание: MAIN-16 · правило A.7.3]

**Периодическая самопроверка пути записи (она пишет через gdocs-replace v2) сверяет уникальное значение своего запуска — точную метку времени, — а не наличие подстроки.** Почему: подстрока могла остаться от прошлого запуска, и проверка зелёная при несостоявшейся записи; факт записи ≠ содержательная корректность записи. Какой воркфлоу самопроверки стоит на инстансе — `registry/tools.md`.
[основание: MAIN-17 · правило A.7.4]

## 11. АНТИПАТТЕРНЫ

Каждая строка — короткая форма правила из названного раздела и наследует его основание.

- НЕ `contentMimeType: application/vnd.google-apps.document` при create_file (§2.1).
- НЕ webhook через curl/bash_tool (§3).
- НЕ вызывать архивные или устаревшие воркфлоу и НЕ подставлять ID воркфлоу по памяти — ID только из прочитанной строки реестра (§1).
- НЕ путать имена полей body (`text` ↔ `newContent`) — это затирание файла, не ошибка вызова (§3).
- НЕ многострочный `search` в replace: многострочный фрагмент документа меняется через overwrite v2 или gdocs-apply-from-file (§3.6); вставка многострочного текста на место однострочного якоря допустима (§3.2).
- НЕ передавать текст крупнее примерно 1–2 КБ через тело вызова gdocs-append/replace/overwrite v2 — gdocs-apply-from-file (§3.0, §3.6).
- НЕ создавать структуру Sheets руками в интерфейсе — только скриптом: Apps Script или воркфлоу через Sheets API (§4.1).
- НЕ считать запись выполненной по executionId или статусу — только обратное чтение (§7).
- НЕ повторять запись, если чтение сразу после неё вернуло пусто или прежний текст, — подождать и перечитать (§7).
- НЕ отвечать по памяти при пустом чтении — СТОП и явное сообщение (§2.2 пункт 3).
- НЕ принимать пустой срез по `fromLine` за отказ чтения — сверить с `totalLines` (§3.5).
- НЕ оценивать размер документа по fileSize (§2.2 пункт 2).
- НЕ обещать экономию контекста диапазоном строк gdocs-read — её нет (§3.5, §9).
- НЕ рассчитывать, что `nodeNames`, `truncateData` или режим `tail` в `get_execution` отсекут `executionData.contextData`: они режут только `runData`, а груз в `contextData` определяется типом узла загрузки воркфлоу (n8n-engineering-manual, references/roots.md, правило R4.5); для чтения Google Docs — §9, для воркфлоу Канала git — таблица «чистые и грязные» в second-brain-git 7.6. [основание: MAIN-18 · правило A.11.1]
- НЕ вызывать удаляющий replace без подсчёта вхождений якоря (§3.2).
- НЕ повторять write-вызов при `success:false` с `occurrencesChanged>0` — замена состоялась, не прошла только проверка после неё; сначала перечитать файл (E16).
- НЕ читать Google Doc через `read_file_content` — только gdocs-read (§0).
- НЕ читать Google Sheets через gdocs-read — он их не умеет и отдаёт `{success:false, length:0, text:null}` с сообщением, похожим на отказ по правам; только gsheets-read (§0, §4.0).
- НЕ экспортировать Sheets в `text/csv` — Google отдаёт только первый лист, без предупреждения (§4.0).
