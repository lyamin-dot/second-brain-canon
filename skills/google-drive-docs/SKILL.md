## 0. ДВА ЖЁСТКИХ ПРАВИЛА (без исключений)

1. **Чтение Google Docs и текстовых файлов — ТОЛЬКО через `gdocs-read`** (n8n workflow `hJZhQ9KaeFgeRm3k`, см. §3.5). Он не режет хвост, не имеет лимита 130 КБ, не искажает не-BMP символы (эмодзи) и отдаёт готовый полный текст.
   **Google Sheets через `gdocs-read` НЕ читаются.** Узел `04_Check_Native_Doc` считает нативным документом только mimeType Google Docs, поэтому таблица уходит в ветку бинарной загрузки `05B_Get_Media`, Google отвечает `"Only files with binary content can be downloaded. Use Export with Docs Editors files."`, и воркфлоу возвращает `{success:false, length:0, text:null}`. Формулировка ответа Google выглядит как проблема прав («Forbidden — perhaps check your credentials?»), но проблема не в правах и не в расшаривании. Путь чтения таблиц — `gsheets-read` (§4.0).
2. **`read_file_content` (Google Drive MCP) ЗАПРЕЩЁН для Google Docs/Sheets.** Разрешён ТОЛЬКО для PDF — и только ради OCR (распознавание текста в отсканированных/графических PDF; недокументированное побочное поведение инструмента, артефакты типа `$28a` вместо `§28a`, `0`/`O` — для точного текста PDF конвертировать в Doc через Drive API v2, см. §4.4). Для любого Doc/Sheet — `gdocs-read`, никогда `read_file_content`.

Причины запрета read_file_content для Docs (сведены в одно): молча обрезает хвост файлов выше ~130 КБ без индикации ошибки (порог ненадёжно определяется по fileSize — см. §2.2 п.2); искажает не-BMP эмодзи двойной UTF-8-перекодировкой на чтении (сам документ не портится — портится только прочитанное); непригоден как источник контрольных сумм/сверок.

## 3. N8N — ЗАПИСЬ И ЧТЕНИЕ GOOGLE DOCS

Только через `n8n:execute_workflow` — НИКОГДА через curl/bash_tool (egress-прокси блокирует прямой webhook).
Production-запуск webhook-воркфлоу через MCP асинхронный: не возвращает тело HTTP-ответа, execution не виден в get_execution/search_executions. Поля success/reason/context наблюдаемы только в manual/pin-режиме (отладка). В бою верификация ЛЮБОЙ записи — только read-back целевого файла через gdocs-read (§7).
Имена полей body — не косметика: старый overwrite ждал `newContent`; вызов с полем `text` даёт PATCH пустым телом → файл МОЛЧА ЗАТИРАЕТСЯ ПУСТОТОЙ (modifiedTime обновлён, файл пуст). v2-воркфлоу защищены от этого (throw при отсутствии нужного поля) — использовать точные имена полей, указанные под каждым воркфлоу ниже.
Поле body в вызове n8n:execute_workflow — `inputs`, не `data`. С `data` тело не доезжает: Parse Payload падает на «Missing fileId», при этом MCP возвращает `{"status":"started"}` — тихий отказ без явной ошибки.

Текст крупнее примерно 1–2 КБ через тело вызова gdocs-append, gdocs-replace или gdocs-overwrite v2 не передавать. Число 1–2 КБ не измерено ни для одного из трёх инструментов: это осторожная граница без замера, а не найденный предел. Известно только одно: у gdocs-overwrite v2 байты портились на объёме около 29 КБ (инцидент 31.07); точной границы успеха нет ни у одного из трёх. Штатный путь для большого текста — gdocs-apply-from-file (§3.6): текст сначала кладётся отдельным файлом на Google Drive, воркфлоу берёт его оттуда сам, и через тело вызова текст не проходит. Дробление на порции по 1–2 КБ с проверкой чтением после каждой порции — запасной путь на случай, если gdocs-apply-from-file недоступен; каждая порция подтверждается чтением до перехода к следующей, иначе теряется знание о том, какая порция легла, а какая нет. Ручная вставка владельцем (текст собирается на диске, владелец вставляет его в Doc, затем чтение для проверки) — только для объёма выше подтверждённого у gdocs-apply-from-file или при отказе этого инструмента. Короткие правки в несколько строк идут одним вызовом, как и раньше. Условие пересмотра числа 1–2 КБ: появится замер хотя бы для одного из трёх инструментов.

## 7. ВЕРИФИКАЦИЯ

Любая запись недостоверна до верификации: в production через MCP ответ воркфлоу не возвращается — read-back целевого файла через gdocs-read обязателен всегда, независимо от инструмента записи.

| Операция | Проверять | Провал |
|---|---|---|
| create_file | `{id,title,mimeType}` | id пуст |
| gdocs-append v2 | read-back: строка в хвосте файла (gdocs-read mode:tail на крупных) | строки нет |
| gdocs-replace v2 | read-back: новый текст в файле | текста нет / склейка строк |
| gdocs-overwrite v2 | read-back: head/tail нового содержимого | не изменилось / пусто |
| gdocs-apply-from-file | `match:true` в ответе и read-back через gdocs-read | `match:false` / текст не совпал |
| google_drive_search | непустой список | пусто ≠ файла нет (см. §2.3) |
| Apps Script | таблица открывается | ошибка в логе |
| любая запись gdocs-* в документ с полем LAST_UPDATED в шапке | поле LAST_UPDATED обновлено отдельным вызовом записи | тело изменилось, а дата в шапке осталась прежней |

Поле LAST_UPDATED в шапке документа инструменты gdocs-* не трогают: они меняют только тот текст, который им передан. Правка тела без отдельной правки этого поля оставляет в шапке старую дату, и следующий читатель решит, что документ не менялся. Поэтому second-brain-engineer Р7 держит «обновить LAST_UPDATED» отдельным шагом; причина этого шага — здесь.

Периодический self-check пути записи (canary, gdocs-replace v2, `B5jkqW0bUScxmTi7`) проверяет точный timestamp запуска, а не просто наличие подстроки — факт записи ≠ содержательная корректность записи.

## 11. АНТИПАТТЕРНЫ

- НЕ `contentMimeType: application/vnd.google-apps.document` при create_file.
- НЕ webhook через curl/bash_tool.
- НЕ вызывать архивные/deprecated ID воркфлоу (см. §1).
- НЕ путать имена полей body (`text` ↔ `newContent`) — это затирание файла, не ошибка вызова.
- НЕ replace для многострочной правки — только overwrite v2 или gdocs-apply-from-file (§3.6).
- НЕ передавать текст крупнее примерно 1–2 КБ через тело вызова gdocs-append/replace/overwrite v2 — gdocs-apply-from-file (§3.6).
- НЕ создавать Sheets вручную — только через Apps Script.
- НЕ считать запись выполненной по executionId/статусу — только read-back.
- НЕ отвечать по памяти при пустом чтении — СТОП и явное сообщение (см. §2.2 п.3).
- НЕ принимать пустой срез по `fromLine` за отказ чтения — сверить с `totalLines` (§3.5).
- НЕ оценивать размер документа по fileSize (см. §2.2 п.2).
- НЕ обещать экономию контекста диапазоном строк gdocs-read — её нет (§3.5, §9).
- НЕ вызывать удаляющий replace без подсчёта вхождений якоря (см. §3.2).
- НЕ повторять write-вызов при `success:false` с `occurrencesChanged>0` — сначала перечитать файл (E16).
- НЕ читать Google Doc через `read_file_content` — только gdocs-read (см. §0).
- НЕ читать Google Sheets через `gdocs-read` — он их не умеет и отдаёт `{success:false, length:0, text:null}` с сообщением, похожим на отказ по правам. Только gsheets-read (см. §4.0).
- НЕ экспортировать Sheets в `text/csv` — Google отдаёт только первый лист, без предупреждения (см. §4.0).
