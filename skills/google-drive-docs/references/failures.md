# google-drive-docs — ошибки, тихие отказы, крупные файлы

Часть Skill google-drive-docs. Читать: при ошибке или пустом ответе инструмента и перед сверкой крупного документа. Номера разделов — прежние, общие с SKILL.md.

## 9. РЕЕСТР ТИХИХ ОТКАЗОВ

Формат: инструмент/ситуация | тихий режим | обязательная страховка.

- gdocs-replace: `occurrencesChanged:0` без ошибки при промахе; неуникальный `search` даёт N>ожидаемого при попадании → read-back всегда; при удалении — подсчёт вхождений до вызова (§3.2).
- gdocs-replace v2: `success:false` при `occurrencesChanged>0` — замена состоялась, не прошла проверка после неё → не повторять вызов, верифицировать перечитыванием (E16, §3.2 (д)).
- Read-back внутри write-воркфлоу: HTTP 500 «Unknown Error» от Drive API export — не то же самое, что «запись не прошла» → перечитать файл вручную отдельным вызовом.
- Файл не расшарен на SA: 404/403 без явной связи с правами → get_file_permissions до первой записи.
- Частичная миграция credential: один узел пишет, второй молча падает на авторизации → мигрировать все узлы одним update.
- google_drive_fetch: пустой ответ на крупных/растущих файлах систематически → не использовать, только gdocs-read.
- get_file_metadata и search_files: fileSize и contentSnippet — кеш, не отражают реальный размер/содержимое нативного Doc → не использовать для оценки размера или верификации содержимого; размер брать gdocs-read с `fromLine:1, toLine:1` (§3.5) — это стоит полного документа в контексте, но другого достоверного способа нет.
- gdocs-read с `fromLine` за концом документа: `success:true` и пустой `text` — выглядит как тихий отказ чтения, но им не является → сверять `fromLine` с `totalLines` до тревоги (§2.2 п.3).
- Пустое чтение + модель: конфабуляция правдоподобного ответа поверх пустого результата инструмента → СТОП, явное сообщение, никакой реконструкции по памяти.
- n8n execute_workflow (MCP, production): `'started'` не гарантия выполнения; execution не виден в get_execution/search_executions; HTTP-ответ не возвращается → read-back целевого объекта.
- n8n execution `success`: цепочка может тихо оборваться в середине (IF без ветки) → сверять число прогонов write-ноды в manual-режиме при отладке.
- HTTP-нода с `neverError:true`: код ошибки API проходит как валидный item → явная проверка code/error после запроса.
- Schedule/webhook после update+publish может не тикать при `active:true` → сверка updatedAt с временем последнего исполнения годится, только если у воркфлоу сохраняются успешные прогоны: при `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none` отсутствие исполнения в списке ничего не значит; живость — по корням R2 и R4 Skill n8n-engineering-manual (счётчики `workflow_statistics`).
- Запись воркфлоу кодом целиком (Workflow SDK, `create_workflow_from_code`): уже привязанные credential узлов НЕ сбрасываются; теряется другое — настройки воркфлоу (часовой пояс, воркфлоу ошибок), число попыток и пауза между попытками у узлов, выражения в IF/Switch превращаются в строковые литералы, может смениться webhookId. На 2026-10-12 `update_workflow` принимает точечные операции и этих потерь в пробах не давал — кроме непроверенных Switch и узла-вебхука. Смена ТИПА credential у узла сбрасывает его фильтры и маппинг. → полная сверка воркфлоу после записи до publish; разбор и список — корень R1b в Skill n8n-engineering-manual. Привязку проверять полем `credentials` в get_workflow_details: с 2026-10-08 оно отдаёт id и имя ключа узла (позиция AH-27 очереди).
  ИСТОРИЯ ДИАГНОЗА: считалось, что credential после update_workflow сбрасывается на заглушку. Опровергнуто: проверка 2026-07-19 в журнале инцидентов n8n-engineering-manual (INCIDENT_LOG), версия «сброс ключа» опровергнута 2026-07-03 и снята как мотив задачи (`projects/wb-reviews/LOG.md`, Р-2, решение Д-2); в card-content-sync (Р-9) эта версия увела диагноз, а причиной был порядок диапазонов. Строка E12 таблицы §8 описывает новый узел без привязки, а не сброс существующей.
- SDK `.to([a,b])`: второй получатель молчит навсегда → `.to(a).add(source).to(b)`.
- Disabled нода пропускает данные насквозь, не блокируя поток → проверять downstream явно.
- HTTP Request может перезаписать `json`, теряя поля → `$('Node').all()[i]` для доступа к исходным данным.
- `executeOnce` на любом месте цепочки, в том числе после Merge, обрабатывает только первый элемент и молча отбрасывает остальные → не ставить на узел, который должен обработать каждый элемент; разбор — n8n-engineering-manual, references/engine.md §4.3. ИСТОРИЯ ДИАГНОЗА: до 2026-10-12 здесь стояло «executeOnce в середине цепочки выполняется на каждый item»; опровергнуто пробой 2026-10-12 (запись Р-31 журнала `projects/archivarius/LOG.md`).
- Правка jsonBody прямо в браузере может оборваться на `=` без ошибки до publish → в сохранённом JSON узла поле выражения хранится как `"={{ … }}"`; сверить через get_workflow_details. В поле редактора то же выражение пишется `{{ … }}` без `=` — одно правило о трёх местах записи: n8n-engineering-manual, references/engine.md §4.8.
- Байтовый релей через контекст (base64 между инструментами) теряет байты начиная примерно с 25 КБ → хеши/контрольные суммы считать на стороне (Apps Script/сервер), не через контекст.
- «Битые» строки, которые меняются от чтения к чтению неизменного источника, — дефект канала чтения, а не данных → не чинить данные; сверять по файлу на диске, по частям или глазами владельца в интерфейсе (выгрузка листа 182 строки около 2026-07-23, строки 114, 146, 176; WB_REVIEWS_INDEX; не перепроверено).
- create_file: дубль при уже существующем имени файла → проверка существования до create.
- `/mnt/skills/user/` в сессии: считалось, что это снимок на старт чата и замена Skill в текущем чате не видна. Опровергнуто 2026-09-24: в сессии SYS (облачная среда Claude Code) файлы Skills в `/mnt/skills/` обновились в том же чате — к следующему сообщению владельца, после сохранения Skill другой сессией. Второе наблюдение 2026-09-26, тоже облачная сессия на основе Claude Code: после двух заливок владельца (second-brain-git и second-brain-engineer) копии в /mnt/skills/ совпали с выданными файлами побайтово к следующему сообщению. Поведение, похоже, зависит от среды → после замены Skill перечитать файл в той сессии, которая на него опирается, и сверить по якорю правки или побайтово; «не видно в текущем чате» не предполагать и не опровергать без чтения.
- get_file_metadata / search_files / gdocs-read: файл в Корзине Drive отвечает «not found»/пусто на всех путях одинаково, неотличимо от «не существует» и от «не расшарен на SA» → если файл должен существовать, но нигде не находится — проверить Корзину Drive через UI вручную (программно эти случаи не различить). Граница правила: оно действует, только когда файл ДОЛЖЕН существовать. Если цель действия — отсутствие файла (перенос в Корзину, удаление, снятие доступа), то «not found» после действия — достигнутый результат, а не отказ: Корзину не проверять и владельца не спрашивать, достаточно назвать в отчёте, какой ответ получен и каким инструментом.
- Чтение файла во время активной записи в него той же сессией: может вернуть пустой ответ (гонка) → не читать во время активной записи; при подозрении — подождать и перечитать.
- `get_execution(includeData:true)` через параллельного субагента: байтовые метрики (byteLength) могут расходиться с прямым чтением без ошибки → контрольные числа (byteLength/checkSum) снимать только прямым вызовом gdocs-read, не через субагента.
- `get_execution(includeData:true)` на воркфлоу чтения или записи Doc: сырой ответ узла экспорта оседает в `executionData.contextData` и приходит в контекст сессии ПОЛНОСТЬЮ. Ни `nodeNames`, ни `truncateData`, ни диапазон строк `fromLine`/`toLine` этого не режут — свойство принадлежит типу узла загрузки (`n8n-nodes-base.httpRequest`) и параметрами вызова не чинится. Наблюдения: exec 67942 (полное чтение) и exec 68199 (`fromLine:1, toLine:1` — в `text` одна строка 21 символ, в contextData весь документ 38 299 Б). Практическое следствие: чтение документа Google Docs стоит сессии полного размера документа при любом запрошенном диапазоне. Страховка не в параметрах вызова, а в ожиданиях: не планировать работу исходя из экономии, которой нет, и не обещать её в правилах. Карта узлов по воркфлоу — `registry/tools.md`.
- Ответ инструмента: в файл или в контекст. Единого порога, после которого среда кладёт ответ инструмента в файл, а не в контекст, нет: в один день 58 тысяч символов ушли в файл, а 82 тысячи байт пришли в контекст (SYS_JOURNAL_2026, 2026-09-08; задача `labs/sys/t-get-execution-context.md`). → любое число про объём ответа — оценка, а не замер; параметры инструментов и шаги плана (например, путь .xlsx в §4.0) на нём не строятся — путь проверяется одним вызовом в своей среде.
- Retry на 429/500/503 (Drive/Docs/Sheets в целом) — общего встроенного паттерна нет вне Sheets-нод (§4.2): реализовывать явно, `wait = 2^attempt + random`, максимум 3 попытки.

## 10. ВЕРИФИКАЦИЯ БОЛЬШИХ ФАЙЛОВ

Рабочий порядок сверки крупного документа: `download_file_content` с `exportMimeType text/plain` → ответ сохраняется целиком на диск → сравнение программно (длина, head/tail, счётчики подстрок, построчный diff). Текст в контексте вместо файла на диске не даёт надёжной побайтовой сверки крупного документа.
Нормализация перед сравнением обязательна — иначе ложные расхождения: экспорт нативного Doc отдаёт `\r\n`, может добавлять BOM и превращать пустой абзац в дополнительный перевод строки; markdown-escape служебных символов (`\#`, `\*\*`, `\-`, `\_`, `\[`, `1\.`) в экспорте — тоже нормализуемый шум, не потеря данных. Это поведение зависит от содержимого документа, не универсально — иногда экспорт не добавляет escape вовсе.
Правка последнего непустого абзаца документа необратимо схлопывает пустые абзацы в его хвосте: ожидаемую контрольную сумму после такой правки считают по нормализованному хвосту, а восстановить прежние пустые абзацы не пытаются (наряды Н-26.08-03…06, 2026-08-27, «проверено дважды, восстановление не работает»; SYS_INDEX).
Контрольная сумма и длина записываются вместе с названием канала, через который сняты: одно и то же содержимое через разные каналы даёт разные байты. download_file_content добавляет в начало метку порядка байт (BOM, 3 байта), gdocs-read её не добавляет; канонический канал для чисел сверки — gdocs-read (JOURNAL_incidents, захват Ж). Сравнивать допустимо только числа одного канала.
Граница применимости контрольной суммы: byteLength/checkSum доказывают «полученное = лежащее в файле сейчас», но НЕ «отправленное при записи = легло в файл» — экспорт нативного Doc закономерно может немного менять байтовый размер (лишние пустые абзацы), и это не страховка записи. Верификация записи — построчная сверка содержания, а не только совпадение контрольной суммы.
`download_file_content` в диапазоне примерно 5–50 КБ возвращает base64 инлайн в контекст, но эта строка не декодируется автоматически — контекст расходуется впустую на нечитаемые байты. В этом диапазоне читать через gdocs-read, не download_file_content.
