# google-drive-docs — ошибки, тихие отказы, крупные файлы

Часть Skill google-drive-docs. Читать: при ошибке или пустом ответе инструмента и перед сверкой крупного документа. Номера разделов — прежние, общие с SKILL.md.

## 9. РЕЕСТР ТИХИХ ОТКАЗОВ

ЗАКОН РЕЕСТРА. Тихий отказ — ответ, который выглядит как успех, как законное «пусто» или как правдоподобное число. Ни код ответа, ни `success`, ни «started», ни число из метаданных не доказывают результата; доказывает только объект воздействия, прочитанный независимым путём (§7). Каждая строка ниже — частный случай: какой ответ врёт и какая проверка его ловит.

Формат: инструмент/ситуация | тихий режим | обязательная страховка.

**Google Docs и Drive — дом этих строк здесь.**
- gdocs-replace: `occurrencesChanged:0` без ошибки при промахе; неуникальный `search` даёт N больше ожидаемого при попадании → read-back всегда; при удалении — подсчёт вхождений до вызова (§3.2).
- gdocs-replace v2: `success:false` при `occurrencesChanged>0` — замена состоялась, не прошла проверка после неё → не повторять вызов, верифицировать перечитыванием (E16, §3.2 (д)).
- Read-back внутри воркфлоу записи: HTTP 500 «Unknown Error» от экспорта Drive API — не то же самое, что «запись не прошла» → перечитать файл вручную отдельным вызовом.
- Файл не расшарен на сервисный аккаунт: 404 или 403 без явной связи с правами → get_file_permissions до первой записи (§6.2).
- Несколько узлов записи с ключами в одном воркфлоу: ключ стоит не на всех — один узел пишет, второй молча падает на авторизации → ключ ставит сама сессия операцией `setNodeCredential` на КАЖДОМ узле записи, операции одного вызова применяются атомарно; после записи сверить поле `credentials` каждого узла (n8n-engineering-manual R1a.1, R1a.5). Для смены ключа у узлов Google Sheets действует запрет n8n-engineering-manual, references/write.md, §2.3, абзац «Отдельный запрет», до пробы.
- google_drive_fetch (прежний инструмент чтения): пустой ответ на крупных и растущих файлах систематически → в нынешнем коннекторе его нет; чтение Docs — только gdocs-read (§0, §2.2 п.1).
- get_file_metadata и search_files: fileSize и contentSnippet — кеш, не отражают реальный размер и содержимое нативного Doc → не использовать для оценки размера или проверки содержимого; размер брать gdocs-read с `fromLine:1, toLine:1` (§3.5) — это стоит полного документа в контексте, но другого достоверного способа нет (§2.2 п.2).
- gdocs-read с `fromLine` за концом документа: `success:true` и пустой `text` — выглядит как тихий отказ чтения, но им не является → сверять `fromLine` с `totalLines` до тревоги (§2.2 п.3).
- Пустое чтение + модель: правдоподобный ответ, сочинённый поверх пустого результата инструмента → СТОП, явное сообщение, никакой реконструкции по памяти (§2.2 п.3).
- Байтовый релей через контекст (base64 между инструментами) теряет байты начиная примерно с 20–25 КБ → хеши и контрольные суммы считать на стороне (Apps Script, сервер), не через контекст (§2.2 п.4).
- «Битые» строки, которые меняются от чтения к чтению неизменного источника, — дефект канала чтения, а не данных → не чинить данные; сверять по файлу на диске, по частям или глазами владельца в интерфейсе (наблюдение не перепроверено).
- create_file: дубль при уже существующем имени файла → проверка существования до вызова (§2.1).
- get_file_metadata, search_files, gdocs-read: файл в Корзине Drive отвечает «not found» или пусто одинаково с «не существует» и «не расшарен» → если файл ДОЛЖЕН существовать — Корзина вручную через интерфейс Drive; если цель действия — отсутствие файла, «not found» после действия и есть результат (§2.2 п.6).
- Чтение файла во время активной записи в него той же сессией: может вернуть пустой ответ (гонка) → не читать во время активной записи; при подозрении — подождать и перечитать (§2.2 п.5).
- `get_execution(includeData:true)` через параллельного субагента: байтовые метрики (`byteLength`) могут расходиться с прямым чтением без ошибки → контрольные числа (`byteLength`, `checkSum`) снимать только прямым вызовом gdocs-read, не через субагента (§10).
- Чтение Google Doc через gdocs-read: диапазон строк, `nodeNames`, `truncateData` и режим `tail` в `get_execution` не уменьшают того, что приходит в контекст: сырой ответ узла загрузки осел в `executionData.contextData` целиком → чтение документа стоит сессии полного размера документа при любом запрошенном диапазоне; экономию не планировать и не обещать в правилах. Механизм (груз в contextData решает тип узла загрузки, а не параметры вызова) — n8n-engineering-manual, references/roots.md R4.5; какие узлы у каких воркфлоу — `registry/tools.md`, раздел «Свойства канала целиком».
- Ответ инструмента: в файл или в контекст. Единого порога, после которого среда кладёт ответ инструмента в файл, а не в контекст, нет: в один день 58 тысяч символов ушли в файл, а 82 тысячи байт пришли в контекст → любое число про объём ответа — оценка, а не замер; параметры инструментов и шаги плана (например путь .xlsx в §4.0) на нём не строятся — путь проверяется одним вызовом в своей среде.
- Повтор при сбое Drive, Docs, Sheets: общего встроенного повтора нет вне узлов Sheets (§4.2) → повтор реализовывать явно, не больше 3 попыток. Для 500 и 503 — пауза по нарастающей, `wait = 2^attempt + random` секунд. Для 429 по минутной квоте эта формула не годится: повтор только после ожидания дольше минуты (n8n-engineering-manual R6.3).
- Правка jsonBody прямо в браузере может оборваться на `=` без ошибки до publish → в сохранённом JSON узла поле выражения хранится как `"={{ … }}"`; сверить через get_workflow_details. В поле редактора то же выражение пишется `{{ … }}` без `=` — одно правило о трёх местах записи: n8n-engineering-manual, references/engine.md §4.8.2.
- `/mnt/skills/` в сессии: снимок Skills может обновиться в том же чате — к следующему сообщению владельца, после заливки Skill (наблюдалось в облачной среде на основе Claude Code; похоже, зависит от среды) → после замены Skill перечитать его в той сессии, которая на него опирается, и сверить по якорю правки или побайтово; «в текущем чате не видно» не предполагать и не опровергать без чтения. Приёмка правки Skill — second-brain-git 2.6, second-brain-engineer Р13.
  Не путать: «`/mnt/skills/` — снимок на старт чата, замена Skill в текущем чате не видна» — опровергнуто наблюдением.

**Движок n8n — дом этих строк в n8n-engineering-manual; здесь только указатель.**
- n8n execute_workflow (MCP, production): `'started'` не гарантия выполнения, исполнение не видно, ответ не возвращается → read-back целевого объекта (§7); механизм — n8n-engineering-manual §1.1 и §8.
- Исполнение `success`, а цепочка тихо оборвалась в середине (ветка IF без продолжения, 0 items) → n8n-engineering-manual R3 и R4 (сверять число прогонов узла записи в ручном прогоне).
- HTTP-узел с `neverError:true`: код ошибки API проходит как валидный item → n8n-engineering-manual R4, T2 слой 3.
- Расписание или вебхук после правки и публикации не тикает при `active:true`; отсутствие исполнения в списке при несохраняемых успехах ничего не значит → n8n-engineering-manual R2.1, R2.2 (живость — по счётчикам `workflow_statistics`).
- Запись воркфлоу кодом целиком (`create_workflow_from_code`) молча теряет настройки, повторы, выражения IF/Switch, webhookId; привязки ключей существующих узлов НЕ сбрасываются; точечная форма `update_workflow` этих потерь в пробах не давала — кроме не проверенных точечной правкой узлов Switch и самого узла-вебхука → n8n-engineering-manual R1b (R1b.0, R1b.8); сверка до публикации — references/write.md §2.3; привязку проверять полем `credentials` в get_workflow_details — R1a.5.
  Не путать: «после update_workflow credential сбрасывается на заглушку» — опровергнуто (журнал инцидентов n8n — `projects/n8n/INCIDENT_LOG.md`); эта версия уже уводила диагноз мимо настоящей причины. Строка E12 таблицы §8 — о новом узле без привязки, а не о сбросе существующей.
- Смена ТИПА credential у узла сбрасывает его фильтры, опции и сопоставление колонок → после смены типа узел настраивается заново и сверяется; n8n-engineering-manual, references/roots.md, таблица симптомов (строка о смене типа ключа в узле Google Sheets).
- SDK `.to([a,b])`: второй получатель молчит навсегда → писать `.to(a).add(source).to(b)`; n8n-engineering-manual, references/engine.md §4.5.
- Отключённый (disabled) узел пропускает данные насквозь, не блокируя поток → проверять узлы ниже явно; n8n-engineering-manual R3.
- HTTP-узел перезаписывает `json`, поля прежних узлов теряются → брать их через `$('Узел').all()[i]`; n8n-engineering-manual R5, references/engine.md §4.8.6.
- `executeOnce` на любом месте цепочки, в том числе после Merge, обрабатывает только первый элемент и молча отбрасывает остальные → n8n-engineering-manual, references/engine.md §4.3.

## 10. ВЕРИФИКАЦИЯ БОЛЬШИХ ФАЙЛОВ

ЗАКОН РАЗДЕЛА. Число сверки (длина, контрольная сумма) сравнимо только с числом того же канала, снятым с тех же байт тем же способом; а совпадение чисел доказывает «прочитанное = лежащее в файле сейчас», но не «отправленное при записи = легло». Поэтому сверка крупного документа делается программно по файлу на диске, после нормализации, с названием канала, а запись проверяется построчно по содержанию.

**Порядок сверки крупного документа:** `download_file_content` с `exportMimeType text/plain` → ответ сохраняется целиком на диск → сравнение программно (длина, начало и конец, счётчики подстрок, построчный diff). Почему: текст в контексте вместо файла на диске не даёт надёжной побайтовой сверки крупного документа. Основание: случай не записан — отчёт синтеза, правило D.10.1.

**Нормализация перед сравнением обязательна**, иначе ложные расхождения: экспорт нативного Doc отдаёт `\r\n`, может добавлять BOM и превращать пустой абзац в дополнительный перевод строки; markdown-экранирование служебных символов (`\#`, `\*\*`, `\-`, `\_`, `\[`, `1\.`) в экспорте — тоже нормализуемый шум, не потеря данных. Поведение зависит от содержимого документа и не универсально — иногда экспорт не добавляет экранирования вовсе. Признак: после ручной вставки текста с форматированием экспорт text/plain расходится с исходником — это экранирование, а не порча. Основание: 2 случая, последний 2026-08-08 — отчёт синтеза, правило D.10.2.

**Хвост пустых абзацев.** Правка последнего непустого абзаца документа необратимо схлопывает пустые абзацы в его хвосте: ожидаемую контрольную сумму после такой правки считают по нормализованному хвосту, а восстановить прежние пустые абзацы не пытаются — восстановление не работает. Признак: после правки последнего абзаца контрольная сумма не сходится. Основание: 1 случай, последний 2026-08-27 — отчёт синтеза, правило D.10.3.

**Число сверки — вместе с названием канала.** Контрольная сумма и длина записываются вместе с названием канала, через который сняты: одно и то же содержимое через разные каналы даёт разные байты. download_file_content добавляет в начало метку порядка байт (BOM, 3 байта), gdocs-read её не добавляет. Канонический канал для чисел сверки — gdocs-read; сравнивать допустимо только числа одного канала. Как gdocs-read считает свои числа (над сырым текстом экспорта, без нормализации) — §3.5. Основание: 1 случай, дата в источнике не записана — отчёт синтеза, правило D.10.4.

**Граница применимости контрольной суммы.** `byteLength` и `checkSum` доказывают «полученное = лежащее в файле сейчас», но НЕ «отправленное при записи = легло в файл»: экспорт нативного Doc закономерно может немного менять байтовый размер (лишние пустые абзацы), и это не страховка записи. Верификация записи — построчная сверка содержания, а не только совпадение контрольной суммы. Основание: случай не записан — отчёт синтеза, правило D.10.5.

**download_file_content в диапазоне примерно 5–50 КБ** возвращает base64 инлайн в контекст, и эта строка не декодируется автоматически — контекст расходуется впустую на нечитаемые байты. В этом диапазоне читать через gdocs-read, не download_file_content. Основание: случай не записан — отчёт синтеза, правило D.10.6.
