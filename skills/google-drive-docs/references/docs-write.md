# google-drive-docs — запись в Google Docs

Часть Skill google-drive-docs. Читать: перед первой записью в документ в сессии. Номера разделов — прежние, общие с SKILL.md.

### 3.1 gdocs-append v2 (`YfzWwu1VmIUCbUu0`)
body `{fileId, text}` → `{success, fileId, ...}`. Read-back зашит в код (indexOf verifyToken по первым 40 символам). При `success:false` — читать `reason`, не повторять вызов вслепую.
Ведущий перевод строки в добавляемом тексте не съедается: Docs API превращает его в отдельные пустые абзацы (их выходит больше, чем в источнике). Для append это безопасно; при последующей побайтовой сверке эти пустые абзацы нужно нормализовать.
Документ, собранный через append много раз подряд, вносит машинные пустые строки на границах вставок. Любой инструмент, разбирающий текст по признаку «пустая строка = граница записи», на таком документе делит по границам вставки, а не по смысловым записям. Перед запуском такого сплиттера — проверять способ сборки документа (append много раз vs единая вставка).

### 3.2 gdocs-replace v2 (`nvNYvvmuOqGyHXfL`)
body `{fileId, search, replace}` → `{success, occurrencesChanged, context, reason}`. Read-back зашит в код (re-fetch + indexOf replace); `context` — ±150 символов вокруг точки совпадения.
МНОГОСТРОЧНЫЙ `search` НЕ ИСПОЛЬЗУЕТСЯ. По умолчанию — короткий однострочный якорь на каждую правку, даже если правок выходит больше. При вынужденном отступлении — одиночный `\n` (Docs API хранит параграфы через `\n`; `\r\n` из экспорта не матчится); составные многострочные блоки не пытаться вовсе. Причина запрета, а не совета: опасность не в промахе, а в попадании — промах виден (`occurrencesChanged: 0`), а совпадение, пересёкшее границу абзаца, склеивает хвост соседнего пункта с новым текстом и рапортует успех.
Guard K1 (`expectedOccurrences==1`) в gdocs-replace v2 делает массовое удаление текста через replace архитектурно невозможным — это намеренное свойство инструмента (страховка от неуникального якоря), а не баг. Многострочные чистки — только gdocs-overwrite v2 полным текстом, gdocs-apply-from-file в режиме overwrite (§3.6), либо руки владельца. Не пытаться обойти Guard K1 дроблением массового удаления на серию однострочных replace.
Копия строки в другом месте того же документа ломает все будущие правки этой строки: две одинаковые строки дают два вхождения якоря, и Guard K1 заблокирует и замену, и удаление. Поэтому, копируя строку внутри документа, копии обязательно дают уникальную пометку с местом и датой — «[перенесено из <раздел> <ГГГГ-ММ-ДД>]» в начале или в конце строки. Пример: строка, перенесённая из Зоны А в Зону Б, начинается с «[перенесено из Зоны А 2026-09-23]». Это профилактика класса П-03: без пометки дословная копия превращает любую следующую правку в отказ Guard K1.

ДЕСТРУКТИВНЫЙ REPLACE (удаление текста, `replace=""`) — отдельный протокол:
(а) ДО вызова скачать текст (gdocs-read) и посчитать вхождения якоря программно (`text.count(search)`). Требуется ровно 1. `occurrencesChanged` сообщает факт ПОСЛЕ того, как затёрто — это не защита, а протокол вскрытия постфактум.
(б) Якорь, неуникальный по смысловой фразе без даты/уникального хвоста, может дать `occurrencesChanged > 1` и затереть несколько мест одновременно. Откат — обратный replace тем же инструментом, подтверждать full-перечитыванием.
(в) «Проба безопасным маркером-заглушкой» — плохой метод: сама проба может быть неуникальной, и её вызов уже деструктивен. Считать вхождения, не пробовать.
(г) Якорь для удаления собирать с датой или уникальным хвостом строки, никогда — по одной смысловой фразе.
(д) При `replace=""` ответ воркфлоу `success:false` может быть ЛОЖНЫМ — запись при этом реальна (re-fetch indexOf по пустой строке не может пройти). Не повторять вызов вслепую — верифицировать только независимым перечитыванием файла (см. E16).

### 3.3 create_folder (`uapccJY1O4ykyDi7`)
Параметры `folder_name` и `parent_id` — ОБА обязательны (без любого — throw "Missing folder_name or parent_id"; для корня My Drive `parent_id:'root'`). Возвращает `folder_id` в ответе — повторный поиск после создания не нужен.

### 3.4 gdocs-overwrite v2 (`M5dqSv2yiklnDXoP`)
body `{fileId, newContent}` → `{success, fileId, bytesSent, bytesRead, reason}`. Read-back зашит в код: re-fetch (export для нативных Docs / alt=media для text-файлов), сверка первых и последних 100 символов с нормализацией `\r\n`. `404` → «file not found OR not shared to SA…», `403` → «permission denied».
Когда использовать: замена всего содержимого; replace не подходит (многострочная правка); пересоздание неприемлемо (ID меняется). Работает с ЛЮБЫМ mimeType (native Doc, .md, .txt). Только plain text — форматирование теряется. Полный текст идёт через тело вызова, поэтому для текста крупнее примерно 1–2 КБ брать gdocs-apply-from-file (§3.6): на объёме около 29 КБ у этого инструмента уже портились байты (инцидент 31.07).
Ограничение bytesRead: export нативного Doc может добавлять BOM/финальный перенос строки — сверка идёт по head/tail 100 символов, не по побайтовому равенству.

### 3.6 gdocs-apply-from-file (`fdiWemSCln1WA8gt`) — запись большого текста из файла
body `{targetId, sourceId, mode, search?}` → `{ok, mode, bytesWritten, targetByteLength, targetCheckSum, expectedCheckSum, match}`.
- `targetId` — Google Doc, в который пишем.
- `sourceId` — файл на Drive, из которого берётся текст: нативный Doc (экспортируется как text/plain) или текстовый файл.
- `mode`: `append` — дописать в конец; `overwrite` — стереть всё и записать текст источника; `replace` — заменить единственное вхождение строки `search` текстом источника. Если вхождений не ровно одно, воркфлоу отказывает с `REPLACE_ANCHOR_NOT_UNIQUE` и документ не трогает.

Текст через тело вызова не проходит, поэтому граница 1–2 КБ из §3 здесь не действует. Пределы: заявлено 1 500 000 символов одним вызовом (паспорт наряда Н-26.08-03), независимо не перепроверено; независимо подтверждена запись 174 326 Б (регрессионная мишень TEST_GDOCS_APPLY, `registry/tools.md`); отказ Docs API зафиксирован на 1 900 000. Граница между 1,5 и 1,9 миллиона не измерена.

Проверка чтением встроена: воркфлоу перечитывает документ и сравнивает контрольную сумму FNV-1a с ожидаемой; `match:false` — запись не подтверждена. Как и для остальных инструментов записи, итог подтверждается независимым чтением gdocs-read (§7), а не ответом воркфлоу.

Режим `overwrite` выполняет полное удаление и перезапись одним вызовом — это машинный путь для многострочной чистки, которую gdocs-replace v2 из-за Guard K1 сделать не может (§3.2). Форматирование, как и у gdocs-overwrite v2, не сохраняется: пишется plain text (ловушка красивого документа, §2.1).

Все узлы загрузки воркфлоу — типа `n8n-nodes-base.httpRequest`: `get_execution(includeData:true)` принесёт в контекст полный текст документа (§9). Статус брать с `includeData:false`, итог — чтением gdocs-read.
