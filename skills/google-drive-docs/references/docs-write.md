# google-drive-docs — запись в Google Docs

Редакция 2026-10-22.

Часть Skill google-drive-docs. Читать: перед первой записью в документ в сессии. Номера разделов — прежние, общие с SKILL.md.

**Закон файла. Каждый инструмент записи проверяет себя сам, но смотрит на узкий кусок результата — первые 40 символов, первые и последние 100, исчезновение якоря, контрольную сумму, — и у каждой такой проверки есть слепая зона.** Поэтому ответ инструмента — сигнал, а не доказательство: итог любой записи подтверждается независимым чтением целевого документа через gdocs-read (§7, основной файл), а при отказе со следами записи вызов не повторяется вслепую — сначала читается файл. Слепая зона каждого инструмента названа в его разделе.

ID каждого воркфлоу ниже — по правилу §1 основного файла: по имени воркфлоу из строки `registry/n8n-map.md`, а если имя там замаскировано — из `registry/tools.md`.

Имя узла-триггера (`triggerNodeName`) каждого воркфлоу ниже — так же не по памяти и не по аналогии с Каналом git: из `get_workflow_details` этого воркфлоу или из его сигнатуры в `registry/tools.md` (§3 основного файла, «Форма вызова»; ошибка — E23).

### Цель разрушительной правки — до вызова

ЦЕЛЬ РАЗРУШИТЕЛЬНОЙ ПРАВКИ — перезаписи (overwrite, apply-from-file в режиме overwrite) и удаляющего replace — подтверждается до вопроса Андрею и до вызова: имя и время изменения из get_file_metadata по этому ID, содержимое из gdocs-read, ID из реестра (`registry/documents.md`), а не из памяти и не из старого текста. Почему: то, что ID открывается и ведёт к настоящему файлу, не доказывает, что это тот файл, — ID из памяти может вести к архивной копии того же документа, и правка удалит в ней то, чего нет в живой версии. Имя файла в отчёте и в вопросе Андрею пишется только из метаданных. Архивную или замороженную копию не правят.
[основание: DW-01 · правило B.W.1]

### 3.0 Текст через тело вызова — граница 1–2 КБ

**Текст крупнее примерно 1–2 КБ через тело вызова gdocs-append, gdocs-replace или gdocs-overwrite v2 не передавать; штатный путь для большого текста — gdocs-apply-from-file (§3.6).** Почему: у инструментов, принимающих текст телом вызова, на настоящем тексте уже портились байты (gdocs-overwrite v2, около 29 КБ), а чистые замеры на больших объёмах сделаны на синтетическом тексте; порча зависит от содержимого, а не только от объёма, поэтому замер на синтетике безопасную границу для настоящего текста не даёт. Число 1–2 КБ — осторожная граница, а не найденный предел.
Не путать: «число 1–2 КБ не измерено ни для одного из трёх инструментов» — на деле измерено: gdocs-overwrite v2 чисто записал 20 и 40 КБ, gdocs-replace v2 — 40 КБ, но на синтетическом тексте (кириллица без эмодзи); граница остаётся по причине выше.
Условие пересмотра числа: замер на настоящем тексте с кириллицей и эмодзи.

Порядок путей для текста крупнее границы:
1. gdocs-apply-from-file (§3.6): текст сначала кладётся отдельным файлом на Google Drive, воркфлоу берёт его оттуда сам, через тело вызова текст не проходит.
2. Запасной путь, если gdocs-apply-from-file недоступен: дробление на порции по 1–2 КБ. Каждая порция подтверждается чтением до перехода к следующей — иначе теряется знание о том, какая порция легла, а какая нет. После последней порции весь собранный текст сверяется с источником целиком — по стыкам порций или побайтно после нормализации (§10). Почему: проверка каждой порции по отдельности разрыва или опечатки на границе двух порций не видит. Признак ложной приёмки: каждая порция проверку прошла, а целого текста против источника никто не сверял.
3. Ручная вставка владельцем (текст собирается на диске, владелец вставляет его в Doc, затем чтение для проверки) — только для объёма выше подтверждённого у gdocs-apply-from-file (§3.6) или при отказе этого инструмента.
Короткие правки в несколько строк идут одним вызовом.

[основание: DW-02 · правило B.3.0.1, B.3.0.2, B.3.0.3]

### 3.1 gdocs-append v2

Воркфлоу «Claude → Google Docs Append v2 (verified)»; ID — по правилу §1.
body `{fileId, text}` → `{success, fileId, ...}`. Read-back зашит в код: indexOf токена проверки — первых 40 символов текста.

**Слепая зона встроенной проверки.** Токен ищется по всему документу, а не в его хвосте: если эти 40 символов уже есть в документе — повтор строки, общий заголовок записи, строка-разделитель, — `success:true` выйдет и при несостоявшейся дозаписи. Итог — только чтение хвоста через gdocs-read. При `success:false` — читать `reason`, не повторять вызов вслепую.

**Куда пишет.** Только в конец документа. Вставки в середину документа — в конец зоны, перед маркером, в раздел — append не умеет: это gdocs-replace по однострочному якорю, где якорь заменяется на «новый текст + перевод строки + тот же якорь» (§3.2, абзац «Многострочный текст на месте однострочного якоря»).

**Переводы строк.** Воркфлоу сам ставит один перевод строки перед текстом. Ведущий перевод строки в добавляемом тексте не съедается: Docs API превращает его в отдельные пустые абзацы, и их выходит больше, чем в источнике. Для append это безопасно; при последующей побайтовой сверке эти пустые абзацы нужно нормализовать (§10).

**Документ, собранный дозаписями.** Текст, собранный несколькими дозаписями, принимается сверкой всего собранного текста или каждого стыка, а не чтением каждой порции по отдельности (§3.0, пункт 2). Документ, собранный через append много раз подряд, несёт машинные пустые строки на границах вставок. Любой инструмент, разбирающий текст по признаку «пустая строка = граница записи», на таком документе делит по границам вставки, а не по смысловым записям. Перед запуском такого разборщика — проверить способ сборки документа (append много раз против единой вставки).

[основание: DW-03 · правило B.3.1.1, B.3.1.2]

### 3.2 gdocs-replace v2

Воркфлоу «Claude → Google Docs Replace v2 (verified)»; ID — по правилу §1.
body `{fileId, search, replace}` → `{success, occurrencesChanged, context, reason}`. Read-back зашит в код (повторная загрузка документа и indexOf нового текста); `context` — ±150 символов вокруг точки совпадения.

**Закон раздела. Якорь — одна короткая строка, которая в документе встречается ровно один раз, и остаётся единственной после правки.** Почему: инструмент находит и меняет все вхождения якоря; промах виден сразу (`occurrencesChanged: 0`), а лишнее попадание — нет: оно меняет чужое место и рапортует успех. Все правила ниже — частные случаи.

**МНОГОСТРОЧНЫЙ `search` НЕ ИСПОЛЬЗУЕТСЯ.** По умолчанию — короткий однострочный якорь на каждую правку, даже если правок выходит больше. При вынужденном отступлении — одиночный `\n` (Docs API хранит параграфы через `\n`; `\r\n` из экспорта не матчится); составные многострочные блоки не пытаться вовсе. Причина запрета, а не совета: совпадение, пересёкшее границу абзаца, склеивает хвост соседнего пункта с новым текстом и рапортует успех.

**Многострочный текст на месте однострочного якоря.** Запрещён многострочный `search`, а не многострочный `replace`: вставка нескольких строк на место однострочного якоря допустима. Так вставляют блок перед маркером: якорь-маркер заменяется на «блок + перевод строки + тот же маркер». Многострочный фрагмент самого документа меняется через gdocs-overwrite v2 (§3.4) или gdocs-apply-from-file (§3.6). Блок крупнее примерно 2 КБ вставляется не телом вызова, а через gdocs-apply-from-file в режиме `replace` с тем же однострочным якорем (§3.0, §3.6).
[основание: DW-04]

**Guard K1.** Инструмент отказывает, если якорь встречается не ровно один раз (`expectedOccurrences==1`). Это делает массовое удаление текста через replace архитектурно невозможным — намеренное свойство инструмента (страховка от неуникального якоря), а не баг. Многострочные чистки — только gdocs-overwrite v2 полным текстом, gdocs-apply-from-file в режиме overwrite (§3.6) либо руки владельца. Не пытаться обойти Guard K1 дроблением массового удаления на серию однострочных replace.
[основание: DW-05 · правило B.3.2.1]

**Копия строки внутри документа получает уникальную пометку.** Копируя строку в другое место того же документа, копии обязательно дают пометку с местом и датой — «[перенесено из <раздел> <ГГГГ-ММ-ДД>]» в начале или в конце строки. Пример: строка, перенесённая из Зоны А в Зону Б, начинается с «[перенесено из Зоны А 2026-09-23]». Почему: две одинаковые строки дают два вхождения якоря, и Guard K1 заблокирует и замену, и удаление этой строки навсегда.
[основание: DW-06 · правило B.3.2.2]

**Символы в якоре.** Длинное тире (—) в якоре матчится штатно, как любой другой символ строки. Опасность якоря вся в его неуникальности, а не в конкретном символе внутри него.
Не путать: «якорь с тире лучше не брать» — на деле тире матчится штатно; перестраховка опровергнута прогонами.
[основание: DW-07 · правило B.3.2.3]

**Символы в полях `search` и `replace` набираются как есть** — кириллица, тире, кавычки-ёлочки, — а не последовательностями `\uXXXX`. Общее правило набора и его причина для Канала git (цена вывода) — Skill `second-brain-git`, `references/write.md`, пункт 8.2. Здесь причина своя: транспорт такие последовательности декодирует верно, опасность в самой модели — она набирает неверный код, и в документ ложится чужой символ, который Guard K1 не ловит (в Канале git, наоборот, содержимое не портится). Если последовательности всё же набраны, обратное чтение сверяется по кодам символов программно, а не на глаз.
[основание: DW-08 · правило B.3.2.4]

ДЕСТРУКТИВНЫЙ REPLACE (удаление текста, `replace=""`) — отдельный протокол:
(а) ДО вызова скачать текст (gdocs-read) и посчитать вхождения якоря программно (`text.count(search)`). Требуется ровно 1. `occurrencesChanged` сообщает факт ПОСЛЕ того, как затёрто, — это не защита, а протокол вскрытия постфактум.
(б) Якорь, неуникальный по смысловой фразе без даты или уникального хвоста, может дать `occurrencesChanged > 1` и затереть несколько мест одновременно. Откат — обратный replace тем же инструментом, подтверждать полным перечитыванием.
(в) «Проба безопасным маркером-заглушкой» — плохой метод: сама проба может быть неуникальной, и её вызов уже деструктивен. Считать вхождения, не пробовать.
(г) Якорь для удаления собирать с датой или уникальным хвостом строки, никогда — по одной смысловой фразе.
(д) Проверка после удаления — по исчезновению якоря: инструмент перечитывает документ и ставит `success:true`, если якоря в тексте больше нет (`verifiedBy=absence-of-search`; это поле в ответ вебхука не выходит, видно только внутри `reason`). `success:false` при `occurrencesChanged>0` значит, что удаление в документе состоялось, а проверка после него не прошла: перечитанный текст пуст или якорь в нём всё ещё найден. Не повторять вызов вслепую — верифицировать только независимым перечитыванием файла (E16).
Не путать: «при удалении `success:false` ложный всегда, потому что indexOf по пустой строке не может пройти» — так было в коде до версии 2026-09-25; на деле удаление проверяется по исчезновению якоря.
[основание: DW-09 · правило B.3.2.5]

### 3.4 gdocs-overwrite v2

Воркфлоу «Claude → Google Docs Overwrite v2 (verified)»; ID — по правилу §1.
body `{fileId, newContent}` → `{success, fileId, bytesSent, bytesRead, reason}`. Read-back зашит в код: повторная загрузка (export для нативных Docs, alt=media для text-файлов), сверка первых и последних 100 символов с нормализацией `\r\n`. `404` → «file not found OR not shared to SA…», `403` → «permission denied».

**Когда использовать:** замена всего содержимого; replace не подходит (многострочная правка); пересоздание неприемлемо (ID меняется). Работает с ЛЮБЫМ mimeType (native Doc, .md, .txt). Только plain text — форматирование теряется (ловушка красивого документа, §2.1). Текст крупнее примерно 1–2 КБ — не этим инструментом, а gdocs-apply-from-file (§3.0, §3.6).

**Слепая зона встроенной проверки.** Сверка идёт по первым и последним 100 символам, а не побайтно: export нативного Doc может добавлять BOM и финальный перенос строки, поэтому `bytesRead` с `bytesSent` побайтно не совпадают и совпадать не обязаны. Середина документа этой проверкой не видна — итог по §7.

**`newContent` передаётся только строкой.** Воркфлоу пишет поле как есть, а проверка сравнивает начало и конец документа со строковым представлением `newContent`; тип поля никто не проверяет. Объект вместо строки, по коду, ляжет в документ сжатым JSON, а проверка ответит `success:false` «content mismatch on first/last 100 chars» при состоявшейся записи. При таком ответе вызов не повторять — читать файл (E21). Механизм выведен из кода, не воспроизведён.
[основание: DW-11 · правило B.3.0.1, B.3.4.2, B.3.4.1]

### 3.6 gdocs-apply-from-file — запись большого текста из файла

Воркфлоу gdocs-apply-from-file; его имя в `registry/n8n-map.md` замаскировано, поэтому ID — из строки GDOCS_APPLY_FROM_FILE файла `registry/tools.md` (правило §1).
body `{targetId, sourceId, mode, search?}` → `{ok, mode, bytesWritten, targetByteLength, targetCheckSum, expectedCheckSum, match}`.
- `targetId` — Google Doc, в который пишем.
- `sourceId` — файл на Drive, из которого берётся текст: нативный Doc (экспортируется как text/plain) или текстовый файл.
- `mode`: `append` — дописать в конец; `overwrite` — стереть всё и записать текст источника; `replace` — заменить единственное вхождение строки `search` текстом источника. Если вхождений не ровно одно, воркфлоу отказывает с `REPLACE_ANCHOR_NOT_UNIQUE` и документ не трогает.

**Почему этот путь.** Текст через тело вызова не проходит, поэтому граница 1–2 КБ из §3.0 здесь не действует. Пределы: заявлено 1 500 000 символов одним вызовом, независимо не перепроверено; независимо подтверждена запись 174 326 Б (регрессионная мишень — строка TEST_GDOCS_APPLY файла `registry/tools.md`); отказ Docs API зафиксирован на 1 900 000. Граница между 1,5 и 1,9 миллиона не измерена.

**Две ловушки — обе дают ложный успех или непонятный отказ:**
- В режиме `replace` многострочный `search` не работает. С переводом строки `\n` воркфлоу отказывает «0 вхождений»; с `\r\n` возвращает успех, а документ не меняется. Якорь — одна строка, как и у gdocs-replace v2 (§3.2); итог в любом случае проверяется чтением, а не ответом.
- Файл-источник (`sourceId`) обязан лежать там, куда есть доступ у сервисного аккаунта; иначе отказ `SOURCE_NOT_ACCESSIBLE`. Файл, созданный create_file от имени владельца вне расшаренных папок, сервисному аккаунту не виден — класть источник в расшаренную папку или расшаривать его до вызова. Общие правила доступа сервисного аккаунта — §6.2 (`references/infra.md`).

**Слепая зона встроенной проверки.** Воркфлоу перечитывает документ и сравнивает контрольную сумму FNV-1a с ожидаемой; `match:false` — запись не подтверждена. Совпадение суммы доказывает «прочитанное = то, что воркфлоу считал ожидаемым», а не «текст = замысел» (граница применимости контрольной суммы — §10). Итог подтверждается независимым чтением gdocs-read (§7), а не ответом воркфлоу.

**Режим `overwrite`** выполняет полное удаление и перезапись одним вызовом — это машинный путь для многострочной чистки, которую gdocs-replace v2 из-за Guard K1 сделать не может (§3.2). Форматирование, как и у gdocs-overwrite v2, не сохраняется: пишется plain text (ловушка красивого документа, §2.1).

**Статус исполнения — без данных.** Узлы загрузки этого воркфлоу — типа `n8n-nodes-base.httpRequest`, поэтому `get_execution(includeData:true)` принесёт в контекст полный текст документа (механизм — Skill `n8n-engineering-manual`, `references/roots.md`, правило R4.5; для Docs — §9). Статус брать с `includeData:false`, итог — чтением gdocs-read.

[основание: DW-12 · правило B.3.6.1, B.3.6.2]
