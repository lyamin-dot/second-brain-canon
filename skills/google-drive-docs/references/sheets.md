# google-drive-docs — Google Sheets

Часть Skill google-drive-docs. Читать: перед любой работой с Google Sheets — чтение, дозапись, создание книги, проектирование листов, которые пишет робот, Apps Script, формулы, узел Sheets в n8n. Номера разделов — прежние, общие с SKILL.md.

## 4. GOOGLE SHEETS

ЗАКОН РАЗДЕЛА. Таблица — общий носитель людей, формул и роботов, и Google разбирает и размещает каждую запись по своим правилам, а не по намерению пишущего: строка становится формулой, число — датой, строки ложатся не туда, формула заменяется значением, чужая ячейка перезаписывается — и ни одно из этого не даёт ошибки. Поэтому: перед записью — прочитать, писать только в своё, после записи — прочитать снова; ответ инструмента записи доказательством не является (§7 SKILL.md).

ЛИСТ — ЕДИНИЦА ВЛАДЕНИЯ. Один лист пишет один хозяин — человек или робот. Почему: внутри листа у Google нет границы, которая удержала бы робота: историю версий Google воркфлоу не читает, защищённый диапазон сервисный аккаунт может не соблюдать (§6.2 (е)), а робот, пересобирающий лист целиком, стирает всё, чего нет в его выходе (корень R18 Skill n8n-engineering-manual). Раздельные листы снимают вопрос конструкцией, а не дисциплиной.
- ЧУЖИЕ ЛИСТЫ. Если Андрей сказал, что над файлом работает другой человек, запись идёт только на отдельный лист, который создаёт сессия или робот; в существующие листы такого файла не пишут.
- РУЧНОЙ ВВОД И ВЫВОД РОБОТА — НА РАЗНЫХ ЛИСТАХ. При проектировании книги, которую ведёт робот (воркфлоу или скрипт), всё, что человек вводит руками — пометки, поправки, ручные цены, параметры, — живёт на отдельном листе; робот этот лист только читает, а пишет только свои листы. Признак нарушения: ручная правка пропала после очередного прогона робота. Если ручной ввод всё же остаётся на перестраиваемом листе, скрипт сохраняет его до перестройки и возвращает по ключу — Skill apps-script-sheets, §4.2.
[основание: SH-01 · правило C.4.S1, C.4.S2]

### 4.0 Чтение Google Sheets — только gsheets-read

ЗАКОН ПОДРАЗДЕЛА. Каждый путь чтения таблицы отдаёт свою часть книги: экспорт CSV — только первый лист, `read_file_content` — образец строк, и оба о неполноте не сообщают; `gsheets-read` — значения и формулы без оформления и не больше `maxRows` строк диапазона, и о неполноте сообщает только полями ответа. Поэтому путь выбирают по тому, что нужно увидеть (абзац «Выбор пути чтения» ниже), а полноту ответа доказывают его поля (`truncated`, `rowCount`, `reason`), а не то, что строки пришли. Это частный случай закона §2.2 (references/mcp.md): ответ доказывает только то, что вернул этот вызов.

Инструмент — воркфлоу «Claude → Google Sheets Read»; ID — по правилу §1 SKILL.md. Инструмент только читает: записи в нём нет и не добавляется — чтение и запись в одном вебхуке с произвольным `fileId` расширяют круг того, что можно испортить одним вызовом (корень R12 Skill n8n-engineering-manual).

body `{fileId, mode: "meta"|"range", sheetName?, range?, render?, maxRows?}` → `{success, fileId, mode, spreadsheetTitle, sheets, sheetName, range, render, rows, rowCount, returnedRows, truncated, maxRows, reason}`.
Вызов — `n8n:execute_workflow`, `executionMode: "manual"` (в `production` тело ответа не возвращается и исполнение не видно — корень R4 Skill n8n-engineering-manual), имя узла-триггера — из `get_workflow_details`; форма вызова — §3 SKILL.md, её дом — Skill n8n-engineering-manual §1.1. Аутентификация вебхука вызов из сессии через MCP не затрагивает — корень R15 того же Skill.

ПОРЯДОК: СНАЧАЛА `mode:"meta"` — список листов с их размерами; затем `mode:"range"` на конкретный лист. Диапазон вслепую не запрашивать: без размеров листа не видно, весь ли он попал в диапазон.

Поля:
- `fileId` — всегда; `mode` — всегда, иное значение → воркфлоу падает; `sheetName` — обязателен при `mode:"range"`, имя листа внутри `range` не работает. Имя листа экранируется внутри воркфлоу, кавычки руками не подставлять.
- `range` — адрес A1 без имени листа (`A1:G12`). Без него читается весь лист.
- `render`: `UNFORMATTED_VALUE` — числа числами (по умолчанию); `FORMATTED_VALUE` — как отображается в интерфейсе; `FORMULA` — текст формул вместо результатов. Формулу (VLOOKUP, IMPORTRANGE) не отдаёт ни один текстовый экспорт и ни один другой режим — только `FORMULA`.
- Даты приходят сериальными числами Google Sheets, не строками.

ТРИ СОСТОЯНИЯ УСПЕШНОГО ОТВЕТА, которые НЕЛЬЗЯ путать:
- `success:true`, `truncated:false` — диапазон прочитан целиком.
- `success:true`, `truncated:true` — в диапазоне больше строк, чем `maxRows` (по умолчанию 500); вернулись только первые. Возвращённые строки НЕ являются всем диапазоном — сузить диапазон или поднять `maxRows`. Число реальных строк — в `reason` и `rowCount`.
- `success:true`, `rows:[]` с текстом EMPTY RANGE в `reason` — диапазон прочитан и он пуст: Sheets API не присылает поле `values`, когда данных нет. Это НЕ провал чтения.
При `success:false` смотреть `reason`: он отдельно различает выключенный Sheets API в проекте Google Cloud сервисного аккаунта (SERVICE_DISABLED — не проблема расшаривания), файл не найден или не расшарен на сервисный аккаунт, отказ по правам.

ЛОЖНАЯ ОШИБКА ТЯЖЁЛОЙ КНИГИ. Книга, которая пересчитывается минутами, может ответить на обращение «Document … is missing (perhaps it was deleted…)», хотя файл на месте: метаданные Drive и gsheets-read файл видят, а повторный запрос проходит. Перед выводом «файл удалён» — повторить запрос и проверить файл через `get_file_metadata`. Что считается тяжёлой книгой и как с ней работать изнутри — Skill apps-script-sheets, references/book-traps.md, §3.7. Тот же корень у воркфлоу, который читает лист тяжёлой книги узлом Google Sheets: узел висит минутами и отдаёт успех с нулём строк или ошибку 503 — правило в §4.2, «Чтение».

ОФОРМЛЕНИЯ gsheets-read НЕ ОТДАЁТ ни в одном режиме: числовые форматы, ширины колонок, высоты строк, заливка, шрифт, правила условного форматирования, проверки данных и графики в его ответе отсутствуют — есть только значения и формулы. Оформление снимается только дампом через Apps Script, который запускает владелец: скрипт пишет снимок на отдельный лист или в отдельную книгу, и этот снимок читается обычным `mode:"range"`. Методы дампа — Skill apps-script-sheets, §1 «Порядок работы», шаг 1. Шаг «прочитать оформление через gsheets-read» в план и в эстафету не ставится — он неисполним.

ЗАПРЕЩЕНО для Sheets:
- `read_file_content` (MCP). §0 п.2 SKILL.md действует и для таблиц: порог обрезки большого файла неизвестен (§0 SKILL.md, правило 2, первая причина), адресации по листам и диапазонам нет вовсе, а по таблице инструмент отдаёт лишь образец около 5 строк на лист.
- Экспорт в `text/csv` через `download_file_content`. Google экспортирует ТОЛЬКО ПЕРВЫЙ ЛИСТ, без предупреждения; на многолистовой книге это тихая потеря остальных листов. Все листы книги одним файлом даёт только экспорт .xlsx (абзац ниже).

РАЗОВЫЙ РАЗБОР ТАБЛИЦЫ ЦЕЛИКОМ: `download_file_content` с `exportMimeType: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` → файл на диске → `openpyxl` (`data_only=False` — формулы, `data_only=True` — значения). Условие, без которого путь планировать нельзя: инструмент возвращает файл base64-строкой В ОТВЕТЕ и сам файла на диске не создаёт. Файлом ответ становится, только если среда сама кладёт крупный ответ инструмента в файл — такое наблюдалось в среде с bash при ответе выше примерно 50 КБ, порог не гарантирован (§9, запись «Ответ инструмента: в файл или в контекст»; наблюдения порога — `registry/tools.md`, абзац «Чтение больших ответов»). Если ответ пришёл в контекст, путь закрыт: base64 через контекст портится (§2.2 п.4, §10). Поэтому перед тем как ставить этот путь шагом плана, его проверяют в своей среде одним вызовом; в Claude Project без bash он неисполним.

ВЫБОР ПУТИ ЧТЕНИЯ: `gsheets-read` — когда нужно посмотреть (структура, диапазон, формула). Среда с bash и .xlsx на диске — когда нужно посчитать по всему массиву в десятки тысяч строк или прочитать все листы разом. Дамп Apps Script — когда нужно оформление.

[основание: SH-02 · правило C.4.0.1, C.4.0.2, C.4.0.3, C.4.0.4, C.4.0.5]
### 4.0а Дозапись строк в Google Sheets — gsheets-append

Инструмент — воркфлоу «Claude → Google Sheets Append»; ID — по правилу §1 SKILL.md.

body `{fileId, sheetName, rows}` → `{success, fileId, sheetName, rowsRequested, updatedRange, updatedRows, reason}`.
- `fileId` — ID книги; `sheetName` — имя листа как есть, кавычки воркфлоу ставит сам; `rows` — непустой массив строк, каждая строка — массив значений ячеек (`[["2026-09-27", "WB", 1250]]`).
- Пустое или неверное поле — воркфлоу падает на разборе входа («Missing fileId», «Missing sheetName», «Missing or empty rows…», «Each row must be an array…») и ответа не отдаёт; в режиме manual причина видна в статусе исполнения.
- Вызов — `n8n:execute_workflow`, `executionMode: "manual"`, `triggerNodeName` из `get_workflow_details`, `inputs: {webhookData: {method: "POST", body: {…}}}` без поля `type` — §3 SKILL.md, дом формы — Skill n8n-engineering-manual §1.1. Аутентификация вебхука вызов через MCP не затрагивает — корень R15 того же Skill.

ЧТО ДЕЛАЕТ: один запрос Sheets API v4 `values:append` к диапазону `'<лист>'!A1` с параметрами `valueInputOption=USER_ENTERED` и `insertDataOption=INSERT_ROWS`, под тем же ключом сервисного аккаунта (тип `googleApi`), что gsheets-read. Книга должна быть расшарена на сервисный аккаунт с правом редактора; иначе `success:false` и `reason` «permission denied…». `success:true` ставится только при наличии в ответе Google объекта `updates`; без него — `success:false` и `reason` «APPEND DID NOT HAPPEN…».

ТРИ ЛОВУШКИ, все следуют из параметров запроса:
- `USER_ENTERED` — значения разбираются так, будто их набрали руками в интерфейсе. Строка, начинающаяся с `=`, становится живой формулой; число и дата разбираются по локали книги (в `ru_RU` «1,5» — число, а «1.5» может стать датой или текстом); строка вида «+49…» может стать числом. Локаль у каждой книги своя — определять по самой книге, а не по привычке (Skill apps-script-sheets, §2.1, зонд разделителя). Текст, который должен остаться текстом, передавать с ведущим апострофом (`"'=A1"`) — как в Skill apps-script-sheets, §2.5.
- Место дозаписи выбирает Google: он ищет «таблицу» от ячейки A1 листа и пишет после её последней строки. Пустая строка внутри данных может увести запись в середину листа, а не в конец. `INSERT_ROWS` вставляет новые строки, а не перезаписывает нижележащие. Фактический адрес записи — всегда по `updatedRange`.
- Повтор при сбое удваивает строки. Узел запроса стоит с повтором при сбое (`retryOnFail`), а `values:append` не идемпотентен: если первый запрос дошёл до Google, а ответ потерялся по таймауту, повтор допишет те же строки второй раз. Поэтому после любого `success:false` с причиной «request failed…» сначала читать лист, потом решать о повторе — не повторять вслепую (тот же класс, что E16).

ПРОВЕРКА — не ответ воркфлоу, а чтение: gsheets-read `mode:"range"` по диапазону из `updatedRange`, сверка числа строк с `rowsRequested` и значений с отправленными. Ответ Google у этого воркфлоу оседает в contextData узла запроса (свойство типа узла `httpRequest` — корень R4 Skill n8n-engineering-manual), но он мал — объект `updates`, — и цена этого в контексте ничтожна.

[основание: SH-03 · правило C.4.0а.1]

### 4.1 Создание таблиц — структура создаётся кодом

Правило не «только Apps Script», а «структура таблицы создаётся кодом, а не руками в интерфейсе». Почему: код можно перечитать, повторить и сверить; ручная разметка не воспроизводится и расходится с тем, что ждут формулы и воркфлоу. Путей два:
- **Apps Script.** Скрипт вставляется в script.google.com и запускается владельцем вручную (Run). Путь для книги, которую дальше перестраивает тот же скрипт: витрины, оформление, формулы.
- **Пустая книга коннектором Drive, структура — воркфлоу через Sheets API.** Сессия создаёт пустую книгу от имени владельца коннектором Drive в нужной папке и расшаривает её на сервисный аккаунт с правом редактора; листы, шапки и служебные колонки создаёт сам воркфлоу, который с этой книгой работает, при первом запуске (запросами к Sheets API). Путь для книги, которую ведёт робот n8n. Почему файл — от владельца, а структура — от робота: создать файл сам сервисный аккаунт не может (§6.2 (в)). Точная форма вызова создания книги коннектором нигде не записана — результат проверять чтением, а не ответом create_file.
Проверка в обоих путях одна: чтение созданного через gsheets-read `mode:"meta"` и `mode:"range"` по шапкам.
[основание: SH-04 · правило C.4.1.1]

ПЕРЕД ЛЮБОЙ ПЕРЕДЕЛКОЙ СУЩЕСТВУЮЩЕЙ КНИГИ читать парный Skill `apps-script-sheets`. Три ловушки оттуда, каждая из которых уже стоила полного прогона:
- `setFormula` пишет формулу буквально, без перевода в локаль книги (в `ru_RU` разделитель аргументов `;`, разделитель колонок в массивах `\`) — Skill apps-script-sheets, §0.2 и §2.1;
- редактор Apps Script запускает первую функцию файла, а не выбранную мысленно — там же, §2.2;
- очистка листа без предварительного поиска ссылок на него убивает чужие формулы молча — там же, §0.1.

Прочие правила скрипта, который строит книгу:
- условное правило форматирования вызывается `whenFormulaSatisfied`, не `whenFormula` — второго метода нет, скрипт падает;
- единое пространство имён, одна функция `onOpen` на проект, константы с префиксом: все файлы проекта Apps Script делят одну область видимости, и одноимённые функции подменяют друг друга;
- `parseFloat(x)||0` при чтении параметров даёт тихий ноль: невалидный или пустой порог становится законным нулём. Пороги валидировать всегда — падать при невалидном пороге, не подставлять 0 молча (общий закон — корень R19 Skill n8n-engineering-manual);
- условное форматирование пересоздавать скриптом (функция вида `setupConditionalFormatting()`), не чинить в интерфейсе вручную: ручная правка не воспроизводится при следующей пересборке.
[основание: SH-05 · правило скрипта, C.4.1.2]

### 4.2 Узел Google Sheets в n8n

Общий закон узла — корень R6 Skill n8n-engineering-manual (привязка через имена колонок, позиции строк, типы и общий счётчик квоты; служебное состояние — вне Sheets). Здесь — то, чего в R6 нет, и указатели. Пункты о тяжёлой книге и об именованных диапазонах действуют и тогда, когда воркфлоу ходит в книгу не узлом Google Sheets, а запросом к Sheets API из HTTP-узла; остальные пункты «Чтение» — свойства самого узла.

ЧТЕНИЕ:
- Get Row(s) — без фильтров; колонка A:A может прийти под именем `'A: field'` — проверять оба варианта имени (E08). Почему — в прежнем тексте не записано.
- У чтения Sheets версии 4.7 опции ограничения числа строк нет: в параметрах только `filtersUI`, `combineFilters` и в `options` — `dataLocationOnSheet`, `outputFormatting`, `returnFirstMatch`, `returnAllMatches`. Порцию ограничивать отдельным узлом Limit после чтения: без него каждая строка листа становится отдельным элементом, и следующий узел делает столько же параллельных вызовов внешнего API. Между узлами, которые сопоставляют элементы по позиции через `$items`, режим узла Limit не менять — сдвинется сопоставление.
  Не путать: «`returnAllMatches` и `limit` конфликтуют — использовать только `limit`» — на деле опции `limit` у чтения этой версии нет (E09).
- `documentId` и `sheetName` — через выражение `={{ 'ID' }}`. Почему — в прежнем тексте не записано.
- IMPORTRANGE ломается на таблицах больше 18 000 строк — такие данные писать в книгу напрямую из n8n, а не тянуть формулой (E10). Прямая ссылка `=лист!$K$4` вместо VLOOKUP. Почему — в прежнем тексте не записано.
- Разделитель аргументов формул, которые пишет узел, — по локали книги (в `ru_RU` — `;`). Литерал массива `{…}` в формуле, которую пишет воркфлоу, — §4.3.
- **Лист тяжёлой книги узлом не читать — читать лёгкий источник, из которого этот лист собран.** Тяжёлая книга — та, что пересчитывается минутами (определение — Skill apps-script-sheets, references/book-traps.md, §3.7). Если нужный лист сам собран из другой книги (формулой IMPORTRANGE; лист, собранный скриптом, — по той же логике, случая нет), узел читает эту книгу-источник напрямую, а не копию внутри тяжёлой книги.
  Почему (гипотеза, для узла n8n не замерено): обращение к тяжёлой книге ждёт её пересчёта, и узел чтения упирается в таймаут Google, а не в объём данных.
  Признак: узел чтения работает минутами и возвращает успех с нулём строк — это не пустой лист, а несостоявшееся чтение; либо падает с ответом Google 503. Ноль строк после долгого прогона сверять с размером листа (`gsheets-read`, `mode:"meta"`), а не принимать как «данных нет». Ложная ошибка «Document … is missing» той же книги — §4.0.
- **Отдельные ячейки книги читать по именам именованных диапазонов, одним запросом.** Когда воркфлоу берёт из книги не таблицу, а отдельные ячейки (текст сводки, метку последнего прогона, дату данных), он читает их запросом Sheets API `values:batchGet` с параметрами `ranges=<имя>&ranges=<имя>` — именами именованных диапазонов книги вместо адресов A1.
  Почему: адрес A1 сдвигается при любой перестройке листа, и узел молча читает соседнюю ячейку; имя едет вместе с ячейкой.
  Признак: несуществующее имя роняет ВЕСЬ запрос ошибкой 400, а не только свой диапазон. Это полезный сигнал — книга ещё не завела это имя (скрипт книги не доехал или имя переименовано); лечится в книге, а не переходом на адреса. Диапазоны в ответе разбирать по полю `range`, не по позиции — R6.14 Skill n8n-engineering-manual. Как книга заводит именованные ячейки для курьера — Skill apps-script-sheets, references/design.md, абзац «Текст тревоги собирается формулами в книге, n8n читает именованные ячейки».

ЗАПИСЬ:
- Режим Map Automatically (`autoMapInputData`) — что он пишет, что не трогает, как заменяет формулу значением и как отличить частичное обновление от потери — корень R6, правило R6.7. Здесь дополнительно: поле входа, для которого колонки нет, по умолчанию создаёт новую колонку — опция `handlingExtraData` по умолчанию `insertInNewColumn`. Колонки с формулами во вход записи не включать; если выше по потоку посчитаны поля, которые писать нельзя, брать режим Map Each Column Below (`defineBelow`) — он пишет только сопоставленные колонки, формулы остаются целы. `defineBelow` через `create_workflow_from_code` сохраняется.
  Не путать: «`defineBelow` SDK не генерирует — брать `autoMapInputData` и донастраивать в интерфейсе» — на деле `defineBelow` сохраняется, а `autoMapInputData` перезаписывает посчитанные поля.
- Значения записи по умолчанию разбираются как набранные руками: `cellFormat` по умолчанию `USER_ENTERED` — те же ловушки, что у gsheets-append (§4.0а).
- Ошибка «Column to Match On required» у Update Row: не задана колонка сопоставления — для update `matchingColumns` обязателен в обоих режимах. Задать её; переключение на Map Automatically ошибку обходит, но меняет, какие поля пишутся (пункт выше).
- `appendOrUpdate` — всегда с явными `matchingColumns`, иначе тихие дубли. Составной ключ (`matchingColumns` из двух колонок) сопоставляет только по первой колонке и порождает дубль ключа — собирать ключ в одну колонку; механизм — R6.7. Тип и чистота ключа — R6.8.
- После структурных правок листа (колонки, шапка) — в узле Refresh columns list → Save → Publish: узел держит снимок схемы листа. Договор шапки со всеми читателями — R6.4.
- Удаление строк больше 5 — `splitInBatches(5)` и Wait 2 с между порциями. Delete Start Row — через выражение. Барьер против удаления строки заголовков и правило номера строки — R6.12. Почему — в прежнем тексте не записано.

КВОТА И ПОВТОР:
- 429 по квоте — R6.3: повтор допустим только после ожидания дольше минутного окна (выход ошибки узла → Wait не меньше 60 секунд → повтор). Не путать: «Wait 2 с и повторить» — на деле пауза в 2 секунды и `retryOnFail` ложатся в то же минутное окно и ускоряют исчерпание.
- Частые правки нескольких файлов подряд — пауза 1–2 с между вызовами `batchUpdate` как профилактика; при 429 — по R6.3.

ФОРМУЛЫ, КОТОРЫЕ СТРОИТ ВОРКФЛОУ:
- Агрегация по дню: COUNTIFS и SUMIFS с границами суток (`">="&A2` и `"<"&(A2+1)`), а не сравнением с датой: значение даты со временем равенству с датой не удовлетворяет.

[основание: SH-06 · правило C.4.2.2, C.4.2.4, C.4.2.5, C.4.2.6, C.4.2.1]

### 4.3 Формулы

- Язык имён функций проверять по локали конкретной книги ДО генерации формул: русские имена (`ЕСЛИ`) или английские (`IF`); несовпадение даёт `#NAME?`. Разделители и десятичная запятая — Skill apps-script-sheets, §2.1.
- FILTER: нативного OR нет — условие ИЛИ записывать арифметикой `(усл1)+(усл2)>0`. Пустой результат FILTER без обёртки даёт ошибку в ячейке. Обёртка `IFERROR(...,"текст")` допустима только там, где пустой результат действительно значит «нет данных»: она же прячет ошибку «Result was not automatically expanded» при нехватке строк, и тогда, например, себестоимость молча становится нулём. Поэтому рядом с обёрнутым FILTER ставится контрольная ячейка с числом строк источника (ловушка книги — Skill apps-script-sheets, references/book-traps.md, §3.10).
- `TEXTJOIN(IF(...))` при автозаполнении не вычисляется как массив без `ARRAYFORMULA()` — оборачивать обязательно.
- **Литерал массива `{…}` в формуле писать из Apps Script** (`setFormula` с переводом в локаль книги — Skill apps-script-sheets, §2.1), а не через Sheets API с `USER_ENTERED` — то есть не узлом Google Sheets, не gsheets-append и не HTTP-запросом `values.update` или `values.append`. Если формулу всё же пишет воркфлоу — строить её без литерала массива.
  Почему: путь Apps Script для литерала массива проверен, путь Sheets API — нет, и на нём такая формула однажды не разобралась. Различает ли Google разбор формулы по пути записи — не установлено; правило — предосторожность до пробы.
  Признак: `#ERROR!` в ячейках с литералом массива, где колонки разделены обратной косой чертой, при том что разделитель аргументов `;` в той же книге работает.
  Не проверено, проба — задача `labs/sys/t-array-separator-probe.md`. До пробы это наблюдение стоит в противоречии с §4.1 (разделитель колонок `\` в `ru_RU` без указания пути записи) и с Skill apps-script-sheets, §2.1; решает проба, не сессия.
[основание: SH-07 · правило C.4.3.1, C.4.3.2]
### 4.4 Apps Script: PDF → Google Doc

Единственный рабочий путь конвертации PDF в Google Doc из Apps Script — Drive API v2: `Drive.Files.insert(metadata, blob, {convert:true})`; версия 3 для конвертации не работает. Требует подключения сервиса Drive v2 (расширенные сервисы) в проекте Apps Script. Почему — в прежнем тексте не записано.
