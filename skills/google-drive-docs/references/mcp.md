# google-drive-docs — MCP-коннектор Google Drive

Часть Skill google-drive-docs. Читать: перед первым вызовом MCP-коннектора Google Drive в сессии. Номера разделов — прежние, общие с SKILL.md.

## 2. MCP — коннектор Google Drive

### 2.1 create_file

У `contentMimeType` два рабочих значения, и выбор между ними делает ВЛАДЕЛЕЦ, а не сессия:

- `text/plain` — ОБЫЧНЫЙ документ. Конвертируется в нативный Google Doc, но плоским текстом: ни заголовков, ни таблиц, ни выделения, ни разрывов страниц. Дёшево и быстро. Годится для черновика, рабочей записи, текста на вычитку, материала, который потом всё равно править.
- `text/html` — КРАСИВЫЙ документ. Тоже конвертируется в нативный Doc, но с настоящими заголовками, таблицами, списками, цветом, врезками и разрывами страниц. Годится для печати и для чтения человеком. Стили задавать блоком `<style>` с классами в `<head>`: он переживает конвертацию и даёт вдвое меньший объём вызова, чем инлайн-стиль на каждом теге. Проверено 2026-09-17 документом REPORT_git-migration_2026-09-17 (блок T-108 реестра `registry/documents.md`).

ПРАВИЛО ВОПРОСА (внесено 2026-09-17 решением владельца). Перед созданием документа, который будет читать человек, сессия задаёт ОДИН короткий вопрос — «обычный или красивый?» — и ждёт ответа. Вопрос задаётся один раз на документ, не на каждый шаг и не на каждую правку. Формулировка короткая, без объяснения разницы, если владелец о ней не спросил.

Вопрос НЕ задаётся, и молча берётся `text/plain`, когда выполнено хотя бы одно:
(а) владелец уже назвал вид в самой задаче — «для печати», «красиво», «оформи», «черновиком», «просто текстом», «на вычитку»;
(б) документ создаётся для машинного чтения, а не для человека;
(в) это служебная запись, лог, промежуточный или временный файл;
(г) владельца нет на связи и ответа ждать не от кого — тогда `text/plain`, и выбранный вид назван в отчёте прямой строкой.

Основание правила, а не вкусовщина: красивый документ дороже в сборке и в объёме вызова, а нужен не всегда — «очень часто мне достаточно обычного» (владелец, 2026-09-17). Решать за владельца, что ему нужен красивый, — такой же дефект, как решать, что достаточно обычного. Оба решения принимает он, и стоит это одну строку вопроса.

`application/vnd.google-apps.document` как contentMimeType даёт пустой или неоткрывающийся документ — не использовать ни при каком виде.

Параметры: title, contentMimeType, textContent, parentId. Для .md: `disableConversionToGoogleType:true` + `text/markdown` (.md не поддерживают append/replace — Docs API; overwrite работает с любым mimeType).

Верификация: ответ `{id, title, mimeType}`; id пуст — провал. Для `text/html` верификация ОБЯЗАТЕЛЬНО дополняется чтением через gdocs-read: в тексте не должно остаться сырой разметки (`<table`, `style=`, `<div`). Если разметка в тексте есть — конвертация не состоялась, документ негоден и пересоздаётся. Ответ `{mimeType: "application/vnd.google-apps.document"}` сам по себе конвертацию содержимого НЕ доказывает.

create_file НЕ обновляет существующие файлы: при совпадении имени создаёт дубль. Перед созданием проверять существование (get_file_metadata / search); обновление — только gdocs-* по сохранённому fileId.

ЛОВУШКА КРАСИВОГО ДОКУМЕНТА: форматирование, полученное через `text/html`, gdocs-overwrite v2 НЕ сохраняет — он пишет только plain text (§3.4). Правка красивого документа через overwrite молча превращает его в обычный: текст на месте, оформление исчезло, ошибки не возвращается. Красивый документ правится пересозданием через create_file с новым HTML либо руками владельца в интерфейсе Docs. Точечные правки текста в красивом документе (gdocs-replace) оформление не трогают и безопасны.

Известное поведение: text/plain теряет .txt в имени.

Ответ create_file сразу после вызова может содержать `fileSize: "1"` — это кеш-заглушка, не признак пустого документа. Верификация только чтением.

### 2.2 ПРАВИЛА ЧТЕНИЯ ЧЕРЕЗ MCP
1. google_drive_fetch — НЕ ИСПОЛЬЗОВАТЬ для крупных/растущих файлов (INDEX/CORE/OPS): даёт пустой ответ без ошибки. Не использовать вовсе — читать через gdocs-read.
2. РАЗМЕР НЕ ОПРЕДЕЛЯТЬ ПО fileSize из get_file_metadata. Для нативных Google Docs fileSize отражает внутреннее представление, а не размер экспортируемого текста: наблюдаемое соотношение на кириллице — экспорт ≈ 3× fileSize. contentSnippet и fileSize из metadata — кеш, для верификации содержимого непригодны. Рабочий способ узнать размер — gdocs-read с `fromLine:1, toLine:1` (§3.5): он возвращает `byteLength` и `totalLines` всего документа при одной строке текста в ответе.
3. ПУСТОЙ РЕЗУЛЬТАТ ЧТЕНИЯ = СТОП. Явно сообщить «чтение вернуло пусто» и остановиться. ЗАПРЕЩЕНО отвечать реконструкцией по памяти — тихий отказ инструмента плюс конфабуляция модели неотличимы от лжи.
   Одно исключение, и оно проверяемо числом: `gdocs-read` с `fromLine` больше `totalLines` возвращает `success:true`, `text:""`, `returnedChars:0` и заполненный `totalLines`. Документ при этом прочитан целиком и корректно — пуст только запрошенный срез. Различать по паре `fromLine` против `totalLines`, а не по одному `text`. Всё прочее пустое чтение остаётся стопом.
4. Байтовый релей через контекст сессии (base64 → декодирование в другом инструменте) портит символы начиная примерно с 20–25 КБ. Для сверок и read-back использовать второй независимый путь чтения (gdocs-read), не пересказ байтов через контекст.
5. Пустое чтение файла, в который в этой же сессии идёт активная запись — возможна гонка чтение/запись, неотличимая от прочих тихих пустых ответов. Не читать файл во время активной записи в него; при подозрении на гонку — подождать и перечитать.
6. Файл, лежащий в Корзине Drive (Trash), на всех путях чтения (metadata/search/gdocs-read) отвечает «not found»/пусто — неотличимо от «не существует» и от «не расшарен на SA». Если объект должен существовать, но не находится нигде — проверить Корзину вручную через UI Drive.

### 2.3 google_drive_search
`name =` / `name contains` / `fullText contains` / `'ID' in parents` / `mimeType =` / `modifiedTime >`. Свежесозданные не-native файлы (PDF, бинарники) не находит сразу (индексация задерживается) — искать через get_file_metadata по ID или search_files по parentId.

### 2.4 get_file_metadata
Верификация после create_file, получение ID. Если файл «не найден», а другие читаются — файл в другом аккаунте / не расшарен на аккаунт коннектора — проверять owner.
copy_file систематически создаёт снимок на 1–3 КБ больше оригинала (издержки метаданных копии) — это норма самого инструмента, не порча данных.
