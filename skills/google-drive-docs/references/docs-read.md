# google-drive-docs — чтение Google Docs

Часть Skill google-drive-docs. Читать: перед первым чтением документа через gdocs-read в сессии. Номера разделов — прежние, общие с SKILL.md.

### 3.5 gdocs-read (`hJZhQ9KaeFgeRm3k`) — ОБЯЗАТЕЛЬНЫЙ путь чтения (см. §0)
body `{fileId, mode?: "full"|"tail", tailChars?: 2000, fromLine?, toLine?}` → `{success, fileId, name, mimeType, mode, length, returnedChars, driveSize, byteLength, checkSum, totalLines, fromLine, toLine, text, reason}`. Полное чтение без лимита 130 КБ, без base64. Ветвление native Doc (export text/plain) / text-файл (alt=media) — автоматически.

Диапазон строк (введён нарядом Н-15.09-04, решение Р-76): `fromLine` и `toLine` — целые от 1; `toLine` необязателен и без него означает «до конца документа». При заданном `fromLine` поле `text` содержит срез строк после split по `\n`, и заполняется `totalLines` — реальное число строк документа. Без `fromLine` поле `totalLines` всегда `null`.

`byteLength` и `checkSum` считаются по ВСЕМУ документу и от среза не зависят. Проверено зондами exec 68149–68152 и 68199: значение не менялось при полном чтении, срезе строк, режиме tail и избыточном fromLine. Поэтому они годятся для проверки целостности чтения независимо от того, запрошен диапазон или нет.
Над чем считаются. Узел `06_Build_Response` считает `byteLength` и `checkSum` (FNV-1a, 32 бита) над сырым текстом экспорта как есть — с `\r\n`, без какой-либо нормализации (код прочитан 2026-10-12). Пересчитывая их в сессии, брать байты UTF-8 поля `text` полного чтения без изменений: открытие файла в Python в текстовом режиме снимает `\r` и даёт ложное расхождение. Нормализация из §10 — для сравнения документа с источником, а не для проверки этих двух чисел. Если контрольная сумма не сошлась, а `returnedChars` совпал, сначала проверять способ подсчёта, потом данные: 2026-08-29 сессия остановилась ложно по такому расхождению (исполнения 51572, 51573), 2026-08-30 повтор (SYS_INDEX).

ИЗМЕРЕНИЕ ДОКУМЕНТА ОДНОЙ СТРОКОЙ ТЕКСТА: вызов с `fromLine:1, toLine:1` возвращает `totalLines`, `byteLength` и `checkSum` при одной строке текста в поле `text` (exec 68199: returnedChars 21, totalLines 253, byteLength 38299). Это единственный достоверный способ узнать реальный размер документа — §2.2 п.2 запрещает выводить его из `fileSize`. Дешёвым он НЕ является: в том же exec 68199 весь документ, 38 299 Б, пришёл в контекст через contextData (абзац «Цена чтения» ниже). Сессия платит полный размер документа, а экономит только разбор текста. Прежнее название «дешёвое измерение» было ошибкой: оно противоречило абзацу о цене чтения в этом же разделе.

`driveSize` — размер по метаданным Drive (узел `03_Get_Metadata`). Он НЕ равен `byteLength` экспортированного текста и оценкой размера не является.

`mode` в ответе — эхо входного `mode` (`full` или `tail`), а не индикатор диапазона. Совместное задание `mode:"tail"` и `fromLine` ошибки не даёт: срез по строкам применяется после tail-среза и подменяет его, `tailChars` при этом игнорируется.

Избыточный `fromLine` (больше `totalLines`) — НЕ ошибка: `success:true`, `text:""`, `returnedChars:0`, `totalLines` заполнен реальным числом строк. Это осознанно другой случай, чем «ПУСТОЙ РЕЗУЛЬТАТ ЧТЕНИЯ = СТОП» из §2.2 п.3 — там речь о пустом ДОКУМЕНТЕ, здесь документ прочитан полностью и корректно, пуст только запрошенный срез.

Поле `length` — размер в БАЙТАХ UTF-8, не в символах. На кириллице ≈1,5–2 Б/символ, поэтому `length` заметно больше `len(text)` — это не обрезка. Проверка перед тревогой: `len(text.encode('utf-8')) == length`.

Счётчики `length`/`returnedChars`: `length` = байты UTF-8 (TextEncoder), `returnedChars` = UTF-16 code units. На не-BMP символах (эмодзи) `returnedChars` больше числа символов на количество суррогатных пар. Ни одно из этих полей не равно числу символов — не использовать их для сверок между JS и Python; сверять только байты и контрольную сумму.

ДЛИННАЯ СТРОКА МОЖЕТ ПРИЙТИ РАЗОРВАННОЙ. Длинная строка документа может прийти несколькими строками ответа. Сам воркфлоу строк не режет — код `06_Build_Response` делит текст только по `\n` (прочитано 2026-10-12); на каком участке пути возникает разрыв, не установлено. Поэтому вывод «строка оборвана, содержания нет» запрещён, пока не прочитана следующая строка: строка, которая кончается не точкой, не другим терминальным знаком и не маркером списка, скорее всего продолжается в следующей. Правило записано в протоколе переноса файлов (`meta/PROTOCOL_file-migration.md`, этап 0в, пункт 3) и действует для любого чтения через gdocs-read, не только при переносе.

ЦЕНА ЧТЕНИЯ. Диапазон строк НЕ экономит контекст сессии: воркфлоу грузит документ узлами типа `n8n-nodes-base.httpRequest`, и сырой ответ Google с полным текстом оседает в `executionData.contextData`. Ни `nodeNames`, ни `truncateData`, ни `fromLine`/`toLine` этого не режут (§9). Диапазон ограничивает то, над чем сессия рассуждает, а не то, за что она платит. Обещать экономию контекста диапазоном ЗАПРЕЩЕНО — это ложное основание для правил.
