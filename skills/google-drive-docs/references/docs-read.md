### 3.5 gdocs-read — ОБЯЗАТЕЛЬНЫЙ путь чтения (см. §0)

Воркфлоу «Claude → Google Docs Read (full)»; ID — по правилу §1.

**Закон раздела. `byteLength` и `checkSum` — а `totalLines`, когда он заполнен, — описывают весь документ в том виде, в каком его отдал экспорт, и от среза строк, режима и других параметров вызова не зависят; поле `text` и счётчик `returnedChars` описывают только то, что вернулось в ответе.** Почему: воркфлоу всегда загружает документ целиком и только потом вырезает из него ответ. Отсюда три следствия, на которых стоят правила ниже: целостность чтения проверяется числами первого рода при любом запрошенном диапазоне; пустой `text` ещё не значит пустой документ; диапазон строк не уменьшает цену чтения.

**Контракт.** body `{fileId, mode?: "full"|"tail", tailChars?: 2000, fromLine?, toLine?}` → `{success, fileId, name, mimeType, mode, length, returnedChars, driveSize, byteLength, checkSum, totalLines, fromLine, toLine, text, reason}`. Полное чтение, без base64. Ветвление native Doc (export text/plain) / text-файл (alt=media) — автоматически.

**Диапазон строк.** `fromLine` и `toLine` — целые от 1; `toLine` необязателен и без него означает «до конца документа». При заданном `fromLine` поле `text` содержит срез строк после split по `\n`, и заполняется `totalLines` — реальное число строк документа. Без `fromLine` поле `totalLines` всегда `null`.

**Целостность.** `byteLength` и `checkSum` считаются по ВСЕМУ документу и от среза не зависят — значение одно и то же при полном чтении, срезе строк, режиме tail и избыточном `fromLine`. Поэтому они годятся для проверки целостности чтения независимо от того, запрошен диапазон или нет.

**Над чем считаются `byteLength` и `checkSum`.** Над сырым текстом экспорта как есть — с `\r\n`, без какой-либо нормализации; `checkSum` — FNV-1a, 32 бита. Пересчитывая их в сессии, брать байты UTF-8 поля `text` полного чтения без изменений. Почему: открытие файла в Python в текстовом режиме снимает `\r` и даёт ложное расхождение. Нормализация из §10 — для сравнения документа с источником, а не для проверки этих двух чисел; канал, через который снято число, записывается рядом с числом — §10. Признак ложного расхождения: контрольная сумма не сошлась, а `returnedChars` совпал — тогда сначала проверять способ подсчёта, потом данные.

**ИЗМЕРЕНИЕ ДОКУМЕНТА ОДНОЙ СТРОКОЙ ТЕКСТА.** Вызов с `fromLine:1, toLine:1` возвращает `totalLines`, `byteLength` и `checkSum` при одной строке текста в поле `text`. Это единственный достоверный способ узнать реальный размер документа — §2.2 п.2 запрещает выводить его из `fileSize`. Дешёвым он НЕ является: весь документ всё равно приходит в контекст через contextData (абзац «Цена чтения» ниже); сессия платит полный размер документа, а экономит только разбор текста.
Не путать: «дешёвое измерение» — прежнее название этого вызова; на деле цена — полный размер документа.

**`driveSize`** — размер по метаданным Drive. Он НЕ равен `byteLength` экспортированного текста и оценкой размера не является.

**`mode` в ответе** — эхо входного `mode` (`full` или `tail`), а не индикатор диапазона. Совместное задание `mode:"tail"` и `fromLine` ошибки не даёт: срез по строкам применяется после tail-среза и подменяет его, `tailChars` при этом игнорируется.

**Избыточный `fromLine`** (больше `totalLines`) — НЕ ошибка: `success:true`, `text:""`, `returnedChars:0`, `totalLines` заполнен реальным числом строк. Это осознанно другой случай, чем «ПУСТОЙ РЕЗУЛЬТАТ ЧТЕНИЯ = СТОП» из §2.2 п.3 — там речь о пустом ДОКУМЕНТЕ, здесь документ прочитан полностью и корректно, пуст только запрошенный срез. Различать по паре `fromLine` против `totalLines`, а не по одному `text`.

**Поле `length`** — размер в БАЙТАХ UTF-8, не в символах. На кириллице ≈1,5–2 Б/символ, поэтому `length` заметно больше `len(text)` — это не обрезка. Проверка перед тревогой: `len(text.encode('utf-8')) == length`.

**Счётчики `length` и `returnedChars`:** `length` = байты UTF-8 (TextEncoder), `returnedChars` = UTF-16 code units. На не-BMP символах (эмодзи) `returnedChars` больше числа символов на количество суррогатных пар. Ни одно из этих полей не равно числу символов — не использовать их для сверок между JS и Python; сверять только байты и контрольную сумму.

**ДЛИННАЯ СТРОКА МОЖЕТ ПРИЙТИ РАЗОРВАННОЙ.** Длинная строка документа может прийти несколькими строками ответа. Сам воркфлоу строк не режет — текст делится только по `\n`; на каком участке пути возникает разрыв, не установлено. Поэтому вывод «строка оборвана, содержания нет» запрещён, пока не прочитана следующая строка: строка, которая кончается не точкой, не другим терминальным знаком и не маркером списка, скорее всего продолжается в следующей. Правило действует для любого чтения через gdocs-read; для переноса файлов оно же записано в `meta/PROTOCOL_file-migration.md`, этап 0в, пункт 3.

**ЦЕНА ЧТЕНИЯ.** Диапазон строк НЕ экономит контекст сессии: узлы загрузки этого воркфлоу — типа `n8n-nodes-base.httpRequest`, и сырой ответ Google с полным текстом документа оседает в `executionData.contextData`. Ни `nodeNames`, ни `truncateData`, ни `fromLine`/`toLine` этого не режут. Механизм и лечение — Skill `n8n-engineering-manual`, `references/roots.md`, правило R4.5; следствие для чтения Google Docs — §9 (`references/failures.md`); карта узлов загрузки по воркфлоу — `registry/tools.md`. Диапазон ограничивает то, над чем сессия рассуждает, а не то, за что она платит. Обещать экономию контекста диапазоном ЗАПРЕЩЕНО — это ложное основание для правил.
