# Паспорт воркфлоу — жизненный цикл документа

Редакция 2026-09-26. Правки этой редакции: адрес живого состава воркфлоу переведён с Google Doc N8N_REGISTRY на файл registry/n8n-map.md; снят раздел «Приоритет создания» — все три названных в нём воркфлоу паспорта уже имеют; маршрут поиска паспорта перестроен, потому что прежний путь 3 указывал на секцию, где строк «Паспорт → ID» нет, а прежний путь 2 работает только для шести воркфлоу Канала из девяти; механизм дозаписи ADR дополнен инструментом для блоков крупнее двух килобайт — прежний единственный путь на таком объёме отказывает; из шаблона убрано `alwaysOutputData: true` как обязательное, потому что это антипаттерн по правилам SDK и корень R3; восстановлены подчёркивания в схеме имени файла; правило «ID воркфлоу в паспорт не вносить» уточнено — оно противоречило блоку СВЯЗИ, который без ID нечитаем.

Правка 2026-10-09 по харвесту 2026-10-08. Что изменилось и почему: строка о SYSTEM-MAP заменена снимком registry/n8n-map.md — SYSTEM-MAP больше не действует (харвест, противоречие В16); абзац «get_workflow_details не отдаёт даже факт наличия credential» переписан — с 2026-10-08 инструмент отдаёт у узлов id и имя credential (позиция очереди AH-27), прежнее утверждение сохранено блоком ИСТОРИЯ ДИАГНОЗА; стадия 3, пункт 5 — кто вписывает строку PASSPORT: владелец руками, как требуют четыре проекта, а запись описания агентом через MCP ограничена 255 знаками (находка А42); добавлена стадия 3а «Фаза не закрыта без паспорта» и правило «временный зонд паспорта не получает» (А42); стадия 5 переписана: ставший ненужным воркфлоу снимается с публикации, а не архивируется (А7, предпочтение владельца 2026-10-08).

Этот файл построен как жизнь одного документа: находят, читают, рождают, дозаписывают, закрывают. Ищи стадию, на которой стоишь.

## Что паспорт знает, а что нет

| Вопрос | Носитель ответа |
|---|---|
| Что существует: ID, имя, статус, черновик, расписание, таймзона, вызовы, документы, типы credential | файл registry/n8n-map.md репозитория second-brain-canon; формат строк — projects/n8n-map/PLAN.md раздел 4 |
| Как работает, с чем связано, почему именно так, какие ловушки | **паспорт воркфлоу** |
| Пути вебхуков и признак их аутентификации | Google Doc N8N_REGISTRY, строки HOOK и HOOKCALL |
| Как воркфлоу складываются в систему: кто кого вызывает, кто в какой документ пишет | тот же снимок registry/n8n-map.md — строки X (вызовы саб-воркфлоу), H (вызовы вебхуков), D (документы). Прежний документ SYSTEM-MAP заменён этим снимком и не ведётся (projects/n8n/STATE.md); указания «сначала читать SYSTEM-MAP» в старых планах проектов устарели |
| Механика n8n, корневые причины отказов, протокол правки | n8n-engineering-manual |
| ID книг Sheets, специфика внешних API, формулы ключей | n8n-workflow-registry |

Что в паспорт НЕ вносится: собственные ID и имя воркфлоу — они выводятся из снимка и в паспорте разойдутся с объектом. Что вносится обязательно: ID и имена того, что воркфлоу ВЫЗЫВАЕТ и КУДА пишет — без них блок СВЯЗИ нечитаем. Прежняя редакция запрещала «ID и Название» без этой оговорки и сама себе противоречила: блок СВЯЗИ шаблона требует назвать вызываемые воркфлоу.

Что вносится обязательно: **имя привязанного credential** у каждого узла. С 2026-10-08 `get_workflow_details` отдаёт у узла поле `credentials` с id и именем ключа (например, воркфлоу `fGHfVrI58Ws1wfTw`, узел `02_Fetch_WB_Cards`: `WB-Content-API-Key`, id `g3bSSmWWg9XjTNOQ`; проверено ещё раз 2026-10-09 на HTTP-узле и узлах Google Sheets воркфлоу `IvgysDKrq3UISYEY`), поэтому имя теперь можно списать из объекта, а не только глазами в редакторе (projects/deklaration-wb/LOG.md, Р-5). Снимок registry/n8n-map.md по-прежнему держит только ТИП credential. Паспорт держит имя ради причины: ПОЧЕМУ у узла именно этот ключ (кабинет, юрлицо, право чтения или записи) — этого объект не скажет. Расхождение имени в паспорте с объектом — дрейф паспорта, правится по объекту.
ИСТОРИЯ ДИАГНОЗА: прежняя редакция утверждала, что `get_workflow_details` «не отдаёт даже факт наличия credential», и делала паспорт единственным носителем имени ключа. Так и было при проверке девяти воркфлоу в августе–сентябре 2026 (projects/n8n-map/PLAN.md, раздел 3); опровергнуто чтениями 2026-10-08 и 2026-10-09 — поле вернулось. На всех ли типах узлов оно есть, не проверено.

## Стадия 1. Найти паспорт — первое действие перед любой работой с воркфлоу

Перед правкой, отладкой, разбором или запуском воркфлоу сначала ищется паспорт. Причина: `get_workflow_details` возвращает сырой JSON, в котором воркфлоу лежит дважды — черновиком и опубликованной версией, — и на крупном воркфлоу это десятки килобайт контекста. Паспорт даёт готовые факты.

Маршрут поиска, первое найденное останавливает поиск:

**Путь 1. Строка паспорта в `description` воркфлоу.** Видна в выдаче `search_workflows`, отдельного чтения воркфлоу не нужно. Искать БЕЗ учёта регистра: на 26.09.2026 из 64 живых воркфлоу со строкой паспорта 57 пишут `PASSPORT:`, а 7 — `Passport:`. Регистрочувствительный поиск теряет эти семь.

**Путь 2. Имя документа в папке DOCS.** Паспорта названы по схеме `[ПРОЕКТ]_WF_[имя-воркфлоу]` (стадия 3), поэтому поиск по имени в Drive находит паспорт без всякого реестра: `N8N_WF_registry-sync`, `WB_WF_telegram-router`. Прежняя редакция запрещала искать по папке словами «папка не говорит, какой документ к какому воркфлоу относится» — это противоречило её же правилу именования: схема имени говорит именно это.

**Путь 3. Строка воркфлоу в `registry/tools.md`** — только для воркфлоу Git-канала, и только для части из них. На 26.09.2026 `registry/tools.md` называет шесть ID паспортов; у Git Read, Git Append, Git Append File и Git Log паспорт не назван ни там, ни в `description`.

Паспорт найден — открыть по ID через `gdocs-read` и читать ТОЛЬКО нужную зону по маркерам (стадия 2), не весь документ. `get_workflow_details` в этом случае не вызывать.

Паспорт не найден ни одним путём — читать `get_workflow_details`, прямо сказать Андрею, что документации нет, и выполнить стадию 3. Молча работать без паспорта нельзя: следующая сессия повторит тот же поиск.

Перед действием с воркфлоу назвать, ЧТО прочитано и откуда: зону паспорта и дату его последнего изменения, либо честно «паспорта нет, читал get_workflow_details». Фиксированная фраза подтверждением не считается — она доказывает, что файл открыт, а не что в нём что-то прочитано.

## Стадия 2. Читать — только нужную зону

Паспорт состоит из трёх зон, каждая открыта и закрыта уникальным маркером, в обычном тексте маркеры не встречаются.

| Ситуация | Читать |
|---|---|
| Касание воркфлоу, понять что это | ЗОНА А |
| Изменение или отладка | ЗОНА А и ЗОНА Б |
| Вопрос «почему выбрали такой подход» | ЗОНА В |
| Создание нового паспорта или полная миграция | все три |

Диапазон строк у `gdocs-read` ограничивает то, над чем сессия рассуждает, а не то, за что платит: узлы загрузки этого воркфлоу оставляют полный текст документа в `contextData` при любом запрошенном диапазоне (google-drive-docs раздел 9). Обещать экономию контекста выбором зоны нельзя — зона экономит внимание, не токены.

## Стадия 3. Родить паспорт

1. Убедиться, что папка DOCS проекта существует. ID папки — в секции ИНСТРУМЕНТЫ INDEX проекта, ключ `DOCS_FOLDER`. Папки нет → создать воркфлоу `uapccJY1O4ykyDi7`, тело `{folder_name, parent_id}`; оба поля обязательны.
2. Создать файл: `create_file` с `title: "[ПРОЕКТ]_WF_[имя-воркфлоу]"`, `contentMimeType: "text/plain"`, `textContent` по шаблону ниже, `parentId` — ID папки DOCS. Подчёркивания в схеме имени обязательны, они и делают имя находимым: `WB_WF_finance-sync`, `N8N_WF_gdocs-append`, `OZON_WF_intake`.
3. `create_file` отказал → фолбэк: копия существующего документа через `copy_file`, затем наполнение через `gdocs-overwrite`. Разбор отказа — google-drive-docs, таблица ошибок, код E14.
4. Взять ID из ответа `create_file`.
5. Строка `PASSPORT: <ID Google Doc>` в конце `description` воркфлоу. Это главный адрес паспорта: он виден в выдаче поиска и не зависит от того, где лежит INDEX проекта. Писать в ВЕРХНЕМ регистре — смешение регистров уже стоило семи воркфлоу, которые находятся только поиском без учёта регистра.
   - Кто вписывает: **Андрей, руками, в настройках воркфлоу в редакторе.** Так требуют планы четырёх проектов (projects/deklaration-wb/PLAN.md, projects/card-content-sync/PLAN.md, meta/DECLARATION_SCAN.md, projects/n8n/STATE.md). Сессия даёт ему готовую строку на вставку и название воркфлоу.
   - Почему не сессия через MCP. Инструмент `update_workflow` теперь умеет менять описание отдельной операцией `setWorkflowMetadata`, не пересобирая узлы, но поле `description` в ней ограничено 255 знаками. Описания длиннее 255 знаков на инстансе есть (у `IvgysDKrq3UISYEY` — 282 знака), а строка PASSPORT стоит в конце: запись агентом длинного описания либо откажет, либо отрежет именно адрес паспорта. Вызов `create_workflow_from_code` тоже сокращает описание до 255 знаков. Сведения взяты из описания инструментов MCP 2026-10-09; вызовом не проверялось.
   - Воркфлоу создаётся в этой же сессии → описание держать коротким, чтобы вместе со строкой PASSPORT оно уложилось в 255 знаков, и передать его параметром `description` вызова `create_workflow_from_code`. Но паспорт к этому моменту обычно ещё не создан — тогда строку позже вписывает Андрей.
   - Проверка: строка видна в выдаче `search_workflows` по имени воркфлоу. Слово «вписал» проверкой не считается — только выдача поиска.
   ИСТОРИЯ ДИАГНОЗА: прежняя редакция запрещала запись описания через MCP, потому что «`update_workflow` пересобирает все узлы из переданного кода и может молча снять аутентификацию вебхука (корень R12)». Это было верно для прежней формы инструмента, которая принимала код воркфлоу целиком; нынешний `update_workflow` принимает отдельные операции, и операция над описанием узлы не трогает. Запрет остаётся по другой причине — предел 255 знаков и требование владельца.
6. Только после проверки сказать «паспорт создан». Проверка упала → ID остаётся в чате как резервная копия, об ошибке сказать прямо, паспорт созданным не считать.

Временный зонд — воркфлоу только для чтения, созданный, чтобы один раз снять факты, — паспорта не получает. Его итог — запись в журнал проекта (что снято, номер исполнения, ID зонда). Если зонд оказался нужен снова и стал инструментом (стадия 5), паспорт создаётся при первой его правке.

Строка в секции ИНСТРУМЕНТЫ INDEX проекта больше не ведётся: она дублировала строку в `description`, и на 26.09.2026 все найденные строки «Паспорт → ID» лежали не в ИНСТРУМЕНТАХ, а в хронике Зоны Б, то есть искать их там, где предписано, было бесполезно. У проектов, чей INDEX перенесён в репозиторий — например лаборатория `labs/sys/` — секции ИНСТРУМЕНТЫ нет вовсе (second-brain-git 4б.3).

## Стадия 3а. Фаза не закрыта без документации

Требование Андрея от 2026-10-02: техническая документация — часть поставки, а не отдельный шаг на потом (projects/deklaration-ozon/LOG.md, Р-20). Фаза плана или наряд, который создаёт или меняет воркфлоу, не считается закрытым, пока нет трёх вещей:
1. паспорт по стадии 3 или новый ADR по стадии 4;
2. строка PASSPORT в `description`, видимая в выдаче `search_workflows`;
3. инструкция для человека, если воркфлоу запускает человек (форма, ручной запуск), — где она лежит, решает план проекта.

Временного зонда это не касается — у него нет паспорта (стадия 3).

## Стадия 4. Дозаписать после каждой правки воркфлоу

Это продолжение протокола изменений из n8n-engineering-manual. Выполняется в той же сессии, где была правка. Не переносится на потом.

**Шаг 1.** Назвать паспорт, которого касается правка.

**Шаг 2.** Паспорта нет → создать по стадии 3 прямо сейчас. Паспорт есть → три действия, все три:
- вставить ADR-блок перед маркером `%%ЗОНА_В_КОНЕЦ%%` (механизм ниже);
- сверить строки ЗОНЫ А — ТРИГГЕР, СВЯЗИ, CREDENTIALS — и ЗОНЫ Б — СХЕМА, ИЗВЕСТНЫЕ ОГРАНИЧЕНИЯ. ADR без этой сверки означает дрейф, а не обновление. Особое внимание составу узлов: правка, добавляющая узлы, делает СХЕМУ неверной молча — 26.09.2026 у воркфлоу `gFFiBPm1OomOzJOj` узлов стало восемь вместо пяти, и схема в паспорте описывала прежнюю цепочку;
- проверить результат перечитыванием документа, а не ответом инструмента.

**Шаг 3.** Сессия не закрывается без выполненного шага 2 либо явного отказа Андрея с указанной причиной.

Ответственность: Claude следит, чтобы шаги не были пропущены. Андрей отвечает за содержание ADR — контекст, альтернативы, последствия.

### Правило записи зон

ЗОНА А и ЗОНА Б — правятся через `gdocs-replace` короткими УНИКАЛЬНЫМИ ОДНОСТРОЧНЫМИ якорями. Многострочный якорь запрещён: промах виден по `occurrencesChanged: 0`, а вот попадание, пересёкшее границу абзаца, склеивает хвост соседнего пункта с новым текстом и рапортует успех. Строка не уникальна → не дробить правку, а дописать новый блок с датой внутри зоны.

ЗОНА В — только дозапись. Старые ADR-блоки не редактировать и не удалять.

Новый ADR вставляется ПЕРЕД маркером `%%ЗОНА_В_КОНЕЦ%%`. Инструмент выбирается по размеру блока:

| Размер ADR-блока | Чем вставлять |
|---|---|
| до примерно 2 КБ | `gdocs-replace`: якорь `%%ЗОНА_В_КОНЕЦ%%` заменяется на (ADR-блок + перенос строки + тот же маркер) |
| крупнее примерно 2 КБ | `gdocs-apply-from-file` в режиме `replace`, `search` = `%%ЗОНА_В_КОНЕЦ%%`, текст ADR вместе с маркером кладётся файлом на Drive. Через тело вызова текст не проходит, ограничение размера не действует |

Граница около 2 КБ — не измеренный предел, а осторожная линия: у инструментов, принимающих текст телом вызова, байты уже портились на объёме порядка 29 КБ. Реальный случай: ADR от 26.09.2026 для воркфлоу `gFFiBPm1OomOzJOj` весил 5 570 байт и пошёл только вторым путём.

Простой `gdocs-append` для ADR ЗАПРЕЩЁН: он пишет в конец документа, ПОСЛЕ маркера, и блок выпадает из читаемой зоны. Наблюдался 30.06.2026 — паспорт Evening Report, три ADR вне зоны.

После вставки перечитать документ: склейка строк не ловится ответом `success: true`.

## Стадия 5. Воркфлоу больше не нужен

Правило владельца от 2026-10-08: ставший ненужным воркфлоу — временный зонд, пробный, одноразовый или вытесненный новым — **снимается с публикации, но не архивируется и не удаляется.** Это инструменты, которые наверняка понадобятся снова; их оставляют и называют как инструменты (projects/deklaration-wb/LOG.md, Р-6; meta/PENDING_RULES.md, строка 6). Пометки «временный — архивировать после снимка» в описаниях воркфлоу и в журналах проектов не исполняются. Прежняя практика архивировать зонды (например, projects/deklaration-ozon/LOG.md, Р-15) этим правилом отменена.

Порядок:
1. Снять с публикации.
2. Проверить снятие чтением объекта: `search_workflows` или `get_workflow_details` показывает `active: false`. Слово «деактивировал» проверкой не считается: 2026-10-01 владелец сообщил, что снял воркфлоу, а поиск показал `active: true` — снятие не состоялось (projects/git-migration/LOG.md, Р-126).
3. Записать, что воркфлоу снят и почему, туда, где проект хранит невзятое и снятое (обычно NOT_TAKEN.md или журнал проекта).
4. Если у воркфлоу есть паспорт — вставить перед `%%ЗОНА_В_КОНЕЦ%%` строку:

```
СТАТУС: СНЯТ С ПУБЛИКАЦИИ [дата] — [причина; чем вытеснен, если вытеснен]
```

Если владелец всё же решил архивировать воркфлоу — та же строка со словом `АРХИВИРОВАН`. Решение об архивации принимает только владелец, сессия её не предлагает по умолчанию.

Паспорт не удалять никогда: ЗОНА В с историей решений остаётся, и именно по ней потом узнают, почему воркфлоу сняли. Состояние `active` или `archived` само по себе выводится из снимка — строка в паспорте нужна ради причины, а не ради статуса.

## Шаблон паспорта

```
ПАСПОРТ ВОРКФЛОУ
Создан: ГГГГ-ММ-ДД
Последнее изменение: ГГГГ-ММ-ДД

%%ЗОНА_А_НАЧАЛО%%
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
ЗОНА А — что это и с чем связано
Читается при каждом касании воркфлоу
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

НАЗНАЧЕНИЕ
[Что делает и зачем]

ТРИГГЕР
[Webhook / Schedule / MCP / Ручной / Псевдо-ручной]
[Детали: путь вебхука, расписание, параметры запуска]

ВХОДНЫЕ ДАННЫЕ
[Источник, формат, обязательные поля]

ВЫХОДНЫЕ ДАННЫЕ
[Куда пишет и что возвращает, ключевые поля, условия записи]

СВЯЗИ
Запускается из: [воркфлоу-инициатор / внешний триггер / MCP]
Запускает:      [воркфлоу и его ID] при [условии]
                [воркфлоу и его ID] при ошибке
Читает:         [источник → лист / документ / API]
Пишет:          [назначение → лист / документ / API]
Правило: связи описываются только в паспорте инициатора. Получатель про
входящую связь не знает — это не его ответственность. Один источник истины
на каждую связь.

CREDENTIALS
[Узел → имя credential → тип]
Пример:
  08A_Generate_Review → Anthropic API Key → Header Auth
  07_Write_RAW        → Google Sheets OAuth → OAuth2
Имя списывается из get_workflow_details (поле credentials узла);
здесь — ещё и почему у узла именно этот ключ (кабинет, юрлицо, право).
%%ЗОНА_А_КОНЕЦ%%

%%ЗОНА_Б_НАЧАЛО%%
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
ЗОНА Б — как устроено внутри
Читается при изменении или отладке воркфлоу
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

СХЕМА (ключевые точки)
[Только развилки, критические настройки, циклы — не все узлы.
 Отступ показывает цепочку: дочерний узел правее родителя.]
Пример:
  Триггер
    → Получить данные (HTTP)
      → Есть данные? (Filter)
        → Нормализовать → Дедуплицировать → Записать
[Ветвь «нечего делать» — сознательный терминал: ноль items штатно
 останавливает цепочку. НЕ ставить alwaysOutputData ради «чтобы не обрывалось»:
 это создаёт пустой item, на котором падают чтения полей — корень R3
 n8n-engineering-manual. Флаг оправдан только когда пустой случай обрабатывает
 отдельная ветвь, и тогда рядом стоит явная проверка на пустоту.]

ИЗВЕСТНЫЕ ОГРАНИЧЕНИЯ
[Что нельзя менять без последствий, зависимости, гонки, ручные шаги владельца]
%%ЗОНА_Б_КОНЕЦ%%

%%ЗОНА_В_НАЧАЛО%%
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
ЗОНА В — история решений
Читается при вопросе "почему именно так"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ГГГГ-ММ-ДД] РЕШЕНИЕ: [что выбрано — параметр, узел, схема]
КОНТЕКСТ:      [какая проблема стояла]
АЛЬТЕРНАТИВЫ:  [что отвергли и почему]
ПОСЛЕДСТВИЯ:   [на что влияет и что ограничивает]
ПРИЁМКА:       [чем доказано, что правка работает — по объекту, не по статусу]

[каждый новый блок вставляется ПЕРЕД маркером ниже, по «Правилу записи зон»]
%%ЗОНА_В_КОНЕЦ%%
```

Поле ПРИЁМКА добавлено этой редакцией: без него ADR фиксирует замысел, но не факт, что правка легла. Доказательство — объект воздействия или номер исполнения, не ответ инструмента.

## Где хранятся паспорта

Папка DOCS заводится отдельно для каждого проекта. Её ID регистрируется в секции ИНСТРУМЕНТЫ соответствующего INDEX строкой `DOCS_FOLDER: [ID папки Google Drive]`.

Имя файла — `[ПРОЕКТ]_WF_[имя-воркфлоу]`:

| Имя файла | Расшифровка |
|---|---|
| `N8N_WF_gdocs-append` | Second Brain, воркфлоу append |
| `WB_WF_finance-sync` | Wildberries, финансовая синхронизация |
| `OZON_WF_intake` | Ozon, загрузка отзывов |

Схема имени — не косметика: она единственное, что позволяет найти паспорт поиском по Drive, когда строки в `description` нет.
