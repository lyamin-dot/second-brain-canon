# Паспорт воркфлоу — жизненный цикл документа

Редакция 2026-10-21.

Этот файл построен как жизнь одного документа: находят, читают, рождают, дозаписывают, закрывают. Ищи стадию, на которой стоишь.

Как устроен текст. Каждое правило держит четыре вещи: что делать и когда; почему; признак, если ситуация неочевидна; основание. Строка «Основание: N случаев, последний <дата> — отчёт синтеза, правило <id>» значит: адреса каждого случая лежат в отчёте `meta/SYNTHESIS_n8n-workflow-passport_2026-10-21.md` репозитория lyamin-dot/second-brain-canon, в таблице «правило → случаи». Как менялся текст — история коммитов зеркала `skills/n8n-workflow-passport/`. Механизмы, чей дом в другом Skill, здесь не повторяются — стоит ссылка на дом и только та часть, которая принадлежит паспорту. Правка этого Skill готовится по `meta/PROTOCOL_knowledge-synthesis.md`: урок не дописывается, стадия переписывается правилом.

## Что паспорт знает, а что нет

Паспорт — носитель одного вопроса: как воркфлоу работает, с чем связан, почему устроен именно так и какие у него ловушки. Остальное о воркфлоу живёт в других носителях, и паспорт его не копирует: копия расходится с объектом молча.

| Вопрос | Носитель ответа |
|---|---|
| Что существует: ID, имя, статус, черновик, расписание, таймзона, вызовы, документы, типы credential | файл `registry/n8n-map.md` репозитория second-brain-canon; формат строк — `projects/n8n-map/PLAN.md`, раздел 4 |
| Как работает, с чем связано, почему именно так, какие ловушки | **паспорт воркфлоу** |
| Пути вебхуков и признак их аутентификации | Google Doc N8N_REGISTRY, строки HOOK и HOOKCALL |
| Как воркфлоу складываются в систему: кто кого вызывает, кто в какой документ пишет | тот же снимок `registry/n8n-map.md` — строки X (вызовы саб-воркфлоу), H (вызовы вебхуков), D (документы) |
| Механика n8n, корневые причины отказов, протокол правки | n8n-engineering-manual |
| ID книг Sheets, специфика внешних API, формулы ключей | n8n-workflow-registry |

Не путать: документ SYSTEM-MAP — не носитель связей. Он заменён снимком `registry/n8n-map.md` и не ведётся (`registry/protocols.md`, строка PROTOCOL_system-map); указание «сначала читать SYSTEM-MAP» в старых планах проектов устарело. Основание: 1 решение, 2026-10-09 — отчёт синтеза, правило NWP.носители.

**Что в паспорт не вносится:** собственные ID и имя воркфлоу. Почему: они выводятся из снимка, а в паспорте разойдутся с объектом при первом переименовании.

**Что вносится обязательно:**
- ID и имена того, что воркфлоу ВЫЗЫВАЕТ и КУДА пишет. Почему: без них блок СВЯЗИ шаблона нечитаем. Запрет «собственные ID не вносить» на них не распространяется.
- Имя привязанного credential у каждого узла — и почему у узла именно этот ключ: кабинет, юрлицо, право чтения или записи. Почему: снимок `registry/n8n-map.md` держит только ТИП credential, а причину выбора ключа объект не скажет. Имя списывается из объекта: `get_workflow_details` отдаёт у узла поле `credentials` с id и именем ключа. Признак дрейфа: имя в паспорте расходится с полем `credentials` узла — правится паспорт по объекту. На всех ли типах узлов поле есть — не проверено; отсутствие поля доказательством отсутствия ключа не считается (n8n-engineering-manual, `references/roots.md`, корень R1a).
Не путать: «`get_workflow_details` не отдаёт даже факт наличия credential, паспорт — единственный носитель имени ключа» — так было при проверке воркфлоу в августе–сентябре 2026; на деле с 2026-10-08 поле `credentials` в ответе есть.
Основание: собственные ID — 1 противоречие прежнего текста, 2026-09-26; поле `credentials` — 2 чтения, последнее 2026-10-09 — отчёт синтеза, правило NWP.что-вносится.

## Стадия 1. Найти паспорт — первое действие перед любой работой с воркфлоу

**Перед правкой, отладкой, разбором или запуском воркфлоу сначала ищется паспорт.** Почему: `get_workflow_details` возвращает сырой JSON, в котором воркфлоу лежит дважды — черновиком и опубликованной версией, — и на крупном воркфлоу это десятки килобайт контекста; паспорт даёт готовые факты.

Маршрут поиска — три пути по порядку, первое найденное останавливает поиск:

**Путь 1. Строка паспорта в `description` воркфлоу.** Видна в выдаче `search_workflows`, отдельного чтения воркфлоу не нужно. Искать БЕЗ учёта регистра. Почему: строка записана в разных воркфлоу то как `PASSPORT:`, то как `Passport:`, и регистрочувствительный поиск теряет вторые. Основание: 1 замер, 2026-09-26 — отчёт синтеза, правило NWP.путь1.

**Путь 2. Имя документа в папке DOCS.** Паспорта названы по схеме `[ПРОЕКТ]_WF_[имя-воркфлоу]` (стадия 3), поэтому поиск по имени в Drive находит паспорт без всякого реестра: `N8N_WF_registry-sync`, `WB_WF_telegram-router`. Почему этот путь законен: схема имени говорит, к какому воркфлоу относится документ.

**Путь 3. Строка воркфлоу в `registry/tools.md`** — только для воркфлоу Git-канала, и только для тех из них, у кого паспорт там назван; у части воркфлоу Канала паспорт не назван ни там, ни в `description`. Основание: 1 сверка, 2026-09-26 — отчёт синтеза, правило NWP.путь3.

**Паспорт найден — открыть по ID через `gdocs-read` и читать ТОЛЬКО нужную зону по маркерам (стадия 2), не весь документ.** Чтобы понять воркфлоу или ответить на вопрос о нём, `get_workflow_details` в этом случае не вызывать: паспорт отвечает дешевле.

**Живой код читается и при найденном паспорте, когда по прочитанному последует действие или вердикт.** Почему: паспорт — заявление, а не доказательство; документ описывает замысел, а исполняется код.
- Правка воркфлоу: пред-полётный чек-лист и пост-полётная сверка идут по `get_workflow_details` — n8n-engineering-manual, `references/write.md`, разделы 2.2 и 2.3; паспорт их не заменяет.
- Аудит, приёмка, разбор отказа, наряд, ЗАДАЧА которого опирается на утверждение паспорта о поведении воркфлоу. Как такой наряд выдавать — Skill naryad, `references/issuer.md`.
Признак: следующий шаг — изменить воркфлоу, вынести о нём вердикт или поручить работу, исходя из того, как он себя ведёт.
Основание: 2 случая, последний 2026-07-29 — отчёт синтеза, правило NWP.живой-код (урок У-126 карты `projects/archivarius/TRIAGE.md`).

**Расхождение паспорта с живым кодом — дрейф паспорта:** правится паспорт по коду (стадия 4), а не наоборот.

**Паспорт не найден ни одним путём** — читать `get_workflow_details`, прямо сказать Андрею, что документации нет, и выполнить стадию 3. Почему: молча работать без паспорта нельзя — следующая сессия повторит тот же поиск.

**Перед действием с воркфлоу назвать, ЧТО прочитано и откуда:** зону паспорта и дату его последнего изменения, либо честно «паспорта нет, читал `get_workflow_details`». Почему: фиксированная фраза доказывает, что файл открыт, а не что в нём что-то прочитано, поэтому подтверждением не считается (то же правило для чтения Skill — n8n-engineering-manual, шапка, «Подтверждение после прочтения»).

## Стадия 2. Читать — только нужную зону

Паспорт состоит из трёх зон, каждая открыта и закрыта уникальным маркером; в обычном тексте маркеры не встречаются.

| Ситуация | Читать |
|---|---|
| Касание воркфлоу, понять что это | ЗОНА А |
| Изменение или отладка | ЗОНА А и ЗОНА Б |
| Вопрос «почему выбрали такой подход» | ЗОНА В |
| Создание нового паспорта или полная миграция | все три |

**Зона экономит внимание, а не токены.** Диапазон строк у `gdocs-read` ограничивает то, над чем сессия рассуждает, а не то, за что платит: полный текст документа приходит в контекст при любом запрошенном диапазоне. Обещать экономию контекста выбором зоны нельзя. Механизм — google-drive-docs, `references/docs-read.md`, абзац «ЦЕНА ЧТЕНИЯ».

## Стадия 3. Родить паспорт

1. **Убедиться, что папка DOCS проекта существует.** ID папки — строка `DOCS_FOLDER:` в каноне проекта (раздел «Где хранятся паспорта»); найти её — поиск по ключу `DOCS_FOLDER` в папке проекта. Папки нет — создать её воркфлоу «Claude → Create Folder»; ID воркфлоу и контракт — google-drive-docs, §1 и `references/docs-write.md`, раздел 3.3.
2. **Создать файл:** `create_file` с `title: "[ПРОЕКТ]_WF_[имя-воркфлоу]"`, `contentMimeType: "text/plain"`, `textContent` по шаблону ниже, `parentId` — ID папки DOCS. Подчёркивания в схеме имени обязательны — они и делают имя находимым: `WB_WF_finance-sync`, `N8N_WF_gdocs-append`, `OZON_WF_intake`.
3. **`create_file` отказал** — фолбэк по google-drive-docs, `references/failures.md`, код E14: копия существующего документа через `copy_file`, затем наполнение через `gdocs-overwrite`.
4. **Взять ID из ответа `create_file`.**
5. **Строка `PASSPORT: <ID Google Doc>` в конце `description` воркфлоу.** Это главный адрес паспорта: он виден в выдаче поиска и не зависит от того, где лежит канон проекта. Писать в ВЕРХНЕМ регистре. Почему: смешение регистров уже разделило воркфлоу на тех, кого находит регистрочувствительный поиск, и тех, кого он теряет (стадия 1, путь 1).
   - **Кто вписывает: Андрей, руками, в настройках воркфлоу в редакторе.** Сессия даёт ему готовую строку на вставку и название воркфлоу. Почему, три причины: так требуют планы проектов; операция `setWorkflowMetadata` инструмента `update_workflow` принимает в поле `description` не больше 255 знаков, а строка PASSPORT стоит в конце — запись длинного описания агентом откажет или отрежет именно адрес паспорта (`create_workflow_from_code` тоже сокращает описание до 255 знаков); и `setWorkflowMetadata` заменяет описание ЦЕЛИКОМ, а не дописывает — без прежнего текста в вызове описание пропадает, и даже при описании короче 255 знаков ошибка переноса молча портит его. Без риска потери обходится только пустой `description`, но и это правило «вписывает Андрей» не меняет.
   - **Воркфлоу создаётся в этой же сессии** — описание держать коротким, чтобы вместе со строкой PASSPORT оно уложилось в 255 знаков, и передать его параметром `description` вызова `create_workflow_from_code`. Паспорт к этому моменту обычно ещё не создан — тогда строку позже вписывает Андрей.
   - **Проверка:** строка видна в выдаче `search_workflows` по имени воркфлоу. Слово «вписал» проверкой не считается — только выдача поиска.
   Не путать: «правка описания через MCP пересобирает все узлы и может молча снять аутентификацию вебхука (корень R12)» — так было у прежней формы `update_workflow`, принимавшей код воркфлоу целиком; нынешняя операция над описанием узлы не трогает. Запрет стоит по причинам выше, а не по этой.
   Основание: требование владельца — 2 плана проектов и состояние проекта n8n; предел 255 знаков — описание инструментов MCP 2026-10-09 (вызовом не проверялся); замена описания целиком — 1 вызов, 2026-10-21 — отчёт синтеза, правило NWP.строка-паспорта.
6. **Только после проверки сказать «паспорт создан».** Проверка упала — ID остаётся в чате как резервная копия, об ошибке сказать прямо, паспорт созданным не считать. Почему: запись доказывается перечитыванием объекта, а не ответом инструмента (second-brain-engineer, раздел Р15).
7. **Строка ПРИЁМКА шаблона в созданном паспорте заменяется результатом приёмки тем же шагом,** что и создание: заготовку «результат после приёмки» в документе не оставлять. Утверждение о поведении платформы, не проверенное пробой (например, «это расписание никогда не сработает»), пишется словами «Гипотеза (не проверена):», пока проба его не подтвердит. Почему: заглушка, оставленная в документе, требует отдельной правки на каждом паспорте, а непроверенное утверждение, записанное фактом, отвергает приёмщик. Основание: 1 прогон, 2026-10-21 — отчёт синтеза, правило NWP.приёмка-при-рождении.

**Временный зонд — воркфлоу только для чтения, созданный, чтобы один раз снять факты, — паспорта не получает.** Его итог — запись в журнал проекта: что снято, номер исполнения, ID зонда. Если зонд понадобился снова и стал инструментом (стадия 5), паспорт создаётся при первой его правке. Почему: паспорт отвечает «почему так устроено», а у одноразового снимка фактов этого вопроса нет; его итог ищут в журнале проекта.

**Строка «Паспорт → ID» в секции ИНСТРУМЕНТЫ INDEX проекта не ведётся.** Почему: она дублировала строку в `description`, а там, где предписано, её не было — найденные строки лежали в хронике Зоны Б, и искать их по предписанию было бесполезно. У проектов, чей INDEX перенесён в репозиторий, — например лаборатория `labs/sys/` — секции ИНСТРУМЕНТЫ нет вовсе (у лаборатории две роли файлов — second-brain-git, 4б.3). Основание: 1 сверка, 2026-09-26 — отчёт синтеза, правило NWP.инструменты-INDEX.

## Стадия 3а. Фаза не закрыта без документации

**Фаза плана или наряд, который создаёт или меняет воркфлоу, не считается закрытым, пока нет трёх вещей:**
1. паспорт по стадии 3 или новый ADR по стадии 4;
2. строка PASSPORT в `description`, видимая в выдаче `search_workflows`;
3. инструкция для человека, если воркфлоу запускает человек (форма, ручной запуск), — где она лежит, решает план проекта.

Почему: техническая документация — часть поставки, а не отдельный шаг на потом; отложенная документация не пишется. Временного зонда это не касается — у него нет паспорта (стадия 3). Основание: требование Андрея 2026-10-02 — отчёт синтеза, правило NWP.фаза.

## Стадия 4. Дозаписать после каждой правки воркфлоу

Это продолжение протокола изменений n8n-engineering-manual (`references/write.md`, раздел 2). Выполняется в той же сессии, где была правка. Не переносится на потом.

**Шаг 1.** Назвать паспорт, которого касается правка.

**Шаг 2.** Паспорта нет — создать по стадии 3 прямо сейчас. Паспорт есть — три действия, все три:
- вставить ADR-блок перед маркером `%%ЗОНА_В_КОНЕЦ%%` («Правило записи зон» ниже);
- сверить строки ЗОНЫ А — ТРИГГЕР, СВЯЗИ, CREDENTIALS — и ЗОНЫ Б — СХЕМА, ИЗВЕСТНЫЕ ОГРАНИЧЕНИЯ. Почему: ADR без этой сверки означает дрейф, а не обновление. Признак: правка добавила или убрала узлы — СХЕМА в паспорте стала неверной молча, она описывает прежнюю цепочку. Основание: 1 случай, 2026-09-26 — отчёт синтеза, правило NWP.сверка-зон;
- проверить результат перечитыванием документа, а не ответом инструмента.

**Шаг 3.** Сессия не закрывается без выполненного шага 2 либо явного отказа Андрея с указанной причиной.

Ответственность: Claude следит, чтобы шаги не были пропущены. Андрей отвечает за содержание ADR — контекст, альтернативы, последствия.

### Правило записи зон

**ЗОНА А и ЗОНА Б правятся через `gdocs-replace` короткими уникальными однострочными якорями.** Почему многострочный якорь запрещён и как выбирать якорь — google-drive-docs, `references/docs-write.md`, раздел 3.2. Строка не уникальна — не дробить правку, а дописать новый блок с датой внутри зоны.

**ЗОНА В — только дозапись.** Старые ADR-блоки не редактировать и не удалять. Почему: зона В — история решений; переписанное решение теряет ответ на вопрос «почему так было».

**Новый ADR вставляется ПЕРЕД маркером `%%ЗОНА_В_КОНЕЦ%%`, инструмент выбирается по размеру блока:**

| Размер ADR-блока | Чем вставлять |
|---|---|
| до примерно 2 КБ | `gdocs-replace`: якорь `%%ЗОНА_В_КОНЕЦ%%` заменяется на (ADR-блок + перенос строки + тот же маркер) |
| крупнее примерно 2 КБ | `gdocs-apply-from-file` в режиме `replace`, `search` = `%%ЗОНА_В_КОНЕЦ%%`; текст ADR вместе с маркером кладётся файлом на Drive. Через тело вызова текст не проходит, ограничение размера не действует |

Механизм вставки многострочного блока на место однострочного якоря, граница около 2 КБ (осторожная линия, а не измеренный предел), её причина и условие пересмотра — google-drive-docs, `references/docs-write.md`, разделы 3.0, 3.2 и 3.6. Здесь — только якорь и порядок «блок, перевод строки, маркер», принадлежащие паспорту. Признак, что нужен второй путь: ADR-блок с подробной СХЕМОЙ или списком альтернатив легко переходит за несколько килобайт. Основание: 1 случай, 2026-09-26 — отчёт синтеза, правило NWP.размер-ADR.

**Простой `gdocs-append` для ADR ЗАПРЕЩЁН.** Почему: он пишет в конец документа, ПОСЛЕ маркера, и блок выпадает из читаемой зоны. Основание: 1 случай, 2026-06-30 — отчёт синтеза, правило NWP.append.

**После вставки перечитать документ.** Почему: склейка строк не ловится ответом `success: true`.

## Стадия 5. Воркфлоу больше не нужен

Ставший ненужным воркфлоу — временный зонд, пробный, одноразовый или вытесненный новым — снимается с публикации, но не архивируется и не удаляется. Исключение: устаревшую версию инструмента, вытесненную его новой версией, архивировать можно (решение Андрея 2026-10-20; n8n-engineering-manual, `references/write.md`, раздел 2.5). Как снимать и как проверять снятие чтением (`active: false`; слово «деактивировал», в том числе от владельца, проверкой не считается) — n8n-engineering-manual, `references/write.md`, раздел 2.5. Что воркфлоу снят и почему, записывается туда, где проект хранит невзятое и снятое (обычно `NOT_TAKEN.md` или журнал проекта), — причина обязательна и тогда, когда паспорта у воркфлоу нет. Пометки «временный — архивировать после снимка» в описаниях воркфлоу и журналах проектов не исполняются.

Часть, принадлежащая паспорту:

**Если у воркфлоу есть паспорт — вставить перед `%%ЗОНА_В_КОНЕЦ%%` строку** (по «Правилу записи зон»):

```
СТАТУС: СНЯТ С ПУБЛИКАЦИИ [дата] — [причина; чем вытеснен, если вытеснен] — КАК ВЕРНУТЬ: [publish_workflow; что проверить перед возвратом, если есть]
```

Если воркфлоу архивирован — та же строка со словом `АРХИВИРОВАН`, а в поле КАК ВЕРНУТЬ — «владелец возвращает из архива руками в редакторе, затем publish_workflow»: архивированный воркфлоу MCP вернуть не умеет. Архивировать без решения владельца можно только устаревшую версию инструмента, вытесненную новой (исключение выше); в остальных случаях решение принимает владелец, сессия архивацию по умолчанию не предлагает.

Почему поле КАК ВЕРНУТЬ: снятый воркфлоу — инструмент, который скорее всего понадобится снова; тот, кто будет его возвращать, читает паспорт, и путь возврата должен стоять рядом с причиной снятия (решение Андрея 2026-10-21).

**Паспорт не удалять никогда.** Почему: ЗОНА В с историей решений остаётся, и именно по ней потом узнают, почему воркфлоу сняли. Состояние `active` или `archived` само выводится из снимка — строка в паспорте нужна ради причины, а не ради статуса.

Основание: решение владельца 2026-10-08 и 1 случай непроверенного снятия, 2026-10-01 — отчёт синтеза, правило NWP.снятие.

## Где хранятся паспорта

**Папка DOCS заводится отдельно для каждого проекта.** Её ID записывается в каноне проекта строкой с ключом `DOCS_FOLDER: [ID папки Google Drive]` — там, где проект держит свои инструменты: у проекта в репозитории — его `PLAN.md`, раздел ИНСТРУМЕНТЫ; у лаборатории — её `INDEX.md`; у проекта, чей INDEX ещё в Google Docs, — секция ИНСТРУМЕНТЫ этого INDEX. Ключ пишется именно так, а не своими словами. Почему: ID папки ищут поиском по ключу в папке проекта, и строка, подписанная иначе («DOCS папка:»), этим поиском не находится. Признак: в папке проекта поиск `DOCS_FOLDER` пуст, а паспорта у проекта есть — ключ подписан иначе или не записан; найти папку поиском по Drive и записать строку с ключом. Основание: сверка носителей 2026-10-21 — отчёт синтеза, правило NWP.docs-folder.

Имя файла — `[ПРОЕКТ]_WF_[имя-воркфлоу]`:

| Имя файла | Расшифровка |
|---|---|
| `N8N_WF_gdocs-append` | Second Brain, воркфлоу append |
| `WB_WF_finance-sync` | Wildberries, финансовая синхронизация |
| `OZON_WF_intake` | Ozon, загрузка отзывов |

**Схема имени — не косметика:** она единственное, что позволяет найти паспорт поиском по Drive, когда строки в `description` нет (стадия 1, путь 2).

## Долг паспортов

**Сколько живых воркфлоу без строки паспорта, с пустым `description` и с разным регистром строки — выводится заново одним вызовом `search_workflows`:** строка паспорта ищется в `description` без учёта регистра. Числа в этот Skill не пишутся. Долгом считается и паспорт, который есть, но недостижим: не назван ни в `description`, ни в `registry/tools.md`, — ни один путь стадии 1, кроме поиска по имени, его не найдёт. Почему: это снимок инстанса, он устаревает с первой правкой; текущие числа держит `projects/n8n/STATE.md`, раздел «Паспорта воркфлоу».

**Недостающие паспорта создаются при следующем касании воркфлоу, а не пачкой заранее.** Почему: паспорт, написанный без повода, описывает воркфлоу, которого никто не проверял по коду в эту минуту; при касании живой код читается всё равно (стадия 1).
