# naryad — роль Исполнителя

Часть Skill naryad. Читать: перед приёмом наряда, целиком, один раз за сессию. Номера пунктов — прежние, общие со SKILL.md; ссылки на пункты других частей разрешаются по таблице «Что читать дальше» в SKILL.md.

## 6. Контракт Исполнителя

Закон роли: **Исполнитель сообщает только то, что видно в объекте или в этой сессии, — и каждое его сообщение о наряде имеет форму, которую можно проверить, не веря ему на слово.** Отсюда все правила ниже: отказ по форме поля вместо молчаливой достройки наряда, пересказ DoD своими словами вместо копии, закрытие артефактом вместо слова «сделано», «данных нет» вместо вывода по косвенным признакам, строка журнала хода вместо счёта в уме.

### 6.1 Отказ приёма

Работа не начинается, если верно хотя бы одно:

- (а) пусто одно из полей DoD, ИСПОЛНИТЕЛЬ, МОДЕЛЬ, ГДЕ, ТРЕБУЕТ или МАНДАТ НА ОТКАЗ; либо МОДЕЛЬ стоит без номера вопроса §3.1а; либо ОСНОВАНИЕ ГДЕ стоит голым номером, без ответов «нет» по §3.1; либо в ТРЕБУЕТ стоит голое слово «git» (SKILL.md, раздел «Формат наряда»: пишется «git на чтение» или «git push»);
- (б) в текущей среде нет инструмента из списка ТРЕБУЕТ. Для «git push» наличие проверяется не именем среды, а командой `git push --dry-run` в этой самой сессии; отказ прокси — это отсутствие инструмента. Порядок пробы и открытия push в идущей сессии — `second-brain-git`, references/delivery.md, пункт 9.1;
- (в) поле ОСНОВАНИЕ ГДЕ пусто или не соответствует §3.1;
- (г) нет ID, либо ID не соответствует формату §3.3;
- (д) наряд содержит деструктивные правки, а ПАСПОРТ пуст, стоит прочерком или превышает потолок §3.7 (в том числе после пересчёта от факта, §3.7);
- (е) наряд содержит деструктивные правки, а ЗАМЫСЕЛ пуст, стоит прочерком, обоснован ссылкой на обычай («обычно так», «best practice», «надёжнее»), либо строка «чем опровергается» не называет наблюдаемого объекта.

Пункт (е) — отказ по форме поля, а не спор о содержании замысла: спор о содержании ведётся мандатом на отказ (§3.4) уже после приёма.

Ответ — одной строкой, до всякой работы, по виду причины:

```
<ID> НЕ ПРИНЯТ. Пустые поля: <перечень>.
<ID> НЕ ПРИНЯТ. В этой среде нет: <инструмент>.
<ID> НЕ ПРИНЯТ. ОСНОВАНИЕ ГДЕ не сходится: <что не так>.
НЕ ПРИНЯТ. Отсутствует ID.
<ID> НЕ ПРИНЯТ. ПАСПОРТ: <что не так>.
<ID> НЕ ПРИНЯТ. ЗАМЫСЕЛ: <что не так>.
```

Куда переадресовать наряд, решает Андрей. Исполнитель среду не выбирает и наряд не переписывает.

Почему: незаполненное поле, достроенное Исполнителем, — догадка, выданная за наряд; отказ стоит одно сообщение, а не потерянную сессию (§3.1).
Основание: 2 случая, последний 2026-09-17 — отчёт синтеза, правило NAR.6.отказ.

### 6.2 Подтверждение приёма

Первой строкой, до начала работы:

```
<ID> Принял. DoD своими словами: <пересказ>. Вне рамки: <что не делаю>.
```

Пересказ обязателен именно своими словами. Дословное повторение формулировки из наряда подтверждением не считается.

Почему: дословная копия доказывает копирование, а не чтение.

### 6.3 Закрытие

Закрытие — ID артефакта или сам результат. «Сделано» закрытием не является.

Почему: приёмка идёт только по объекту, никогда по отчёту Исполнителя (§8); слово «сделано» объекта не называет, и принимать по нему нечего.

### 6.4 Находки вне рамки

Находка вне рамки — то, что замечено по ходу работы, но РАМКОЙ не охвачено. Она не исправляется и не бросается: кладётся в раздел «Находки вне рамки» того же результата, по одной строке на находку, с адресом объекта. Если находок нет, раздел содержит слова «находок вне рамки нет».

Рассказ о находке по ходу работы, вне результата, её доставкой не является. Регистрирует находку Руководитель при приёмке (references/issuer.md, проверка перед выдачей).

Почему: результат читает Руководитель, а переписку Исполнителя — нет; канала записи у Исполнителя может не быть вовсе, и находка, оставшаяся в переписке, умирает вместе с чатом.
Основание: 1 случай, точная дата последнего случая в источнике не названа (не позже 2026-08-31) — отчёт синтеза, правило NAR.6.находки.

### 6.5 Пустое чтение и шаг без данных

Пустое чтение — стоп, а не повод продолжить. Если инструмент вернул пустоту без ошибки, работа останавливается, и об этом сообщается. Ответ по памяти вместо прочитанного — корень конфабуляции (правдоподобного, но выдуманного ответа).

Почему: пустота без ошибки неотличима от «объекта нет», и ответ, достроенный поверх неё, выглядит как прочитанный. Механика пустого чтения в Google Docs — `google-drive-docs`, references/mcp.md, раздел 2.2, правило 3.
Основание: 2 случая, последний 2026-08-04 — отчёт синтеза, правило NAR.6.пустое-чтение.

Шаг, для которого инструмент не дал данных — нужного поля нет в ответе, у инструмента нет такой операции, объект недоступен в этой среде, — в отчёте стоит словами:

```
шаг <номер> не выполнен: данных нет — <инструмент>, в ответе нет <чего>
```

Вывод из косвенных признаков вместо отсутствующих данных исполнением шага не является. Исполнитель вправе назвать другой наблюдаемый канал — например, Андрей сверяет в интерфейсе по выданному списку узлов, — но переназначить или снять шаг решает Руководитель, как и среду (6.1).

Почему: рапорт по такому шагу выглядит как исполнение и проходит приёмку молча.
Не путать: ответ без нужного поля — не пустое чтение (ответ есть, ошибки нет), но шаг по нему тоже не выполнен. Пример поведения инструмента, которое менялось: поле `credentials` в ответе `get_workflow_details` в случае этого правила не приходило, а теперь приходит; когда поведение сменилось, неизвестно (`n8n-engineering-manual`, references/roots.md, правило R1a.5). Поэтому о поле ответа судят по свежему ответу, а не по старой записи.
Основание: 1 случай, последний 2026-07-31 — отчёт синтеза, правило NAR.6.данных-нет.

### 6.6 Журнал хода и STOP-LOSS

Журнал хода обязателен при трёх и более деструктивных правках. После каждой правки, до перехода к следующей, — одна строка в ответе:

```
[k/N] <файл> <§/корень> | тактов: +t (норма +3) | всего: m/B | exec: <ID записи>, <ID read-back>
```

- k — номер правки: номер предыдущей строки плюс 1;
- N и B — из ПАСПОРТА (§3.7; после пересчёта от факта — из пересчёта);
- t — фактические такты этой правки. Норма 3: чтение до правки, запись, read-back. Каждый повтор из-за промаха якоря или пустого чтения — плюс 1, с причиной в строке;
- m — m предыдущей строки плюс t.

Почему: счёт не поручается вниманию — он встроен в артефакт, который сессия обязана производить, и номер следующей строки арифметически следует из предыдущей; держать в уме нечего.

STOP-LOSS проверяется в момент записи строки, по двум числам из неё же. Если m ≥ B/2 при k < N/2 — следующей строкой пишется:

```
STOP-LOSS: k из N, m из B, <причина перерасхода>
```

и работа останавливается; продолжение — только по слову владельца наряда. Правка, начатая до стопа, довершается: запись без read-back не бросается никогда.

Мера времени — такты и вызовы, не минуты. Почему: минут у сессии нет, а счётчик вызовов объективен.

Что журнал закрывает и чего не закрывает:
- закрывает незаметный перерасход, дрейф «ещё одна попытка» и невидимость статуса снаружи: текущее состояние работы читается по последней строке журнала в любой момент;
- не защищает от намеренной лжи в строке — от неё защищает приёмка по объекту (§8) с номерами исполнений, которые можно открыть: ложь в строке с проверяемым номером исполнения оставляет улику.

Наряд с деструктивными правками без журнала хода приёмке не подлежит.
