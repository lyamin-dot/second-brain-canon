# naryad

Наряд — сообщение, которым работа раздаётся ролям: Руководитель проектирует, Прораб дробит, Исполнитель делает, Андрей — шина. Здесь: форма наряда и его полей, маршрут шага собственного плана, контракты ролей, паспорт и замысел деструктивных правок, приёмка, пересмотр этого Skill.

Применяется к разработке новых идей и сложных задач в Claude-Project и в Летописи (проект в репозитории без Claude Project, мастер-промпт которого ведёт работу по нарядам): чтение файлов и воркфлоу, извлечение из технической документации, написание кода новых воркфлоу, проверка старого кода. Формат окупается в диагностике, аудите, деструктивных и боевых операциях — там, где независимая проверка может поймать ложную тревогу, сбор ключей доступа вслепую или цифру без источника. Не применяется к рядовым вопросам, единичным операциям и к быстрой тесно связанной итерации, где Андрей и так в диалоге на каждом шаге.

## Стоп-правила

### Роли и шина
- Руководитель не читает файлы, не пишет и не вызывает инструменты — кроме шага с напечатанной строкой `МАРШРУТ: Б`.
- Вызов инструмента Руководителем без строки `МАРШРУТ: Б` перед ним и блок НАРЯД без строки `МАРШРУТ: В` перед ним — нарушение роли.
- Роли между собой не сообщаются: все наряды и отчёты идут через Андрея (вне автономного режима — без изменений).
- Исполнитель нарядов не выдаёт никогда.
- Прораб не дробит за пределами полученного DoD и не выдаёт нового наряда от себя при выходе за РАМКУ — возврат Андрею.
- Прораб не подменяет DoD родителя серией мелких удобных дочерних нарядов.
- Прораб не создаёт собственных корневых ID и не пересылает отчёты дочерних нарядов по одному.
- Прораб не расширяет унаследованные ТРЕБУЕТ, ГДЕ, МАНДАТ НА ОТКАЗ — только сужает.
- Дробление, которое ломает замысел родителя, не ведётся частями — возврат Андрею.
- Исполнитель среду не выбирает и наряд не переписывает; куда переадресовать отбитый наряд, решает Андрей.
- Исполнитель не достраивает незаполненное поле наряда сам — отказ приёма.

### Форма наряда
- Строку поля не пропускать: незаполненное поле — прочерк.
- Наряд не публиковать двумя носителями как половинками (блок НАРЯД в чате и документ рядом) — один носитель целиком.
- DoD не писать состоянием («разобраться», «улучшить», «проверить») — только объектом.
- В поле ТРЕБУЕТ не писать оснастку и метод — только потребность.
- Слово «git» в ТРЕБУЕТ голым не писать — «git на чтение» или «git push».
- Действие в интерфейсе n8n или в браузере Андрея не выполнять без отдельной строки «интерфейс n8n» или «браузер Андрея» в ТРЕБУЕТ и явного «да» Андрея на эту строку; «не знаю», молчание и отсутствие возражений разрешением не считать.
- Привязку ключа в ТРЕБУЕТ как действие в интерфейсе не писать, если сессия может сделать её сама операцией `setNodeCredential`.
- Сообщение о наряде без ID не выдавать, не принимать и закрытием не засчитывать.
- В ID больше одной точки не ставить; префикс проекта не вводить.
- Отмену и новое поручение по отменённому объекту не отправлять одним сообщением.
- Журнал выданных нарядов не заводить, пока Андрей дважды не смог найти наряд по ID (ID самодостаточен: дата и номер).
- Файлов на Drive под наряд не создавать, Drive-ID не заводить, в INDEX не писать: наряд — сообщение (ID наряда файлом не является).

### Поле ГДЕ
- ГДЕ не выбирать по инструментам среды — только по нужному наряду контексту.
- Объём результата и диалог по ходу выполнения доводом за выбор среды (за чат проекта) не считать.
- Не удалось ответить на вопрос 1 или 2 дерева ГДЕ — не писать «новый чат вне проекта»: «ГДЕ: не определено», наряд не выдаётся.
- ОСНОВАНИЕ ГДЕ голым номером не печатать — с ответами «нет» и фактами по всем предыдущим вопросам.
- Наличие инструментов на выдаче не проверять — проверка на приёме.
- Наряд, которому нужны и push, и Канал, в сессии без инструментов n8n одним нарядом не выдавать — два наряда по потребности с явно назначенным порядком.
- При повторном отказе пробы push обход не искать — НЕ ПРИНЯТ.
- Наряд, назначающий ГДЕ по имени среды в расчёте на открытый push, на приёме отбивается: среда знает о push только по пробе `git push --dry-run`.

### Поле МОДЕЛЬ
- В поле МОДЕЛЬ не печатать имя модели — класс и номер сработавшего вопроса.
- Имена моделей в этом Skill не писать.
- Ни один вопрос дерева МОДЕЛЬ не сработал — наряд не выдавать: он переписывается (дефект ЗАДАЧИ, не поля).

### Мандат на отказ
- Наряд на проверку, аудит, верификацию не выдавать с мандатом уже, чем «процедура, посылка, цифры, вход».
- Отказ по мандату без объекта (строка файла, номер исполнения, замер) не оформлять — рассуждение основанием не является.
- Значение «процедура» не применять к бюджетам чтения и размерам файлов репозитория: отказ по размеру файла — нарушение мандата.
- На потолки записи в байтах у файлов репозитория не ссылаться: их нет.
- МАНДАТ НА ОТКАЗ не копировать из прошлого наряда.

### Ограничители
- Глубина 1: наряды выдают только Руководитель и Прораб.
- Больше пяти открытых корневых нарядов одновременно не выдавать; шестой ждёт закрытия любого из пяти (дочерние в потолок не входят).
- Нет DoD — наряд не выдавать и не принимать; поручений «вообще» нет.
- Один файл — один наряд, в обе стороны.
- Два наряда, работающих с одним файлом, одновременно не вести — даже если один пишет в голову файла, другой в хвост.
- Для файлов репозитория непересечение путей гонки не снимает: параллельные записи состязаются за голову ветки.
- Пока открыт наряд Контролёра (проверка чужой работы), Руководитель не пишет ни в его объект, ни в ветку, по голове которой Контролёр снимает вердикты, — и маршрутом Б тоже.
- Один наряд не правит больше одного пути (исключение — атомарная запись, «Как делать», раздел «Паспорт стоимости»).
- Два наряда или два чата, работающие одновременно, не выдавать без непересекающихся наборов путей репозитория, названных в РАМКЕ каждого.

### Деструктивные правки: паспорт и замысел
- Наряд с деструктивными правками (любое изменение объекта) без ПАСПОРТА недействителен — не выдавать, не принимать.
- Паспорт с числами «на глаз», без следа формулы, не печатать.
- Наряд с N > 5 или правимых путей > 1 не выдавать Исполнителю — только через Прораба.
- Наряд, превышающий потолок, не разбивать на отдельные корневые наряды с отдельными пересылками.
- Исключение об атомарной записи не брать самопровозглашением: без номера (названия) правила, требующего атомарности, — не применяется.
- В исключение об атомарной записи не добирать пути, которые атомарности не требуют.
- Записи результата (файл контракта, запись в журнал, позиция очереди) из N не выкидывать.
- РАМКОЙ не запрещать запись в путь, куда обязан лечь результат наряда.
- ЗАМЫСЕЛ не обосновывать обычаем («обычно так», «best practice», «так надёжнее»).
- Строку «слабое звено» не оставлять пустой и не писать «слабых мест нет».
- Наряд с несущим слабым звеном не выдавать — и не выдавать, пометив звено в поле.
- Мандат на отказ проверку замысла не заменяет: он включается после пересылки и приёма.
- Историю правок наряда не печатать — печатается итоговая версия.
- Кто разметил, что вырезать, тот в том же заходе не режет; кто режет, тот список не пополняет.
- Наряд с деструктивными правками без журнала хода (при трёх и более правках) приёмке не подлежит.
- Правку, начатую до STOP-LOSS, не бросать: запись без read-back не оставлять никогда.
- После STOP-LOSS работу не продолжать без слова владельца наряда.
- Время работы не мерить минутами — тактами и вызовами.

### Выдача (Руководитель)
- Сессия Руководителя не заканчивается без блока НАРЯД или строки `МАРШРУТ: Б` с результатом по объекту.
- Якорь правки в наряде не диктовать — только целевой текст; Исполнитель не подбирает похожий якорь, если названного дословно нет, — называет расхождение в отчёте.
- Skills и коннекторы аккаунта в наряд для другой среды не пересказывать.
- Наряд для другой среды не выдавать без рамки, всех ID файлов и формата результата целиком.
- Результат, который станет входом следующего наряда, не оставлять «в ответ» — только файлом.
- Наряд не выдавать за лёгкость исполнения вместо важности.
- Наряд на находку «кандидат в БЛОКЕРы» и на мелочь не печатать.
- Находку без объекта в реестре БЛОКЕРом не объявлять; при сомнении — ветка «кандидат».
- На `core/R-05.md` как на место, где стоит объект-БЛОКЕР, не ссылаться: там нет строк-задач.
- Три и более наряда подряд с меткой БЛОКЕР без ссылок на разные объекты реестра — не продолжать: спросить Андрея, не мелочь ли это.
- Условие «подстроки нет» в DoD не писать поиском по всему файлу — только с адресом (строка, таблица, абзац).
- Протокол или наряд из нескольких шагов не выпускать, пока у каждого шага нет ветки «если не выполнено, то …».
- Решение по исполняемому протоколу не предлагать, не прочитав протокол целиком, включая поздние фазы.
- В задание проверяющему (аудит, приёмка, сверка, сценарий для подагента) не вписывать ожидаемый вердикт и ожидаемую роль объекта; широкий МАНДАТ НА ОТКАЗ от подсказки не спасает; устойчивость конкретного проверяющего правило не отменяет.
- Утверждение документа о коде (паспорт воркфлоу, INDEX, журнал, лист настроек, реестр заданий, прошлый наряд) за факт не брать — посылка.
- Наряд на аудит или приёмку, DoD которого выполним одним чтением документов без чтения живого объекта, не выдавать: такой аудит не проведён.
- Паспорт воркфлоу доказательством для правки, аудита и приёмки не считать — только первым чтением.
- Мандат «только чтение» правом записи находок Исполнителю не считать.
- Наряд с DoD «промпт переключён» не выдавать без файла со старым текстом мастер-промпта.

### Маршрут шага
- Шаг собственного плана без строки `МАРШРУТ:` не начинать.
- «Сложность», «важность», «ощущение контекста» входами вопросов маршрута не считать.
- Наряд на шаг с маршрутом А или Б не выдавать.
- Маршрут Б не снимает паспорт, журнал хода, ограничители и приёмку по объекту.
- Действие, в выдаче наряда на которое отказано (по ПАСПОРТУ, ЗАМЫСЛУ, релевантности) или которое отклонил Андрей, маршрутом Б не исполнять — ни целиком, ни первым шагом под другим названием.
- Самопроверка подмену названия не ловит — её ловит вопрос со стороны.

### Исполнитель
- Работу не начинать, пока не прошла проверка приёма («Как делать», раздел «Приём наряда»).
- Дословную копию DoD подтверждением приёма не считать — только пересказ своими словами.
- «Сделано» закрытием не считать.
- Находку вне рамки не исправлять и не бросать; рассказ о ней вне результата доставкой не считать.
- Пустое чтение (пустота без ошибки) — стоп и сообщение; ответ по памяти вместо прочитанного не давать.
- Вывод из косвенных признаков вместо отсутствующих данных исполнением шага не считать.
- Ответ без нужного поля — не пустое чтение, но шаг по нему тоже не выполнен.
- О поле ответа инструмента не судить по старой записи — только по свежему ответу.
- Шаг без данных Исполнитель сам не переназначает и не снимает — это решает Руководитель.
- Журнал хода от намеренной лжи в строке не защищает — защищает приёмка по объекту с номерами исполнений.

### Приёмка
- Не принимать по отчёту Исполнителя или по слову «сделал» — включая собственный отчёт Руководителя о собственной работе; закрывающий читает объект сам и не сверяет два описания объекта между собой (особенно утверждения об отсутствии, удалении, состоянии).
- Правку построчного списка (INDEX.md и подобных) не принимать по размеру (byteLength) — по diff строк с предыдущим прочитанным текстом.
- Отдельный наряд на приёмку не выдавать для голого числа — только когда проверяется суждение Исполнителя.

### Пересмотр этого Skill
- Условие пересмотра не записывать счётчиком («если из N нарядов…», «если за 10 нарядов…») — только вопросом харвеста.
- При превышении прогноза паспорта без STOP-LOSS формулировки не ужесточать — искать, какой слой Skill действовал в сессии.

## Как делать

### Роли

- **Руководитель** — проектирует: формирует замысел, разбивает на наряды, оценивает результаты. Инструменты — только на шаге с `МАРШРУТ: Б`; нужны данные, а инструмента в среде нет — наряд на чтение. Оснастку сред знать не обязан. Заполняет ТРЕБУЕТ (по задаче), ГДЕ и ОСНОВАНИЕ ГДЕ, ID (в момент выдачи). Один замысел — минимум нарядов, а не максимум.
- **Прораб** — организует: получил наряд, дробит его на наряды Исполнителям внутри полученного DoD (definition of done — проверяемый признак готовности), собирает отчёты, отдаёт один результат.
- **Исполнитель** — делает: один наряд, один результат, один артефакт.
- **Андрей** — шина: все наряды и отчёты идут через него. Исключение — автономный режим (Skill `avtopilot`, раздел «Ворота 4. Исполнение — Андрея нет»): там шина — сессия-диспетчер, Андрей один раз согласует контракт запуска.
- Роли распределяют ответственность за шаг, а не правоту. Прав тот, кто читал источник, независимо от класса модели (Skill `second-brain-engineer`, раздел «Р15. Провенанс и верификация — единый стандарт»): Исполнитель, прочитавший файл, опровергает Руководителя, который его не читал. Наряд при этом остаётся в силе до отмены Андреем.
- Наличие инструментов проверяет та среда, которая знает о себе достоверно, — в момент приёма наряда. Реестра инструментов сред нет.

### Форма наряда

Наряд печатается всегда целиком, одним носителем — либо блоком НАРЯД в чате, либо документом.

```
<ID> НАРЯД
ЗАДАЧА:
DoD: (проверяемо: объект, а не состояние)
РАМКА: (что НЕ делать / где остановиться)
МАНДАТ НА ОТКАЗ: (что Исполнитель вправе отвергнуть — раздел «Мандат на отказ»)
ТРЕБУЕТ: (инструменты и доступы, без которых наряд не выполнить)
ПАСПОРТ: (стоимость по формуле раздела «Паспорт стоимости»; обязателен при деструктивных правках, для read-only нарядов — прочерк)
ЗАМЫСЕЛ: (три строки по разделу «Замысел»; обязателен при деструктивных правках, для read-only нарядов — прочерк)
ИСПОЛНИТЕЛЬ: Прораб | Исполнитель
МОДЕЛЬ: средний | высокий | высший — номер сработавшего вопроса раздела «Поле МОДЕЛЬ»:
ГДЕ: чат проекта <имя> | сессия Летописи <имя> | новый чат вне проекта
ОСНОВАНИЕ ГДЕ: номер сработавшего вопроса раздела «Поле ГДЕ»
РЕЗУЛЬТАТ В: <ID файла или «в ответ»> — раздел «Куда писать результат»
```

- **РАМКА** у нарядов (чатов), работающих одновременно, называет непересекающиеся наборы путей репозитория — у каждого свой.
- **DoD** — в терминах объекта: «ID созданного паспорта», «occurrencesChanged=1 + подтверждающее чтение», «список из N строк».
- **ТРЕБУЕТ** — потребность, не оснастка: чтение Drive, запись Drive, n8n, shell (командная строка), git, интернет, работа с загруженными файлами. «git» пишется как «git на чтение» (клон, diff, история, `git hash-object`) или «git push» (доставка в ветку main по Skill `second-brain-git`, раздел «Маршрут доставки в main»; Исполнитель проверяет на приёме пробой `git push --dry-run`). Действие в интерфейсе n8n или в браузере Андрея (клик в редакторе, вставка текста; привязка ключа — только когда сессия не может сделать её сама `setNodeCredential`) — отдельной строкой «интерфейс n8n» или «браузер Андрея», исполняется только по явному «да» Андрея на эту строку.

### Поле ГДЕ

Умолчания нет. Вопросы по порядку, первое «да» останавливает проверку; выбор — по нужному наряду контексту.

1. Нужен ли контекст Claude-Project — мастер-промпт, Зона А INDEX, история переписки проекта, — который наряд не может унести с собой целиком в поля ЗАДАЧА, РАМКА, ТРЕБУЕТ? ДА → `чат проекта <имя>`.
2. Работа принадлежит Летописи — проекту в репозитории без Claude Project, мастер-промпт которого ведёт работу по нарядам? ДА → `сессия Летописи <имя>`: сессия, в которую загружен мастер-промпт этой Летописи (её контекст — мастер-промпт и папка репозитория).
3. На вопросы 1 и 2 ответ «нет», и каждое «нет» обосновано фактом из ТРЕБУЕТ или ЗАДАЧИ → `новый чат вне проекта`. Наряд несёт всё, что нужно Исполнителю (раздел «Наряд для другой среды»).

ОСНОВАНИЕ ГДЕ — номер сработавшего вопроса и ответы «нет» на все предыдущие с фактом из ТРЕБУЕТ или ЗАДАЧИ. Образец: «3 — контекст проекта не нужен (1), работа не Летописи (2)».

Инструменты проверяются на приёме:
- push не гарантирован ни одной средой: предикат — список репозиториев, авторизованных для сессии. Исполнитель пробует `git push --dry-run`; при отказе добавляет репозиторий в сессию с правом записи (если среди её инструментов есть добавление репозитория) и повторяет пробу; при повторном отказе — `НЕ ПРИНЯТ` (раздел «Приём наряда», пункт б). Порядок пробы — Skill `second-brain-git`, раздел «Push: проверка и открытие».
- Канал (воркфлоу n8n чтения и записи репозитория, Skill `second-brain-git`) есть только там, где к сессии подключены инструменты n8n (MCP n8n): проверяется по списку инструментов самой сессии, не по имени среды.
- Чат проекта, не обоснованный в ТРЕБУЕТ или ЗАДАЧЕ потребностью в контексте проекта, на приёме отбивается (пункт в). Ошибка в ГДЕ ловится на приёме: её цена — одно сообщение.

### Поле МОДЕЛЬ

Адресат поля — Андрей (модель чата выбирает он; сессия не знает достоверно, на какой модели работает). Поле печатает класс и номер вопроса, который сверяется с ЗАДАЧЕЙ за одно чтение. Вопросы по порядку, первое «да» останавливает проверку:

1. Работе нужен весь каталог или весь корпус в поле зрения сразу? ДА → высший.
2. Наряд проверяет суждение другой сессии (аудит, приёмка, ревизия), ведёт диагностику без готовой гипотезы или проектирует новое (правило, архитектуру, воркфлоу)? ДА → высокий.
3. У шага написана процедура, гипотеза готова, DoD — объект? ДА → средний.

Поле без номера вопроса на приёме отбивается как незаполненное (пункт а). Критерий классов — Skill `second-brain-engineer`, раздел «Р18. Калибровка исполнителя»; здесь только порядок вопросов.

### ID и сообщения о наряде

ID = `Н-ДД.ММ-NN`: ДД.ММ — дата выдачи, NN — порядковый номер с 01 в пределах суток. Дочерние наряды Прораба — `Н-ДД.ММ-NN.1`, `.2`, `.3`. Пример: Н-08.08-02 и его дочерние Н-08.08-02.1, .2.

- До присвоения номера выдающий ищет его по репозиторию (журналы, планы проектов) — номер должен быть свободен.
- Коллизия (два Руководителя в один день): Андрей дописывает букву при передаче — Н-08.08-02а.

ID — первое слово каждого сообщения о наряде, во всех направлениях:
- выдача: `Н-08.08-02 НАРЯД`
- отказ приёма: `Н-08.08-02 НЕ ПРИНЯТ. <причина>`
- приём: `Н-08.08-02 Принял. DoD своими словами: …`
- закрытие: `Н-08.08-02 ЗАКРЫТ. <ID артефакта>`
- отказ по мандату: `Н-08.08-02 ОТКАЗ ПО МАНДАТУ: <что отвергнуто> — <на каком основании>.`
- сводка Прораба: `Н-08.08-02 СВОДКА. Закрыты: .1 .2 .3`
- отмена Андреем: `Н-08.08-02 ОТМЕНЁН.`

### Мандат на отказ

РАМКА говорит, чего НЕ делать; МАНДАТ НА ОТКАЗ — что Исполнитель вправе отвергнуть. Значения:
- процедура — вправе объявить сам метод негодным и остановиться;
- посылка — вправе отвергнуть допущение, на котором стоит ЗАДАЧА;
- цифры — вправе не принять числа из наряда без источника;
- вход — вправе отвергнуть результат предыдущего наряда;
- нет — отказ не предусмотрен, выполнять как написано.

Для нарядов на проверку, аудит и верификацию — всегда «процедура, посылка, цифры, вход». Отказ по мандату оформляется как результат (`<ID> ОТКАЗ ПО МАНДАТУ: …`) — это закрытие наряда, а не провал; основание — объект: строка файла, номер исполнения, замер. Спор о содержании замысла ведётся мандатом после приёма. У бюджетов чтения и размеров файлов репозитория есть переливной клапан (Skill `second-brain-git`, раздел «Превышение бюджета чтения» и «Стоп-правила», подраздел «Запись»): размер файла — не негодность метода.

### Наряд для другой среды

В другую среду переезжает только то, что живёт на уровне аккаунта: Skills аккаунтного уровня и коннекторы (Settings) действуют во всех средах — в наряд не переписываются. Мастер-промпт, Зона А INDEX и история переписки проекта не переезжают — наряд для сессии Летописи или нового чата вне проекта несёт целиком рамку, все ID файлов и формат результата. Диалог по ходу работы (сообщение Андрея → действие Исполнителя → продолжение; привязка ключа, «готово», восстановление из корзины) идёт в любой среде так же, как в чате проекта.

### Релевантность Главной цели

Перед печатью блока НАРЯД Руководитель про себя отвечает на два вопроса:
- (а) Известна ли Главная цель текущей сессии или проекта в явном виде? Нет — наряд о её выяснении, ЗАДАЧА так и пишется: «выяснить Главную цель».
- (б) Продвигает ли наряд к Главной цели, или он выбран за лёгкость исполнения?

Ответ на (б) «нет» или неочевиден — решает объект в реестре:

| Чем является находка | Что делать |
|---|---|
| БЛОКЕР — уже зафиксированный объект: существующая строка с меткой БЛОКЕР в Зоне А INDEX Docs-проекта, в `labs/sys/INDEX.md` или в STATE.md проекта в репозитории | Наряд выдаётся. Одной строкой перед блоком НАРЯД — какой объект-БЛОКЕР он закрывает, ссылкой на строку, не пересказом. |
| Кандидат в БЛОКЕРы — похоже на риск потери данных или повреждения структуры, но нигде не зарегистрировано | Наряд не выдаётся. Находка фиксируется `[ЗАХВАЧЕНО → НОВЫЙ БЛОКЕР?: ...]`; решение о статусе — при следующем прямом контакте с Андреем; до решения — задача в `labs/sys/` с меткой «кандидат в БЛОКЕРы». Потеря данных наблюдается прямо сейчас — сообщить немедленно, регистрация задним числом. |
| Не БЛОКЕР — мелочь, «давно не трогали», второстепенное | Наряд не печатается. Находка фиксируется `[ЗАХВАЧЕНО → ...]` и, если её нужно помнить, регистрируется задачей в `labs/sys/` (Skill `second-brain-engineer`, разделы «Р14. Запреты» (запрет 4) и «Р16. Работа вне Claude Project и регистрация обязательств»). |

Метки БЛОКЕР и РЫЧАГ определены в `core/R-05.md`; реестр объектов — строки INDEX и STATE.md, не CORE.

### Маршрут шага

Каждый шаг собственного плана — после ревизии denken, если она была, и до первого действия по шагу — получает маршрут: А — продолжать проектирование; Б — исполнить самой; В — выдать наряд. Перед первым действием печатается строка:

```
МАРШРУТ: <А|Б|В> — <№ вопроса>: <наблюдённый факт>
```

Входы вопросов — только наблюдаемые: инструмент в среде, вход в контексте, происхождение входа, число вызовов. Вопросы по порядку, первое «да» даёт маршрут:

1. У шага нет DoD-объекта, либо поле наряда (ГДЕ, якорь, ID, номер записи, посылка) пришлось бы заполнить по памяти, а не по прочитанному в этой сессии? ДА → А. Первое действие маршрута А — чтение недостающего входа (самой, если инструмент есть; иначе наряд на чтение с результатом в файл), затем шаг маршрутизируется заново.
2. Шаг исполним только в другой момент (дата, автозапуск, чужой результат), либо в ТРЕБУЕТ шага есть инструмент, которого нет в этой среде? ДА → В; ГДЕ — по разделу «Поле ГДЕ».
3. Вход шага — продукт этой сессии (её решение, замер, текст), так что поля наряда содержали бы сам записываемый текст? ДА → Б.
4. Результат шага — вход следующего шага этого же плана? ДА → Б.
5. Стоимость шага B = N×3 + R (раздел «Паспорт стоимости») не больше накладных наряда O = S + 3, где S — число Skill, которые Исполнитель обязан прочитать по ТРЕБУЕТ и по приёму (сам naryad считается), а 3 — текст наряда, приём с пересказом и отчёт через шину? ДА → Б. НЕТ → В.

Маршрут Б снимает для шага запрет Руководителю на вызов инструментов; следующий шаг маршрутизируется заново; сессия Исполнителем не становится и наряды по-прежнему выдаёт. После отказа в действии допустимый следующий шаг — тот, что снимает основание отказа (дочитать недостающий вход, посчитать паспорт), либо шаг только на чтение, который объект не меняет; само действие — только после нового решения по существу. Признак подмены: объект и операция шага те же, что в отклонённом наряде (тот же файл, те же строки, то же удаление), а название другое.

### Паспорт стоимости

Для наряда с деструктивными правками (любое изменение объекта; наряд только на чтение сюда не относится). Паспорт считается формулой:

```
ПАСПОРТ: правок=N, чтений=R, вызовов B = N×3 + R, прогноз T = B × 20 с × 2
```

- N — число деструктивных правок; каждая стоит 3 такта: свежее чтение объекта до правки, запись, независимое обратное чтение (read-back).
- R — чтения источников сверх тактов правок: задание, матрица, канон целиком и подобное.
- 20 с — латентность одного обращения к воркфлоу вместе с паузой; ×2 — запас на промахи якорей и повторы.
- Последние строки паспорта любого наряда — `запись результата: <путь>, N=1` на каждый путь, куда ляжет результат (файл контракта, запись в журнал, позиция очереди — каждая входит в N).
- Совокупный размер пересчитывается при каждом доливе задач в наряд.

Пересчёт от факта. До первой деструктивной правки Прораб, а в наряде без Прораба сам Исполнитель, пересчитывает паспорт той же формулой от факта, прочитанного в своей сессии, и печатает пересчёт. Оценка Руководителя исполнителя не связывает ни в большую, ни в меньшую сторону.

| Итог пересчёта | Что делать |
|---|---|
| укладывается в потолок | работа идёт по новому паспорту; журнал хода считает m и B по нему |
| выходит за потолок, наряд у Прораба | Прораб дробит наряд на дочерние (раздел «Прораб») |
| выходит за потолок, наряд у Исполнителя | `<ID> НЕ ПРИНЯТ. ПАСПОРТ: пересчёт от факта даёт N=…` |

Потолок наряда (для дочернего — дочернего): N ≤ 5 и правимых путей ≤ 1. Больше — наряд идёт через Прораба: тот разбивает его на дочерние внутри одной сессии; Андрею — одна пересылка и один сводный отчёт. Потолок не касается чтений: наряд только на чтение (инвентаризация, аудит, замер) читает столько источников, сколько требует DoD.

Атомарная запись. Если внешний контракт требует записать несколько путей одним неделимым действием, потолок путей не применяется — считается N. Все три условия обязательны:
1. в наряде названо правило, требующее атомарности, — например Skill `second-brain-git`: ротация журнала (архив и журнал одним коммитом), задача лаборатории вместе со строкой INDEX.md, пара «файл и список, в котором он должен быть назван»;
2. все пути перечислены поимённо в поле РАМКА;
3. запись выполняется одним вызовом, и N этого вызова равно 1.

Путь, который можно записать отдельным коммитом без нарушения названного правила, в исключение не входит и считается по общему потолку. Без названного правила наряд отбивается на приёме (пункт д).

Если повтор записи в путь результата нужно ограничить, РАМКА пишется так: «не более раза на файл, каждый случай назвать».

### Замысел

Поле печатается, а не проверяется про себя:

```
ЗАМЫСЕЛ:
почему сработает: если выполнен DoD, то <наблюдаемый результат>, потому что <механизм>
чем опровергается: <наблюдаемый факт, который покажет, что наряд был ошибкой>
слабое звено: <самое необоснованное место этого наряда>
```

| Строка | Обязана | Не годится |
|---|---|---|
| почему сработает | называть механизм | «потому что обычно так делают», «это best practice», «так надёжнее» |
| чем опровергается | называть объект: строку файла, номер исполнения (execution), замер, число | факт, который назвать нельзя: наряд переписывается до проверяемого вида |
| слабое звено | быть заполненной всегда | пустая строка; «слабых мест нет» |

- Слабое звено оказалось несущим (замысел на нём стоит и без него разваливается) — задача уходит на ревизию замысла (Skill `denken`), наряд печатается по её результату.
- Дефекты, найденные при заполнении ЗАМЫСЛА, правятся в наряде до печати.

Разметка и вырезание. Наряд, который удаляет или сокращает текст (вычитка Skill, чистка журнала, перенос с удалением в исходнике), исполняет готовый список того, что вырезать. Список — объект: файл или раздел результата другого захода (другой сессии или предыдущего наряда), с адресом и причиной каждой позиции. Новый кандидат, найденный при вырезании, идёт в раздел «Находки вне рамки» результата, а не под нож. В ЗАМЫСЛЕ такого наряда строка «чем опровергается» называет сверку вырезанного со списком по diff.

### Проверка перед выдачей

Проходится целиком перед печатью каждого блока НАРЯД:

1. DoD не уже ЗАДАЧИ.
2. ТРЕБУЕТ не содержит метода.
3. Отмена и новое поручение по отменённому объекту не идут одним сообщением.
4. Если назначена очерёдность нарядов — назначен и способ её проконтролировать.
5. МАНДАТ НА ОТКАЗ заполнен осознанно, не скопирован из прошлого наряда.
6. ПАСПОРТ посчитан формулой, потолок соблюдён (N ≤ 5, правимых путей ≤ 1 — с исключением об атомарной записи), либо наряд отдан Прорабу на разбиение; после каждого долива задач — пересчитан.
7. Проверка релевантности пройдена: наряд явно продвигает Главную цель или закрывает объектный БЛОКЕР со ссылкой на строку реестра; кандидаты и мелочь уже ушли в ЗАХВАЧЕНО.
8. ЗАМЫСЕЛ заполнен: механизм назван, опровергающий факт объектен, слабое звено названо и не несущее.
9. МОДЕЛЬ выведена номером вопроса.
10. ОСНОВАНИЕ ГДЕ содержит ответы «нет» с фактами, а не только номер.
11. Перед блоком НАРЯД напечатана строка `МАРШРУТ: В`.
12. Номер Н-ДД.ММ-NN поискан по репозиторию и свободен.
13. Условие «подстроки нет» в DoD — с адресом (строка, таблица, абзац).
14. Каждое число и каждая текстовая формулировка условия несут, откуда взяты, и что делать при расхождении с объектом; Руководитель назвал потребителя условия — кто и чем его проверит.
15. У каждого шага многошагового наряда есть ветка «если не выполнено, то …».
16. Исполняемый протокол, по которому строится наряд, прочитан целиком, включая поздние фазы.
17. Задание проверяющему несёт вопрос и объект («какую роль воркфлоу X играет для таблицы Y — читатель или писатель; доказательство — узел и операция»), а не ответ («подтвердить, что X — читатель»). Что ожидает, Руководитель записывает у себя до выдачи как прогноз и сверяет с ним результат.
18. Если ЗАДАЧА стоит на утверждении документа о коде («сделать как в эталонном загрузчике», «воркфлоу пишет только в лист A»): посылка названа в ЗАДАЧЕ прямо как посылка; МАНДАТ НА ОТКАЗ включает «посылка»; первый шаг наряда — сверка посылки с живым объектом (`get_workflow_details`, код узла, содержимое листа) с ответом при расхождении `<ID> ОТКАЗ ПО МАНДАТУ: посылка — <что в объекте иначе>`. Руководитель код не читает, поэтому сверка либо входит в наряд первым шагом, либо исполняется раньше отдельным шагом с маршрутом.
19. Перед ЗАДАЧЕЙ ревизии (аудита) объекта прочитано оглавление журналов хозяев объекта (проектов, которые его ведут).
20. Наряд на чтение, аудит или диагностику называет канал находок вне рамки: раздел «Находки вне рамки» в результате по полю РЕЗУЛЬТАТ В. Находку регистрирует Руководитель при приёмке — по адресу из Skill `second-brain-engineer`, разделы «Р14. Запреты» (запрет 4) и «Р16. Работа вне Claude Project и регистрация обязательств», — либо прямо пишет, что регистрировать нечего.
21. Наряд с DoD «промпт переключён» — есть файл со старым текстом мастер-промпта.
22. Наряды или чаты, работающие одновременно, — в РАМКЕ каждого назван свой набор путей репозитория, наборы не пересекаются.

### Прораб

- Дочерние наряды нумерует от родительского ID: Н-ДД.ММ-NN.1, .2, .3.
- Проверка релевантности применяется к дроблению так же, как к выдаче.

| Поле родителя | Что Прораб делает с ним в дочернем наряде |
|---|---|
| ТРЕБУЕТ, ГДЕ, МАНДАТ НА ОТКАЗ | Наследует. Меняет только сузив, никогда не расширив. |
| ГДЕ, если среда дочернего наряда другая | Заново проходит вопросы «Поле ГДЕ» и печатает новое ОСНОВАНИЕ ГДЕ. |
| ЗАМЫСЕЛ, строка «почему сработает» | Наследует без изменений: дробление не создаёт нового замысла. |
| ЗАМЫСЕЛ, строки «чем опровергается» и «слабое звено» | Заполняет для каждого дочернего наряда заново. |

- Наряд с превышением потолка (N > 5 или правимых путей > 1, кроме атомарной записи) Прораб обязан разбить на дочерние в пределах потолка и вести их внутри одной сессии последовательно; между дочерними сверяет журнал хода каждого с его паспортом (контрольная точка). Паспорт пересчитывает от факта до первой деструктивной правки.
- Отдаёт один сводный результат под родительским ID: `<ID> СВОДКА. Закрыты: .1 .2 .3`.

### Приём наряда

Исполнитель читает этот раздел перед приёмом. Работа не начинается, если верно хотя бы одно:

- (а) пусто одно из полей DoD, ИСПОЛНИТЕЛЬ, МОДЕЛЬ, ГДЕ, ТРЕБУЕТ или МАНДАТ НА ОТКАЗ; либо МОДЕЛЬ без номера вопроса; либо ОСНОВАНИЕ ГДЕ голым номером, без ответов «нет»; либо в ТРЕБУЕТ голое слово «git»;
- (б) в текущей среде нет инструмента из ТРЕБУЕТ. Для «git push» наличие проверяется командой `git push --dry-run` в этой самой сессии, не именем среды; отказ прокси — это отсутствие инструмента;
- (в) ОСНОВАНИЕ ГДЕ пусто или не соответствует разделу «Поле ГДЕ» (в том числе ГДЕ назначено по имени среды в расчёте на открытый push);
- (г) нет ID, либо ID не соответствует формату `Н-ДД.ММ-NN`;
- (д) наряд содержит деструктивные правки, а ПАСПОРТ пуст, стоит прочерком или превышает потолок (в том числе после пересчёта от факта), или исключение об атомарной записи взято без названного правила;
- (е) наряд содержит деструктивные правки, а ЗАМЫСЕЛ пуст, стоит прочерком, обоснован обычаем («обычно так», «best practice», «надёжнее»), либо строка «чем опровергается» не называет наблюдаемого объекта. Это отказ по форме поля, не спор о содержании.

Ответ — одной строкой, до всякой работы:

```
<ID> НЕ ПРИНЯТ. Пустые поля: <перечень>.
<ID> НЕ ПРИНЯТ. В этой среде нет: <инструмент>.
<ID> НЕ ПРИНЯТ. ОСНОВАНИЕ ГДЕ не сходится: <что не так>.
НЕ ПРИНЯТ. Отсутствует ID.
<ID> НЕ ПРИНЯТ. ПАСПОРТ: <что не так>.
<ID> НЕ ПРИНЯТ. ЗАМЫСЕЛ: <что не так>.
```

Подтверждение приёма — первой строкой, до начала работы, пересказ своими словами:

```
<ID> Принял. DoD своими словами: <пересказ>. Вне рамки: <что не делаю>.
```

Закрытие — ID артефакта или сам результат: `<ID> ЗАКРЫТ. <ID артефакта>`.

Находки вне рамки — замеченное по ходу работы, но РАМКОЙ не охваченное: кладутся в раздел «Находки вне рамки» того же результата, по одной строке на находку, с адресом объекта; нет находок — раздел содержит слова «находок вне рамки нет».

Шаг без данных (нужного поля нет в ответе, у инструмента нет такой операции, объект недоступен в этой среде) — в отчёте словами:

```
шаг <номер> не выполнен: данных нет — <инструмент>, в ответе нет <чего>
```

Исполнитель вправе назвать другой наблюдаемый канал (например, Андрей сверяет в интерфейсе по выданному списку узлов); переназначить или снять шаг решает Руководитель.

### Журнал хода и STOP-LOSS

Журнал хода обязателен при трёх и более деструктивных правках. После каждой правки, до перехода к следующей, — одна строка в ответе:

```
[k/N] <файл> <раздел/корень> | тактов: +t (норма +3) | всего: m/B | exec: <ID записи>, <ID read-back>
```

- k — номер правки: номер предыдущей строки плюс 1;
- N и B — из ПАСПОРТА (после пересчёта от факта — из пересчёта);
- t — фактические такты этой правки; норма 3: чтение до правки, запись, read-back; каждый повтор из-за промаха якоря или пустого чтения — плюс 1, с причиной в строке;
- m — m предыдущей строки плюс t.

STOP-LOSS проверяется в момент записи строки по двум числам из неё: если m ≥ B/2 при k < N/2 — следующей строкой

```
STOP-LOSS: k из N, m из B, <причина перерасхода>
```

и работа останавливается; продолжение — только по слову владельца наряда; правка, начатая до стопа, довершается. Текущее состояние работы читается по последней строке журнала.

### Приёмка

- Приёмка — по объекту: закрывающий читает объект сам. Общий стандарт верификации — Skill `second-brain-engineer`, раздел «Р15. Провенанс и верификация — единый стандарт».
- Правка построчного списка (INDEX.md и подобных) — по diff строк с предыдущим прочитанным текстом.
- Отдельный наряд на приёмку — только когда проверяется суждение Исполнителя; два-три числа принимаются без наряда.

### Пересмотр Skill

Читается на харвесте (шаг 4 `meta/PROTOCOL_harvest.md`) и при прямом слове Андрея о пересмотре этого Skill. Харвест задаёт вопросы Андрею по одному, короткой строкой; ответ Андрея по памяти и по чатам нарядов считается данными. Что делать с ответами «да» и «не помню» — шаг 4 `meta/PROTOCOL_harvest.md`.

1. Поле ТРЕБУЕТ. «Со времени прошлого харвеста был ли хоть один наряд отбит на приёме потому, что в среде не оказалось инструмента?» Нет — проверить оба объяснения, не выбирая заранее: среды стали универсальны и поле ТРЕБУЕТ лишнее, либо Исполнители не отказывают.
2. Мандат на отказ. «Был ли хоть один отказ по мандату — Исполнитель остановился и объявил метод, посылку, цифры или вход негодными?» Нет при нескольких нарядах с широким мандатом — поле не работает: либо не читается, либо выдаётся формально.
3. Поле ЗАМЫСЕЛ. «Изменился ли хоть один наряд по итогу заполнения ЗАМЫСЛА, ушла ли хоть одна задача на ревизию denken, отбит ли хоть один наряд по пустому ЗАМЫСЛУ?» Нет на все три — поле заполняется формально, задним числом. Признак того же: строка «слабое звено» из наряда в наряд называет одно и то же общее место (сроки, объём, «может не хватить контекста»).
4. ОСНОВАНИЕ ГДЕ. «Указывало ли ОСНОВАНИЕ ГДЕ почти всегда на вопрос 1 (контекст проекта), даже там, где контекст проекта наряду не был нужен?» Да — пересматривается вопрос 1, а не дерево целиком; признак вопроса 1 — контекст, а не диалог.
5. git push. «Был ли наряд с ТРЕБУЕТ "git push" отбит дважды подряд, причём добавить репозиторий в сессию не удалось?» Да — посылка «push открывается добавлением репозитория в любой сессии» перестала быть верной; пересматривается выбор ГДЕ «по контексту, не по инструментам», а не отдельная среда.
6. Дрейф. «Бывало ли, что серия нарядов шла по мелочам вместо БЛОКЕРА, а пометки о дрейфе не появлялось?» Да — проверка релевантности требует более жёсткого места, например обязательного поля в блоке НАРЯД. «Появлялись ли БЛОКЕРы, которые оказались мелочью?» Да — вопрос к тому, кто ставит метку БЛОКЕР в INDEX, `labs/sys/INDEX.md` и STATE.md.
7. Паспорт. «Превышал ли наряд прогноз паспорта больше чем вдвое без строки STOP-LOSS в журнале хода?» Да — искать, какой слой Skill фактически действовал в той сессии: Customize, зеркало `skills/` в репозитории или снимок в сессии (дрейф слоёв).
8. Маршрут Б по стоимости. «Был ли шаг с маршрутом Б по вопросу 5, у которого по журналу хода фактические вызовы m превысили накладные наряда O больше чем вдвое (m > 2·O)?» Да — прокси «вызовы» не отражает цену шага, и вопрос 5 маршрута шага переводится на байты по бюджетам чтения Skill `second-brain-git` (раздел «Превышение бюджета чтения»).

## Адреса и ловушки

- Инструмент чтения возвращает пустоту без ошибки, неотличимую от «объекта нет» — проверяй признаком, а не продолжай поверх.
- Ответ инструмента молча не содержит нужного поля, и поведение полей меняется со временем (поле `credentials` в `get_workflow_details` то не приходило, то приходит) — проверяй по свежему ответу.

## Куда писать результат

- Наряд — сообщение в чате (или документ — один носитель), не файл.
- Результат наряда — по полю РЕЗУЛЬТАТ В: «в ответ» или ID файла; результат, который станет входом следующего наряда, — только в файл.
- Находки вне рамки — разделом «Находки вне рамки» того же результата; регистрирует Руководитель при приёмке (Skill `second-brain-engineer`, разделы «Р14. Запреты» и «Р16. Работа вне Claude Project и регистрация обязательств»).
- Журнал хода и STOP-LOSS — строками в ответе Исполнителя.
- Пересчёт паспорта — печатается в сессии до первой деструктивной правки.
