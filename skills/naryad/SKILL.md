# naryad

Наряд — один самодостаточный текст, которым чат передаёт готовую работу в Claude Code на автономное исполнение. Работа идёт так: разработка нового — в чате мелкими шагами вместе с Андреем; когда план готов и проверен, чат сам отмечает точку перехода и выдаёт наряд; Андрей один раз переносит его в Claude Code; там диспетчер ведёт работу до итога по Skill `avtopilot`; итог возвращается через канон, и чат принимает его по объекту. Андрей не носит ответы обратно и не передаёт сообщения между ролями.

Этот Skill — сторона чата: когда выдавать, как составить, как принять результат. Сторона исполнения — Skill `avtopilot`. Граница между ними — среда.

## Стоп-правила

### Роли и шина
- Андрей переносит наряд из чата в Claude Code один раз; ответы, отчёты и вопросы между ролями он не носит. Возврат результата — через канон.
- Чат, выдавший наряд, не пишет в канон проекта, пока в Claude Code идёт исполнение этого наряда: писатель канона в это время один — диспетчер.
- Свою эстафету в STATE.md чат после приёмки ставит вместо эстафеты диспетчера, а не рядом с ней.
- Исполнитель внутри Claude Code нарядов не выдаёт; раздачу внутри наряда ведёт диспетчер по Skill `avtopilot`.

### Точка перехода
- Наряд не выдавать, пока не выполнены все четыре признака раздела «Точка перехода».
- Разработку нового (замысел ещё меняется от ответа к ответу) в наряд не превращать: она идёт в чате мелкими шагами.
- Работу из одного-двух дешёвых шагов в наряд не превращать: чат делает её сам со строкой `МАРШРУТ: Б`.

### Форма наряда
- Наряд печатается целиком, одним текстом; поле без содержания — прочерк, строку поля не пропускать.
- Наряд для Claude Code обязан быть самодостаточным: сессия в Code не видит разговора чата.
- DoD и проверочный объект пакета не писать состоянием («разобраться», «улучшить», «проверить») — только объектом: число, отпечаток выдачи, сумма, файл, строка.
- Окно дат не писать словами («за октябрь») — только цифрами от и до.
- В наряд не включать действие, которое запрещает Skill или правило проекта; такое действие идёт в поле РУЧНОЕ или снимается до выдачи.
- Механику инструментов проекта в наряд не переписывать: она вносится в `PLAN.md` проекта, наряд называет место.
- Сообщение о наряде без ID не выдавать, не принимать и закрытием не засчитывать.
- В ID больше одной точки не ставить; префикс проекта не вводить.
- Отмену и новое поручение по отменённому объекту не отправлять одним сообщением.
- Файлов на Drive под наряд не создавать и в INDEX не писать: наряд — текст, его адрес в каноне — запись журнала проекта о выдаче.

### Поле МОДЕЛЬ
- Имя модели в поле МОДЕЛЬ не печатать — класс и номер сработавшего вопроса.
- Имена моделей в этом Skill не писать.
- Ни один вопрос дерева МОДЕЛЬ не сработал — наряд не выдавать: переписывается ЗАДАЧА.

### Мандат на отказ
- Наряд на проверку, аудит, верификацию не выдавать с мандатом уже, чем «процедура, посылка, цифры, вход».
- Отказ по мандату без объекта (строка файла, номер исполнения, замер) не оформлять.
- Значение «процедура» не применять к бюджетам чтения и размерам файлов репозитория.
- МАНДАТ НА ОТКАЗ не копировать из прошлого наряда.

### Деструктивные правки: паспорт и замысел
- Наряд с деструктивными правками (любое изменение объекта) без ПАСПОРТА и ЗАМЫСЛА не выдавать и не принимать.
- Записанный пакет разрешения (Skill `avtopilot`, «Ворота 3. Контракт запуска»; Skill `second-brain-engineer`, «Р10. Воркфлоу n8n — полномочия») не заменяет ПАСПОРТ и ЗАМЫСЕЛ.
- Паспорт с числами «на глаз», без следа формулы, не печатать.
- Пакет с числом правок больше пяти или с правкой больше одного пути не выдавать одним пакетом — делить на пакеты (исключение — атомарная запись по разделу «Паспорт стоимости»).
- Исключение об атомарной записи не брать без названного правила, которое её требует.
- Записи результата (журнал, файл контракта, позиция очереди) из числа правок не выкидывать.
- ЗАМЫСЕЛ не обосновывать обычаем («обычно так», «best practice», «так надёжнее»); строку «слабое звено» не оставлять пустой и не писать «слабых мест нет».
- Наряд с несущим слабым звеном не выдавать — и не выдавать, пометив звено в поле.
- Кто разметил, что вырезать, тот в том же заходе не режет; кто режет, тот список не пополняет.

### Выдача (Руководитель)
- Наряд не выдавать за лёгкость исполнения вместо важности; наряд на находку «кандидат в БЛОКЕРы» и на мелочь не печатать.
- Находку без объекта в реестре БЛОКЕРом не объявлять; при сомнении — ветка «кандидат».
- На `core/R-05.md` как на место, где стоит объект-БЛОКЕР, не ссылаться: там нет строк-задач.
- Условие «подстроки нет» в DoD не писать поиском по всему файлу — только с адресом (строка, таблица, абзац).
- Пакет из нескольких шагов не выпускать, пока у каждого шага нет ветки «если не выполнено, то …».
- Решение по исполняемому протоколу не предлагать, не прочитав протокол целиком, включая поздние фазы.
- В задание проверяющему (аудит, приёмка, сверка) не вписывать ожидаемый вердикт и ожидаемую роль объекта.
- Утверждение документа о коде (паспорт воркфлоу, INDEX, журнал, лист настроек, прошлый наряд) за факт не брать — посылка.
- Наряд на аудит или приёмку, DoD которого выполним одним чтением документов без чтения живого объекта, не выдавать.
- Паспорт воркфлоу доказательством для правки, аудита и приёмки не считать — только первым чтением.
- Наряд с DoD «промпт переключён» не выдавать без файла со старым текстом мастер-промпта.
- Два наряда, исполняемые одновременно, не выдавать без непересекающихся наборов путей репозитория и объектов в РАМКЕ каждого.

### Маршрут шага
- Шаг собственного плана без строки `МАРШРУТ:` не начинать.
- «Сложность», «важность», «ощущение контекста» входами вопросов маршрута не считать.
- Действие, в выдаче наряда на которое отказано или которое отклонил Андрей, маршрутом Б не исполнять — ни целиком, ни первым шагом под другим названием.

### Приёмка
- Не принимать по отчёту диспетчера или по слову «сделал»; закрывающий читает объект сам.
- Самоотчёт исполнителя о себе (адрес своей сессии, число созданных объектов) доказательством не считать: в отчёте конвейера было 15 функций при 14 в базе.
- Статус «выполнено» у запуска облачной задачи признаком конца работы не считать — только объект в каноне.
- Правку построчного списка (INDEX.md и подобных) не принимать по размеру — по diff строк.

### Пересмотр этого Skill
- Условие пересмотра не записывать счётчиком — только вопросом харвеста.

## Как делать

### Роли

| Роль | Где | Что делает |
|---|---|---|
| Андрей | чат и Claude Code | решения, ключи, ручные действия из поля РУЧНОЕ; один раз переносит наряд в Claude Code |
| Руководитель | чат Claude Project или сессия Летописи | разрабатывает с Андреем, отмечает точку перехода, пишет наряд, принимает итог по объекту |
| Диспетчер | Claude Code | исполняет наряд по Skill `avtopilot`: раздаёт пакеты помощникам, единственный писатель канона во время исполнения |
| Помощник | внутри сессии диспетчера (или облачный исполнитель) | один пакет или одна проверка |
| Приёмщик | отдельный помощник, работу не делавший | опровергает утверждения о результате по объекту |

Роли распределяют ответственность за шаг, а не правоту: прав тот, кто читал источник (Skill `second-brain-engineer`, раздел «Р15. Провенанс и верификация — единый стандарт»).

### Маршрут шага

Каждый шаг собственного плана Руководителя получает маршрут; перед первым действием печатается строка:

```
МАРШРУТ: <А|Б|В> — <№ вопроса>: <наблюдённый факт>
```

Входы — только наблюдаемое: инструмент в среде, вход в контексте, происхождение входа, число вызовов. Вопросы по порядку, первое «да» даёт маршрут:

1. У шага нет объекта готовности, либо поле наряда пришлось бы заполнить по памяти, а не по прочитанному в этой сессии? ДА → А (продолжать разработку; первое действие — прочитать недостающее).
2. Шаг — часть работы, прошедшей все признаки точки перехода? ДА → В (наряд в Claude Code).
3. Шагу нужен инструмент или право, которых нет в этой среде (правка опубликованного или общего объекта, отклонённая защитой чата; копия репозитория с правом записи; скрипт по большим данным)? ДА → В.
4. Иначе → Б: Руководитель делает шаг сам.

Маршрут Б не снимает паспорт, ограничители и приёмку по объекту. Признак подмены: объект и операция шага те же, что в отклонённом наряде, а название другое.

### Точка перехода

Руководитель сам отслеживает момент и говорит Андрею «переходим в Code», когда выполнены все четыре признака:

1. План готов и не меняется от ответа к ответу; для нового решения (новая архитектура, новый воркфлоу, необратимая операция) пройдена ревизия Skill `denken`.
2. У каждого пакета есть проверочный объект: число, отпечаток выдачи функций до и после, сумма против отчёта площадки, файл. Пакет, где пишется текст для человека, получает второй круг приёмщика.
3. Всё, что может сделать только Андрей (согласие Google при первом запуске кода в книге, ключ доступа в редакторе n8n, решение о деньгах), собрано одним списком в поле РУЧНОЕ до запуска.
4. Пакетов не меньше трёх: иначе перенос наряда дороже, чем работа в чате.

Примеры работы для наряда: переделка учёта юнит-экономики по готовому плану; создание контента для артикулов по готовому шаблону.

### Форма наряда

```
<ID> НАРЯД
ЗАДАЧА: (цель одной-двумя фразами; где лежит план — адрес в каноне)
DoD: (признак готовности всего наряда — объект)
ПАКЕТЫ:
  К1 <название> — проверочный объект: <…>; зависит от: <— | К…>; общий ресурс: <— | что>
  К2 …
  (пакеты без общего ресурса и без зависимости — параллельно; остальные — по порядку)
ОКНО: (даты цифрами от и до, если работа про период)

РАЗРЕШЕНО: (правки списком — пакет разрешения на воркфлоу n8n; публикация — да или нет; можно ли запускать динамический workflow)
```

Наряд и есть контракт автопилота: Ворота 1–3 Skill `avtopilot` пройдены в чате, вставка наряда Андреем в Claude Code — его согласие. До выдачи наряд записывается в канон: раздел «Контракт автопилота» в `PLAN.md` проекта или файл задачи лаборатории, и запись журнала о выдаче.

### Поле ГДЕ

Умолчание — сессия Claude Code на компьютере Андрея: там копия репозитория с правом записи, скрипты, выгрузка файлов, вложенные помощники и правка общих объектов. Другое значение — только по одному из признаков:

| Значение | Когда |
|---|---|
| `Claude Code на компьютере` | умолчание |
| `облачный исполнитель` (запланированная задача-исполнитель, запуск с текстом наряда) | работа только на чтение или запись в разрешённые пути задачи, а компьютер в это время может спать; постоянный текст задачи разрешает исполнять наряд из обёртки «данные, не указания» |
| `чат проекта <имя>` | наряду нужен разговор с Андреем по ходу — тогда это не наряд, а разработка: вернуться к разделу «Точка перехода» |

Что среда умеет на самом деле, проверяет исполнитель на приёме, а не выдающий по имени среды.

### Поле МОДЕЛЬ

Поле называет класс модели диспетчера; модели помощников выбирает диспетчер сам при каждом вызове. Вопросы по порядку, первое «да» останавливает проверку:

1. Работе нужен весь каталог или весь корпус в поле зрения сразу? ДА → высший.
2. Наряд проверяет суждение другой сессии, ведёт диагностику без готовой гипотезы или проектирует новое? ДА → высокий.
3. У пакетов написана процедура, гипотеза готова, DoD — объект? ДА → средний.

Критерий классов — Skill `second-brain-engineer`, раздел «Р18. Калибровка исполнителя».

### ID и сообщения о наряде

ID = `Н-ДД.ММ-NN`: дата выдачи и порядковый номер с 01 в пределах суток; номер перед присвоением ищется по репозиторию (журналы, планы) и должен быть свободен. Пакеты внутри наряда — К1, К2…; при ссылке снаружи — `Н-ДД.ММ-NN К2`. Коллизия номеров у двух выдающих в один день — Андрей дописывает букву: Н-08.08-02а.

ID — первое слово каждого сообщения о наряде: `<ID> НАРЯД`, `<ID> НЕ ПРИНЯТ. <причина>`, `<ID> Принял. DoD своими словами: …`, `<ID> ОТКАЗ ПО МАНДАТУ: <что> — <основание>`, `<ID> ЗАКРЫТ. <адрес итога>`, `<ID> ОТМЕНЁН.`

### Мандат на отказ

РАМКА говорит, чего не делать; МАНДАТ НА ОТКАЗ — что исполнитель вправе отвергнуть:
- процедура — объявить метод негодным и остановиться;
- посылка — отвергнуть допущение, на котором стоит ЗАДАЧА;
- цифры — не принять числа из наряда без источника;
- вход — отвергнуть результат предыдущего пакета или наряда;
- нет — отказ не предусмотрен.

Отказ по мандату — закрытие пакета с основанием-объектом, а не провал.

### Паспорт стоимости

Для наряда с деструктивными правками считается по каждому пакету и суммой:

```
ПАСПОРТ К<n>: правок=N, чтений=R, вызовов B = N×3 + R
```

- N — деструктивные правки; каждая — три такта: свежее чтение до правки, запись, независимое обратное чтение.
- В N входят: каждая запись результата (журнал, отчёт, STATE.md); каждый объект, который пишется отдельной записью (каждый лист, функция, книга показа); каждый круг исправлений документа с текстом для человека — правка по находке приёмщика и её обратное чтение (закладывается хотя бы один круг). Без этих слагаемых паспорт конвейера Н-09.11-07 дал 19 шагов записи при фактических 31.
- Потолок пакета: N ≤ 5 и правимых путей ≤ 1; больше — пакет делится. Исключение — атомарная запись нескольких путей одним вызовом, если наряд называет требующее её правило (Skill `second-brain-git`: ротация журнала, задача лаборатории со строкой INDEX.md, пара «файл и список, в котором он назван»).
- Диспетчер пересчитывает паспорт от факта до первой деструктивной правки (Skill `avtopilot`, «Ворота 4. Исполнение — Андрея нет»).

### Замысел

```
ЗАМЫСЕЛ:
почему сработает: если выполнен DoD, то <наблюдаемый результат>, потому что <механизм>
чем опровергается: <наблюдаемый факт: строка файла, номер исполнения, замер, число>
слабое звено: <самое необоснованное место наряда>
```

Слабое звено несущее — ревизия Skill `denken`, наряд печатается по её результату. Наряд, который удаляет или сокращает текст, исполняет готовый список того, что вырезать (файл с адресом и причиной каждой позиции); новый кандидат при вырезании идёт в «Находки вне рамки», а не под нож.

### Проверка перед выдачей

1. Все четыре признака точки перехода выполнены.
2. Наряд самодостаточен: сессия, не видевшая разговора, исполнит его без вопросов; окно — цифрами; механика — адресом в `PLAN.md`.
3. Каждый пакет имеет проверочный объект и пометку зависимости или общего ресурса.
4. В наряде нет действия, запрещённого Skill или правилом проекта; такие действия — в РУЧНОЕ.
5. РУЧНОЕ — полный список; всё, что может только Андрей, названо.
6. РАЗРЕШЕНО перечисляет правки; публикация и динамический workflow названы явно (да или нет).
7. ПАСПОРТ посчитан формулой со всеми слагаемыми; потолок пакета соблюдён.
8. ЗАМЫСЕЛ заполнен, слабое звено не несущее.
9. Наряд продвигает Главную цель или закрывает объектный БЛОКЕР со ссылкой на строку реестра.
10. Задание проверяющему несёт вопрос и объект, а не ответ; ожидаемое Руководитель записал у себя как прогноз.
11. Если ЗАДАЧА стоит на утверждении документа о коде — оно названо посылкой, МАНДАТ включает «посылка», первый шаг — сверка с живым объектом.
12. Перед ЗАДАЧЕЙ ревизии объекта прочитано оглавление журналов его хозяев.
13. Наряд на чтение, аудит или диагностику называет раздел «Находки вне рамки» в результате.
14. Номер Н-ДД.ММ-NN поискан по репозиторию и свободен; наряд записан в канон.

### Приём наряда

Сессия Claude Code перед работой:
1. Пробует среду: `git push --dry-run` (Skill `second-brain-git`, «Push: проверка и открытие»); инструменты n8n; командная строка; другие инструменты, которых требует РАЗРЕШЕНО и МЕХАНИКА. Чего нет — `<ID> НЕ ПРИНЯТ. В этой среде нет: <что>`. Наряд, рассчитывающий на push по имени среды, без пробы не принимается.
2. Проверяет форму: пустое поле DoD, ПАКЕТЫ, РАМКА, РАЗРЕШЕНО или МАНДАТ; пакет без проверочного объекта; деструктивные правки без ПАСПОРТА или ЗАМЫСЛА; ЗАМЫСЕЛ по обычаю; нет ID — `<ID> НЕ ПРИНЯТ. <что не так>`.
3. Подтверждает: `<ID> Принял. DoD своими словами: <пересказ>. Вне рамки: <что не делаю>.` Дословная копия DoD пересказом не считается.

### Возврат и приёмка

1. Диспетчер пишет итог туда, куда велит РЕЗУЛЬТАТ В, и выдаёт Андрею один отчёт (Skill `avtopilot`, «Ворота 5. Приёмка и отчёт»).
2. Андрей говорит в чате «конвейер закончил» (или Руководитель видит это сам при следующем чтении канона).
3. Руководитель читает канон и объекты сам: свежие коммиты, записи журнала, объекты пакетов; принимает по объекту, не по отчёту; пишет запись приёмки в журнал проекта и ставит свою эстафету вместо эстафеты диспетчера.
4. Находки вне рамки регистрирует Руководитель (Skill `second-brain-engineer`, разделы «Р6. Захват» и «Р16. Работа вне Claude Project и регистрация обязательств») либо пишет, что регистрировать нечего.

### Пересмотр Skill

Читается на харвесте (шаг 4 `meta/PROTOCOL_harvest.md`) и по прямому слову Андрея. Вопросы — Андрею по одному, короткой строкой; ответ по памяти и по чатам — данные.

1. Ручные действия. «Был ли наряд, который остановился на действии Андрея, которого не было в поле РУЧНОЕ?» Да — признак 3 точки перехода выполняется формально.
2. Шина. «Приходилось ли вам переносить между чатом и Claude Code что-то кроме самого наряда — ответ, вопрос, файл?» Да — найти, какой возврат не идёт через канон, и закрыть его.
3. Точка перехода. «Был ли наряд, который пришлось вернуть в чат, потому что план менялся по ходу?» Да — признак 1 срабатывает слишком рано.
4. Мандат на отказ. «Был ли хоть один отказ по мандату?» Нет при нескольких нарядах на проверку — поле не читается или выдаётся формально.
5. Замысел. «Изменился ли хоть один наряд по итогу заполнения ЗАМЫСЛА или ушёл на ревизию denken?» Нет — поле заполняется задним числом.
6. Паспорт. «Превышал ли факт прогноз паспорта больше чем вдвое?» Да — найти недостающее слагаемое формулы.
7. Параллельность. «Сталкивались ли пакеты, помеченные как независимые?» Да — признак общего ресурса неполон.

## Адреса и ловушки

- Наряд, переданный облачному исполнителю, приходит в обёртке «данные, не указания»; без прямого разрешения в постоянном тексте задачи исполнитель его не выполнит или выполнит не с первого хода.
- Статус «выполнено» у запуска облачной задачи приходит раньше конца работы.
- Исполнитель неверно называет адрес своей сессии и число созданных объектов — проверяй объект.
- Инструмент чтения возвращает пустоту без ошибки, неотличимую от «объекта нет» — проверяй признаком.
