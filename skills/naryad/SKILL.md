## Область применения

Применяется к разработке новых идей и сложных задач в Claude-Project и в Летописи — проекте в репозитории без Claude Project, мастер-промпт которого ведёт работу по нарядам: чтение файлов и воркфлоу, извлечение из технической документации, написание кода новых воркфлоу, проверка старого кода.

Не применяется к рядовым вопросам и единичным операциям; применяется в Claude-Projects и в Летописях — проектах в repo без Claude Project, мастер-промпт которых ведёт работу по нарядам. Основание: решение Андрея 2026-10-11, позиция AI-5 Очереди `registry/maintenance-queue.md`.

Причина существования: класс модели, достаточный для проектирования, разорителен для чтения и записи. Роли разделяют дорогое мышление и дешёвое исполнение.

Где формат окупается: диагностика, аудит, деструктивные и боевые операции — там, где цена ошибки высока и независимая проверка реально ловит дефекты. Признак такой работы: проверка может поймать ложную тревогу, сбор ключей доступа вслепую или цифру без источника. Основание: 3 случая, последний 2026-08-05 — отчёт синтеза, правило NAR.окупаемость.

Где не окупается: быстрая тесно связанная итерация, где Андрей и так в диалоге на каждом шаге. Там наряд — накладной расход.

## 2. Роли

Руководитель — проектирует. Формирует замысел, разбивает на наряды, оценивает результаты. Не читает файлы, не пишет, не вызывает инструменты — кроме шага, перед которым напечатана строка МАРШРУТ: Б (§3.9, references/issuer.md): дешёвый шаг он исполняет сам, без наряда.

Прораб — организует. Получил наряд, дробит его на наряды Исполнителям ВНУТРИ полученного DoD (definition of done — проверяемый признак готовности, поле наряда). Собирает отчёты, отдаёт один результат.

Исполнитель — делает. Один наряд, один результат, один артефакт.

Андрей — шина. Все наряды и отчёты идут через него. Роли между собой не сообщаются.

Исключение — автономный режим (Skill `avtopilot`, «Ворота 4. Исполнение — Андрея нет»): там шина — сессия-диспетчер, а Андрей один раз согласует контракт запуска; вне автономного режима правило «Андрей — шина» действует без изменений. Как работает диспетчер — только в Skill `avtopilot`, здесь не повторяется. Основание: решение Андрея 2026-10-13, чат SYS, после ревизии `denken` уровня 2; 3 случая автономного режима, последний 2026-10-17 — отчёт синтеза, правило NAR.роли.автопилот.

## 3. Формат наряда

Наряд печатается ВСЕГДА целиком. Незаполненное поле — прочерк, не пропуск строки. Почему: отсутствие поля невидимо, прочерк виден.

Наряд публикуется ОДНИМ носителем целиком — либо блоком НАРЯД в чате, либо документом, но не тем и другим сразу как половинками одного целого. Почему: второй носитель рядом с блоком доезжает до Исполнителя частями. Признак: повторяющийся отказ приёма по одному и тому же основанию. Основание: 1 случай, дата последнего случая в источнике не названа — отчёт синтеза, правило NAR.формат.носитель.

```
<ID> НАРЯД
ЗАДАЧА:
DoD: (проверяемо: объект, а не состояние)
РАМКА: (что НЕ делать / где остановиться)
МАНДАТ НА ОТКАЗ: (что Исполнитель вправе отвергнуть — см. §3.4)
ТРЕБУЕТ: (инструменты и доступы, без которых наряд не выполнить)
ПАСПОРТ: (стоимость исполнения по формуле §3.7; обязателен при деструктивных правках, для read-only нарядов — прочерк)
ЗАМЫСЕЛ: (три строки по §3.8; обязателен при деструктивных правках, для read-only нарядов — прочерк)
ИСПОЛНИТЕЛЬ: Прораб | Исполнитель
МОДЕЛЬ: средний | высокий | высший — номер сработавшего вопроса §3.1а:
ГДЕ: чат проекта <имя> | сессия Летописи <имя> | новый чат вне проекта
ОСНОВАНИЕ ГДЕ: номер сработавшего вопроса §3.1
РЕЗУЛЬТАТ В: <ID файла или «в ответ»> — см. §3.5
```

DoD пишется в терминах объекта: «ID созданного паспорта», «occurrencesChanged=1 + подтверждающее чтение», «список из N строк». Не «разобраться», не «улучшить», не «проверить».

Поле ТРЕБУЕТ перечисляет потребность, а не оснастку: чтение Drive, запись Drive, n8n, shell (командная строка), git, интернет, работа с загруженными файлами. Почему: поле про задачу — Руководитель способен его заполнить, не зная, что подключено к какой среде.

Слово «git» в поле ТРЕБУЕТ голым не пишется. Пишется либо «git на чтение» — клон, diff, история, git hash-object, — либо «git push» — доставка в ветку main по маршруту `second-brain-git` 9.4(б) (references/delivery.md). Почему: это две разные потребности с разной проверкой — чтение даёт клон в любой сессии, а отправку Исполнитель проверяет на приёме пробой `git push --dry-run` (§3.1, §6(б)). Наряд с голым «git» на приёме отбивается по §6(а) как наряд с незаполненным полем.

Действие в интерфейсе n8n или в браузере Андрея — клик в редакторе, вставка текста; привязка ключа — только когда сессия не может сделать её сама операцией `setNodeCredential` — пишется в ТРЕБУЕТ отдельной строкой «интерфейс n8n» или «браузер Андрея» и выполняется только по явному «да» Андрея на эту строку. «Не знаю», молчание и отсутствие возражений разрешением не являются. Почему: обход границы ролей неотличим от обхода канала записи до первого случая, когда рука в интерфейсе поменяет не то. Основание: решение Андрея 2026-09-06, запись Р-48 журнала `projects/git-migration/LOG_ARCHIVE.md`.

### 3.1 Выбор поля ГДЕ

Умолчания нет. Среда выбирается ответом на вопросы по порядку, первое «да» останавливает проверку. Список подключённых инструментов здесь не приводится сознательно: он устареет раньше, чем понадобится.

Закон пункта: ГДЕ выбирается по тому, какой контекст нужен наряду, а не по инструментам. Почему: отправка в git (git push), клон репозитория и командная строка доступны в любой сессии любого проекта, которая умеет пользоваться Skills: push открывается добавлением репозитория в сессию с правом записи, если среди её инструментов есть добавление репозитория (порядок пробы и признак отказа — `second-brain-git` 9.1, references/delivery.md). Поэтому инструменты среды выбор не различают — их наличие проверяет Исполнитель на приёме (ниже). Основание: решение Андрея 2026-10-21, чат SYS — отчёт синтеза, раздел «Решения Андрея 2026-10-21 по спискам отчёта».

1. Нужен ли контекст Claude-Project — мастер-промпт, Зона А INDEX, история переписки проекта, — который наряд не может унести с собой целиком в поля ЗАДАЧА, РАМКА, ТРЕБУЕТ? ДА → чат проекта <имя>.
2. Работа принадлежит Летописи — проекту в репозитории без Claude Project, мастер-промпт которого ведёт работу по нарядам? ДА → сессия Летописи <имя>: сессия, в которую загружен мастер-промпт этой Летописи. Почему: у Летописи нет Claude Project сознательно — это архитектурное решение Андрея (2026-10-21, чат SYS), поэтому её контекст живёт в её мастер-промпте и папке репозитория, а не в чате проекта.
3. На вопросы 1 и 2 ответ «нет», и каждое «нет» обосновано фактом из ТРЕБУЕТ или ЗАДАЧИ → новый чат вне проекта. Наряд несёт в себе всё, что нужно Исполнителю: рамку, ID файлов, формат результата (§3.2, references/issuer.md).
   Не довод за выбор среды: объём результата — файл любого размера пишется в Drive из любого чата воркфлоу; диалог по ходу выполнения — он доступен в любой среде (§3.2).

Не удаётся ответить на вопрос 1 или 2 — это не «новый чат вне проекта», это «ГДЕ: не определено», и наряд не выдаётся.

Проверка инструментов — на приёме, не на выдаче. Push не гарантирован ни одной средой: предикат — не имя среды, а список репозиториев, авторизованных для сессии. Исполнитель проверяет push на приёме командой `git push --dry-run`, при отказе добавляет репозиторий в сессию с правом записи и повторяет пробу; при повторном отказе отвечает НЕ ПРИНЯТ по §6(б), а не ищет обход. Канал (воркфлоу n8n чтения и записи репозитория, `second-brain-git`) есть только там, где к сессии подключены инструменты n8n (MCP n8n): его наличие тоже проверяется в самой сессии на приёме — по списку её инструментов, а не по имени среды. Если инструментов n8n в сессии нет, наряд, которому нужны и push, и Канал, одним нарядом не выдаётся — он дробится на два по потребности, и порядок их исполнения назначается явно. Основание: 2 случая, последний 2026-09-24 — отчёт синтеза, правило NAR.3.1.канал.

Не путать: «git push и клон есть только в Cowork и Claude Code, а в чате проекта их нет» — так дерево ГДЕ стояло до 2026-10-21; на деле отправка в git открывается добавлением репозитория в любой сессии, умеющей пользоваться Skills (решение Андрея 2026-10-21).

ОСНОВАНИЕ ГДЕ печатает номер сработавшего вопроса и ответы «нет» на все предыдущие вопросы с фактом из ТРЕБУЕТ или ЗАДАЧИ. Образец: «3 — контекст проекта не нужен (1), работа не Летописи (2)». Почему: номер без ответов — копия предыдущего наряда, а не выбор; предыдущий блок НАРЯД в контексте — самый сильный шаблон для следующего, и поля переезжают в него целиком. Признак: ГДЕ называет среду или чат, которого нет. Основание: 1 случай, последний 2026-09-10 — отчёт синтеза, правило NAR.3.1.основание.

Чат проекта, не обоснованный в ТРЕБУЕТ или ЗАДАЧЕ потребностью в контексте проекта, на приёме отбивается по §6(в).

Ошибка в ГДЕ ловится на приёме (§6), а не на выдаче. Цена ошибки — одно сообщение, а не потерянная сессия.

### 3.3 Маркировка ID = Н-ДД.ММ-NN

ДД.ММ — дата выдачи. NN — порядковый номер, с 01, в пределах суток.

Дочерние наряды Прораба: Н-ДД.ММ-NN.1, .2, .3

Больше одной точки запрещено — это нарушение глубины (§7).

Пример: Н-08.08-02 и его дочерние Н-08.08-02.1, .2

Коллизия (два Руководителя в один день): Андрей дописывает букву при передаче — Н-08.08-02а. Префикс проекта не вводится.

ID — первое слово КАЖДОГО сообщения о наряде, во всех направлениях:

- выдача: Н-08.08-02 НАРЯД
- отказ приёма: Н-08.08-02 НЕ ПРИНЯТ. <причина>
- приём: Н-08.08-02 Принял. DoD своими словами: …
- закрытие: Н-08.08-02 ЗАКРЫТ. <ID артефакта>
- сводка Прораба: Н-08.08-02 СВОДКА. Закрыты: .1 .2 .3
- отмена Андреем: Н-08.08-02 ОТМЕНЁН.

Сообщение о наряде без ID сообщением о наряде не является: не выдаётся, не принимается, закрытием не засчитывается.

### 3.4 Мандат на отказ

РАМКА говорит, чего НЕ делать. МАНДАТ НА ОТКАЗ говорит, что Исполнитель вправе отвергнуть. Почему поле нужно: без него исполнитель, работающий по написанной процедуре, не может усомниться в самой процедуре — и добросовестно доводит до конца заведомо неверную работу.

Значения:

- процедура — вправе объявить сам метод негодным и остановиться
- посылка — вправе отвергнуть допущение, на котором стоит ЗАДАЧА
- цифры — вправе не принять числа из наряда без источника
- вход — вправе отвергнуть результат предыдущего наряда
- нет — отказ не предусмотрен, выполнять как написано

Для нарядов на проверку, аудит и верификацию значение всегда «процедура, посылка, цифры, вход». Почему: аудит с узким мандатом бесполезен — он подтвердит то, что ему дали подтверждать.

Отказ по мандату оформляется как результат, а не как сбой:

```
Н-ДД.ММ-NN ОТКАЗ ПО МАНДАТУ: <что отвергнуто> — <на каком основании>.
```

Это закрытие наряда, а не его провал. Основание отказа обязано быть объектом (строка файла, номер исполнения, замер), а не рассуждением.

Значение «процедура» не распространяется на бюджеты чтения и размеры файлов репозитория: у них есть переливной клапан (`second-brain-git` 5.5, references/write.md), а в сводке запретов того же Skill (пункт 14, references/write.md) стоит запрет «Отказывать в записи или откладывать запись по причине бюджета чтения или размера файла». Размер файла — не негодность метода: отказ по размеру файла — нарушение мандата, а не его применение. Потолков записи в байтах у файлов репозитория нет с 2026-09-17 (`second-brain-git` 4.5, references/write.md — «Правило происхождения текста»), поэтому ссылаться на них как на основание отказа нельзя: ссылаться не на что. Основание: 1 случай, последний 2026-09-09 — отчёт синтеза, правило NAR.3.4.размер.

## 7. Ограничители

Глубина 1. Наряды выдают только Руководитель и Прораб. Исполнитель — никогда. Признак нарушения — больше одной точки в ID (§3.3).

Потолок 5. Больше пяти открытых КОРНЕВЫХ нарядов одновременно не выдаётся. Дочерние в потолок не входят: они живут внутри DoD родителя и закрываются вместе с ним. Шестой корневой ждёт закрытия любого из пяти.

Нет DoD — нет наряда. Поручения «вообще» не выдаются и не принимаются.

Один файл — один наряд, в обе стороны.

Конкуренция. Два наряда, работающих с одним файлом, одновременно не ведутся — даже если один пишет в голову файла, а другой в хвост. Почему: замер одного становится ложным от записи другого. Основание: 1 случай, последний 2026-08-05 — отчёт синтеза, правило NAR.7.конкуренция. Для файлов репозитория непересечение путей гонки не снимает: параллельные записи состязаются за голову ветки — механика и порядок — `second-brain-git` 8.9 (references/delivery.md).

Конкуренция касается и Руководителя. Пока открыт наряд Контролёра (проверка чужой работы), Руководитель не пишет ни в его объект, ни в ветку, по голове которой Контролёр снимает вердикты, — даже маршрутом Б. Почему: голова уходит со снимка, по которому Контролёр снимал вердикты, и каждый вердикт приходится перепроверять в двух точках. Основание: 1 случай, последний 2026-09-15 — отчёт синтеза, правило NAR.7.контролёр.

Охват. Один наряд не правит больше одного пути (§3.7, references/destructive-orders.md), кроме исключения об атомарной записи, описанного там же. Почему отдельной строкой: правило о конкуренции, прочитанное узко, позволяет одному наряду охватить несколько файлов и архив, оставаясь формально чистым. Основание: 1 случай, последний 2026-08-20 — отчёт синтеза, правило NAR.7.охват.

Потолок правок и обязательный паспорт — §3.7 (references/destructive-orders.md).

## 8. Приёмка

Приёмка только по объекту, никогда по отчёту Исполнителя — включая собственный отчёт Руководителя о собственной работе. Закрывающий наряд читает объект сам, а не сверяет два описания объекта между собой. Почему: отчёт бывает формально верен и по существу ложен — описание объекта совпадает с другим описанием, а объект другой. Признак: отчёт утверждает отсутствие («потерь нет», «стыки чистые»), удаление («пункт удалён») или состояние («активен»), а закрытие опирается на этот отчёт или на слово «сделал», не на чтение объекта. Основание: 5 случаев, последний 2026-09-24 — отчёт синтеза, правило NAR.8.объект. Общий стандарт верификации записи для обоих носителей — `second-brain-engineer` Р15.

Приёмка правки построчного списка (INDEX.md и подобных) — по diff строк с предыдущим прочитанным текстом, а не по размеру. Почему: число байт (byteLength) не отличает чужую параллельную запись от ошибки Исполнителя — обе меняют число байт. Основание: 1 случай, дата последнего случая в источнике не названа — отчёт синтеза, правило NAR.8.список.

Отдельный наряд на приёмку оправдан только тогда, когда проверяется суждение Исполнителя, а не голое число. Почему: приёмка двух-трёх чисел не требует наряда, отдельной сессии и круга пересылок — они сжигают слот потолка 5 (§7) без надобности. Основание: 1 случай, дата последнего случая в источнике не названа — отчёт синтеза, правило NAR.8.отдельный.

## Чего этот Skill НЕ определяет

Роли распределяют ОТВЕТСТВЕННОСТЬ ЗА ШАГ, а не правоту.

Прав тот, кто читал источник, независимо от класса модели — правило «кто читал источник, тот и прав», `second-brain-engineer` Р15, пункт 1. Исполнитель, прочитавший файл, опровергает Руководителя, который его не читал. Наряд при этом остаётся в силе до отмены Андреем.

Skill не называет модели по именам и не хранит критерий классов — он в `second-brain-engineer` Р18 (references/permissions.md). Здесь только порядок вывода класса (§3.1а), чтобы поле было выведено и проверено, а не заполнено по правдоподобию.

Skill не ведёт реестр инструментов сред. Наличие проверяет та среда, которая знает о себе достоверно, — в момент приёма наряда.

Skill не ведёт журнал выданных нарядов. ID самодостаточен: дата и номер. Журнал заводится, только если Андрей дважды не смог найти наряд по ID.

## Границы

Не заменяет `context-handoff`: тот переносит контекст между чатами одной работы, этот раздаёт разные работы разным чатам.

Не создаёт файлов на Drive, не заводит Drive-ID и не пишет в INDEX. Наряд — сообщение. Идентификатор наряда по §3.3 файлом не является и под это ограничение не подпадает.
