НАРЯД — распределение ролей внутри Claude-Project

Область применения Применяется к разработке новых идей и сложных задач внутри Claude-Project: чтение файлов и воркфлоу, извлечение из технической документации, написание кода новых воркфлоу, проверка старого кода.

Не применяется к: рядовым вопросам, единичным операциям, работе вне Claude-Projects.

Причина существования: класс модели, достаточный для проектирования, разорителен для чтения и записи. Роли разделяют дорогое мышление и дешёвое исполнение.

Где формат окупается эмпирически (замер 2026-08-04/05): диагностика, аудит, деструктивные и боевые операции — там, где цена ошибки высока и независимая проверка реально ловит дефекты. Три подтверждённые поимки за одну сессию: false positive монитора; отказ собирать credentials вслепую; отказ подтвердить цифру без источника.

Где не окупается: быстрая тесно связанная итерация, где Андрей и так в диалоге на каждом шаге. Там наряд — накладной расход.

Роли Руководитель — проектирует. Формирует замысел, разбивает на наряды, оценивает результаты. Не читает файлы, не пишет, не вызывает инструменты.

Прораб — организует. Получил наряд, дробит его на наряды Исполнителям ВНУТРИ полученного DoD. Собирает отчёты, отдаёт один результат.

Исполнитель — делает. Один наряд, один результат, один артефакт.

Андрей — шина. Все наряды и отчёты идут через него. Роли между собой не сообщаются.

Формат наряда Печатается ВСЕГДА целиком. Незаполненное поле — прочерк, не пропуск строки. Отсутствие поля невидимо; прочерк виден.

<ID> НАРЯД ЗАДАЧА: DoD: (проверяемо: объект, а не состояние) РАМКА: (что НЕ делать / где остановиться) МАНДАТ НА ОТКАЗ: (что Исполнитель вправе отвергнуть — см. §3.4) ТРЕБУЕТ: (инструменты и доступы, без которых наряд не выполнить) ПАСПОРТ: (стоимость исполнения по формуле §3.7; обязателен при деструктивных правках, для read-only нарядов — прочерк) ЗАМЫСЕЛ: (три строки по §3.8; обязателен при деструктивных правках, для read-only нарядов — прочерк) ИСПОЛНИТЕЛЬ: Прораб | Исполнитель МОДЕЛЬ: средний | высокий — номер сработавшего вопроса §3.1а: ГДЕ: чат проекта <имя> | Cowork | Claude Code ОСНОВАНИЕ ГДЕ: номер сработавшего вопроса §3.1 РЕЗУЛЬТАТ В: <ID файла или «в ответ»> — см. §3.5 DoD в терминах объекта: «ID созданного паспорта», «occurrencesChanged=1 + подтверждающее чтение», «список из N строк». Не «разобраться», не «улучшить», не «проверить».

ТРЕБУЕТ перечисляет потребность, а не оснастку: чтение Drive, запись Drive, n8n, shell, git, интернет, работа с загруженными файлами. Это поле про задачу — Руководитель способен его заполнить, не зная, что подключено к какой среде. Одно уточнение обязательно: слово «git» в этом поле не пишется голым. Пишется либо «git на чтение» — клон, diff, история, hash-object, — либо «git push» — доставка в main по маршруту second-brain-git 9.4(б). Это две разные потребности, их удовлетворяют разные среды (§3.1), и наряд с голым «git» на приёме отбивается по §6(а) как наряд с незаполненным полем.

3.1 Выбор поля ГДЕ Умолчания нет. Среда выбирается ответом на вопросы по порядку, первое «да» останавливает проверку. Список подключённых инструментов здесь не приводится сознательно: он устареет раньше, чем понадобится.

Нужен git push — доставка в main по маршруту second-brain-git 9.4(б): ротация журнала, возврат версии из истории, сборка файла из уже существующего текста — либо файловая система, тесты, сборка, сервер? ДА → Claude Code. Две оговорки, обе печатаются в наряде. Первая: push там не гарантирован — предикат не имя среды, а список репозиториев, авторизованных для сессии (second-brain-git 9.1); Исполнитель проверяет его на приёме командой git push --dry-run и при отказе отвечает НЕ ПРИНЯТ по §6(б), а не ищет обход. Вторая: Канал n8n есть в Claude Code только там, где к сессии подключён MCP n8n — Н-10.09-05 застал сессию без него, а облачная сессия Claude Code 2026-09-24 вызывала Канал весь день (Р-18 журнала projects/kontext-reduktion/LOG.md). Поэтому наличие Канала, как и push, проверяется в самой сессии на приёме — по списку её инструментов, а не по имени среды. Если MCP n8n в сессии нет, наряд, которому нужны и push, и Канал, одним нарядом не выдаётся — он дробится на два по потребности, и порядок их исполнения назначается явно.
Нужен git на чтение — клон, diff, git hash-object, история, дешёвое сплошное чтение файла (second-brain-git 7.6) — вместе с Каналом n8n или без него? ДА → Cowork. Там клон и fetch открыты, Канал работает, push закрыт (second-brain-git 9.1, 9.2); если push всё-таки нужен — это был вопрос 1. До 2026-09-17 дерево этой среды не знало: вопрос про «git» гнал такие наряды в Claude Code, где нет Канала, и три наряда за день упирались в это слепое место.
Нужен ли контекст Claude-Project — мастер-промпт, Зона А INDEX, история переписки проекта — который наряд не может унести с собой целиком в поля ЗАДАЧА/РАМКА/ТРЕБУЕТ? ДА → чат проекта <имя> НЕТ → к вопросу 4
Исполнитель создаёт новый артефакт с нуля или обрабатывает несколько файлов подряд, отдавая результат одним пакетом? ДА → Cowork НЕТ → чат проекта <имя> Разделяет не объём результата. Файл любого размера пишется в Drive из чата проекта воркфлоу. Разделяет не диалог — диалог по ходу выполнения доступен и в чате проекта, и в Cowork (см. §3.2). Разделяет то, что реально не переезжает: контекст Claude-Project и автономность создания артефакта с нуля.

Ни один вопрос не имеет ответа по умолчанию. Не удаётся ответить — это не «чат проекта», это ГДЕ: не определено, и наряд не выдаётся. ОСНОВАНИЕ ГДЕ печатает номер сработавшего вопроса и ответы «нет» на все предыдущие вопросы с фактом из ТРЕБУЕТ. Образец: «4 — push не нужен (1), git на чтение не нужен (2), контекста проекта нет (3), результат одним пакетом (4)». Номер без ответов — копия предыдущего наряда, а не выбор: предыдущий блок НАРЯД в контексте — самый сильный шаблон для следующего, и поля переезжают в него целиком (прецедент Н-10.09-09: ГДЕ назвал чат проекта, которого не существует). Чат проекта, не обоснованный в ТРЕБУЕТ потребностью в контексте проекта, на приёме отбивается по §6(в).

Ошибка в ГДЕ ловится на приёме (§6), а не на выдаче. Цена ошибки — одно сообщение, а не потерянная сессия. 3.1а Выбор поля МОДЕЛЬ. Введён 2026-09-11. Адресат поля — Андрей: модель чата выбирает он, а Исполнитель проверить своё соответствие не может — сессия не знает достоверно, на какой модели работает. Поэтому поле печатает не имя модели, а класс и основание, которое сверяется с ЗАДАЧЕЙ за одно чтение. Вопросы по порядку, первое «да» останавливает проверку:

Наряд проверяет суждение другой сессии (аудит, приёмка, ревизия), ведёт диагностику без готовой гипотезы или проектирует новое (правило, архитектуру, воркфлоу)? ДА → высокий.
У шага написана процедура, гипотеза готова, DoD — объект? ДА → средний. Ни одно не сработало — наряд не готов: у него нет ни процедуры, ни гипотезы. Это дефект ЗАДАЧИ, не поля; наряд переписывается, не выдаётся. Критерий классов — CORE Р.12 п.9; здесь только порядок вопросов. Имена моделей в Skill не пишутся: они меняются чаще, чем Skill. Поле без номера вопроса пустым не считается, но на приёме отбивается по §6(а) как незаполненное.

3.3 Маркировка ID = Н-ДД.ММ-NN

ДД.ММ — дата выдачи. NN — порядковый номер, с 01, в пределах суток.

Дочерние наряды Прораба: Н-ДД.ММ-NN.1, .2, .3 Больше одной точки запрещено — это нарушение глубины (§7).

Пример: Н-08.08-02 и его дочерние Н-08.08-02.1, .2

Коллизия (два Руководителя в один день): Андрей дописывает букву при передаче — Н-08.08-02а. Префикс проекта не вводится. ID — первое слово КАЖДОГО сообщения о наряде, во всех направлениях:

выдача: Н-08.08-02 НАРЯД отказ приёма: Н-08.08-02 НЕ ПРИНЯТ. <причина> приём: Н-08.08-02 Принял. DoD своими словами: … закрытие: Н-08.08-02 ЗАКРЫТ. <ID артефакта> сводка Прораба: Н-08.08-02 СВОДКА. Закрыты: .1 .2 .3 отмена Андреем: Н-08.08-02 ОТМЕНЁН. Сообщение о наряде без ID сообщением о наряде не является: не выдаётся, не принимается, закрытием не засчитывается.

3.4 Мандат на отказ РАМКА говорит, чего НЕ делать. МАНДАТ НА ОТКАЗ говорит, что Исполнитель вправе отвергнуть. Без этого поля исполнитель, работающий по написанной процедуре, не может усомниться в самой процедуре — и добросовестно доводит до конца заведомо неверную работу.

Значения:

процедура — вправе объявить сам метод негодным и остановиться посылка — вправе отвергнуть допущение, на котором стоит ЗАДАЧА цифры — вправе не принять числа из наряда без источника вход — вправе отвергнуть результат предыдущего наряда нет — отказ не предусмотрен, выполнять как написано Для нарядов на проверку, аудит и верификацию значение всегда процедура, посылка, цифры, вход. Аудит с узким мандатом бесполезен: он подтвердит то, что ему дали подтверждать.

Отказ по мандату оформляется как результат, а не как сбой:

Н-ДД.ММ-NN ОТКАЗ ПО МАНДАТУ: <что отвергнуто> — <на каком основании>. Это закрытие наряда, а не его провал. Основание обязано быть объектом (строка файла, execution, замер), не рассуждением. Значение «процедура» не распространяется на бюджеты чтения и размеры файлов repo: у них есть клапан (second-brain-git §5.5, запрет 16), и размер файла — не негодность метода. Отказ по размеру файла — нарушение мандата, не его применение. Потолков записи в байтах у файлов repo с 2026-09-17 нет (second-brain-git 4.5) — ссылаться на них как на основание отказа нельзя, потому что ссылаться не на что. Основание: Т-38 журнала git-migration.

Ограничители Глубина 1. Наряды выдают только Руководитель и Прораб. Исполнитель — никогда. Больше одной точки в ID — признак нарушения. Потолок 5. Больше пяти открытых КОРНЕВЫХ нарядов одновременно не выдаётся. Дочерние в потолок не входят: они живут внутри DoD родителя и закрываются вместе с ним. Шестой корневой ждёт закрытия любого из пяти. Нет DoD — нет наряда. Поручения «вообще» не выдаются и не принимаются. Один файл — один наряд, в обе стороны. Конкуренция: два наряда, работающих с одним файлом, одновременно не ведутся, даже если один пишет в голову, а другой в хвост — замер одного становится ложным от записи другого (прецедент 2026-08-05). Охват: один наряд не правит больше одного пути (§3.7), кроме исключения об атомарной записи, описанного там же — узкое прочтение только про конкуренцию позволило Н-20.08-04 охватить три файла и zip, оставаясь формально чистым (прецедент 2026-08-20). Потолок правок и обязательный паспорт — §3.7. Приёмка Приёмка только по объекту, никогда по отчёту Исполнителя — включая собственный отчёт Руководителя о собственной работе.

Класс ошибки зафиксирован 2026-08-07 тремя независимыми случаями за день: отчёт «потерь ноль, реестры на месте, стыки чистые» на разрезе, который был сломан; запись об удалении пункта, который остался на месте; пометка «активен» про выключенные мониторы. Во всех трёх случаях отчёт был формально верен и по существу ложен.

Практически: закрывающий наряд читает объект сам, а не сверяет два описания объекта между собой.

Чего этот Skill НЕ определяет Роли распределяют ОТВЕТСТВЕННОСТЬ ЗА ШАГ, а не правоту.

Прав тот, кто читал источник, независимо от класса модели (second-brain-engineer, правило «кто читал источник, тот и прав»). Исполнитель, прочитавший файл, опровергает Руководителя, который его не читал. Наряд при этом остаётся в силе до отмены Андреем.

Skill не называет модели по именам и не хранит критерий классов — он в CORE Р.12 п.9. Здесь только порядок вывода класса (§3.1а), чтобы поле было выведено и проверено, а не заполнено по правдоподобию.

Skill не ведёт реестр инструментов сред. Наличие проверяет та среда, которая знает о себе достоверно, — в момент приёма наряда.

Skill не ведёт журнал выданных нарядов. ID самодостаточен: дата и номер. Журнал заводится только если Андрей дважды не смог найти наряд по ID.

Границы Не заменяет context-handoff: тот переносит контекст между чатами одной работы, этот раздаёт разные работы разным чатам. Не создаёт файлов на Drive, не заводит Drive-ID и не пишет в INDEX. Наряд — сообщение. Идентификатор наряда по §3.3 файлом не является и под это ограничение не подпадает. Не активен, пока zip не перезалит в Customize → Skills.
