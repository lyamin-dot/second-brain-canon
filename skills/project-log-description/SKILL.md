# PROJECT_LOG — контракт журнала решений проекта

ПОСЛЕ ПРОЧТЕНИЯ ПОДТВЕРДИ дословной цитатой пункта контракта чтения, релевантного текущей задаче.

## 1. Назначение

Хранит то, чего нет ни в INDEX, ни в CHANGELOG:
- почему выбран вариант и что отвергнуто;
- что пробовали и не вышло (тупики);
- ошибки: симптом, корневая причина, фикс, детектор.

НЕ хранит цель, план и сделанное — они живут в Зоне А INDEX и в CHANGELOG. Дублирование источника истины запрещено (мастер-промпт SYS, принцип 1).

Один файл на проект: PROJECT_LOG_<КОД>, папка _SYSTEM. Регистрация ID: CORE Р.2 и строка в Зоне А INDEX проекта.

Носитель — Google Docs. Проект, чей канон переехал в repo `second-brain-canon`, ведёт журнал решений не этим контрактом, а формой §11 `second-brain-git` (Git Append/Git Replace вместо gdocs-*, blob sha вместо канарейки) — два контракта об одном и том же факте на двух разных носителях, не конкуренты. Этот Skill относится только к проектам, чей журнал реально лежит в Docs.

## 2. Ленивое создание

Файл НЕ создаётся заранее. Пока решений нет, в Зоне А INDEX стоит строка `PROJECT_LOG: не заведён`. Файл создаётся автоматически в момент первой квалифицирующей записи на !save.

Отсутствие файла и пустое чтение — РАЗНЫЕ события:
- `success:false` / `reason: not found` — законный ответ «журнал не заведён», работа продолжается;
- `success:true` при пустом тексте — конфабуляция, СТОП.

## 3. Контракт чтения (нарушение любого пункта = чтение не состоялось)

1. Только `gdocs-read` (`hJZhQ9KaeFgeRm3k`), `mode: full`, `executionMode: manual`, ПРЯМЫМ вызовом. Не через субагента: byteLength через субагента расходится с прямым чтением на 47–80% без ошибки (класс 2026-08-17).
2. `read_file_content` и `google_drive_fetch` по журналам ЗАПРЕЩЕНЫ независимо от размера. `fileSize` не индикатор размера экспорта (E17, прецедент N8N_INDEX 2026-07-24).
3. `get_execution` вызывать с `nodeNames` и `truncateData: 1`.
4. Пересчитать FNV-1a(32) по UTF-8 байтам поля `text`, сверить с `checkSum` и `byteLength`. Расхождение — чтение недостоверно, СТОП без обсуждения. Граница исполнимости: пересчёт требует записать байты `text` на диск и посчитать — без инструмента кода этих байтов у сессии нет, текст приезжает только в контекст ответа. Без инструмента кода пункт исполняется как сверка `len(text.encode('utf-8')) == length` — без остатка, без усечения; это слабее полного FNV и ловит только обрезку/добавление, не точечную подмену внутри объёма. Граница называется вслух в ответе, а не молчится [PROJECT_LOG_SYS Т-06].
5. ДВУХКООРДИНАТНАЯ КАНАРЕЙКА. Процитировать ЗАПИСЕЙ N из шапки И номер с датой последней записи из хвоста. Не совпало — либо чтение обрезано, либо запись сделана наполовину. СТОП, обсуждению не подлежит.

Канарейка считает УНИКАЛЬНЫЕ номера записей, не строки: два разных решения, случайно получившие один и тот же номер (см. §5 ниже), канарейкой не ловятся — оба совпадают со счётчиком. Это не брешь контракта чтения, а граница его чувствительности; закрывает её §5, не этот пункт.

6. Чтение сразу после записи — с паузой или двумя совпадающими чтениями. Read-after-write в Google Docs не немедленный, ложное подтверждение возможно в обе стороны.
7. Режим `tail` для верификации НЕПРИГОДЕН: `checkSum` считается по всему файлу, а возвращается только хвост, локальная сверка невозможна.

Почему канарейка двухкоординатная: журнал append-only, ценность монотонно растёт к хвосту. Инструмент, режущий хвост, отдаёт непротиворечивый на вид текст без последних записей. Одна координата (номер в хвосте) доказывает, что хвост доехал. Вторая (счётчик в шапке) доказывает, что хвост актуален. Канарейка меняется при каждой записи — её нельзя воспроизвести по памяти или по прошлой сессии.

## 4. Гейт: где именно читать

ПЕРЕД тем как предложить архитектурный вариант, план работ или наряд по проекту — не в начале сессии: отказ, который лечит этот пункт, наступает в момент предложения, не в момент старта.

Шапка наряда по проекту с заведённым журналом содержит обязательное поле:
ПРОВЕРЕНО ПО PROJECT_LOG_<КОД>: шапка N=<N> | хвост зап.№<N> от <дата> |
релевантные решения: №… | тупики: №… (или «нет»)


Наряд с незаполненным полем к приёмке не принимается (`naryad` §8). Заполненное поле само является записью Ч-NN в ЖУРНАЛ ЧТЕНИЙ.

## 5. Контракт записи

Пишет сессия на !save, без участия Владельца.

Квалифицирует одно из трёх:
- (а) выбран вариант из двух и более и названа причина;
- (б) попытка провалилась и от неё отказались;
- (в) удивление или незапланированная отладка.

Ни одного — писать явное «решений нет». Молчание означает, что !save не закрыт.

РЕТРОСПЕКТИВНАЯ ЗАПИСЬ ЗАПРЕЩЕНА. Пишется только то, что произошло в этой сессии. Восстановление истории проекта по памяти — конфабуляция, того же класса, что сочинение передачи по памяти (`PROTOCOL_project-development` §0).

Порядок: `gdocs-replace` по маркеру нужного раздела, затем `gdocs-replace` строки ЗАПИСЕЙ в шапке, затем `gdocs-replace` строки в хвосте. Выполняются все три или ни одной. `gdocs-append` для журнала ЗАПРЕЩЁН.

Правило «один файл — одна сессия» (`naryad` §7 «Конкуренция») распространяется на журналы: если наряд или другая сессия могут параллельно писать в тот же журнал — запись откладывается, две сессии по одному журналу не ведутся одновременно. Номер записи не резервируется заранее: он берётся из СВЕЖЕГО чтения непосредственно перед первым из трёх `gdocs-replace`, а не из чтения, сделанного раньше по сессии, и не из плана, составленного до чтения. Прецедент, ради которого это здесь написано текстом, а не осталось только в истории: 2026-08-30 две сессии писали в PROJECT_LOG_SYS параллельно и дважды за сутки заняли одинаковые номера; первую коллизию (Р-05, Р-06, Т-03, Ч-02) заметили и перенумеровали в тот же день, вторую — нет. Две разные записи, обе от 2026-08-30, обе подписаны номером Р-11 и обе стоят «в силе» в документе на момент, когда пишутся эти строки. Канарейка их не разделяет (см. §3) — единственная защита от повтора и есть это правило.

Записи append-only. Решение не редактируется — отменяется новой записью со ссылкой на номер.

## 6. Форма записи

`Р-NN | дата | вопрос | что принято | почему | кто подтвердил` — обязательны.
`что отвергнуто и почему | обратимость | допущение` — по наличию; поле без данных не пишется, заглушки запрещены (`second-brain-git` 11.4).

`статус: в силе / отменено Р-NN`

`Т-NN | дата | что пробовали | почему не вышло | условие возврата`
По наличию: стоимость попытки.

`Ч-NN | дата | сессия | зачем читали | изменило ли план`

Поле «условие возврата» обязательно: тупик часто временный (OZON_CV ждал Premium Plus, error-memory ждал JWT-миграции). Тупик без условия возврата превращается в вечный запрет. Поле «по наличию» без данных не пишется — ни прочерком, ни заглушкой «не зафиксировано при записи»; отсутствие поля и есть запись о том, что данных не было. Обязательное поле без содержания — запись не пишется, наряд возвращается выдавшему. Правило совпадает с `second-brain-git` 11.4.

## 7. Потолок и ротация

Живая часть — не более 16 384 байт. Выше потолка старые записи уезжают в `PROJECT_LOG_<КОД>_ARCHIVE` на обслуживании. Потолок не пожелание: он гарантирует, что живая часть всегда заведомо ниже порога усечения, то есть обрезка становится невозможной физически, а не по договорённости.

## 8. Запрещено

- Копировать в журнал цель, план, список задач, содержимое CHANGELOG.
- Заводить пустые журналы впрок: пустой документ учит систему, что чтение бесполезно.
- Писать в журнал через `gdocs-append` в любом виде. §5 запрещает его безусловно; порядок записи — три `gdocs-replace` (раздел, шапка, хвост), выполняются все три или ни одной. Прежняя формулировка запрещала лишь append «без последующего обновления шапки и хвоста», то есть допускала append с обновлением — и противоречила §5. [verified: 2026-09-07]
- Считать факт вызова инструмента фактом чтения.
- Продолжать работу при расхождении канарейки.
- Резервировать номер записи заранее, вместо чтения непосредственно перед записью (§5).
