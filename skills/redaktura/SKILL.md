# redaktura

Мастер-промпт и Skill — один слой: оба живут в аккаунте, оба правит только Андрей, оба действуют лишь после того, как он их вставил или залил. Сессия здесь пишет текст, Андрей его ставит.

## На какие вопросы отвечает этот Skill

- **Что написать в мастер-промпте и чего туда не писать?** — «Р22. Мастер-промпт: от старого текста к новому».
- **Каким должен быть блок Второго мозга в промпте?** — «Р2. Эталонный блок Второго мозга в мастер-промпте», затем «Р3. Валидация мастер-промпта».
- **Нужен ли новый Skill, куда положить правило, как не размножить пересечения?** — «Р20. Гигиена каталога Skill и правило в код (16)».
- **Как правка Skill вступает в силу, как её принять, обновить зеркало `skills/`, найти копии старой формулировки и собрать архив для заливки?** — «Правка Skill: приёмка, зеркало, копии, архив для заливки». Чтение и запись файлов репозитория при этом — Skill `second-brain-git`.
- **Регламент Второго мозга (старт, захват, !save, команды)** — не здесь: Skill `second-brain-engineer`. Этот Skill только следит, чтобы промпт его не пересказывал.

## Как отдаётся работа Андрею

1. Правка промпта или Skill — полным текстом на вставку: имя Skill или проекта, якорь-строка места, блок «было → стало». Ссылка «та же формулировка, что в …» правкой не считается.
2. Рядом с текстом — найденные противоречия и устаревшие места с объяснением; решение по каждому принимает Андрей.
3. Каждый Skill пишется своим стилем, непохожим на соседние: так сессия и Андрей быстрее различают, где какой.
4. Правка действует только после заливки Андреем: текст в чате, в зеркале `skills/`, в файле Drive ничего не меняет. Приёмка — по снимку живого Skill в той сессии, которая на правку опирается (раздел «Правка Skill: приёмка, зеркало, копии, архив для заливки»).
5. Поправка выданного мастер-промпта — тем же шагом в зеркало `meta/prompts/<папка>.md`.

## Стоп-правила

### Мастер-промпт и онбординг
- Мастер-промпт или блок Второго мозга не выдавать, если не выполнен хоть один пункт раздела «Р3. Валидация мастер-промпта».
- Блок Второго мозга не менять без явного «да» Андрея в чате и текста «было → стало»; правила, уже стоящие в Skill, в блок не вписывать.
- Регламент Второго мозга (строку старта, маршрут !save, таблицу команд, формат захвата, порядок записи) в промпте не пересказывать.
- Ссылки на общие документы (USER_PROFILE, INBOX, CHANGELOG), Docs-ID CORE и ID замороженных документов как источников состояния в блок и промпт не вписывать.
- Изменчивые факты (статусы, расписания, адреса ячеек, версии, числа замеров, список багов) и ID, у которых есть реестр, в промпт не писать; исключение — ID, без которых не прочитать реестр (воркфлоу Git-канала, gdocs-read, gsheets-read).
- Обрыв старого промпта не дописывать по догадке — спросить остаток; первую строку нового текста не писать, пока не получены все части инструкций.
- Знания, которых нет нигде, кроме промпта, не удалять как «изменчивые».
- Расхождение двух копий промпта тихо не выравнивать — стоп и вопрос Андрею, какая права.
- Обязательных фраз в конце ответа в промпт не ставить; лимиты самостоятельности по счёту вызовов не ставить.
- Поправку выданного промпта не оставлять только в чате — тем же шагом в зеркало `meta/prompts/<папка>.md`.
- Рассказ урока о промпте в метод не дописывать.

### Правка Skill и каталог
- Пороги «свыше 90 % успеха до 20 навыков, деградация после 30» основанием решения о создании или объединении Skill не брать; довод «у нас почти 30 Skills» доводом не считать.
- Единый язык формулировок при массовой правке описаний Skills не вводить.
- Состояние и особенности конкретного проекта, таблицы, книги, воркфлоу, сервера или кабинета в Skill не писать; поведение API маркетплейса — тоже.
- Проверку, условие или счётчик, которые среда не исполняет, в правку Skill не вписывать без пометки «неисполнимо».
- Список неразобранных пересечений описаний молча на следующую карту каталога не переносить.
- Рассказы случаев, номера исполнений и историю правок в Skill не писать.
- Правило без триггера и момента действия в Skill не вносить.

### Правка Skill: зеркало, копии, архив
- Зеркало `skills/<имя>/` моделью или Каналом не писать — только копией файлов живого Skill командой.
- Правку Skill не закрывать без обновления зеркала и без механического поиска копий старой формулировки.
- Правку владельца не принимать словом «внёс» — только по объекту.
- Зеркало поверх незалитой правки не копировать — стоп и вопрос владельцу.
- Живой Skill с находкой классов 1–4 (Skill `second-brain-git`, раздел «Носитель и данные») в зеркало не писать — владелец убирает значение, зеркало после.
- Среда без открытого push зеркало не пишет — ни Каналом, ни частями.
- Работу по тексту Skills (черновик, замер, «предлагаю снять», архив) не строить по зеркалу без сверки с живым в этой сессии; «зеркало совпадает с живым» без сверки не писать.
- Архив Skill не выдавать без всех выданных и не залитых правок этого Skill и без названия прежних наборов, которые не заливать.
- Архив с description длиннее 1024 знаков не выдавать.
- Многофайловый Skill не заливать кнопкой Save skill в Cowork — только zip через Customize → Skills (заливает Андрей).
- Правку Skill не считать действующей по тексту в чате, в зеркале или в файле Drive — только по снимку `/mnt/skills/` (по якорю правки или побайтово).

## Как делать

### Р22. Мастер-промпт: от старого текста к новому
Триггер: написать, переписать или проверить мастер-промпт Claude Project целиком (не только блок Второго мозга); после выдачи нашлось, что пошло не так. Шаги 1–6 по порядку; урок — в конце.

В промпте живёт то, что нужно на каждом ходе и меняется редко: роль и мандат, граница проекта, правила домена с причинами, граница самостоятельности, стандарт доказательности, форма ответа, где лежит канон, блок Второго мозга. Изменчивым фактам место — `STATE.md` и `PLAN.md`, в промпте — указатель. Механика инструментов — в Skills `n8n-engineering-manual`, `google-drive-docs`, `second-brain-git`: промпт называет Skill и момент чтения. Правила домена без другого носителя (канон проекта ссылается на промпт как на место правил) — в промпте строка «правила X живут только здесь: правка промпта = правка правил», в отчёте Андрею — предложение завести им второй носитель.

Шаг 1. Собрать материал до первой строки:
1. Получить старый промпт целиком и проверить, что он целый: признак обрыва — нет закрывающей строки, нет раздела, на который ссылается текст или канон проекта, нет конца истории версий.
2. Прочитать канон проекта: `STATE.md`, `PLAN.md`, оглавление `LOG.md` и записи, меняющие рамку (решения последних дней), `NOT_TAKEN.md`.
3. Сверить с живым объектом то, что промпт утверждает о системе: снимок `registry/n8n-map.md` (состав, расписания, часовые пояса, errorWorkflow, неопубликованные черновики), реестр проектов, живые ID. Все ID, которые останутся в промпте, сверить с `registry/tools.md` и снимком.
4. Перед советом о структуре носителя (журнал, файлы проекта или лаборатории) — прочитать правило Skill `second-brain-git` об этом типе носителя (для лаборатории — раздел «Лаборатория»), потом советовать.
5. Внешние факты (тарифы, версии платформы, рекомендации по промптам) — поиском, с источником и датой.
6. Предпочтения Андрея — из памяти и из прошлых промптов: формат итогового ответа, «не наращивать приборы наблюдения», «полный текст было → стало», «не спрашивать разрешения внутри согласованного плана», «держать позицию аргументами».

Шаг 2. Каждое утверждение старого промпта — ровно в одну корзину:

| Корзина | Признак | Что делать |
|---|---|---|
| устойчивое правило | меняется раз в месяцы, нужно на каждом ходе | оставить, дописать причину |
| изменчивый факт | статус, число, адрес, расписание | убрать; если в каноне его нет — сначала перенести туда или назвать Андрею |
| устарело или неверно | расходится с каноном или живым объектом | убрать; в отчёт — что, почему, где правда |
| дубль Skill | регламент Второго мозга, механика инструментов | убрать, оставить имя Skill и момент чтения |
| вне границы проекта | принадлежит другому проекту | убрать, одной строкой назвать, где это ведётся |

Знания, которых нет нигде, кроме промпта (формулы, правила домена), отметить отдельно: оставить с пометкой или предложить перенос в `PLAN.md`.

Шаг 3. Писать:
- причина рядом с правилом;
- без нажима (капслок, «ОБЯЗАН», «ЗАПРЕЩЕНО») — обычное «делай так, потому что…»;
- что делать, а не только что нельзя: гипотезу помечать «Гипотеза (не проверена): … Проверить: …»;
- граница самостоятельности по риску: чтение — свободно и параллельно; необратимое и видимое снаружи (публикация, правка живого воркфлоу, запись в книгу, удаление) — после «да»; пакет, одобренный одним разрешением и записанный в каноне, повторного «да» не требует;
- форма ответа по задаче: простой вопрос — одна-три фразы с источником; расследование — проблема → причина → решение → что сделать Андрею → что не проверено; три варианта — только на архитектурных развилках;
- роль с мандатом, а не титулами: «доводи до результата: причина доказана, исправление сделано или выдано точной правкой, находка записана в канон»;
- право спорить — отдельной строкой: позицию держать аргументами до контраргумента Андрея.

Шаг 4. Две копии:
- агентская — английская, разделы в XML-тегах (`<role>`, `<working_mode>`, `<evidence>`, `<answer_format>`, `<sources_of_truth_repo>`, блок Второго мозга последним), компактно; Андрей вставляет её в инструкции Проекта; строка «Always reply in Russian»;
- человеческая — русская, Markdown, те же разделы по смыслу; в шапке — редакция, дата, какую версию заменяет, тег, вес, носитель канона, «при правке менять обе»;
- содержание копий совпадает; термины, которые модель выводит Андрею (ПРОЧИТАНО В ЭТОЙ СЕССИИ, Проблема, Причина), в агентской копии остаются по-русски;
- правка одной копии — тем же действием правка другой; перед выдачей копии сверяются по составу: те же разделы, правила, числа и исключения.

Порядок разделов: 1) роль и мандат (+ тон, + право спорить); 2) предмет и граница проекта; что сейчас сломано и меняет любое решение; 3) правила домена с причинами и приоритетом при конфликте; 4) как работать: самостоятельность, граница «да», безопасная правка, экономия токенов, мелкие правки Андрею; 5) доказательность; 6) форма ответа; 7) источники истины проекта и порядок поиска; 8) блок Второго мозга.

Шаг 5. Проверить до выдачи:
- каждое утверждение о системе сверено с источником этой сессии;
- ни одна строка не говорит о деле как о сделанном, если это открытая задача;
- нет команды без источника данных (например, `!map` без разделов «Связи» в каноне);
- нет противоречия со Skills: промпт не велит читать путём, который Skill запрещает (например, INDEX через Google Drive вместо gdocs-read), не ссылается на замороженный носитель (CORE в Docs, SYS_INDEX), не ищет объект там, где его больше нет, не пересказывает регламент; при правке Skill или переезде носителя копии прежней формулировки ищутся и в зеркале `meta/prompts/` (раздел «Правка Skill: приёмка, зеркало, копии, архив для заливки» этого Skill); найденный устаревший промпт правится по этому методу, Андрею — текстом «было → стало»;
- нет приборов наблюдения без читателя;
- блок Второго мозга проходит раздел «Р3. Валидация мастер-промпта»;
- старый промпт сохранён файлом до вставки.

Шаг 6. Выдать и закрыть:
1. Два файла: английский — вставить, русский — читать.
2. Отчёт Андрею по его формату: что изменилось и почему; противоречия и устаревшие места с объяснением, решение по каждому — за ним; правки отдельных мест — полным текстом «было → стало» с якорем.
3. После вставки: английский текст — в `meta/prompts/<папка>.md` с шапкой (что это, откуда снято, что изменено после вставки); русский — оформленным Google Doc в папку DOCS проекта; закрыть позиции очереди, которые промпт выполнил; любая поправка выданного текста — тем же шагом в зеркало `meta/prompts/<папка>.md`, и Андрею выдаётся строка для интерфейса.

Урок после выдачи: что пошло не так, записывается случаем в журнал своего проекта (журнала нет — задачей в `labs/sys/` по Skill `second-brain-engineer`, раздел «Р16. Работа вне Claude Project и регистрация обязательств»), а метод правится по уроку синтезом по `meta/PROTOCOL_knowledge-synthesis.md`.

Проверка: перед выдачей пройдены все пункты шага 5, Андрею показан отчёт шага 6.2; после вставки обе копии лежат в своих носителях.

### Р2. Эталонный блок Второго мозга в мастер-промпте
Регламент Второго мозга живёт в этом Skill. Мастер-промпт несёт четыре вещи: адрес проекта, триггер старта, слова, которые обязаны вызвать этот Skill, и особенности проекта. Особенность — правило, которого нет в Skill или которое для проекта отличается: своя строка старта, своё значение команды, свой маршрут находки, своё правило записи. Тон, роль, предмет и правила домена — не особенности блока, а остальная часть промпта.

Агентская копия (английская) — блок ставится последним в промпте:
```
<second_brain>
Second Brain project: <ТЕГ>. Canon: <projects/<папка>/ | labs/<папка>/> in repo lyamin-dot/second-brain-canon (weight, status, carrier: registry/projects.md).
The Second Brain regulation lives in Skill second-brain-engineer, not in this prompt. Load that Skill and follow it:
- at session start, before replying to the first message — section Р1 (start);
- when a message starts with !save, !tasks, !priority, !inbox, !review, !status, !digest, !map or «харвест» — section Р8 (commands; !save — section Р7);
- when the conversation produces a new task, idea, question, decision, bug, result or external event — section Р6 (capture);
- before any change to an n8n workflow — section Р10.
Repo reads and writes — Skill second-brain-git. Never run these steps from memory of an earlier session.
Project specifics (override the Skill for this project only): <список или «none»>
</second_brain>
```

Человеческая копия (русская) — тот же блок по смыслу:
```
## Второй мозг
Проект Второго мозга: <ТЕГ>. Канон: <projects/<папка>/ | labs/<папка>/> в репозитории lyamin-dot/second-brain-canon (вес, статус, носитель — registry/projects.md).
Регламент Второго мозга живёт в Skill second-brain-engineer, а не в этом промпте. Загрузи этот Skill и действуй по нему:
- на старте сессии, до ответа на первое сообщение, — раздел Р1 (старт);
- когда сообщение начинается с !save, !tasks, !priority, !inbox, !review, !status, !digest, !map или «харвест», — раздел Р8 (команды; !save — раздел Р7);
- когда в разговоре появляется новая задача, идея, вопрос, решение, баг, результат или внешнее событие, — раздел Р6 (захват);
- перед любым изменением воркфлоу n8n — раздел Р10.
Чтение и запись репозитория — Skill second-brain-git. Не исполняй эти шаги по памяти прошлых сессий.
Особенности проекта (меняют правила Skill только для этого проекта): <список или «нет»>
```

Docs-проект (изолированный контур) получает тот же блок; в строке канона вместо папки — «Google Doc <ИМЯ>_INDEX, ID — registry/documents.md».

Проверка: блок прошёл раздел «Р3. Валидация мастер-промпта».

### Р3. Валидация мастер-промпта
Перед выдачей любого мастер-промпта или его блока Второго мозга Андрею — все пункты:
- Тег — как в весах `registry/projects.md`; носитель и папка совпадают со строкой проекта в реестре.
- Блок называет Skill second-brain-engineer и четыре триггера: старт (Р1), слова-команды (Р8, все девять слов), захват (Р6), изменение воркфлоу (Р10).
- Регламент Второго мозга в промпте не пересказан: нет формата строки старта, маршрута !save, таблицы команд, формата захвата, порядка записи.
- Особенности проекта — только то, чего в Skill нет или что для проекта отличается; каждая — одна строка с причиной.
- Docs-ID CORE и ID замороженных документов как источников состояния отсутствуют.
- Тон и роль — в проектной части промпта: неформально, на «ты», с иронией.

Проверка: чеклист показан Андрею вместе с промптом, каждый пункт отмечен.

### Р20. Гигиена каталога Skill и правило в код (16)
Триггер: планируется новый Skill; готовится правка Skill (синтез по `meta/PROTOCOL_knowledge-synthesis.md`, правка харвеста, позиция очереди); ревизия каталога (харвест, любое «не завести ли отдельный Skill»); повтор правила после внесения.
1. Правило, которое может исполнить инструмент (проверка в узле воркфлоу, отказ в коде, замок в Канале), переносят в код, а текст правила тем же действием убирают из Skill, протокола и промпта, оставляя строку-указатель на код, если без неё сессия сделает лишнее действие. Частный случай в n8n — Skill `n8n-engineering-manual`, «Стоп-правила», раздел «Неизвестное значение» (запрет записи — только в коде узла).
2. Цель — ноль неразобранных пересечений областей `description` между Skills, а не число Skills.
3. Рабочий вопрос при новом Skill или ревизии: «с каким существующим Skill пересекается это описание, и как сессия и Андрей различат триггер одного от триггера другого». Разрешённое пересечение без слияния: `second-brain-engineer` и `second-brain-git` — разделение по носителю и по вопросу («что и когда» — здесь, «как физически» — там).
4. Массовая правка описаний: единый каркас полей (что делает, когда читать, чего не делает) допустим; каждое описание называет свои слова-триггеры своими словами, каждый Skill — своим стилем.
5. Слова-триггеры описания покрывают и вопрос без действия — диагностику, на которую Андрей правки не просит («почему ноль», «отработал зелёным, а данных нет»).
6. Поведение после правки описаний принимается по Skill `denken`, раздел «Проверка, которая не может соврать», буква г: вопросы теста составляет не автор описаний, тест — в живом чате проекта.
7. Skill держит инструкции, нужные любой сессии любого проекта. Носитель особенностей объекта — канон проекта или лаборатории (STATE.md, PLAN.md, INDEX), паспорт воркфлоу, реестр `registry/` или файл кейсов `meta/CASES_*.md`; в Skill — не более указателя. Свойство платформы или внешнего инструмента, верное для любого экземпляра (движок n8n, Google Sheets, Telegram, git), особенностью не является и идёт в Skill; поведение API маркетплейса (Wildberries, Ozon) — в файл кейсов своего маркетплейса.
8. Каждая проверка, условие и счётчик в правке Skill называют то, что среда отдаёт: инструмент, который отдаёт поле; шаблон, где есть эти поля; журнал, по которому считает счётчик. Чего среда не даёт — переписать другим средством (другим инструментом; вопросом харвеста вместо счётчика) или назвать неисполнимым вслух.
9. Новое правило называет триггер и момент действия; они определяют место (Skill `denken`, раздел «Р19. Метод проектирования», пункт 3, ворота 2).

Проверка: карта каталога `meta/SKILLS_MAP.md` (шаг К1 `meta/PROTOCOL_knowledge-synthesis.md`) называет число неразобранных пересечений description — «ноль» либо список; правка Skill не называет особенностей конкретного объекта, кроме указателя на носитель; у каждой проверки и условия правки назван инструмент, шаблон или журнал.

### Правка Skill: приёмка, зеркало, копии, архив для заливки
Канон Skills — живой Skill в аккаунте владельца (Customize → Skills); правит его владелец; сессия видит снимок в `/mnt/skills/plugins/<имя>/` и только читает. Зеркало `skills/<имя>/` — резервная копия и единственная история версий; расхождение зеркала с живым — «зеркало отстало». Когда правка вступает в силу и кто заливает — Skill `second-brain-engineer`, раздел «Р13. Права доступа».

Любая работа по тексту Skills (черновик правки, замер размеров, список «предлагаю снять», сборка архива) читает живой Skill и начинается со сверки зеркала с ним в той же сессии (команда шага 2(а)); стоп по сверке — только перед обновлением зеркала и заливкой; расхождение называется в работе; в среде без клона называется, что сверка не выполнена.

Правка, которую внёс владелец, закрывается четырьмя шагами одной сессии по порядку; пропущенный шаг называется в отчёте.

Шаг 1. Приёмка по объекту — чтением снимка Skill (`/mnt/skills/`) в той сессии, которая на правку опирается, по якорю или побайтово: новый текст по якорям правки на месте, старых формулировок нет. Тем же шагом: каждая открытая позиция Очереди, в тексте которой названо имя принятого Skill, проверяется по снимку; та, чьё содержание теперь стоит в живом Skill, получает новое слово статуса (каждая часть отдельно); принят синтез — строка Skill в разделе «Ход прохода» `meta/SKILLS_MAP.md` получает новый статус. Общее правило — Skill `second-brain-engineer`, раздел «Р6. Захват» («Исполненная работа закрывает запись»).

Шаг 2. Обновление зеркала.
(а) Сверка в обе стороны по каждому файлу: `diff -rq skills/<имя> /mnt/skills/plugins/<имя>`. В зеркале есть файл или текст, которого нет в живом, — стоп и вопрос владельцу.
(б) Поиск признаков классов 1–4 (Skill `second-brain-git`, «Стоп-правила», раздел «Носитель и данные») в живом Skill: `grep -rnE '@|/webhook/|Bearer|credential' /mnt/skills/plugins/<имя>`, каждая находка читается глазами; находка класса — стоп, владелец убирает значение из живого Skill, зеркало пишется после.
(в) Файлы живого Skill копируются в `skills/<имя>/` командой (`cp`), маршрутом (б) Skill `second-brain-git` (раздел «Маршрут доставки в main»), в среде, где прошёл `git push --dry-run`.
(г) Приёмка: после коммита и свежего fetch `diff -rq` этой папки пуст.
(д) Среда без открытого push: обновление называется в отчёте и ложится позицией в Очередь.

Шаг 3. Поиск копий старой формулировки (в других Skills, `meta/`, STATE.md и PLAN.md проектов, `meta/prompts/`):
(а) из каждого заменённого фрагмента (БЫЛО) — одна характерная фраза из пяти–восьми слов в пределах одной строки;
(б) `git fetch && grep -rnF '<фраза>' <клон> /mnt/skills/plugins` (ключ -F: русские буквы работают без настроенной локали);
(в) шаг идёт после шага 2: находка в `skills/` — копия в другом Skill, не прежняя версия этого;
(г) каждая находка тем же действием правится (файл repo — по правилам записи; другой Skill или живой мастер-промпт — текстом «было → стало» владельцу и позицией в Очереди) либо названа в отчёте с причиной, почему не копия (запись журнала не правится);
(д) в отчёте по каждой фразе — фраза, число находок, что сделано; ноль находок — явно;
(е) живой текст мастер-промптов поиску недоступен — ищется зеркало `meta/prompts/`; находка там означает, что живой промпт, скорее всего, несёт ту же копию;
(ж) среда без клона шаг не исполняет: называет невыполненным, позиция в Очередь;
(з) тот же поиск по имени, ID и пути — при заморозке или переносе носителя (Skill `second-brain-git`, файл `references/redkie-operacii.md`, раздел «Заморозка носителя»).
Общее правило «копии ищут и снимают тем же действием» — Skill `denken`, раздел «Р19. Метод проектирования».

Шаг 4. Сборка и сверка перед заливкой. Архив заменяет живой Skill целиком.
(а) Архив собирается непосредственно перед выдачей, после свежего `git fetch`: от живого Skill (или зеркала, сверенного с ним в этой сессии) плюс все выданные владельцу и не залитые правки этого Skill — правки позиций Очереди, ждущих его заливки или внесения (кроме обусловленных ещё не наступившим событием), и правки наборов, выданных другими сессиями; правки накладываются скриптом с проверкой, что прежний текст найден ровно один раз.
(б) В ответе с архивом и в статусах позиций, которые он несёт, названы прежние наборы того же Skill, которые теперь не заливать, — с датой и сессией.
(в) Перед заливкой зеркало сверяется с живым в обе стороны по каждому файлу, расхождение переносится в отстающий носитель до заливки; SKILL.md из архива сравнивается с собранным текстом побайтно.
(г) Длина description: `python3 -c "import sys,yaml;t=open(sys.argv[1],encoding='utf-8').read();print(len(yaml.safe_load(t.split('---')[1])['description']))" <клон>/skills/<имя>/SKILL.md` — не больше 1024 (разбор YAML, не поиск строки).

## Ловушки
- Архив Skill при заливке заменяет живой Skill целиком: всего, чего в архиве нет, в живом Skill не станет — без ошибки и предупреждения.
- Customize отказывает в заливке, если description длиннее 1024 знаков; описание блоком «|» или «>» поиском строки считается одним знаком и проходит проверку ложно — считай разбором YAML.
- Кнопка Save skill в Cowork у многофайлового Skill молча заменяет только SKILL.md, файлы references/ остаются прежними — заливка только zip через Customize → Skills.
- Текст мастер-промпта живёт только в интерфейсе Anthropic: инструментом не читается и не откатывается — старый текст сохранять файлом до вставки.
- Drive и вставка в чат молча режут хвост старого мастер-промпта — проверять закрывающую строку, разделы, на которые ссылается текст, конец истории версий.
